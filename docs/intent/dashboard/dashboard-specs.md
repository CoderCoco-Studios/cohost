# dashboard specs

Prefix `DASH`. Design: [dashboard-design.md](dashboard-design.md). Verified against the code at git `49ba935` (audit pass 2026-11-01); owner decisions of 2026-11-01 applied at git `1b57790`. The UI specs (`DASH-UI`, `DASH-VIEWERS-010` to `-023`, `DASH-ACC`, `DASH-NAV`, `DASH-THEME`, `DASH-A11Y`, `DASH-SET`, `DASH-BUILD`) and the secret and pick-list routes (`DASH-SECRET`, `DASH-OPT`) describe the React UI of the design's The UI section, and a spec marked `[x]` is exercised by the test it names, under `services/dashboard/test/ui/` for a UI spec. "The page" means that UI as loaded in a browser. A spec that needs real layout is worded as a rule the stylesheet holds or a class or attribute the markup carries, and the visual claim is a named check of the design's Manual verification. "Secret" means a configuration key the config package marks secret (MOD-CFG-002). "Control token" is `CONTROL_TOKEN`. Markers: `[x]` implemented, `[ ]` intended but not yet implemented (gap), `[D]` deferred. `<!-- test: -->` names the test file that exercises the spec; `<!-- openspec: -->` names the retired OpenSpec requirement the line descends from (the LID line wins where they differ). DASH-CTRL-006 is retired; the number is not reused.

## HTTP routes

- [x] **DASH-HTTP-001**: When `GET /` is requested, the dashboard shall respond 200 `text/html; charset=utf-8` with `cache-control: no-cache` and the built UI's `index.html`, read on that request (DASH-BUILD-005), with every occurrence of `__COHOST_NAME__` replaced by `cohost.name` with `&`, `<`, `>`, `"` and `'` escaped as HTML entities. <!-- openspec: dashboard § Page and health --> <!-- test: services/dashboard/test/routes.test.ts, services/dashboard/test/static.test.ts -->
- [x] **DASH-HTTP-002**: When `/health` is requested with any method that no earlier route handles, the dashboard shall respond 200 `ok`. <!-- openspec: dashboard § Page and health --> <!-- test: services/dashboard/test/routes.test.ts -->
- [x] **DASH-HTTP-003**: If a request matches no route, then the dashboard shall respond 404 `not found`. <!-- openspec: dashboard § Page and health --> <!-- test: services/dashboard/test/routes.test.ts -->
- [x] **DASH-HTTP-004**: If an HTTP handler throws (for example invalid JSON on `POST /control` or `POST /sink`, a payload the event schema rejects, a request URL that does not parse, or a failed upstream audio fetch), then the dashboard shall log `request failed` and respond 500 with the error text without exiting. <!-- openspec: dashboard § Error handling --> The audio proxy shall read the whole upstream body before it chooses the status and writes headers, so a failed body read is still answered 500; an error response is never attempted once headers have been sent, and no handler failure becomes an unhandled rejection. <!-- test: services/dashboard/test/routes.test.ts, services/dashboard/test/routes.test.ts -->
- [x] **DASH-HTTP-005**: When `GET /personality` is requested, the dashboard shall respond with the personality file text as `text/plain`. <!-- openspec: dashboard § Personality editing --> <!-- test: services/dashboard/test/routes.test.ts -->
- [x] **DASH-HTTP-006**: When `PUT /personality` is requested, the dashboard shall save the request body as the personality file, publish `control {cmd: "reload_personality"}` and respond 204. <!-- openspec: dashboard § Personality editing --> <!-- test: services/dashboard/test/routes.test.ts -->
- [x] **DASH-HTTP-007**: When `POST /control` carries `{cmd, text?, target?, route?}`, the dashboard shall publish a `control` event with those fields (`route` as DASH-HTTP-017) and respond 204; a `cmd` outside the event schema (`mute`, `unmute`, `say`, `forget_context`, `reload_personality`, `pause`, `resume`, `set_routing`) shall be answered 500 and nothing published. <!-- openspec: dashboard § Control commands --> <!-- test: services/dashboard/test/routes.test.ts, services/dashboard/test/routes.test.ts -->
- [x] **DASH-HTTP-008**: When `POST /control` carries `{cmd: "pause" | "resume", target}`, the dashboard shall publish the targeted `control` event; the web page's Pause and Resume buttons (MOD-PAUSE-001) post to it. <!-- openspec: dashboard § Control commands --> <!-- test: services/dashboard/test/control.test.ts -->
- [x] **DASH-HTTP-009**: The dashboard shall listen with its full surface on the port `dashboard.port` of `config.yaml` (default 3000) and shall read no environment variable for it, and shall publish its `ready` heartbeat only once both the full-surface listener and the LAN listener (DASH-HOST-001) are listening; the full-surface bind address is DASH-CTRL-001 and DASH-CTRL-003. <!-- openspec: dashboard § (add-service-health) Heartbeat --> <!-- test: services/dashboard/test/host.test.ts, services/dashboard/test/host.test.ts --> <!-- test: services/dashboard/test/service.test.ts -->
- [x] **DASH-HTTP-010**: When the dashboard shuts down gracefully, it shall stop the feed's staleness tick and the stack probe, close the WebSocket server and both HTTP listeners, and stop the bus, without stopping or changing any Compose container and without waiting for or killing a `docker compose` command a running stack action started. <!-- test: services/dashboard/test/host.test.ts -->
- [x] **DASH-HTTP-011**: If the body of `POST /control`, `PUT /personality`, `POST /sink`, `POST /mouth/routing` or `POST /services/:id/(start|stop|restart)` exceeds 64 KiB, then the dashboard shall respond 413 and shall publish, save and run nothing. <!-- test: services/dashboard/test/control.test.ts, services/dashboard/test/routes.test.ts -->
- [x] **DASH-HTTP-012**: If the feed's health seed fails because Redis is unreachable, then the dashboard shall log a warning, keep serving every route, and retry the seed with the bus backoff (250 ms, doubling per consecutive failure, capped at 30 s) until it succeeds, without exiting; if a client's connect replay fails, it shall log the error and keep that socket open without the replay, so the client still receives the `services` and `stack` snapshots and every later push. <!-- test: services/dashboard/test/feed.test.ts, services/dashboard/test/feed.test.ts, services/dashboard/test/feed.test.ts, services/dashboard/test/feed.test.ts -->
- [x] **DASH-HTTP-013**: If the service id in `POST /services/:id/(start|stop|restart)` contains a malformed `%` escape, then the dashboard shall respond 404 as for an unknown service. <!-- test: services/dashboard/test/control.test.ts -->
- [x] **DASH-HTTP-014**: When `GET /services/manifest` is requested, the dashboard shall answer `200` JSON `{units}` with one `{id, config, uses, requires, pause, test, infra, defaultMode}` per control-plane manifest unit (sixteen, including the `discord` connector, CTRL-MANIFEST-001), in manifest order, ungated, and with no compose name, pnpm filter or environment preset (module-contract MOD-MAN-007). <!-- test: services/dashboard/test/stack-rebuild.test.ts -->
- [x] **DASH-HTTP-015**: The dashboard shall read every request body through one reader that keeps at most the route's cap and, past it, drains and discards the rest and reports the body as too large; the JSON and text routes cap at 64 KiB. <!-- test: services/dashboard/test/body.test.ts -->
- [x] **DASH-HTTP-016**: The dashboard's entry file shall start the service through the shared bootstrap `runService` (shared-runtime SHARED-BOOT-001), which owns its configuration load, bus, heartbeat and shutdown hook, and the entry shall build none of them itself; the heartbeat becomes `ready` from the service's main once both listeners listen, and the teardown step registered with the bootstrap stops the feed and the stack probe and closes both listeners (DASH-HTTP-010). If the configuration does not load or startup throws (a bad control configuration, DASH-CTRL-002), the process exits with status 1. <!-- test: services/dashboard/test/service.test.ts, packages/control/test/derived-lists.test.ts -->
- [x] **DASH-HTTP-017**: When `POST /control` carries a `route` (an array of mouth output ids), the dashboard shall publish it unchanged on the `control` event, and when `POST /inject/event` carries a `brain.say` whose `data` has a `route`, it shall publish it unchanged on the `brain.say`; a body without `route` shall publish no `route`, and a `route` that is not an array of strings shall be refused by the event schema (400 for `/inject/event`; for `/control`, a failure as in DASH-HTTP-004). <!-- test: services/dashboard/test/routes.test.ts --> <!-- test: services/dashboard/test/inject-event.test.ts -->

## Audio proxy and sink

- [x] **DASH-SINK-001**: When `GET /audio/<path>` is requested, the dashboard shall fetch `<urls.voice()>/audio/<path>` and return the upstream status and content-type (default `audio/wav`) with `cache-control: no-store`. <!-- openspec: dashboard § Audio sink --> <!-- test: services/dashboard/test/routes.test.ts -->
- [x] **DASH-SINK-002**: When `POST /sink` carries `{event: "playing", id}`, the dashboard shall publish `voice.playing {id, sink: "dashboard"}`; when it carries `{event: "done", id}`, it shall publish `voice.done {id, sink: "dashboard"}`; in both cases it shall respond 204. <!-- openspec: dashboard § Audio sink --> <!-- test: services/dashboard/test/routes.test.ts -->
- [x] **DASH-SINK-003**: If `POST /sink` carries an `event` other than `playing` or `done`, then the dashboard shall respond 400 and publish nothing. <!-- openspec: dashboard § Audio sink --> <!-- test: services/dashboard/test/routes.test.ts -->
- [x] **DASH-SINK-004**: When `VOICE_URL` is not set, the dashboard shall proxy audio from voice's loopback address `http://127.0.0.1:<VOICE_PORT>` (port default 8700), as resolved by `urls.voice()`. <!-- openspec: dashboard § Audio sink --> <!-- test: packages/config/test/config.test.ts -->

## WebSocket feed

- [x] **DASH-FEED-001**: When a client connects to `/ws`, the dashboard shall first send a `{type: "services", services}` snapshot, then the `{type: "stack"}` snapshot (DASH-FEED-008), and then the 60 most recent bus events, oldest first, each marked `replay: true`, skipping any `service.heartbeat` and the viewer-notes events of DASH-FEED-007. <!-- openspec: dashboard § Live event feed --> A live event that arrives while the replay is being read shall reach that client once, after the replay (not at all if the replay already contained it), and shall carry no `replay` marker; clients that are not replaying receive it immediately. <!-- test: services/dashboard/test/feed.test.ts, services/dashboard/test/feed.test.ts, services/dashboard/test/feed.test.ts, services/dashboard/test/feed.test.ts, services/dashboard/test/feed.test.ts, services/dashboard/test/feed.test.ts, services/dashboard/test/feed.test.ts -->
- [x] **DASH-FEED-002**: While the dashboard is running, it shall forward every new event on the main bus stream, unfiltered by type except for `service.heartbeat` and the viewer-notes events of DASH-FEED-007, as JSON to every connected client whose socket is OPEN. <!-- openspec: dashboard § Live event feed --> <!-- test: services/dashboard/test/feed.test.ts, services/dashboard/test/feed.test.ts, services/dashboard/test/feed.test.ts -->
- [x] **DASH-FEED-003**: When the dashboard starts its feed, it shall seed the health tracker from the 500 most recent heartbeats and follow the health stream from the last seen id. <!-- test: services/dashboard/test/feed.test.ts -->
- [x] **DASH-FEED-004**: When the tracker's derived service state changes, the dashboard shall push a `services` message to connected clients; identical repeated heartbeats shall not cause a push. <!-- test: services/dashboard/test/feed.test.ts -->
- [x] **DASH-FEED-005**: While the dashboard is running, it shall re-evaluate heartbeat staleness every 1000 ms and push the result to connected clients when a state changes. <!-- test: services/dashboard/test/feed.test.ts -->
- [x] **DASH-FEED-006**: When `GET /services` is requested, the dashboard shall respond 200 JSON `{services}` listing every known service with its derived state (`unknown` for services never seen). <!-- test: services/dashboard/test/routes.test.ts -->
- [x] **DASH-FEED-008**: When a client connects to `/ws`, the dashboard shall send it a `{type: "stack", ...}` message carrying the `GET /stack` body (DASH-STACK-001) after the `services` snapshot and before the event replay, also when the replay cannot be read; while running, it shall push such a message to every OPEN client whenever the stack state, Docker reachability, any container's status, health, restart count or overrides, the running action or its phase, `last`, or bus reachability changes (containers compared by service name, ignoring the order Compose lists them in), and at no other time. <!-- test: services/dashboard/test/feed.test.ts, services/dashboard/test/feed.test.ts, services/dashboard/test/stack.test.ts -->
- [x] **DASH-FEED-009**: The dashboard shall report the bus as `unreachable` from the first failed health seed or tail read until the next read that completes without an error (an empty blocking read counts), and as `connected` otherwise. <!-- test: services/dashboard/test/feed.test.ts, services/dashboard/test/feed.test.ts -->
- [x] **DASH-FEED-010**: Where the Compose status probe carries container restart counts, every `services` snapshot the dashboard sends (the `/ws` `services` message and `GET /services`) shall pass through control-plane `withContainerRestarts` (CTRL-HEALTH-010), so a service that never published a heartbeat but whose container keeps restarting shows `crash-looping` and its `containerRestarts`; the dashboard shall send a fresh `services` message whenever the stack snapshot changes. <!-- test: services/dashboard/test/stack-rebuild.test.ts -->
- [x] **DASH-FEED-007**: The dashboard shall never send `memory.notes.request`, `memory.notes.reply`, `memory.viewers.request` or `memory.viewers.reply` events to a `/ws` client, neither live nor in the connect replay, because they carry viewer-note text. <!-- test: services/dashboard/test/feed.test.ts, services/dashboard/test/feed.test.ts -->

## Control gating

- [x] **DASH-CTRL-001**: Where `CONTROL_ENABLED` is not `1`, the dashboard shall not require a bearer token on any route except the `/viewers` routes (DASH-VIEWERS-007), `PUT /secrets/:path` (DASH-SECRET-003) and a `PUT /config/:section` that changes a sensitive key (DASH-CTRL-009), shall answer `POST /services/:id/(start|stop|restart)` and every `POST /stack/*` route with 404, and shall report `{enabled: false}` from `GET /services/control`; its full-surface address is DASH-CTRL-003 and DASH-HOST-007. <!-- openspec: dashboard § (add-service-control) Service lifecycle routes --> <!-- test: services/dashboard/test/control.test.ts, services/dashboard/test/inject.test.ts, services/dashboard/test/stack.test.ts, services/dashboard/test/secrets.test.ts, services/dashboard/test/sensitive.test.ts -->
- [x] **DASH-CTRL-002**: If `CONTROL_ENABLED=1` and `CONTROL_TOKEN` is empty or unset, then the dashboard shall fail startup with an error naming `CONTROL_TOKEN`. <!-- test: services/dashboard/test/control.test.ts -->
- [x] **DASH-CTRL-003**: The dashboard shall bind its full surface to `DASHBOARD_HOST` when set and non-empty, else to `127.0.0.1`, in both control modes, and shall log a warning when that address is not loopback because the tokens travel in cleartext over plain HTTP. <!-- test: services/dashboard/test/control.test.ts -->
- [x] **DASH-CTRL-004**: Where `CONTROL_ENABLED=1`, the dashboard shall require `Authorization: Bearer <CONTROL_TOKEN>`, compared in constant time, on `POST /control`, `PUT /personality`, `PUT /config/:section`, `POST /mouth/routing`, `POST /inject/text`, `POST /inject/image`, `POST /inject/audio`, `POST /inject/event`, `POST /services/:id/(start|stop|restart)` and `POST /stack/(launch|stop|restart|consolidate|rebuild)`, responding 401 with `www-authenticate: Bearer` and performing no action otherwise. <!-- openspec: dashboard § (add-service-control) Bearer token on mutating routes --> <!-- openspec: dashboard § (add-test-injection) Injection gating --> <!-- test: services/dashboard/test/control.test.ts, services/dashboard/test/control.test.ts, services/dashboard/test/inject.test.ts, services/dashboard/test/stack.test.ts -->
- [x] **DASH-CTRL-005**: Where `CONTROL_ENABLED=1`, the dashboard shall leave `GET /services/control`, `GET /services`, `GET /services/manifest`, `GET /stack`, `GET /personality`, `GET /config/schema`, `GET /config/:section`, `GET /options/voices`, `GET /options/models`, `GET /audio/*`, `POST /sink`, `/health`, the `/ws` feed, `GET /`, `GET /assets/*`, `GET /favicon.svg` and every docs request (DASH-DOCS-001) unauthenticated: control mode guards mutations only (the secret write and a config change to a sensitive key excepted, DASH-SECRET-003, DASH-CTRL-009), and an OBS Browser Source sink page, which cannot present a token, needs `/ws`, `/audio/*`, `POST /sink` and the UI's files. <!-- test: services/dashboard/test/control.test.ts, services/dashboard/test/stack.test.ts, services/dashboard/test/host.test.ts --> <!-- impl: services/dashboard/src/routes.ts -->
- [x] **DASH-CTRL-007**: Where `CONTROL_ENABLED=1`, `GET /services/control` shall respond 200 JSON `{enabled: true, runtime, advanced}`, where `runtime` is always `compose` (the only runtime) and `advanced` is true only when `CONTROL_ADVANCED=1`. <!-- openspec: dashboard § (add-service-control) Service control UI --> <!-- test: services/dashboard/test/control.test.ts, services/dashboard/test/control.test.ts -->
- [x] **DASH-CTRL-008**: Where `CONTROL_ENABLED=1` and `CONTROL_ADVANCED=1`, the dashboard shall log a startup warning that redis and postgres can be stopped from the dashboard. <!-- test: services/dashboard/test/control.test.ts -->
- [x] **DASH-CTRL-009**: In both control modes, a `PUT /config/:section` without `?dryRun=1` whose `values` change a sensitive key (a key the presentation table marks `sensitive`, CFG-PRES-011; a key is changed when its value in `values` differs from its effective value in `config.yaml` as it is now) shall require `Authorization: Bearer <CONTROL_TOKEN>`, compared in constant time, and shall answer 401 with `www-authenticate: Bearer` and `{ok: false, detail, sensitive: [<dotted paths of the changed sensitive keys>]}` and write nothing otherwise; the check runs after the Host and Origin checks and the body's size and shape and before the etag is compared or any value is validated; a save that changes no sensitive key is gated as DASH-CTRL-004 states, and a dry run is never gated by this rule. <!-- test: services/dashboard/test/settings.test.ts, services/dashboard/test/sensitive.test.ts -->
- [x] **DASH-CTRL-010**: If a `PUT /config/:section` that changes a sensitive key (DASH-CTRL-009) arrives while no control token is configured (control mode off and `CONTROL_TOKEN` unset), then the dashboard shall answer 403 `{ok: false, detail, sensitive}` with a detail naming `CONTROL_TOKEN` and `CONTROL_ENABLED` and write nothing. <!-- test: services/dashboard/test/settings.test.ts, services/dashboard/test/sensitive.test.ts -->

## Service lifecycle

- [x] **DASH-SVC-001**: Where `CONTROL_ENABLED=1`, when an authorized `POST /services/:id/(start|stop|restart)` arrives, the dashboard shall delegate to the service controller, publish a `service.lifecycle` audit record with `by: "dashboard"`, and respond 200 `{ok, detail?}`. <!-- openspec: dashboard § (add-service-control) Service lifecycle routes --> <!-- test: services/dashboard/test/control.test.ts -->
- [x] **DASH-SVC-002**: When the lifecycle request body is empty, the dashboard shall treat it as `{}`; when it is not a JSON object, or `mode` is not `resume` or `fresh`, or `isolated` is not a boolean, it shall respond 400 and run nothing; only `mode` and `isolated` are read. <!-- openspec: dashboard § (add-service-control) Service lifecycle routes --> <!-- test: services/dashboard/test/control.test.ts, services/dashboard/test/control.test.ts -->
- [x] **DASH-SVC-003**: When the controller refuses a lifecycle request, the dashboard shall respond 404 for an unknown service (including `dashboard`, which is not a manifest unit) and 403 for a forbidden target (infrastructure without `CONTROL_ADVANCED=1`), each with `{ok: false, detail}`. <!-- openspec: dashboard § (add-service-control) Service lifecycle routes --> <!-- test: services/dashboard/test/control.test.ts, services/dashboard/test/control.test.ts -->
- [x] **DASH-SVC-004**: If publishing the `service.lifecycle` audit record fails, then the dashboard shall log a warning and still answer the lifecycle request normally. <!-- test: services/dashboard/test/control.test.ts -->

## Upload store (Redis)

- [x] **DASH-UPL-001**: The dashboard shall enforce a per-kind upload size cap before it stores anything: `dashboard.inject.max_image_bytes` for an image (default 8 MiB) and `dashboard.inject.max_audio_bytes` for audio (default 25 MiB), each read from `config.yaml` at start and validated there (CFG-SCH-038), with no environment variable involved. <!-- test: services/dashboard/test/uploads.test.ts -->
- [x] **DASH-UPL-002**: The dashboard shall store each accepted upload with `Bus.putUpload` under the key `cohost:upload:<id>` and an expiry of `dashboard.inject.ttl_ms` (default 300000 ms, 5 minutes; read from `config.yaml` at start and validated there, CFG-SCH-038), so an upload nobody reads disappears by itself. <!-- test: services/dashboard/test/uploads.test.ts, services/dashboard/test/inject.test.ts -->
- [x] **DASH-UPL-003**: If writing an upload to Redis fails, then the dashboard shall respond 503 `upload store unavailable` and publish no `inject.request`.
