# deployment

Parent: [high-level-design](../../high-level-design.md). Specs: [deployment-specs.md](deployment-specs.md).

The retired OpenSpec baseline (`openspec/specs/`, 17 capabilities, one per package or service plus `service-control` and `service-health`) has no capability for Compose, the Dockerfile, the installer, CI, the docs site or licensing. Everything below is written from the files.

## Context and Design Philosophy

The segment is everything that turns the repository into a running stack or a published artifact: the Compose topology (every service except the dashboard), the host start script for the dashboard, the one Dockerfile, the Linux installer, the CI workflows, the VitePress docs site, the workspace and TypeScript build setup, and the licensing and contribution rules. It owns no runtime behaviour of cohost itself; it wires the other segments together and checks that they start.

The installer, the docs site and the examples serve the owner's own stream; packaging cohost for other streamers is not a goal. A defect in the installer or the docs is still a bug and is fixed with the same weight as a runtime defect, and the installer fails loudly rather than leaving a half-working stack: it aborts on a lockfile mismatch, on a failed smoke probe, and after a fresh Docker install that needs a re-login.

Describes the intended design and the files that realize it; where the files lag, the text says so and names the gap spec.

Philosophy, with the evidence for each:

- **One image, many services.** Every TypeScript service is built from the same Dockerfile and differs only by a build argument; the whole workspace is compiled once per image (`Dockerfile:1-2`).
- **Compose publishes on loopback only; the host-run dashboard is the only LAN door.** Redis, Postgres, Ollama, TTS and STT are published on `127.0.0.1` "for `pnpm dev` outside docker" (`docker-compose.yml:55`, same pattern at `:70,81,112,118`), and voice on `127.0.0.1:8700` for the host-run dashboard. The dashboard is not a Compose service: the owner starts it on the host (`pnpm dashboard`), it launches the stack, and its LAN listener is what OBS on another machine loads the sink page from (dashboard LLD, Host process and stack control).
- **The dashboard is started first.** Nothing has to be running for it to start; its Launch button runs `docker compose up -d --build --remove-orphans` through the control plane, so a plain `docker compose up -d` is the same stack the button brings up.
- **CPU by default, GPU as an overlay.** The base file is CPU-only and the GPU is layered on by a second file that `install.sh` selects through `COMPOSE_FILE` (`docker-compose.yml:1-2`, `docker-compose.gpu.yml:1-4`).
- **chat keeps its refreshed Twitch token on the host.** `./data/chat` is mounted at `/app/data/chat` on `chat` only (DEPLOY-COMPOSE-022): Twitch rotates refresh tokens, so a token persisted in the container's own filesystem would be lost when the container is recreated (Rebuild, `docker compose down`) and the stale `.env` token would no longer refresh. Every other service's generated files (clip caches) are cheap to regenerate and stay in the container.
- **Config is bind-mounted, not baked.** `./config` is mounted at `/app/config` and `CONFIG_DIR` points at it (`docker-compose.yml:20,32-33`, `Dockerfile:22`), so the config segment's seeding writes real files on the host.
- **Optional pieces behind profiles.** `eyes`, `ears` and `mouth` are Compose profiles (`docker-compose.yml:6-7,170,175`; README.md:58-63 "Add the optional pieces when you're ready").
- **Docs have one source of truth.** The README and `examples/*/README.md` are generated into the docs site rather than copied by hand (`scripts/docs-prepare.mjs:1-4`).
- **Process rules checked where a machine can check them.** The Contributor License Agreement (`CLA.md`, required by `CONTRIBUTING.md`) is enforced in CI on every pull request (DEPLOY-CI-005) and the docs site builds on every pull request (DEPLOY-CI-004); linked-intent development (`CLAUDE.md`, `docs/SPEC-DRIVEN.md`) stays a convention.

Shared settings come from the `x-ts-service` anchor (`:9-46`): `restart: unless-stopped`, `env_file: .env`, in-network service URLs (`REDIS_URL`, `DATABASE_URL`, `OLLAMA_URL`, `TTS_URL`, `STT_URL`, `VOICE_URL`), `CONFIG_DIR=/app/config` and the isolation pass-throughs under `environment:` (which wins over `.env`, so the in-network URLs and `CONFIG_DIR` cannot be changed from `.env`), the `./config:/app/config` volume, `host.docker.internal:host-gateway` (reach OBS or VTube Studio on the host), `depends_on: redis: service_healthy`, and the container healthcheck. Injected test uploads reach `eyes` and `ears` through Redis (dashboard DASH-INJ-005), so the services take no dashboard address and nothing on the host has to be reachable from a container (DEPLOY-COMPOSE-002). The code today pins `CONTROL_ENABLED: "0"` (gap; DEPLOY-COMPOSE-016 is retired). A service that declares its own `depends_on` (memory, cortex, voice, ears) replaces the anchor's map and therefore re-lists `redis`. Nine of the 10 `services/*` directories have a Compose service; `services/dashboard` has none (gap DEPLOY-COMPOSE-001). Every service directory keeps its `tsconfig.json` reference; the 7 `packages/*` are libraries with none.

Because `env_file: .env` applies to every application service, any variable an operator puts in `.env` reaches every container unless the `environment:` block names it. `CONTROL_ENABLED=1` and `CONTROL_TOKEN` in `.env` therefore reach every container too; nothing in a container reads them (only the dashboard and `loadControlConfig` do), so they need no pin.

The reverse direction matters for the control plane's isolated starts: `ComposeRuntime` sets the isolation preset (`CHAT_SOURCE`, `MEMORY_STORE`, `MEMORY_EMBEDDER`, `LLM_PROVIDER`, `VOICE_ENGINE`, `AVATAR_DRIVER`, `VISION_ENABLED`, `EARS_SOURCE`, `MOUTH_DISCORD_ENABLED`) on the `docker compose` process (`packages/control/src/runtime.ts:61`), and those reach a container only if the `environment:` block names them. The `x-ts-service` block passes each through as `${VAR:-}` (`:24-31`), so an unset variable still falls to the `${VAR:-default}` in `config.yaml` (DEPLOY-COMPOSE-017, control-plane CTRL-RUNTIME-009). Compose interpolates `${VAR:-}` from the process environment first and `.env` second, so a value an operator keeps in `.env` (for example `AVATAR_DRIVER=null`) still reaches the container.

**Container healthcheck** (`:39-46`): `node packages/control/dist/healthcheck.js $$SERVICE`, interval 10 s, timeout 5 s, 3 retries, 30 s start period. `SERVICE` is baked into the image (`Dockerfile:20`). The script is in `@cohost/control` (`packages/control/src/healthcheck.ts:10-31`): it reads the last 200 entries of `cohost:health`, takes the newest heartbeat for the named service, and is healthy iff it is not `stopping` and younger than `STALE_FACTOR` (3) times that heartbeat's own `intervalMs`; it self-terminates with exit 1 after 4 s. The healthcheck only reports; no `depends_on` waits for an application service to be healthy, so health gates nothing at startup. Heartbeat semantics belong to control-plane.

**`models`**: `until curl -sf ollama:11434/api/tags; do sleep 2; done`, then for `LLM_MODEL`, `VISION_MODEL`, `EMBED_MODEL` and `NOTES_MODEL` (default `gemma3:4b` when unset or empty, DEPLOY-COMPOSE-008) POSTs `/api/pull` with `curl -fsS` into a temp file and prints its last 200 bytes. A pull fails when curl reports an HTTP error or the response holds an `"error"` line (Ollama reports a pull error that begins after the response started as a 200 with an `{"error":...}` line); the loop still tries the remaining models, then the container exits non-zero (DEPLOY-COMPOSE-011). `NOTES_MODEL` is pulled last and its failure is only a `WARNING` line on stderr: it does not change the exit status, because only viewer-note capture uses it and capture already degrades to writing no notes. It has no restart policy, so the failure stays visible in `docker compose ps`. `memory` and `cortex` stay on `service_started` for `ollama`: both wait for the model backend themselves. It is not profile-gated: it runs on every plain `docker compose up -d`, as do `tts` and `stt`; the only way to start without them is to name services explicitly, as the comment at `:5` shows. It does not pull `STT_MODEL`.

**`consolidate`**: the memory service's one-shot (memory LLD § Viewer notes, `MEM-CONSOL-012`) as a Compose service, so the owner can run a pass after shutting the AI down by any route: `docker compose run --rm consolidate` or `cohostctl consolidate` (control-plane CTRL-CLI-008). It builds the same image as `memory` (`SERVICE: memory`; the layers are shared) and replaces the image's default command with `node services/memory/dist/consolidate.js`. It inherits `x-ts-service` for the env file, `environment`, the `./config` mount and `extra_hosts`; it sets only `depends_on`, `command`, `restart`, `profiles` and `healthcheck`, and none of those hides the anchor's `volumes`. `depends_on` is `postgres` healthy and `ollama` started, restated in full because a service's own `depends_on` replaces the anchor's map; `redis` is left out on purpose, because the entry point reads config, opens the store and calls the consolidator model, and never connects to the bus (`services/memory/src/consolidate.ts`). `docker compose run` starts the listed dependencies if they are down, so a pass works after `docker compose down`; `postgres` and `ollama` then keep running until the next `down`. The anchor's healthcheck asks for a fresh bus heartbeat, which a process that never joins the bus cannot produce, so it is disabled. The service is in the `tools` profile so a plain `docker compose up -d` never starts it (a one-shot started at boot would find nothing dirty and exit, or compete with the memory service's startup); naming it in `docker compose run` runs it without `--profile`. Nothing waits on it: a stack stopped by `down`, Ctrl-C or a dashboard button is caught up by the memory service at its next start (`MEM-CONSOL-013`, `MEM-CONSOL-015`), so a skipped or failed run loses nothing. Like `models` it runs on the stack's Compose project and its network, so it reaches `postgres` and `ollama` by service name.

**Image pins** (DEPLOY-COMPOSE-014): every image carries an exact version tag, looked up in its registry when it was pinned. Redis stays on major 7 and Postgres on 16 (pgvector 0.8.7) although later majors exist, because the `redis-data` and `pg-data` volumes are not portable across majors; moving to a new major is a deliberate migration, not a tag bump. Changing a pin is an edit to the Compose files that CI then exercises.

**GPU overlay**: the `x-gpu` anchor adds an NVIDIA `deploy.resources.reservations.devices` entry (`count: all`) to `ollama`, `tts`, `stt` and swaps the `tts`/`stt` images to the GPU variants (`docker-compose.gpu.yml:6-23`). `KOKORO_IMAGE` / `SPEACHES_IMAGE` override the image in both files, so setting one for a GPU host also changes the base (CPU) file's default image.

**Fallback clips** (gap): voice keeps its generated fallback clips under `/app/data/voice/fallback-clips` and serves them over its HTTP server; mouth fetches them into `/app/data/mouth/fallback-clips` ([voice](../voice/voice-design.md) Fallback Clips, [mouth](../mouth/mouth-design.md) Fallback Line, [config](../config/config-design.md) `dataDir()`). No volume is added and no directory is shared: both live in their container's filesystem. A container restart keeps them; after a recreate voice regenerates in the background (one TTS call per phrase), and mouth re-fetches from voice.

**Voice reachability**: `voice` listens on `VOICE_PORT` (default 8700, `services/voice/src/index.ts:21`) and advertises `urls.voice()` = `http://voice:8700` inside Compose. Compose publishes it on `127.0.0.1:8700` only, because the dashboard runs on the host and proxies `/audio/*` to `urls.voice()`, whose default is `http://127.0.0.1:8700` (DEPLOY-COMPOSE-007). Browsers, OBS and any other player still go through the dashboard proxy, the only supported path for them; in-network sinks such as `ears` fetch `http://voice:8700` directly. A loopback publish also lets `pnpm dev` services on the host reach a containerised voice. The code today publishes nothing (gap).

## Host-run dashboard

The dashboard is not a Compose service (owner decision; dashboard LLD, Host process and stack control). This segment owns how the owner starts it and what a fresh install needs for it:

- **Start script.** The root `package.json` script `dashboard` runs `tsc -b services/dashboard && node services/dashboard/dist/index.js` (DEPLOY-HOST-001). `pnpm` runs root scripts in the repository root, so the dashboard's working directory, and the `docker compose` commands it issues, are the root. `tsc -b` builds the dashboard and the workspace packages it references, incrementally.
- **`.env.example`.** Ships `CONTROL_ENABLED=1`, an empty `CONTROL_TOKEN=` with a comment saying the installer fills it and how to generate one by hand, and `DASHBOARD_LAN_PORT=3001` beside `DASHBOARD_PORT=3000` (DEPLOY-HOST-002). With control enabled and no token the dashboard refuses to start and names `CONTROL_TOKEN` (dashboard DASH-CTRL-002).
- **Installer.** Fills an empty `CONTROL_TOKEN` in `.env` with a generated 48-hex-character secret and never prints it (DEPLOY-INST-013), and its closing instructions say to run `pnpm dashboard`, open the URL and press Launch, instead of `docker compose up -d` (DEPLOY-INST-008).
- **README.** Quick start, Getting the voice onto stream, Two-PC setup and service control describe the host-run dashboard: first run, where the token is, the same-PC sink URL `http://localhost:3000/?sink=1`, the second-PC sink URL `http://<ai-pc>:3001/?sink=1`, and upgrading from a containerised dashboard (`docker compose down --remove-orphans` once, or Launch, which removes the orphan) (DEPLOY-HOST-003).

- **`.env` additions.** `DASHBOARD_HOST=127.0.0.1` (the full surface's address; `0.0.0.0` opens it to other machines and then requires control mode) and a commented-out `COHOST_DOCKER_BIN=` for a WSL2 distro without Docker Desktop's WSL integration, where only `docker.exe` is on the path (DEPLOY-HOST-002, control-plane CTRL-STACK-012).
- **Single-PC testing.** The first test machine is WSL2 with Docker Desktop and no second PC. `docs/TESTING.md` carries the checklist (DEPLOY-HOST-004): the dashboard runs in the distro and a Windows browser opens `http://localhost:3000` through WSL's localhost forwarding; Launch runs through `docker` or `docker.exe`; the sink page plays in a second tab or a same-PC OBS Browser Source at `http://localhost:3001/?sink=1`; Docker Desktop makes the loopback-published Redis and voice ports reachable from the distro; one image and one audio injection check that test uploads reach eyes and ears over Redis. The dashboard LLD (One PC: WSL2 with Docker Desktop) gives the reasoning for each path.

Nothing about the image changes: the `Dockerfile` has no dashboard-specific stage or target, every image still compiles the whole workspace (dashboard included, unused), and no image named for the dashboard is built because Compose no longer names the service.

## Image build

`Dockerfile`, three stages on `node:22-slim`:

1. `base`: `WORKDIR /app`, copy `package.json`, then `corepack enable && corepack prepare "$(node -p "require('./package.json').packageManager")" --activate`, so the pnpm version is the `packageManager` field and nothing else (DEPLOY-IMG-006).
2. `build`: `CI=true`, copy `pnpm-workspace.yaml package.json pnpm-lock.yaml tsconfig.base.json tsconfig.json`, then `packages/` and `services/`, `pnpm install --frozen-lockfile`, `pnpm exec tsc -b` (`:10-16`). The root `tsconfig.json` references all 17 projects, so every service directory must exist in the build context and every image compiles the whole workspace.
3. `runtime`: `ARG SERVICE`, `ENV NODE_ENV=production SERVICE=${SERVICE}`, `COPY --from=build /app /app` (the full tree including sources and dev dependencies), `CMD ["sh","-c","exec node services/${SERVICE}/dist/index.js"]` (`:18-23`).

The Dockerfile does not prune (`:3-5`): under pnpm 10, `pnpm prune --prod` empties `services/*/node_modules` and drops the `@cohost/*` workspace links (issue #6), and `pnpm deploy --prod` on pnpm 10.0.0 needs `inject-workspace-packages=true`, which fails `--frozen-lockfile` unless enabled workspace-wide (commit 18ea80a). The consequence is a larger image that ships dev dependencies. No `USER` is set (containers run as root, so files the config loader seeds into the bind mount are root-owned on Linux hosts) and the Dockerfile declares no `HEALTHCHECK` (Compose supplies it).

`.dockerignore`: `node_modules`, `**/node_modules`, `**/dist`, `.git`, `data`, `.env`, `**/*.tsbuildinfo`, `**/*.log`, `config/.vts-token`, `config/config.yaml`, `config/personality.md`, `config/expressions.yaml` (`:1-12`). Excluding `.tsbuildinfo` stops stale host incremental state from making `tsc -b` in the image skip emitting while `**/dist` is ignored (issue #7, commit 7e89e4e). It does not exclude `worktrees/`, `docs/` or `graphify-out/`, which only inflate the context. `config/` can hold the VTube Studio credential (`<config>/.vts-token`, `services/avatar/src/drivers/vtube-studio.ts:104`) and the operator's own `config.yaml`, `personality.md` and `expressions.yaml`; `.dockerignore` excludes those four files so neither the credential nor operator files reach the daemon (DEPLOY-IMG-005). The `config/*.example.*` files stay in the context; the Dockerfile copies only `packages/` and `services/`, and config arrives by bind mount.

## Installer: `scripts/install.sh`

`set -euo pipefail`, runs from the repo root, flag `--no-pull`. Steps in order:

1. Detect WSL (`grep -qi microsoft /proc/version`), source `/etc/os-release`, warn if the distro is not Ubuntu or Debian (`:16-24`).
2. Detect NVIDIA via `nvidia-smi` (`:26-34`).
3. If `docker` is missing, install docker-ce from the Docker apt repo, `usermod -aG docker`, start the daemon (`service` on WSL, `systemctl` otherwise), then stop and exit non-zero with a "log out and back in, then re-run" message, because the current shell lacks the new group and the docker commands below would fail part-way (DEPLOY-INST-010, `:36-55`); on every run, die if `docker compose version` fails (`:57`).
4. If a GPU exists and `docker info` shows no NVIDIA runtime, install `nvidia-container-toolkit` if needed, `nvidia-ctk runtime configure`, restart Docker (`:59-74`).
5. If Node is missing or its numeric major (from `node -p "process.versions.node.split('.')[0]"`) is below 22, install NodeSource `setup_22.x` (piped to `sudo -E bash`) (DEPLOY-INST-009); if `pnpm` is missing, `corepack enable` and prepare the `packageManager` version of `package.json`, read by `pnpm_spec` (DEPLOY-IMG-006).
6. Seed `.env` and the three `config/` files from their examples if absent (`:85-95`); rewrite the `COMPOSE_FILE=` line in `.env` on every run from the GPU detected on that run (GPU: `docker-compose.yml:docker-compose.gpu.yml`), replacing a hand-set value by design (`:96-101`); fill an empty `CONTROL_TOKEN=` line with a generated secret (gap DEPLOY-INST-013); `mkdir -p data` (`:102`, nothing references `data/` afterwards).
7. `pnpm install --frozen-lockfile`, aborting with its error on a lockfile mismatch as CI and the `Dockerfile` do, never falling back to a plain `pnpm install` (DEPLOY-INST-012, `:108`), then `pnpm typecheck` (`:104-110`).
8. Unless `--no-pull`: `docker compose pull --ignore-buildable`, `up -d ollama models`, follow `models` logs, `docker compose wait models` (`:112-122`).
9. Smoke test: `up -d redis postgres`, then `probe <name> 60 <fn>` polls `redis-cli ping`, `pg_isready` and, when pulling, Ollama `/api/tags` once a second until each passes (printing `  <name> ok`) or 60 s elapse, when it prints one failure line naming the probe and exits non-zero (DEPLOY-INST-007, `:124-145`). The probes compare command substitutions rather than piping into `grep -q`, so `pipefail` cannot turn an early-closing reader into a false failure.
10. Next steps (`:146-166`): run `pnpm dashboard`, open the dashboard URL and press Launch, instead of `docker compose up -d` (gap DEPLOY-INST-008); the dashboard URL uses `DASHBOARD_PORT` from the calling shell, else the last `DASHBOARD_PORT=` line of `.env` parsed with `sed` (inline comment, quotes and CR stripped, non-numeric rejected, default 3000), never sourcing `.env` (DEPLOY-INST-008); the Docker-free dev loop lists `redis postgres ollama tts stt` (DEPLOY-INST-011). `corepack prepare pnpm@10.0.0` (`:83`) duplicates `package.json:8` and `Dockerfile:7`.

## Build, test and CI

**Workspace and TypeScript**: `pnpm-workspace.yaml` globs `packages/*` and `services/*`. `tsconfig.json` is solution-style (`files: []`, 17 references: config, bus, llm, modules, working-memory, control, testing plus the 10 services). `tsconfig.base.json` sets ES2022, NodeNext, `strict`, `composite`, declarations and `noUncheckedIndexedAccess`, with `lib: ["ES2022"]` (no DOM). Every per-package tsconfig includes only `src`, so test files are executed through `tsx` but not type-checked by `tsc -b`.

**Root scripts** (`package.json:12-25`): `build`, `typecheck` (`tsc -b --noEmit`), `lint` (identical to `typecheck`; there is no linter), `dev` (`pnpm -r --parallel --filter './services/*' dev`; each service runs `tsx watch src/index.ts`), `reflect`, `clean`, `test` (`tsc -b && node --import tsx --test "packages/*/test/*.test.ts" "services/*/test/*.test.ts"`), `test:only`, and the `docs:*` scripts. `pnpm.onlyBuiltDependencies` allows install scripts for `esbuild`, `@snazzah/davey`, `libsodium-wrappers`, `opusscript` (`package.json:32-39`). `packageManager` pins `pnpm@10.0.0`; `engines.node` is `>=22`.

## Licensing and contribution

cohost is dual licensed. The public licence is AGPL-3.0-only: `LICENSE` is the 661-line AGPL v3 text, added as the canonical gnu.org text (commit 686cc8f), and the root and all 17 workspace `package.json` files declare `AGPL-3.0-only` (DEPLOY-LIC-001). A separate commercial licence, which exempts the licensee from the AGPL obligations, is reserved to the owner, CoderCoco; `COMMERCIAL.md` says what it is for and how to ask for one, and the README License section and the docs-site footer name both licences (DEPLOY-LIC-004).

What the AGPL does and does not stop: anyone may use cohost commercially under the AGPL, including running it as a paid service. Running a modified private copy obliges nothing by itself. AGPL section 13 requires offering the corresponding source of a modified version to the users who interact with it remotely over a network; distributing (conveying) a copy has its own conditions in sections 4-6, including source and licence for recipients. What it stops is a closed fork that serves users or is shipped: a business that wants to keep its changes private while offering them over a network, or ship cohost inside a proprietary product, needs the commercial licence. `COMMERCIAL.md` and the README state this plainly rather than implying the AGPL forbids commercial use.

The owner can only grant that exemption for code they hold the rights to relicense. Every outside contribution is therefore accepted under an individual Contributor License Agreement, `CLA.md`, adapted from the Apache Individual CLA: the contributor keeps copyright and grants CoderCoco a perpetual, worldwide, royalty-free copyright licence that includes the right to sublicense and to relicense the contribution under other terms (commercial terms included), plus a patent licence, and represents that the contribution is their own original work or is identified as third-party work (DEPLOY-LIC-003). The text is a template adaptation, not legal advice. `CONTRIBUTING.md` requires that a contribution is offered to the public under AGPL-3.0-only and that its author has signed the CLA, and explains how to sign (DEPLOY-LIC-002).

Enforcement is the `cla` workflow (DEPLOY-CI-005):

- **Who must sign.** Each commit in the pull request resolves to one contributor: the commit author's GitHub account, else the committer's GitHub account, else the raw author name. Every such contributor must have signed, not only the pull request's opener.
- **No allow-list.** The action matches allow-list entries against the commit author's raw name, and a commit whose author email is not linked to a GitHub account resolves to that raw name, so an entry such as `CoderCoco` or `*[bot]` could be claimed by anyone who sets that author name. The workflow therefore sets none: the owner signs once like any contributor, and the repository uses no bot accounts that commit to pull requests. The action itself skips `github-actions[bot]` by account id. A bot that later commits to pull requests is added by its exact account name.
- **Signing once.** A signature is recorded once per contributor, with the pull request it was given on; later pull requests from the same contributor pass without a new comment.
- **Where signatures live.** `.github/cla/signatures.json` on the dedicated `cla-signatures` branch. The branch carries a seed file, `{"signedContributors": []}`, because v2.6.1 fails with a 404 comparison bug on the first pull request when the file is missing; after the seed only the action writes it. `main` is protected by a repository ruleset that requires pull requests, which would reject the action's direct commits, so the record lives on an unprotected branch that only the action writes. That branch must exist before the workflow first runs.
- **What it does not check.** `Co-authored-by:` trailers are not read, so a co-author named only in a trailer is not asked to sign; a pull request with human trailer co-authors needs their signatures collected by hand before it merges. Corporate contributions are out of scope: the CLA is individual only, and someone contributing on an employer's behalf opens an issue first.
- **History.** Commits already on `main` before the `cla` workflow existed are not re-checked.

Needs a Docker daemon, a real account or a real run; the single-PC checklist in `docs/TESTING.md` is where each is checked and ticked off.

4. **First real run.** `cohostctl launch` against the real stack (images, model pulls, healthchecks) is the first step of the single-PC checklist (DEPLOY-HOST-004).
