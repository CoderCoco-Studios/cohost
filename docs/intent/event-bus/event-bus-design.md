## Context and Design Philosophy

`@cohost/bus` (`packages/bus`) is the only channel between cohost services. The header of `packages/bus/src/events.ts:5-8` says so directly: services "only ever talk through these events - never directly to each other - so any piece can be swapped". The package has three jobs:

1. A **schema registry** (`events.ts`): one zod schema per event type, plus the derived TypeScript types (`EventType`, `EventData`, `EventInput`, `BusEvent`) and `EVENT_TYPES`.
2. A **thin typed wrapper over two Redis Streams** (`index.ts`): `cohost:events` for domain events and `cohost:health` for heartbeats. Publish is validate-then-`XADD`; subscribe is a consumer-group loop; `tail` / `recent` are non-group reads for the dashboard.
3. **Process-lifecycle helpers** that happen to live here: `onShutdown` and `beforeShutdown` (`index.ts:311-356`), and the heartbeat helper `startHeartbeat` (`heartbeat.ts`, owned by [control-plane](../control-plane/control-plane-design.md)).

Guiding principles visible in the code:

- Validate on both sides. `publish` parses against `EventPayloads[type]` before writing (`index.ts:82`); `decode` parses again on every read (`index.ts:303`). Malformed entries are dropped rather than delivered (`index.ts:296`, `index.ts:305-307`).
- Keep services decoupled from Redis. Region logic depends on `Publisher = Pick<Bus, "publish">` (`index.ts:30`) so tests can pass a recorder (see [Test double](#test-double-packagestestingsrcindexts)).
- Heartbeats must not evict domain events, so they have their own capped stream (`index.ts:10-12`, comment at line 10).
- Binary payloads never ride the stream. Live connector audio rides its own capped streams, `<prefix>:audio.in.<source>` and `<prefix>:audio.out.<sink>`, with registrations in keys `<prefix>:connector:<id>`; both are specified by [connections](../connections/connections-design.md) and use the prefix of BUS-STREAM-008. `inject.request` carries an `uploadId`; the bytes sit in the Redis key `cohost:upload:<id>` (`Bus.putUpload` / `Bus.takeUpload`, BUS-UPL-001 to BUS-UPL-003), outside the stream.

Scope of this segment: the Cargo workspace at the repository root (`Cargo.toml`, `crates/cohost-bus`, `crates/cohost-bus-node`), the contract fixtures under `packages/bus/fixtures/contract/`, `packages/bus/src/index.ts`, `packages/bus/src/native.ts`, `packages/bus/src/events.ts`, `packages/bus/test/bus.test.ts`, `packages/bus/test/resilience.test.ts`, `packages/bus/test/shutdown.test.ts`, `packages/bus/test/shutdown.fixture.ts`, `packages/bus/test/shutdown-multi.fixture.ts`, `packages/bus/test/shutdown-hooks.fixture.ts`, `packages/bus/package.json`, `packages/bus/tsconfig.json`, and (documented here because it is the test double for `Bus`) `packages/testing/src/index.ts`. `packages/bus/src/heartbeat.ts` and the `service.heartbeat` / `service.lifecycle` semantics belong to [control-plane](../control-plane/control-plane-design.md); this document records only their schemas and the `Bus` methods that carry them.

## Stream layout and envelope

| Stream | Constant | Trim | Carries |
|---|---|---|---|
| `cohost:events` | `STREAM` (`index.ts:8`) | `MAXLEN ~ 20000` (`index.ts:9`, used at `index.ts:52`) | every event type except `service.heartbeat` |
| `cohost:health` | `HEALTH_STREAM` (`index.ts:11`) | `MAXLEN ~ 1000` (`HEALTH_MAXLEN`, `index.ts:12`, used at `index.ts:67`) | `service.heartbeat` only |

Both streams use the same entry fields (`index.ts:85-91`, `index.ts:105-112`): `type`, `ts` (`String(Date.now())`, publisher clock), `source` (the `Bus` constructor's first argument, usually the service name), `data` (`JSON.stringify` of the zod-parsed payload). The Redis stream id is the event id. `decode` (`index.ts:291-308`) rebuilds a `BusEvent`: `{ id, type, ts: Number(m.ts ?? 0), source: m.source ?? "?", data }` and returns `undefined` for an unknown type, non-JSON `data`, or a schema failure.

Typing detail: `publish` accepts `EventInput<T>` (`z.input`, defaults optional), subscribers receive `EventData<T>` (`z.infer`, defaults applied). So `chat.message` published without `isMod` is stored and delivered with `isMod: false`.

## Bus API

Constructor: `new Bus(source, log?, url = urls.redis(), options?)`. The optional `BusOptions` object supplies a transport factory (`transport`, default the native transport of [Native transport](#native-transport)), the retry delay base and cap (`retryBaseMs` 250, `retryMaxMs` 30000), `streamPrefix` (default `cohost`: the instance uses `<prefix>:events` and `<prefix>:health`, BUS-STREAM-008, so a test works on streams of its own) and `failFast` (BUS-STREAM-009); tests pass a fake `BusTransport` through `transport` so the subscribe, tail and publish paths run without a Redis server. `urls.redis()` is `REDIS_URL` or `redis://127.0.0.1:6379` (`packages/config/src/index.ts:167`). The transport opens its shared connection when the `Bus` is constructed; each `subscribe`, `tail`, `tailHealth` and `tailAudio` opens a reader with a connection of its own, because a blocking read occupies its connection. `consumer` is `${HOSTNAME ?? "local"}-<8 hex of a random uuid>`, fixed for the life of the `Bus` instance.

| Method | Behavior | Lines |
|---|---|---|
| `publish(type, data)` | throws for `service.heartbeat`; zod-parses; `XADD cohost:events MAXLEN ~ 20000`; returns stream id; debug log; an `XADD` rejection is logged at warn (`{ err, type }`, `publish failed`) and rethrown unchanged (BUS-STREAM-007) | `index.ts:79-99` |
| `publishHealth(data)` | zod-parses as `service.heartbeat`; `XADD cohost:health MAXLEN ~ 1000`; returns id; a rejection is logged and rethrown the same way | `index.ts:101-117` |
| `subscribe(opts, handler)` | consumer-group loop (below); resolves only after `stop()` | `index.ts:173-226` |
| `tail(handler, fromId="$")` | non-group `XREAD COUNT 100 BLOCK 5000` loop on `cohost:events`; no ack, no replay | `index.ts:228-252` |
| `tailHealth(handler, fromId="$")` | same loop on `cohost:health`; only `service.heartbeat` entries reach the handler | `index.ts:119-144` |
| `recent(count=100)` | `XREVRANGE + - COUNT n`, decoded, undecodable entries filtered, reversed to oldest-first | `index.ts:255-259` |

| `stop()` | sets the instance-wide `stopped` flag, wakes any retry backoff sleep, disconnects every sub/tail connection and the publish connection | `index.ts:282-289` |

### Consumer-group subscription loop

`SubscribeOptions` (`index.ts:19-35`): `group` (one per service), `types?` (client-side filter), `start` (`SubscribeStart`, `"latest"` or `"resume"`; required), `blockMs?` (default 5000), `onReady?` (called once after the group is created or positioned and before the first read; BUS-SUB-012).

**Start mode.** Every subscription names where it starts reading after a process start (BUS-SUB-011):

- `latest`: the group is moved to the newest entry (`$`) on every start, so a restarted subscriber never acts on events published while it was down (BUS-SUB-010). Used by every subscribing service except memory: a co-host that speaks, reacts or animates must not replay stale chat, focus or speech lines after a restart.
- `resume`: an existing group keeps its stored position, so the backlog still held by the 20000-entry stream is delivered after a restart (BUS-SUB-002). Used by memory, which wants to store what it missed.
- In either mode a missing group is created at `$` (BUS-SUB-001); a first-ever start never replays the stream.

`Bus.resetGroup` remains the separate path a control-plane `fresh` start uses to move a group to `$` from outside the service.

Loop:

1. Create the group with `XGROUP CREATE cohost:events <group> $ MKSTREAM`. On `BUSYGROUP`, `latest` runs `XGROUP SETID cohost:events <group> $` and `resume` leaves the stored position; any other error rejects `subscribe` (BUS-SUB-001), so a Redis outage at subscribe time still rejects the promise (`index.ts:179-184`). Retry covers the read loop only.
2. Read loop (`index.ts:188-224`): starts with cursor `"0"` (this consumer's pending entries) and drains them batch by batch: after each entry the cursor moves to that entry's id, so the next read returns the entries after it, until a read returns none, and then it switches to `">"` (new entries) (BUS-SUB-003). An entry whose `XACK` Redis refused stays pending but is not read again by the same drain, so the drain always ends; a later drain delivers it at most once more, and drops it if that ack is refused too (BUS-SUB-008, BUS-NAT-ACK-008). Batches are `COUNT 50` with `BLOCK blockMs`. If `stop()` lands while a handler runs, the handler finishes, the entry is not acked and the rest of the batch is neither handled nor acked (BUS-SUB-013).
3. For each entry: `decode`; if it decodes and passes the `types` filter, `await handler(ev)` inside try/catch (error logged as `"handler failed"`, `index.ts:213`); then `XACK` regardless of filter result, decode failure, or handler failure (`index.ts:217`); a refused `XACK` is logged at warn (`ack failed`) and not retried; the loop moves on, and the entry, still pending, is delivered again only by a later drain, and only once: if the ack of that redelivery is refused as well, the entry is logged as dropped and never delivered again (BUS-SUB-008, BUS-SUB-009, BUS-NAT-ACK-008). Handlers therefore run strictly one at a time per subscription, and failed events are dropped with no retry or dead-letter.
4. A read error while `stopped` breaks the loop quietly. Any other read error is logged at warn (`{ err, delayMs, failures }`) and the read retried after `min(cap, base * 2^(failures-1))` ms (base 250, cap 30000 by default; the failure count resets after a successful read), so a Redis outage never ends the subscription and never rejects the `subscribe` promise (BUS-SUB-009). The sleep ends as soon as `stop()` is called (`index.ts:261-272`).

**Delivery is at most once, with one exception** (BUS-SUB-008). Handler failures are acknowledged, and an entry read but not acknowledged by a process that then dies is not redelivered to its successor: each `Bus` instance reads under its own consumer name (`index.ts:65`) and nothing claims another consumer's pending entries. Within one process an entry whose handler has run is not delivered again, except an entry whose acknowledgement Redis refused: it stays in this consumer's pending list, and the next drain (after a later read failure, [Errors, reconnect and backoff](#errors-reconnect-and-backoff)) delivers it once more. The subscription records each id whose ack was refused. If the ack of the redelivery is refused again, the facade logs `ack failed, entry dropped` at warn and moves the id to a dropped set; a later drain that reads a dropped entry neither hands it to the handler nor queues its ack, so the entry is delivered at most twice in all and stays pending under this consumer (BUS-NAT-ACK-008). A refused ack is rare (the group was destroyed, for example, in which case the read fails too), so both records stay small; they live as long as the subscription. The pending drain only matters within one process lifetime; it is not crash recovery.

### Health-stream methods

`publishHealth`, `tailHealth` and `recentHealth` exist because `publish("service.heartbeat", ...)` throws `service.heartbeat goes on the health stream: use publishHealth()` (`index.ts:81`). `tailHealth` and `recentHealth` are used by the dashboard feed (`services/dashboard/src/feed.ts:46,49`) and by control-plane's CLI and healthcheck (`packages/control/src/cli.ts:111`, `packages/control/src/healthcheck.ts:23`). `resetGroup` is used by the service controller for "fresh" starts (`packages/control/src/controller.ts:23,42`). This segment owns the heartbeat transport (BUS-STREAM-004, BUS-HEALTH-001 to 004); what a heartbeat means and how it is consumed is [control-plane](../control-plane/control-plane-design.md)'s.

`tail` and `tailHealth` follow the same failure rule as `subscribe`: a non-stop read error is logged at warn and retried with the same capped, growing delay from the last delivered id, never rejecting the promise (BUS-TAIL-003), and a handler that throws is logged at error (`handler failed`) and the loop continues with the next entry (BUS-TAIL-004; `index.ts:274-281`). A caller that must know whether Redis answers (the dashboard feed's bus reachability) passes an optional `onRead` callback as the third argument of either method; it hears every read's outcome, success or error (BUS-TAIL-005), so the tail loops stay the one place that reads the stream.

### Shutdown helpers

The process shutdown sequence is specified by shared-runtime (SHARED-LIFE-001 to 005) and its code moves to `@cohost/shared`, leaving this package the transport only; the bus's own `stop()` stays here (BUS-STOP-001). The description below is of the helpers as they stand in `packages/bus/src/index.ts` until that move.

- `beforeShutdown(fn)` pushes onto a module-global list (`index.ts:315-317`). The only in-repo registrant is `startHeartbeat` (`heartbeat.ts:117`), which registers its `stop()` so a `stopping` heartbeat goes out first.
- `onShutdown(fn, log?)` (`index.ts:350-356`) appends `fn` to a module-global callback list and, on the first call only, installs the SIGINT and SIGTERM handlers. The first signal starts the one shutdown sequence of the process (`runShutdown`, `index.ts:320-345`): every `beforeShutdown` hook runs concurrently (each wrapped in an `async` function, so a synchronous throw is a rejection; `Promise.allSettled`), raced against a 2000 ms `HOOK_TIMEOUT_MS` (unref'd timer); then every registered callback runs in registration order, each awaited to completion, and `process.exit(0)` runs once in a `finally` (SHARED-LIFE-001 to 006). Later signals are ignored. A callback that throws or rejects is logged at error through the registration's `log` (a pino-style logger, optional) or `console.error` when none was given, and the remaining callbacks still run. This segment owns these mechanics (hook window, callback order, exit code); control-plane only registers the heartbeat's `stop()` as a hook (SHARED-LIFE-010).
- Several registrations in one process are normal: eyes, ears and chat each register more than one stop step through `onStop` (`runService`, `packages/shared/src/lifecycle.ts:54`), and all of their callbacks run.
- `index.ts` re-exports `./heartbeat.js` at its last line (`index.ts:358`) and `heartbeat.ts` imports `beforeShutdown` from `./index.js`; the cycle works because `beforeShutdown` is only called at runtime.
- The subprocess fixture `packages/bus/test/shutdown.fixture.ts` proves the ordering `hb:starting`, `hb:ready`, `hb:stopping`, `bus.stop` (asserted at `bus.test.ts:257-261`). `shutdown-multi.fixture.ts` and `shutdown-hooks.fixture.ts` prove the composition: all callbacks in order with failures logged and one `exit(0)`, and a synchronously throwing hook that skips neither the other hooks nor the callbacks (`shutdown.test.ts`).

## Native transport

The bus client's transport is native code, so the central highway has headroom as sources and services grow (HLD, Native layer). Rust owns the Redis I/O and the wire conventions; the TypeScript `Bus` facade keeps the public API, the zod registry, validation on publish and on read, and every loop's control flow (start modes, drain, backoff, stop). There is one path: the facade always runs on a `BusTransport`, which in production is the native binding.

### Architecture

```
services (TS) ──> @cohost/bus  Bus facade (TS: zod, envelope, loops, backoff, logging)
                      │  BusTransport interface
                      ├── native binding  packages/bus/src/native.ts ──> cohost-bus.linux-x64-gnu.node
                      │                                                   crates/cohost-bus-node (napi-rs, thin)
                      │                                                   crates/cohost-bus (pure Rust: redis-rs + tokio)
                      └── test fakes (scripted BusTransport)
Rust services ──────────────────────────────────────────────────────────> crates/cohost-bus directly
```

- **Cargo workspace** at the repository root (`Cargo.toml` with `members = ["crates/*"]`, one `Cargo.lock`, a `rust-toolchain.toml` pinning an exact stable toolchain version with the `rustfmt` and `clippy` components; the Docker `native` stage uses the same version).
- **`crates/cohost-bus`**: pure Rust, no Node dependency. Owns the Redis connections (one shared multiplexed connection plus one dedicated connection per reader), every Redis command the bus issues, ack batching, the key and stream naming under the prefix (BUS-STREAM-008), the stream caps and expiries, the audio frame codec, the tag grammar, and the typed codec of the events Rust services touch. A Rust service depends on it directly, with no Node in between. It never logs: every failure is returned to the caller as an error value.
- **`crates/cohost-bus-node`**: the napi-rs wrapper. It converts arguments and results, maps errors to JS errors with a `code`, and holds no logic of its own; anything it does that a Rust service would also need belongs in `cohost-bus`.
- **`packages/bus/src/native.ts`**: loads the `.node` file and adapts it to `BusTransport`. It is the only TypeScript file that imports the addon.
- **The `Bus` facade** (`packages/bus/src/index.ts`) keeps every behaviour this document specifies above: what is validated, the envelope fields and their values (`ts` is still the publisher's `Date.now()`), what is delivered, acked, logged and retried. It decides; the transport executes.

### Facade public API

The transport is invisible to callers. `@cohost/bus` exports, with the behaviour this document specifies:

- `class Bus`: `constructor(source, log?, url?, options?)`, `consumer`, `publish`, `publishHealth`, `subscribe`, `tail`, `tailHealth`, `recent`, `recentHealth`, `resetGroup`, `serverTime`, `putUpload`, `takeUpload`, `connectorKey`, `audioStream`, `writeRegistration`, `readRegistration`, `deleteRegistration`, `listConnectors`, `publishFrame`, `tailAudio`, `stop`.
- Types and constants of `index.ts`: `STREAM`, `HEALTH_STREAM`, `HEALTH_MAXLEN`, `SubscribeStart`, `SubscribeOptions`, `Handler`, `Publisher`, `ReadOutcome`, `HeartbeatEvent`, `BusOptions`.
- Everything re-exported from `events.ts` (the registry), `connector.ts` and `registrar.ts` (see [What moves to Rust](#what-moves-to-rust-from-connectorts)).

The test seam is `BusOptions.transport` with the `BusTransport` type; there is no connection-level seam. The `publish` and `subscribe` call sites, `FakeBus`, `ConnectorFakeBus` and every `Pick<Bus, ...>` consumer depend only on this API, not on the transport.

### The `BusTransport` interface

The seam between facade and native code. It is named `BusTransport` because `connector.ts` already exports `Transport` (a capability's `stream` / `http` transport, CONN-DESK-003). Every method maps to a fixed set of Redis commands; the transport adds no retries of its own, so the facade's backoff is the only retry policy.

```ts
type EventStream = "events" | "health";
/** The four envelope fields as stored (BUS-STREAM-001). */
interface EntryFields { type: string; ts: string; source: string; data: string }
/** One entry as read. Only the four envelope fields are returned; a missing field is undefined.
 *  A pending entry whose stream entry was trimmed, and an entry with an envelope field that is
 *  not valid UTF-8, come back with no fields. */
interface RawEntry { id: string; type?: string; ts?: string; source?: string; data?: string }
interface AckError { ids: string[]; err: Error }
/** `entries` is null when the block timed out with nothing to read. */
interface GroupRead { entries: RawEntry[] | null; ackErrors: AckError[] }
interface FrameEntry { id: string; decoded: DecodedFrame }

interface BusTransport {
  /** XADD <prefix>:<stream> MAXLEN ~ 20000 (events) | 1000 (health) * type ts source data. Resolves to the id. */
  append(stream: EventStream, fields: EntryFields): Promise<string>;
  /** XREVRANGE <prefix>:<stream> + - COUNT n, returned oldest first. */
  recent(stream: EventStream, count: number): Promise<RawEntry[]>;
  /** XGROUP CREATE <prefix>:events <group> $ MKSTREAM. true: created; false: BUSYGROUP; any other error rejects. */
  createGroup(group: string): Promise<boolean>;
  /** XGROUP SETID <prefix>:events <group> $. */
  moveGroupToLatest(group: string): Promise<void>;
  /** SET <prefix>:upload:<id> <bytes> PX ttlMs (BUS-UPL-001). */
  putUpload(id: string, bytes: Buffer, ttlMs: number): Promise<void>;
  /** GETDEL <prefix>:upload:<id> (BUS-UPL-002). */
  takeUpload(id: string): Promise<Buffer | null>;
  /** SET <prefix>:connector:<id> <json> PX leaseMs (CONN-REG-001). */
  writeRegistration(id: string, json: string, leaseMs: number): Promise<void>;
  /** GET <prefix>:connector:<id>. */
  readRegistration(id: string): Promise<string | null>;
  /** DEL <prefix>:connector:<id> (CONN-REG-003). */
  deleteRegistration(id: string): Promise<void>;
  /** SCAN MATCH <prefix>:connector:* COUNT 100 to cursor 0, de-duplicated, then one MGET; values that exist (CONN-REG-006). */
  listRegistrations(): Promise<string[]>;
  /** Encode, then XADD <prefix>:audio.<dir>.<tag> MAXLEN ~ cap(dir) * ... and PEXPIRE 60000 in one pipeline (CONN-AUD-001).
   *  Rejects BUS_INVALID, writing nothing, when pcm exceeds MAX_FRAME_BYTES or has an odd byte count. */
  appendFrame(dir: AudioDirection, tag: string, frame: Frame): Promise<string>;
  /** TIME, as epoch ms (CTRL-CHECK-004). */
  serverTime(): Promise<number>;
  /** A reader with its own connection, for one blocking loop. */
  openReader(): BusReader;
  /** Send every reader's queued acks on the shared connection in one pipeline (nothing when none are queued), then
   *  close the shared connection and every reader; blocked reads reject with BUS_CLOSED. The flush is abandoned after
   *  2000 ms. Never rejects: a failed or abandoned flush is not retried. A second close() resolves when the first has.
   *  Every other method called afterwards rejects with BUS_CLOSED. */
  close(): Promise<void>;
}

interface BusReader {
  /** Sends the queued acks of this reader, then XREADGROUP GROUP <group> <consumer> COUNT n BLOCK ms STREAMS <prefix>:events <cursor>,
   *  in one pipeline. `ackErrors` reports queued acks that Redis refused. */
  readGroup(group: string, consumer: string, cursor: string, count: number, blockMs: number): Promise<GroupRead>;
  /** Queue XACK <prefix>:events <group> <id>; synchronous, sent with the next readGroup or by the transport's close(). */
  ack(group: string, id: string): void;
  /** XREAD COUNT n BLOCK ms STREAMS <prefix>:<stream> <fromId>. null on timeout. */
  read(stream: EventStream, fromId: string, count: number, blockMs: number): Promise<RawEntry[] | null>;
  /** XREAD on <prefix>:audio.<dir>.<tag>, each entry decoded by the frame codec (never throws, CONN-BP-006). null on timeout. */
  readFrames(dir: AudioDirection, tag: string, fromId: string, count: number, blockMs: number): Promise<FrameEntry[] | null>;
  /** Close this reader's connection, dropping its queued acks; a blocked read rejects with BUS_CLOSED. */
  close(): void;
}

type TransportFactory = (url: string, opts: { prefix: string; failFast: boolean }) => BusTransport;
```

The facade maps onto it one to one: `publish` and `publishHealth` are `append`; `subscribe` is `createGroup` (then `moveGroupToLatest` for `latest` on `false`), `onReady`, and a loop of `readGroup` / handler / `ack`; `resetGroup` is `createGroup` then `moveGroupToLatest` on `false`; `tail` and `tailHealth` are loops of `read`; `tailAudio` is a loop of `readFrames`; `recent` and `recentHealth` are `recent` plus `decode`; `stop()` sets `stopped`, wakes the backoff sleeps and awaits `close()`, so it returns `Promise<void>`, which the process shutdown sequence awaits. `decode` (BUS-STREAM-006, BUS-SUB-007) stays in the facade and works on `RawEntry`.

Test fakes implement `BusTransport` directly: a resilience test scripts what `readGroup` resolves or rejects with, at the level the facade decides on.

### Crossing the napi boundary

- **Async methods.** Every I/O method of the binding returns a Promise, resolved from a Rust future on the addon's tokio runtime. One runtime per process, created when the addon is first loaded, with a small fixed worker count (one worker unless the measurement gate shows that more helps); the bus is I/O-bound (constraint N3). The codec helpers exported for tests and fakes (`encodeFrame`, `decodeFrame`, `tagProblem`) are synchronous.
- **TypeScript owns every read loop.** Rust never calls into JavaScript: there are no threadsafe functions and no callbacks from the runtime (constraint N1). A loop iteration is one awaited `readGroup` / `read` / `readFrames` call that returns a whole batch, so the boundary is crossed once per batch, not once per entry.
- **Handlers run serially, as today.** The facade awaits each `subscribe` handler before the next entry and before the next read (BUS-SUB-006); tail handlers run under the facade's guard (BUS-TAIL-004). The next read is not issued until the batch is done, so backpressure is natural: a slow handler leaves the backlog in Redis, bounded by the stream cap, and never in process memory.
- **Acks are pipelined, delivery stays at most once.** After a handler finishes (or fails, or the entry is filtered or undecodable), the facade calls `ack`, which only queues the id. The queued XACKs travel in the same pipeline as the next `XREADGROUP`, so a batch of 50 costs one round-trip instead of 51. Order and outcome are unchanged: an entry is acked only after its handler returned (BUS-SUB-005), a handler failure is still acked, and an entry never acked is not redelivered to another process (BUS-SUB-008). A refused XACK comes back in `ackErrors` of that `readGroup` and the facade logs it at warn as `ack failed` with the ids, then carries on without retrying it; the entry stays pending and a later drain delivers it once more, and a second refusal of the same id drops it (`ack failed, entry dropped`, BUS-SUB-008, BUS-SUB-009, BUS-NAT-ACK-003, BUS-NAT-ACK-008). During the pending drain the cursor still follows the last id handled (BUS-SUB-003), so within one drain an entry whose ack is queued or refused is never read twice. If the pipeline fails on the connection, the queued acks stay queued and are sent with the next pipeline that reaches Redis (XACK is idempotent).
- **Stop during a handler** keeps BUS-SUB-013: the facade does not queue an ack for that entry or any later entry of the batch.
- **Acks queued at `stop()`** are sent before the connections close: `close()` flushes every reader's queue on the shared connection, which no blocking read occupies, in one pipeline, and only then closes. With no queued acks it sends nothing. Every entry handled before `stop()` is therefore acked when Redis answers, and a shutdown leaves no handled entry pending under a consumer name that is never used again. A flush that fails (the shared connection is down, or Redis refuses an ack) is not retried and is not logged by the transport; `stop()` still resolves. A flush that has not completed 2000 ms after `close()` was called is abandoned the same way (BUS-NAT-ACK-007), so `stop()` resolves within about 2 s even when Redis hangs or the first connect attempt is still in flight; the shutdown budget of shared-runtime counts on that bound (SHARED-BOOT-006).
- **Buffers.** An audio frame's `pcm` and an upload's bytes cross as Node `Buffer`s. Inbound (`appendFrame`, `putUpload`), the binding copies the bytes into the outgoing command synchronously, inside the call, so the caller may reuse or change its `Buffer` as soon as the call returns, before the Promise settles. Outbound (`readFrames`, `takeUpload`), the bytes parsed from the Redis reply are handed to Node as an external `Buffer` that owns the Rust allocation, with no copy into the JS heap; Rust frees it when V8 collects the `Buffer` (constraint N2; BUS-NAT-TRN-010). Event `data` crosses as a JS string (one UTF-8 to UTF-16 conversion by V8), which `decode` then parses.
- **Per-frame objects.** `readFrames` returns one small object per frame. If the measurement gate shows that building these objects dominates the frames path, the first lever is to return a batch as one `Buffer` of all `pcm` plus a flat header array, sliced in the facade, without changing `tailAudio`'s handler signature.

### Errors, reconnect and backoff

The binding rejects with a JS `Error` whose `code` is one of:

| Code | Meaning | Facade response |
|---|---|---|
| `BUS_CONNECTION` | could not connect, connection reset or closed by the peer, connect timeout; the message names the cause (the operating system's error text, or `connect timeout`; BUS-NAT-ERR-009) | read loops: warn and back off (BUS-SUB-009, BUS-TAIL-003); publish and other calls: reject to the caller (BUS-STREAM-007) |
| `BUS_REDIS` | Redis answered with an error; the message is Redis's text (`NOGROUP ...`, `WRONGTYPE ...`) | as `BUS_CONNECTION`; `subscribe` and `resetGroup` rethrow a group-creation error other than BUSYGROUP (BUS-SUB-001, BUS-GROUP-001), which the transport has already turned into `false` |
| `BUS_CLOSED` | the transport or reader was closed, including a blocked read interrupted by `close()` | after `stop()`: end the loop quietly (BUS-STOP-001) |
| `BUS_INVALID` | an argument the codec refuses: a tag outside the grammar, a frame whose `pcm` exceeds `MAX_FRAME_BYTES` or has an odd byte count, a frame the encoder cannot otherwise write. Nothing is written | reject to the caller |
| `BUS_INTERNAL` | a Rust panic caught at the boundary, or a reply of an unexpected shape | as `BUS_CONNECTION` |

Reconnect semantics:

- **Readers** do not retry. A reader whose connection fails rejects the read at once; the facade logs and sleeps for its capped backoff (base 250 ms doubling to 30 s, reset on a successful read) and calls the reader again, which reconnects on that call. So the facade's backoff is the only retry clock, every failed attempt produces exactly one warn line and one `onRead` report (BUS-TAIL-005), and the subscribe and tail promises never reject on a read failure (BUS-SUB-009, BUS-TAIL-003). Tail loops resume from the last id they delivered.
- **The shared connection** reconnects in the background after a failure (a failed first attempt included; never with `failFast`), with its own capped delay (the same 250 ms base doubling to a 30 s cap). The connection has two phases. **Boot:** from construction until the first connect attempt settles (at most the 10 s connect timeout, BUS-NAT-CONN-007), a command waits for that attempt and then runs, or rejects with `BUS_CONNECTION` if the attempt failed (BUS-NAT-CONN-006), so a service's first heartbeat does not fail merely because it was published before the socket opened. **After boot:** no command ever waits for a connect attempt. Whenever the connection is down (the first attempt failed, or an established connection dropped) every command on it (`publish`, `publishHealth`, `publishFrame`, `putUpload`, `takeUpload`, the registration calls, `recent`, `recentHealth`, `resetGroup`, `createGroup` for `subscribe`, `serverTime`) rejects with `BUS_CONNECTION` at once, including while a background reconnect attempt is in flight, until a reconnect succeeds; nothing is queued for later (BUS-NAT-CONN-005). Rejecting at once keeps heartbeats and frames from piling up behind a dead connection: a heartbeat or frame that cannot go out now is worthless later, and each failure reaches the caller's warn log (BUS-STREAM-007) at the moment it happens.
- **Drain after a read failure.** After any read failure in `subscribe` (once its backoff sleep ends), the loop goes back to cursor `0` and drains this consumer's pending entries again before returning to `>`, with the same drain rules as at the start (BUS-SUB-003). Entries Redis handed to this consumer in a reply that never arrived are therefore delivered late rather than lost. The acks still queued from before the failure travel in the pipeline of that first cursor-`0` read, ahead of the `XREADGROUP`, so every entry whose handler had already run is acked before the drain reads the pending list and is not delivered again. An entry whose ack Redis refused (reported in `ackErrors`) is still pending, so the drain after a later read failure delivers it once more (BUS-SUB-008); within that drain the cursor has moved past it, so it is not read twice. An entry whose ack was refused on both deliveries is in the dropped set, and every later drain skips it without handling or acking it (BUS-NAT-ACK-008).
- **`failFast`** (BUS-STREAM-009): the shared connection is never re-established. The boot phase is the same as without it: a command issued while the first attempt is in flight waits for it, so a refused connection fails within milliseconds and an unanswered one within the 10 s connect timeout; after a failed attempt, or once an established connection drops, every command rejects with `BUS_CONNECTION` at once. Nothing is printed, because the native layer never writes to stdout or stderr. The rejection's message names the cause (BUS-NAT-ERR-009), which `cohostctl` prints (CTRL-CLI-017).
- The connect timeout is 10 s for every attempt: the shared connection's first attempt, its background reconnects and each reader's connect (BUS-NAT-CONN-007).

### Rust service codec and contract fixtures

A Rust service does not run zod. `crates/cohost-bus` carries a hand-written, typed serde codec for exactly the event types a Rust service publishes or reads, plus the registration value and the frame. The first set is `service.heartbeat`, the registration and the frame, which is what a Rust connector needs; a type is added to the codec, with its fixtures, when a Rust service first touches it. The codec mirrors the zod schema's rules for that type: required and optional members, enums, ranges, and the defaults zod applies on parse.

The contract between the two codecs is a set of shared JSON fixtures in `packages/bus/fixtures/contract/`:

- `events/<type>/<case>.json`: `{ "payload": ..., "valid": true|false, "parsed": ... }`, where `parsed` (valid cases only) is the payload as zod returns it (defaults applied, unknown keys removed).
- `registration/<case>.json`: the same shape for a registration value.
- `frames/<case>.json`: an entry's field list (binary values base64-encoded) and the expected `DecodedFrame` (`ok` with the frame, or the `reason`).

Both sides consume every fixture of the types they implement. `packages/bus/test/contract.test.ts` checks each event and registration case against the zod schema (`safeParse` success equals `valid`; the parse result deep-equals `parsed`) and each frame case against the native `decodeFrame`. `crates/cohost-bus/tests/contract.rs` reads the same directory (resolved from `CARGO_MANIFEST_DIR`), checks that its codec accepts exactly the valid cases, that serialising what it parsed gives JSON equal to `parsed`, and that its frame decoder gives the expected result. A schema change in `events.ts` for a type in the Rust codec therefore fails a test until fixtures and Rust codec agree. Fixtures for types outside the Rust codec are read by the TS test only.

### Build, CI and Docker

- **Local build.** `pnpm build` and `pnpm test` both run `build:native` before `tsc -b`: `cargo build --release -p cohost-bus-node` followed by a copy of `target/release/libcohost_bus_node.so` to `packages/bus/native/cohost-bus.linux-x64-gnu.node`, so the addon exists before any test (BUS-NAT-BLD-002). The `.node` and Cargo's `target` directory are build outputs, ignored by git (BUS-NAT-BLD-003) and excluded from the Docker build context (deployment DEPLOY-IMG-004). A developer needs the Rust toolchain of `rust-toolchain.toml`; `scripts/install.sh` installs it through rustup and builds the addon on the host (deployment DEPLOY-INST-014).
- **One addon, two builders.** `crates/cohost-bus-node` is a `cdylib`, and its plain `cargo build --release` output `target/release/libcohost_bus_node.so`, copied under the name `cohost-bus.linux-x64-gnu.node`, is the whole addon: the napi CLI adds only the copy and the name. `native.ts` declares the binding's TypeScript types itself and uses no file the napi CLI generates, so an addon built without the CLI loads and typechecks the same (BUS-NAT-BLD-009).
- **Target.** linux-x64-gnu only (BUS-NAT-BLD-006): Docker images are `node:22-slim` (Debian, glibc), CI is ubuntu, and every Node process that uses the bus runs in one of them or in WSL on the same target. The addon does not load on macOS, arm64 or a Node process on the Windows host; a Node tool there that needs the bus runs inside WSL. A Rust program on the Windows host, such as the desktop capture helper (connections CONN-DESK-001), links `crates/cohost-bus` directly and needs no addon.
- **Locating the addon.** `native.ts` loads `../native/cohost-bus.<platform>-<arch>-gnu.node` relative to its own file with `createRequire(import.meta.url)`, and nothing else: no search path, no environment override, no fallback transport. On any other platform, or when the file is missing or fails to load, importing `@cohost/bus` throws an error naming the platform and arch it looked for, the path, and `pnpm build:native`.
- **Docker** (deployment DEPLOY-IMG-001). A `native` stage `FROM rust:<toolchain>-slim-bookworm` (the Debian release `node:22-slim` is built on, so the addon links against the same glibc) runs plain `cargo build --release` on the workspace and copies the cdylib to `cohost-bus.linux-x64-gnu.node`; the stage has neither Node nor the napi CLI. The `build` stage copies that file into `packages/bus/native/` before `tsc -b`. Every service image carries the addon, since every service uses the bus. The runtime stage needs no Rust.
- **CI** (deployment DEPLOY-CI-001). The `test` workflow installs the pinned toolchain and, with the job's Redis service and `REDIS_URL`, runs `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings` and `cargo test --workspace` (Rust integration tests use their own stream prefix, as the TS tests do, BUS-NAT-CI-002), then `pnpm test`. Cargo's registry and target directory are cached between runs, and the job's timeout is 20 minutes, room for a Rust build with a cold cache.
- **Release profile.** `panic = "unwind"` (BUS-NAT-BLD-007), so a panic inside a Rust future is caught at the boundary and becomes a `BUS_INTERNAL` rejection rather than aborting the process (BUS-NAT-ERR-006). A test reaches that path through the test-only cargo feature `test-panic`, which adds a binding call that panics inside its future; no release build enables it (BUS-NAT-ERR-011).

### Measurement gate

The native transport merges only if, on `scripts/dev/bus-bench.ts --sources 8 --runs 3` (default 20 s per phase) against the same Redis and machine, run on the branch and, back to back, on the branch's merge base (the TypeScript transport, since the branch removes it), all of these hold when the medians over the three runs of the `frames x8` and `events x8` rows are compared between the two transports (BUS-NAT-GATE-001):

- the **frames path** (`publishFrame` / `tailAudio`) median process CPU is at least 40% lower than the TypeScript transport's (the `cpu%` column, from `process.cpuUsage`, which counts the addon's runtime threads too; native at most 0.6 times TypeScript; BUS-NAT-GATE-002);
- the frames path's median **p99 hop latency is not worse**: at most 1.1 times the TypeScript transport's median p99 (BUS-NAT-GATE-003);
- the **events path** (`publish` / `subscribe`) median process CPU is no greater than the TypeScript transport's (BUS-NAT-GATE-004); and
- the events path's median **p99 hop latency is not worse**, by the same 10% bound (BUS-NAT-GATE-005).

Three runs and their medians keep one noisy run from deciding the merge; the 10% bound on p99 allows for the run-to-run noise of a tail percentile measured over a 20 s phase, so "not worse" means not worse beyond that noise. The bench gains `--runs N`, which repeats every phase N times and prints the per-row medians, and `--json`, which writes every run's rows and the medians as one JSON document, so the two transports' results can be compared by a script rather than by reading tables (BUS-NAT-GATE-007). The bench's `p99ms` column is the hop latency and its final PASS/FAIL line (p99 under 5 ms) is a separate sanity bound, not the gate. The bench measures both paths in one process with publisher and consumer on one clock; its events path is a `chat.message` carrying base64 PCM at audio rate, a worst case for that path rather than real traffic. On the branch the bench runs on the native transport; its scratch-stream cleanup still uses ioredis, which stays a devDependency used only by tests and the bench, never by runtime code (BUS-NAT-API-003). The events-path conditions exist because every domain event rides that path: a transport that sped up audio while slowing the speech and chat chain would trade one latency budget for another. The reference run recorded with the HLD is 7.7% of a core and 1.75 ms p99 for the TypeScript frames path at 8 sources; the gate compares against fresh TypeScript runs on the same machine, not against that number. If the gate is missed after the per-frame-object lever above, the native transport is not merged: the TypeScript transport stays, the branch is closed with its numbers recorded, and the HLD's Native layer section is revised to match (BUS-NAT-GATE-006).

### Native design constraints

Properties of the native layer that shape its code but that no test observes from outside; review checks them.

- **N1. Rust never calls into JavaScript.** No threadsafe functions and no callbacks from the runtime; each read-loop iteration is one awaited `readGroup`, `read` or `readFrames` call that returns a whole batch ([Crossing the napi boundary](#crossing-the-napi-boundary)).
- **N2. Outbound bytes are not copied into the JS heap.** `readFrames` and `takeUpload` hand Node an external `Buffer` that owns the Rust allocation, freed when V8 collects it. The observable half, that such a `Buffer` keeps its content while referenced, is BUS-NAT-TRN-010.
- **N3. One tokio runtime per process.** Created when the addon is first loaded, with one worker thread unless the measurement gate shows that more helps; every I/O method is a Promise resolved from a future on it.

### Edge-case probe

What the native transport does in situations the sections above do not make obvious.

| # | Situation | Expected behaviour |
|---|---|---|
| 1 | Connection drops while `XREADGROUP` is blocked | The read rejects `BUS_CONNECTION`; the facade logs warn and backs off; the next `readGroup` reconnects. Entries Redis delivered to this consumer whose reply never arrived stay in its pending list; after the backoff the loop returns to cursor `0` and drains them, so they are delivered late, not lost. Queued acks are kept and sent ahead of that first drain read, in its pipeline. |
| 2 | Pending-entry drain on process restart | The new process has a new consumer name, so its cursor-`0` read returns nothing and the loop moves to `>` at once; the predecessor's pending entries are not claimed (BUS-SUB-003, BUS-SUB-008). |
| 3 | A pending entry was trimmed from the stream before the drain read it | Redis returns the id with no fields; the transport returns a `RawEntry` without fields; `decode` treats it as undecodable, the facade acks it without logging, and the drain moves on (BUS-SUB-007). |
| 4 | An entry with unknown `type`, non-JSON `data` or a failed schema | Unchanged: not delivered, acked in `subscribe`, skipped in tails and `recent`, no log line (BUS-SUB-007, BUS-TAIL-002). |
| 5 | An envelope field (`type`, `ts`, `source`, `data`) that is not valid UTF-8 | The entry is poison: the transport returns it with no fields, `decode` treats it as undecodable, and it is dropped (acked in `subscribe`, skipped in tails and `recent`) without a log line, as BUS-SUB-007. No lossy decode: an entry is never delivered with text the publisher did not write. |
| 6 | A frame read with `pcm` over `MAX_FRAME_BYTES`, odd length, wrong version, or no `pcm` | `readFrames` returns `{ ok: false, reason }` for it; the consumer drops and counts it (CONN-BP-006, CONN-AUD-002). |
| 7 | `publishFrame` called with `pcm` over `MAX_FRAME_BYTES` or with an odd byte count | Rejects with `BUS_INVALID` before writing anything; the producer learns of the bad frame at its source instead of every consumer dropping it. Consumers still drop such a frame if one reaches the stream by another writer (row 6). |
| 8 | A `subscribe` handler throws or rejects | The facade catches it, logs `handler failed` at error, queues the ack, continues (BUS-SUB-005). Rust is not involved: it never calls a handler. |
| 9 | A handler is slower than the producer | The next read waits for the batch; the backlog stays in Redis. If the group falls more than the stream cap behind, `MAXLEN ~` trims entries it never read and `>` resumes at the oldest entry left; those entries are lost, consistent with at-most-once. Process memory holds at most one batch (50 entries; for frames 100 entries of at most 64 KiB). |
| 10 | Tail handler returns a slow Promise | As today: tail handlers are guarded, not awaited, so the read loop does not wait for them (BUS-TAIL-004); bounding their concurrency is the handler owner's concern. |
| 11 | `stop()` with acks queued but not yet sent | `close()` sends them on the shared connection before closing; `stop()` resolves after that flush whether or not it succeeded, and at the latest 2000 ms after `close()` was called, abandoning a flush that has not completed (BUS-NAT-ACK-007). A refused or abandoned ack leaves its entry pending under a consumer name never used again; with at-most-once delivery across restarts that costs only pending-list space. |
| 12 | `stop()` while a read is blocked, or while `createGroup` is in flight | `close()` interrupts the read, which rejects `BUS_CLOSED`; the facade sees `stopped` and resolves the promise without logging (BUS-STOP-001). A `createGroup` that rejects after `stop()` also resolves `subscribe` quietly instead of rethrowing. |
| 13 | Redis down at boot | Constructing the `Bus` does not throw. A command issued while the first connect attempt is in flight waits for that attempt (at most 10 s; a refused connection settles it at once), and once it has failed every command rejects with `BUS_CONNECTION` at once until a background reconnect succeeds; `subscribe` rejects from `createGroup` (BUS-SUB-001), which a service's bootstrap reports as `fatal` and exits (SHARED-BOOT-003). With `failFast` the same first wait applies, there is no background reconnect, and nothing is printed (BUS-STREAM-009). The container healthcheck's own 4 s limit (CTRL-CHECK-002) ends a check that waits on a connect attempt Redis never answers. |
| 14 | Redis goes away while services publish | `append` rejects with `BUS_CONNECTION` at once while the shared connection is down; the facade logs it at warn and rethrows (BUS-STREAM-007). Publishing works again as soon as the background reconnect succeeds. |
| 15 | Two `Bus` instances with the same consumer name | The name is still `HOSTNAME-<8 hex>` built in the facade (BUS-STREAM-005); a collision would make two instances share one pending list. Accepted as negligible (32 random bits); no detection. |
| 16 | Several subscribers and tails in one process | Each loop has its own reader and connection, as today; blocking reads never share a connection. Non-blocking commands of every loop and every publish share the one multiplexed connection. Connections per process: 1 + loops. |
| 17 | Many concurrent `publish` or `publishFrame` calls without awaiting | Commands enter the shared connection in call order and Redis applies them in that order, so stream order equals call order for one `Bus` (frames' `seq` stays monotonic in the stream). |
| 18 | The `.node` is missing, built for another platform, or the host is not linux-x64-gnu (Windows, macOS, arm64) | Importing `@cohost/bus` throws the load error described in Build; there is no fallback. linux-x64-gnu is the only supported platform. |
| 19 | A large JSON payload or a large `recent(count)` | Parsing and zod validation stay on the Node event loop exactly as today; the native layer neither adds nor removes that cost. Batch sizes (50 group, 100 tail) bound the work per loop turn. |
| 20 | Clocks: envelope `ts`, `timing` stamps, `serverTime` | `ts` is stamped by the facade with `Date.now()` before `append`, so `timing` stamps that copy an envelope `ts` (`heardAt`, `focusedAt`) mean what they mean today. A Rust service stamps `ts` from its system clock in epoch ms. `serverTime` is Redis `TIME` on the shared connection (CTRL-CHECK-004); the transport never substitutes it for `ts`. |
| 21 | The caller reuses or mutates a `Buffer` it passed to `publishFrame` or `putUpload` | Safe once the call has returned: the bytes were copied synchronously. |
| 22 | A `Buffer` returned by `readFrames` or `takeUpload` is kept long after the read | Safe: it owns its memory until V8 collects it; a held frame keeps only its own allocation alive. |
| 23 | A Rust panic inside a transport call | Caught at the boundary; the call rejects `BUS_INTERNAL` and the loop backs off like any read failure. The process does not abort. |
| 24 | A call after `stop()` | Rejects `BUS_CLOSED`; `publish` logs it at warn and rethrows as any failed write (BUS-STREAM-007). A second `stop()` resolves once the first close has completed (BUS-NAT-ERR-008). |
| 25 | An ack refused by Redis (for example `NOGROUP` after the group was destroyed) | Reported in the next `readGroup`'s `ackErrors`, logged at warn `ack failed`, not retried; the entry stays pending. The same read most likely fails with `NOGROUP` too and backs off; the drain after that failure delivers the entry once more (BUS-SUB-008). If the ack of that redelivery is refused too, the facade logs `ack failed, entry dropped` and no later drain delivers it again (BUS-NAT-ACK-008). |
| 27 | `stop()` while the first connect attempt is still in flight | `close()` abandons the attempt and the commands waiting on it reject `BUS_CLOSED` (BUS-NAT-ERR-010); `close()` has nothing to flush or abandons the flush at 2000 ms, so `stop()` resolves without waiting out the 10 s connect timeout. |
| 26 | Events path latency or CPU worse than TypeScript while the frames path passes the gate | The gate is missed and the native transport is not merged (Measurement gate). |

`voice.stop` orders the body to stop speaking now: `reason` is a free string naming why (salience publishes `barge-in`), `ids` narrows the order to the named `brain.say` ids and, when absent, means every line voice holds and every line a mouth output holds or plays. It is an order and not a report: it carries no sink, and the events that report its effect are the ordinary `voice.done` (flagged `interrupted`) from each sink that was playing. It is not a mute: a `brain.say` published after it is spoken as usual.

`voice.failed` reports that a sink gave up on an utterance; `fallback` is present when the sink plays a pre-generated fallback clip in the line's place. `voice.playing` and `voice.done` keep their shape: a fallback clip is reported through them as ordinary playback under the given-up id.

### Injection flags

Added by the `add-test-injection` change. `injected` marks an event that came from the dashboard test-injection panel; `remember` says whether an injected event may be persisted to long-term memory (`remember` is meaningful only when `injected` is true; `services/memory/src/region.ts:13` `skipInjected`). The five flagged types are `chat.message`, `vision.summary`, `speech.heard` (the perception inputs) and `brain.say`, `attention.focus` (derived outputs that carry the flags of the input that caused them). Real traffic never carries the keys: zod `.optional()` with no default leaves them absent (asserted at `bus.test.ts:321-333`). Copying flags from an input onto a derived output is done by `propagatedFlags` in [working-memory](../working-memory/working-memory-design.md), not here.

### Other schema notes

- `control.target` is optional so old publishers stay valid (`events.ts:178` comment).
- `voice.utterance.audioUrl` is a path on the voice service (`/audio/<id>.wav`); its comment names no host or port.
- `route` (BUS-EVT-023) is one optional string-array schema shared by `control` (meaningful for `say`), `brain.say` and `voice.utterance`: the list of mouth output ids a line is for. The producers copy it down the chain unchanged (cortex, voice); only mouth reads it. Absent means every enabled output, so old publishers stay valid.
- `voice.playing` is the schema `PlaybackReport` (`id`, `sink`); `voice.done` extends it with `interrupted?` (the literal `true`), `spokenText?` and `unsaidText?` (BUS-EVT-017, BUS-EVT-031). `interrupted` marks a line that `voice.stop` ended before its audio finished; `spokenText` is the part of the line's text that had been spoken and `unsaidText` the rest, both present only when the publishing sink could compute them from the line's timing (mouth, [mouth](../mouth/mouth-design.md) Stopping a line) and absent otherwise. No consumer reads the two texts in this release: the transcript keeps the line as it was meant to be said.
- `avatar.state` carries ranges, as `affect.state` does (BUS-EVT-018): `intensity`, `mouthOpen`, `mouthSmile` and `blink` 0..1, `eyeX` and `eyeY` -1..1, and the head angles `headX`, `headY`, `headZ` in degrees -90..90 (the avatar's own yaw range is -30..30; the bound here rejects only a corrupt value).
- `speech.partial` (BUS-EVT-026) is an interim, unstable transcript of an utterance that is still open: `text` is the words ears has committed so far (the stable prefix of its latest transcriptions, [ears](../ears/ears-design.md) Partial transcripts), `seq` counts the partials of one utterance from 0 and `utteranceId` names the utterance, the same id the final `speech.heard` carries (BUS-EVT-027). A consumer holds only the latest partial of an utterance (a later one replaces the earlier) and treats it as stale after `PARTIAL_STALE_MS` or when the utterance's final or the speaker's next utterance appears (BUS-EVT-028), so a partial whose utterance ended without a final does not linger. It is never a final transcript and has no injection flags: injection delivers whole clips. `speech.heard` stays the one final event.
- `timing` (BUS-EVT-024) is one optional schema, `Timing`, shared by `speech.heard`, `speech.partial`, `vision.summary`, `attention.focus` and `brain.say`: up to eight optional integers, each an epoch-millisecond stamp from the publishing service's clock: `audioEndedAt` (ears: the last audio of the utterance arrived), `heardAt` (the `speech.heard` envelope `ts`), `capturedAt` and `describedAt` (eyes: the frame's screenshot returned, and the vision model's reply returned), `focusedAt` (the `attention.focus` envelope `ts`), `llmStartedAt` and `llmEndedAt` (cortex: the first LLM request of the think, and the return of its reply call, the critic excluded) and `criticEndedAt` (cortex: the return of the critic hook's call, present only when the critic ran). Every member is optional and a non-negative integer; the schema bounds the numbers and nothing else, so a reader tolerates any member being absent. Each stage copies the object it received, adds only its own stamps, and never changes or removes a stamp it received (BUS-EVT-025), so the `brain.say` that answers a spoken line or a screen change carries the whole chain; a line with no such trigger (chat, an operator `say`, a reflex) carries only the stamps its own stage adds, or none. The bus validates the shape only; which stamps appear is each producer's spec ([ears](../ears/ears-design.md), [salience](../salience/salience-design.md), [cortex](../cortex/cortex-design.md)), and the report that reads them is [control-plane](../control-plane/control-plane-design.md) (Latency report).
- `EVENT_TYPES` (`events.ts:261`) is exported and used by the dev scripts `scripts/dev/bus-pub.ts` and `scripts/dev/bus-tail.ts` and by tests; `decode` uses `type in EventPayloads` instead (`index.ts:296`).

## Test double: `packages/testing/src/index.ts`

  - `published: { type, data }[]` holds the zod-parsed payload of each accepted publish; `of(type)` returns the payloads of one type, `types()` the type sequence, `clear()` empties both `published` and `health`.

- `event(type, data, source="test")` (`:84-86`): builds a `BusEvent` as a subscriber would receive it, with `EventPayloads[type].parse(data)` (defaults applied), `ts: Date.now()`, and a time-ordered id from the same generator as the fake bus (BUS-TEST-011).

Each call registers another `beforeShutdown` hook in the module-global list (never removed); harmless in tests, a small leak.
- `waitFor(cond, what="condition", ms=2000)` (`:106-112`): polls every 2 ms and throws `timed out waiting for <what>`.

## Decisions & Alternatives

| Decision | Chosen | Alternatives Considered | Rationale |
|----------|--------|------------------------|-----------|
| Upload bytes | A plain Redis string `cohost:upload:<id>` with a TTL, written by `putUpload` and read-and-deleted by `takeUpload` (`GETDEL`), on the bus's publish connection; the event carries only the id | Base64 in the event; an HTTP fetch from the dashboard | The stream is capped at 20000 entries and replayed to every group and `/ws` backfill, so megabytes do not belong on it; containers cannot always reach the host, but all of them reach Redis. A TTL means a key nobody reads (service down) expires by itself. |
| Pending drain | Read this consumer's pending entries batch by batch, the cursor following the last id seen, until a read returns none; on the native transport a drain runs at the start of `subscribe` and again after every read failure | One batch only; always re-read from `0` | A cursor that follows the ids ends even when an entry cannot be acked and so stays pending; re-reading from `0` within a drain would loop on it (BUS-SUB-003). |
| Stop during a handler | The running handler finishes; its entry is not acked and the rest of the batch is neither handled nor acked | Ack on the closed connection; cut the handler short | `stop()` closes the connections, so an ack would fail on a dead socket; an unacked entry is at most once in effect because the next process has a new consumer name (BUS-SUB-013, BUS-SUB-008). |
| A `Bus` is single-use | `stop()` is instance-wide and final; one instance is never restarted | Reset `stopped` on a new `subscribe` | Every service builds one bus for its life and stops it once at shutdown; restart support would add states nothing uses. |
| Streams for tests | `BusOptions.streamPrefix` names an instance's stream pair; integration tests each use their own and delete it | Production keys with unique group names and best-effort cleanup | Tail and `recent` read the whole stream, so group names alone cannot keep a test off other traffic in a shared dev Redis (BUS-STREAM-008). |
| `avatar.state` and playback shapes | Ranges on every `avatar.state` number; `voice.done` is `PlaybackReport` plus three optional interruption fields, `voice.playing` is `PlaybackReport` alone | Leave `avatar.state` unconstrained; two unrelated schemas | A corrupt value should fail at the producer's publish rather than reach a driver or the preview; the two playback events keep one shared base so the shape cannot drift (BUS-EVT-017, BUS-EVT-018). |
| Interruption on the playback events | A separate `voice.stop` order; the interrupted line ends with the existing `voice.done` carrying `interrupted` | A new `voice.interrupted` report event; `voice.done` alone, with each service inferring the stop from a consumer-specific event; `voice.failed` for an interrupted line | Cortex, avatar and any later consumer already release on `voice.done`, so an interrupted line needs no new release path; an interrupted line is not a failure, so `voice.failed` (which triggers the fallback line) is wrong for it. The stop itself is a command to several services at once, which a report event cannot be. |
| `voice.stop` addressing | `ids?` narrows the order; absent means everything | A required id; a boolean `all` | Salience stops whatever is speaking without knowing which lines voice and mouth hold, so the common order names none; a later caller that wants one line can name it. |
| Fake ids | `FakeBus` and `event()` produce Redis-form `<ms>-<seq>` ids that strictly increase | Random uuids; counters | Code that sorts or compares ids behaves the same against the fake as against Redis (BUS-TEST-011). |
| Logging undecodable entries | A poison entry (unknown type, non-JSON data, failed schema) is acked and dropped without a log line | Log each one; log at a rate limit | The HLD's transport decision drops poison events without logging so one bad producer cannot flood every consumer's log; a producer/consumer schema mismatch shows up in the producer's tests, since both sides validate against the one registry. Owner decision (gap-closure dispositions, event-bus O7). |
| Transport | Redis Streams with consumer groups, one stream for all domain events | Pub/sub, per-event-type streams, direct HTTP between services | Services never talk to each other directly so any piece can be swapped (header comment `events.ts:5-8`), and each service's group keeps its own read position (comment `index.ts:20`). Streams rather than pub/sub because pub/sub drops whatever is published while a subscriber is disconnected and keeps no history, whereas a stream gives each group a stored position (needed by `resume` subscribers such as memory) and a bounded backlog that the dashboard backfill reads (`recent`). One stream rather than one per type keeps a single total order across types, lets a service read everything it needs with one `XREADGROUP`, and bounds memory with one `MAXLEN`. |
| Validation | zod schema per type, parsed on publish and on read | Validate only on publish; trust the stream | Publish-side parsing rejects a bad payload at its source with a readable error. Read-side parsing is needed because the stream is not guarded by `publish` alone: anything with Redis access can `XADD` an entry, and during a partial restart services built from different versions of the schema share the stream. Parsing on read also applies zod defaults, so a subscriber always receives `EventData<T>`. An entry that fails is dropped and acked rather than delivered half-typed or left to wedge the group. `index.ts:82` and `index.ts:305`, with the malformed-entry test at `bus.test.ts:84-98`. |
| Heartbeats on a separate stream | `cohost:health`, `MAXLEN ~ 1000` | Same stream as events | Comment `index.ts:10`: heartbeats live on their own capped stream "so they never evict domain events" from the 20000-entry cap; `publish` hard-rejects the type at `index.ts:49`. Introduced with that split in commit `691b079`. |
| Handler failure | Log, ack, continue | Leave pending and retry; dead-letter stream | Owner decision 2026-11-01: delivery is at most once, and a poison event must not wedge a live co-host. Pinned by the XPENDING assertion at `bus.test.ts:56-81`. |
| Delivery across restarts | At most once: a dead process's unacknowledged entries are not redelivered (BUS-SUB-008) | At least once via stable consumer names plus `XAUTOCLAIM` of dead consumers' pending entries | Owner decision 2026-11-01: nearly every subscriber wants only fresh input and handlers already ack on failure, so redelivery would only replay a line the co-host has moved past; the in-process pending drain stays. |
| Start position after a restart | Explicit per-subscription start mode: `latest` resets the group to `$` on every start, `resume` keeps the stored position; memory uses `resume`, every other subscriber `latest` (BUS-SUB-002, BUS-SUB-010, BUS-SUB-011) | `fromNow` that only positions a new group (an existing group always resumes); leave the reset to control-plane `fresh` starts | Owner decision 2026-11-01: a compose or crash restart must not make the co-host speak, react to or animate stale events, while memory still stores what it missed. Putting the choice in the subscription makes it hold for every restart path, not only control-plane starts. |
| Subscribe and tail read failures | Log and retry with a capped, growing delay; guard tail handlers (BUS-SUB-009, BUS-TAIL-003, BUS-TAIL-004) | Reject the promise and let the process crash for compose to restart; leave reconnection to the Redis client alone | Owner decision 2026-11-01: an unhandled rejection ends a Node 22 process, and a crash-restart loop hides the cause behind a container restart instead of a log line. |
| `onShutdown` with several registrations | One sequence: hooks once, every callback to completion with errors logged, exit 0 once; synchronous hook throws treated like rejections (SHARED-LIFE-004, SHARED-LIFE-005) | Each registration exits on its own; exit non-zero when a callback fails | Owner decision 2026-11-01: services such as eyes and ears register more than one cleanup, and a failing cleanup must not skip the others; exit 0 keeps compose from treating a deliberate stop as a crash. |
| Per-kind `inject.request` completeness | Checked by each target service's `inject.ts`, which answers `inject.result` | Enforce `url` / `text` per `kind` in the bus schema | Owner decision 2026-11-01: the target service already validates and reports a readable failure to the dashboard; a schema rejection would only surface as a publish error. | Ownership of heartbeat transport and shutdown mechanics | event-bus owns `publishHealth` / the `cohost:health` stream (BUS-STREAM-004, BUS-HEALTH-001 to 004) and the `onShutdown` / `beforeShutdown` sequence (BUS-STOP-001 to 006); control-plane owns heartbeat meaning and the heartbeat's `beforeShutdown` registration (SHARED-LIFE-010) | Restate the same statements in both segments | Owner decision 2026-11-01: one spec line per behaviour; the code entry points carry one segment's IDs. |
| Type filtering | Client-side after read; filtered entries acked | One group/stream per type | Follows from the single stream: each service group reads the whole stream, delivers the types it asked for and acks the rest so nothing stays pending (`index.ts:209-222`). | Fresh start of a service | `resetGroup` moves the group to `$` | Delete and recreate the group | The doc comment `index.ts:155-158` says it exists for "fresh" service starts; commit `1d316ff` adds it with the controller's fresh/resume start (`packages/control/src/controller.ts:42`). `SETID` is one atomic command that keeps the group in place; `DESTROY` then `CREATE` is two commands, and a reader of the group between them would fail with `NOGROUP`. | Test double | `FakeBus` implements only the publish and health halves, with real zod validation | Mock Redis; full in-memory bus | Comment `packages/testing/src/index.ts:42`: it "validates like the real Bus, records instead of talking to Redis". | Path timing | An optional `timing` object of epoch-ms stamps on `speech.heard`, `vision.summary`, `attention.focus` and `brain.say`, one schema for the speech and vision paths, extended stage by stage; publish times of every other event come from the envelope `ts` (BUS-STREAM-001) | A separate vision timing schema (twice the carry-over rules for the same chain); a new `latency.sample` event published by the last stage; a top-level timing field on every event type; a trace id with a separate timing store; monotonic clock stamps | Additive fields leave every old publisher and reader valid and add no event type (the catalogue stays 24). Epoch ms, not a monotonic clock, because a monotonic reading is meaningful only inside one process and the stages run in different ones; the services share one host clock (HLD, Speech-path latency and Vision-path latency), so a stamp difference is a duration up to that clock's own steps. A publisher on another host (a Windows helper against WSL services, say) can disagree with that clock; the reader excludes any resulting negative duration (CTRL-LAT-007) and a skewed but positive one is not detectable. |
| Where the stale rule lives | In the event bus package, with the partial's own contract, as a constant and a pure function | In ears (it cannot know what consumers hold); in the dashboard, the only UI | Staleness is a property of the event contract that every consumer, today none, would share; the dashboard has no row for partials yet and would only copy it. 5000 ms is several partial steps (default 1000 ms) so a slow backend's gap between partials is not mistaken for an ended utterance. |
| Split between Rust and TypeScript | Rust owns transport (connections, commands, ack batching, key and stream naming, caps, frame codec, tag grammar); the TS facade owns validation, decode, the envelope and every loop's control flow | Rust validates too, from generated schemas; Rust owns the read loops and calls handlers through threadsafe functions | zod is the one registry and `FakeBus` plus the service tests depend on it; generating Rust schemas for the whole catalogue is a project of its own (Deferred). Keeping loop control in TS keeps BUS-SUB-* and BUS-TAIL-* where they are implemented and tested today, and Rust never re-enters JavaScript, so there is no callback lifetime, re-entrancy or handler-await protocol across the boundary. The cost is one boundary crossing per batch, which batching makes small. |
| Facade kept | `Bus` keeps its public API; only the test seam changes | A new native-shaped API that services adopt | 49 publish and 13 subscribe call sites, `FakeBus` and every `Pick<Bus, ...>` type stay untouched, so the change is confined to this segment and its benchmark compares like with like. |
| Test seam | A `BusTransport` interface at batch and command granularity, implemented by the binding and by test fakes | Keep faking ioredis connections; fake the napi module's raw exports; test the facade only against a real Redis | The facade's decisions (start mode, drain cursor, backoff, ack after handler, stop) are made on transport results, so a fake at that level scripts exactly the cases the resilience tests need without imitating a Redis client. Named `BusTransport` because `Transport` already names a connector capability's transport. |
| Node binding | napi-rs | neon; a C ABI with `ffi-napi` or `koffi`; a sidecar process over a socket | napi-rs uses Node-API, which is ABI-stable across Node versions, maps Rust futures to Promises on its tokio integration and builds with `@napi-rs/cli`. neon covers the same ground with a smaller async story; an FFI library adds a per-call marshalling cost and an unmaintained-native-dependency risk; a sidecar adds a hop per event. |
| Native language | Rust | Go; C++; Zig | A Go shared library cannot load into Node in-process without cgo and a second runtime and garbage collector in the process; Rust has no runtime to host, mature async Redis and Node-API crates, and the crate is reused unchanged by Rust services. C++ and Zig would give up memory safety at the boundary for no gain here. |
| Redis client crate | `redis` (redis-rs) with tokio multiplexed connections | `fred`; a hand-written RESP client | redis-rs is the most widely used client, supports pipelines, multiplexing and stream commands, and is what a Rust service would pick anyway. A hand-written client would own protocol bugs for no measured benefit. |
| One path | The TS Redis client is removed from runtime code when the native transport merges; no fallback, no flag. ioredis stays a devDependency for tests and `scripts/dev/bus-bench.ts` (BUS-NAT-API-003) | Keep ioredis as a fallback or behind a switch | Pre-alpha: nothing is deployed that a second path would protect, and two transports would double the behaviour this segment must specify and test. The measurement gate decides before merge whether the native transport replaces the TS one at all. |
| Ack batching | Queue acks and send them in the next read's pipeline | One awaited XACK per entry; a timer-driven flush | Per-entry XACK costs a round-trip per entry; tying the flush to the next read keeps the ack-after-handler order and at-most-once semantics, and needs no timer. |
| Addon loading | One fixed path beside the package, linux-x64-gnu, no fallback | Prebuilt binaries for many platforms (macOS, arm64, Windows); a search path; an environment override | Every deployment is the Debian Docker image, the ubuntu CI or WSL; one path makes a load failure unambiguous, and each extra platform would add a build target and a CI leg nothing deployed needs. |
| Shared-connection commands while Redis is down | Reject with `BUS_CONNECTION` at once from a failure until a reconnect succeeds, including during a reconnect attempt; only the first connect attempt after construction is waited for, at most 10 s, with or without `failFast` | Queue and wait a bounded time for the reconnect (the ioredis behaviour: queue, give up after three reconnect attempts) | A heartbeat or frame that cannot go out now is stale by the time Redis returns, and a queue only delays the failure the caller must log anyway; rejecting at once puts each failure in the log when it happens. |
| Pending entries after a read failure | Return to cursor `0` and drain this consumer's pending entries after every read failure; an entry whose ack Redis refused is redelivered once by that drain (BUS-SUB-008) | Drain only at the start of `subscribe`, losing entries whose reply was lost | Late delivery over loss: an entry Redis already assigned to this consumer is one the co-host would otherwise silently miss within one process lifetime; queued acks precede the drain read, so handled entries are not repeated. |
| Entry whose ack is refused | Redelivered at most once by a later drain; a second refusal drops it with a warn log, and later drains skip it (BUS-NAT-ACK-003, BUS-NAT-ACK-008) | Skip it from the first refusal (no redelivery); redeliver it on every drain until an ack succeeds | One redelivery gives an ack that failed for a passing reason a second chance without losing the entry. A second refusal shows the ack cannot succeed (the group is gone, say), and redelivering on every drain would repeat the same line after each read failure for as long as the fault lasts. The records of refused and dropped ids hold only refused acks, which are rare, so they need no expiry. |
| Acks queued at `stop()` | `close()` flushes them on the shared connection, abandoning the flush after 2000 ms, so `stop()` is `Promise<void>`, resolves within about 2 s, and the shutdown sequence awaits it | Keep `stop()` synchronous and leave up to one batch of handled entries pending; an unbounded flush | Pending lists would grow by a batch on every shutdown under consumer names never used again; one extra round-trip at shutdown avoids that. The cap keeps a hung Redis from holding a container past Compose's stop grace period: 2 s of `beforeShutdown` hooks, 5 s of teardown steps and 2 s of bus stop fit in its 10 s (SHARED-BOOT-006). |
| Non-UTF-8 envelope fields | The entry is poison: dropped and acked without a log line | Decode lossily, replacing invalid bytes with U+FFFD (the ioredis behaviour) | A lossy decode can deliver text the publisher never wrote; no cohost publisher writes non-UTF-8, so such an entry comes from a foreign writer and is treated like any other undecodable entry (BUS-SUB-007). |
| Frame size and alignment on publish | `publishFrame` rejects a `pcm` over `MAX_FRAME_BYTES` or with an odd byte count with `BUS_INVALID`, writing nothing | Write it and let every consumer drop it | The producer is the one place that can fix a bad frame; writing it would only spend stream space and make every consumer count a drop. |
| Gate scope | The gate covers the frames path and the events path (CPU and p99 on both) | Frames path only, events path reported | Every domain event rides the events path; a transport that slows it would move latency from audio onto the speech and chat chain. |
| Gate statistics | Three runs per transport; medians compared; p99 "not worse" means within 10% of the TypeScript median p99; the frames CPU cut of at least 40% is on the medians (BUS-NAT-GATE-001 to BUS-NAT-GATE-005) | One run per transport; a strict "no greater" p99; best of N runs | A single run lets one noisy phase decide the merge either way; a median of three damps that at the cost of a longer bench. A tail percentile moves between identical runs, so a strict bound would fail on noise; best of N would favour whichever transport got one lucky run. |
| Docker `native` stage | Plain `cargo build --release`, then copy the cdylib to `cohost-bus.linux-x64-gnu.node`; no napi CLI and no Node in the stage (BUS-NAT-BLD-009, DEPLOY-IMG-001) | Install Node and `@napi-rs/cli` in the stage and run `build:native` | The CLI only copies and names the library, so the stage stays a stock Rust image with nothing to install, and the copy is one `COPY`-sized step. The cost is that `native.ts` declares the binding's types itself instead of using a generated `index.d.ts`. |
| Host build | `scripts/install.sh` installs rustup and the toolchain `rust-toolchain.toml` pins, and builds the addon on the host (DEPLOY-INST-014) | Ship a prebuilt addon; build the addon only inside Docker | The dashboard, `cohostctl` and the Docker-free dev loop run on the host and import `@cohost/bus`, so the host needs the addon; nothing publishes a prebuilt one, and the pinned toolchain keeps the host build equal to CI's. |
| Panic test | A test-only cargo feature `test-panic` adds a binding call that panics, so a test drives BUS-NAT-ERR-006 (BUS-NAT-ERR-011) | Check the catch by review only; trigger a panic through a crafted Redis reply | The catch is what keeps a Rust bug from killing a service, so it deserves a test; a crafted reply depends on a panic existing in production code, which is the bug the catch guards against. A feature keeps the call out of every release build. |
| Untestable boundary properties | No calls into JavaScript, zero-copy outbound buffers and one tokio runtime are LLD design constraints N1 to N3, checked by review; the observable half of zero-copy (a returned `Buffer` keeps its content) stays a spec (BUS-NAT-TRN-010) | Keep them as EARS specs | An EARS line no test can observe is a marker that can never honestly turn `[x]`; as constraints they still bind the code and the review. |
| Partials as a separate event | `speech.partial` is its own type; `speech.heard` stays the sole final event | A `final: boolean` flag on `speech.heard`; `partial` events reusing `speech.heard` with `utteranceId`; no partials on the bus | Every consumer of `speech.heard` (salience, affect, memory, cortex, the dashboard) treats each one as a finished utterance, so a flagged partial would need all of them to filter it, and one that forgot would answer half a sentence. A separate type is ignored by default because consumer groups name the types they read; the cost is one more catalogue entry. |

## Cross-segment impacts

Work the native transport requires in other segments, specified there:

- [deployment](../deployment/deployment-design.md): the Dockerfile gains a Rust `native` stage that runs plain `cargo build --release` and renames the cdylib to the addon, and the `.node` file and Cargo `target` directory leave the build context (DEPLOY-IMG-001, DEPLOY-IMG-004); the `test` workflow installs the pinned toolchain, runs `cargo fmt`, `clippy` and `test` before `pnpm test`, caches Cargo and has a 20 minute timeout, with every action pinned (DEPLOY-CI-001, DEPLOY-CI-009); the installer installs the pinned toolchain through rustup and builds the addon on the host (DEPLOY-INST-007, DEPLOY-INST-014); compose-smoke builds the Rust stage and its `pnpm build` step needs the toolchain (DEPLOY-CI-002, DEPLOY-CI-007); `lid-check` reads `@spec` annotations in Rust sources (DEPLOY-CI-006).
- [control-plane](../control-plane/control-plane-design.md): the `serverTime` test moves from faking the Redis connection through `BusOptions.connect` to a `BusTransport` fake (CTRL-CHECK-004); `cohostctl` recognises an unreachable Redis by the code `BUS_CONNECTION` and prints the error's message as the reason (CTRL-CLI-017, BUS-NAT-ERR-009).
- [connections](../connections/connections-design.md): the connector client library lives in `@cohost/bus`, with the codec, tag grammar and key naming in `crates/cohost-bus` (BUS-NAT-RS-003 to BUS-NAT-RS-007); `publishFrame` rejects a frame whose `pcm` exceeds `MAX_FRAME_BYTES` or has an odd byte count with `BUS_INVALID`, writing nothing (CONN-AUD-002).
- [shared-runtime](../shared-runtime/shared-runtime-design.md): `Bus.stop()` returns `Promise<void>` (it flushes queued acks for at most 2 s), and the shutdown sequence awaits it (SHARED-BOOT-005, SHARED-BOOT-006, SHARED-LIFE-001, SHARED-LIFE-004).
- [ears](../ears/ears-design.md) and the [dashboard](../dashboard/dashboard-design.md) feed: a read during a Redis outage rejects at once instead of waiting inside the client, so `onRead` reports a failure each backoff interval and a dependency or the bus reachability turns `down` or `unreachable` sooner; neither design states a timing the native transport changes.
- [mouth](../mouth/mouth-design.md): its frame producer handles a `BUS_INVALID` rejection from `publishFrame` like any failed write; it may reuse a frame `Buffer` once `publishFrame` returns.
- [voice](../voice/voice-design.md) and [avatar](../avatar/avatar-design.md): a publish rejects at once while Redis is down after boot, the first connect is waited for at most 10 s, and a subscription read fails and backs off without rejecting, so only group creation at subscribe time can reject the subscription (BUS-NAT-CONN-005, BUS-NAT-CONN-006, BUS-SUB-009; AVATAR-BUS-008, AVATAR-STATE-002).
- [connections](../connections/connections-design.md): the Windows desktop capture helper is a Rust program on `crates/cohost-bus`, its build deferred (CONN-DESK-001).
