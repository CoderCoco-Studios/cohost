# control-plane specs

Specs for `packages/control`, `packages/bus/src/heartbeat.ts`, and the semantics the dashboard and compose consumers delegate to. Verified against the code at git `49ba935` (audit pass 2026-11-01); owner decisions of 2026-11-01 applied at git `1b57790`. `[x]` = implemented and observed in code, `[ ]` = intended but not yet implemented (gap), `[D]` = deferred (deliberately not provided). CTRL-HEARTBEAT-007 is retired (its statements are event-bus BUS-STREAM-004 and BUS-HEALTH-001). CTRL-RUNTIME-005 to 008, CTRL-GUARD-009, CTRL-CLI-006 and CTRL-CLI-007 are retired with the host-process runtime (compose is the only runtime). CTRL-GUARD-002 is retired with the `self` flag (the dashboard runs on the host and is not a manifest unit). Retired numbers are not reused. Each `<!-- test: -->` pointer names the `test(` line that carries the matching `@spec` annotation; a line with no pointer has no direct test. Design context: [control-plane-design.md](control-plane-design.md).

## Service manifest (CTRL-MANIFEST)

- [ ] **CTRL-MANIFEST-001**: The system shall define `SERVICE_MANIFEST` as the allow-list of exactly 14 controllable units: nine pnpm app services (`chat`, `salience`, `affect`, `memory`, `cortex`, `voice`, `avatar`, `eyes`, `ears`; the host-run `dashboard` is not a unit), each with `composeName` equal to its id and `pnpmFilter` equal to `@cohost/<id>`, and five compose-only units (`redis`, `postgres`, `ollama`, `tts`, `stt`) that have no `pnpmFilter`. <!-- openspec: service-control § Manifest-only service ids --> <!-- test: packages/control/test/manifest.test.ts:6 -->
- [ ] **CTRL-MANIFEST-002**: The manifest shall declare, per unit, the Redis consumer groups on `cohost:events` that a fresh start resets (`chat`, `salience`, `affect`, `cortex`, `voice`, `avatar`, `eyes` and `ears` each own a group of their own name; `memory` owns `memory`, `memory-recall` and `memory-notes`; the compose-only units own none) and a default start mode of `fresh` for every pnpm service that owns groups except `memory` (`chat`, `salience`, `affect`, `cortex`, `voice`, `avatar`, `eyes`, `ears`) and `resume` for `memory` and the compose-only units, so the control-plane default matches each service's bus subscribe start mode (`latest` for all but `memory`, which resumes). <!-- openspec: service-control § Start modes (resume vs fresh) --> <!-- test: packages/control/test/manifest.test.ts:28 -->
- [ ] **CTRL-MANIFEST-003**: The manifest shall flag `redis` and `postgres` as `infra`, carry no `self` flag on any unit, and carry these isolation env presets applied by an isolated start: `chat` `CHAT_SOURCE=fake`; `memory` `MEMORY_STORE=memory` and `MEMORY_EMBEDDER=hash`; `cortex` `LLM_PROVIDER=mock`; `voice` `VOICE_ENGINE=stub`; `avatar` `AVATAR_DRIVER=null`; `eyes` `VISION_ENABLED=false`; `ears` `EARS_SOURCE=off`; every other unit an empty preset. <!-- openspec: service-control § Protected services --> <!-- test: packages/control/test/manifest.test.ts:28 -->
- [x] **CTRL-MANIFEST-004**: When `findService` is given an id that is not a manifest entry (including a crafted string such as `cortex; rm -rf /`), the system shall return `undefined`, so no request text can reach a runtime argv except by selecting a manifest entry. <!-- openspec: service-control § Manifest-only service ids --> <!-- test: packages/control/test/manifest.test.ts:43 -->
- [x] **CTRL-MANIFEST-005**: Every name in `KNOWN_SERVICES` (the health tracker's default known list) shall be the id of a `SERVICE_MANIFEST` entry. <!-- test: packages/control/test/manifest.test.ts:23 -->

## Runtime adapters (CTRL-RUNTIME)

- [x] **CTRL-RUNTIME-001**: When `ComposeRuntime` is asked to start, stop or restart a manifest unit, the system shall run `docker compose up -d <composeName>`, `docker compose stop <composeName>` or `docker compose restart <composeName>` through `execFile` with an argv array (no shell), a 120 s timeout and the configured `cwd`. <!-- openspec: service-control § Runtime interface and adapters --> <!-- test: packages/control/test/runtime.test.ts:19 -->
- [x] **CTRL-RUNTIME-002**: When `ComposeRuntime.restart` receives a non-empty env override, the system shall run `docker compose up -d --force-recreate <composeName>` instead of `restart`, and shall merge the override over the base environment of the spawned `docker` process. <!-- openspec: service-control § Runtime interface and adapters --> <!-- test: packages/control/test/runtime.test.ts:44 -->
- [x] **CTRL-RUNTIME-003**: If a `docker compose` command fails, then `ComposeRuntime` shall resolve `ok: false` with `detail` set to the trimmed stderr (else the error message), truncated to 500 characters, rather than throwing. <!-- test: packages/control/test/runtime.test.ts:54 -->
- [x] **CTRL-RUNTIME-004**: If `ComposeRuntime` is asked to act on an id that is not in its manifest, then it shall resolve `ok: false` with an `unknown service` detail without executing anything. <!-- openspec: service-control § Manifest-only service ids --> <!-- test: packages/control/test/runtime.test.ts:33 -->
- [x] **CTRL-RUNTIME-009**: Where `ComposeRuntime` starts or recreates a service with an isolation env preset, the system shall make that env visible inside the started container, through pass-through entries for every preset variable (`CHAT_SOURCE`, `MEMORY_STORE`, `MEMORY_EMBEDDER`, `LLM_PROVIDER`, `VOICE_ENGINE`, `AVATAR_DRIVER`, `VISION_ENABLED`, `EARS_SOURCE`) in the compose `x-ts-service` environment, written as `VAR: ${VAR:-}` so an unset variable still falls to the `${VAR:-default}` in `config.yaml`. <!-- openspec: service-control § Runtime interface and adapters -->
- [x] **CTRL-RUNTIME-010**: When `ComposeRuntime.consolidate` is called, the system shall run `docker compose run --rm -T consolidate` through the injected exec (argv only, no shell, cwd and env as for the other verbs) with a 30 minute timeout instead of the 120 s default, and resolve `ok: true` with the last non-empty line of the command's stdout as `detail` when it exits 0, or `ok: false` with the trimmed stderr (else stdout tail, else the error message), cut to 500 characters, as `detail` when it fails or times out. The argv is fixed: the `consolidate` job is not in the manifest and no caller input reaches it. <!-- test: packages/control/test/runtime.test.ts:81 --> <!-- test: packages/control/test/runtime.test.ts:95 -->

## Controller guards and orchestration (CTRL-GUARD)

- [x] **CTRL-GUARD-001**: If `ServiceController` is asked to act on an id that is not in its manifest, then it shall return `refused: "unknown"` without calling the runtime, resetting any group or publishing an audit record. <!-- openspec: service-control § Manifest-only service ids --> <!-- test: packages/control/test/controller.test.ts:81 -->
- [x] **CTRL-GUARD-003**: If an action targets a unit flagged `infra` (`redis`, `postgres`) and `advanced` is not set, then `ServiceController` shall return `refused: "forbidden"` naming `CONTROL_ADVANCED=1`; where `advanced` is set it shall execute the action and shall always use `resume` mode for infra, so no consumer group is reset. <!-- openspec: service-control § Protected services --> <!-- test: packages/control/test/controller.test.ts:100 -->
- [x] **CTRL-GUARD-004**: When a start is requested in `fresh` mode (the caller's `mode`, else the manifest `defaultMode`) for a unit that owns consumer groups, the system shall reset each group to `$` in manifest order and then start the service, and if a reset fails shall not start it and shall return `ok: false` with detail `consumer group reset failed: <reason>`. <!-- openspec: service-control § Start modes (resume vs fresh) --> <!-- test: packages/control/test/controller.test.ts:51 --> <!-- test: packages/control/test/controller.test.ts:131 -->
- [x] **CTRL-GUARD-005**: When a restart is requested in `fresh` mode (for a unit with groups) or with isolation env, the system shall stop the service, reset its groups only after the stop resolved `ok`, and then start it, returning the reset failure without starting if a reset fails; when a restart is requested in `resume` mode without isolation env it shall issue one native runtime restart and leave all groups untouched; a stop shall never reset groups; if the stop step fails, the failure shall be returned without resetting or starting. <!-- openspec: service-control § Start modes (resume vs fresh) --> <!-- test: packages/control/test/controller.test.ts:27 --> <!-- test: packages/control/test/controller.test.ts:34 --> <!-- test: packages/control/test/controller.test.ts:41 --> <!-- test: packages/control/test/controller.test.ts:51 --> <!-- test: packages/control/test/controller.test.ts:59 -->
- [x] **CTRL-GUARD-006**: Where an action carries `isolated: true` and the unit is not infra, the system shall pass a copy of the unit's manifest `isolatedEnv` to the runtime start, and shall replace a native restart with stop-then-start even when that preset is empty. <!-- test: packages/control/test/controller.test.ts:69 -->
- [x] **CTRL-GUARD-007**: When an action has been executed (not refused), the system shall call the controller's `audit` callback with `service`, `action`, `by`, `ok` and, whenever the runtime returned one (on success as well as failure), `detail`; it shall swallow any error the callback throws, and shall return only `ok` and `detail` to the caller. <!-- openspec: service-control § Lifecycle audit event --> <!-- test: packages/control/test/controller.test.ts:112 --> <!-- test: packages/control/test/controller.test.ts:122 -->
- [x] **CTRL-GUARD-008**: Where an isolated start of a unit is requested, the system shall also start the units named in that unit's manifest `requires` list, transitively (for cortex: salience and affect), and nothing else; a start that is not isolated, and every restart and stop, shall act on the named unit only. Required units start first, depth-first in `requires` order, each once (a unit already in the closure, or the named unit itself, is skipped, so cycles terminate), each with its own isolation preset and its own default mode (a `fresh` unit has its groups reset before its start), and each executed start is audited as its own `service.lifecycle` record. If a required unit fails to start (including a reset failure), the system shall not start the remaining units or the named unit, shall return `ok: false` with a detail naming the failed unit (`required unit <id> failed to start: <reason>`), and shall publish no audit record for the named unit, which was not executed. <!-- openspec: cortex § Isolation preset and closure --> <!-- test: packages/control/test/controller.test.ts:141 --> <!-- test: packages/control/test/controller.test.ts:147 --> <!-- test: packages/control/test/controller.test.ts:160 --> <!-- test: packages/control/test/controller.test.ts:171 --> <!-- test: packages/control/test/controller.test.ts:180 -->

## Stack controller (CTRL-STACK)

- [ ] **CTRL-STACK-001**: The system shall run every `StackController` command, and every `ComposeRuntime` command issued by the dashboard or `cohostctl`, through the injected exec with an argv array (no shell) and the workspace root (`findWorkspaceRoot()`, else the process cwd) as the working directory and the process environment as the base environment.
- [ ] **CTRL-STACK-002**: When `StackController.launch` is called, the system shall report phase `compose-up`, run `docker compose up -d --remove-orphans` with a 30 minute timeout, and if that command fails shall resolve `ok: false` with the trimmed stderr (else the error message) cut to 500 characters as `detail`, without polling.
- [ ] **CTRL-STACK-003**: When `docker compose up` has succeeded during a launch, the system shall report phase `waiting` and run the status probe every 2000 ms until every long-running container present in the status (every listed container except the one-shots `models` and `consolidate`; `consolidate` is profile-gated and not started by `up`) has status `running` and health `healthy` or no healthcheck, and then resolve `ok: true` with the last status as `services`.
- [ ] **CTRL-STACK-004**: If the long-running containers are not all ready 180 s after `docker compose up` succeeded, or the status probe reports Docker unavailable while waiting, then the launch shall resolve `ok: false` with a `detail` naming each container that is not ready with its status and health (or the probe's detail) and the last status as `services`, and shall stop, remove or restart nothing.
- [ ] **CTRL-STACK-005**: If, when a launch resolves, the status shows a one-shot container (`models`) exited with a non-zero code, then the system shall append `<service> exited <code>` to the result's `detail` without changing `ok`.
- [ ] **CTRL-STACK-006**: When `StackController.stopAll` is called, the system shall report phase `stopping` and run `docker compose stop` with a 300 s timeout, resolving `ok: true` when it exits 0 and `ok: false` with the stderr detail (cut to 500 characters) otherwise; it shall never run `docker compose down` and never remove containers, networks or volumes.
- [ ] **CTRL-STACK-007**: When `StackController.restartAll` is called with a `ServiceController`, the system shall run the status probe and then, in manifest order, for every manifest unit that has a `pnpmFilter` and whose container the status shows `running`, report phase `restarting <id>` and call the controller's restart for it in its default mode without isolation, continuing after a failure; it shall resolve `ok: true` only when at least one unit was restarted and every restart succeeded, with a `detail` naming each failure, and `ok: false` with detail `no application service is running` when none was running; infrastructure and compose-only units shall not be restarted.
- [ ] **CTRL-STACK-008**: When `StackController.status` is called, the system shall run `docker compose ps --all --format json` with a 10 s timeout and resolve `{docker: {ok: true}, services: [{service, status, health?, exitCode?}]}` from its output, accepting both a JSON array and one JSON object per line; if `docker` is missing, the command fails or times out, or the output does not parse, it shall resolve `{docker: {ok: false, detail}, services: []}` with the stderr or error message cut to 500 characters, and shall never throw.
- [ ] **CTRL-STACK-009**: Every `StackController` action shall take no caller input that reaches a command line: the `docker compose` argv of `status`, `launch`, `stopAll` and `consolidate` is fixed, and `restartAll` reaches a command only by selecting manifest entries through `ServiceController`.
- [ ] **CTRL-STACK-010**: `StackController.launch` and `StackController.stopAll` shall act on every Compose service of the stack, infrastructure included, without requiring `CONTROL_ADVANCED`; `restartAll` shall apply the controller's guards to each unit.
- [ ] **CTRL-STACK-011**: When the stack state is derived from a status and the running action (if any), the system shall consider as long-running every container present in the status except the one-shots `models` and `consolidate`, and shall return, in this precedence, `docker-unavailable` when Docker is not available, `stopping` while a stop-all runs, `starting` while a launch runs, `down` when no long-running container is `running`, `up` when every long-running container is `running` with health `healthy` or no healthcheck, `starting` when every long-running container that is not ready is `running` with health `starting`, and `degraded` otherwise.

- [ ] **CTRL-STACK-012**: When `ComposeRuntime` or `StackController` runs a Docker command, the system shall execute `COHOST_DOCKER_BIN` when that variable is set and non-empty, else `docker` when it is found on `PATH`, else `docker.exe` when it is found on `PATH` (the Windows Docker Desktop CLI seen from WSL2), always with the same argv (`compose ...`); if none is found, the status probe shall report Docker unavailable with a detail naming `COHOST_DOCKER_BIN`, and every action shall resolve `ok: false` with that detail without throwing.

## Control configuration (CTRL-CONFIG)

- [x] **CTRL-CONFIG-001**: The system shall treat control as disabled unless `CONTROL_ENABLED` is exactly `1`, and if control is enabled with `CONTROL_TOKEN` unset or blank then `loadControlConfig` shall throw an error naming `CONTROL_TOKEN`. <!-- openspec: service-control § Enablement gating --> <!-- test: packages/control/test/config.test.ts:6 --> <!-- test: packages/control/test/config.test.ts:12 -->
- [x] **CTRL-CONFIG-002**: Where control is enabled, `loadControlConfig` shall default `bind` to `127.0.0.1` (with `bindExplicit` false unless `CONTROL_BIND` is non-blank), shall set `advanced` only when `CONTROL_ADVANCED` is exactly `1`and shall carry no runtime selection (`CONTROL_RUNTIME` and `CONTROL_PROCESS_MODE` are not read); `isLoopback` shall accept `localhost`, `::1` and any host starting with `127.`. <!-- openspec: service-control § Enablement gating --> <!-- test: packages/control/test/config.test.ts:18 --> <!-- test: packages/control/test/config.test.ts:24 -->

## Heartbeat contract (CTRL-HEARTBEAT)

- [x] **CTRL-HEARTBEAT-001**: When `startHeartbeat` builds a heartbeat, the system shall set `service` from the options, `instance` to the bus consumer name, `pid` to the process pid, `version` to the option, else `COHOST_VERSION`, else `dev`, `startedAt` to the module-load time of `heartbeat.ts` (constant for the process), `state` from the `starting`/`ready`/`degraded` base, `deps`, `mode`, optional `detail` and `intervalMs`. <!-- openspec: service-health § Heartbeat contract -->
- [x] **CTRL-HEARTBEAT-002**: When `startHeartbeat` is called, the system shall publish a `starting` heartbeat immediately, publish immediately on every `ready()` or `degraded(detail?)` call, and republish every `intervalMs`, where `intervalMs` is `HEARTBEAT_INTERVAL_MS` floored when it is a positive finite number and otherwise 5000. <!-- openspec: service-health § Heartbeat contract --> <!-- test: packages/bus/test/bus.test.ts:200 -->
- [x] **CTRL-HEARTBEAT-003**: While a heartbeat is running, the system shall re-read `deps` and `mode` (each may be a getter) at least once per second (every `min(1000, intervalMs)` ms) and republish at once when the state, deps, mode or detail differs from the last publication; when the base state is `ready` and any dep is `down` it shall publish `degraded` with detail `dependency down: <names>`. <!-- openspec: bus (add-service-health) § Heartbeat helper --> <!-- test: packages/bus/test/bus.test.ts:214 -->
- [x] **CTRL-HEARTBEAT-004**: When `stop()` is called, the system shall publish exactly one heartbeat with `state: "stopping"`, cancel both timers, ignore later `ready()`/`degraded()` publications, and make repeated `stop()` calls no-ops. <!-- openspec: bus (add-service-health) § Heartbeat helper --> <!-- test: packages/bus/test/bus.test.ts:231 -->
- [x] **CTRL-HEARTBEAT-005**: When `startHeartbeat` is called, the system shall register the heartbeat's `stop()` as a `beforeShutdown` hook, so that a SIGINT or SIGTERM handled through `onShutdown` publishes the `stopping` heartbeat before the service's own shutdown callback runs; the hook time limit, callback order and exit code are event-bus BUS-STOP-002. <!-- openspec: bus (add-service-health) § Heartbeat helper --> <!-- test: packages/bus/test/bus.test.ts:257 -->
- [x] **CTRL-HEARTBEAT-006**: If publishing a heartbeat fails, then the system shall log a warning (when a logger was supplied) and keep running without throwing into the service. <!-- openspec: bus (add-service-health) § Heartbeat helper --> <!-- test: packages/bus/test/bus.test.ts:244 -->
- [x] **CTRL-HEARTBEAT-008**: The system shall provide `tracked(fn, set)` which wraps an async call so `set(true)` follows a success and `set(false)` follows a failure while the error still propagates, so a service can feed a dependency status from real call outcomes. <!-- test: packages/bus/test/bus.test.ts:265 -->
- [x] **CTRL-HEARTBEAT-009**: Where `startHeartbeat` is given a standing `detail`, the system shall publish it as the heartbeat `detail` in every state, including `starting` and after `ready()`, unless an explicit `degraded(detail)` or the derived `dependency down: ...` detail applies, which take precedence in that order.

## Health derivation (CTRL-HEALTH)

- [x] **CTRL-HEALTH-001**: When `HealthTracker` derives the state of a service that has never sent a heartbeat, the system shall report `unknown` (not `down`) with no heartbeat and zero restarts. <!-- openspec: service-health § Derived health states --> <!-- test: packages/control/test/health.test.ts:42 -->
- [x] **CTRL-HEALTH-002**: When a service's latest heartbeat is `stopping` or older than 10 times its `intervalMs`, `HealthTracker` shall report `down` (a `stopping` heartbeat immediately regardless of age), and when it is older than 3 times its `intervalMs` it shall report `stale`, using the latest heartbeat's own `intervalMs` and the tracker's receive-time clock. <!-- openspec: service-health § Derived health states --> <!-- test: packages/control/test/health.test.ts:25 --> <!-- test: packages/control/test/health.test.ts:35 --> <!-- test: packages/control/test/health.test.ts:69 -->
- [x] **CTRL-HEALTH-003**: When a service's latest heartbeat is fresh, `HealthTracker` shall report `degraded` if its `state` is `degraded` or `starting` or any dep is `down`, and `up` otherwise (`n/a` deps do not degrade). <!-- openspec: service-health § Derived health states --> <!-- test: packages/control/test/health.test.ts:17 --> <!-- test: packages/control/test/health.test.ts:49 --> <!-- test: packages/control/test/health.test.ts:62 -->
- [x] **CTRL-HEALTH-004**: While a service has at least 3 distinct `startedAt` values first seen within the last 60 s, `HealthTracker` shall report `crash-looping` in preference to every other state (including silence), and shall clear it once fewer than 3 such starts remain in the window; repeated heartbeats with the same `startedAt` shall not count as restarts. <!-- openspec: service-health § Crash-loop detection --> <!-- test: packages/control/test/health.test.ts:77 --> <!-- test: packages/control/test/health.test.ts:92 --> <!-- test: packages/control/test/health.test.ts:104 -->
- [ ] **CTRL-HEALTH-005**: When `HealthTracker.snapshot` is called, the system shall return one `ServiceHealth` (state, latest heartbeat, `lastSeenAgeMs`, `restarts`) for each name in the known list (default `KNOWN_SERVICES`, the nine manifest app services, without `dashboard`) plus any other service that has sent a heartbeat (so the host-run dashboard appears once it beats). <!-- openspec: service-health § Tracker snapshot --> <!-- test: packages/control/test/health.test.ts:112 -->
- [x] **CTRL-HEALTH-006**: When a heartbeat is ingested or `tick()` is called, `HealthTracker` shall notify its `onChange` listeners only if a service's derived state, restart count or heartbeat state/mode/detail/deps/instance differs from what was last notified, and shall never publish derived states to the bus. <!-- openspec: service-health § Derived health states --> <!-- test: packages/control/test/health.test.ts:126 -->
- [x] **CTRL-HEALTH-007**: When `HealthTracker.seed` is given history oldest-first, the system shall use each record's `ts` as its receive time, and shall not let a replayed older heartbeat overwrite a newer one already held for the same service. <!-- test: packages/control/test/health.test.ts:139 -->

## cohostctl command line (CTRL-CLI)

- [ ] **CTRL-CLI-001**: When `cohostctl` parses its arguments, the system shall accept `status [service]`, `start|restart <service> [--mode resume|fresh] [--isolated]`, `stop <service>` (no options), `consolidate`, `launch`, `stop-all` and `restart-all`, and if the command is missing or unknown, a service name is missing for start/stop/restart, an extra positional is given (including any argument to `consolidate`, `launch`, `stop-all` or `restart-all`), `--mode` is not `resume` or `fresh`, an unknown flag is used, or options are given to `status`, `stop`, `consolidate`, `launch`, `stop-all` or `restart-all`, then it shall print the usage text and exit 2. <!-- openspec: service-control § Optional cohostctl CLI --> <!-- test: packages/control/test/cli.test.ts:7 --> <!-- test: packages/control/test/cli.test.ts:17 --> <!-- test: packages/control/test/cli.test.ts:72 -->

- [x] **CTRL-CLI-003**: When `cohostctl start|stop|restart` runs, the system shall delegate to `ServiceController` and exit 0 printing `<cmd> <id>: ok` (followed by ` (<detail>)` when the controller returned a detail) on success, and shall exit 1 printing `refused (<reason>): <detail>` for a refusal (unknown, conflict, forbidden) or `<cmd> <id> failed: <detail>` for a runtime failure. <!-- openspec: service-control § Optional cohostctl CLI --> <!-- test: packages/control/test/cli.test.ts:46 --> <!-- test: packages/control/test/cli.test.ts:54 --> <!-- test: packages/control/test/cli.test.ts:61 -->
