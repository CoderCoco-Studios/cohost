# ears

> Brownfield LLD, mapped 2026-10-31 at git `686cc8f`; audited 2026-11-02 at `1b57790` with the owner's decisions of 2026-11-01 applied. ears is the listening half: the Discord playback sink and the spoken fallback line belong to [mouth](../mouth/mouth-design.md), and Discord itself belongs to the Discord connector in [connections](../connections/connections-design.md): ears holds no Discord client and consumes the audio the connector publishes. HLD: [high-level-design](../../high-level-design.md).

## Context and Design Philosophy

ears is the co-host's hearing. It is one Node process (`services/ears`) with two jobs:

1. **Listen.** It consumes audio from the enabled sources, cuts each speaker's audio into utterances on silence, transcribes each with the configured STT engine (speaches by default; any server speaking the OpenAI transcription route; or a streaming engine, NVIDIA Nemotron Speech Streaming or Kyutai STT), and publishes `speech.heard` carrying the speaker's name. Discord voice is one such source: the Discord connector publishes each human speaker's audio on `audio.in.discord` and ears reads it ([Connector sources](#connector-sources)).
2. **Transcribe injected audio.** It accepts `inject.request` for uploaded audio, transcribes it through the same STT path, and publishes an injected `speech.heard` (`services/ears/src/inject.ts`). This job is independent of the Discord session.

ears does not speak and does not talk to Discord. The co-host's voice reaches Discord through [mouth](../mouth/mouth-design.md) and the Discord connector, and Discord's audio reaches ears through the same connector, which holds the one bot and the one voice connection ([connector-protocol](../connections/decisions/connector-protocol.md)). Discord is the default listening source. `ears.sources` lists the sources that are enabled, any number at once: connector sources (`discord`, or any tag a connector registers), the host's desktop audio (`desktop`, which arrives through the HTTP capture path until the helper becomes a connector), and the account-free capture sources `http` and `dir` ([Capture sources](#capture-sources), [Multiple sources](#multiple-sources)); an empty list is `off`.

Design leanings (evidence per bullet):

- **Pure logic is split from the glue.** `Hearing`, `createInjectHandler`, `EarsHealth`, the utterance assembler, the session helpers and the audio helpers take their effects as injected functions and objects (the STT engine, `fetch`, `now`), and the service body (`service.ts`) takes its environment and the connector client as injected options, so all of it is unit-tested with fakes under `runService` (`services/ears/test/*.test.ts`). `index.ts` is the one line that hands the body to `runService`.
- **Never exit for a configuration gap.** `ears.sources` empty, or only gap sources, leaves the process up and idle with an honest heartbeat rather than crash-looping (`services/ears/src/health.ts`, `services/ears/src/service.ts`). A connector that is not present is a dependency `down`, not an exit. Evidence: `earsPlan` doc comment; commit 51d5a9c; add-isolated-backends design D7.
- **No Discord library in ears.** Discord, Opus decoding and the voice connection live in the Discord connector, so ears carries no gateway client, no native voice dependency and no Discord token.

Ownership notes: `src/health.ts` implements the heartbeat contract owned by [control-plane](../control-plane/control-plane-design.md); `src/inject.ts` is ears' half of test injection (the panel, the Redis upload write and bus-level injection belong to [dashboard](../dashboard/dashboard-design.md); the `inject.*` schemas belong to [event-bus](../event-bus/event-bus-design.md)); the "off" mode belongs here; the connector registry, the `audio.in` stream and the frame format belong to [connections](../connections/connections-design.md).

## Startup Plans

At boot `index.ts` hands the service body (`service.ts`) to the shared `runService`, which loads config, creates a `Bus("ears")` and starts the heartbeat (EARS-START-008); the body derives a **plan** per enabled source with the pure function `earsPlan(sources, hasDirPath)`, which returns the set of sources to start ([Multiple sources](#multiple-sources)); the table below is the plan of each source taken alone, which is the whole plan when one source is enabled:

| --- | --- | --- | --- |
| `off` | `off` | none | mode `off`, deps `discord: n/a, stt: n/a`, state `ready` immediately (EARS-START-001) |
| `discord` (or another connector tag) | `discord` | none | mode `live`; `ready` once subscribed; `deps.discord` `ok` while the connector is present and `ready` (EARS-CON-005) |
| `http` | `http` | none | mode `live`; `ready` once the port is listening (EARS-CAP-007) |

`ears.sources` is a list of source names: `http`, `dir`, or a connector source tag, an open set that connectors register (default `[discord]`; empty is `off`; `desktop` is such a tag); the isolation override `EARS_SOURCES` overrides the list by key path (config CFG-ISO-007; a flow-syntax value such as `[http, dir]` or `[]`) (`packages/config/src/schema.ts`, CFG-SCH-030). Only `dir` can be a configuration gap; a connector source with no connector is `down`, and the plan never depends on a token. The sources are read at start; changing them takes effect on restart.

In every plan the process reads `inject.request` on consumer group `ears` (EARS-START-003), and it creates no Discord client whatever the plan (EARS-CON-002). It reads `voice.playing` and `voice.done` as well only where an enabled source is named in `ears.echo_suppress_sources`, for the echo gate (EARS-ECHO-001); it never reads `voice.utterance` and never publishes a `voice.*` event. In the idle plans (`off`, `no-dir`):

- `ready` is signalled after the subscription is established, except where the plan is `degraded` (`no-dir`);
- both run through the shared idle plan `startIdle`: `off` logs one warning and is `ready` in mode `off`; `no-dir` logs an error naming the missing key, reports `degraded`, and repeats the warning backing off from 60 s (doubling to one hour, SHARED-IDLE-003, SHARED-IDLE-006) (EARS-START-008);
- on shutdown the idle timer is cleared and the bus stopped, as one `runService` teardown (EARS-START-005).

The `ears` consumer group uses the bus start mode `latest`: the group is reset to the newest entry on every start, so injection requests published while ears was down are not handled (EARS-START-006). `subscribeEars` creates the group first (`Bus.resetGroup`, so it exists before any `ready` signal) and then starts the read loop with `start: "latest"`.

Shutdown is one sequence registered once with `runService`'s `onStop`: stop each source independently, then `runService` stops the bus, even if a stop throws (EARS-SRC-004). The heartbeat's pre-shutdown hook sends `stopping` before any callback runs, and the bus runs every registered callback in order and exits once ([event-bus](../event-bus/event-bus-design.md)).

## Listening Pipeline

Implemented in `connector-source.ts` (consume, assemble and each utterance's session), `hearing.ts` (STT + publish) and `stt.ts` (the batch and session calls).

1. **Consume.** For a connector source, ears reads `audio.in.<tag>` with a plain blocking `XREAD` from the end of the stream, never replaying older frames, and keeps one reader per enabled connector source ([Connector sources](#connector-sources)).
2. **Assemble per speaker.** Frames carry `spk` and `name`. ears appends each frame to the open buffer of its `spk` and closes that buffer where the endpointing rule of [Utterance endpointing](#utterance-endpointing) says the utterance has ended (EARS-HEAR-001, EARS-VAD-001): a shorter `ears.silence_ms` sends speech to STT sooner but splits sentences at pauses. The closed buffer is 16 kHz mono PCM already, so it goes to `Hearing.heardClip` with the source tag, drops anything shorter than `ears.min_speech_ms`, and is transcribed by the engine ([STT engines](#stt-engines)): a batch engine takes it wrapped as a 16 kHz mono WAV with the shared `wavWrap`; for a streaming engine the text comes from the utterance's session, which has been fed since the utterance opened. The speaker's name is the frames' `name`.
3. **Transcription.** The engine returns the utterance's text. The `speaches` and `openai` engines POST multipart form data to the server's `/audio/transcriptions` route with fields `file`, `model` (= `ears.stt_model`), `language` = `"en"`, `response_format` = `json`; a non-2xx throws `stt <status>: <body>`; the result is `json.text.trim()`. Every engine's `transcribe` accepts an optional content-type hint so injected uploads keep their container.
4. **Publish.** Text with no word character (a Unicode letter or number in any script, EARS-HEAR-007) is dropped silently, as is a transcript equal to an `ears.drop_phrases` entry (EARS-HEAR-010; compared case-insensitively with whitespace collapsed and leading and trailing punctuation ignored, so `Thank you.` matches `thank you`; the list is empty by default and `config.example.yaml` shows Whisper's common silence phrases); otherwise `speech.heard { speaker, speakerId, text, durationMs }` is published, where `speakerId` is the speaker id the source gave, for Discord the user id, unmodified (EARS-HEAR-011) and the identity [memory](../memory/memory-design.md#voice-speakers) keeps notes under; ears holds no identity mapping. Any exception becomes a `"transcription failed"` warning. `speech.heard` is defined in `packages/bus/src/events.ts`. Where early transcripts are enabled the text of a final may be an early transcript reused ([Early transcripts](#early-transcripts)).

Every batch call, whole clip or utterance, and every session outcome passes through `SttRouter` (`services/ears/src/stt.ts`), which sets `deps.stt` through `EarsHealth` (`health.ts`).

`speech.heard` also carries `timing.audioEndedAt`, the epoch-millisecond time the last speech frame of a connector utterance arrived: the last frame classified as speech under `silero`, the last frame received under `gap`. It is the same for an ordinary final and for one that reuses an early transcript, except that a Kyutai end of turn ends the clip at the last frame received when the signal arrived and stamps that frame's arrival (EARS-KYU-010); it is not the later moment the silence rule or the gap timer closes the utterance (EARS-HEAR-012). For an `http` or `dir` clip and for injected audio it is the time ears received the clip. A connector utterance's `speech.heard` also carries `timing.closedAt`, the epoch-millisecond time ears closed the utterance (the silence rule, the frame-gap rule, the length cap or a Kyutai end of turn firing). The two stamps split ears' share of the speech path into two measured stages: `endpoint`, from the arrival of the last speech frame to the close, which is about `ears.silence_ms` and which nothing here shortens, and `stt`, the close to the published `speech.heard`. A clip, a file and an injection are not closed by ears, so they carry no `closedAt` and the report measures one `stt` stage from `audioEndedAt` ([event-bus](../event-bus/event-bus-design.md) `timing`, [control-plane](../control-plane/control-plane-design.md) Latency report).

A connector utterance is cut by speech activity and capped in length ([Utterance endpointing](#utterance-endpointing)), and may be previewed by partial transcripts ([Partial transcripts](#partial-transcripts)). The co-host's own audio and every other bot's never reaches ears from Discord, because the Discord connector reads no bot account (CONN-DISC-007). A source that can carry the co-host's voice back, such as the desktop capture, is covered by the echo gate ([Echo gate](#echo-gate)). Echo that leaks through a person's own microphone into the Discord channel is not handled: no gate or cancellation exists for it.

## STT engines

Every engine implements one contract, so ears' pipeline never knows which server is behind it (HLD tenet 2). There are two kinds.

```ts
interface SttEngine {
  readonly kind: "batch" | "streaming";
  readonly name: "speaches" | "openai" | "nemotron" | "kyutai" | "stub";
  /** Optional readiness probe; absent where the server has no verified health route. */
  ping?(signal: AbortSignal): Promise<boolean>;
  /** Host of the server, for the egress note and the heartbeat detail. */
  readonly destination?: string;
}
interface BatchSttEngine extends SttEngine {
  readonly kind: "batch";
  /** One whole clip in, its text out. */
  transcribe(audio: Buffer, hint?: { contentType: string }): Promise<string>;
}
interface StreamingSttEngine extends SttEngine {
  readonly kind: "streaming";
  /** Resolves when the server is connected and ready for audio. */
  open(opts: { signal: AbortSignal }): Promise<SttSession>;
}
interface SttSession {
  /** 16 kHz mono signed 16-bit PCM, any length; the adapter resamples and frames for its server. */
  push(pcm: Buffer): void;
  /** The current whole hypothesis, each time it changes. */
  onHypothesis(cb: (text: string) => void): void;
  /** Called at most once, only by an engine whose server signals a semantic end of turn (`kyutai`). */
  onEndOfTurn(cb: () => void): void;
  /** Flush what the server holds, return the final text, close. */
  finish(): Promise<string>;
  abort(): void;
  /** Settles when the connection drops or the server reports an error. */
  readonly failed: Promise<Error>;
}
```

A **batch** engine takes the audio of one utterance and returns text: `speaches`, `openai` and `stub`. A **streaming** engine is fed frames as they arrive and returns partial text and a final: `nemotron` and `kyutai`; it has no whole-clip call. `ears.stt_engine` selects the engine for live speech; `EARS_STT_ENGINE` can replace it with `stub` for an isolated start.

**The batch engine.** Whole-clip work always goes to a batch engine: the selected engine when it is batch, otherwise `ears.stt_fallback_engine` (`speaches` by default, `openai`, or `none`). Whole-clip work is the `http` and `dir` capture sources, test injection, an utterance of a streaming engine that has no session or whose session failed, and the utterances of a source named in `ears.echo_suppress_sources`. With a streaming engine selected and `none` as the fallback there is no batch engine: whole-clip work fails with the reason `no batch STT engine` (a `502` from the `http` listener, `ok:false` for an injection, a `failed` outcome for a `dir` file), and an utterance with no session is dropped with a warning. A one-shot input never takes a streaming session, so a live speaker can always have one. Whole-clip work answers with a configuration reason only where the batch engine's own configuration is incomplete; a blank URL of the selected streaming engine does not stop it.

**Where a session lives.** One session belongs to one open utterance, that is to one speaker id of one connector source, as the buffer, detector state and partial state already do (EARS-VAD-007). It opens when the utterance opens, unless the source is echo-suppressed (below) or `ears.max_stt_sessions` sessions are open: the pre-roll and the frames buffered while the connection is made are sent first, as fast as the socket takes them, bounded together by `ears.stt_timeout_ms`, then every frame as it arrives, silence frames of the open utterance included. The session ends with the utterance: `finish()` at close, `abort()` when the utterance is dropped. An utterance dropped at close for being shorter than `ears.min_speech_ms` aborts its session. No session outlives its utterance, so several speakers, or several sources, speaking at once hold one session each.

**Echo-suppressed sources.** A source named in `ears.echo_suppress_sources` never opens a streaming session. Its utterances are held until close, the echo gate decides on the audio-end time as it does for every clip (EARS-ECHO-004), and a clip the gate lets through goes to the batch engine. No audio of a suppressed source reaches a streaming engine, and no partial of one is published while a line plays.

**Who ends an utterance.** ears does, for every engine, by the rule of [Utterance endpointing](#utterance-endpointing): the voice-activity detector and `ears.silence_ms`, the frame gap, `ears.max_utterance_ms`. A streaming server's own endpointing is not used (`nemotron`'s is off by default and ears leaves it off). The one engine signal that can end an utterance earlier is `kyutai`'s end of turn.

**The final.** At close, the connector source applies the minimum-duration gate to a live session and aborts the session of an utterance too short for it, without sending a commit or marker, publishing nothing. For an utterance that passes, it takes the final text from `session.finish()`, bounded by `ears.stt_timeout_ms`; `Hearing` then applies the word-character and drop-phrase filters and publishes the same `speech.heard`, with the same `utteranceId` and `timing.audioEndedAt`. An utterance that closes while its connect is still pending waits for the connect: the frames held while connecting are pushed, and the same rule then applies. Only a connect that fails or times out sends the utterance to the batch engine.

**Partials.** With `ears.partials` on, a session's hypotheses become `speech.partial` events (the same payload and filters as under [Partial transcripts](#partial-transcripts)). The first change is published at once; after that at most one per `ears.partial_step_ms`, and when the window ends the latest change not yet published is published. `ears.min_speech_ms` applies as for a batch engine: no partial before the utterance has that much audio. A hypothesis is published only when it differs from the last one published, and one that arrives after the utterance closed is discarded. They cost no extra call, so only the rate is limited. An utterance with no session publishes no partials. Under a batch selected engine partials stay the re-transcription method of Partial transcripts.

**When a session cannot serve.** A streaming utterance falls back to the batch engine, with the retained clip, when the session could not be opened, was refused for capacity (`ears.max_stt_sessions`, or the server answering that it has no free channel), dropped before the close, did not take its buffered start within `ears.stt_timeout_ms`, or did not deliver its final within `ears.stt_timeout_ms` of the close. ears holds the whole utterance for the clip as it does for a batch engine, so the fallback loses nothing but the partials. With no batch engine the utterance is dropped with a warning; `deps.stt` says why when the cause is an outage-class failure, and is left unchanged when the cause is a capacity refusal. An utterance of an echo-suppressed source that the gate lets through, with no batch engine, is dropped with a warning and leaves `deps.stt` unchanged. One attempt per utterance is the retry: a server that is down fails each connect at once, with no reconnection loop and no queue of failed audio.

**Timeouts.** Every call to an engine is bounded by `ears.stt_timeout_ms` (default 20000): a batch request, a connect (aborted at the bound through its `signal`, and when its source stops), a ping (aborted at the bound, and no second ping is sent while one is in flight) and `finish()`. The push of the buffered start is not yet bounded: `push` has no acknowledgement to wait on, so it is open under EARS-SES-003. Within an open session silence from the server is normal and is not a timeout.

**Errors and health.** `deps.stt` is the state of the selected engine. It goes `down` on an outage-class failure and `ok` after the next success. The outage class is a refused or dropped connection, a timeout, a 5xx, a 401, 403, 404 or 429, any other failed batch status except 400 and 422, a session error before the close, a failed `finish()` (a final that never arrives, or a connection that drops during it) and an engine whose configuration is incomplete. A 400 or 422 for one clip, a refusal for capacity, an utterance dropped for being short or echo, and a failed partial leave it alone (EARS-PART-010). While ears is running on the fallback because the selected engine is down, `deps.stt` stays `down`, so the service reads `degraded`, with the detail `<engine> unavailable: <reason>; transcribing with <fallback>`; with no batch engine the detail ends `no fallback engine, utterances dropped`; a failure of the fallback itself adds `fallback <name> failed: <reason>`. Only a session of the selected engine that opens and delivers its final, or a successful ping of it, returns it to `ok`: a successful call of the fallback engine does not. A failed call of the batch engine on a whole clip (`http`, `dir`, injection) while the selected streaming engine is up leaves `deps.stt` unchanged, logs a warning and is reported by that input's own outcome. An engine with a `ping` (`nemotron`: `GET /ready`) starts `down` until its first ping succeeds, which ears sends at start and again every 10 s while the dependency is `down`; an engine without one starts `ok`. A blank URL for the selected engine, or for the fallback engine where the selected engine is streaming, is a configuration gap (HLD tenet 5): ears starts, `deps.stt` is `down` with `ears.<engine>.<key> is not set`, and injection answers with the reason. Only a value that is present and invalid fails the config load. The heartbeat detail otherwise names the engine and the host it talks to.

| `ears.stt_engine` | Kind | Server and route | Audio | Voice-activity and end of turn | Notes |
| --- | --- | --- | --- | --- | --- |
| `speaches` (default) | batch | `POST <STT_URL>/v1/audio/transcriptions`, multipart, `model` = `ears.stt_model`, `language` `en` | 16 kHz mono WAV | ears' | the Compose-run server |
| `openai` | batch | `POST <ears.openai.base_url>/audio/transcriptions`, the same fields, `Authorization: Bearer` when `ears.openai.api_key` is set | 16 kHz mono WAV | ears' | any server speaking the route, local or hosted; the URL carries its version path and has no default |
| `nemotron` | streaming | WebSocket `<ears.nemotron.url>/v1/audio/transcriptions/realtime` (`http` maps to `ws`, `https` to `wss`), bearer key when `ears.nemotron.api_key` is set; `GET /ready` probe | binary little-endian PCM16 at 16 kHz, sent as it arrives | ears'; the server's endpointing stays off | NeMo-Speech.cpp; default URL the Compose service `stt-nemotron` |
| `kyutai` | streaming | WebSocket `<ears.kyutai.url>/api/asr-streaming` (`http` maps to `ws`, `https` to `wss`), header `kyutai-api-key` (the key, or `public_token` when none is set) | MessagePack `Audio` messages, float32 in -1..1 at 24 kHz | ears', and optionally the model's end of turn | `moshi-server`; default URL the Compose service `stt-kyutai` |
| `stub` | batch | none | n/a | ears' | `stub transcript (<n> ms)` |

**`nemotron`.** On connect the server sends `session.created`; ears sends no `session.update`, since the defaults (16 kHz, endpointing off) are what it needs. Audio goes as binary frames of whatever size ears has. `conversation.item.input_audio_transcription.delta` events maintain the hypothesis: where `extends_previous` is true the `delta` is appended, otherwise it is the whole revised text and becomes the hypothesis. At close ears sends `input_audio_buffer.commit` and takes the `transcript` of the `...completed` event as the final, then closes the connection; a session is not reused, so `input_audio_buffer.clear` is not needed. An `error` event fails the session. A final that does not arrive within `ears.stt_timeout_ms`, or a connection that drops during `finish()`, is a failed session: the clip goes to the batch engine.

**`kyutai`.** The server needs 24 kHz audio and does not resample, so the adapter upsamples ears' 16 kHz frames with the shared `resample` and sends float32 samples. The server advances only on audio, so a pause with no audio would stall the model and its end-of-turn probabilities: while a session is open and no frame has arrived for 80 ms the adapter sends 80 ms of zeros, which is fill, not speech. Frames that arrive after fill are appended to the stream. Each `Word` message is appended to the hypothesis once (a word is never revised; `EndWord` is ignored). A `Step` message carries four probabilities that a pause of 0.5, 1, 2 and 3 s has begun; the adapter reads the third.

- **Flush.** Words arrive about 0.5 s after they are spoken, so `finish()` makes sure the model has had at least 0.6 s of silence after the last real audio (it sends the shortfall as zeros), sends a `Marker` and keeps sending silence until the server echoes it, bounded by `ears.stt_timeout_ms`. A flush that times out is not a failure: the words received by then are the final, because they were heard and a missing tail costs less than the whole utterance.
- **End of turn.** Where `ears.kyutai.end_of_turn` is `on`, the adapter calls `onEndOfTurn` when a `Step`'s third probability exceeds `ears.kyutai.end_of_turn_threshold` (default 0.5). It fires at most once per session, only after speech has begun in the utterance (at least one `Word` has arrived and the detector has classified a frame as speech) and before the utterance is closed, and never under `ears.vad.engine: gap`, where no frame is classified as speech. ears then closes the utterance: the clip ends at the last frame ears had received when the signal fired, and that frame's arrival time is `timing.audioEndedAt`. Audio that arrives after it begins a new utterance whose pre-roll holds only frames that arrived after the close, so no audio already sent is sent twice. If `ears.max_utterance_ms` is reached first, that close wins and the signal does nothing. The final is taken as above. This shortens the wait after a speaker stops, the `endpoint` stage of the latency report; it does not shorten anything else, the flush still needs the model's own delay, and it can cut a speaker who pauses mid-thought, which is why it is off by default. Whether it is shorter in practice is for the latency report to show.
- **A drop during the flush.** A connection that closes during `finish()`, while the `Marker` is awaited, is a failed session and the clip goes to the batch engine; only a flush that times out with the connection open takes the words received so far.
- **Intake and the server falling behind.** Buffered frames at open are sent as fast as the socket takes them. Whether the server accepts audio faster than real time is unverified; if it does not keep up, or closes, the push bound or the session failure above sends the utterance to the batch engine.
- **Connection.** The server closes a stream after 20 s without a frame and after 120 s without a binary message and has no resume; the fill keeps an open session supplied, and a session lasts one utterance, at most `ears.max_utterance_ms`.

## Utterance endpointing

For a connector source served from frames, ears decides where an utterance ends. Two engines, chosen by `ears.vad.engine` (EARS-VAD-001):

- **`silero`** (default). ears runs a Silero voice-activity detector in the ears process over each speaker's 16 kHz mono frames. An utterance opens at the first frame whose speech probability reaches `ears.vad.threshold` (default 0.5) and closes when `ears.silence_ms` of received audio has passed since the last speech frame (EARS-VAD-002); the utterance includes up to 200 ms of audio from just before that frame, so a word's onset is not clipped by the detector's reaction time, and other frames with no open utterance are discarded, which keeps a continuous source such as desktop loopback from opening an utterance on silence (EARS-VAD-003). The clip sent to speech-to-text ends at the last speech frame, so the closing silence is neither transcribed nor counted in the audio-end stamp (EARS-HEAR-012). Closing on silence is a measured end of speech, so `ears.silence_ms` can stay short without splitting a sentence at a breath, but it still trades sentence splitting against latency.
- **`gap`**. The frame-gap rule of EARS-HEAR-001: an utterance closes when no frame from its speaker has arrived for `ears.silence_ms`. Right for a connector that sends frames only while someone speaks (the Discord connector).

Under both engines the frame-gap rule stays in force (EARS-VAD-004), so a stalled source, or a connector that disappears mid-utterance (EARS-CON-004), closes the utterance. Under both engines `ears.max_utterance_ms` (default 15000) closes an utterance whose buffered audio reaches it and the speaker's next speech opens a new one (EARS-VAD-005): nothing waits for a speaker who never pauses, and the cap bounds both memory and the size of a partial transcription's growing window. Each speaker id has its own buffer, detector state and partial state (EARS-VAD-007); a missing frame (`seq` gap) is counted and neither closes nor resets anything (EARS-VAD-008). When the detector model cannot be loaded the source is `down` with a detail that carries `vad unavailable: <reason>` and ears does not substitute the gap engine, so the operator sees the fault and can choose `gap` (EARS-VAD-006).

A streaming STT engine does not change who ends an utterance: ears does, by the rules above. The one addition is Kyutai's semantic end of turn, which under `ears.kyutai.end_of_turn` closes an open utterance early at the frame it fired on ([STT engines](#stt-engines)).

Sources that deliver whole clips (`http`, `dir`, a connector served over `http`) and injection have nothing to cut: the sender or the file is the utterance, so the engine setting does not apply to them, and they are transcribed by the batch engine ([STT engines](#stt-engines)).

## Partial transcripts

While a connector utterance is open, ears can publish `speech.partial` events carrying the words it has firmed up so far. A streaming engine supplies its own hypotheses ([STT engines](#stt-engines)). A batch engine has no streaming mode a live feed can use, so ears runs LocalAgreement over its `transcribe`; this is the method of the rest of this section:

1. **Step.** Every `ears.partial_step_ms` (default 1000), once the utterance has `ears.min_speech_ms` of audio, ears sends all of the utterance's audio so far to `/v1/audio/transcriptions` (EARS-PART-004).
2. **Commit.** The words that the two most recent successful transcriptions agree on, from the start, are committed; the committed text is taken in the later transcription's wording (EARS-PART-005). A partial of a batch engine is published only when the committed text has grown, so those partials never get shorter in words (a streaming engine's hypothesis can be revised to something shorter); a later partial may still revise an earlier word (the first two runs can agree on "ice" and a later pair on "I scream"), so a consumer takes each partial of an utterance in place of the previous one, never appends.
3. **Publish.** `speech.partial { speaker, speakerId?, source, text, seq, utteranceId, timing? }` (EARS-PART-006, BUS-EVT-026), through the same word-character and drop-phrase filters as a final (EARS-PART-007).

The final is unchanged: when the utterance closes, ears transcribes the whole clip once and publishes `speech.heard` with the same `utteranceId` (EARS-PART-003). The final does not wait for a partial in flight and a partial that returns late is discarded, so no partial follows the final (EARS-PART-009).

**When it runs.** `ears.partials` is `on` or `off` (default `off`): partials cost speech-to-text calls, so they are an explicit choice (EARS-PART-001). `ears.stt_gpu` (default false) is the operator saying a batch backend runs on a GPU; it changes nothing but a startup warning when partials are `on` with a batch engine and without it, and a streaming engine never warns, because a CPU backend is estimated at 1 to 2 s per call against a 1 s step and will mostly skip steps (EARS-PART-012). ears does not detect the backend's hardware: speaches reports none. A batch engine at a hosted URL sends the growing window off the LAN again at every step, so partials with `openai` multiply the audio that leaves. The `stub` engine never produces partials (EARS-PART-011) and whole-clip sources and injection never do (EARS-PART-002).

**Cost control.** Each partial sends a growing window, so a call costs up to the cap's worth of audio. At most one partial call per utterance is in flight and a step that finds one running is skipped, not queued, so a backend slower than the step only lowers the partial rate (EARS-PART-008). A failed partial call publishes nothing, restarts agreement, and leaves `deps.stt` alone: only a final or injected transcription moves that dependency, so a struggling backend's partials cannot flap the heartbeat (EARS-PART-010).

**Who reads partials.** Nothing in this release: salience, cortex, working-memory (so affect and memory too) subscribe to `speech.heard` and not to `speech.partial`, and the dashboard feed has no row for it. A partial never enters context as speech and never triggers a reply.

## Early transcripts

An utterance closes when `ears.silence_ms` (default 700) of silence has passed since the speaker's last speech frame, and everything downstream waits for the close. An **early transcript** lets the brain start work on what has been said while ears is still deciding whether the speaker has finished. The close itself is not shortened: `endpoint` stays about `silence_ms`. What early reply removes from the wait after the close is the transcription, which has already run, and the model call, which the brain has already started ([HLD](../../high-level-design.md) Early reply, [salience](../salience/salience-design.md) Early transcripts, [cortex](../cortex/cortex-design.md) Provisional think). ears owns only the early snapshot and its signals. In ears' words: it **reuses** an early transcript as the final when the speaker does not resume, and it **retracts** it when the speaker does.

**When it applies.** `ears.early.enabled` is a boolean, default false: early reply spends a transcription on each pause and a model call on each retraction, and its effect on the latency report is for the owner to measure first, as `partials` and barge-in are explicit settings. It applies to an utterance ears cuts itself from a connector source's frames ([Utterance endpointing](#utterance-endpointing)), when the selected engine is a batch engine. `http`, `dir` and injected clips have no endpointing and no wait to use. A source named in `ears.echo_suppress_sources` never has an early snapshot, because its utterances are held until close and the echo gate decides on the audio-end time ([Echo gate](#echo-gate)).

**A streaming engine.** With a streaming engine selected (`nemotron`, `kyutai`) and `ears.early.enabled` true, ears makes no early snapshot and publishes no early transcript. The config load does not fail. ears logs one warning at start that names `ears.early.enabled` and the selected engine and says early reply is off because that engine is streaming, and its heartbeat detail says `early reply off: streaming engine`. The reason is that the final text of such an utterance comes from the session's `finish()`, which can differ from a hypothesis taken in a pause, so nearly every early transcript would be retracted.

**The early snapshot.** For each open utterance, ears takes an early snapshot, a transcription of the audio so far that leaves the utterance open (unlike a close, which ends it), when all of these hold:

- `ears.early.after_ms` (default 250, at least 100 and always below `ears.silence_ms`, so a wait is left) has passed since the last speech frame, by the same measure as the close: received audio since the last frame classified as speech under `silero`, or the frame gap under `gap`;
- the utterance has at least `ears.min_speech_ms` of audio, as a final needs;
- no early transcription of this utterance is in flight, and no published early transcript of it is unresolved;
- a frame classified as speech (any frame under `gap`) has arrived since the last early snapshot of this utterance was taken, whether that snapshot published, was filtered or failed, so there is at most one snapshot per pause;
- fewer than `ears.early.max_per_utterance` (default 2, from 1 to 5) early snapshots have been taken in the utterance, counting every snapshot whether or not it published. A speaker who pauses and resumes more often than that is not one whose pauses predict the end, so the rest of that utterance takes the ordinary close.

The clip is the utterance up to its last speech frame, the same clip a final would send. The batch engine transcribes it, bounded by `ears.stt_timeout_ms` like every engine call. The text goes through the same word-character and `ears.drop_phrases` filters as a final, and an early transcript that is empty, filtered or failed publishes nothing and leaves the utterance to close in the ordinary way; a failed early call leaves `deps.stt` alone, as a failed partial does (EARS-PART-010), because only a final or injected transcription moves that dependency. `ears.min_speech_ms`, the echo gate and the length cap apply as they do to a final: a snapshot needs the minimum audio and an echo-suppressed source has none. A close by the length cap can only follow continued speech, so any early transcript of that utterance was already retracted, and a cap close is always transcribed anew, with neither `earlySeq` nor `earlyLate`.

**Publish.** `speech.early { speaker, speakerId?, source, text, seq, utteranceId, sttMs, timing? }`: `seq` counts the early transcripts published for one utterance from 0 (a snapshot that publishes nothing takes no `seq`; the cap `ears.early.max_per_utterance` counts snapshots taken, because it bounds transcription cost), `utteranceId` is the id the utterance's final carries, `sttMs` is the duration of the early transcription, and `timing.audioEndedAt` is the arrival of the last speech frame, the stamp a final will carry. `speech.early` is its own event, distinct from the other two transcript events: a `speech.partial` is an unstable preview that nothing may act on, and `speech.heard` is final.

**Resumption: retracting.** When the same speaker's next speech frame (any frame, under `gap`) arrives while the utterance is still open:

- if an early transcript of it has been published, ears publishes `speech.retracted { speaker, speakerId?, source, utteranceId, seq }` naming it, once;
- if an early transcription is still in flight, its result is discarded and nothing is published, so there is nothing to retract;
- the utterance continues as one utterance, with its buffer, detector state and partial state untouched. A later pause may take a further early snapshot, within the limit above. A retracted early transcript is never reused. A later early transcript of the same utterance (a new `seq`, covering the whole clip so far) is reused like any other when the utterance closes with no speech after it; otherwise the final is transcribed from the whole clip as ordinary.

ears publishes `speech.retracted` before any later event of that utterance, so a consumer that reads the stream in order sees the retraction first.

**Reuse: the final is the early transcript.** When the utterance closes with no speech after the last early transcript, the final `speech.heard` is that transcript: ears sends no second transcription, publishes `speech.heard` with the same `utteranceId`, `earlySeq` set to the `seq` of the early transcript it reused (which tells a consumer that the final text is the text it already saw) and `earlySttMs` set to that transcript's `sttMs`. The final's `timing` carries the `audioEndedAt` of the early transcript and the `closedAt` of the close, and its `stt` stage is the time to publish, not to transcribe.

If the utterance closes while an early transcription is still in flight and was not discarded because speech resumed (a discarded result is never published, not as a final either), ears waits for that call (it is already the transcription the final needs, bounded by `ears.stt_timeout_ms`) and passes its result through the filters of a final (empty, no word character or a drop phrase publishes nothing); a result that passes is the final, published with `earlyLate` true and no `earlySeq`, and no `speech.early`: no consumer acted on a transcript that was never published. That outcome says the early snapshot came too late for this engine or this `after_ms`. If the call fails, ears transcribes the clip once as for an ordinary final. A connector that disappears mid-utterance closes the utterance by the frame-gap rule (EARS-CON-004), and an early transcript published before then is reused by that close.

**Who reads them.** salience subscribes to `speech.early` and `speech.retracted`; cortex, affect and memory do not, and the dashboard feed has no row for either. An early transcript enters a working-memory window in one case only, a spoken interjection, as an unfinished line appended before the reply; the utterance's final is appended later as an ordinary line ([salience](../salience/salience-design.md) Interjection, [working-memory](../working-memory/working-memory-design.md) An unfinished line).

**Counts.** ears keeps four counts since it started, the one list used wherever ears reports them: early transcripts published, retracted, reused as the final, and early transcriptions still running at the close, whatever their outcome (a filtered or failed one counts, though it publishes nothing). They are reported in the heartbeat detail beside the frame counts, as `early: <published> published, <retracted> retracted, <reused> reused, <late> late`; `cohostctl latency` derives its counts from bus history.

## Connector sources

A connector source is a source name that is not `http` or `dir`: the Discord connector serves `discord` today, and any connector may register another tag ([connections](../connections/connections-design.md)). ears does not know what stands behind a tag.

- **Availability.** ears reads the connector registry (CONN-REG-006). The source's dependency is `ok` while a live registration offers `audio-in` for the tag with `ready` true and ears is reading the stream, and `down` with the detail `<tag> connector not connected` otherwise (EARS-CON-005). A connector that restarts, or is started after ears, is picked up without restarting ears.
- **Format.** `audio.in` frames are 16 kHz mono, so ears performs no resampling for them (CONN-AUD-003); a frame of another format or a malformed frame is dropped and counted, and missing frames are counted from `seq` gaps; both counts go in the heartbeat detail (EARS-CON-003).
- **Loss.** ears reads live and never replays: audio from while ears was down is lost by design, and if ears is slower than the producer the stream's cap evicts the oldest frames (CONN-BP-001 to CONN-BP-003).
- **Isolation.** A connector source failing marks only its own dependency `down`; the other sources, injection and the heartbeat keep running (EARS-SRC-004, CONN-ISO-001). A speaker whose connector disappears mid-utterance is closed by the silence rule (EARS-CON-004).
- **No Discord in ears.** The bot login, the voice connection, the rejoin loop, Opus decoding, the bot-account filter and the resampling from 48 kHz stereo all belong to the Discord connector (CONN-DISC-*).

## Capture sources

A capture source is an adapter that hands finished audio clips to the one `Hearing` path (`hearing.ts`); it owns how audio arrives and nothing else. `capture.ts` defines the contract: `CaptureAdapter { name; start(): Promise<void>; stop(): Promise<void> }` and `decodeClip`, which turns uploaded bytes into 16-bit PCM with its rate and channel count. a connector source (such as `discord`) is the adapter that cuts utterances per speaker from the frames of `audio.in.<tag>`; `desktop` is the `http` adapter's listener serving the desktop capture helper ([Desktop audio](#desktop-audio)); `http` and `dir` are the adapters that need no account, so ears can be run, tested and used in mock mode (`ears.stt_engine: stub`) with nothing but a terminal.

`Hearing.heardClip(clip, speaker, source)` is the shared path. It resamples the clip to 16 kHz mono with the shared `resample`, drops it when shorter than `ears.min_speech_ms`, transcribes it, drops a transcript with no word character or equal to an `ears.drop_phrases` entry, and otherwise publishes `speech.heard { speaker, text, durationMs, source }` (a live transcript: not `injected`, no `speakerId`; `source` is the adapter's name). It returns the outcome (`heard`, or the reason nothing was published: `too-short`, `empty`, `drop-phrase`, `echo`, `stt-error`), which the adapters report back to the caller.

**`http`.** ears listens on `ears.http.host:ears.http.port` (default `127.0.0.1:8765`; port 0 picks a free one for tests). `POST /audio` carries one clip: a WAV (`audio/wav`, `audio/x-wav`, `audio/wave`, parsed by the shared `parseWav`, 16-bit only) or raw little-endian 16-bit PCM (`audio/L16` or `audio/pcm`, with `rate` and `channels` content-type parameters defaulting to 16000 and 1). The optional `speaker` query parameter names the speaker (default `http`). The reply is JSON `{ heard, text?, reason? }` with status 200 once the clip has been through the path. The listener is bounded with the inject limits (the byte cap and timeout of EARS-INJ-010, the queue length `INJECT_QUEUE_LIMIT` of `@cohost/shared`): a body over `INJECT_MAX_BYTES` (25 MiB) is refused 413 as soon as it is known to exceed the cap, a body that takes longer than `INJECT_READ_TIMEOUT_MS` to arrive is cut off, clips are processed one at a time, and more than `INJECT_QUEUE_LIMIT` waiting clips are refused 503. Other statuses: 404 (path), 405 (method), 415 (content type), 400 (audio that does not decode), 502 (speech-to-text failed). A port that cannot be bound leaves the process up with `deps.http` down and a `degraded` heartbeat, the configuration-gap posture.

**`dir`.** ears polls `ears.dir.path` every `ears.dir.poll_ms` (default 1000; the directory is created when missing). A regular file whose name ends in `.wav` (any case) and whose size is the same on two consecutive polls (so a file still being copied in is left alone) is processed once: it goes through `heardClip` with speaker `dir`, then is moved to a name with a suffix recording the outcome (`.done`, `.rejected` for a file over the byte cap or not decodable, `.failed` when speech-to-text failed). If the rename fails the name is remembered in memory and the file is not read again. At most `INJECT_QUEUE_LIMIT` files are taken per poll, in name order, one at a time. Polling instead of `fs.watch` keeps behaviour identical across WSL, Docker bind mounts and network shares.

Both adapters transcribe through the same `EarsHealth.track`-wrapped transcriber as connector sources and injection, so `deps.stt` follows them too, and every source shares the same filters, so a stub-engine clip ("stub transcript (n ms)") flows through the same drop-phrase and word checks.

### Example clients

The docs site's Send audio to ears page shows how to feed the `http` source from a program. `examples/audio-in/` holds a client in Python (`send_clip.py`, standard library) and one in TypeScript (`send-clip.ts`, Node built-ins, run with `node` on Node 22.18 or later), both with the same arguments (a file, `--url`, `--speaker`, `--source`), a `curl` script (`send.sh`) sending the same request, and two one-line conversion scripts that turn any recording into the 16 kHz mono 16-bit WAV ears transcribes without resampling (`to-wav-sox.sh`, `to-wav-ffmpeg.sh`). ears resamples any rate and channel count itself, so conversion is for formats ears does not read (MP3, M4A, Ogg), not a requirement of the route. Every client sends the bearer token from `EARS_HTTP_TOKEN` when it is set (EARS-SRC-013), prints ears' JSON reply and exits non-zero when the clip was not accepted (EARS-EX-001 to EARS-EX-004).

`services/ears/test/example-clients.test.ts` runs each client against a real `http` capture with the stub transcriber, so the clients are held to the listener they talk to (EARS-EX-005); a client or converter whose program is not installed is skipped, as the reference hook server test skips `server.py` without `python3` (EARS-EX-006, EARS-EX-007).

## Echo gate

The desktop capture helper records the host's output device, so when the co-host's voice plays on that device (a local audio output, or the dashboard page opened on the host) the helper hears it and ears would transcribe the co-host as if it were a person, answer it, and, for salience, treat it as an interruption. The Discord source cannot do this, because the connector reads no bot account. The echo gate drops utterances from the sources that can.

- **Which sources.** `ears.echo_suppress_sources` (default `[desktop]`, CFG-SCH-036) lists source names. A name that is not an enabled source has no effect and is not an error. Sources not listed are never gated.
- **What it listens to.** Only where a listed source is enabled, ears subscribes its `ears` group to `voice.playing` and `voice.done` as well as `inject.request` (EARS-ECHO-001). A `voice.playing` from any sink except `virtual` (which plays nothing anywhere) opens the entry of the clause it names, keyed by the line's `id` and the clause's `seq`, in a set of playing clauses; the `voice.done` for that `id` and `seq`, from any sink and whether or not it is flagged `interrupted` or `final`, removes it (EARS-ECHO-002). An entry that never receives its `voice.done` expires after a fixed 60 s, so a sink that crashed mid-clause cannot keep the gate shut (EARS-ECHO-003).
- **The window.** The gate is open while the set is not empty and for `ears.echo_tail_ms` (default 1500, CFG-SCH-036) after it last became empty. A `voice.playing` that arrives during the tail reopens the gate at once, so a tail that overlaps the next line simply merges with it (EARS-ECHO-006). The clauses of a streamed line are separate entries: the gate is open while a clause plays, shuts its tail when the clause ends, and reopens on the next clause's `voice.playing`, so the pause between two clauses is bridged by the tail. A pause longer than `ears.echo_tail_ms` (a model slower than the speech) lets the gate close in the pause: the echo of the clause before it has by then arrived or been dropped, and a person who speaks in the pause is heard. All times are ears' own clock at the moment it receives the event or the audio.
- **What it drops.** An utterance of a listed source whose audio ended, the `audioEndedAt` that `speech.heard` already carries (EARS-HEAR-012), while the gate was open is dropped before speech-to-text: no transcription call, no `speech.partial`, no `speech.heard` (EARS-ECHO-004, EARS-ECHO-005). An utterance that began before the line and ended inside the window is dropped whole; one that ends after the tail is kept whole, whatever it contained. Injected audio is never gated (EARS-ECHO-008).
- **The tail.** The echo of a line reaches ears late: the helper cuts a clip after its own silence period and posts it, and a stream source is closed by `ears.silence_ms` after the last frame. `ears.echo_tail_ms` must cover that delay, or the clip that holds a line's last words arrives after the gate has closed. The default covers the helper's default cut with margin; an operator who raises the helper's `--silence-ms` raises the tail with it.
- **State.** The gate is in memory. A restart starts with it closed, so one line in progress at the restart can leak a single echo (EARS-ECHO-007).
- **Streaming engines.** A gated source never opens a streaming session ([STT engines](#stt-engines)): its utterances are held until close and the gate decides before any engine sees them.
- **Early transcripts.** A gated source has no early snapshot ([Early transcripts](#early-transcripts)), for the same reason: the gate decides at close.
- **The price.** While a line plays, a person's speech on a gated source is lost too. That is why salience's `barge_in_sources` defaults to Discord and not the desktop source ([salience](../salience/salience-design.md) Barge-in).

## Speaking

ears does not play audio. The Discord playback sink, the spoken fallback line and its clip cache are [mouth](../mouth/mouth-design.md)'s. ears never hears the co-host's own voice from Discord, because the Discord connector reads no bot account's audio (CONN-DISC-007), and it drops the audio of sources that can (the echo gate).

ears does not subscribe to `control`: it publishes `speech.heard` whatever the mute or pause state, which cortex and salience enforce upstream (EARS-HEAR-009).

## Audio Injection

`createInjectHandler` (`inject.ts`) returns the `inject.request` handler. It is built in `service.ts` for **every** plan and is the only handler on the `ears` loop in every plan (EARS-START-003). The shared handler queues a request and returns at once, so the loop reads the next `inject.request` while STT is still working on the last one; requests are answered in order, and a ninth waiting request is answered `busy` (EARS-INJ-011, SHARED-INJ-*).

Processing order for a request `r` (publishing `inject.result { id, ok, detail? }` on every failure path):

1. `r.target !== "ears"` returns silently with nothing published.
2. Older than `INJECT_STALE_MS` = 60 000 ms by the event's `ts` returns `ok:false, "stale"` (`INJECT_STALE_MS` from `@cohost/shared`, SHARED-INJ-008). (Consumer groups resume after a restart, which is why.)
3. `r.kind !== "audio"` returns `ok:false, "ears cannot handle kind '<kind>'"`.
4. The request must carry an `uploadId` (32 hex digits); otherwise `ok:false, "request carries no upload id"` and nothing is read.
5. The shared handler reads the bytes with `Bus.takeUpload(uploadId)` (`GETDEL` of `cohost:upload:<id>`), bounded by 30 s and 26214400 bytes; a missing or expired key returns `ok:false, "upload expired or missing"` (SHARED-INJ-013), a timeout or oversize returns `ok:false` with a detail naming it (SHARED-INJ-006, SHARED-INJ-007).
6. The bytes go **unchanged** to STT with the request's `contentType` as a hint (default `audio/wav`); `ears.min_speech_ms` does not apply.
7. A transcript with no word character (Unicode letter or number) returns `ok:false, "empty transcript"`.
8. Success publishes `speech.heard { speaker: r.meta?.user || "injected", text, durationMs: wavDurationMs(audio), injected: true, remember: r.remember }` plus `source: r.meta.source` when the request carries one (EARS-INJ-012) then `inject.result { ok:true, detail: text }`. `wavDurationMs` returns 0 for non-WAV or unreadable input. No `speakerId` is set.
9. Any exception logs `"audio injection failed"` and attempts `inject.result { ok:false, detail: String(err) }` (swallowing a bus failure).

Injection works in every plan whether or not any source is available (it must work when `ears.sources` is empty or Discord is not connected). The `off` plan and every plan with sources subscribe at startup, before any source starts, and keep handling injection whatever the sources do (EARS-CAP-003, EARS-INJ-009).

## Multiple sources

ears runs every enabled source at the same time. `ears.sources` is a list of source names: `http`, `dir` or a connector source tag such as `discord` or `desktop`, where the tags are an open set registered by connectors and ears holds no list of them; the default is `[discord]`, which is the behaviour of a single-source install. An empty list means `off`. `EARS_SOURCES` overrides the list in flow syntax; the Compose file passes it through as an isolation preset.

**One adapter per source.** `earsPlan` returns the set of sources to start, each with its own state: `runnable`, or a configuration gap (the `dir` source with an empty `ears.dir.path`, EARS-CAP-010; a listener-fed source whose listener cannot bind is not a gap but a failure, EARS-SRC-004). The service starts each runnable source as a `CaptureAdapter` and stops each one independently. Starting is isolated: a source whose `start()` rejects, whose listener cannot bind, or whose connector is absent marks only its own dependency `down` and does not stop, restart or delay the others. A source that is a configuration gap does not exit the process; it logs an error and reports itself `down` with the reason, and the other sources run. When no source is runnable (the `off` plan, or every enabled source is a gap) the service takes the shared idle plan, with the reason text of the gap or gaps, exactly as a single-source install does today (EARS-START-008). Injection (`inject.request`) is handled whatever the sources.

**Per-source health.** The heartbeat carries one dependency per enabled source, named for it (a connector tag such as `discord` or `desktop`, `http`, `dir`), `ok` while that source is delivering (the connector present and ready, the listener bound, the directory polled) and `down` otherwise; a `down` dependency makes a `ready` service `degraded` through the shared heartbeat, naming it. A source that is not enabled shows `n/a`. `stt` stays shared, since every source transcribes through the one health-tracked transcriber.

**Source tag.** Each adapter passes its own name to the shared path, so `Hearing.heardClip` publishes `speech.heard` with an optional string `source` (a connector tag, `http` or `dir`). The field is optional and additive: consumers that ignore it are unaffected, an event from before the field existed has none, and an injected transcript (`injected: true`) carries one only when its request names a source (`meta.source`, EARS-INJ-012), so a test input can stand in for a listening source; otherwise it carries none because it did not come from one. The bus event schema owns the field ([event-bus](../event-bus/event-bus-design.md)). Every source passes the same filters: minimum duration, word character and drop phrases (EARS-CAP-001).

**Speaker labels.** A source that cannot tell speakers apart names the speaker by source: a source published as `desktop` uses speaker `desktop` unless the helper names one (the `http` and `dir` default labels are `http` and `dir`). Discord keeps its per-speaker display names and `speakerId`. The source tag and the speaker are separate fields, so a downstream consumer can tell "the desktop audio" from "a person called desktop".

## Desktop audio

ears runs in Docker or WSL and cannot see the host's audio devices, so desktop audio (the game, a browser, OBS's own output: OBS is one program playing into it) does not enter ears through a device adapter. A small bundled **capture helper** runs on the host that owns the audio, and the helper is a connector serving the source tag `desktop` ([connections](../connections/connections-design.md#desktop-audio-helper)). It registers and keeps its registration fresh through the connector protocol (CONN-DESK-001), and until it writes frames its clips ride the existing `http` capture adapter: its capability declares `transport` `http`, so ears serves the `desktop` source through the `http` listener and reads no stream for it. ears gains no audio-device dependency. Moving the clips onto `audio.in.desktop` is deferred (CONN-DESK-002, EARS-SRC-016): the HTTP clip path described here is the interim path, and the registration and liveness do not change when it migrates.

**Helper platforms.** One cross-platform helper, with a backend per host: on Windows it records the default render device through WASAPI loopback, and on Linux it records the PulseAudio or PipeWire monitor source of the default sink (selectable by device or source name). On an unsupported host, or when the device cannot be opened, the helper exits non-zero with a message and posts nothing.

**Cutting clips.** The helper, not ears, turns the continuous feed into clips, because it holds the raw stream: it converts to 16 kHz mono 16-bit PCM, closes a clip after a configurable run of silence (`--silence-ms`) and at a configurable maximum clip length (`--max-clip-ms`), drops a clip with no audible sample above a level threshold (`--silence-level`), and POSTs each as `audio/L16` (`rate=16000`, `channels=1`) with the source tag `desktop`. The maximum clip length keeps every body under `INJECT_MAX_BYTES`, so a feed that never pauses still produces clips. ears applies its own minimum-duration and drop-phrase filters (EARS-SRC-007) on top, so the helper's cut is a transport concern and the `http` adapter stays the single place clips enter `Hearing`.

**Clip and delivery rules.** Defaults are `--silence-ms` 700, `--max-clip-ms` 15000 and `--silence-level` 500 (an absolute 16-bit magnitude, about 1.5% of full scale; a sample is audible above it); a clip closes when the silent run reaches `--silence-ms` and when it holds exactly `--max-clip-ms`, begins and ends up to 100 ms (or `--silence-ms` when shorter) around the audible span so the closing silence is not posted (the leading span takes what is available, stops at the previous clip's end and counts toward the cap), and the 15 s cap keeps a body near 480 kB, far under `INJECT_MAX_BYTES` (EARS-SRC-017). `--device` names a Linux source and has no Windows value; a missing source or a Windows value is a non-zero exit with nothing posted (EARS-SRC-018). A change of the followed default device re-opens it, and any other device failure flushes the held clip, deregisters and exits non-zero (EARS-SRC-019). Posting retries on a connection failure, 400, 408, 429 and 5xx with a delay of 500 ms doubling to 30 s, logs the failure when it first occurs and when it changes, drops any other refusal, and holds at most four waiting clips (EARS-SRC-020); a stop makes one last attempt for the held clip before it deletes the registration, and drops every clip not delivered (EARS-SRC-022); a helper displaced by another instance does the same without deleting the key and exits non-zero (CONN-DESK-004). The token is `--token`, then `EARS_HTTP_TOKEN`, an empty value counting as unset and a CR or LF in it refused (EARS-SRC-021). Command-line values are validated before capture: the URL is a plain `http` URL with a host, no userinfo and a valid port, the clip flags have bounds, and a token sent to a non-loopback host draws one warning (EARS-SRC-015, EARS-SRC-017). A POST times out after 5 s to connect, 10 s to send and 120 s for a response; a response timeout is dropped, never retried, because ears answers after transcription and a retry would repeat `speech.heard`, while a connection closed before the status line is retried (EARS-SRC-020). The resampler keeps its state across buffers and low-passes before decimation (EARS-SRC-014), and a delivery-task panic is reported at stop (EARS-SRC-022). A read failure on a followed default device first asks whether the default changed (EARS-SRC-019); a second stop signal exits at once, and a panic in the capture thread exits without the registration delete, so in both cases the key expires on its lease (EARS-SRC-022). The registration's fields, interval and lease, and its retry while Redis is unreachable, are CONN-DESK-004 and CONN-DESK-005.

**Addressing and authentication.** The helper posts to the `ears.http` listener (default `http://127.0.0.1:8765`, overridable with `--url`). The Compose file publishes that port on the host's loopback only (the HLD's deployment posture), which a Windows host reaches through WSL2's localhost forwarding, so no port opens to the LAN. The operator's loopback is the trust boundary, as for the rest of `http`. Where the owner binds the listener beyond loopback, or wants a shared secret regardless, `ears.http.token` (a key of `secrets.yaml`) makes `POST /audio` require `Authorization: Bearer <token>` and answer 401 otherwise; the helper reads the same value from `--token` or from its own `EARS_HTTP_TOKEN` environment variable (a variable of the client program, outside cohost's own environment). With no token set the listener behaves as before.

**Source tag.** The helper names the source with the optional `source` query parameter on `POST /audio` (`/audio?source=desktop`). The accepted values are `http` (the default when the parameter is absent) and the tag of an enabled source whose live registration declares `transport` `http`, which today is `desktop`. A value that names a source that is not enabled, is served by a stream, has no live registration, or is any other value, is refused 400, so a mistyped tag cannot invent a source. The adapter passes the tag to `Hearing.heardClip` as its `source` argument, which is how `speech.heard.source` reaches the bus, and the default speaker label is the tag (an explicit `speaker` parameter still wins).

**Liveness.** A desktop feed can be silent for minutes, so the absence of clips does not mean the helper is gone. The helper therefore holds a connector registration (`audio-in` for `desktop`, `transport` `http`) that it rewrites every `intervalMs` and deletes on an orderly stop, and `deps.desktop` is `ok` while the listener is bound and that registration is live and `ready` (EARS-SRC-012, CONN-REG-006). With the helper absent, stopped or unable to reach Redis the `desktop` dependency is `down` (the service is `degraded`, naming it) while every other source keeps running; the helper retries with increasing delay when ears or Redis is unreachable, and the dependency returns to `ok` when the registration reappears, without a restart of ears. ears has no `POST /ping` route.

**Testing.** The helper's clip cutting runs against a fake feed (a synthetic PCM stream), and the `desktop` source is tested by a test client that writes a registration and posts tagged clips to the listener, so neither needs a sound device, OBS or an account.

## Health

`EarsHealth` (`health.ts`) is the `HeartbeatSpec` for `service: "ears"`:

- `mode`: `"off"` for the `off` plan, `"mock"` with the stub engine, else `"live"`.
- `deps`: `off` gives `{ discord: "n/a", stt: "n/a" }`; otherwise `stt` is the outcome of the last transcription or session (initially `"ok"`, or `"down"` until the first ping where the engine has one) and each enabled source has its own dependency (`discord` or another connector tag, `desktop`, `http`, `dir`), `ok` while that source is delivering and `down` otherwise, and a source that is not enabled is `n/a` (EARS-SRC-005, EARS-HLTH-002, EARS-CON-005); taken alone, the `http` and `dir` plans add `http` and `dir` (EARS-CAP-011). The heartbeat detail carries the dropped and missing frame counts of the connector sources (EARS-CON-003) and, where early transcripts are enabled, the early counts ([Early transcripts](#early-transcripts), Counts).
- `startHeartbeat` (owned by [control-plane](../control-plane/control-plane-design.md)) turns any `down` dep on a `ready` service into state `degraded` (`packages/shared/src/lifecycle.ts`).
- A connector source's `ok` comes from the registry read and the stream reader, not from a Discord connection; ears has none.
- A connector coming back after an outage returns its dependency to `ok` without a restart of ears (CONN-ISO-001).


## Stub transcriber and shared modules

Where `ears.stt_engine` is `stub` (CFG-SCH-022; the isolation preset sets it, whichever engine is configured), the engine is a batch engine that makes no network request and returns `stub transcript (<n> ms)` for every captured or injected clip; the heartbeat reports mode `mock` (or `off` with source `off`) and `deps.stt` `n/a` (EARS-STUB-*). Injection runs through the shared inject handler with kind `audio`, 25 MiB and 30 s (EARS-INJ-010).

| Utterance endpointing | A Silero voice-activity detector run in the ears process (EARS-VAD-002), with the frame-gap rule kept as a safety and `ears.max_utterance_ms` as a cap | Speaches' server-side `POST /v1/audio/speech/timestamps`; speaches' `/v1/realtime` WebSocket turn detection; the gap timer alone; sherpa-onnx streaming with its own endpointing | The server-side endpoint takes an uploaded file, so it cannot cut a live stream; the realtime WebSocket does server-side turn detection but then makes one batch transcription per turn and yields no partials, so it adds a transport without adding capability; the gap timer cannot cut a continuous source and always waits the full pause. A detector in ears is local, cheap on CPU and independent of the STT backend; keeping the gap rule means a stalled source still closes. |
| Partial transcripts (batch engines) | LocalAgreement over the batch endpoint: re-send the growing utterance each step, commit the prefix two consecutive runs agree on (EARS-PART-004, EARS-PART-005); a streaming engine publishes its own hypotheses instead | `stream=true` SSE on the transcription endpoint; speaches' realtime WebSocket; sherpa-onnx (a streaming recogniser as a new service); no partials | speaches 0.8.3 has no streaming transcription for a live source: SSE streams the segments of an already uploaded file, and the realtime WebSocket publishes only a finished turn. sherpa-onnx streams on CPU but adds a service and a lower-accuracy model for a feature nothing consumes yet. LocalAgreement needs only the endpoint ears already uses, at an estimated 0.1 to 0.3 s per call on a GPU and 1 to 2 s on a CPU, which is why it is opt-in. |
| Partials switch | An explicit `ears.partials` (`on`, `off`, default `off`); `ears.stt_gpu` only gates a warning | An `auto` mode that follows `ears.stt_gpu`; detect the backend's hardware; partials always on | speaches exposes no hardware, so detection would be a guess; always on would load a CPU backend with calls it cannot finish; `auto` plus a flag is two settings for one choice, since an operator who declares a GPU and wants partials sets `on` anyway. |
| `utteranceId` minted by ears | Every utterance, clip and injected clip gets a unique id that the partials and the final share | Derive it from speaker and start time; carry no id and match a partial to its final by text | The speaker id repeats across utterances and text changes between partial and final, so only an id minted at open ties them; a uuid needs no clock or counter shared across speakers. |
| Partials never reach the brain | `speech.partial` is its own event that no brain region subscribes to; `speech.heard` stays the sole trigger, including for salience's speech trigger (SAL-TRIG-001) | Let salience score partials to react sooner; fold the latest partial into working memory | Reacting to an unstable transcript would answer words the speaker is about to change; the final `speech.heard` is the earliest point at which the words are settled, and salience starts its decision there, so a partial would only add decisions about text that is about to change. |
| Trailing silence trimmed under the detector | The clip ends at the last speech frame | Send the closing silence too | The silence carries nothing for speech-to-text and would move the audio-end stamp (EARS-HEAR-012) `ears.silence_ms` after the speech, hiding the pause from the latency report's `stt` stage. |
| Engine contract | `SttEngine` of two kinds: a batch engine has `transcribe`, a streaming engine has `open` and no whole-clip call; whole-clip work always goes to the batch engine (the selected one, or `ears.stt_fallback_engine`) | Separate code paths per engine; a streaming engine that also transcribes whole clips through a one-shot session; streaming only for connector sources | A one-shot session would take a server slot a live speaker needs, and whole-clip inputs (a `dir` file, a test injection) arrive in bursts. A batch engine for them is always available, with no streaming server involved, so the capture adapters have no engine special cases. |
| Session scope | One session per open utterance, opened at the speech edge and closed with the utterance | One long-lived connection per speaker; one per source; a warm pool | A speaker's connection would sit idle between utterances and hold a server slot (Kyutai closes an idle stream and has a fixed slot count); a session per utterance holds a slot only while someone speaks and gets its audio from the fill, so there is no keep-alive and no reconnect logic. A warm pool is the remedy if the connect delay proves large. |
| End of utterance under a streaming engine | ears' detector and `silence_ms` decide, as for batch; Kyutai's end of turn may close earlier, only under `ears.kyutai.end_of_turn` (off by default), at most once, only after speech has begun, at the frame it fired on, and never past `ears.max_utterance_ms`; the third probability is the one read | The server's endpointing (Nemotron's own, Kyutai's end of turn alone); end of turn on by default; the first or second probability | ears cuts several speakers and continuous sources with one rule independent of the engine, which the server's endpointing cannot do for a source with no pauses between frames. The third probability is what the reference clients read; it is the model's prediction that the speaker has finished, not a measured 2 s of silence, so reading it ends a turn sooner than the pause its name suggests. Semantic end of turn is a prediction that can cut a speaker mid-thought, so it is an explicit setting, off until verified live, as `partials` and barge-in are. |
| Trailing words and the fill | The Kyutai adapter sends zeros (fill) while a session is open and no frame has arrived for 80 ms, and flushes with 0.6 s of zeros and a `Marker`; on a flush timeout the words received so far are the final and it is not a failure | Send audio only when frames arrive; drop the utterance on a flush timeout; close without flushing | The server advances only on audio, so the model sees a pause only if the stream carries it, and a connector sends no frames while nobody speaks; its words lag 0.5 s, so a close without a flush loses the last words. A timeout that dropped the whole utterance would lose speech that was transcribed. |
| An utterance whose session cannot serve | The retained clip goes to the batch engine; with none, the utterance is dropped and `deps.stt` says why | Drop the utterance; retry the session; keep a second copy of the audio | ears already holds the whole utterance for the clip, so a session that cannot open, is refused, drops or does not deliver costs only the partials and a call; retrying a session cannot replay audio that has gone. |
| Session capacity | `ears.max_stt_sessions` (default 2); over it, an utterance runs unstreamed and goes to the batch engine at close | Unlimited sessions; a queue of utterances; refuse the utterance | The server's slot count is fixed and a refusal (`no free channels`) would otherwise drop speech; the limit keeps the failure on the ears side. Two covers one speaker on Discord and the desktop source. |
| Batch fallback for a streaming engine | `ears.stt_fallback_engine` (`speaches` default, `openai`, `none`) transcribes the clip of an utterance whose session cannot serve and every whole-clip input; while it runs, `deps.stt` stays `down` with the reason so the service reads `degraded`, until a session of the selected engine succeeds | No fallback (a streaming outage silences the co-host's hearing); fall back to the selected engine's own one-shot call; report `ok` while the fallback works | A streaming server is the likelier to be absent (a heavy GPU container, a first download), and the co-host that cannot hear is a failure of Goal 6. A default of `speaches` keeps the local default hearing. Reporting `ok` would hide that the engine the owner chose is not serving, which is the actionable fact, and a successful fallback call proves nothing about it, so only a session of the selected engine clears the dependency (owner decision). `none` is for an owner who would rather drop speech than send audio to a second engine. Owner decision. |
| Echo-suppressed sources never stream | A source in `ears.echo_suppress_sources` is held to close and transcribed by the batch engine after the gate decides | Open a session and abort it when the gate closes; gate at open | The gate decides on the audio-end time, which is known only at close, and a session opened early would already have sent the echo to an engine and published partials of it. |
| Nemotron route | NeMo-Speech.cpp's realtime WebSocket (`nemotron`) | NVIDIA NIM / Riva gRPC `StreamingRecognize` | No NVIDIA account or key, a self-hostable server whose release build covers RTX 50-series cards (Apache-2.0), and a plain WebSocket that needs no gRPC stack in Node. Riva is NVIDIA's supported production path but needs an account and key (free for development only) and a gRPC client and its protocol files. The cost: NeMo-Speech.cpp is pre-1.0 and its event shapes may change; Riva would be a separate engine value. |
| Hosted STT | Only the `openai` engine pointed at a URL with a key; no hosted-specific adapter | A vendor adapter | The generic adapter covers any service that speaks the route (owner decision), and the URL being off the LAN is explicit egress (HLD tenet 8, Non-Goal 5). |
| STT timeouts | `ears.stt_timeout_ms` (default 20000) on every engine call, including the push of an utterance's buffered start into a new session | No bound; a bound per kind | HLD tenet 3. One key serves the batch request, the connect, the push and the flush; a long silence inside an open session is not a call and is not bounded. |
| Detector runtime and model | `onnxruntime-node` (MIT) running the Silero VAD v5.1.2 ONNX model (MIT, 2.3 MB), committed at `services/ears/models/silero_vad.onnx` with its source URL, tag, SHA-256 and licence in `models/README.md`; a thin wrapper in `services/ears/src/vad.ts` (512-sample windows with a 64-sample context, one recurrent state per speaker id) | `avr-vad` (wraps the same runtime); `@ricky0123/vad-web` and `@ricky0123/vad-node` (browser-oriented and stale); fetching the model at first start | The runtime is the one the model is published for and a wrapper adds a dependency for about sixty lines; a committed 2.3 MB file needs no network at first start and makes the image reproducible. | Early snapshot owner and shape | ears takes an early snapshot after `ears.early.after_ms` of silence, publishes `speech.early` and keeps the utterance open; the final is the early transcript reused when no speech follows, and a resumption publishes `speech.retracted` | salience or cortex asks ears for a transcript on demand; a second, short utterance split off at the early snapshot; a connector-side early marker; scoring partials | ears holds the audio, the detector and the clock that say when a pause began, so the cut belongs to it; asking over the bus would add a round trip to a wait the cut exists to shorten. ## Open Questions & Future Decisions

- **Streaming servers on this hardware.** Unverified: whether `moshi-server` runs on RTX 50-series cards and its VRAM at one stream; the VRAM of NeMo-Speech.cpp; whether either accepts audio faster than real time (the burst of a session's buffered start depends on it; if it does not, the push bound sends the utterance to the batch engine); the stability of NeMo-Speech.cpp's event shapes before 1.0; whether Kyutai's `Marker` echo guarantees every earlier word has arrived.
- **Hearing while the streaming engine is down.** The fallback keeps the co-host hearing, and the service reads `degraded` for as long as the selected engine is down. Reading A (kept): `down` for the selected engine. Reading B: `ok` while the fallback works, with the detail naming it.
- **A language setting.** The language is the constant `en` (the EARS-HEAR-005 reading). Reading B, a multilingual streamer, would add `ears.language`, which `speaches`, `openai` and perhaps `kyutai` (a model for two languages) could use. Decision wanted.
- **End-of-turn tuning.** The threshold 0.5 on the third probability follows the reference clients (their smoothed variant uses 0.6); how it behaves on this stream is for a live run.
- **Partial semantics for revised hypotheses.** A streaming hypothesis may shrink; the consumer rule of BUS-EVT-028 already says a partial replaces the last, and nothing reads partials.
- **Partials of an utterance that ends with no final.** An utterance whose final is dropped (too short, empty, a drop phrase, a failed transcription) leaves its partials without a `speech.heard` that ends them; there is no retract event. A consumer's staleness rule covers it (BUS-EVT-028); nothing reads partials today.
- **Partial load with several speakers.** The one-call-in-flight limit is per utterance, so several speakers talking at once multiply the calls the backend sees. A service-wide limit is deferred (EARS-PART-015).
- **Detector footprint.** `onnxruntime-node` adds about 300 MB to `node_modules` and so to the image; a smaller runtime, or a build that keeps only the target platform's binary, would shrink it.
- **Time to first partial.** The latency report has no stage for it; it is deferred (CTRL-LAT-010) because measuring it needs a stamp for the start of speech, which `speech.heard` and `speech.partial` do not carry.
- **When a partial is stale.** A consumer treats a partial as stale by the rule in the event-bus segment (BUS-EVT-028); no consumer exists yet.
- **Tuning `ears.early.after_ms`.** The default 250 ms is a starting point between the length of a breath and the time a transcription needs; whether a shorter value saves more than it retracts is for the connector-path measurement to show.
- **Early snapshots under a streaming engine.** Deferred (Decisions): an owner who selects `nemotron` or `kyutai` gets no early reply. Whether a streaming engine's own hypothesis can be made reliable enough to reuse as a final is open.
- **Event schema owner.** The optional `source` field on `speech.heard` is specified here (EARS-SRC-006) and is added to the event schema's own spec, BUS-EVT-013, which belongs to the event-bus segment.
