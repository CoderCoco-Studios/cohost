# config

Parent: [high-level-design](../../high-level-design.md). Specs: [config-specs.md](config-specs.md).

## Context and Design Philosophy

`@cohost/config` (`packages/config`) is the dependency root of the workspace: it has no workspace dependencies and every other package and service imports it (`packages/config/package.json` lists only pino, yaml, zod). It owns four things:

1. The **shape** of the settings and of the emotion map (zod schemas in `packages/config/src/schema.ts`: `ConfigSchema`, its section list and `ExpressionMapSchema`), including the nine-value `Emotion` enum that the bus event schemas also import (`schema.ts`), and `SECRET_PATHS`, the list of the settings' credential paths (CFG-SEC-003).
2. The **projection loader**: locate the config directory, load `.env`, read the unit's projection `settings.json`, validate each section it holds, set the credentials the process received in memory at their secret paths, apply the isolation overrides by key path, warn about unknown keys, make an undeclared section throw on access, and cache (`packages/config/src/index.ts`, `pipeline.ts`). The same pipeline, without the file, is `parseConfig`, which the settings store runs on every write.
3. **Small runtime helpers** every service uses: `env`/`envOr`, the `urls.*` service-address functions, `createLogger`, `loadPersonality` and `loadExpressions`, and `ollamaModels`, the list of local models a configuration needs (`models.ts`).
4. The **presentation table** (`packages/config/src/presentation.ts`): the plain-language title, group and one-sentence description of every section, and the help text, label, unit and widget hint of every key, which the settings editor serves with the schema so the Settings screen names every setting without hard-coding any (module-contract MOD-CFG-*).

The settings themselves live in the **settings store** ([settings-store](../settings-store/settings-store-design.md)): one SQLite database on the host, owned by the dashboard, the control plane and the `mise run config:*` tasks, holding every operator setting, the persona, the emotion map and every credential (encrypted). This package does not open it and names no path of it (CFG-SEC-021); it defines what the store holds and how a service reads its share.

Design philosophy (HLD tenet 7; [config in one place](../../decisions/config-in-one-place.md)): every operator setting is a key of the schema with a default, held in the store as a key of its section's document, so the dashboard's settings editor shows and edits all of it; a credential is a secret path, held encrypted in the store and handed to a unit in memory (settings-store Credential delivery), never in a file this package reads and never returned by a read API; `.env` holds only bootstrap values and no credential. A service sees only its **projection**, the JSON file the control plane writes into the unit's config directory before it starts the unit, holding the sections and documents the unit's manifest entry declares and nothing else. No environment variable reaches a setting except through the isolation override: the control plane passes one variable, `COHOST_ISOLATION`, to a container it starts isolated, and the loader applies its entries by key path to fourteen keys (CFG-ISO-006, CFG-ISO-007); every stored value is a literal, and a store write that holds a `${VAR}` placeholder is refused (CFG-ENV-011). Each backend that can be swapped for a mock or off variant is selected by an enum key of that kind; the mock variants are never the default (comment `schema.ts`). The schema is lenient about unknown keys (warn, do not fail) and strict about enums and ranges. The shipped `config/config.example.yaml`, the settings part of the seed a new store imports (settings-store STORE-IO-005), validates with no credential at all: every key it holds is a literal (CFG-ISO-005), while a value that is set but invalid, such as an unknown `avatar.driver`, still fails validation.

## Files and directory resolution

| File | Where | Role | Written by |
| --- | --- | --- | --- |
| `settings.json` | `<configDir>/settings.json`: in a container `/app/config/settings.json`, the read-only mount of `./data/projections/<composeName>` (deployment DEPLOY-COMPOSE-025); on the host the projection directory the unit runner points `CONFIG_DIR` at (settings-store STORE-DLV-007) | the unit's projection: JSON `{format: 1, unit, revision, sections, documents}` holding the sections and documents its manifest entry declares and no credential (settings-store STORE-PROJ-001, STORE-PROJ-002); read by `loadConfig`, `loadPersonality`, `loadExpressions` and the logger's bootstrap read | the settings store, before every start the control plane issues and on every unit-runner start (settings-store STORE-PROJ-003); never by a service |
| `.env` | `COHOST_ENV_FILE`, else `.env` at the workspace root, else the parent of `configDir()` (CFG-ENV-010) | bootstrap values only, no credential; loaded by `loadDotEnv` | the owner, from `.env.example` (copied by `install.sh`, not by code) |
| per-service data | `dataDir()`: `COHOST_DATA_DIR`, else `data` under the workspace root (CFG-DIR-006, CFG-DIR-007); each service writes only under `<dataDir()>/<service>/`, its log file apart (next row), such as voice's fallback clip store, mouth's clip cache, chat's encrypted Twitch token, avatar's encrypted VTube Studio token and the dashboard's uploaded avatar models | generated files a service keeps across restarts; not edited by hand and ignored by version control (`data/` in `.gitignore`) | the service itself: services create what they need |
| log files | `<dataDir()>/logs/<program>.log` and its rotated `<program>.<n>.log` (CFG-LOG-012, CFG-LOG-015) | every entry a program logs, as pino JSON lines; written by the logger of every program except `tools` (CFG-LOG-022), from containers through the `./data/logs` bind mount (deployment DEPLOY-COMPOSE-029); read by people and their tools, never by cohost | the first program that logs creates them |

The settings store (`<dataDir()>/store/cohost.db`), its backups, the projections directory as a whole and the master key file are the settings store's ([settings-store](../settings-store/settings-store-design.md)); nothing in this package reads, writes or names them (CFG-SEC-021). The committed `config/config.example.yaml`, `config/personality.example.md` and `config/expressions.example.yaml` are the seed the store imports when it is created (settings-store STORE-IO-005); no program copies them into a file of the owner's, and nothing in this package reads them outside its tests.

Resolution (`paths.ts`):

- `findWorkspaceRoot(start = cwd)` walks parent directories until one contains `pnpm-workspace.yaml`, returning `undefined` at the filesystem root. It exists because a host-run service runs with its package directory as cwd.
- `configDir()` = `resolve(CONFIG_DIR ?? join(findWorkspaceRoot() ?? cwd, "config"))` (CFG-DIR-001, CFG-DIR-002). It is the directory that holds the unit's projection: Compose sets `CONFIG_DIR=/app/config`, where the projection is mounted, and the unit runner sets `CONFIG_DIR` to the host projection directory it has just written. A program started without either finds no `settings.json` under `<root>/config` (which holds only the committed examples) and fails naming the file and the programs that write it (CFG-LOAD-007).
- `dataDir()` = `resolve(COHOST_DATA_DIR ?? join(findWorkspaceRoot() ?? cwd, "data"))`, the same resolution as `configDir()` (CFG-DIR-006, CFG-DIR-007). Each service keeps its own files under `<dataDir()>/<service>/` and never reads another service's subdirectory: voice's fallback clip store is `voice/fallback-clips`, mouth's clip cache `mouth/fallback-clips`, the dashboard's uploaded VRM models `dashboard/avatar-models` (the dashboard is a host process, so its `dataDir()` is the checkout's `data/` or `COHOST_DATA_DIR`; no container reads or mounts it). Services exchange those files over HTTP (HLD tenet 1). In a container the workspace root is `/app`, so the default is the container's own `/app/data`, with no volume except the mounts deployment names for a service that keeps files across a recreate (chat's `./data/chat`, avatar's `./data/avatar`). The path is a per-machine value, so it is an environment variable and not a setting (HLD tenet 7).
- `dotEnvPath()` is `COHOST_ENV_FILE` when set, else `.env` at the workspace root (`findWorkspaceRoot()`), else the parent of `configDir()` when there is no workspace root (CFG-ENV-010). A `CONFIG_DIR` elsewhere, the projection directory included, does not move where `.env` is looked for. In a container the workspace root is `/app`, so the path is `/app/.env`, which does not exist (it is `.dockerignore`d, `.dockerignore`) and does not matter because Compose injects `.env` through `env_file`. A missing `.env` is not an error: every variable it may hold has a default.

Personality and expressions are documents of the store, not keys of `ConfigSchema`, and a unit receives one in its projection only when its manifest entry's `documents` list names it (module-contract MOD-MAN-016). `loadPersonality()` returns the projection's `personality` text and `loadExpressions()` its `expressions` object, each re-reading `settings.json` on every call (uncached by design: a service that wants a fresh copy asks again, as cortex does on `control reload_personality`, after the dashboard has rewritten the personality projections, settings-store STORE-PROJ-006). `loadPersonality()` throws naming the unit when the projection holds no `personality` document (CFG-USR-001). `loadExpressions()` parses the document with `ExpressionMapSchema`, treats an absent document as `{}`, and reports a schema failure as `Invalid <file>:` followed by `  path: message` lines, the shape `loadConfig` produces (CFG-USR-002). A value in the `browser` block longer than 64 characters fails validation, because the browser driver's frames carry it and a longer one would make every frame invalid ([event-bus](../event-bus/event-bus-design.md) Avatar frames); the store runs the same schema on every write of the document, so a stored map always passes. No service writes either document: the dashboard saves the personality to the store, and the reflection pass writes its new text to an outbox the unit runner applies (settings-store STORE-OUT-001). The consumers are cortex (loads at start, reloads on `control reload_personality`, `services/cortex/src/cortex.ts`), memory reflection (`services/memory/src/reflect.ts`, which reads it to extend it) and avatar (expressions, `services/avatar/src/boot.ts`); the dashboard reads and writes the personality through the store.

## Loading pipeline

`loadConfig(force = false)` (`index.ts`):

1. Return the module-level cached `Config` unless `force` (`index.ts`; CFG-LOAD-001, CFG-LOAD-008). There is no file watching: configuration is read once per process; only the personality has a reload path.
2. `loadDotEnv()` (`paths.ts`), from `dotEnvPath()` (CFG-ENV-004). Parses `KEY=value` lines (it never sets `COHOST_ISOLATION`, CFG-ISO-008): trims each line, skips blank and `#` whole-line comments, requires `=` at index 1 or later, trims key and value, strips one layer of matching single or double quotes, and sets `process.env[key]` only when it is `undefined` (CFG-ENV-005). Comments follow Compose's `env_file` rules (CFG-ENV-006): an unquoted value loses a whitespace-then-`#` suffix (`KEY= # note` is empty), a quoted value may be followed by a comment and keeps any `#` inside the quotes, and a `#` with no preceding whitespace (`a#b`) is part of the value.
3. Read the projection: `<configDir>/settings.json`, parsed as JSON. A missing file, a file that is not JSON, or an object whose `format` is not 1 fails the load with an error naming the file and saying that the unit is started through the dashboard, `cohostctl` or the unit runner, which write it (CFG-LOAD-007); the loader never creates or repairs it. The projection's `unit` names the unit in every later message.
4. `coerceEmptyNumbers` drops every `null`-valued key at any depth (`pipeline.ts`; the name says numbers but the filter is type-blind; `null` array elements are kept) so schema defaults apply: a key held as `null` is the same as a key left out (CFG-LOAD-002).
5. Isolation overrides (`pipeline.ts`): when `COHOST_ISOLATION` is set and non-empty, the loader parses it as a JSON object from override name to string and sets each entry at the key path `ISOLATION_OVERRIDES` gives that name, over the stored values and before validation, so the override wins; a value is parsed as a YAML flow value for the boolean keys, `chat.sources` and `ears.sources` and kept as a string for the rest, and the section it lands in is validated again (CFG-ISO-007). A malformed object or an unknown name fails the load naming `COHOST_ISOLATION` (CFG-ISO-010). No other environment variable is consulted.
6. Validate each section the projection holds with that section's own schema, taken from `ConfigSchema`'s shape by section path (CFG-LOAD-001). Only the declared sections are present, so a section the unit does not read is neither required nor validated; the store has already validated the whole configuration on the write that produced these sections (settings-store STORE-SET-002), so a failure here means a stored section fails the schema of the running code, after a code update changed what a key may hold. On failure `loadConfig` throws a `ConfigError` whose message is `Invalid <file>:` followed by one `  path: message` line per issue (CFG-LOAD-003, CFG-RCV-001). The isolation overrides are already in place, so an override passes the same defaults and enum checks as a stored value; a refinement across sections is checked only where the unit holds every section it reads, since the store validated the whole configuration on write.
7. Credentials (`pipeline.ts`): the shared runtime has already read the unit's credentials message before the load, from `/run/cohost/credentials.json` in a container or the pipe `COHOST_CREDENTIALS_FD` names on the host (settings-store STORE-DLV-004), and hands the loader the credentials it holds in memory. The loader sets each non-empty string at its secret path into the validated configuration, after validation and never before (CFG-SEC-002), as Credentials below states.
8. `unknownKeys(raw, parsed)` recursively lists dotted paths present in the projection's sections but missing from the parsed ones; non-empty results are reported by one warning through the config logger that names only the ignored keys, and loading continues (CFG-LOAD-005). The walk descends into array entries and reports them as `path[index].key`, so a typo inside a reflex shows up as `brain.salience.reflexes[0].cooldwn_ms` (CFG-LOAD-006). A stored section can hold an unknown key when a code update removed it; the settings editor lists it for removal (module-contract MOD-CFG-006).
9. Guard undeclared sections: the returned `Config` throws, on a read of a section the projection does not hold, an error naming the section and the unit (CFG-LOAD-001), so a service that reads a section its manifest entry does not declare fails at the first read instead of running on defaults. The guard covers top-level sections and the seven `brain.*` sections alike.
10. Cache and return.

The validation core is one function, `parseConfig(tree, {credentials, overrides})` (`pipeline.ts`): the placeholder check (every string value holding a `${NAME}` or `${NAME:-default}` placeholder, `NAME` matching `[A-Z0-9_]+`, becomes an issue at that key's dotted path, an array entry as `path[index]`; CFG-ENV-011), null-dropping and the schema. The settings store calls it on the whole assembled configuration with no credentials and no overrides on every write (settings-store STORE-SET-002), so a value it stores is one the loader accepts; the loader calls it per section. No placeholder is ever substituted, and the message says that `${...}` is not supported; there is no escape for a literal dollar-brace before an upper-case name, so prose that needs one is reworded or the name written in lower case, which is literal text.

Programs that own the store (the dashboard, `cohostctl`, the unit runner and the `config:*` tasks) do not read a projection for their own settings: the store assembles the configuration from its rows and validates it with `parseConfig` (settings-store STORE-DB-005).

All diagnostics (the unknown-key warning and the credential warnings) go through a pino logger named `config`, created on first use; `setConfigLogger` swaps it so tests and hosts can capture or redirect them (CFG-LOG-001). Nothing in the package writes to `console`. No diagnostic and no error message carries a credential's value (CFG-SEC-010).

## Credentials

A credential is a value at a secret path. The store holds it encrypted and hands it to a unit in memory; no settings section holds one, so a section can be shown, exported without `--secrets` and projected to a unit with nothing to hide.

- **The paths.** `SECRET_PATHS` lists `llm.openai.api_key`, `llm.claude.api_key`, `llm.bedrock.access_key_id`, `llm.bedrock.secret_access_key`, `vision.obs.password`, `ears.openai.api_key`, `ears.nemotron.api_key`, `ears.kyutai.api_key`, `voice.openai.api_key`, `voice.pocket.hf_token`, `chat.twitch.client_id`, `chat.twitch.client_secret`, `chat.twitch.access_token`, `chat.twitch.refresh_token`, `chat.youtube.api_key`, `connections.discord.token` and `tools.servers.*.token` (CFG-SEC-003). Each is a key of `ConfigSchema` defaulting to `""` (CFG-SCH-039), so a service that has no credential reads the empty string and reports the gap. An engine's key is a credential like every other, and the engine's URL is not (it is a `sensitive` setting, below).
- **The wildcard.** A path of the list may hold one `*` segment, which matches exactly one key of the map the settings hold at that place (CFG-SEC-016): `tools.servers.*.token` is the `token` of each entry of the stored `tools.servers`, so the credential of a server the owner adds from the dashboard is a secret path with no change to the list. The store refuses to set a token for a server the stored `tools` section does not hold and deletes a removed server's token in the same write (settings-store STORE-SET-005, STORE-SET-006).
- **The derived listener key.** Besides the secret paths, the loader sets `ears.http.verifier` from the delivery (CFG-SEC-020): the ears audio listener's key, derived from the control token when the owner sets it (control-plane CTRL-RUNTIME-017) and stored by the store as `keys.ears-listener`. It is a string of 64 lowercase hex digits; any other value is dropped with one warning naming the path, never the value, and does not fail the load, so the listener then has no key (ears EARS-SRC-013). It is not a secret path: the dashboard's secret write refuses it, no read route reports it, and only the `ears` unit's message carries it.
- **Delivery.** The control plane builds each unit's message from the paths its manifest entry's `secrets` list declares ([module-contract](../module-contract/module-contract-design.md)), the wildcard expanded to the servers the stored `tools` section holds, and hands it to the started process: into a container's `tmpfs` through `docker exec` from standard input, or to a host-run process on an inherited pipe (settings-store STORE-DLV-001 to STORE-DLV-007). The shared runtime reads it before the load, refuses a message holding a path its unit does not declare, and keeps the values in memory. A service process therefore holds only its own credentials (HLD Trust boundary). No Compose `environment:` entry carries an operator credential; the fixed credential of the local-only Postgres service is the one exception (deployment DEPLOY-COMPOSE-025).
- **Merge.** The loader sets each non-empty delivered value at its secret path after the projection's sections have validated, not before: setting first would let a credential create a parent object (a whole `llm.bedrock` section, say) or a `tools.servers` entry the settings do not hold, and validation would then pass for the wrong reason (CFG-SEC-002). A token for a server the projection's `tools` section does not hold is not set and gets one warning naming the path, never the value (CFG-SEC-017). The delivery is the one source of a credential; the stored values are trimmed and checked when written (settings-store STORE-SET-005), so the loader uses each as delivered.
- **What this package does not do.** Nothing in `@cohost/config` reads, writes or names a credentials file, the settings store or the master key file (CFG-SEC-021); the loader receives credentials only from the shared runtime. Writing a credential is the store's one write (settings-store STORE-SET-001), reached through the dashboard's gated, write-only secret route ([dashboard](../dashboard/dashboard-design.md)) or `mise run config:secret`, never through `PUT /config/:section`, whose write refuses a key at a secret path (module-contract MOD-CFG-009). Nothing exported by this package returns a credential's value other than the loaded `Config`; the settings editor reports a credential only as set or not set, from the store at request time (module-contract MOD-CFG-005).
- **Credentials a service obtains at run time.** The refreshed Twitch token chat persists and the VTube Studio token avatar receives are not secret paths and never reach the store: each service keeps its token in a file under its own data directory, encrypted under the per-unit state key its message carries (`<dataDir()>/chat/`, chat CHAT-TW-011; `<dataDir()>/avatar/vts-token.enc`, avatar AVATAR-VTS-003; settings-store STORE-STATE-002).

## Structured errors

The dashboard's config recovery mode ([dashboard](../dashboard/dashboard-design.md) Config recovery mode) and the settings editor need validation failures as data. They come from the one pipeline, so the loader, the store's write and the recovery screen can never disagree about what fails.

- **`ConfigError`** (`errors.ts`). A failure of a projection's section (CFG-LOAD-003), and a store write refused for an issue of the settings (settings-store STORE-SET-002, a placeholder of CFG-ENV-011 included), is a `ConfigError`: an `Error` whose message is exactly the text those requirements give and whose `problems` lists each issue as `{path, message}` (CFG-RCV-001). `path` is dotted with each list index written `[i]` (`brain.salience.reflexes[0].match`). Callers read `problems` and never parse the message. Failures that are not about the settings' content (a missing or unreadable `settings.json`, CFG-LOAD-007; a malformed `COHOST_ISOLATION`, CFG-ISO-010) stay plain errors.
- **Recovery.** The list of problems that stop the store's use is the store's `checkStore()` (settings-store STORE-RCV-001), which validates the stored settings with `parseConfig` and returns the issues as `ConfigError` problems. A store whose settings fail the current schema is fixed one key at a time by the store's key-alone write, which validates the key it sets against that key's own schema (settings-store STORE-RCV-002); this package supplies the schema and the section list it uses and holds no editing of its own.

## Presentation table

`packages/config/src/presentation.ts` carries, beside the zod schema, everything the Settings screen needs to name and explain a setting, so the page holds no section names and no help text of its own. It is data, not behaviour: it holds no value and no default.

| Level | Field | Meaning |
| --- | --- | --- |
| section | `title` (required) | Plain name, such as "Salience" for `brain.salience` |
| section | `group` (required) | One of `GROUPS`, in order: Identity, Brain, Senses, Voice and body, System |
| section | `about` (required) | One sentence saying what the section affects |
| section | `page` (optional) | Another section whose screen shows this one (`brain.working_memory_events` is shown on `brain.memory`, `renderer` on `avatar`) |
| section | `live` (optional, `true`) | The dashboard applies a saved change to this section at once, with no restart, so the page header says so instead of naming a restart (`renderer`) |
| key | `help` (required, every key) | One sentence of help |
| key | `label` (optional) | Display name when the key name is not plain |
| key | `unit` (optional) | `ms`, `bytes`, `days`, `hours`, `dB`, `chars`, `words`, `fps` and the like |
| key | `sensitive` (optional, `true`) | The key decides where a secret-bearing or private request goes, or who may reach the dashboard's network listeners; the settings screen shows a warning beside it. It is a hint only: a save that changes it is gated like every other save, by the control token or the session cookie (CFG-PRES-010) |
| key | `widget` (optional) | A hint from a closed set: `timezone`; `model` with a kind `chat`, `small`, `vision`, `embed` or `stt`; `voice`; `sources`; `textarea` (a multi-line string); `options` with labelled `value`/`label` pairs; `slider` (a numeric key rendered as a slider whatever the span of its range, `renderer.turn`, and moved by the `step` the hint carries when it has one: `renderer.zoom` 0.05, `renderer.offset_y` 0.01, `renderer.turn` 1); `mcp-servers` (the map `tools.servers`) and `tool-list` (the map `tools.allow`), the two purpose-built controls of the Tools settings ([dashboard](../dashboard/dashboard-design.md) The Tools settings); `avatar-model` (the key `renderer.model`), the model list with its upload and live preview ([dashboard](../dashboard/dashboard-design.md) Avatar settings) |

A section is a declared section path: every top-level key of `ConfigSchema` except `brain`, plus `brain.working_memory_events`, `brain.working_memory_own_lines`, `brain.input_limits`, `brain.salience`, `brain.affect`, `brain.memory` and `brain.cortex` (the sections the manifest's `config` lists cover, MOD-MAN-008, plus the two the dashboard alone reads and no unit declares, `dashboard` and `renderer`). A key is a leaf of a section: a scalar or an array, named by its dotted path from the config root (`brain.salience.reflexes`, `voice.fallback.lines`); an array is one key.

The table is checked at build time (CFG-PRES-007): a key or section without its required fields, an entry for a key or section the schema does not have, a `page` that names no section, a widget outside the closed set or a `model` widget on a key that is not a string fails a test, so a new setting cannot ship unexplained. The widget assignments are fixed by CFG-PRES-006: `cohost.timezone` is a `timezone`; every model-name key is a `model` (`llm.model` and the consolidator's model `chat`, `llm.embed_model` `embed`, `vision.model` `vision`, `ears.stt_model` `stt`, the other hooks' models `small`); `voice.voice` is a `voice`; `vision.prompt` is a `textarea`; `chat.sources`, `ears.sources`, `ears.echo_suppress_sources` and `brain.salience.barge_in_sources` are `sources`; `voice.lang_code` is `options` with a plain language name for each of its nine codes. A key's `help` is also its JSON Schema `description`, generated from the table, so the schema has one source for help (CFG-PRES-008). The `sensitive` keys are exactly the keys that decide where a request carrying a credential or the co-host's private context goes, or who may reach the dashboard's network listeners (CFG-PRES-011): `dashboard.allowed_hosts` and `network.lan` (what the egress marks treat as the LAN); `llm.provider` and `llm.openai.base_url` (where the conversation and the OpenAI-compatible API key go), `vision.obs.host` and `vision.obs.port` (the OBS password), `avatar.vtube_studio.host` and `avatar.vtube_studio.port` (the saved VTube Studio token), `mouth.outputs.http.url` (the co-host's voice audio); `tools.servers` (where the co-host's tool requests and each server's token go) and `tools.allow` (which tools may be called and which may act); the `url` of each of the five hooks (`brain.salience.module`, `brain.affect.module`, `brain.cortex.critic`, `brain.memory.notes.capture`, `brain.memory.notes.consolidator`), which receive the conversation and viewer notes; and the speech and vision engines' destinations: `vision.provider` (which provider receives the screen frames, with a credential it may already hold), `voice.engine`, `voice.openai.base_url` and `voice.pocket.url` (where the text of every spoken line goes), `ears.stt_engine`, `ears.stt_fallback_engine`, `ears.openai.base_url`, `ears.nemotron.url` and `ears.kyutai.url` (where the audio of every utterance goes). `voice.pocket.hf_token` is a secret, so it is written through the secret route and never appears here. An engine selector is sensitive as well as its URL, because choosing an engine whose URL is already stored redirects what that URL receives. Keys that choose a vendor's own endpoint (`llm.bedrock.region`, the Twitch and Discord ids, `chat.youtube.video`, which names a broadcast and not a host) or a local listening address (`ears.http.host`) are not sensitive: nothing a secret travels to changes with them.

## Egress destinations

`egressDestinations(config)` (`packages/config/src/egress.ts`) is a pure function from a loaded config to the places private data is configured to go, one entry per destination: `{ service, data, engine, host, hosted, offLan }`. `data` is `text` (voice: the text of each spoken line and fallback phrase; cortex: the conversation sent to the chat model; tools: the arguments of a tool call, which the model wrote from the conversation), `audio` (ears: each utterance) or `frames` (eyes: each screenshot, from the look loop and from an injected image). `host` is the host name or address of the server the entry names, without a port, or absent; `hosted` names a provider that is hosted by nature, or is absent.

| Entry | Host | Notes |
| --- | --- | --- |
| voice, engine `kokoro` | the `urls.tts()` host | |
| voice, `openai`, `pocket` | the host of `voice.openai.base_url`, `voice.pocket.url` | no entry while the value is blank |
| ears, selected engine and, where the selected engine is `nemotron` or `kyutai`, `ears.stt_fallback_engine` | `speaches`: the `urls.stt()` host; `openai`, `nemotron`, `kyutai`: the host of their URL key | one entry per engine that can receive audio; the fallback only where it is used and is not `none` |
| eyes, provider `ollama` | the `urls.ollama()` host | present whenever the provider is not `stub`, whether or not `vision.enabled` (the describer also serves injected images) |
| eyes, provider `openai` | the host of `llm.openai.base_url`, which defaults to `https://api.openai.com/v1`, so choosing `openai` with the default is the explicit hosted choice and is flagged | |
| eyes, providers `anthropic`, `bedrock` | none; `hosted` is the provider name and `offLan` is true | a provider name is never read as a host name |

A `stub` engine, the `mock` chat provider and a blank value have no entry. The voice, ears, eyes and tools services log one warning at start for each of their entries with `offLan` true and name engine and host (or `hosted` provider) in their heartbeat detail; the dashboard shows the whole list ([dashboard](../dashboard/dashboard-design.md) Egress note). The list is computed from the stored settings, so after an edit it describes what the services will do at their next restart. A change to `network.lan` is applied by restarting voice, ears, eyes and tools, which log the warnings.

**The off-LAN rule.** `offLan` is true for a `hosted` provider and otherwise comes from one rule, shared by every consumer, which judges a host by its form and never resolves a name, so the services and the dashboard, which read the same configuration, agree:

- On the LAN: an IPv4 loopback, private or link-local address (127/8, 10/8, 172.16/12, 192.168/16, 169.254/16); the IPv6 loopback `::1`, unique-local addresses (fc00::/7) and link-local addresses (fe80::/10); an IPv4-mapped IPv6 address (`::ffff:a.b.c.d`), judged as the IPv4 address it carries; `localhost`; `host.docker.internal`; a host name (not an IP literal) with no dot (a Compose service name such as `tts`, `tts-pocket` or `stt-kyutai`); a name ending `.local`. The brackets of an IPv6 literal in a URL are removed before the host is judged.
- Also on the LAN: any host, suffix or address range the owner lists in `network.lan`, for a tunnel or overlay network (a Tailscale address range, a name inside a VPN). A host entry matches the name exactly, a suffix entry (one starting with a dot) matches names ending in it, a range entry matches addresses inside it.
- Off the LAN: every other host, including a public name that resolves to a LAN address, which the rule cannot see. The owner who runs such a name lists it in `network.lan`.

## Models to pull

`ollamaModels(config)` (`models.ts`) answers "which local models does this config need?" for the `models` container, so the model names live only in the settings (CFG-MODEL-001). `required` holds `llm.model` while `llm.provider` is `ollama`, `llm.embed_model` while `brain.memory.embedder` is `ollama`, and `vision.model` while it is non-empty and `vision.provider` is `ollama`; `optional` holds the model of every hook (`brain.salience.module`, `brain.affect.module`, `brain.cortex.critic`, `brain.memory.notes.capture`, `brain.memory.notes.consolidator`) whose `kind` is `llm` and whose provider, its own or the inherited `llm.provider`, is `ollama`, an unset hook model meaning `llm.model`; each list is duplicate-free and `optional` leaves out names already required. A failed pull of a required model fails the container; a failed pull of an optional one is a warning (deployment DEPLOY-COMPOSE-008, DEPLOY-COMPOSE-011). `pull-models.ts` is the container's entry point: it calls `loadConfig` over the `models` projection, which holds exactly the sections `ollamaModels` reads (settings-store STORE-PROJ-005), so an invalid section fails with the loader's own message naming the keys.

Spoken fallback line keys: `voice.fallback.lines` is the list of lines the co-host says when a line fails to play (CFG-SCH-017), `mouth.fallback.min_interval_ms` the minimum time between two fallback lines on one output (CFG-SCH-018; owner decision, default 20000), and `brain.cortex.fallback_ack_chance` the base chance stated to the model after a fallback (CFG-SCH-019; owner decision, default 0.25). The example carries a key only when the schema defines it, because the example must load with no unknown-key warning (CFG-USR-003). The `tools` section ([tools](../tools/tools-design.md)) is optional and every key is defaulted, so a config with no `tools` section runs with no tool enabled. The shipped example carries it with nothing configured and the starter filler lines for the owner to edit:

A `tools.servers` entry is written by the dashboard or with `mise run config:set` (`weather: {url: "http://host.docker.internal:8931/mcp"}`), and its token only as a credential, `tools.servers.weather.token`, on the dashboard's Settings screen or with `mise run config:secret`; a credential does not belong in the URL. The `url` of a server is an `http(s)` URL; a name outside the grammar, a missing `url` or an `allow` entry that sets `acts` and `chat` together fails validation naming the key. A `tools.allow` entry whose tool no server lists is kept and ignored; the dashboard shows it as unknown.

`ModuleSchema` (`schema.ts`) is the shared hook config for the three region hooks and the two memory notes hooks: `kind` (blank to `rules`; `rules|llm|http`), `url` (default `""`), `timeout_ms` 8000, and `llm{provider?, model?}` where both blank values mean "inherit" and a provider without a model is rejected via `superRefine` (`schema.ts`). The override provider enum is `ollama|openai|anthropic|bedrock`: `mock` cannot be named on a hook, though a hook that inherits reaches the mock provider when `llm.provider` is `mock` (CFG-SCH-009). The whole object `.default({})`s. Hook behaviour itself belongs to region-hooks.

Required-ness is uneven: `brain.*` regions and `llm.openai/claude/bedrock` default to `{}`, but the nine top-level sections themselves, plus `vision.obs`, `avatar.vtube_studio` and `avatar.vmc` are required objects with no default (`chat.twitch` and `chat.youtube` are optional objects whose every key is defaulted), and the avatar hosts default to `host.docker.internal` and the two avatar ports to 8001 and 39539 (CFG-SCH-001, CFG-SCH-010, CFG-SCH-037, CFG-ISO-005). A blank `vision.model` while `vision.enabled` is true is a configuration gap eyes reports, not a refinement that fails the load (CFG-SCH-025); the same holds for every blank URL, model, voice or key of a selected engine or provider, which its service reports as a down dependency. A usable config therefore needs every section present (an empty `{}` suffices for `brain`, `voice`, `dashboard`), which the example provides.

Blank handling is uniform. An enum key wraps `z.enum` in `z.preprocess((v) => v || default, ...)` (`avatar.driver` blank means `null`; a non-empty unknown value still fails, CFG-ISO-005; `llm.claude.effort` blank means `low`), and a plain string key that has a default wraps `z.string().default(d)` in a preprocess that maps `""` to `undefined` (`cohost.timezone`, `llm.openai.base_url`, `vision.obs.host`, `vision.obs.source`, the two `plugin_*` keys and `ears.stt_model`, CFG-SCH-024), so a key written as an empty string, or an override whose value is empty, lands on the default instead of an empty string. `voice.pocket.url`, `ears.nemotron.url` and `ears.kyutai.url` are the exception: a blank value stays blank and is a configuration gap, only an absent key taking the Compose-service default. `voice.voice` is blank-to-the-engine's-default in the same way, the default depending on `voice.engine`, and an error for the `openai` engine, which has none. Keys with no default and a non-empty requirement (`cohost.name`, `cohost.streamer`, `llm.model`, `llm.embed_model`) still fail validation when blank, and secrets keep `""` as their default.

The dashboard's settings editor ([module-contract](../module-contract/module-contract-design.md), MOD-CFG-*) reads and writes the settings store, using what `packages/config/src/editor.ts` exports: `sectionJsonSchema(path)` generates JSON Schema from the zod schema (objects, strings, numbers with their int and range checks, booleans, enums, arrays, defaults, descriptions; a small walker over zod 4's schema classes that reads each wrapper's inner type and each check's definition, so no JSON-Schema dependency is added); `SECRET_PATHS` marks the secret keys (CFG-SEC-003), which the schema output carries as `"x-secret": true` and `sectionSecrets` lists per section; `presentation.ts` supplies each section's and key's name and help to the schema route (MOD-CFG-019 to MOD-CFG-021); `readSection(stored, section, credentialsSet, running)` takes the section's stored document and returns each key's source (`literal` when the document holds it, `default` when it does not), editability, effective value and raw text (the stored value written as YAML; a secret only as set or not set, from the set of credential paths the store holds), the override name and the running units that override a key of `ISOLATION_OVERRIDES` (`isolation.overriddenBy`), and the section's unknown keys (found by walking the document against the schema, so a section that fails validation still reports them) (module-contract MOD-CFG-004 to MOD-CFG-006). An edit is applied by the store: it sets each named key in the section's document, removes each key the request names in `remove`, validates the whole assembled configuration with `parseConfig` and commits in one transaction against the revision the editor read (settings-store STORE-SET-002, STORE-SET-003). Configuration is read once per process (HLD tenet 10), with the one exception the renderer section states.

## Environment variables

Three tiers, none of which is validated by `ConfigSchema`. An environment variable is never an operator setting (CFG-ENV-012), and the one that carries overrides is written only by the control plane.

**Isolation overrides** (`COHOST_ISOLATION`, CFG-ISO-006, CFG-ISO-007). The control plane sets this one variable, a JSON object from override name to value, on the `docker compose` process for an isolated start of one unit (and sets it empty for every other start); Compose passes the one name to the container (deployment DEPLOY-COMPOSE-017), and the loader applies each entry by key path after reading the projection and setting the delivered credentials. The override names below are labels in that object, not environment variables: a variable named `AVATAR_DRIVER` or `LLM_PROVIDER` in `.env` or the shell is read by nothing, and `loadDotEnv` never sets `COHOST_ISOLATION` (CFG-ISO-008), so only the control plane's channel can carry an override. The overrides are start-time, per-container, not settings: `.env.example` lists none, no guide tells the operator to set one, and the settings editor reports a key a running unit has overridden (MOD-CFG-018) instead of presenting a permanent shadow. A variable named like a setting (for example `TWITCH_CHANNEL`) is not read from `.env`, and nothing warns when `.env` defines one; a store write that holds a `${VAR}` placeholder is refused (CFG-ENV-011).

## Logging

Every cohost TypeScript program logs through `createLogger(service)`: the services through `runService` (shared-runtime SHARED-BOOT), the dashboard (a `runService` program run on the host), and the one-shots `consolidate`, `reembed` and `reflect`, which create their logger before they load the configuration (memory MEM-START-007). Each entry goes to two outputs: a terminal line a person reads, and a JSON line in a file that keeps every field. `cohostctl` and `pull-models` print plain text of their own and are not loggers. Outside the scheme altogether are the Rust programs and native code: the desktop audio helper prints its own lines, and the bus addon, like Node itself, writes to standard error directly. Raw standard error (Node's own warnings, a native addon's panic, the desktop helper's `eprintln!`) reaches the terminal or `docker compose logs` as written and never the log file.

**Settings and the bootstrap read.** The `logging` section (CFG-SCH-113, CFG-SCH-114) holds the level, the terminal format and the file's on switch and rotation limits. The logger exists before `loadConfig` runs, because `runService` creates it first so that a failed load can be logged, and the loader's own diagnostics go through it (CFG-LOG-001). So the first `createLogger` call of a process reads the `logging` section itself (CFG-LOG-002). The read runs once per process, at the first `createLogger` call or the first config-logger write, whichever comes first, and its result is reused. It first calls `loadDotEnv()`, the loader's own idempotent `.env` step that never overrides a variable the process already has, so `CONFIG_DIR` and `COHOST_DATA_DIR` set in `.env` locate the files exactly as `loadConfig` will (with `COHOST_DATA_DIR` set in `.env`, the host-run programs log to `$COHOST_DATA_DIR/logs` while the containers still log to the workspace's `data/logs/`, because the Compose bind mount is relative to the project directory). It then takes the `logging` section from one of two sources:

- **A registered logging source.** A program that owns the settings store (the dashboard, `cohostctl`, the unit runner and the `config:*` tasks, settings-store STORE-PKG-001) has no projection of its own, so before its first `createLogger` call it registers, with `setLoggingSource(fn)`, a function that returns the store's stored `logging` section. This package never opens the store (CFG-SEC-021); the store-owning program supplies the read.
- **The projection.** With no source registered, the read parses `settings.json` in the config directory and takes the `logging` section of its `sections`. Every application unit declares `logging` (module-contract MOD-MAN-002), so every projection holds it.

It validates that one section with the section's own schema, merges no credential and applies no isolation override: the section holds no secret path and no override. When the source holds no `logging` section, the file is missing or not JSON, or the section is invalid, the read takes the schema defaults and reports nothing (CFG-LOG-003), because `loadConfig` or the store runs moments later over the same settings and reports the same fault with its full message. No environment variable decides a logging setting (CFG-LOG-004).

**One sink per process.** The first `createLogger(service)` call builds the process's sink, which owns standard output and the file `<dataDir()>/logs/<service>.log`; later `createLogger` calls share it and keep their own `name` in every entry (CFG-LOG-017). The file is therefore per program: `dashboard.log`, `chat.log`, `consolidate.log`. The config logger (CFG-LOG-001) is not a `createLogger(service)` call and never names the sink: it looks up the process's sink at each write, so a warning the loader emits after the program's logger exists lands in the program's file, and one emitted before any sink exists (a program that calls `loadConfig` without logging of its own, such as `pull-models`) prints to standard output only, under the bootstrap read's settings, and opens no file (CFG-LOG-018, CFG-LOG-019). `createLogger(service, { file: false })` builds a sink with no file (CFG-LOG-022); `tools` uses it (tools TOOL-SVC-012), because its container mounts no part of `./data` (deployment DEPLOY-COMPOSE-026).

**Crashes.** The sink installs a `process.on("uncaughtExceptionMonitor")` listener that logs the error at `fatal` with `err` before Node's default handling prints it and ends the process with status 1 (CFG-LOG-023). Since Node turns an unhandled rejection into an uncaught exception by default, the same listener covers both. The write is synchronous, so the crash is in the file. A program's own `fatal` paths (`runService` and the one-shots) are unchanged.

**Terminal, `pretty`** (the default; CFG-LOG-005 to CFG-LOG-010). One line per entry:

```
14:03:22.517 ERROR cortex: Invalid /app/config/settings.json:
      llm.model: String must contain at least 1 character(s)
      brain.cortex.max_clauses: Number must be less than or equal to 16
14:03:22.519 INFO  chat: joined channel channel=cocostream attempt=2
14:03:23.004 WARN  cortex: model call failed
    err:
      Error: connect ECONNREFUSED 127.0.0.1:11434
          at TCPConnectWrap.afterConnect (node:net:1611:16)
      {"code":"ECONNREFUSED"}
```

Time is the process's local time to the millisecond, with no date: the file keeps the full epoch timestamp, and a container's local zone is UTC unless its image sets another. The level name is padded to five characters so messages line up. The name is the logger's: the program's name, or `config` for the loader's diagnostics. A multi-line message prints as real lines, each indented by four spaces on top of whatever indentation the line already has (CFG-LOG-006): the loader's issue list (CFG-LOAD-003) indents each issue by two, so its issues sit six spaces in. A blank line of a message prints as an empty line, with no trailing spaces. Scalar fields follow the message on the first line as `key=value`, quoted as JSON only when the bare form would be ambiguous; objects, arrays and errors print below as indented JSON or as the stack. `time`, `level`, `name`, `msg`, `pid` and `hostname` are left out of the terminal line, since the layout already shows the first four and the last two are noise on one machine; the file keeps them.

Colour marks the level name only, and only when standard output is a TTY and `NO_COLOR` is unset or empty (CFG-LOG-009). Under Compose and under `mise run dev` the output is a pipe, so it carries no escape sequence, and `docker compose logs`, a redirected file and mise's per-task prefix stay plain text. Under `mise run dev` a line reads `[dev:chat] 14:03:22.519 INFO  chat: ...`, and the continuation lines carry the same prefix followed by their indentation, so the prefix does not break the layout. `docker compose logs` adds its own `chat-1  | ` prefix the same way.

Logged text can come from outside: a viewer's chat message, a tool result, a model's reply. The pretty form escapes every C0 and C1 control character and `DEL`, except the line feeds it lays out and the tab, and the bidirectional overrides and isolates U+202A to U+202E and U+2066 to U+2069 (CFG-LOG-010), so no logged text can drive the terminal or reorder what a line shows. The JSON forms are pino's: it escapes C0 controls, but `DEL`, the C1 controls and the bidirectional characters pass through as raw characters, so a JSON line shown raw in a terminal (`cat data/logs/chat.log`) is not neutralised; a JSON tool reading the file is the intended reader.

**Terminal, `json`** (CFG-LOG-011) prints pino's own line, for an owner who pipes the output into a JSON tool or a log shipper.

**File** (CFG-LOG-012 to CFG-LOG-016, CFG-LOG-020, CFG-LOG-021). The file receives pino's own JSON line for every entry at or above the level, whatever the terminal format, so it holds every field: the epoch time, the numeric level, `pid`, `hostname` and any field a caller attached. The logger creates the `logs` directory with mode 0755 and the files with mode 0644, never 0600: they are the owner's to read with any tool, and a file created by a root container stays readable from the host. Writes are synchronous and happen before the logging call returns (CFG-LOG-013), so the line a program logs just before `process.exit(1)` is in the file.

Before each entry the logger stats the file's path (CFG-LOG-014): the stat's size decides rotation, and a path that is gone or names another file than the open descriptor (deleted or replaced by hand) makes the logger open `<program>.log` afresh. One stat per entry costs nothing at cohost's log volume, and it handles a hand-deleted, truncated or replaced file at the very next entry, where tracking the size from the bytes written would keep writing into a deleted file until the tracked size reached the limit. Rotation is by size: when the file is non-empty and the next entry would push it past `max_size_mb`, the files shift up one number (`.log` to `.1.log`, `.1.log` to `.2.log`), the one past `max_files` is deleted, and a new `<program>.log` starts (CFG-LOG-015, CFG-LOG-016); an empty file never rotates, so an entry larger than the limit is written whole into the fresh file. A program's logs therefore never take more than `(max_files + 1) × max_size_mb` MiB plus one entry, 40 MiB with the defaults. A restart appends to the existing file. One writer per file is assumed: running the same program on the host and in a container at once is not a supported setup (the two would also share a consumer group), and two writers would race on rotation.

Failures never stop a program (CFG-LOG-020, CFG-LOG-021). When the directory cannot be created or a write fails (a full disk, a directory belonging to another user), the entry still prints on the terminal, the logger warns once on the terminal with the path and the error code, and it tries the file again with the next entry; the warning repeats only after a write has succeeded and a new failure begins. A failed rename or delete during rotation warns once the same way and the logger keeps appending to the current file, trying the rotation again at the next entry. The usual cause of a failing directory is ownership: application containers run as root, so a `./data/logs` that Compose creates is root's. The control plane and the installer create the directory as the owner before Compose can (control-plane CTRL-RUNTIME-016, deployment DEPLOY-INST-017), so in practice only a hand-run `docker compose up` on a checkout with no `data/logs` produces a root-owned one; the files containers write are root's in any case, readable by the owner and removable only as root. The troubleshooting page names both.

**Secrets and privacy.** No service logs a secret value (CFG-SEC-010 for the loader, and the same rule everywhere else); as a second line, the sink walks every entry (a pino `formatters.log` hook) and replaces with `[Redacted]` the value of every field, at any depth, whose key is `token`, `authorization`, `password`, `api_key`, `apikey`, `secret` and `cookie`, compared case-insensitively (CFG-LOG-024), so `Authorization` in a request's headers, an `apiKey` option or a whole `cfg.llm.openai` object logged by mistake does not carry its credential into either output. Only those key names are covered: a credential under another name, or inside a string message, is the rule's to keep out. The logs do hold conversation: chat messages, transcripts and the co-host's lines appear in them at `info` and `debug`. Rotation bounds how long they stay (the oldest file is deleted when the count is reached), and a viewer's forget request (memory) removes stored notes and memories, not log lines; an owner who must purge a viewer's text deletes the files under `data/logs/`.

**No transport, no new dependency** (CFG-LOG-025). The pretty formatter and the size rotator are small in-repo modules in `@cohost/config`, used as a pino destination stream in the logging thread: pino serialises the entry, and the sink writes that line to the file and, for `pretty`, parses it and lays it out for the terminal. Neither pino transports nor `pino-pretty` or `pino-roll` are used (Decisions & Alternatives).

**No log view in the dashboard.** The dashboard has no screen that shows service logs; an owner reads them with `docker compose logs <service>` or in `data/logs/`. A Logs screen that reads the files is a separate feature (Open Questions).

## Tests

`packages/config/test/config.test.ts` carries an `@spec` annotation on every test and restores `CONFIG_DIR`, `COHOST_ENV_FILE` and the environment after each one; it writes a `settings.json` projection into a temporary directory it points `CONFIG_DIR` at, points `.env` at its sandbox through `COHOST_ENV_FILE`, passes credentials to the loader as the shared runtime would after reading a delivery, and captures loader warnings through `setConfigLogger`. No test of this package opens a settings store or writes a credentials file. `config-c3.test.ts` covers blank-to-default strings, `vision.model`, `ModuleConfig`, `.env` resolution, logger routing (both bootstrap sources), `loadPersonality` and `loadExpressions`, and `.env.example`; `editor.test.ts` covers the schema export, the secret marks and section reads over stored documents. Like the example-file specs, the shipped-example tests read `config/config.example.yaml`, `.env.example` and `config/expressions.example.yaml` from the repository root on purpose: they are the seed the specs describe, validated with `parseConfig` as the store's import validates them.

Not covered by any test: `urls.database/ollama/tts/stt`.

## Open Questions & Future Decisions

- **Hook provider overrides are not `sensitive`.** `llm.provider` and `llm.openai.base_url` carry the warning, but a hook can name its own `llm.provider` (`brain.salience.module.llm.provider` and the other four), which can send the conversation to a hosted provider. Every save needs the control token either way. Reading A (kept): only the chat model's keys carry the warning. Reading B: mark the five hook provider keys too.
- **Consolidator model follows `llm.model`?** The example writes the consolidator's `llm.model` as the same literal as `llm.model`; editing `llm.model` leaves the consolidator on the old name. A blank hook model would inherit `llm.model`, but the hook also names `provider: ollama` explicitly, and a blank model with a provider is rejected (CFG-SCH-003). Decision wanted: let a hook with a provider and no model inherit `llm.model` when providers match, or keep two literals.
- **`vision.model` pulled while vision is off.** `ollamaModels` pulls a non-empty `vision.model` whatever `vision.enabled` says, so enabling vision later needs no second pull and a fresh install downloads the model it may never use. Decision wanted: gate on `vision.enabled`.
- **A Logs screen.** The dashboard shows no service log; the owner reads `docker compose logs` or `data/logs/`. A screen that tails the files under `data/logs/` would serve the host-run programs and the containers alike, but it is a dashboard feature with its own access question (logs carry chat text and tool arguments, which the open reads of the trust boundary already expose on `/ws`). Decision wanted: whether to add one.
- **The two upload caps.** `dashboard.inject.max_image_bytes` and `vision.upload_max_bytes` are separate keys that must agree for an injected image to pass both; nothing ties them.
