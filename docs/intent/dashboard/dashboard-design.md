# dashboard

Describes the intended design and the code that realizes it. Each row in Decisions & Alternatives cites the evidence for its rationale, or gives the engineering reason the design rests on where no recorded source exists. Specs: [dashboard-specs.md](dashboard-specs.md). See the [high-level design](../../high-level-design.md).

## Context and Design Philosophy

`services/dashboard` is the operator's window onto the stack and the one place a human can push things into it. It is a standalone program the owner starts on the host, outside Docker Compose, before anything else: once it is up, its Launch button brings up the whole Compose stack, and it can stop the stack and restart all or one of its services (Host process and stack control, below; [decision doc](decisions/standalone-dashboard.md)). One Node process serves the dashboard UI, a bundled React application, and a small JSON/HTTP API on `dashboard.port` (default 3000), plus a WebSocket that mirrors the Redis event stream, the service-health stream and the stack's state to the browser. It is also the stack's browser audio sink: the page plays the co-host's voice and reports `voice.playing` / `voice.done` back, so an OBS Browser Source pointed at `/?sink=1` puts the voice on stream without virtual audio cables (`services/dashboard/src/index.ts`). It is also where the avatar renderer lives: the page OBS shows as a Browser Source to draw the owner's VRM model, the owner's model files and the relay that feeds the page the avatar's frames (Avatar renderer, below). It also serves the built docs site at `/cohost/`, the base path the GitHub Pages build uses, so the owner reads the documentation for the checkout they are running, offline, from the address they already have open (Docs site, below).

The dashboard has almost no logic of its own. It publishes `control`, `voice.playing`, `voice.done`, `inject.request` and perception events onto the bus, proxies audio from `voice`, folds heartbeats through `HealthTracker` from `@cohost/control`, delegates start/stop/restart to `ServiceController` and launch/stop-all/restart-all to the stack controller from the same package (owned by the control-plane segment). This segment owns the HTTP surface, the listeners, the gating rule, the stack card, the injection panel and its upload store, the feed, the route that serves the built docs site, the avatar renderer (page, relay, model files and their upload, the settings with a live preview), the secret write and the pick-list routes, the serving of the UI bundle, and the UI app itself (`services/dashboard/ui/`). What the docs site contains, and how it is built, is the docs-site segment's.

Security posture follows the project's trust boundary: the operator's LAN, with a control surface that is host-local by default. The full surface binds to `DASHBOARD_HOST`, else `127.0.0.1`, in both control modes (DASH-CTRL-003). With `CONTROL_ENABLED` unset, every route except the Viewers routes and the secret write is open, and the full surface must stay on loopback: a non-loopback address without control mode fails startup (DASH-HOST-007). With `CONTROL_ENABLED=1` a shared bearer token guards the mutating routes, the stack routes included (`control.ts`, `routes.ts`). The owner, running cohost on a dedicated PC, sets `DASHBOARD_HOST=0.0.0.0` to open the full dashboard from another machine; the token requirements then hold the stack actions and viewer notes behind their secrets, and the dashboard warns that the tokens cross the network in cleartext. Control mode guards mutations only, except that the secret write needs the control token in both modes (Secret write) and so does a config save that changes a sensitive key, one that decides where a credential or the co-host's private context goes (Settings routes). The `/ws` upgrade refuses a foreign `Origin` on both listeners, so a page from another origin cannot read the feed (Listeners). Reads (`/ws`, `GET /personality`, `GET /services`, `GET /stack`, `GET /audio/*`, `GET /options/*`, the UI's files, the docs site under `/cohost/`, the renderer page, its relay socket and the active model file) stay open, and so does `POST /sink`, because the OBS Browser Source that serves as the stream's audio sink cannot present a token. A second listener on all interfaces serves only the ungated routes a sink page or a renderer page needs (Listeners, below). Viewer notes are the exception to the open reads: they never travel on `/ws`, and the Viewers page routes need their own token, `VIEWERS_TOKEN`, in both modes (Viewers page).

The dashboard is the only path by which a browser or other player reaches voice's audio: browsers and OBS fetch `/audio/<id>-<seq>.wav` through the dashboard proxy, the dashboard fetches it from voice's port, which Compose publishes on the host's loopback address only, and in-network sinks such as ears fetch `http://voice:8700` directly.

## Process wiring

`index.ts` (`services/dashboard/src/index.ts`) is one call to the shared bootstrap, `runService({ service: "dashboard", health, main })` (DASH-HTTP-016); the bootstrap loads the configuration, builds the bus and the heartbeat and registers the shutdown hook. `dashboardService` (`service.ts`) supplies `main`, which takes its environment and its `exit` as injectable dependencies so a test can run it without Redis, signals or a process exit. `main` does, in order:

1. Reads the bootstrap's `cfg`, `bus`, `log` and `heartbeat`. `dashboardHealth` is a constant spec: service `dashboard`, mode `live`, `deps: {}` (`health.ts`).
2. `new HealthTracker()`; the ports from `cfg.dashboard.port` (default 3000) and `cfg.dashboard.lan_port` (default 3001), the only things that decide them (DASH-HTTP-009, DASH-HOST-001; `host.ts` `resolvePorts`; `packages/config/src/schema.ts`); `VOICE = urls.voice()`.
3. `setupControl(process.env, bus, log)` reads the `CONTROL_*` and `DASHBOARD_HOST` env and returns `{control?, bind}`, where `bind` is the full-surface address: `DASHBOARD_HOST`, else `127.0.0.1`, an empty value ignored (DASH-CTRL-003). It throws, aborting startup, when `CONTROL_ENABLED=1` without a token, and when the address is not loopback while control mode is off (DASH-HOST-007).
4. The UI bundle, `services/dashboard/dist-ui/` next to the server's `dist/`, is located once here; its `index.html`, its `avatar.html` and its files are read per request (The UI, below). The docs directory, `docs/.vitepress/dist` under the workspace root (`findWorkspaceRoot()`, `@cohost/config`), is resolved once here (the working directory stands in when no workspace root is found, so the docs route then answers its not-built page); its files are read per request (Docs site).
5. The upload limits from `cfg.dashboard.inject` (`uploads.ts`, DASH-UPL-001, DASH-UPL-002); uploads themselves live in Redis, not in the process. The renderer (`renderer.ts`, `models.ts`) is built from `cfg.renderer`, which becomes the applied view (Avatar renderer, The applied view), and `cfg.dashboard.models.max_bytes`, with the model directory `<dataDir()>/dashboard/avatar-models/`, which it creates at the first upload and from which it removes stale `.incoming-*` files at start, when no upload can be running.
6. A `StackService` (`stack.ts`) holds the stack state: the latest status probe, the one action slot, the last result. Its controller is an `ObservedStackController` (a control-plane `StackController` whose every status read is serialised and reported to the service); the service hands it its phase callback. `createDashboardHandler({...})` builds the routes over the service, and a `WebSocketServer({noServer: true})` is shared by both listeners for the feed, and a second one serves the renderer relay on `/avatar/ws`, each upgrade routed by its path. Each connection calls `feed.onConnection`, and `feed.start()` begins following the bus. `startFeed` (`feed.ts`) runs `feed.start()` in the background: when the health seed fails because Redis is unreachable, the feed logs a warning, marks the bus `unreachable`, and retries the seed with the bus's backoff (250 ms doubling to 30 s) until it succeeds, while the page, the stack routes and the stack state keep working (DASH-HTTP-012). `serveClient` awaits each connection's replay: when it fails it logs the error and keeps the socket open without the replay, so a page opened while Redis is down still receives the services and stack snapshots and every later push.
7. `startListeners` (`host.ts`) listens on the full-surface address and port and on all interfaces at `dashboard.lan_port`, sharing the handler and WebSocket server (DASH-HOST-001); a listener that cannot bind logs `fatal` naming the address and port and exits non-zero (DASH-HOST-003). The heartbeat becomes `ready` only once both listeners are listening (DASH-HTTP-009), and the startup log carries the full-surface URL from the address and port actually bound and the LAN port (DASH-HOST-006).
8. The stack prober (`StackService.start`) runs the stack controller's status at startup, every 5 s and after each action phase, and pushes changes to `/ws` clients (DASH-STACK-007). A launch's readiness wait supplies its own statuses while it polls; the 5 s probe is skipped then, and no two status reads overlap.
9. One `onStop` step stops the feed, the stack prober and the relay's frame reader and closes the WebSocket servers and both HTTP listeners; the bootstrap then stops the bus. The heartbeat's `stopping` is published by `startHeartbeat`'s own shutdown hook (control-plane). Shutting the dashboard down never stops the stack: a stack left running keeps running, and a restarted dashboard picks its state up again from Compose and the bus.

Environment read by this segment: `DASHBOARD_HOST`, `VOICE_URL` / `VOICE_PORT` (via `urls.voice()`, `packages/config/src/index.ts`), `TTS_URL` and `OLLAMA_URL` (via `urls.tts()` and `urls.ollama()`, for the pick lists), `CONTROL_ENABLED`, `CONTROL_TOKEN`, `CONTROL_ADVANCED` (`packages/control/src/config.ts`), `VIEWERS_TOKEN` (Viewers page; env only), plus the heartbeat interval env owned by control-plane; ports and upload limits are `config.yaml` keys (the config segment's CFG-SCH-038).

All routes are handled by one function, `createDashboardHandler` (`routes.ts`). Gated routes answer `401` with `www-authenticate: Bearer` on a missing or wrong token; `bearerOk` does a constant-time comparison of SHA-256 digests (`routes.ts`, `packages/control/src/config.ts`). When control is disabled there is no token check anywhere except on the `/viewers` routes and the secret write. The `/ws` feed is never authenticated (the sink page needs it).

Request bodies for `/control`, `/personality`, `/sink`, `/mouth/routing`, `PUT /secrets`, `/secrets/*` and lifecycle posts are capped at 64 KiB (`BODY_LIMIT`, `body.ts`), matching `/inject/text` (DASH-HTTP-011): `readText` stops collecting past the cap, drains the rest and throws `BodyTooLarge`, which the catch-all answers `413` with nothing published, saved or run. `/inject/*` has its own caps (`inject.ts`), and `POST /avatar/models` its own, `dashboard.models.max_bytes`, enforced while the body streams (Model files). A malformed `%` escape in a lifecycle service id is answered `404` like any unknown id, before the body is read (DASH-HTTP-013, `routes.ts`).

### Service lifecycle routes

When control is enabled, `POST /services/:id/(start|stop|restart)` takes an optional JSON body. Only `mode` (`resume` | `fresh`) and `isolated` (boolean) are read; an empty body is `{}`; a malformed body, non-object, or bad field type is `400` (`routes.ts`). The controller's result maps to HTTP: refusal `unknown` to 404 (which includes `dashboard`, not a manifest unit because it is not a Compose service; DASH-SVC-003), `forbidden` (redis/postgres without `CONTROL_ADVANCED=1`) to 403, each with `{ok:false, detail}`; otherwise `200 {ok, detail?}` (`routes.ts`). The controller has only these two refusals. While a stack action or another lifecycle request holds the action slot, the route answers `409 {ok: false, detail: "busy: <kind> held by dashboard (pid <pid>)"}` (`kind` is `service-start`, `service-stop` or `service-restart` for a lifecycle request) before the controller runs (DASH-STACK-003). The controller (manifest-only ids, consumer-group resets for `fresh`, isolated env) is control-plane's. The dashboard supplies `by: "dashboard"` and an `audit` callback that publishes `service.lifecycle`, logging and swallowing a publish failure (`control.ts`). `setupControl` warns on a non-loopback `DASHBOARD_HOST` (token travels in cleartext) and when `CONTROL_ADVANCED=1` (`control.ts`).

## Settings routes

`GET /config/schema`, `GET /config/:section` and `PUT /config/:section` (`services/dashboard/src/settings.ts`) are the settings screen's surface, specified by module-contract MOD-CFG-001 to 016 and driven by `@cohost/config`'s editor. The reads are ungated; the write is gated like `PUT /personality` (and, for a change to a sensitive key, in both control modes, below), takes at most 64 KiB, reads and compares the file's etag and writes it without an await between, and never starts, stops or restarts a unit or touches `.env`. The Settings screen (Settings screen, above; DASH-SET-*) renders any section from its JSON Schema and the schema's presentation metadata, offers Check and Save, and, after a save, restarts the listed units through the lifecycle routes. Two further routes serve it: the secret write and the pick-list reads.

### Sensitive keys

A config save can redirect a credential: changing `llm.openai.base_url`, `vision.obs.host` or `mouth.outputs.http.url` sends the stored key, the OBS password or the co-host's voice to another address at the next restart. With control mode off `PUT /config/:section` is open on loopback by design, so the presentation table marks the keys that decide where such a request goes `sensitive: true` (those of config CFG-PRES-011, among them `dashboard.allowed_hosts`, which widens who may reach the listeners other machines can reach, and `tools.servers` and `tools.allow`, which decide where tool requests and a credential go and what the co-host may do) and the route treats a change to one like the secret write (DASH-CTRL-009, DASH-CTRL-010):

- **When it applies.** A `PUT` without `?dryRun=1` whose `values` change a sensitive key, meaning a value whose write would change the key's effective value in the file now: the edit is applied to the text as a save applies it and the result is read back and compared with the current value by type and value (a value the editor refuses is compared as submitted), so `"undefined"`, `"null"` and a numeric string are never taken for an absent value or the number the file holds. A save that touches no sensitive key, or sends one unchanged, keeps its ordinary gating; a dry run writes nothing and stays as it is.
- **Gate.** `Authorization: Bearer <CONTROL_TOKEN>` in both control modes. A missing or wrong token is `401` with `www-authenticate: Bearer` and `{ok: false, detail, sensitive: [paths]}` naming the changed sensitive keys; with no control token configured it is `403 {ok: false, detail, sensitive}` naming `CONTROL_TOKEN` and `CONTROL_ENABLED`. The check runs after the Host and Origin checks and the body's size and shape and before the etag is compared or any value validated, so the answer does not depend on the file's state.
- **On the page.** The Settings screen reads `sensitive` from the schema, notes beside the key that changing it needs the control token, sends the token with a save that includes such an edit, and opens the Access dialog naming the change when it holds none or the save answers `401`; Cancel keeps the edits (DASH-SET-028).

### Secret write

`PUT /secrets/<config path>` sets or clears one secret, addressed by its full dotted config path: a section's `path` from `GET /config/schema`, a dot, and one of the section's `secrets` names (`llm` and `openai.api_key` give `llm.openai.api_key`). The paths are those of CFG-SEC-003: the OpenAI-compatible and Claude API keys, the two Bedrock keys, the OBS password, the ears bearer token, the API keys of the ears OpenAI-compatible, Nemotron and Kyutai engines, the voice OpenAI-compatible API key and the Pocket Hugging Face token, the four Twitch credentials, the YouTube API key, the Discord bot token and the token of each MCP server, `tools.servers.<name>.token` for a name that the saved `config.yaml` holds under `tools.servers`; a token path whose server `config.yaml` does not hold is `404 unknown secret` for a set, and `null` clears it, so the token of a removed server can be cleared. The value is stored in `secrets/secrets.yaml`, a separate git-ignored file outside `config/` that the configuration loader merges over it (config segment), and reaches a service at its next start or restart through the control plane, which projects it into the units that declare it (deployment Secret scoping); no secret is ever written to `config.yaml` or `.env`.

- **Body.** `{ "value": "<text>" }` sets; `{ "value": null }` clears: the key stays in `secrets.yaml` with an empty value, which keeps the file's comments and layout, and every read reports the secret not set. The value is trimmed of leading and trailing whitespace and must then be non-empty and hold no control character, C0 or DEL (a newline pasted after the key is trimmed, not refused); anything else is `400 {ok: false, detail}`, and clearing is `null`. The body is capped at 64 KiB (`413`).
- **Gate.** The route always requires `Authorization: Bearer <CONTROL_TOKEN>`, whether or not `CONTROL_ENABLED=1`, and answers `401` with `www-authenticate: Bearer` otherwise. When no control token is configured at all (control mode off, `CONTROL_TOKEN` unset) it answers `403 {ok: false, detail}` naming `CONTROL_TOKEN` and `CONTROL_ENABLED`, as the Viewers routes do for `VIEWERS_TOKEN`; a secret is never writable by an unauthenticated request. It is served only on the full-surface listener; the Host and Origin checks apply as to every `PUT`. Refusals are checked in this order: `403` Host or Origin, `403` no token configured, `401` token, `413` body size, `404` unknown path, `400` body. The order is what lets the Access dialog check the control token without writing anything: a request to a path that is no secret path answers `401` for a wrong token and `404` for the right one (Access).
- **Unknown path.** A path that is not one of those secret paths, or whose `%` escape is malformed, is `404 {ok: false, detail: "unknown secret"}`.
- **Several at once.** `PUT /secrets` with `{ "values": { "<config path>": "<text>" | null, ... } }` applies every entry in one `updateSecrets` write, so the request succeeds or writes nothing, under the same gate and the same per-value rules; it answers `200 {ok: true, set: { "<config path>": boolean }, restart}` with the units of every named secret's section, a body that is not an object holding a non-empty `values` object or a value the single form refuses is `400`, and a path that is not a secret path is `404 {ok: false, detail: "unknown secret", paths}` naming it (DASH-SECRET-011).
- **The Bedrock pair.** `llm.bedrock.access_key_id` and `llm.bedrock.secret_access_key` work only together: with exactly one of them set, the services that build the model client refuse to start. A request, in either form, that names one of them and would leave exactly one with a value is `400 {ok: false, detail, paths}`, `paths` being the two config paths, and writes nothing; setting or clearing both in one `PUT /secrets` is the way to change them from empty or to empty, and rotating one while the other is set is a single-path write. A request that names neither is not refused for a pair already half set (DASH-SECRET-012).
- **Answer.** `200 {ok: true, set: boolean, restart: string[]}`: `set` is whether a value is now stored, and `restart` lists, in manifest order, the units whose manifest `secrets` list declares the path (a wildcard entry matching it) and that the latest stack status shows running (none when Docker is unavailable), as MOD-CFG-015 does. The value is never in any response, log line, error text or bus event; reads keep reporting only set or not set (MOD-CFG-005).
- **Writing.** The route calls `updateSecrets` (CFG-SEC-009), which rewrites the file atomically with mode `0600` and keeps every other secret and comment; the value is stored trimmed (CFG-SEC-013), and the file has no etag, so the last write to a path wins. Two writes in flight are applied one after the other in arrival order. A failed write is `500 {ok: false, detail}` carrying the error text, never the value, and leaves the file as it was. The route never starts, stops or restarts a unit and never reads or writes `config.yaml` or `.env`.

### Pick lists

Two read-only routes feed the settings widgets. They are ungated, like `GET /config/*`, and served on the full-surface listener only.

| Route | Source | Success |
|---|---|---|
| `GET /options/voices` | `<urls.tts()>/v1/audio/voices` (the Kokoro-FastAPI voice list), while `voice.engine` is `kokoro`; no other engine has a voice list | `200 {voices: string[]}`, sorted, without duplicates; with any other engine `502 {ok: false, detail: "no voice list for engine <name>"}` |
| `GET /options/models` | `<urls.ollama()>/api/tags` (the models installed in Ollama) | `200 {models: string[]}`, the model names, sorted |

When the backing server is unreachable, answers non-2xx, answers a body that is not the expected shape, exceeds 1 MiB, or takes longer than 3 s, the route answers `502 {ok: false, detail}` naming the cause. Neither answer is cached (`cache-control: no-store`). The UI treats a failure as "no list" and shows a plain text box holding the current value (DASH-SET-010). The dashboard fetches the lists itself because the voice and model servers publish no CORS header and are not meant to be reached from a browser; a list of OBS scene sources is a recorded follow-up, not served.

## Host process and stack control

The owner's decisions here are settled: the dashboard is a standalone program started on the host, outside Compose, and nothing else has to be running for it to start; Compose has no `dashboard` service; a Launch button brings up the whole stack through the control plane's compose runtime, and the dashboard can stop the stack and restart its services; stack actions sit behind `CONTROL_ENABLED=1` and `CONTROL_TOKEN`; the UI shows the stack's state. The mechanics below are owner decisions too. The [decision doc](decisions/standalone-dashboard.md) weighs where the dashboard runs and how it listens.

### Starting it

The owner runs `mise run dashboard` from anywhere in the repository (deployment DEPLOY-HOST-001). The task, which the deployment segment owns (DEPLOY-HOST-001), builds the bus addon and the UI bundle through its dependencies, rebuilds the docs site when the docs changed (`mise run docs:build`), then builds the dashboard and the workspace packages it imports (`tsc -b services/dashboard`, incremental, so a second start is quick), and runs `node services/dashboard/dist/index.js` with the repository root as the working directory. A failed docs build is printed and the dashboard starts anyway (DEPLOY-HOST-006); the docs route then serves whatever build is in place, or its not-built page. A failed addon or UI build stops the task, so the dashboard never starts with an old or missing UI. Node and pnpm come from `mise.toml` through mise, which the installer sets up. `cohostctl dashboard` is not offered: `@cohost/control` cannot depend on the dashboard (the dashboard depends on it), and a CLI that spawns the dashboard would be the control plane supervising a host process, which it never does.

First run, documented on the docs site's Install for real page (`docs/guide/install/real-install.md`, DEPLOY-HOST-003): run the installer (it seeds `.env`, which ships `CONTROL_ENABLED=1`, and writes a generated `CONTROL_TOKEN` into it, DEPLOY-INST-013), run `mise run dashboard`, open `http://localhost:3000`, paste the token from `.env` into the Access dialog when the page first asks (DASH-UI-006), and press Launch. At startup the dashboard logs both URLs, `http://127.0.0.1:<port>` and the LAN listener's port, and where the token lives, never the token itself (DASH-HOST-006). With control enabled and no token the dashboard refuses to start with an error naming `CONTROL_TOKEN` (DASH-CTRL-002).

### Files and addresses on the host

- **Config.** `loadConfig()` reads `.env` from the repository root into the process environment without overriding what is already set, and `configDir()` resolves to `<repo>/config` (config CFG-DIR-001, CFG-ENV-004). These are the same files Compose bind-mounts into every container at `/app/config`, so `PUT /personality` writes the file cortex re-reads. A `personality.md` first seeded by a container (which runs as root) is root-owned on a Linux host and the save then fails with `500` and the error text (DASH-HTTP-004); the installer seeds the files as the owner, which avoids it.
- **Data.** The dashboard keeps its test uploads in Redis for a few minutes (Test-input injection and uploads). The one thing it writes under `dataDir()` is the owner's avatar models, in `<dataDir()>/dashboard/avatar-models/`, a folder git ignores with the rest of `data/` (Model files, below); no container mounts or reads it.
- **Redis.** `urls.redis()` defaults to `redis://127.0.0.1:6379`, the loopback port Compose publishes (deployment DEPLOY-COMPOSE-006). No `.env` change is needed.
- **Voice.** `urls.voice()` defaults to `http://127.0.0.1:8700`; Compose publishes voice's port on `127.0.0.1:8700` for this (deployment DEPLOY-COMPOSE-007). The dashboard is the host-side player of record, and every browser goes through its proxy.
- **Postgres.** Never read by the dashboard (HLD tenet 1). Viewer notes arrive over the bus (Viewers page).
- **Containers and the dashboard.** Injected uploads travel over Redis, which the containers already reach on the Compose network, so nothing on the host needs to be reachable from a container for test injection; no URL is advertised (DASH-INJ-005).

### One PC: WSL2 with Docker Desktop

A supported host is WSL2 with Docker Desktop, and it is where the whole design is first tested: everything runs on one PC, with no second machine. The dashboard runs inside the WSL distro (`mise run dashboard`); the containers run in Docker Desktop.

- **Windows browser to the dashboard.** WSL forwards `localhost` ports from Windows to listeners in the distro, so a Windows browser opens `http://localhost:3000` against the full surface on `127.0.0.1:3000`, and the Host check (DASH-HOST-004) accepts it because the browser sends `Host: localhost:3000`. If forwarding is turned off in the owner's WSL settings, the owner sets `DASHBOARD_HOST=0.0.0.0` instead, which requires control mode (DASH-HOST-007).
- **Same-PC sink.** OBS on Windows, or a second browser tab standing in for it, loads `http://localhost:3001/?sink=1` from the LAN listener (or `http://localhost:3000/?sink=1` from the full surface). Both exercise the same sink page the second-PC setup uses at `http://<ai-pc-ip>:3001/?sink=1`.
- **Dashboard to the containers.** Docker Desktop makes ports published on `127.0.0.1` reachable on `localhost` inside the WSL distro, so the dashboard reaches Redis on `127.0.0.1:6379` and voice on `127.0.0.1:8700` with the same defaults as on native Linux.
- **Containers to the dashboard.** None for test injection: uploads travel over Redis (DASH-INJ-005). The LAN listener serves the sink page and the audio proxy to a browser or OBS, not to containers. Containers reach voice on the Compose network (`http://voice:8700`) on every host.
- **The `docker` binary.** Inside WSL, `docker` is Docker Desktop's WSL integration when that is enabled; otherwise only the Windows `docker.exe` is on the path. The control plane runs `COHOST_DOCKER_BIN` when it is set, else `docker`, else `docker.exe` (control-plane CTRL-STACK-012), so the dashboard and `cohostctl` work either way.

### Listeners

| Listener | Address | Serves |
|---|---|---|
| Full surface | `DASHBOARD_HOST`, else `127.0.0.1`, in both control modes; a non-loopback address requires control mode (DASH-HOST-007); port `dashboard.port` (3000) | every route |
| LAN | all interfaces, `dashboard.lan_port` (default 3001) | `GET /`, the UI's files (`GET /assets/*`, `GET /favicon.svg`), `/ws`, `GET /audio/*`, `POST /sink`, `/health`, and for the avatar renderer `GET /avatar`, `GET /avatar/model` and the `/avatar/ws` upgrade; everything else `404` (DASH-HOST-002), the docs site under `/cohost` and every other `/avatar/*` route, the model list, upload and delete included, among it (DASH-DOCS-012) |

The LAN listener exists so an OBS Browser Source on a second PC can load `http://<ai-pc-ip>:3001/?sink=1` for the audio, and `http://<ai-pc-ip>:3001/avatar` for the avatar (by IP address, or by a name listed in `dashboard.allowed_hosts`, DASH-HOST-009) while every gated route, the stack routes above all, is reachable only from the host. Its handler has no path to a gated route, so host-locality does not depend on a per-route check. `GET /` on it without a `sink` parameter is answered with a `302` to `/?sink=1` (DASH-HOST-002), so a browser pointed at the bare LAN address lands on the sink view instead of a page whose every call would 404. A same-PC OBS source keeps using `http://localhost:3000/?sink=1`. Both listeners share one handler instance and one feed.

Two request checks guard the full-surface listener while it is bound to a loopback address (DASH-HOST-004, DASH-HOST-005):

- **Host.** A request whose `Host` names anything other than a loopback name (`localhost`, `127.*`, `[::1]`) is answered `403`. This stops a DNS-rebinding page (a public name that resolves to `127.0.0.1`) from reading `/ws` or `GET /personality` through the owner's browser.
- **Origin.** A state-changing request (`POST`, `PUT`, `DELETE`) that carries an `Origin` header whose host and port differ from its `Host` is answered `403` and nothing runs. Requests without `Origin` (curl, `cohostctl`, OBS) pass. The bearer token already stops a cross-site request, since a page on another origin can neither read the token from this origin's `sessionStorage` nor send an `Authorization` header without a CORS preflight the dashboard never approves; the Origin check is defence in depth for the routes that drive Docker.

- **`/ws` Origin.** A `/ws` or `/avatar/ws` upgrade on either listener that carries an `Origin` header whose host and port differ from its `Host`, or that is `null` or unparseable, is answered `403` and completes no upgrade (DASH-HOST-008): a WebSocket upgrade is a `GET` that the browser sends cross-origin with no preflight, so without the check any page in the owner's browser could read the feed, voice transcripts included, or the avatar's frames. The renderer page, in a tab or in an OBS Browser Source, opens its socket from the origin it was loaded from, so its `Origin` equals its `Host` and it passes. An upgrade with no `Origin` is not refused on that ground (a non-browser client; the LAN trust boundary accepts it).
- **Host on the listeners other machines can reach (DASH-HOST-009).** The Origin comparison alone does not stop a DNS-rebinding page, which controls both headers: its `Origin` and `Host` are the same attacker name, which resolves to the dashboard's address. It also reads the ungated GET routes (`/config/<section>`, `/personality`, `/services`, `/stack`, `/audio/<id>`) as same-origin. So every request, HTTP of any method and `/ws` and `/avatar/ws` upgrades alike, with or without an `Origin`, on the LAN listener and on a full surface bound beyond loopback must carry a `Host` whose name is an IPv4 address (four decimal octets, no leading zeros), a bracketed IPv6 address, `localhost` or a name in `dashboard.allowed_hosts`; anything else is answered `403` `forbidden`, or refused for an upgrade, and nothing runs. Names are compared case-insensitively with a trailing dot removed and the port is not checked; the other spellings of an address a resolver might accept (`0x7f.1`, `2130706433`, `010.1.1.1`, `1.2.3`) are refused because a browser does not send them for a typed address. An address literal names no domain anyone can rebind, which is why the list is the only place a name enters; a name is listed only for a machine the operator controls. The loopback-bound full surface keeps its own rule (DASH-HOST-004) and ignores the list. The rule stops a page reading the listener, not reaching it: a page on another site that knows the listener's address can still send requests whose responses it cannot read, so it can detect that the dashboard is there and, if it has an utterance id, cause that audio to load in an element without reading it. The key is read at start, like the other `dashboard.*` keys.
- **`POST /sink` Origin (DASH-HOST-010).** The LAN listener's one state-changing route has no token (an OBS Browser Source cannot present one), so a web page that can reach the listener could send a cross-site simple `POST` with a text body and publish forged `voice.playing` or `voice.done` events. A request on it that carries an `Origin` must name its own `Host`'s host and port, as on the full surface (DASH-HOST-005); `null` or unparsable fails; none is accepted, as from a script. The sink page posts from the origin it was loaded from, in a browser tab and in an OBS Browser Source alike, so its `Origin` equals its `Host` and it passes; the Vite dev proxy rewrites `Origin` and accepts only a loopback `Host` (DASH-BUILD-007).
- **Second-PC setup.** The Browser Source loads the sink page by the AI PC's IP address (`http://192.168.1.20:3001/?sink=1`), or by a machine name once that name is in `dashboard.allowed_hosts` (`allowed_hosts: [streampc]` for `http://streampc:3001/?sink=1`); a name that is not listed is answered `403` and the page does not load. Nothing the project itself ships addresses either listener by name: compose services never call the dashboard, `host.docker.internal` is how containers reach OBS and VTube Studio on the host, and `cohostctl` reaches Docker and the bus, not the dashboard.

The token is accepted only from the `Authorization` header, never from a query string or body, and neither the header nor the token is ever written to the log (DASH-HOST-006). The two listeners' ports differ whenever the configuration loads (config CFG-SCH-038), so a saved setting cannot make the second bind fail on a clash the loader could see; a port another program holds is a bind-time failure (DASH-HOST-003).

### Stack routes

`GET /stack` (ungated, like `GET /services`) answers the snapshot the page also receives on `/ws` (DASH-STACK-001):

```
{ state, docker: { ok, detail? }, bus: "connected" | "unreachable",
  action: null | { kind, phase, startedAt },
  last:   null | { kind, ok, detail?, services?, finishedAt },
  services: [ { service, status, health?, restartCount?, overrides? } ] }
```

`state` is the control plane's stack state (`docker-unavailable`, `down`, `starting`, `up`, `degraded`, `stopping`; control-plane CTRL-STACK-011), `services` lists each Compose container the status probe saw, with its restart count (DASH-STACK-008) and, where the probe read them, its `overrides`: the isolation-override variables set in the container, each with its value (control-plane CTRL-STACK-016, DASH-STACK-010), which is how the settings editor learns that a unit runs isolated. `bus` is the dashboard's own Redis reachability (DASH-FEED-009).

With control enabled, `POST /stack/launch`, `/stack/stop`, `/stack/restart` and `/stack/consolidate` start the matching stack-controller action in the background and answer `202 {ok: true, action}` at once (DASH-STACK-002); progress and the result travel on `/ws` and `GET /stack`, because a launch can take many minutes (an image build on first launch) and a consolidation pass up to 30. The routes take no body fields: nothing from the request reaches an argv (control-plane CTRL-STACK-009).

- **One action at a time.** The dashboard holds one action slot for stack actions and per-service lifecycle requests together. While an action runs, every other stack or lifecycle request is answered `409 {ok: false, detail: "busy: <kind> held by dashboard (pid <pid>)"}` and nothing runs (DASH-STACK-003; every busy refusal names its holder in this shape). Launch pressed twice therefore runs once. `cohostctl` is a separate process, so the slot is backed by the control plane's lifecycle lock file (control-plane CTRL-LOCK-001 to 004): the dashboard takes it for every stack or lifecycle request and `cohostctl` takes it for every command but `status`, so an action started from one entry point refuses the other with `409 {ok: false, detail: "busy: <action> held by <by> (pid <pid>)"}` (DASH-STACK-009).
- **Docker unreachable.** When the latest probe found Docker unavailable, a stack `POST` is answered `503 {ok: false, detail}` naming the cause (DASH-STACK-004). The page explains it instead of offering the buttons.
- **Preconditions.** `POST /stack/restart` is refused `409` while the stack is `down` (there is nothing to restart); `POST /stack/consolidate` is refused `409` while the `memory` container is running, so the one-shot never races the memory service's own pass (DASH-STACK-005).
- **Launch.** Runs the control plane's launch: `docker compose up -d --build --remove-orphans` (images are rebuilt on every launch, so they never lag the code), then a wait until every long-running container is running and, where it has a healthcheck, healthy (control-plane CTRL-STACK-002 to 005). Launching while some or all services already run is the same action and converges the stack on the Compose file: stopped services start, a service an isolated start had recreated with a preset is recreated without it, and services already as configured are left alone. A partial failure is reported per service and nothing is rolled back.
- **Stop.** Runs `docker compose stop`: every container of the stack, infrastructure included, stops gracefully (SIGTERM, Compose's grace period, reverse dependency order), so the memory service stops before Postgres and Redis and records `notes.shutdown_run_owed` as it always does on a graceful stop (memory MEM-CONSOL-013). Containers, networks and volumes are kept; `down` is never run. After a successful stop the page offers to run the consolidation one-shot (DASH-UI-019), which is optional: the memory service catches up at its next start.
- **Restart all.** Restarts every running application service through the per-service controller, each in its default mode and audited as its own `service.lifecycle` record; infrastructure is left alone (control-plane CTRL-STACK-007).
- **Audit.** Launch, stop and consolidate publish no bus event: the bus is down before a launch and goes down during a stop. The dashboard logs each action's start and result (DASH-STACK-006). Restart-all is audited per service by the controller.

### Stack state on the page

The Services screen opens with a stack card (DASH-UI-017, DASH-UI-018), and the header shows the stack state beside what the co-host is doing. The card is always shown, with control on or off: it states the stack's state as a status with a sentence of cause, the Launch / Restart all / Rebuild / Stop buttons when control is enabled (each asks for confirmation in a dialog and is disabled while an action runs), the running action's phase in words and elapsed time, and the last result with each not-ready service and its status (DASH-UI-020). With Docker unreachable the card says so and shows the probe's detail; with the stack down it says the stack is down and offers Launch; with the bus unreachable it says what cannot be sent meanwhile. The per-service rows below stay driven by the heartbeat tracker; the card adds what heartbeats cannot show: whether Docker answers, whether containers exist, and the infrastructure containers that send no heartbeat.

### Egress note

The speech and vision engines and the chat model can be pointed at a server outside the LAN (HLD tenet 8). The Services screen marks the `voice`, `ears`, `eyes`, `cortex` and `tools` rows whose configured destination is off the LAN, with one sentence per destination: "spoken text goes to <host>", "audio goes to <host>", "screen frames go to <host>", "the conversation goes to <host>", "tool requests go to <host>" (the `tools` row names each such server). A destination with no host, a hosted provider, is named by its provider instead: "screen frames go to anthropic". The marks come from `GET /egress`, which answers `egressDestinations(config)` for the saved `config.yaml` (config, Egress destinations): `{destinations: [{service, data, engine, host, hosted, offLan}]}`, no credential in it. The dashboard evaluates the configuration the services read, including `network.lan`, and judges names by their form, so Compose service names count as the LAN there and in the containers. It is an open read on the full-surface listener, like `GET /config/*`, which already returns the same host values. The screen shows an entry only where `offLan` is true. The Settings screen shows the same note beside `voice.engine`, `ears.stt_engine`, `ears.stt_fallback_engine`, `vision.provider` and `llm.provider`, so an owner who has just chosen a hosted engine sees where their audio, text or frames will go before they restart the service. The list describes the saved file, so after a save it differs from what a running service does until that service restarts; the service's own heartbeat detail, which names engine and host, is what it runs now. The three engine services log their own entries at start; the chat model's entry is shown here and is not logged by a service of this capability.

### When Redis is down or restarts

The dashboard starts and serves its page with Redis absent (DASH-HTTP-012). Until the bus answers, the feed reports `bus: unreachable`, the Services screen shows every service `unknown`, routes that publish (`/control`, `/inject/*`, `PUT /personality`) answer `500` with the publish error (DASH-HTTP-004), `/viewers` routes answer `504`, and the dashboard's own heartbeat publishes fail with a logged warning at most once per 60 s (SHARED-LIFE-011). When Redis comes up (by Launch or otherwise), the seed succeeds, the tails resume through the bus's own retry, and the bus reports `connected`.

Restarting Redis or Postgres from the dashboard stays behind `CONTROL_ADVANCED=1` per service (control-plane CTRL-GUARD-003). A Redis restart drops the dashboard's connections for its duration; the tails resume from their last seen ids (stream ids are time-based, so new entries sort after them), the tracker shows services `stale` until fresh heartbeats arrive, and the audit record of the restart itself may be lost (the audit is best effort). Stack actions ignore `CONTROL_ADVANCED`: stopping the whole stack is a deliberate whole-stack act, and Launch has to start Redis and Postgres.

## Docs site

The dashboard serves the docs site's built output, `docs/.vitepress/dist` under the workspace root, at `/cohost` and every path beginning `/cohost/` (`docs.ts`, `handleDocs`, called from `createDashboardHandler` right after `GET /`; DASH-DOCS-001). `/cohost/` is the base path the GitHub Pages build already uses (docs-site DOCS-BUILD-003): VitePress writes the base into every link and asset URL, so the one build the `pages` workflow publishes is the build the dashboard serves, and the owner reads the docs for the checkout they run at `http://localhost:3000/cohost/`, offline. The dashboard never builds or writes that directory. `mise run dashboard` rebuilds the site when the docs changed before it starts the dashboard (deployment DEPLOY-HOST-001), and `mise run docs:build` run by hand refreshes it while the dashboard runs. While a build is rewriting the directory, requests may briefly see the not-built page or a `404`; a reload after the build finishes shows the new site.

Only `GET` and `HEAD` are served; any other method on these paths falls through to the catch-all `404` and reads nothing (DASH-DOCS-011). `HEAD` answers exactly what `GET` would, without the body (DASH-DOCS-010). Each request runs these steps in order:

1. **Built?** `index.html` in the docs directory must be a regular file. When it is not, the request is answered `503` with `cache-control: no-store` and a short HTML page, titled "Docs not built", saying that the docs have not been built yet, to run `mise run docs:build` in the repository and reload, and that `mise run dashboard` builds them when it starts (DASH-DOCS-009). The check runs per request, so a build that finishes while the dashboard runs is served without a restart.
2. **Decode and guard.** The part of the path after `/cohost/` (the *remainder*) is decoded with `decodeURIComponent`. A remainder it cannot decode (a malformed escape, or escapes that are not valid UTF-8) or a decoded remainder holding a NUL character is answered `400` (DASH-DOCS-007). The decoded remainder is resolved against the docs directory; when the result is not inside the docs directory, or the real path (symlinks followed) of any existing candidate in step 3 is not inside the docs directory's real path, the request ends there and is answered as an unknown path (the `404` below) and no file outside the docs directory is read (DASH-DOCS-008). The URL parser has already removed `.` and `..` segments, `%2e` spellings included, before the handler sees the path; the guard covers what decoding still produces, such as `..%2F`.
3. **Resolve**, first match wins:
   - a remainder that is empty or ends in `/`: the file `<remainder>index.html` (DASH-DOCS-002);
   - the remainder itself, when it names a regular file (`assets/…`, `favicon.svg`, a page asked for with its `.html`) (DASH-DOCS-002);
   - `<remainder>.html`, VitePress's clean URLs: `/cohost/guide/operate/health` serves `guide/operate/health.html` (DASH-DOCS-002);
   - a directory holding `index.html`, asked for without the trailing slash: `301` to the same path with `/` appended and the query string kept, which also takes `/cohost` to `/cohost/` (DASH-DOCS-003). VitePress's router maps `/cohost/advanced/testing/` to that directory's index page but `/cohost/advanced/testing` to a page that does not exist, and shows its not-found page after hydration, so the slash is added by redirect, as GitHub Pages does, rather than by serving the index at both URLs;
   - nothing: `404` with the body of the built `404.html` (the server-rendered not-found page, docs-site DOCS-THEME-039) as `text/html; charset=utf-8`, or `not found` as plain text when that file is missing (DASH-DOCS-004).
4. **Answer** `200` with the file, read whole before the status is written, so a failed read is a `500` like any other handler failure (DASH-HTTP-004); the largest built file is well under a megabyte. Headers (DASH-DOCS-005, DASH-DOCS-006): `content-type` from the file's extension (table below), `content-length`, `x-content-type-options: nosniff`, `etag: W/"<size>-<mtime>"` (the size in bytes and the modification time in milliseconds rounded down, each in lowercase hex), and `cache-control: public, max-age=31536000, immutable` for a file at any depth under `assets/`, whose name VitePress gives a content hash, or `cache-control: no-cache` for every other file, so a rebuilt page is fetched again while unchanged assets come from the browser's cache. A request whose `If-None-Match` lists the file's current etag, or is `*`, is answered `304` with only the `etag` and `cache-control` headers and no body. A missing `404.html` makes the `404` a plain-text `not found`.

| Extension | `content-type` |
|---|---|
| `.html` | `text/html; charset=utf-8` |
| `.js`, `.mjs` | `text/javascript; charset=utf-8` (VitePress's scripts are ES modules, which a browser refuses under any non-JavaScript type) |
| `.css` | `text/css; charset=utf-8` |
| `.json` | `application/json` |
| `.svg` | `image/svg+xml` |
| `.woff2` | `font/woff2` |
| `.png` | `image/png` |
| `.jpg`, `.jpeg` | `image/jpeg` |
| `.webp` | `image/webp` |
| `.ico` | `image/x-icon` |
| `.txt` | `text/plain; charset=utf-8` |
| anything else | `application/octet-stream` |

**Where it is served.** On the full-surface listener only. The LAN listener keeps its allow-list (DASH-HOST-002), on which `/cohost` is not, so it answers every docs path `404` without reading a file (DASH-DOCS-012): it exists for a second PC's OBS sink, which needs no docs. The docs paths are reads and ungated in both control modes (DASH-CTRL-005). On a loopback-bound full surface the Host check (DASH-HOST-004) applies to them as to every request; a `HEAD` or `GET` carries no state change, so the Origin check (DASH-HOST-005) never applies. With `DASHBOARD_HOST=0.0.0.0` the full surface, docs included, is reachable from other machines; the docs are the content GitHub Pages already publishes.

**Same origin.** The docs pages share the dashboard's origin. That lets the live health table on the docs' Service health page (docs-site, Served by the dashboard) read `GET /services` with a root-relative URL, and the dashboard sends no `access-control-*` header on any route. Sharing the origin is safe because the docs build is the repository's own code, loads nothing from any other origin (docs-site DOCS-THEME-010) and carries no user content.

**From the page.** The header's Docs link and the Services screen's "How to read these states" link open the docs in a new tab (The UI, below).

## Feed and health

`createFeed` (`feed.ts`) is the glue between Redis and the browser.

- `start()`: seeds `HealthTracker` from `bus.recentHealth(500)`, tails the health stream from the last seen id with `bus.tailHealth` into `tracker.ingest`, tails the main stream with `bus.tail` and broadcasts every event as JSON to all OPEN sockets, subscribes `tracker.onChange` to push a `{type:"services", services}` message, and ticks the tracker every 1000 ms (unref'd) so staleness transitions are pushed even without new heartbeats (`feed.ts`).
- `onConnection(ws)`: sends the current services snapshot, then the stack snapshot (DASH-FEED-008), then `bus.recent(60)` oldest-first, each event with `replay: true` added (`feed.ts`; `bus.recent` reverses an `XREVRANGE`, `packages/bus/src/index.ts`). The socket is already in `wss.clients` when `connection` fires, so the feed registers it in a `replaying` map before its first await: live events for that socket are held there, and after the replay they are sent once, skipping any id the replay already contained (DASH-FEED-001). Other clients get live events immediately. The page also de-duplicates by bus event id and never plays a `replay`-marked utterance (DASH-UI-013). `serveClient` wraps the call so a failed replay affects only that socket, which stays open without the replay (DASH-HTTP-012).
- Stack state (DASH-FEED-008, DASH-FEED-009): a new socket receives a `{type: "stack", ...}` snapshot (the `GET /stack` body) right after the `services` snapshot, and every change of the stack state, a container's status or health, the running action, its phase, the last result or the bus reachability is pushed to every OPEN socket. The feed sets bus reachability `unreachable` when the seed or a tail read fails and `connected` after the next successful read. The stack snapshot is sent before the event replay, so a client that cannot get a replay (Redis down) still gets both snapshots.
- Heartbeat events are filtered from both paths (`feed.ts`). They normally never appear on the main stream, since `publish` refuses them (`packages/bus/src/index.ts`, `publish`); the filter is defensive.
- Everything else on the main stream goes to every browser, including event types the page then ignores, including the tool events (shown as the feed's Tool rows; the catalog also drives the Tools settings), except the viewer-notes events `memory.notes.request`, `memory.notes.reply`, `memory.viewers.request` and `memory.viewers.reply`, which carry note text (including health and family notes) and are never sent on `/ws`, live or in the connect replay (DASH-FEED-007). There is no per-client subscription and no authentication on `/ws`.
- **Tool text stays off the LAN.** The feed knows which listener a socket arrived on. The recall text (`memory.recall.request` `query`, each memory's `text` in `memory.recall.reply`) is emptied the same way, and so is the `text` of an `inject.request` for the tools unit and the `note` of a `tool.timer` (DASH-FEED-011). To a socket that arrived on the LAN listener, or on the full-surface listener while it is bound to a non-loopback address, it sends `tool.request` with `arguments` `{}`, `tool.confirm` with `arguments` `{}` and `tool.result` with `content` empty and no `truncated`, each with `redacted: true` when it emptied something (a `/ws` frame member only, never on the bus), and an `inject.request` for the tools unit with empty `text` and a `tool.timer` with empty `note`, live and in the connect replay, so the tool name, the status and the duration are all those connections see; a bar for a call sent without its arguments says so and its Allow is off (DASH-TOOL-005); a socket on the loopback full surface gets the events whole. The argument and result text can hold recalled viewer memories and the owner's private lookups, which is why viewer-notes events are kept off `/ws` the same way (DASH-FEED-007).

## Test-input injection and uploads

The per-unit test side sheet, `POST /inject/event`, the refusal of an injection for a unit that is not running (MOD-TEST-005) and the settings editor's routes are the [module contract](../module-contract/module-contract-design.md)'s; this section describes the inject routes as they stand.

`handleInject` (`inject.ts`) serves the four `POST /inject/*` routes. It runs after the `/audio` proxy and before the services, personality and control routes (`routes.ts`).

`POST /inject/text` (JSON, 64 KiB cap, `inject.ts`): validated fields are `level` (`service` | `bus`, required), `as` (`chat` default | `speech` | `vision` | `tool`), `text` (non-blank string), optional `remember`, `user`, `platform` (`twitch` | `youtube` | `discord`), `isMod`, `isSub`, and, for `level: "bus"` with `as: "speech"` only, `source` (a source tag, stamped on the `speech.heard`; DASH-INJ-009). `level: "service"` supports `as: chat` and `as: tool`.

- `level: service` with `as: tool` always requires the control token, whether or not control mode is on, as `POST /tools/answer` does, because an injected call can run an acting tool. It publishes `inject.request {id, target:"tools", kind:"text", text, remember:false}`, `text` being the JSON `{"tool", "arguments"}` of one call; the tools service runs it through its pipeline with origin `dashboard`, publishes the `tool.result` and answers with `inject.result` ([tools](../tools/tools-design.md) Test injection). `level: bus` with `as: tool` is refused with 400: a tool call is not a perception event.
- `level: service` with `as: chat` publishes `inject.request {id, target:"chat", kind:"text", text, meta, remember}` with the raw text; chat re-validates and runs its normal path (computing `mentionsCohost`, `services/chat/src/inject.ts`) and replies with `inject.result` (`inject.ts`).
- `level: bus` publishes the perception event directly with `injected: true` and `remember`: `chat.message` (platform default `twitch`, user default `injected_viewer`, whitespace collapsed; `userId` omitted and `mentionsCohost` not computed, so it takes its schema default `false`: mention detection is chat's perception step, which bus level skips, so affect, memory and salience never see a bus-level chat line as a mention), `speech.heard` (speaker = user or `injected`, `durationMs: 0`), or `vision.summary` (`changed: true`). The envelope `source` is `dashboard` because the bus was constructed as `new Bus("dashboard")`. No `inject.result` follows; the UI says so.
- Response `202 {id}`: at `level: service` the `id` is the fresh UUID carried by the `inject.request` (chat answers with `inject.result` of that id); at `level: bus` it is the published event's own bus id, so the id can be matched to the event on the feed.

`POST /inject/image` and `/inject/audio` (raw body): content-type allowlists (PNG/JPEG/WebP; WAV/x-wav/MPEG/Ogg/WebM/MP4), `?level` must be `service` (`bus` and anything else is 400), size cap per kind checked on `Content-Length` and while streaming, empty body 400. The bytes go into Redis (`Bus.putUpload`, key `cohost:upload:<id>`, a 128-bit random hex id, TTL `dashboard.inject.ttl_ms`, default 5 min); the event stream only carries `inject.request {target: eyes|ears|connector-discord, kind, uploadId, contentType, meta?, remember}`. `?user=`, `?remember=1|true` and, for audio, an optional `?source=` (a source tag, carried as `meta.source`; DASH-INJ-009) and, for audio, an optional `?target=` (`ears`, the default, or `connector-discord`, whose clip the Discord connector plays on its sink path; DASH-INJ-010) are read from the query. The target service reads the bytes through its own Redis connection and deletes the key (shared-runtime SHARED-INJ-005). A Redis write that fails answers 503 and publishes nothing (DASH-UPL-003).

`uploads.ts` holds only the limits: per-kind byte caps (`dashboard.inject.max_image_bytes`, default 8 MiB, and `dashboard.inject.max_audio_bytes`, default 25 MiB) and the TTL (`dashboard.inject.ttl_ms`), all read from `config.yaml` at start (DASH-UPL-001, DASH-UPL-002). Redis expiry replaces the in-memory store's sweep and eviction, so there is no sweeper and no entry-count cap: at most one upload per accepted request exists, each bounded by its kind's cap and dropped by its TTL or by the consumer.

## Avatar renderer

The browser renderer is a web page that draws the owner's own VRM model, added to OBS as a Browser Source at `http://<ai-pc-ip>:3001/avatar` (or `http://localhost:3000/avatar` on one PC). It is a drawing surface and nothing else: the avatar Engine decides every pose and writes each frame to a capped Redis stream through its `browser` driver ([avatar](../avatar/avatar-design.md) browser; the stream is the event bus's, [Avatar frames](../event-bus/event-bus-design.md#avatar-frames)), and the dashboard relays the frames to the page. The dashboard keeps no animation logic. Its parts are the relay, the page, the model files and the settings that frame the model; the avatar service opens no port and never sees a model file, which is why the dashboard, the one program that listens on the LAN, owns all four (HLD Key Decisions, Browser renderer placement).

### The applied view

The dashboard holds one record of what the renderer shows: the applied view, the applied model (its name and its version) and the three framing values, with the model name the file holds kept beside it for a note. At start it is set from `cfg.renderer`: when `renderer.model` names a stored model that is listed without an `error` (names compare without regard to ASCII case) the applied model is that one, and otherwise the applied model is null, the dashboard logs a warning naming the key, and the configured name is kept for the settings note. After start it changes in two ways only. A save of the `renderer` section through the dashboard sets it from the whole `renderer` section as the file holds it after the save: before writing, the dashboard computes that section as the edited file would hold it and checks that its `model` is blank or names a listed valid model, whether or not the request sent `model`, a failing check refusing the save and writing nothing; after a successful write it sets the applied view from that section. The file is thus the source of truth at save time, and a value edited by hand into the file goes live with the next save of any key. An upload that replaces the applied model's file gives it a new version. It is read back from `config.yaml` at no other time. Every route and check that depends on the active model or the framing reads the applied view and not the file: `GET /avatar/model`, the `active` field of the list, the delete guard, the selection check and the relay's `view`. A hand edit of `renderer.*` therefore takes effect at the next dashboard start or at the next successful save, and until then the Avatar settings show a note when the file's values differ from the applied ones (they compare `GET /config/renderer` with the `applied` field of `GET /avatar/renderer`). This is the narrow exception HLD tenet 10 states: no service reloads its own settings while it runs, and what the dashboard pushes to the pages it serves when the owner saves it is applied at once; the settings editor reading and writing `config.yaml` to show and save settings is not a reload. Upload commit, delete and the selection check and apply of a save run one at a time under one lock, so a delete never races a select.

### The relay

`GET /avatar/ws` upgrades to the relay's WebSocket, on both listeners, under the Origin and Host rules of `/ws` (Listeners). It is a path of its own, not the `/ws` feed: frames arrive at the Engine's rate, up to `avatar.fps` a second, and the feed's pages (the audio sink among them) must not receive them, while the feed carries events the renderer must not need.

**Messages.** Text frames of JSON, three from the relay and one from the page:

| Direction | Message | Meaning |
|---|---|---|
| to the page | `{"type":"view","model":{"version":"<opaque>"} or null,"framing":{"zoom":1,"offsetY":0,"turn":0}}`; to a preview, `model` is `{"version":"<opaque>","name":"<file name>"}` | what to draw and how to frame it: the applied model's version, an opaque string that tells a page when its copy is out of date and names no file (only a preview, which is on the owner's own machine, also receives the name, to say it in its status line), and the applied framing; sent on connect and whenever either changes |
| to the page | `{"type":"status","state":"live" or "waiting" or "off","driver":"<name>" or null}` | whether frames are flowing and, when they are not, why; sent on connect and on a change |
| to the page | `{"type":"frame","frame":{"mouthOpen":0,"mouthSmile":0.15,"headX":0,"headY":0,"headZ":0,"eyeX":0,"eyeY":0,"blink":0,"emotion":"neutral","intensity":0,"expression":""}}` | the newest frame, exactly the avatar frame |
| from the page | `{"type":"model","version":"<…>","state":"loading" or "ready" or "failed","detail":"<text, at most 200 characters>"}` | the outcome of loading a model, for the owner to see (Health and visibility) |

**Who may speak.** Every page is a viewer. The relay ignores every message from a socket whose remote address is not loopback: such a page is listed to the owner only as connected, with the frame rate sent to it. The relay's WebSocket server sets a maximum message size of 4096 bytes for every socket, a larger message closing the socket with code 1009. A message from a loopback socket is accepted only in the shape above, and its `detail` is shown to the owner as plain text, never markup, after being cut at 200 characters. The status line and `GET /avatar/renderer` therefore cannot be written by a host on the LAN. A socket is loopback when its remote address is `::1`, an IPv4 address in 127.0.0.0/8, or either of those written IPv4-mapped (`::ffff:127.x.y.z`, `isLoopbackPeer`), so a dual-stack listener's IPv4 peers are judged as IPv4. A NAT or port-forwarding layer that makes remote clients arrive from loopback makes them look local, and the check cannot see that: the design adds no setting for it, so no such layer may sit in front of the LAN listener. A socket that sends more than 20 messages in one second is closed with code 1008, and terminated one second later if the close is not completed. A socket whose address has the query `?preview=1` is the settings preview; it is counted apart from the renderer pages and accepted only on the full-surface listener, where on the LAN listener the query is ignored and the page counts as a renderer page.

**One reader.** The relay holds one frame reader on the avatar-frame stream, started when the first socket connects and stopped when the last one closes, so Redis carries no read for a dashboard nobody watches through. Of each batch the reader returns, the relay keeps only the newest frame: a frame is the Engine's whole state, so an older one is superseded and dropping it loses nothing. Each frame is checked against the frame schema (BUS-AVF-002) before it is kept, and one that fails is dropped with a warning logged at most once per 10 s (DASH-AVR-034). A reader that fails retries through the bus client's backoff; meanwhile no frame is sent. The relay cannot observe the failure, so the state is `live` for at most 1 s after the last frame it received and `waiting` or `off` from then on (DASH-AVR-008); the `status` pushed to a socket can lag the evaluated state by up to one 1 s tick.

**Back-pressure.** A slow page gets the newest frame and never a longer queue. Each socket sends one message at a time; frames that arrive while a send is unfinished replace one waiting slot, and when the send finishes the slot's frame goes out. `view` and `status` have a slot each, sent before the frame, newest wins. A socket whose send does not finish in 5 s is terminated, a send counting as stuck only while its data is still buffered in the socket: a send whose data has reached the kernel is finished, though its completion callback may run later (DASH-AVR-035). A page that cannot keep up therefore sees fewer frames and each is current; nothing in the relay grows with time.

**Pages.** At most 4 renderer pages are open on each listener, 4 on the LAN listener and 4 on the full surface, and, apart from them, at most 2 previews on the full surface. A remote address that is not loopback holds at most 2 of the renderer pages across both listeners (DASH-AVR-032; an IPv4-mapped address counts as its IPv4 address), so one host on the LAN cannot take every place; the owner's loopback address is not limited per address, only per listener, so a client on the LAN cannot lock a page out of the owner's own machine. An upgrade past its cap is answered `503` with `retry-after: 5` and completes no socket; the page, which sees only a closed socket, retries as the socket rule below says and takes a place as soon as one frees, and a refused preview shows "Reconnecting". The relay pings each socket every 10 s and terminates one that has not answered in 20 s, so an OBS that was killed does not hold a place. Four pages are the OBS source, a second scene's copy and room for two test tabs; the caps bound the work one `ws.send` per frame per socket costs.

**A late page.** A page that connects or reconnects receives `view` and `status`, then the frames as they arrive; it receives no replay. A frame is a snapshot, the next one is at most one Engine tick away, and a page that has not yet got one holds the rest pose.

**State.** `status.state` is `live` while a frame arrived in the last second (the relay's own clock); otherwise `off` when the latest `avatar.state` the feed has seen, received at most 3 s ago on the dashboard's monotonic clock (the event's own `ts` is not used), names a driver other than `browser`, and `waiting` in every other case (avatar down or restarting, the Engine stopped, or no `avatar.state` seen yet). The driver name comes from that `avatar.state`, so the relay learns it from the tail of the event stream the feed already holds and opens no read of its own on it. When the driver is not `browser`, or avatar is down, the relay still serves the page and the socket; there are simply no frames.

**View changes.** Each change of the applied view is pushed to every open socket as a `view`. The relay never watches or reads `config.yaml`; the applied view is set as The applied view says.

### The renderer page

The page is a separate entry of the UI build, `avatar.html` with `ui/src/avatar/`, plain TypeScript with no React. It carries the 3D libraries; the dashboard's own entry and the sink view carry none of them, so a sink page and the owner's dashboard load no 3D code. Both entries are self-contained scripts: no dynamic import and no chunk shared between them, so a page left open across a rebuild never asks for a file that no longer exists.

**Testing without a browser.** Everything the page decides that needs no GPU lives in pure modules the UI test runner exercises under `node:test` (DASH-BUILD-006): frame validation, the mapping from a frame to a pose (the angle conversions, the expression weights and their write order), the hold and ease, handling of relay messages, the model-load state machine (versions, cancellation, failure, timeout, reports), the preview's status line and draft-message filter, the loader's URL filter, the reconnect schedule, the framing arithmetic and the etag comparison. A scan of the built bundle shows that the 3D libraries are in the renderer entry only and that it creates no audio. The scene, the loader, the spring bones, WebGL, transparency and the Content-Security-Policy in a real Browser Source are the thin layer around them and are checked by hand (Manual verification); the specs that only a real browser can show are marked `manual` in the spec file.

**What it requests.** Its own script and stylesheet under `/assets/`, `GET /avatar/model` (or, in the preview, `GET /avatar/models/<name>`), and the relay socket. It makes no request to any other origin, and the response that serves it says so in a Content-Security-Policy (below): the libraries are in its bundle, no font, image or script is fetched from elsewhere, and the model file is parsed from the bytes the page fetched, with every URL the loader would request other than a `data:` or `blob:` one refused, so a crafted file that points at an external image or buffer cannot make the page contact another origin. It creates no audio element or audio context and never plays a sound; the audio stays on the sink page.

**Content-Security-Policy.** `GET /avatar` is served with `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' blob: data:; connect-src 'self' blob: data:; worker-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'self'`, stated here once. A glTF loader in Chromium decodes the images embedded in a model by fetching them as `blob:` or `data:` URLs, which `connect-src` governs, and uses them as `blob:` or `data:` images, which `img-src` governs; `connect-src 'self'` also covers the model fetch and the same-origin socket. There is no `unsafe-eval` and no `unsafe-inline`, and no worker, because no decoder is bundled. The settings preview, the one place the page is framed, is same-origin, which `frame-ancestors 'self'` allows.

**Look.** The document and the canvas are transparent (`alpha` WebGL context, clear alpha 0, `background: transparent`), so OBS composites the model over the scene. The canvas fills the window and re-fits on every resize and whenever `devicePixelRatio` changes, which the page checks on each draw because a change of zoom or monitor sends no resize event; it caps the ratio at 2. The page draws on every animation frame while the document is visible, so its frame rate is the Browser Source's own and the spring bones and the ease run continuously; the owner sets the source's FPS (OBS defaults to 30) to the display rate or to `avatar.fps`, whichever is lower. Nothing but the model is ever drawn in OBS: no text, no border, no loading indicator. The preview alone adds a short status line (below).

**The model.** The page loads the model the latest `view` names from `GET /avatar/model` with a glTF loader and the VRM loader plugin, which reads VRM 0.x and VRM 1.0; a 0.x model is turned half a revolution about the vertical axis by the loader's own helper so it faces the camera like a 1.0 one. The response's `etag` equals the `version` of the `view` once the weak prefix and the quotes are removed from the header; a page that gets another version (the file changed between the push and the fetch) fetches once more bypassing its cache, and uses what it then gets. A fetch that delivers no byte for 30 s is aborted and reported `failed`. No decoder for compressed geometry or textures is bundled, because Draco, KTX2 and meshopt decoders are separate WebAssembly and worker files that would break the page's one-script, no-other-file rule, and the VRM exporters in common use write none of them; an upload that needs one is refused (Model files). The page computes the model's bounding box once, at rest pose, for framing.

**Loading.** A `view` whose model version differs from the one being loaded or held, and a preview's model draft, cancel a load in flight: the page aborts the fetch, disposes a half-built model and starts the newest, and only the newest request may finish, so two models are never held and a late old load cannot win. A `view` with the same model version, a framing-only change, aborts nothing. When the new model is ready it swaps in and the old one is disposed, so a change never flashes an empty frame. Disposal covers the geometry, textures and materials, the spring-bone state and the VRM object, and removes the model from the scene. The page reports `loading`, then `ready` or `failed` upstream. A reload of the page, which OBS does when a source is set to shut down when not visible or to refresh when its scene becomes active, refetches the model, and the etag lets the browser's cache answer with a `304`.

**Expression names.** An expression is addressed by its VRM 1.0 preset name (`neutral`, `aa`, `ih`, `ou`, `ee`, `oh`, `happy`, `angry`, `sad`, `relaxed`, `surprised`, `blink`, `blinkLeft`, `blinkRight`, `lookUp`, `lookDown`, `lookLeft`, `lookRight`) or, for a custom expression, by the model's own name. A VRM 0.x model's presets are mapped to those names once, here: `neutral` to `neutral`, `a` to `aa`, `i` to `ih`, `u` to `ou`, `e` to `ee`, `o` to `oh`, `joy` to `happy`, `angry` to `angry`, `sorrow` to `sad`, `fun` to `relaxed`, `blink` to `blink`, `blink_l` to `blinkLeft`, `blink_r` to `blinkRight`, `lookup` to `lookUp`, `lookdown` to `lookDown`, `lookleft` to `lookLeft`, `lookright` to `lookRight`; a 0.x blend shape group with no preset is custom and keeps its own name. The `browser` block of `expressions.yaml`, the frames and the model list all use these names.

**Direction.** The page shows each angle in the direction the avatar segment defines ([avatar](../avatar/avatar-design.md) Engine, Direction of the angles). The head quaternion is `eulerToQuat(headY, headX, headZ)` of `@cohost/shared/head-rotation`, the VMC driver's own function, which is written for the left-handed space VMC receivers use; the page converts it for the right-handed space of the 3D library by negating its `y` and `z` components, `[x, -y, -z, w]`, which is the same rotation seen in the other handedness, and applies that to the normalized humanoid `head` bone of a VRM 1.0 model. A VRM 0.x model's normalized bones have their `x` and `z` axes mirrored relative to a 1.0 model's, so for a 0.x model the page negates the `x` and `z` components of that quaternion as well, `[-x, -y, z, w]` in all, and the viewer sees the same direction on both. A unit test pins the four components for a sample angle, and a check on a real 0.x and a real 1.0 model confirms the direction (Manual verification).

**Gaze.** The page turns the look-at's own auto target off and sets no target. Where the model has a look-at, the yaw is `eyeX` times the `inputMaxValue` of its horizontal outer range map and the pitch is `eyeY` times the `inputMaxValue` of its vertical up map for a positive `eyeY` and of its vertical down map for a negative one, each signed so that a positive `eyeX` moves the gaze toward the viewer's right and a positive `eyeY` moves it up. A model with no look-at shows no gaze.

**Mapping a frame to the model.** The page applies the newest frame it holds as given; each frame it writes in this order, so the Engine's mouth and blink always win:

1. the previous frame's expression returns to weight 0 when this frame's `expression` differs from it, including when this one is empty;
2. the frame's `expression`, when not empty, takes the weight `intensity`;
3. the `happy` expression takes the smile weight `clamp((mouthSmile - 0.15) / 0.85, 0, 1)`, or the larger of that and the frame's `intensity` when the frame's `expression` is `happy`, so it keeps no weight from an earlier frame, the resting value 0.15 shows nothing and the Engine's 0.7 for a happy face shows 0.65;
4. the `aa` expression takes the weight `mouthOpen`, and the `blink` expression takes the weight `blink`;
5. the head bone takes the rotation of Direction and the look-at the angles of Gaze.

A model that lacks a mapped expression, bone or look-at shows nothing for it. At load the page sets every expression's mouth, blink and look-at override to none, so `mouthOpen`, `blink` and gaze always show as the Engine sent them, whatever the model's author configured. The page does not interpolate between frames, blink on its own, sway at rest or time a gesture: those are the Engine's, and the same values drive every other driver ([avatar](../avatar/avatar-design.md) What the page may do on its own).

**Framing.** A perspective camera with a vertical field of view of 30 degrees looks at the middle of the model's bounding box, the pivot of every framing change, from the front. The frame height is measured at the distance of that target. At `zoom` 1 it is 1.05 times the bounding box's height (feet to top of head, a 5 percent margin), and `zoom` divides it, so 2 is twice as close; only the height is fitted. `offsetY` moves the model up the frame by that many frame heights (negative moves it down), so a bust shot is a larger zoom with a negative `offsetY`. `turn` rotates the model about the vertical axis through the bounding box's centre by that many degrees, a positive angle turning its front toward the viewer's right; the head's own rotation is added on top of `turn`, never replacing it. Framing changes apply on the next draw, with no reload.

**What the page does by itself.** Beyond applying frames it does three things, each with no co-host meaning. It holds a static rest pose: the normalized humanoid's left upper arm is rotated -65 degrees and its right upper arm +65 degrees about the model's Z axis for a VRM 1.0 model, and +65 and -65 degrees for a VRM 0.x model, the mirroring of Direction, which lowers both from the T-pose a VRM loads in, because an arms-out avatar on stream is wrong whatever the frame says. It runs the model's own spring bones (hair, cloth, accessories), stepped with the real time since the last draw clamped to 50 ms so a throttled tab does not throw them across the frame. And it eases to the rest values when frames stop.

**When frames stop.** The page times on `performance.now()` from the arrival of the last valid frame; a frame that fails validation does not reset the timer. Before any frame it draws the rest values: `mouthOpen` 0, `mouthSmile` 0.15, head angles 0, gaze 0, `blink` 0, no expression. A page that has had no valid frame for 2 s (frames stopped, avatar down, the driver another one, or the socket closed: the page treats them alike) holds the last pose for those 2 s and then, over 1 s, moves each frame parameter in a straight line to its rest value and the expression's intensity to 0, converting the interpolated parameters to the pose as it does for a frame; at the end it shows no expression. It stays there, with spring bones still running, until a valid frame arrives, which it applies at once.

**Frames and messages.** A frame is dropped, and the previous one kept, when a field is missing or not a finite number, a value is outside its range, the `emotion` is not one of the nine canonical emotions or the `expression` is not a string of at most 64 characters (the schema of [event-bus](../event-bus/event-bus-design.md) Avatar frames); fields it does not know are ignored. A message with a type the page does not know is ignored. A `view` message, or a preview draft, whose numbers are not finite or whose zoom is not above 0 is ignored as a whole, and the page keeps what it had (DASH-AVP-038).

**The socket.** The page connects at load. Every close of a socket, a refused upgrade included (the browser reports a refusal as a close and shows no status), counts as a failed attempt unless the connection had stayed open for 10 s; the page reconnects after 1 s and doubles the delay per consecutive failed attempt up to a ceiling of 10 s, and a connection that stays open 10 s resets the delay to 1 s. A `503` for too many pages or a `403` therefore retries every 10 s at most as fast. When the socket opens again the page sends its last model report once more (DASH-AVP-040, a preview excepted) and asks the loader for nothing: a model already held stays, and a version that failed is reported `failed` again rather than fetched again.

**No model, or one that fails.** With `model: null` the page draws nothing. If a model fails to load the page keeps drawing the previous model when it has one and nothing when it has none, and reports `failed` with the loader's message; it never goes blank on stream because a new pick is bad. A lost WebGL context is rebuilt when the browser restores it. When it has not been restored within 10 s the page reloads itself, so a stream is not left blank, and a further reload for a lost context within 60 s of the last waits twice as long as the last wait, up to 60 s (the count is kept in `sessionStorage`; where that fails the wait is 10 s).

**Preview mode.** With `?preview=1` the page opens its socket as a preview, receives the applied model's name in `view` and shows one line of plain text over the picture, the first that applies: "Reconnecting" (the socket is closed), "No model selected", "Loading <name>", "Could not load <name>: <reason>", "avatar.driver is <name>; the renderer needs browser", "Waiting for the avatar". It accepts `postMessage` from the page that embeds it, same origin only, in three kinds: `{"type":"framing","framing":{"zoom":<n>,"offsetY":<n>,"turn":<n>}}`, `{"type":"model","name":"<stored name>"}`, which loads the model from `GET /avatar/models/<name>` and draws nothing when the name is the empty string, and `{"type":"clear"}`, which drops both drafts. A draft overrides the relay's `view` for what it covers until a clear, so the owner sees an unsaved choice without OBS changing; a message of any other shape is ignored. A preview sends no model report to the relay (DASH-AVP-039), so a loopback preview never overwrites the health line of the page OBS loads. A stored model's name reaches `GET /avatar/models/<name>` as one percent-encoded path segment with its dots escaped, so no name can change the path or add a query (DASH-AVP-036).

### Model files

**Where they live.** One file per model in `<dataDir()>/dashboard/avatar-models/`, named exactly as `renderer.model` names it, `.vrm` included, which follows the one name grammar of config: at most 80 characters in all, letters, digits, space, `_`, `.` and `-`, starting with a letter or digit and ending in a lower-case `.vrm`. Names are unique and matched without regard to ASCII case, so `Aiko.vrm` and `aiko.vrm` cannot both be stored; a file in the folder whose name does not follow the grammar, or that is not a regular file (a symbolic link is never followed, to list, read or serve), is not listed. The model store (`models.ts`) owns the directory: it lists, validates, counts bytes and applies the limits below. `data/` is git-ignored, the folder is the dashboard's own, and no container sees it: the model reaches the browser through the dashboard alone. A model is the owner's asset, never committed and never copied by a build.

**Serving.** `GET /avatar/model` (also `HEAD`) streams the applied model's file with `content-type: model/gltf-binary`, `content-length`, `x-content-type-options: nosniff`, `etag: W/"<version>"`, the version the relay's `view` carries (a size and modification time, as the docs route builds its etag), and `cache-control: no-cache`, so a page revalidates, an unchanged file is a `304` (`If-None-Match` as the docs route reads it) and a replaced one is fetched. It is streamed from the file, not read whole, because a model can be a hundred megabytes; a read error after the headers are sent cuts the connection. The name comes from the applied view, already validated by the grammar, and is still resolved by listing the directory and matching an entry that is a regular file, never a symbolic link, so the route holds no path built from a request. No model applied, or a name with no file, is `404 {ok: false, detail}` whose detail holds no file name, because this route is open on the LAN listener and the name is kept from it. The route is on both listeners and ungated, and `GET /avatar/models/<name>` serves any one stored model that the list shows without an `error` the same way on the full surface only, for the settings preview, and answers `404` for one with an `error`.

**The LAN listener gives the model away.** Anyone who can reach the LAN listener can download the active model without a token, as anyone there can fetch an utterance's audio. The trust boundary is the LAN (HLD Trust boundary), an OBS Browser Source cannot answer an auth prompt, and the URL it holds is typed by the owner. The owner who does not want that keeps the LAN listener off untrusted networks, or uses the full surface on loopback (`http://localhost:3000/avatar`) from an OBS on the same PC. The model is not a secret of the co-host, but it can be an asset under a licence that forbids redistribution (below), which is the owner's to weigh.

**The list.** `GET /avatar/models` answers `{models, active, maxBytes, maxModels, maxTotalBytes}`: the directory's `.vrm` regular files whose names follow the grammar, sorted by name, each as `{name, bytes, modified, active, vrm, title, authors, license, usage, expressions, error?}`; `active` is the applied view's model name, or `null`. The directory is read per request; what the file's own metadata gives is cached by size and modification time, so a list is cheap and a model copied in by hand shows up. An entry that fails validation, with the checks of Upload step 3 applied to its head, is listed with its `error` and cannot be selected.

**Metadata.** The dashboard reads only the glTF container's JSON chunk of each file (at most 16 MiB; a larger one is an `error`), never the geometry. `vrm` is `"1"` for a file with the `VRMC_vrm` extension and `"0"` for one with only the `VRM` extension; a file with both is read as 1.0. The model's own text is shown to the owner for information: for 1.0, `meta.name`, `authors`, `licenseUrl`, `copyrightInformation`, `contactInformation` and the permission fields (`avatarPermission`, `commercialUsage`, `creditNotation`, `modification`, `redistribution` and the usage flags); for 0.x, `meta.title`, `author`, `licenseName`, `otherLicenseUrl`, `contactInformation` and `allowedUserName`, `commercialUssageName`, `violentUssageName`, `sexualUssageName`. They are normalised to `title`, `authors`, `license` (name and URL as text) and `usage` (label and value pairs), each string cut at 500 code points, and `expressions` is the list of expression names the model defines (sorted, at most 256), in the names of The renderer page, Expression names (the 1.0 `expressions.preset` and `custom` names, or the 0.x blend shape groups with each preset mapped to its 1.0 name), which is what the owner writes in the `browser` block of `expressions.yaml`. The permission fields become `usage` pairs with these labels, a boolean shown as `Allowed` or `Not allowed` and other values as the file's text: `avatarPermission` and `allowedUserName` `Allowed users`; `commercialUsage` and `commercialUssageName` `Commercial use`; `creditNotation` `Credit`; `modification` `Modification`; `redistribution` `Redistribution`; `allowExcessivelyViolentUsage` and `violentUssageName` `Violent use`; `allowExcessivelySexualUsage` and `sexualUssageName` `Sexual use`; `allowPoliticalOrReligiousUsage` `Political or religious use`; `allowAntisocialOrHateUsage` `Antisocial or hateful use`. The screen shows all of it as plain text, never markup and never a link built from the file, with the sentence that the terms are the model's author's, that cohost enforces none of them, and that the owner should read them before using the model on stream. Nothing is stored beyond the file.

**Upload.** `POST /avatar/models?name=<file name>` with the file as the raw body (the route's body is not JSON and not capped at 64 KiB), on the full-surface listener only, and gated like the other mutations: with `CONTROL_ENABLED=1` it needs the bearer token, a foreign `Origin` is refused (DASH-HOST-005), and with control mode off it is open on a loopback full surface, as `PUT /personality` is. Its steps:

1. **Before the body.** The checks run in this order, each answering and reading nothing further (a refusal here is answered with the connection closed, so the server takes in no more of the body than its socket buffers hold): the Host check (`403`), the Origin check (`403`), the control token (`401`), a `Content-Length` over `dashboard.models.max_bytes` (`413`), `name`, which is required, then the upload slot, then a collision or a limit. `name` is reduced to its last path segment, normalised to NFC, its `.vrm` extension (any case) removed, every character outside the grammar (ASCII letters, digits, space, `_`, `.`, `-`) replaced by `_`, leading characters that are not an ASCII letter or digit removed, the stem cut to 76 characters, and an empty stem made `model`; the stored name is the stem plus `.vrm`. Another upload running is `409` (one at a time, so disk and validation work stay bounded). A stored model of that name, compared without regard to case, and no `replace=1` is `409 {ok: false, detail, name}`, so the screen can ask whether to replace it; with `replace=1` the stored file's own name is kept. A store already holding 20 models, or 2 GiB, refuses a new name with `409 {ok: false, detail}` naming the limit (a replace is judged on the size it leaves), and the total is checked again at the end of the body, once the length check has passed, answering `409` and removing the temporary file, because a request without a `Content-Length` shows its size only then; the owner deletes one first.
2. **While it streams.** The body goes to `.incoming-<16 random hex>` in the same folder, created exclusively. The model store counts the bytes as they arrive and aborts at the first byte over the cap: it deletes the temporary file, answers `413` and closes the connection, so a request without a `Content-Length` cannot fill the disk past the cap. A header whose total length passes the cap is refused the same way as soon as the head is read. The answer is written with `connection: close`; the rest of the input is drained for at most 2 s, and the socket is then destroyed (at once when the client has closed its end). An upload that sends no byte for 30 s is aborted with `408`, which deletes the temporary file and frees the slot; the full-surface server sets no request timeout, so a body that keeps moving is cut only by this limit. The file is never held in memory: only the glTF header and JSON chunk (at most 16 MiB) are buffered to be read, and the rest is written through with the request paused whenever the write backs up.
3. **Validation, at the head of the stream.** The first 12 bytes must be the glTF binary header (the magic `glTF`, version 2) and give a total length; the first chunk must be the JSON chunk and no larger than 16 MiB; the JSON must parse and name the `VRMC_vrm` or `VRM` extension in `extensionsUsed` with the extension object present. The file is also refused when its `extensionsRequired` names anything outside the supported list, when it uses Draco, KTX2 or Basis, or meshopt compression (`KHR_draco_mesh_compression`, `KHR_texture_basisu`, `EXT_meshopt_compression`; the page bundles no decoder, see The model), or when any buffer or image `uri` is not embedded, that is anything but the file's own binary chunk or a `data:` URI. The supported extensions are the VRM ones (`VRM`, `VRMC_vrm`, `VRMC_springBone`, `VRMC_node_constraint`, `VRMC_materials_mtoon`, `VRMC_materials_hdr_emissiveMultiplier`) and the material and texture ones the loader handles without a decoder (`KHR_materials_unlit`, `KHR_materials_emissive_strength`, `KHR_texture_transform`, `KHR_mesh_quantization`, `EXT_texture_webp`). A file that fails is rejected as soon as its head is read, `400 {ok: false, detail}` naming the reason, the temporary file removed and the connection closed without reading the remaining bytes (the answer is written, the rest drained for at most 2 s, then the socket destroyed). At the end of the body the byte count must equal the header's total length (a truncated or padded file is `400`). This proves a file is a VRM container, not that it loads: whether it loads is shown by the preview.
4. **Commit.** Without `replace=1` the temporary file is hard-linked to `<name>.vrm`, so two uploads of one name cannot overwrite each other: the link fails if the name exists, and a collision found now is the same `409`. An entry the listing does not show (a directory, a link, a case variant) holding the name is the same `409`. With `replace=1` it is renamed over the old file, which is atomic: a page fetching the old model finishes with it and the next fetch gets the new one. If the replaced model is the active one, the relay's `view.model.version` changes and every open page reloads it.
5. **Answer.** `201 {ok: true, model}` with the list entry. A full disk is `507 {ok: false, detail}`; any other failure is `500 {ok: false, detail}` carrying the error text, with the temporary file removed. A client that drops the connection mid-upload leaves nothing behind.

The route changes no setting: storing a model does not select it.

**Delete.** `DELETE /avatar/models/<name>` removes one stored model, gated like the upload and in the same check order. The name is decoded, must follow the grammar and must match an entry of the directory listing, without regard to case; anything else is `404`. The applied model is `409 {ok: false, detail}`: select another model, or none, and save first. The check and the unlink run under the lock of The applied view. The file is unlinked, `200 {ok: true}`.

**Select.** Choosing the active model is an edit of `renderer.model` saved through the settings route (Avatar settings), with the settings' own gating (the control token when control mode is on), on the full surface only. The save checks, after the loader's validation, that a non-blank `model` names a stored file that passed validation (an entry the list shows without an `error`), otherwise answering `400` with an issue on `renderer.model`, a dry run included, and applies the values under the lock of The applied view.

### Avatar settings

The `renderer` section is shown on the Avatar page of the Settings screen (`#settings/avatar`) as a group titled Avatar renderer, under the avatar app's own keys. Its group opens with a line that a save applies at once, to open pages too, because the section is `live` (config); a save restarts nothing. On the LAN listener the model list and the status are answered `404`, and the group says they are not available here instead of offering them.

**Model and preview.** `renderer.model` renders with the `avatar-model` widget, which is the whole of the group's top: the model list, the upload and the preview.

- *List.* One row per stored model as radio options, with a first option, None: name, size, `VRM 0.x` or `VRM 1.0`, the title and authors, the licence line as plain text, a disclosure of the usage permissions and of the expression names, and a Delete button, disabled with its reason for the saved active model. A row that failed validation shows its reason and is not selectable. A badge names the saved active model, and a second badge the unsaved choice. Choosing a row is an edit like any other: it waits for the section's Save and Discard.
- *Upload.* A drop zone and a file picker for `.vrm`, stating the limit read from `maxBytes`, refusing a larger file or another extension before sending, with a progress bar and the server's reason when it refuses. A name that exists asks "Replace <name>?" in a dialog and retries with `replace=1`. The control token is asked for through the Access dialog as for any gated action. A successful upload adds the row and selects nothing.
- *Preview.* An embedded copy of the renderer page, `/avatar?preview=1` in a frame on a checkerboard so the transparency shows, with a choice of 16:9, square or tall (kept in `localStorage` as the page's other conveniences are). It shows the saved model and, as soon as the owner picks another row or moves a slider, the unsaved draft, posted to the frame; Save or Discard clears the draft, and a preview that reloads is sent the drafts again, because the edits stay on the page. Because it is the same page, it draws exactly what the OBS source will, from the live frames of the avatar service.
- *Status.* Above the preview, a line from `GET /avatar/renderer`, polled every 2 s while the page is on screen: "1 OBS page connected · 30 fps sent" with the model state of each loopback page ("model failed to load: <reason>"), "No OBS page connected", "avatar.driver is vmc; the renderer needs browser" or "Waiting for the avatar", with a link to the Avatar page of the Settings screen, where the `avatar.driver` key is, above it. A driver the route names as `null` is shown as `null`. A link to the third-party notices (Libraries) sits beside it.

**Framing.** The three other keys are sliders with exact boxes, each in its range from the schema (each carries the `slider` widget with its step, and `renderer.turn` needs the widget because a range over 100 would otherwise be a number box): `renderer.zoom` (0.5 to 3, step 0.05, default 1), `renderer.offset_y` (-1.5 to 1.5, step 0.01, default 0, "Vertical position", in frame heights) and `renderer.turn` ("Turn", -90 to 90 degrees, step 1, default 0). The steps are the hints' own, in `packages/config/src/presentation.ts`: a span-based rule would give `renderer.offset_y` the wrong step. A Reset framing button sets all three to their defaults as an edit. Every movement is posted to the preview as a draft at once; Save writes `PUT /config/renderer` and the relay pushes the new framing to every open page, which re-frames on its next draw with no reload.

**Applying a save.** After a successful `PUT /config/renderer` the dashboard sets the applied view to the section's validated values, the ones it just wrote, and the relay pushes it (The applied view); the save's answer lists no unit to restart and no isolation warning. The group shows a note when the file's values differ from the applied ones: "`config.yaml` holds <values> but the renderer shows <values>; restart the dashboard to apply the file".

### Health and visibility

The dashboard's own heartbeat has no renderer dependency: `deps` stay empty, because a page being closed is not a fault of the dashboard. The avatar heartbeat's `deps.driver` for the `browser` driver means frames are being written to Redis, not that a page is open ([avatar](../avatar/avatar-design.md) Health). Whether anything is drawing is shown here:

- `GET /avatar/renderer` (full surface, ungated, `no-store`) answers `{state, driver, fps, applied, pages, previews, maxPages, maxPreviews}`: `state` and `driver` as the status message; `fps` the frames the relay received in its last 2 s, per second and rounded, or `null` when not `live`; `applied` the applied view as `{model, configuredModel, zoom, offsetY, turn}`, `model` being the applied model's name or null and `configuredModel` the model name the file held at the last start or successful save; `pages` one `{sentFps, model: {state, detail?} or null, since}` per open renderer page, `since` being the epoch milliseconds at which its socket connected, `sentFps` being the frames actually sent to that socket in its last 2 s (a slow page shows less than `fps`) and `model` null for a socket that is not on loopback; `previews` the count of previews; `maxPages` and `maxPreviews` the caps. The reader runs only while a socket is open, so with no socket `fps` is `null` and `state` is computed from the feed alone.
- The Avatar settings status line above, and the Live screen's Avatar card, which, while the latest `avatar.state` names the `browser` driver, adds a line "Renderer: 1 page · 30 fps" (the number of renderer pages and the highest `sentFps` among them) or "Renderer: no page connected" from the same route, polled every 2 s while the card is on screen. The card's SVG face stays what it is: a preview of the canonical state from `avatar.state`, not a stream asset (HLD Non-Goal 6).

### Latency

The path from a lip-sync value to pixels, and what bounds each part:

| Step | Time | Bound |
|---|---|---|
| The Engine tick that computes the value | up to one tick, `1000 / avatar.fps` ms, after the envelope sample changes | the Engine's own period |
| The driver writes the frame | one `XADD` and `PEXPIRE` in a pipeline from the avatar container to Redis | a write in flight blocks the next frame, which is dropped, so a slow Redis costs frames and no queue |
| The relay's read wakes | a blocked `XREAD` returns when the entry lands | one round trip to Redis on the host's loopback |
| The relay sends | JSON of the newest frame on each socket | one pending frame per socket; a slow socket replaces it |
| The network | loopback, wired LAN or Wi-Fi | outside cohost; the largest variable on a second PC |
| The page draws | the next `requestAnimationFrame` after the message | one draw period: 16.7 ms at 60 fps, 33 ms at OBS's default 30 |

Nothing in the path queues, so lag does not accumulate: the age of the pixels is at most one Engine period, one draw period, the round trips and the network. The design states no end-to-end figure, because the network and OBS's own compositing and encode are outside it. On one PC the expectation is a few tens of milliseconds, dominated by the draw period, which the owner shortens by raising the Browser Source's FPS. The mouth also starts after the sound: avatar starts a clause's mouth at the sink's `voice.playing`, which the sink page posts after its `play()` begins and which reaches avatar over the bus, so the mouth follows the audio by that hop and the path above. OBS buffers audio and video separately; an owner who sees the mouth early or late delays the audio source in OBS (the source's Audio Sync Offset in the Advanced Audio Properties), a manual alignment that no design here can replace.

### Libraries and notices

The page's libraries are `three` and `@pixiv/three-vrm`, dev dependencies of the dashboard package like every UI package (they are bundled; the running dashboard loads none of them), bundled into the avatar entry alone, never fetched from a CDN. Their versions are the registry's latest when they are added, and the lockfile pins them; no version is stated here. Both are MIT-licensed, which asks that the copyright and permission notices travel with copies.

The UI build carries notices for every third-party package it bundles (one outside the pnpm workspace), React and the 3D libraries alike ([deployment](../deployment/deployment-design.md) Licensing and contribution, Third-party notices): it writes `assets/third-party-notices-<hash>.txt`, one entry per bundled package with its name, version, licence and full licence text, and the first line of each entry script is a comment naming that file. The UI source holds the string literal `"__COHOST_NOTICES_NAME__"` for the file name; the plugin replaces that whole literal, quotes included, in each entry script with the file name, and the Avatar settings link `/assets/<file name>`. A test, or a build that did not replace it, reads the global `globalThis.__COHOST_NOTICES__` instead. Being an ordinary asset, it is served on both listeners wherever the bundle is, and the Avatar settings link to it. The build fails when a bundled package has no licence text or a licence the owner has not allowed.

## The UI

The UI is a React 19 and TypeScript 7 application in `services/dashboard/ui/`. Vite builds it into static files that the dashboard serves; it is the one page both the operator and the OBS Browser Source load. `GET /` answers the built `index.html`, and the `sink` query parameter turns the same bundle into the audio sink view (Sink mode, below). The server stays plain Node (`ws` and the workspace packages are its only runtime dependencies); everything the UI needs at run time is in the bundle, so the page makes no request to any other origin and needs no network beyond the dashboard itself. The theme uses the system UI and monospace font stacks, so there is no font file to bundle.

### Technology, build and serving

New packages, all dev-only (they are bundled or run by tests; the running dashboard loads none of them). Versions are the registry's latest at the time of writing; the lockfile pins them and the [decision doc](decisions/dashboard-revamp.md) records the check.

Neither uses a dynamic `import()`: a tab left open across a rebuild then never asks for a chunk whose hashed name no longer exists. Source maps are not shipped.

**Where the built files live: built, not committed.** `vite build` writes `services/dashboard/dist-ui/` (`index.html`, `avatar.html`, `assets/<name>-<hash>.js`, `assets/<name>-<hash>.css`, `assets/third-party-notices-<hash>.txt`, `favicon.svg`), a git-ignored directory beside the server's `dist/`. The UI build is the `build:ui` task of `mise.toml` (`vite build`, DASH-BUILD-001). The deployment segment owns the tasks that run it: `build` and `test` depend on it, `dashboard` depends on it, so a pull followed by `mise run dashboard` serves the new UI, `clean` removes `dist-ui/`, `typecheck` also runs `tsc -p services/dashboard/ui --noEmit` over the UI and its tests (DASH-BUILD-008), the `test` globs include `services/*/test/ui/*.test.tsx` (DASH-BUILD-006), and the Node `mise.toml` pins satisfies the bundler's Node requirement (DEPLOY-TOOL-001, DEPLOY-REPO-003, DEPLOY-HOST-001).

**Serving.** The UI's files are served by the same machinery as the docs site: one static-file helper takes a root directory and applies the resolution, real-path guard, content types, etag and cache headers of DASH-DOCS-002 to 008. `GET /avatar` reads `dist-ui/avatar.html` per request the same way, with no substitution and a `503` page, titled "Avatar renderer not built", when it is missing. `GET /` reads `dist-ui/index.html` per request, replaces every `__COHOST_NAME__` with the HTML-escaped `cohost.name`, and answers it `no-cache` (DASH-HTTP-001). `GET` and `HEAD` for `/assets/*` and `/favicon.svg` answer files under `dist-ui/` with `cache-control: public, max-age=31536000, immutable` for the hashed `assets/` files (DASH-BUILD-003). Reading per request makes `vite build --watch` visible with a reload and no restart. When `dist-ui/index.html` is not a regular file, `GET /` answers a `503` page, titled "Dashboard not built", that names `mise run build` and loads nothing (DASH-BUILD-005); every other route is unaffected. The LAN listener serves `GET /`, `GET /avatar`, `GET /assets/*` and `GET /favicon.svg` so a second PC's OBS source can load either bundle, and still answers every other path `404` (DASH-HOST-002). The page reads the co-host name from `<meta name="cohost-name">`, so no inline script carries it.

**Dev mode.** `mise run dashboard:ui` runs the Vite dev server (hot reload) on its own port and proxies `/ws`, `/audio`, `/services`, `/stack`, `/personality`, `/control`, `/mouth`, `/inject`, `/tools`, `/viewers`, `/config`, `/secrets`, `/options`, `/avatar`, `/sink` and `/health` (the renderer page, its socket and the model routes included; `/avatar` matches the path `/avatar` and the paths under `/avatar/` only, never `/avatar.html`, which is the dev server's own entry file for the renderer page) to the running dashboard at `http://127.0.0.1:<dashboard.port>`, the port read from `config.yaml`. The dev server listens on loopback only. The proxy serves only a request (an upgrade included) whose `Host` is `localhost`, `127.0.0.1` or `[::1]` with the dev server's port and answers `403` to any other `Host`, because a DNS-rebinding page controls `Host` and `Origin` alike and the Origin comparison alone would let it read the live feed. It then rewrites `Host` to the target's and, for a state-changing request or a `/ws` upgrade, forwards an `Origin` only when it is the dev server's own origin (rewritten to the target's) and answers `403` to any other, so a cross-site page cannot use the dev server as a way past the dashboard's Origin check; the dashboard's Host and Origin checks (DASH-HOST-004, DASH-HOST-005, DASH-HOST-008) are not weakened (DASH-BUILD-007). `vite build --watch` is the second option: it keeps `dist-ui/` current for a dashboard running as in production, with a manual reload.

**Browser support.** Current Chrome, Edge, Firefox and Safari, and the Chromium embedded in OBS Browser Sources; the renderer page also needs WebGL, which the OBS Browser Source provides when its hardware acceleration is on. The stylesheet relies on `<dialog>`, `:has()`, `color-mix()` and `<meter>`; the OBS version is checked in Manual verification.

### Structure

**Header.** Four groups that wrap: the brand (the co-host's name from `<meta name="cohost-name">`, then "cohost"); the nav (Live, Services with an attention count, Viewers, Settings, then a Docs link that opens `/cohost/` in a new tab and carries an external-link icon); the status cluster (what the co-host is doing, from `brain.status`, and the stack state); the controls (Audio on/off, Mute ("Mute co-host" or "Unmute co-host", with a pending state and the outcome beside it), Access showing Locked or Unlocked, and the theme control). The header sits above a 3 px gradient rule from `--accent-fill` to `--current-fill`. While the socket is down the status cluster is dimmed, marked `aria-busy` and titled as the last known status (DASH-UI-001). Below 720 px the brand and the status cluster share the first row (a pill truncates with its full label as a title), the nav is its own full-width row, and the controls are the last row: Audio, Mute and Access become icon buttons whose text stays for assistive technology, and the theme control sits at the right (about 150 px tall in all at 390 px, from 264 px before). A skip link is the first focusable element (DASH-A11Y-001).

**Routing.** The view is the URL hash: `#live`, `#services`, `#viewers`, `#settings` and `#settings/<section path>` (for example `#settings/brain.salience`, `#settings/personality`). Loading a hash opens that view; an empty or unknown hash opens Live; back and forward follow the hash; the nav marks the current view with `aria-current="page"` (DASH-NAV-001, DASH-NAV-002). The server serves one HTML route (`GET /`), so nothing else needs a server-side fallback.

**Keyboard shortcuts.** `/` opens Live and focuses the Say box, `1` to `4` open Live, Services, Viewers and Settings, `m` toggles mute, `Esc` closes the top-most open dialog (the one opened last; two can be open when a 401 raises the Access dialog over a confirmation), `?` opens a dialog listing them. A shortcut does nothing while focus is in an input, textarea, select or editable element, with Ctrl, Alt or Meta held, or while a modal dialog is open (other than `Esc`) (DASH-NAV-003).

**Dialogs.** Every confirmation, reason prompt, option form, the Access dialog and the shortcut list is a native `<dialog>` opened with `showModal()`: the browser traps focus, `Esc` closes the top-most one, and the page returns focus to the control that opened it after the dialog has closed (a modal dialog makes the page behind it inert, so an earlier focus call is refused; when the opener is gone, the screen heading takes focus). Each has a visible Close button in its header. A click on the backdrop closes only a dialog that holds no input the operator could lose (the shortcut list); a dialog or side sheet with fields (the Access dialog, the unit test sheet, a reason prompt) or a confirmation never closes on a backdrop click, so a stray click cannot discard typed text or answer a confirmation; a press that starts inside the dialog and ends on the backdrop closes nothing. Dialogs never block the page's own work: the feed, the audio sink and live updates keep running behind an open dialog. A dialog that submits a request shows its failure inside itself and stays open.

**Action feedback.** Every control that changes state reports its outcome beside itself: a success in an `<output>` (a polite live region) and a failure in a `role="alert"` region carrying the HTTP status and the server's `detail`, which stays until dismissed or the action is tried again. A success is shown only after a 2xx answer (DASH-UI-015).

**Connection banner.** While the WebSocket is closed, a banner says live updates stopped, at what time the feed stopped, and when the next attempt is (reconnects every 2 s); the feed, services and stack regions are marked `aria-busy` and dimmed; service ages stop counting. On reconnect the banner clears and the regions update from the new snapshots (DASH-UI-001). A frame that is not valid JSON is dropped (DASH-UI-001).

**Settings.** See Settings screen, below.

**Sink mode.** With the `sink` query parameter present (any value) the bundle renders the sink view only: the brand, the audio state and a one-line status. It makes no request except the `/ws` socket, `GET /audio/<id>-<seq>.wav` and `POST /sink`, because on the LAN listener every other route answers `404` (DASH-UI-011). Audio starts on without a click.

**Audio.** A live `voice.utterance` the page sees while audio is on is queued and its audio, `GET /audio/<id>-<seq>.wav`, is played one at a time in the order the utterances arrived, posting `playing` on start and `done` on end or error, each with the clause's `id` and `seq`; the clauses of a streamed line arrive in order, so they play in order, and the page plays utterances in arrival order and never waits for a clause that has not arrived, so a pause between two clauses of a line is a pause in the audio and another line's clause that arrives meanwhile plays next; utterances in the connect replay are shown and never played; an event id is handled once; a refused `play()` turns audio off, drops the queued clauses of that clause's line and keeps the other utterances queued, and posts `done` for the refused clause flagged `final` only when the line was open on the page (a page that had not played the line posts nothing); turning audio off by hand empties it (DASH-UI-012 to 014, DASH-UI-022). A line is open on the page from its `voice.playing` for clause 0 (event-bus Streamed lines). When the page stops taking the clauses of a line open on it (audio switched off by hand, a refused `play()`, or the page being unloaded, where the browser lets it send), it posts a `done` flagged `final` with the `seq` of the first clause it will not play, once per such line; this ends the line on this page only. A page that had not played the line, because audio was off, it joined mid-line, or clause 0 came in the connect replay, skips all its later clauses and posts nothing: an autoplay refusal or a closed tab there does not affect the reply or the other sinks. Two pages with audio on both play every utterance and both post `voice.playing`; voice accepts that (voice segment, Sink Arbitration Protocol).

**Stop.** On any dashboard page that is playing audio (the sink view or the full page with audio on), a live `voice.stop`, from whichever service published it (never one in the connect replay) empties the queue of the lines it names (every line when it names none) and stops the clip that is playing if it belongs to one of them; for that clip the page posts `done` with `interrupted: true` and the line's `spokenText` and `unsaidText`, so cortex, avatar and ears' echo gate see the line end. The page estimates the split from the clip's `currentTime` over its duration and the texts of the clauses it received, as mouth does (clauses played, the part of the current one, then the clauses still queued as unsaid). When the stop falls between two clauses of a line the page had started, it posts the same `done` for the last clause it played. It posts nothing for the clips it dropped from the queue, and nothing for a line it never started. The page applies to a line the same open and end rules as a mouth output (event-bus Streamed lines; it reads the closing `brain.clause` from the same socket): a line is open on it from its own `voice.playing` post for clause 0, ends when the closing clause has been read and the clause `through` has finished or been passed, on a stop, on its own `final`, or after 300 s with no clause activity, and an ended line gets nothing. The page drops any later clause of a stopped line that arrives after the stop.

**Feed handling.** The socket reconnects after 2 s; each frame is parsed defensively; `onEvent` first drops an event whose bus `id` it has handled (a bounded `seen` set), then routes `services`, `stack`, `inject.result`, `avatar.state`, `brain.status`, `voice.utterance` and `voice.stop`; the feed renders rows for the types of DASH-UI-002 and drops `attention.focus`, `affect.state`, `memory.recall.request`, `memory.recall.reply`, `memory.viewer` and `tool.catalog` (which the Tools settings read, not the feed). Mute state is the latest `mute` or `unmute` `control` event seen live or in the replay (DASH-UI-005). The inject status matches `inject.result` to the HTTP `id` (a result that arrives before the response is cached, last 50) and reports "no response" after 10 s. The platform list, the inject target map and the 10 s timeout are named constants in one module.

### Access

Two tokens guard what the page does: the control token (`CONTROL_TOKEN`) for every gated route, and the viewers token (`VIEWERS_TOKEN`) for every `/viewers` route. Neither is ever in a URL; each is sent only as `Authorization: Bearer`.

- *Header button.* Access shows Locked or Unlocked for the control token and opens the Access panel (DASH-ACC-001). The panel lists each token: its state (Unlocked and for how long: this tab or this browser, Locked, or "Not set up on the server"), what it unlocks ("Needed to mute, say lines, save settings, send test inputs and control services"; for viewers, "Needed to read and edit viewer notes"), and Change token and Lock buttons (DASH-ACC-008).
- *Asking.* When a gated action has no token to send, or the server answers `401`, the page opens the Access dialog, naming the waiting action ("Restart voice is waiting. It runs as soon as the page is unlocked."). A successful unlock runs that action once; Cancel runs nothing and reports "not done: locked" beside the control (DASH-UI-006, DASH-ACC-002).
- *The dialog.* A masked field with a Show/Hide button and a Paste button; "Where do I find it?" with the exact command to copy, `grep ^CONTROL_TOKEN= .env`, run in the cohost folder (the installer generated the token); for the viewers token, the exact line to add, since the installer does not generate it, `echo "VIEWERS_TOKEN=$(openssl rand -hex 24)" >> .env`; what the token unlocks; "Stay unlocked" as a radio group, This tab (default, `sessionStorage`) or This browser (opt-in, `localStorage`, with the note that it stays until the page is locked) (DASH-ACC-003, DASH-ACC-007). A "Where these are set" disclosure explains that `CONTROL_TOKEN`, `CONTROL_ENABLED`, `CONTROL_ADVANCED`, `DASHBOARD_HOST` and `VIEWERS_TOKEN` live in `.env`, are read once when the dashboard starts, and take effect only after it restarts (DASH-ACC-010). The field is `autocomplete="off"`, typed text is cleared when the dialog closes, and the page never writes a token to the console (DASH-ACC-012).
- *Checked before it is stored.* The control token is checked, in both control modes, with `PUT /secrets/access-check` (body `{"value": null}`): the secret route checks the token before the path and the body (Secret write), and `access-check` is no secret path, so `401` means rejected and `404` means accepted with nothing written; `403` means the dashboard has no control token (`CONTROL_TOKEN` and `CONTROL_ENABLED` are named, and the token shows as Not set up on the server); any other outcome (a network error, a `403` from the Host or Origin check, a `5xx`) stores nothing and shows the failure in the dialog. The viewers token is checked with `GET /viewers`: `401` rejected, `200` and `504` accepted (`504` only means memory did not answer after the token passed), `403` means the server has no `VIEWERS_TOKEN` (below). A rejected token is not stored; the dialog stays open and says "The dashboard rejected this token. Nothing was changed." with the things to check: copy the whole value after `CONTROL_TOKEN=`, with no spaces or quotes; if `.env` changed after the dashboard started, restart the dashboard (DASH-ACC-004, DASH-ACC-005). No new route exists for checking. The check works with control mode off because the secret route always needs the token (DASH-SECRET-003), so the dialog never stores a token unchecked.
- *Later rejection.* A stored token that the server later rejects (the dashboard restarted with a new `.env`) is cleared, the Access button shows Locked, and the dialog reopens with the rejection message (DASH-ACC-006).
- *Viewers token not set up.* A `403` from `/viewers` shows, in place of the Viewers list, a setup state: numbered steps (add the line to `.env`; restart the dashboard so it reads the new value; come back and paste the same value), the copyable line, and a Check again button that repeats `GET /viewers`. It has no field to paste into, since there is nothing to paste yet (DASH-ACC-009).
- *Storage.* The two tokens use separate keys (`cohost.controlToken`, `cohost.viewersToken`). Lock removes the token from both storages. A `storage` event from another tab that removes or changes a token updates this tab. When storage is unavailable (a private window), the token lives in memory for the page's life and the dialog says it will be asked for again after a reload (DASH-ACC-007, DASH-ACC-011).

### Settings screen

The screen names no section and no setting itself. Everything it shows about a section or key comes from `GET /config/schema`: for each section its `title`, `group`, `about` and optional `page`, and for each key its `help`, optional `label` and `unit`, an optional `widget` (an `options` widget carries an enum's labelled options) and, for an array of objects, the `items` help of each property. The config segment owns the wire shape (module-contract MOD-CFG-019 to MOD-CFG-021, config CFG-PRES-*); the screen reads it through one module, so a change of encoding touches that module alone.

**Navigation.** A section list beside the form (above it under 720 px), grouped Identity, Brain, Senses, Voice and body and System, in the order of the answer's `groups`; sections inside a group keep schema order. The first entry of Identity is Personality, which the screen provides itself (the personality editor). Each entry carries the number of edited keys in that section. A section whose metadata has `page` is not listed: its keys are a group on the page of the section `page` names (DASH-SET-001, DASH-SET-002).

**Page header.** The section's `title` as the heading, a smaller line from `about` saying what the section affects, then a line with the config path and what reads it: "config.yaml · `llm` · 14 settings · read by eyes, salience, affect, memory, cortex · changes apply when they restart"; a section read by no unit says it is read by the dashboard itself and applies at its next start, except a section marked `live`, which says the dashboard applies a save at once, open pages included, and restarts nothing (DASH-SET-002). A group of a `live` section that is a member of a page opens with the same sentence; the `renderer` group on the Avatar page is one such.

**Rows and groups.** Keys are grouped by their path prefix into collapsible groups, open by default, titled from the prefix words (keys with no prefix are "General"). A row has the label, the key path in monospace, the control, per-key help, a note line (range, default, "Not in config.yaml yet. Saving a change adds it."), and a right-hand column naming the source: `secret` for a secret key, `default` for a key absent from the file, `config.yaml` for every other key (DASH-SET-004). Nothing on the screen is read-only because of an environment variable (DASH-SET-003). A key that a running unit overrides, because the control plane started that unit isolated, stays editable and carries a notice naming the units and the override: "voice runs isolated: its VOICE_ENGINE override is set, and a restart keeps it. Your saved value applies again once it is started without isolation." (DASH-SET-027). A sensitive key carries a note that changing it needs the control token (DASH-SET-028).

**Widgets.** The generic control follows the key's JSON Schema type; a `widget` hint refines it. A key whose metadata is missing or whose hint is unknown renders with the generic control for its type; no key is ever hidden (DASH-SET-004, DASH-SET-013).

| integer or number with both `minimum` and `maximum` spanning 100 or less (a wider span, such as a port number, has no useful slider resolution and stays a number box) | Styled range slider with both end values printed and an exact number box beside it; the step of the key's `slider` hint when it has one, else 1 for an integer and otherwise 0.01 over spans of 2 or less and 0.05 above |
| other integer or number | Number box (`inputmode` numeric); ports and unbounded counts stay here |
| string | Text box; a string whose default or loaded value is longer than 80 characters or holds a line break is a textarea |
| array of strings | Textarea, one value per line |
| array of an enum | Chips, one per value, with the `options` widget's labels as chip text |
| array of objects (reflexes) | A card per item, built from the item schema: each property uses these same rules, a string with a `pattern` or regular-expression refinement is a text box, an enum is a select, an integer is a number box with its unit; the card has Add and Remove, a heading numbered from 1 (a card is keyed by a client-side id that follows it, so a half-typed value stays with its card when another is removed), and help from the key's `items` metadata, the property's schema `description`; an empty list shows what that means |
| any other shape | A JSON textarea marked as raw JSON, checked before saving; this is the fallback for shapes with no renderer |
| `widget.type` `timezone` | Select over the browser's zone list (`Intl.supportedValuesOf("timeZone")`, plus `UTC`, plus the current value when absent); a text box when the browser has no list |
| `widget.type` `model` with `kind` `chat`, `small`, `vision`, `embed` or `stt` | Free-text box with suggestions: the models installed in Ollama first, then a curated list for the kind; a key whose schema allows empty meaning "same as the main model" shows that as the placeholder; with Ollama unreachable, the box alone |

| `widget.type` `textarea` | A multi-line text area for the string, whatever its length or content (`vision.prompt`) |
| `widget.type` `sources` | Tile grid: one checkbox tile per source (name and one line of description), with an add-your-own tile for connector tags |
| `widget.type` `slider` | A slider with both end values printed and an exact number box, whatever the span of the key's range (`renderer.turn`), moved by the step the hint carries (`renderer.zoom` 0.05, `renderer.offset_y` 0.01, `renderer.turn` 1); a hint on a key with no bounds, or on a key that is not a number, is absent |
| `widget.type` `avatar-model` | The model list, the upload and the live preview (Avatar renderer, Avatar settings); it reads `GET /avatar/models` and `GET /avatar/renderer` and posts drafts of the section's keys to the embedded renderer page |
| the key is a declared secret | Masked secret field (below) |

An enum or array-of-enum options list, a model kind or a widget the screen does not know is treated as absent. A value the schema's enum does not list (an old file) is shown as an extra selected option, never dropped.

**Pick lists.** The model box asks `GET /options/models` once when the section opens, and the voice select asks `GET /options/voices` (DASH-OPT-001, DASH-OPT-002); these two routes are where the `model` and `voice` widgets get their lists, since the schema route serves none. A failed request leaves the plain text box holding the current value and a note, "Could not reach <the model server / the voice server>. Type the name instead."; the request is not repeated until the section is opened again (DASH-SET-010).

**Secrets.** A secret key shows its state as Set or Not set, never a value. The field is masked with Show and Hide for what the operator typed; Save replaces the value, Clear removes it (with a confirmation), and each sends `PUT /secrets/<path>` at once, apart from the section's own Save, because the secret lives in `secrets/secrets.yaml` and not in `config.yaml` (DASH-SET-009, DASH-SECRET-001). A saved secret is never read back: the page cannot display one. A secret action needs the control token, and asks for it through the Access dialog when none is held (DASH-SECRET-003). Its success feeds the same restart banner as a save.

**Validation.** Each field validates what the schema states (type, integer, minimum, maximum, pattern, JSON syntax) as the operator types, marks itself invalid with `aria-invalid` and its message in `aria-describedby`, and disables Check and Save while any field in the section is invalid. Issues the server returns (`400 { issues: [{ path, message }] }`) attach to the field whose path matches; an issue with no matching field stays in a summary above the save bar (DASH-SET-005).

**Edits and the save bar.** Edits are kept per section until saved, discarded or the page is reloaded. The sticky save bar names the count ("3 edits in this section"), and offers Discard, Check (a dry run, `?dryRun=1`, whose `warnings` appear beside the bar) and Save; with no edits, Check and Save are disabled. Leaving the page with unsaved edits asks first (`beforeunload`) (DASH-SET-006, DASH-NAV-004).

**After a save.** A success with a non-empty `restart` shows a banner at the top of Settings: "Restart these services to apply: voice, mouth" with the server's `warnings` and a Restart button when control is enabled. The button restarts the listed units one after another through the lifecycle routes, continuing after a failure and showing each result; a unit leaves the list only when its restart succeeded, so a failed one stays offered. Where control is off, the banner names the units and the `cohostctl restart <unit>` command instead. A secret save adds its units to the same list. The list is page state: it survives moving between screens and is lost on reload (DASH-SET-007, DASH-SET-008).

**The etag and multi-section saves.** The etag is the hash of the whole `config.yaml`: every section read returns the same value for the same file, and each successful write changes it for everyone. The screen therefore treats it as the file's, not a section's. A page that merges two sections, or a save with edits in several sections, writes them one after another, each with the etag the previous write answered; after a write, the loaded sections that held the etag it used take the new one, and a section loaded at any other file state keeps its own, so its save still answers `409`. If a later section fails after an earlier one was written, the bar names the sections saved and the ones not ("Saved: Demo. Not saved: Extra (save found 1 problem). Your edits to Extra are kept."), keeps the unsaved sections' edits, adds the saved sections' units to the restart banner, and offers Reload only for a `409`, whose message says Reload discards the edits to the section it names (DASH-SET-031).

**Unrecognised keys.** `GET /config/<section>` answers `unknown`, the dotted paths of keys the file holds under the section that the schema does not define (a misspelt name, a key from an older version). They have no control and the services ignore them; a save never touches them (`applySection` rewrites only the keys it was sent), and the screen has no way to delete one. Each page therefore shows a notice listing them for every section it shows, saying they are not recognised and ignored and that editing `config.yaml` removes them (DASH-SET-033).

**Edits made during a save.** The values a save marks as saved are the ones the request carried. A field changed while the request ran stays an unsaved edit and goes out with the next save (DASH-SET-032).

**Conflicts.** A `409` from a save means `config.yaml` changed since the section was loaded. The page keeps the operator's edits on screen, says the file changed, and offers Reload, which re-reads the section and discards the edits to it; nothing is discarded until the operator reloads (DASH-SET-011); Discard after a 409 clears the conflict and takes the file's current etag, so the next save is not refused again. A save whose answer is lost to a network error re-reads the section: when every edited key already holds its edited value the save is reported as done; otherwise the edits stay with the etag they were made against (a save after another client changed the file is then refused with 409, not written over their change) and the page says the outcome of the save is unknown and what the file now holds for the edited keys (DASH-SET-012). The etag of a re-read is never handed to the other loaded sections, because it can include a write the page has not seen; only a write response's etag is (DASH-SET-031).

**Personality.** The editor is a page of this screen. It loads `GET /personality`; while the load has not succeeded the editor is empty and locked, shows the reason and a Retry button, and Save is off, so an empty editor can never overwrite the file. It shows the line count and the size against the 64 KiB cap and disables Save over the cap. Save (also `Ctrl+S` while the editor has focus) sends `PUT /personality`, and reports "saved · brain reloaded" only after a 2xx answer; it applies at once, with no service restarts (DASH-SET-014, DASH-SET-015).

### The Tools settings

The `tools` section is a Settings section like the others: its ordinary keys (`mode`, the timeouts, the result limit, the timer and stream-info limits, `reply.*`) render by the generic rules, and the group is Brain. Two keys render with purpose-built controls named by their `widget` hint: `tools.servers` (`mcp-servers`) and `tools.allow` (`tool-list`). The page names no tool and no server itself: what it shows about the tools comes from the latest `tool.catalog` on the feed ([tools](../tools/tools-design.md) Tools and the catalog) and from the saved file, and a description is rendered as plain text, never as markup.

**Servers.** One row per entry of `tools.servers`: the name, the URL, whether a token is set (set or not set, read as every secret is, MOD-CFG-005), and the state the catalog reports for it (`ok`, `down`, `auth`, `mock`) with its detail sentence. Add server is a form: a name (the grammar of config), a URL and an optional token. The form also takes a header name (blank for `Authorization`) and an External switch (blank: derived from the host). Adding first clears any token stored under the name with a single-path `PUT /secrets/tools.servers.<name>.token` of `null`, which the route accepts for any name, so a token left in `secrets.yaml` never reaches the new server; the clear leaves an empty value under that key and offers no restart. Then the map is written through `PUT /config/tools` (a `tools.servers` change is a sensitive key), then the typed token is set through the same secret route, all behind the control token, and then a restart is offered of the units that read the `tools` section (`tools`, `cortex` and `salience`, for the map) together with the units whose `secrets` list declares `tools.servers.*.token` (`tools`, for the token). A failed clear stops the add with no map write; a failed token write leaves the server listed and shows `server added without a token`. Removing a server always clears its token first, then writes the map without it. A remove whose map write fails after the clear leaves the server listed without its token, and the page says so. The server's tools appear only after `tools` has restarted and connected, because the service is what discovers them; the form says so, and a probe of an unsaved URL is not offered (a token would have to travel to make it). Removing a server removes its entry and clears its secret in the same save. A server that is external shows the egress note beside its URL ("tool requests go to <host>"), with the credential-without-TLS detail when the catalog reports it. The page says that cohost cannot see what a server on the LAN itself sends on, which is what the External switch is for. A URL whose query holds a parameter named like a credential shows an advisory that a secret belongs in the header. A server's row also shows how many of its tools were left out by the catalog limits.

**Tools.** The catalog's tools, grouped under their server or under Built in, one row each: the name, the description, a badge for the effect (Read only, Changes things, Not labelled by the server) and three switches, Allowed, May act and Usable for viewer chat, which write `enabled`, `acts` and `chat` of the tool's `tools.allow` entry. Nothing is on until the owner switches it on, built-in tools included. Approving an MCP tool shows its description in full and writes `enabled` and the definition's `hash` together. Where the entry carries the catalog's `hash`, the approval counts in the unsaved edit: the not-approved note is hidden and Allowed shows on, and the row says it applies when `tools` restarts until then; a tool whose definition the server has changed shows "Changed since you approved it" and is not offered until the owner approves it again, and a tool of a server that is not `ok` shows that. The page enforces what the config enforces: May act and Usable for viewer chat cannot both be on (turning one on turns the other off and says why), and May act is offered for any tool, with a note that it makes the tool count as acting whatever its server claims. A tool that acts also has a switch, Ask me before it runs, on by default, saved as `confirm`; the built-in timer has none. A tool that changes things or is not labelled, switched on without May act, shows "Not offered to the co-host until you allow it to act" and, in the catalog of a running service, the reason it is refused. A switch's saved value and the running one can differ until `tools` restarts; the row says "Saved. Applies when tools restarts" for a difference. An `allow` entry for a tool no server lists is shown last as "Not found on any server" with a button that removes the entry. Saving `tools.allow` writes the map through `PUT /config/tools` behind the control token and offers the same restart.

**Without the service.** When no catalog is current (three of its intervals, which is how the tools service's absence is told) the page says the tools service is not running with a Start link to its Services row, lists the saved servers and `tools.allow` entries from the file with no description or state, and keeps every control editable: a setting is saved to the file whether or not the service is up.

**Advice.** The Services row of cortex shows the heartbeat detail it sets when a tool call was cut off by `tools.reply.max_tokens`, and the Tools page links the key.

The feed shows the calls: a `tool.request` row says which tool was asked for, a `tool.result` row says the status, how long it took and the start of its text (a refusal says why in words), and a `tool.timer` row says a timer went off with its note, or that it was missed (the co-host could not say it within the hold time). The Services screen's `tools` row has a Test button whose side sheet is a text injection naming a tool and its arguments (module contract Test inputs); the answer is the `tool.result` row.

### Confirming a tool call

A call to a tool that acts waits for the owner ([tools](../tools/tools-design.md) Confirming an acting call). The page shows every pending `tool.confirm` in a bar under the header on every screen, not only in Settings, so the owner sees it wherever they are: the tool's name, its arguments as plain text, never markup, each value cut at 200 characters, the reply that prompted it in words ("your voice", "the dashboard"), a countdown counted down by the page from the remaining time between the event's arrival and `expiresAt`, so a difference between the browser's clock and the host's does not matter, and Allow and Deny. The bar goes away at the call's `tool.result` or at `expiresAt`. Allow and Deny post to `POST /tools/answer` with `{id, allow}`, which publishes `tool.answer` and answers `202`; the route always requires the control token, whether or not control mode is on, like the secret write, and refuses a foreign `Origin`, because an Allow lets an action run. Where no control token is configured the route answers `403` and the call times out as `unconfirmed`.

### Layout, accessibility and width

- *Width.* The layout works from 320 px: no horizontal page scroll at any width; the services list stacks to name, state, reason and actions with inline labels on phones; the Viewers master and detail panes become one stacked view with a Back button; the settings nav sits above the form, collapsed to the current section, and each settings row stacks label, control and help; long names, service ids, tokens and details wrap (`overflow-wrap: anywhere`, `min-width: 0` on text cells) (DASH-A11Y-007).
- *Semantics.* Native elements throughout; a `<label>` for every field; `<nav aria-label>` with `aria-current`; one `<h1>` per screen; the feed a `role="log"`; results in `<output>`, failures in `role="alert"`; stale regions `aria-busy`; sections of the settings form are `<fieldset>`s with legends (DASH-A11Y-003 to 005).
- *Targets.* Interactive elements are at least 30 px tall in dense desktop rows and 44 px on touch widths (DASH-A11Y-006). A switch, slider, radio, checkbox or file input is never stretched to reach it: it keeps its shape and its label or row carries the 44 px.
- *Motion.* Transitions and the spinner are removed under `prefers-reduced-motion: reduce` (DASH-THEME-005).
- *Icons.* Inline SVG with a text label; no emoji carries meaning (DASH-A11Y-008).

## Viewers page

The owner's requirements are settled (`DASH-VIEWERS-*`, `DASH-FEED-007`): every stored viewer note is
visible and deletable here, the regular flag is set here, the layout is
master and detail (below), and every `/viewers` route requires `VIEWERS_TOKEN`.

The co-host keeps short, fading notes about viewers (memory segment, Viewer notes).
This page is how the owner sees and controls them. It satisfies the HLD principle
that nothing the co-host learns is hidden in a table: notes live in Postgres, but
every one of them, and every deletion with its reason, is listed here and can be
deleted or restored.

### Layout (master and detail)

The Viewers screen of the UI app:

- **Left: viewer list.** A search box filters by display name (the request is debounced by 200 ms and an answer to a superseded search is ignored). Each row is a `<button>` showing the display name (wrapping), a `REGULAR` badge when the viewer is a regular, "set by you" when the owner's flag (not the message count) makes them one, a `VOICE` tag for a voice speaker, and the message and note counts (DASH-VIEWERS-010). A name field above the list, with a Mark regular button, marks a viewer as regular before they have ever chatted (DASH-VIEWERS-013).
- **Right: detail panel** for the selected viewer: an "Always a regular" switch (DASH-VIEWERS-013), the memory-strength explainer (DASH-VIEWERS-022), the notes split into **Core** (long-lived) and **Recent** (fade unless repeated), each note showing its text, a category tag, a labelled strength meter and a Delete button (DASH-VIEWERS-011, DASH-VIEWERS-012), a "Clear all notes" button (DASH-VIEWERS-014), and the viewer's deleted notes with their reasons and an Undo button (DASH-VIEWERS-015).
- **Voice speakers.** A person who spoke in the voice channel is listed like any viewer, with a `VOICE` tag (memory `MEM-VOICE-009`). A voice viewer's panel has a "Link to a chat viewer" button that opens a dialog asking for the chat viewer's name and sends the link, moving its notes over; a chat viewer's panel lists the Discord ids linked to it, each with an Unlink button that asks for confirmation (DASH-VIEWERS-020, DASH-VIEWERS-021).
- **Narrow widths.** The list and the panel become one stacked view: selecting a viewer shows the panel with a Back button.

**Memory strength.** A note's strength is a percentage the panel explains in words and shows with a labelled meter: a `<meter>` of fixed width with its value as text on one line, "Strong · 90%" (a word, then the percent); the meter's low and high are the thresholds below, and its fill is drawn from the `--ok`, `--warn` and `--bad` tokens so it follows the theme, the word carrying the meaning. The words are Strong at 70% or more, Fading from 30% up to 70%, and Weak below 30%. Beside the word the meter says what happens next: "halves every 60 days" for a core note; "drops to recent under 30%" for a core note near the floor; "forgotten under 10%, in about 3 days" for a weak recent note, the days computed from the note's strength and its layer's half-life. The explainer above the notes says what the percentage means: how firmly the co-host remembers a note, from 0 to 100%; that a new note starts at 100%; that it fades with time (a recent note loses half its strength every 7 days, a core note every 60); that it jumps back up each time the viewer brings the topic up again, and after 3 mentions a recent note becomes core; and that it decides what is used (the co-host is given a viewer's strongest notes first, 5 at most; a recent note under 10% is forgotten and a core note under 30% drops back to recent). The numbers are `brain.memory.notes.recent_half_life_days`, `core_half_life_days`, `promote_mentions`, `max_notes_per_viewer`, `drop_below` and `demote_below`, read from `GET /config/brain.memory`; when that read fails the explainer keeps its sentences and leaves the figures out (DASH-VIEWERS-022).

Delete opens a dialog with a labelled optional reason and the explanation beside it: with a reason, the co-host stops re-learning similar notes about this viewer; with none, the topic can come back, weakly, if they keep raising it (memory `MEM-ADMIN-003`, `MEM-CAPTURE-006`, `MEM-CAPTURE-007`). Its buttons are Keep note and Delete note.

### Routes

The dashboard holds no notes and cannot read Postgres (HLD tenet 1). Each route
publishes `memory.viewers.request {id, op, ...}` and waits up to 3000 ms for the
`memory.viewers.reply` with the same `id`, which it receives from the feed's
existing main-stream tail (DASH-VIEWERS-008).

| Route | `op` sent to memory | Spec |
|---|---|---|
| `GET /viewers?q=` | `list` | DASH-VIEWERS-001 |
| `GET /viewers/:key` | `get` | DASH-VIEWERS-002 |
| `POST /viewers/:key/notes/:id/delete` `{reason?}` | `delete_note` | DASH-VIEWERS-003 |
| `POST /viewers/deletions/:id/restore` | `restore` | DASH-VIEWERS-004 |
| `POST /viewers/:key/clear` `{reason?}` | `clear` | DASH-VIEWERS-005 |
| `POST /viewers/regular` `{key? , name?, regular}` | `set_regular` | DASH-VIEWERS-006 |
| `POST /viewers/links` `{discordId, key? , name?}` | `link_discord` | DASH-VIEWERS-018 |
| `POST /viewers/links/:discordId/delete` | `unlink_discord` | DASH-VIEWERS-019 |

A reply with `ok: true` answers 200 with its `data`; `error: "not_found"` answers
404; any other failure 500; no reply in time answers 504 "memory did not answer"
(DASH-VIEWERS-008). Bodies are capped at 64 KiB like the other JSON routes
(DASH-VIEWERS-009).

### Access protection

Health and family notes must not leak to anyone who can reach the dashboard port.
Two paths would leak them: the open `/ws` feed (it forwards every bus event)
and any open read route. The design closes both:

1. The feed never forwards the viewer-notes events (DASH-FEED-007). This holds
   whatever option below is chosen.
2. Every `/viewers` route, reads included, requires `Authorization: Bearer
   <VIEWERS_TOKEN>`, a secret in `.env`, independent of control mode; with
   `VIEWERS_TOKEN` unset every `/viewers` route answers 403 with a message telling
   the owner to set it, and publishes nothing (DASH-VIEWERS-007). This is option
   A below, the owner's choice. The page asks for the token through the Access dialog on a 401, as it does for the control token, keeping the two in separate storage keys, and shows a setup state on a 403 (DASH-VIEWERS-016, DASH-ACC-009).

The options considered (the owner chose A):

| Option | What it is | Cost |
|---|---|---|
| **A. Dedicated `VIEWERS_TOKEN` on all `/viewers` routes (chosen)** | bearer token on reads and writes, always on, independent of `CONTROL_ENABLED`; page locked until set | one more `.env` secret; the token travels in cleartext over plain HTTP on the LAN, as the control token does; a fresh install shows a locked Viewers page until the owner sets it |
| B. Reuse `CONTROL_TOKEN`, Viewers routes only with control mode on | same mechanism as lifecycle routes | the page would be unusable with control mode off; turning control on also turns on service control the owner may not want; the notes' secrecy would be tied to the token that also drives Docker |
| C. Loopback-only Viewers routes | answer only requests from `127.0.0.1` / `::1` | the owner could not use the page from another machine, which is how an owner on a dedicated PC works |
| D. `/ws` exclusion only, routes open like `GET /personality` | rely on the LAN boundary | anyone on the LAN can read health and family notes with one `curl`; consistent with today's open reads, but those reads expose stream-adjacent text, not viewers' private matters |
| E. Never put notes on the bus; dashboard reads them another way | e.g. the dashboard queries Postgres | breaks HLD tenet 1 (only memory touches Postgres); rejected outright |

A was chosen because it is the only option that protects notes in every
control mode, and its cost is one `.env` line. The Viewers routes are not on
the LAN listener (Listeners), so with control enabled they are host-local as
well. Notes still cross the Redis stream, which the trust boundary already
covers (Compose publishes Redis on the host's loopback only, deployment segment).

## Open Questions & Future Decisions

Recorded follow-ups, none of which blocks the design:

- **State endpoint for mute and pause.** The page infers mute from replayed `control` events (DASH-UI-005); a proper read endpoint is control-plane work.
- **OBS scene-source list.** The vision settings could offer a list of OBS sources through a read route like the other pick lists; not served.
- **Concurrency guard for the personality file.** `PUT /personality` has no etag, so two tabs or a hand edit are last-write-wins; an etag on `GET` and `PUT /personality` would give it the settings editor's `409` path.
- **A record of pending restarts.** The list of services to restart after a save is page state and is lost on reload; the server keeps no record of what was saved since a unit last started.
- **Control token whitespace.** The server compares `CONTROL_TOKEN` untrimmed (control-plane); a token with stray whitespace in `.env` cannot match what the page sends after trimming.
- **LAN requests without an `Origin`.** The Origin and Host checks (DASH-HOST-008 to 010) refuse a cross-site or rebinding page on both listeners; a non-browser client on the LAN that addresses the dashboard by IP sends no `Origin` and still reads the feed and posts to `/sink`, which the LAN trust boundary accepts.
- **Conflict merge.** After a settings `409`, offering to re-apply the operator's edits over the new file, not only Reload.
- **Secrets etag.** `secrets.yaml` has no etag, so two tabs saving the same credential are last-write-wins; whether to add one is the config segment's open question.

## Manual verification

An emulated DOM covers behaviour, roles and names; these need a real browser and are checked in the first run that opens the page, and again when the bundle's styling changes.

1. **Autoplay in a real browser.** The refusal path (DASH-UI-022) is tested against a fake `Audio`; that a real browser's autoplay policy rejects `play()` the way the fake does is confirmed in a normal tab and in an OBS Browser Source.
2. **OBS Browser Source.** `?sink=1` loads and plays in the OBS version in use: the bundle needs `<dialog>`, `:has()`, `color-mix()` and `<meter>`, and the sink view must start audio without a click.
3. **320 px.** Live, Services, Viewers and Settings, and every dialog, in a 320 px viewport and on a phone: no horizontal page scroll, nothing clipped, 16 px gutters (DASH-A11Y-007).
4. **Keyboard.** Each screen and dialog reached and operated without a pointer: focus order, the trap inside a modal dialog, focus returning to the opener, a visible focus ring everywhere, shortcuts inactive while typing (DASH-NAV-003, DASH-A11Y-002).
5. **Screen reader.** The feed (`role="log"`), results (`<output>`), failures (`role="alert"`), dialogs, the strength meters and the settings form read sensibly in NVDA or VoiceOver.
6. **Colour and motion.** Both themes, with the OS scheme switched and the override set, and with reduced motion on (DASH-THEME-002, DASH-THEME-005).
7. **Dev proxy.** `mise run dashboard:ui` against a running dashboard: pages load, writes succeed (the Origin check passes), the socket connects, and a cross-site form post to the dev server's port is refused (DASH-BUILD-007).
8. **Header wrapping.** The header wraps into groups at desktop widths and puts the nav on its own full-width row below 720 px (DASH-NAV-002).
9. **Touch targets.** Interactive elements measure at least 30 px tall in dense desktop rows and 44 px tall below 720 px (DASH-A11Y-006).
10. **Stale dimming.** With the socket closed the feed, services and stack regions look visibly dimmed and recover on reconnect (DASH-UI-001).
11. **Feed following.** The feed follows new rows, stops following when scrolled up and shows "Jump to latest" (DASH-UI-026).
12. **Focus ring and status shapes.** The 2 px focus ring is visible on every control in both themes, and the five statuses are told apart without colour (DASH-A11Y-002, DASH-THEME-004).
13. **Esc in a dialog.** `Esc` closes a modal dialog as a cancel in each supported browser and the OBS Browser Source (DASH-ACC-011).
14. **The renderer in OBS.** `http://<ai-pc-ip>:3001/avatar` as a Browser Source in the OBS version in use: the background is transparent (DASH-AVP-006), the Content-Security-Policy lets the model's embedded textures load and blocks everything else (DASH-AVP-002, DASH-AVP-004), the model loads from the LAN listener and draws at the source's FPS on every animation frame (DASH-AVP-008, DASH-AVP-031), the rest pose lowers the arms and the spring bones move (DASH-AVP-018, DASH-AVP-019), a change of framing in the settings reaches it without a reload, and the mouth and the sink page's audio line up well enough to stream (with the audio sync offset if not).
15. **The renderer with two PCs.** The Browser Source on the stream PC reconnects after the dashboard restarts, shows the rest pose while the stack is down, and recovers at the first frame.
16. **A real VRM 0.x and VRM 1.0 model.** Each loads, faces the camera, and takes the head, gaze, mouth and blink mapping in the directions of avatar AVATAR-DIR-001 to AVATAR-DIR-005, the head direction being the same on both versions and the same as under the VMC driver (DASH-AVP-037); each shows its emotion expressions, with the model's own overrides and the look-at's auto target off (DASH-AVP-016, DASH-AVP-017); each model's resources are released when another replaces it (DASH-AVP-025).
17. **Context loss.** With the GPU process of the Browser Source reset (or the WebGL context lost by the browser's developer tools), the page rebuilds when the context returns and reloads after 10 s when it does not (DASH-AVP-034); the resize and the device pixel ratio are followed (DASH-AVP-007).
