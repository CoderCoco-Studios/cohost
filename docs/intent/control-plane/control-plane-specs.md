# control-plane specs

Specs for `packages/control` and the semantics the dashboard and compose consumers delegate to. `[x]` = implemented and observed in code, `[ ]` = intended but not yet implemented (gap), `[D]` = deferred (deliberately not provided). Each `<!-- test: -->` pointer names the test file that carries the matching `@spec` annotation; a line with no pointer has no direct test. Design context: [control-plane-design.md](control-plane-design.md).

## Service manifest (CTRL-MANIFEST)

- [x] **CTRL-MANIFEST-001**: The system shall define `SERVICE_MANIFEST` as the allow-list of exactly 20 controllable units: twelve pnpm app services (`chat`, `salience`, `affect`, `memory`, `cortex`, `tools`, `voice`, `avatar`, `eyes`, `ears`, `mouth`, `connector-discord`; the host-run `dashboard` is not a unit), each with `composeName` equal to its id and `pnpmFilter` equal to `@cohost/<id>`, and eight compose-only units (`redis`, `postgres`, `ollama`, `tts`, `stt`, `tts-pocket`, `stt-nemotron`, `stt-kyutai`) that have no `pnpmFilter`. <!-- openspec: service-control § Manifest-only service ids --> <!-- test: packages/control/test/manifest.test.ts -->
- [x] **CTRL-MANIFEST-002**: The manifest shall declare, per unit, the Redis consumer groups on `cohost:events` that a fresh start resets (`chat`, `salience`, `affect`, `cortex`, `tools`, `voice`, `avatar`, `eyes`, `ears` and `mouth` each own a group of their own name; `memory` owns `memory`, `memory-recall` and `memory-notes`; `connector-discord` owns a group of its own name, for `inject.request`; the compose-only units own none) and a default start mode of `fresh` for every pnpm service that owns groups except `memory` (`chat`, `salience`, `affect`, `cortex`, `tools`, `voice`, `avatar`, `eyes`, `ears`, `mouth`, `connector-discord`) and `resume` for `memory` and the compose-only units, so the control-plane default matches each service's bus subscribe start mode (`latest` for all but `memory`, which resumes). <!-- openspec: service-control § Start modes (resume vs fresh) --> <!-- test: packages/control/test/manifest.test.ts -->
- [x] **CTRL-MANIFEST-003**: The manifest shall flag `redis` and `postgres` as `infra`, carry no `self` flag on any unit, and carry these isolation presets (override names to values, CFG-ISO-006) applied by an isolated start, each preset delivered as `COHOST_ISOLATION` (CTRL-RUNTIME-009): `chat` `CHAT_SOURCES=[fake]` (the list `chat.sources` with only the fake source, so neither Twitch nor YouTube is read); `memory` `MEMORY_STORE=memory` and `MEMORY_EMBEDDER=hash`; `cortex` `LLM_PROVIDER=mock`; `voice` `VOICE_ENGINE=stub`; `avatar` `AVATAR_DRIVER=null`; `eyes` `VISION_ENABLED=false` and `VISION_PROVIDER=stub`; `ears` `EARS_SOURCES=[]` (the empty list of `ears.sources`, EARS-SRC-001) and `EARS_STT_ENGINE=stub`; `mouth` `MOUTH_DISCORD_ENABLED=false` and `MOUTH_DRYRUN_ENABLED=true`; `connector-discord` `CONNECTIONS_DISCORD_ENABLED=false`; `tools` `TOOLS_MODE=mock`; every other unit an empty preset. <!-- openspec: service-control § Protected services --> <!-- test: packages/control/test/manifest.test.ts -->
- [x] **CTRL-MANIFEST-004**: When `findService` is given an id that is not a manifest entry (including a crafted string such as `cortex; rm -rf /`), the system shall return `undefined`, so no request text can reach a runtime argv except by selecting a manifest entry. <!-- openspec: service-control § Manifest-only service ids --> <!-- test: packages/control/test/manifest.test.ts -->
- [x] **CTRL-MANIFEST-005**: The health tracker's default known list and `cohostctl status`'s list shall both be `appServiceIds()`, the ids of the manifest units that have a `pnpmFilter` (the twelve application services, each named by its heartbeat `service`), so no service list is kept outside `SERVICE_MANIFEST`. <!-- test: packages/control/test/manifest.test.ts -->
- [x] **CTRL-MANIFEST-006**: The manifest shall carry `tts-pocket`, `stt-nemotron` and `stt-kyutai` as compose-only units that own no consumer group, have default mode `resume`, carry an empty isolation preset and no `infra` flag, so the Services screen lists them and start, stop and restart act on them like `tts` and `stt`.

## Runtime adapters (CTRL-RUNTIME)

- [x] **CTRL-RUNTIME-001**: When `ComposeRuntime` is asked to start, stop or restart a manifest unit, the system shall run `docker compose up -d <composeName>`, `docker compose stop <composeName>` or `docker compose restart <composeName>` through `execFile` with an argv array (no shell), a 120 s timeout and the configured `cwd`. <!-- openspec: service-control § Runtime interface and adapters --> <!-- test: packages/control/test/runtime.test.ts -->
- [x] **CTRL-RUNTIME-002**: When `ComposeRuntime.restart` receives a non-empty env override, the system shall run `docker compose up -d --force-recreate <composeName>` instead of `restart`, and shall merge the override over the base environment of the spawned `docker` process. <!-- openspec: service-control § Runtime interface and adapters --> <!-- test: packages/control/test/runtime.test.ts -->
- [x] **CTRL-RUNTIME-003**: If a `docker compose` command fails, then `ComposeRuntime` shall resolve `ok: false` with `detail` set to the trimmed stderr (else the error message), truncated to 500 characters, rather than throwing. <!-- test: packages/control/test/runtime.test.ts -->
- [x] **CTRL-RUNTIME-004**: If `ComposeRuntime` is asked to act on an id that is not in its manifest, then it shall resolve `ok: false` with an `unknown service` detail without executing anything. <!-- openspec: service-control § Manifest-only service ids --> <!-- test: packages/control/test/runtime.test.ts -->
- [x] **CTRL-RUNTIME-009**: Where `ComposeRuntime` starts or recreates a service with an isolation preset, the system shall make the preset visible inside the started container as one variable, `COHOST_ISOLATION`, whose value is the JSON object of the preset's names and values (for example `{"AVATAR_DRIVER":"null"}`), set on the spawned `docker compose` process and passed to the container by a single pass-through entry `COHOST_ISOLATION: ${COHOST_ISOLATION:-}` in the compose `x-ts-service` environment; the system shall set no per-name variable (`CHAT_SOURCES`, `LLM_PROVIDER` and the rest). <!-- openspec: service-control § Runtime interface and adapters --> <!-- test: packages/control/test/runtime.test.ts --> <!-- test: packages/control/test/compose.test.ts -->
- [x] **CTRL-RUNTIME-010**: When `ComposeRuntime.consolidate` is called, the system shall run `docker compose run --rm -T consolidate` through the injected exec (argv only, no shell, cwd and env as for the other verbs) with a 30 minute timeout instead of the 120 s default, and resolve `ok: true` with the last non-empty line of the command's stdout as `detail` when it exits 0, or `ok: false` with the trimmed stderr (else stdout tail, else the error message), cut to 500 characters, as `detail` when it fails or times out. The argv is fixed: the `consolidate` job is not in the manifest and no caller input reaches it. <!-- test: packages/control/test/runtime.test.ts --> <!-- test: packages/control/test/runtime.test.ts -->
- [x] **CTRL-RUNTIME-011**: When `ComposeRuntime.reembed` is called, the system shall behave as for `consolidate` (CTRL-RUNTIME-010) with the fixed argv `docker compose run --rm -T reembed`. <!-- test: packages/control/test/runtime.test.ts -->
- [x] **CTRL-RUNTIME-012**: Where the Docker executable is a Windows binary seen from WSL2 (its name ends in `.exe`), the system shall list `COHOST_ISOLATION` in the `WSLENV` of the process it spawns for a start or recreate that sets it (appended to any existing `WSLENV`, once), including when its value is the empty string (CTRL-RUNTIME-013, CTRL-STACK-017), because WSL interop forwards only the variables `WSLENV` names to a Windows process and the preset would otherwise never reach the Compose pass-through of CTRL-RUNTIME-009; for any other executable the environment shall be passed unchanged. <!-- test: packages/control/test/runtime.test.ts -->
- [x] **CTRL-RUNTIME-013**: Where `ComposeRuntime` runs any `docker compose` action that carries no isolation preset, the system shall set `COHOST_ISOLATION` to the empty string on the spawned process, replacing any value it inherited from its own environment, so that an ambient `COHOST_ISOLATION` never reaches a container; a recreated service started without a preset therefore comes up without overrides. <!-- test: packages/control/test/runtime.test.ts -->
- [x] **CTRL-RUNTIME-014**: Before `ComposeRuntime` runs `start`, `restart` (either form), `consolidate` or `reembed`, and before `StackController.launch` and `rebuild` run `up`, the control plane shall call `projectSecrets` (CFG-SEC-019) with the workspace root and, for every manifest unit that has a Compose service and a non-empty `secrets` list, its `composeName` and that list, and when the call fails it shall run no `docker compose` command and return `ok: false` with the error's message, which names no secret value (deployment DEPLOY-SECRET-004).
- [x] **CTRL-RUNTIME-015**: When `node packages/control/dist/project-secrets.js` runs from the repository root, it shall make the call of CTRL-RUNTIME-014 for the workspace root and exit 0 when it succeeds, and print the error's message to stderr and exit 1 when it fails (deployment DEPLOY-SECRET-006).
- [x] **CTRL-RUNTIME-016**: Before `ComposeRuntime` runs `start`, `restart` (either form), `consolidate` or `reembed`, and before `StackController.launch` and `rebuild` run `up`, the control plane shall create `data/logs` under the workspace root (`mkdir -p`, as the user running the control plane), so that the directory the `./data/logs` bind mount names (deployment DEPLOY-COMPOSE-029) is the owner's and not created by Compose as root; a failure to create it shall be logged as a warning and shall not stop the command.

## Controller guards and orchestration (CTRL-GUARD)

- [x] **CTRL-GUARD-001**: If `ServiceController` is asked to act on an id that is not in its manifest, then it shall return `refused: "unknown"` without calling the runtime, resetting any group or publishing an audit record. <!-- openspec: service-control § Manifest-only service ids --> <!-- test: packages/control/test/controller.test.ts -->
- [x] **CTRL-GUARD-003**: If an action targets a unit flagged `infra` (`redis`, `postgres`) and `advanced` is not set, then `ServiceController` shall return `refused: "forbidden"` naming `CONTROL_ADVANCED=1`; where `advanced` is set it shall execute the action and shall always use `resume` mode for infra, so no consumer group is reset. <!-- openspec: service-control § Protected services --> <!-- test: packages/control/test/controller.test.ts -->
- [x] **CTRL-GUARD-004**: When a start is requested in `fresh` mode (the caller's `mode`, else the manifest `defaultMode`) for a unit that owns consumer groups, the system shall reset each group to `$` in manifest order and then start the service, and if a reset fails shall not start it and shall return `ok: false` with detail `consumer group reset failed: <reason>`. <!-- openspec: service-control § Start modes (resume vs fresh) --> <!-- test: packages/control/test/controller.test.ts --> <!-- test: packages/control/test/controller.test.ts -->
- [x] **CTRL-GUARD-005**: When a restart is requested in `fresh` mode (for a unit with groups) or with isolation env, the system shall stop the service, reset its groups only after the stop resolved `ok`, and then start it, returning the reset failure without starting if a reset fails; when a restart is requested in `resume` mode without isolation env it shall issue one native runtime restart and leave all groups untouched; a stop shall never reset groups; if the stop step fails, the failure shall be returned without resetting or starting. <!-- openspec: service-control § Start modes (resume vs fresh) --> <!-- test: packages/control/test/controller.test.ts --> <!-- test: packages/control/test/controller.test.ts --> <!-- test: packages/control/test/controller.test.ts --> <!-- test: packages/control/test/controller.test.ts --> <!-- test: packages/control/test/controller.test.ts --> <!-- test: packages/control/test/controller.test.ts -->
- [x] **CTRL-GUARD-006**: Where an action carries `isolated: true` and the unit is not infra, the system shall pass a copy of the unit's manifest `isolatedEnv` to the runtime start, and shall replace a native restart with stop-then-start even when that preset is empty. <!-- test: packages/control/test/controller.test.ts -->
- [x] **CTRL-GUARD-007**: When an action has been executed (not refused), the system shall call the controller's `audit` callback with `service`, `action`, `by`, `ok` and, whenever the runtime returned one (on success as well as failure), `detail`; it shall swallow any error the callback throws, and shall return only `ok` and `detail` to the caller. <!-- openspec: service-control § Lifecycle audit event --> <!-- test: packages/control/test/controller.test.ts --> <!-- test: packages/control/test/controller.test.ts -->
- [x] **CTRL-GUARD-008**: Where an isolated start of a unit is requested, the system shall also start the units named in that unit's manifest `requires` list, transitively (for cortex: salience and affect), and nothing else; a start that is not isolated, and every restart and stop, shall act on the named unit only. Required units start first, depth-first in `requires` order, each once (a unit already in the closure, or the named unit itself, is skipped, so cycles terminate), each with its own isolation preset and its own default mode (a `fresh` unit has its groups reset before its start), and each executed start is audited as its own `service.lifecycle` record. If a required unit fails to start (including a reset failure), the system shall not start the remaining units or the named unit, shall return `ok: false` with a detail naming the failed unit (`required unit <id> failed to start: <reason>`), and shall publish no audit record for the named unit, which was not executed. <!-- openspec: cortex § Isolation preset and closure --> <!-- test: packages/control/test/controller.test.ts --> <!-- test: packages/control/test/controller.test.ts --> <!-- test: packages/control/test/controller.test.ts --> <!-- test: packages/control/test/controller.test.ts --> <!-- test: packages/control/test/controller.test.ts -->

## Stack controller (CTRL-STACK)

- [x] **CTRL-STACK-001**: The system shall run every `StackController` command, and every `ComposeRuntime` command issued by the dashboard or `cohostctl`, through the injected exec with an argv array (no shell) and the workspace root (`findWorkspaceRoot()`, else the process cwd) as the working directory and the process environment as the base environment, except `COHOST_ISOLATION`, which every `docker compose` command sets itself (CTRL-STACK-017). <!-- test: packages/control/test/cli.test.ts --> <!-- test: services/dashboard/test/control.test.ts --> <!-- test: packages/control/test/stack.test.ts -->
- [x] **CTRL-STACK-002**: When `StackController.launch` is called, the system shall report phase `compose-build`, run `docker compose up -d --build --remove-orphans` with a 30 minute timeout (so the images of changed code are rebuilt on every launch), and if that command fails shall resolve `ok: false` with the trimmed stderr (else the error message) cut to 500 characters as `detail`, without polling. <!-- test: packages/control/test/stack.test.ts --> <!-- test: packages/control/test/stack.test.ts -->
- [x] **CTRL-STACK-003**: When `docker compose up` has succeeded during a launch, the system shall report phase `waiting` and run the status probe every 2000 ms until every long-running container present in the status (every listed container except the one-shots `models`, `consolidate` and `reembed`; `consolidate` and `reembed` are profile-gated and not started by `up`) has status `running` and health `healthy` or no healthcheck, and then resolve `ok: true` with the last status as `services`. <!-- test: packages/control/test/stack.test.ts --> <!-- test: packages/control/test/stack.test.ts -->
- [x] **CTRL-STACK-004**: If the long-running containers are not all ready 180 s after `docker compose up` succeeded, or the status probe reports Docker unavailable while waiting, then the launch shall resolve `ok: false` with a `detail` naming each container that is not ready with its status and health (or the probe's detail) and the last status as `services`, and shall stop, remove or restart nothing. <!-- test: packages/control/test/stack.test.ts --> <!-- test: packages/control/test/stack.test.ts -->
- [x] **CTRL-STACK-005**: If, when a launch resolves, the status shows a one-shot container (`models`) exited with a non-zero code, then the system shall append `<service> exited <code>` to the result's `detail` without changing `ok`. <!-- test: packages/control/test/stack.test.ts -->
- [x] **CTRL-STACK-006**: When `StackController.stopAll` is called, the system shall report phase `stopping` and run `docker compose stop` with a 300 s timeout, resolving `ok: true` when it exits 0 and `ok: false` with the stderr detail (cut to 500 characters) otherwise; it shall never run `docker compose down` and never remove containers, networks or volumes. <!-- test: packages/control/test/stack.test.ts -->
- [x] **CTRL-STACK-007**: When `StackController.restartAll` is called with a `ServiceController`, the system shall run the status probe and then, in manifest order, for every manifest unit that has a `pnpmFilter` and whose container the status shows `running`, report phase `restarting <id>` and call the controller's restart for it in its default mode without isolation, continuing after a failure; it shall resolve `ok: true` only when at least one unit was restarted and every restart succeeded, with a `detail` naming each failure, and `ok: false` with detail `no application service is running` when none was running; infrastructure and compose-only units shall not be restarted. <!-- test: packages/control/test/stack.test.ts --> <!-- test: packages/control/test/stack.test.ts --> <!-- test: packages/control/test/stack.test.ts --> <!-- test: packages/control/test/stack.test.ts -->
- [x] **CTRL-STACK-008**: When `StackController.status` is called, the system shall run `docker compose ps --all --format json` with a 10 s timeout and resolve `{docker: {ok: true}, services: [{service, status, health?, exitCode?}]}` from its output, accepting both a JSON array and one JSON object per line; if `docker` is missing, the command fails or times out, or the output does not parse, it shall resolve `{docker: {ok: false, detail}, services: []}` with the stderr or error message cut to 500 characters, and shall never throw. <!-- test: packages/control/test/stack.test.ts --> <!-- test: packages/control/test/stack.test.ts --> <!-- test: packages/control/test/stack.test.ts -->
- [x] **CTRL-STACK-009**: Every `StackController` action shall take no caller input that reaches a command line: the `docker compose` argv of `status`, `launch`, `stopAll` and `consolidate` is fixed, and `restartAll` reaches a command only by selecting manifest entries through `ServiceController`. <!-- test: packages/control/test/stack.test.ts -->
- [x] **CTRL-STACK-010**: `StackController.launch` and `StackController.stopAll` shall act on every Compose service of the stack, infrastructure included, without requiring `CONTROL_ADVANCED`; `restartAll` shall apply the controller's guards to each unit. <!-- test: packages/control/test/stack.test.ts -->
- [x] **CTRL-STACK-011**: When the stack state is derived from a status and the running action (if any), the system shall consider as long-running every container present in the status except the one-shots `models`, `consolidate` and `reembed`, and shall return, in this precedence, `docker-unavailable` when Docker is not available, `stopping` while a stop-all runs, `starting` while a launch runs, `down` when no long-running container is `running`, `up` when every long-running container is `running` with health `healthy` or no healthcheck, `starting` when every long-running container that is not ready is `running` with health `starting`, and `degraded` otherwise. <!-- test: packages/control/test/stack.test.ts -->

- [x] **CTRL-STACK-012**: When `ComposeRuntime` or `StackController` runs a Docker command, the system shall execute `COHOST_DOCKER_BIN` when that variable is set and non-empty, else `docker` when it is found on `PATH`, else `docker.exe` when it is found on `PATH` (the Windows Docker Desktop CLI seen from WSL2), always with the same argv (`compose ...`); if none is found, the status probe shall report Docker unavailable with a detail naming `COHOST_DOCKER_BIN`, and every action shall resolve `ok: false` with that detail without throwing. <!-- test: packages/control/test/runtime.test.ts --> <!-- test: packages/control/test/runtime.test.ts --> <!-- test: packages/control/test/stack.test.ts -->
- [x] **CTRL-STACK-013**: When `StackController.rebuild` is called, the system shall behave exactly as `launch` (the same command, phases `compose-build` and `waiting`, readiness wait, results and one-shot warnings) but report its phases under kind `rebuild`; it is the separate Rebuild action the dashboard (DASH-STACK-008) and `cohostctl rebuild` keep beside Launch. <!-- test: packages/control/test/stack-rebuild.test.ts -->
- [x] **CTRL-STACK-014**: When `StackController.statusWithRestarts` is called, the system shall run the status probe (CTRL-STACK-008), then, when Docker is available, `docker compose ps --all -q` and `docker inspect` with a fixed format (CTRL-STACK-016) over the container ids that output (only ids matching `^[0-9a-f]{12,64}$` reach the argv), and resolve the status with `restartCount` and `overrides` on each container the inspect output names; the inspect output, which holds each container's whole environment, tokens included, shall never be placed in an error detail, a status field or a log line; if either extra command fails the status shall still resolve, without counts; `status` and the launch readiness poll shall not run the extra commands. <!-- test: packages/control/test/stack-rebuild.test.ts -->
- [x] **CTRL-STACK-015**: Where a Docker daemon is reachable, a test shall run `StackController.launch` against a minimal Compose project (one health-checked container), assert it resolves `ok` with that container `running` and `healthy`, run `stopAll` and assert the container is `exited`, and remove the project in a `finally`; where Docker is unavailable the test shall skip. <!-- test: packages/control/test/launch.e2e.test.ts -->
- [x] **CTRL-STACK-016**: When `StackController.statusWithRestarts` runs `docker inspect`, its fixed format shall name each container's Compose service label, restart count and environment entries, and the system shall parse the `COHOST_ISOLATION` entry as a JSON object and keep, as `overrides` on that container's status, only the entries whose name is an isolation-override name of the manifest (CFG-ISO-006) and whose value is non-empty (an empty object when it sets none or the entry is absent), discarding every other environment entry without logging or returning it; if the inspect command fails, or the entry is not a JSON object, the status shall resolve without `overrides`, as without counts. <!-- test: packages/control/test/stack-rebuild.test.ts -->
- [x] **CTRL-STACK-017**: The system shall set `COHOST_ISOLATION` explicitly on every `docker compose` process `StackController` spawns (status, launch, rebuild, stop-all, the restart probes): the empty string, since the stack controller never carries a preset, replacing any value in the process environment, so that neither a `COHOST_ISOLATION` exported in the shell that started the dashboard or `cohostctl` nor a `COHOST_ISOLATION=` line in the project `.env` (which Compose interpolates when the process environment lacks the name) reaches a container; for a Windows `docker.exe` the name is listed in `WSLENV` even though its value is empty, so Windows Compose receives the empty value instead of falling back to `.env`. <!-- test: packages/control/test/stack.test.ts -->
- [x] **CTRL-STACK-018**: Where `COMPOSE_PROFILES` in `.env` names `pocket`, `nemotron` or `kyutai`, `StackController.launch` shall build and start that profile's service with the same `docker compose up -d --build --remove-orphans` command and no added argument, and where it names none of them, shall start none of the three.
- [x] **CTRL-STACK-019**: When `StackController.launch` runs, it shall write the content of `voice.pocket.hf_token` to the file `data/tts-pocket-secret/hf_token` under the workspace root, creating the directory first, before it runs `docker compose up`, and shall leave that file absent when the token is blank, and write no other secret to a file. The token is trimmed, so a whitespace-only token is blank, and the file is written with mode 0600. Where `voice.engine` is `pocket` (the engine whose profile the owner enables in `COMPOSE_PROFILES`; the variable itself is not read, CFG-ENV-012), a failure to create the directory or write the file fails Launch before `docker compose up`. A configuration that cannot be read, and a write failure under any other engine, is reported as a warning in the launch result, and Launch proceeds without a token file.

## Lifecycle lock (CTRL-LOCK)

- [x] **CTRL-LOCK-001**: When `LifecycleLock.tryAcquire(action)` is called, the system shall create `<workspace root>/data/control.lock` (the directory created when missing) exclusively, write `{pid, by, action, startedAt}` into it, and resolve `{ok: true, release}`; `release` shall remove the file only while it still names this holder and shall be idempotent. <!-- test: packages/control/test/lock.test.ts -->
- [x] **CTRL-LOCK-002**: If the lock file exists and names a live process, then `tryAcquire` shall resolve `{ok: false, holder, detail}` without touching the file, where `detail` is `busy: <action> held by <by> (pid <pid>)`; a pid that exists but cannot be signalled (`EPERM`) counts as live. <!-- test: packages/control/test/lock.test.ts -->
- [x] **CTRL-LOCK-003**: If the lock file names a pid that no longer exists, or its content does not parse, then `tryAcquire` shall remove it and acquire the lock, so a crashed holder never blocks later actions. <!-- test: packages/control/test/lock.test.ts -->
- [x] **CTRL-LOCK-004**: When `cohostctl` runs `start`, `stop`, `restart`, `consolidate`, `reembed`, `launch`, `rebuild`, `stop-all` or `restart-all`, the system shall hold the lifecycle lock for the whole command and release it when the command ends, however it ends; if the lock is refused, it shall run nothing, print `refused: <detail>` (the lock's `busy: <action> held by <by> (pid <pid>)`) and exit 1. `status` takes no lock. <!-- test: packages/control/test/cli-main.test.ts -->

## Config gate (CTRL-GATE)

- [ ] **CTRL-GATE-001**: When `configRefusal(check = checkConfig)` is called, the system shall return undefined when `check` returns no problem, and otherwise the text `the config is invalid (<n> problem(s); first: <path>): fix it on the dashboard's config recovery screen (mise run dashboard), then try again`, `<path>` being the first problem's path, or its file when the path is empty; a failure `check` throws shall propagate.

## Heartbeat contract (CTRL-HEARTBEAT)

The heartbeat publisher lives in `@cohost/shared`, and its mechanics are shared-runtime SHARED-LIFE-006 to SHARED-LIFE-014. What the published states mean to an observer stays in this segment, under Health derivation.

## Health derivation (CTRL-HEALTH)
