# event-bus

Status: AUDITED 2026-11-14 at git `4319d8d`. Parent: [high-level-design](../../high-level-design.md). Specs: [event-bus-specs.md](event-bus-specs.md). Arrow: [docs/arrows/event-bus.md](../../arrows/event-bus.md).

## Context and Design Philosophy

`@cohost/bus` (`packages/bus`) is the only channel between cohost services. The header of `packages/bus/src/events.ts` says so directly: services "only ever talk through these events - never directly to each other - so any piece can be swapped". The package has two jobs:

1. A **schema registry** (`events.ts`): one zod schema per event type, plus the derived TypeScript types (`EventType`, `EventData`, `EventInput`, `BusEvent`) and `EVENT_TYPES`.
2. A **thin typed wrapper over two Redis Streams** (`index.ts`): `cohost:events` for domain events and `cohost:health` for heartbeats. Publish is validate-then-`XADD`; subscribe is a consumer-group loop; `tail` / `recent` are non-group reads for the dashboard.

The process-lifecycle helpers (`onShutdown`, `beforeShutdown`, `startHeartbeat`) are not part of this package: they live in `@cohost/shared` ([shared-runtime](../shared-runtime/shared-runtime-design.md)).

Guiding principles visible in the code:

- Validate on both sides. `publish` parses against `EventPayloads[type]` before writing; `decode` parses again on every read. Malformed entries are dropped rather than delivered.
- Keep services decoupled from Redis. Region logic depends on `Publisher = Pick<Bus, "publish">` so tests can pass a recorder (see [Test double](#test-double-packagestestingsrcindexts)).
- Heartbeats must not evict domain events, so they have their own capped stream (`HEALTH_STREAM`, `HEALTH_MAXLEN`).
- Binary payloads never ride the stream. The browser avatar driver's frames, high-rate but not binary, ride a capped stream of their own, `<prefix>:avatar.frames` ([Avatar frames](#avatar-frames)). Live connector audio rides its own capped streams, `<prefix>:audio.in.<source>` and `<prefix>:audio.out.<sink>`, with registrations in keys `<prefix>:connector:<id>`; both are specified by [connections](../connections/connections-design.md) and use the prefix of BUS-STREAM-008. `inject.request` carries an `uploadId`; the bytes sit in the Redis key `cohost:upload:<id>` (`Bus.putUpload` / `Bus.takeUpload`, BUS-UPL-001 to BUS-UPL-003), outside the stream.

Scope of this segment: the Cargo workspace at the repository root (`Cargo.toml`, `crates/cohost-bus`, `crates/cohost-bus-node`), the contract fixtures under `packages/bus/fixtures/contract/`, `packages/bus/src/index.ts`, `packages/bus/src/native.ts`, `packages/bus/src/transport.ts`, `packages/bus/src/frames.ts`, `packages/bus/src/avatar-frame.ts`, `packages/bus/src/events.ts`, `packages/bus/src/connector.ts`, `packages/bus/src/registrar.ts`, `packages/bus/test/`, `packages/bus/package.json`, `packages/bus/tsconfig.json`, and (documented here because it is the test double for `Bus`) `packages/testing/src/index.ts`. `startHeartbeat` and the `service.heartbeat` / `service.lifecycle` semantics belong to [shared-runtime](../shared-runtime/shared-runtime-design.md) and [control-plane](../control-plane/control-plane-design.md); this document records only their schemas and the `Bus` methods that carry them.

## Stream layout and envelope

| Stream | Constant | Trim | Carries |
|---|---|---|---|
| `cohost:events` | `STREAM` | `MAXLEN ~ 20000` | every event type except `service.heartbeat` |
| `cohost:health` | `HEALTH_STREAM` | `MAXLEN ~ 1000` (`HEALTH_MAXLEN`) | `service.heartbeat` only |
| `<prefix>:avatar.frames` | `avatarFramesStream()` | the producer's `XADD MAXLEN ~ 120` (`AVATAR_FRAMES_MAXLEN`) and `PEXPIRE 10000` (`AVATAR_FRAMES_TTL_MS`) | the browser avatar driver's frames only ([Avatar frames](#avatar-frames)); not an event stream: no envelope, no consumer group |

The two event streams use the same entry fields (the avatar-frame stream below has its own, `ts` and `data`): `type`, `ts` (`String(Date.now())`, publisher clock), `source` (the `Bus` constructor's first argument, usually the service name), `data` (`JSON.stringify` of the zod-parsed payload). The Redis stream id is the event id. `decode` rebuilds a `BusEvent`: `{ id, type, ts: Number(m.ts ?? 0), source: m.source ?? "?", data }` and returns `undefined` for an unknown type, non-JSON `data`, or a schema failure.

Typing detail: `publish` accepts `EventInput<T>` (`z.input`, defaults optional), subscribers receive `EventData<T>` (`z.infer`, defaults applied). So `chat.message` published without `isMod` is stored and delivered with `isMod: false`.

## Bus API

Constructor: `new Bus(source, log?, url = urls.redis(), options?)`. The optional `BusOptions` object supplies a transport factory for the events path (`transport`, default the native transport of [Native transport](#native-transport)), a frame transport factory for the frames path (`frames`, default the ioredis frame transport of [Frames path](#frames-path)), the retry delay base and cap (`retryBaseMs` 250, `retryMaxMs` 30000), `streamPrefix` (default `cohost`: the instance uses `<prefix>:events` and `<prefix>:health`, BUS-STREAM-008, so a test works on streams of its own) and `failFast` (BUS-STREAM-009); tests pass a fake `BusTransport` through `transport` and a fake `FrameTransport` through `frames` so the subscribe, tail, publish and frame paths run without a Redis server. `urls.redis()` is `REDIS_URL` or `redis://127.0.0.1:6379` (`packages/config/src/index.ts`). The transport opens its shared connection when the `Bus` is constructed; each `subscribe`, `tail` and `tailHealth` opens a reader with a connection of its own, because a blocking read occupies its connection. The frame transport opens its publish connection at the first `publishFrame` or `publishAvatarFrame`, and each `tailAudio` and `tailAvatarFrames` opens a frame reader with a connection of its own. `consumer` is `${HOSTNAME ?? "local"}-<8 hex of a random uuid>`, fixed for the life of the `Bus` instance.

| Method | Behavior |
|---|---|
| `publish(type, data)` | throws for `service.heartbeat`; zod-parses; `XADD cohost:events MAXLEN ~ 20000`; returns stream id; debug log; an `XADD` rejection is logged at warn (`{ err, type }`, `publish failed`) and rethrown unchanged (BUS-STREAM-007) |
| `publishHealth(data)` | zod-parses as `service.heartbeat`; `XADD cohost:health MAXLEN ~ 1000`; returns id; a rejection is logged and rethrown the same way |
| `subscribe(opts, handler)` | consumer-group loop (below); resolves only after `stop()` |
| `tail(handler, fromId="$")` | non-group `XREAD COUNT 100 BLOCK 5000` loop on `cohost:events`; no ack, no replay |
| `tailHealth(handler, fromId="$")` | same loop on `cohost:health`; only `service.heartbeat` entries reach the handler |
| `recent(count=100)` | `XREVRANGE + - COUNT n`, decoded, undecodable entries filtered, reversed to oldest-first |
| `recentHealth(count=100)` | same on `cohost:health` |
| `resetGroup(group)` | `XGROUP CREATE cohost:events group $ MKSTREAM` first (creates a missing stream and group; works on a fresh Redis 8, where `SETID` on a missing key fails with `requires the key to exist`); on `BUSYGROUP` (group exists, including a concurrent create) `XGROUP SETID cohost:events group $`; rethrow anything else |
| `stop()` | sets the instance-wide `stopped` flag, wakes any retry backoff sleep, closes the events transport (flushing queued acks for at most 2 s) and the frame transport, and returns a `Promise<void>` that resolves once both have closed (BUS-STOP-001) |

### Consumer-group subscription loop

`SubscribeOptions`: `group` (one per service), `types?` (client-side filter), `start` (`SubscribeStart`, `"latest"` or `"resume"`; required), `blockMs?` (default 5000), `onReady?` (called once after the group is created or positioned and before the first read; BUS-SUB-012).

**Start mode.** Every subscription names where it starts reading after a process start (BUS-SUB-011):

- `latest`: the group is moved to the newest entry (`$`) on every start, so a restarted subscriber never acts on events published while it was down (BUS-SUB-010). Used by every subscribing service except memory: a co-host that speaks, reacts or animates must not replay stale chat, focus or speech lines after a restart.
- `resume`: an existing group keeps its stored position, so the backlog still held by the 20000-entry stream is delivered after a restart (BUS-SUB-002). Used by memory, which wants to store what it missed.
- In either mode a missing group is created at `$` (BUS-SUB-001); a first-ever start never replays the stream.

`Bus.resetGroup` remains the separate path a control-plane `fresh` start uses to move a group to `$` from outside the service.

Loop:

1. Create the group with `XGROUP CREATE cohost:events <group> $ MKSTREAM`. On `BUSYGROUP`, `latest` runs `XGROUP SETID cohost:events <group> $` and `resume` leaves the stored position; any other error rejects `subscribe` (BUS-SUB-001), so a Redis outage at subscribe time still rejects the promise. Retry covers the read loop only.
2. Read loop: starts with cursor `"0"` (this consumer's pending entries) and drains them batch by batch: after each entry the cursor moves to that entry's id, so the next read returns the entries after it, until a read returns none, and then it switches to `">"` (new entries) (BUS-SUB-003). An entry whose `XACK` Redis refused stays pending but is not read again by the same drain, so the drain always ends; a later drain delivers it at most once more, and drops it if that ack is refused too (BUS-SUB-008, BUS-NAT-ACK-008). Batches are `COUNT 50` with `BLOCK blockMs`. If `stop()` lands while a handler runs, the handler finishes, the entry is not acked and the rest of the batch is neither handled nor acked (BUS-SUB-013).
3. For each entry: `decode`; if it decodes and passes the `types` filter, `await handler(ev)` inside try/catch (error logged as `"handler failed"`); then `XACK` regardless of filter result, decode failure, or handler failure; a refused `XACK` is logged at warn (`ack failed`) and not retried; the loop moves on, and the entry, still pending, is delivered again only by a later drain, and only once: if the ack of that redelivery is refused as well, the entry is logged as dropped and never delivered again (BUS-SUB-008, BUS-SUB-009, BUS-NAT-ACK-008). Handlers therefore run strictly one at a time per subscription, and failed events are dropped with no retry or dead-letter.
4. A read error while `stopped` breaks the loop quietly. Any other read error is logged at warn (`{ err, delayMs, failures }`) and the read retried after `min(cap, base * 2^(failures-1))` ms (base 250, cap 30000 by default; the failure count resets after a successful read), so a Redis outage never ends the subscription and never rejects the `subscribe` promise (BUS-SUB-009). The sleep ends as soon as `stop()` is called.

**Delivery is at most once, with one exception** (BUS-SUB-008). Handler failures are acknowledged, and an entry read but not acknowledged by a process that then dies is not redelivered to its successor: each `Bus` instance reads under its own consumer name and nothing claims another consumer's pending entries. Within one process an entry whose handler has run is not delivered again, except an entry whose acknowledgement Redis refused: it stays in this consumer's pending list, and the next drain (after a later read failure, [Errors, reconnect and backoff](#errors-reconnect-and-backoff)) delivers it once more. The subscription records each id whose ack was refused. If the ack of the redelivery is refused again, the facade logs `ack failed, entry dropped` at warn and moves the id to a dropped set; a later drain that reads a dropped entry neither hands it to the handler nor queues its ack, so the entry is delivered at most twice in all and stays pending under this consumer (BUS-NAT-ACK-008). A refused ack is rare (the group was destroyed, for example, in which case the read fails too), so both records stay small; they live as long as the subscription. The pending drain only matters within one process lifetime; it is not crash recovery.

### Health-stream methods

`publishHealth`, `tailHealth` and `recentHealth` exist because `publish("service.heartbeat", ...)` throws `service.heartbeat goes on the health stream: use publishHealth()`. `tailHealth` and `recentHealth` are used by the dashboard feed (`services/dashboard/src/feed.ts`) and by control-plane's CLI and healthcheck (`packages/control/src/cli.ts`, `packages/control/src/healthcheck.ts`). `resetGroup` is used by the service controller for "fresh" starts (`packages/control/src/controller.ts`). This segment owns the heartbeat transport (BUS-STREAM-004, BUS-HEALTH-001 to 004); what a heartbeat means and how it is consumed is [control-plane](../control-plane/control-plane-design.md)'s.

`tail` and `tailHealth` follow the same failure rule as `subscribe`: a non-stop read error is logged at warn and retried with the same capped, growing delay from the last delivered id, never rejecting the promise (BUS-TAIL-003), and a handler that throws is logged at error (`handler failed`) and the loop continues with the next entry (BUS-TAIL-004). A caller that must know whether Redis answers (the dashboard feed's bus reachability) passes an optional `onRead` callback as the third argument of either method; it hears every read's outcome, success or error (BUS-TAIL-005), so the tail loops stay the one place that reads the stream.

### Process shutdown

The process shutdown sequence (`onShutdown`, `beforeShutdown`, the heartbeat's `stopping` hook) is specified and implemented by [shared-runtime](../shared-runtime/shared-runtime-design.md) (SHARED-LIFE-001 to SHARED-LIFE-005, `packages/shared/src/lifecycle.ts`). This package keeps `Bus.stop()` (BUS-STOP-001), which that sequence awaits (SHARED-BOOT-005).

## Native transport

The bus client's events path is native code, so the central highway has headroom as sources and services grow (HLD, Native layer). Rust owns the Redis I/O of the events path; the TypeScript `Bus` facade keeps the public API, the zod registry, validation on publish and on read, and every loop's control flow (start modes, drain, backoff, stop). The facade has two paths, split by the HLD's one-language-per-service tenet (tenet 12), which applies its coarse-boundary gate to native code this project writes:

- **Events path**: `publish`, `publishHealth`, `subscribe` and its acks, `tail`, `tailHealth`, `recent`, `recentHealth`, `resetGroup`, `serverTime`, `putUpload`, `takeUpload`, `putTimer`, `deleteTimer`, `listTimers` and the registration calls. It always runs on a `BusTransport`, which in production is the native binding. One call carries a whole batch or one command, so the boundary is crossed once per batch.
- **Frames path**: `publishFrame` and `tailAudio` on `<prefix>:audio.in.<tag>` and `<prefix>:audio.out.<tag>`, and `publishAvatarFrame` and `tailAvatarFrames` on `<prefix>:avatar.frames`. It runs on a `FrameTransport`, which in production is TypeScript on ioredis ([Frames path](#frames-path)), and never crosses into the addon: a frame is small and frequent, and the measurement gate showed that one napi crossing per frame costs more than native Redis I/O saves ([Measurement gate](#measurement-gate)). Frames move to `crates/cohost-bus` when connector-discord, ears and mouth are Rust services, which link the crate directly, and the crate gains its frame codec, tag grammar, constants and audio names then ([Deferred](#deferred)).

### Architecture

```
services (TS) ──> @cohost/bus  Bus facade (TS: zod, envelope, loops, backoff, logging)
                      │  events path: BusTransport interface
                      ├── native binding  packages/bus/src/native.ts ──> cohost-bus.linux-x64-gnu.node
                      │                                                   crates/cohost-bus-node (napi-rs, thin)
                      │                                                   crates/cohost-bus (pure Rust: redis-rs + tokio)
                      ├── test fakes (scripted BusTransport)
                      │  frames path: FrameTransport interface
                      ├── ioredis frame transport  packages/bus/src/frames.ts (audio stream names; frame
                      │                                                       codec, tag grammar in connector.ts)
                      └── test fakes (scripted FrameTransport)
Rust services ──────────────────────────────────────────────────────────> crates/cohost-bus directly (events path;
                                                                            frames path deferred)
```

- **Cargo workspace** at the repository root (`Cargo.toml` with `members = ["crates/*"]`, one `Cargo.lock`, a `rust-toolchain.toml` pinning an exact stable toolchain version with the `rustfmt` and `clippy` components; mise installs it on the host and in the Docker build stages).
- **`crates/cohost-bus`**: pure Rust, no Node dependency. For the events path it owns the Redis connections (one shared multiplexed connection plus one dedicated connection per reader), every Redis command the addon issues, ack batching, the names of the keys and streams it uses under the prefix (BUS-STREAM-008) and the events stream caps. For Rust services it also holds the typed codec of the events they touch, held to the contract fixtures ([Rust service codec and contract fixtures](#rust-service-codec-and-contract-fixtures)). It does not carry the audio frame codec, tag grammar, audio stream naming or the avatar-frame stream and exports no connector protocol constants; those are TypeScript until a Rust service needs them ([Deferred](#deferred)). The one protocol value it holds is a private registration version (1), which its registration codec checks the value's `v` against (BUS-NAT-RS-004). A Rust service depends on it directly, with no Node in between. It never logs: every failure is returned to the caller as an error value.
- **`crates/cohost-bus-node`**: the napi-rs wrapper. It converts arguments and results, maps errors to JS errors with a `code`, and holds no logic of its own; anything it does that a Rust service would also need belongs in `cohost-bus`.
- **`packages/bus/src/native.ts`**: loads the `.node` file and adapts it to `BusTransport`. It is the only TypeScript file that imports the addon.
- **`packages/bus/src/frames.ts`**: the ioredis `FrameTransport` of the frames path and the stream naming (`audioStreamName`, which `Bus.audioStream` returns, and `avatarFramesStream`), and the only TypeScript file that imports ioredis. It encodes and decodes with the TypeScript frame codec of `connector.ts`.
- **The `Bus` facade** (`packages/bus/src/index.ts`) keeps every behaviour this document specifies above: what is validated, the envelope fields and their values (`ts` is the publisher's `Date.now()`), what is delivered, acked, logged and retried. It decides; the transport executes.

### Facade public API

The transport is invisible to callers. `@cohost/bus` exports, with the behaviour this document specifies:

- `class Bus`: `constructor(source, log?, url?, options?)`, `consumer`, `publish`, `publishHealth`, `subscribe`, `tail`, `tailHealth`, `recent`, `recentHealth`, `resetGroup`, `serverTime`, `putUpload`, `takeUpload`, `putTimer`, `deleteTimer`, `listTimers`, `connectorKey`, `audioStream`, `writeRegistration`, `readRegistration`, `deleteRegistration`, `listConnectors`, `publishFrame`, `tailAudio`, `avatarFramesStream`, `publishAvatarFrame`, `tailAvatarFrames`, `stop`.
- Types and constants of `index.ts`: `STREAM`, `HEALTH_STREAM`, `HEALTH_MAXLEN`, `SubscribeStart`, `SubscribeOptions`, `Handler`, `Publisher`, `ReadOutcome`, `HeartbeatEvent`, `BusOptions`.
- `BusTransport`, `BusReader`, `TransportFactory`, `FrameTransport`, `FrameReader` and `FrameTransportFactory`.
- Everything exported from `events.ts` (the registry), `connector.ts` and `registrar.ts` (see [Wire conventions](#wire-conventions)).

The test seams are `BusOptions.transport` with the `BusTransport` type for the events path and `BusOptions.frames` with the `FrameTransport` type for the frames path; there is no connection-level seam. The `publish` and `subscribe` call sites, `FakeBus`, `ConnectorFakeBus` and every `Pick<Bus, ...>` consumer depend only on this API, not on the transport.

### The `BusTransport` interface

The seam between the facade and native code on the events path. It is named `BusTransport` because `connector.ts` already exports `Transport` (a capability's `stream` / `http` transport, CONN-DESK-003). Every method maps to a fixed set of Redis commands; the transport adds no retries of its own, so the facade's backoff is the only retry policy.

```ts
type EventStream = "events" | "health";
/** The four envelope fields as stored (BUS-STREAM-001). */
interface EntryFields { type: string; ts: string; source: string; data: string }
/** One entry as read. Only the four envelope fields are returned; a missing field is undefined.
 *  A pending entry whose stream entry was trimmed, and an entry with an envelope field that is
 *  not valid UTF-8, come back with no fields. */
interface RawEntry { id: string; type?: string; ts?: string; source?: string; data?: string }
interface AckError { ids: string[]; err: Error }
/** `entries` is null when the block timed out with nothing to read. */
interface GroupRead { entries: RawEntry[] | null; ackErrors: AckError[] }

interface BusTransport {
  /** XADD <prefix>:<stream> MAXLEN ~ 20000 (events) | 1000 (health) * type ts source data. Resolves to the id. */
  append(stream: EventStream, fields: EntryFields): Promise<string>;
  /** XREVRANGE <prefix>:<stream> + - COUNT n, returned oldest first. */
  recent(stream: EventStream, count: number): Promise<RawEntry[]>;
  /** XGROUP CREATE <prefix>:events <group> $ MKSTREAM. true: created; false: BUSYGROUP; any other error rejects. */
  createGroup(group: string): Promise<boolean>;
  /** XGROUP SETID <prefix>:events <group> $. */
  moveGroupToLatest(group: string): Promise<void>;
  /** SET <prefix>:upload:<id> <bytes> PX ttlMs (BUS-UPL-001). */
  putUpload(id: string, bytes: Buffer, ttlMs: number): Promise<void>;
  /** GETDEL <prefix>:upload:<id> (BUS-UPL-002). */
  takeUpload(id: string): Promise<Buffer | null>;
  /** HSET <prefix>:tools:timers <id> <json>; HDEL <prefix>:tools:timers <id>; HGETALL <prefix>:tools:timers (the tools service's pending timers). */
  putTimer(id: string, json: string): Promise<void>;
  deleteTimer(id: string): Promise<void>;
  listTimers(): Promise<{ id: string; json: string }[]>;
  /** SET <prefix>:connector:<id> <json> PX leaseMs (CONN-REG-001). */
  writeRegistration(id: string, json: string, leaseMs: number): Promise<void>;
  /** GET <prefix>:connector:<id>. */
  readRegistration(id: string): Promise<string | null>;
  /** DEL <prefix>:connector:<id> (CONN-REG-003). */
  deleteRegistration(id: string): Promise<void>;
  /** SCAN MATCH <prefix>:connector:* COUNT 100 to cursor 0, de-duplicated, then one MGET; values that exist (CONN-REG-006). */
  listRegistrations(): Promise<string[]>;
  /** TIME, as epoch ms (CTRL-CHECK-004). */
  serverTime(): Promise<number>;
  /** A reader with its own connection, for one blocking loop. */
  openReader(): BusReader;
  /** Send every reader's queued acks on the shared connection in one pipeline (nothing when none are queued), then
   *  close the shared connection and every reader; blocked reads reject with BUS_CLOSED. The flush is abandoned after
   *  2000 ms. Never rejects: a failed or abandoned flush is not retried. A second close() resolves when the first has.
   *  Every other method called afterwards rejects with BUS_CLOSED. */
  close(): Promise<void>;
}

interface BusReader {
  /** Sends the queued acks of this reader, then XREADGROUP GROUP <group> <consumer> COUNT n BLOCK ms STREAMS <prefix>:events <cursor>,
   *  in one pipeline. `ackErrors` reports queued acks that Redis refused; when the read of the same pipeline is itself refused, the rejection's error carries them as its own `ackErrors` (BUS-NAT-ACK-009). */
  readGroup(group: string, consumer: string, cursor: string, count: number, blockMs: number): Promise<GroupRead>;
  /** Queue XACK <prefix>:events <group> <id>; synchronous, sent with the next readGroup or by the transport's close(). */
  ack(group: string, id: string): void;
  /** XREAD COUNT n BLOCK ms STREAMS <prefix>:<stream> <fromId>. null on timeout. */
  read(stream: EventStream, fromId: string, count: number, blockMs: number): Promise<RawEntry[] | null>;
  /** Close this reader's connection, dropping its queued acks; a blocked read rejects with BUS_CLOSED. */
  close(): void;
}

type TransportFactory = (url: string, opts: { prefix: string; failFast: boolean }) => BusTransport;
```

The facade maps onto it one to one: `publish` and `publishHealth` are `append`; `subscribe` is `createGroup` (then `moveGroupToLatest` for `latest` on `false`), `onReady`, and a loop of `readGroup` / handler / `ack`; `resetGroup` is `createGroup` then `moveGroupToLatest` on `false`; `tail` and `tailHealth` are loops of `read`; `recent` and `recentHealth` are `recent` plus `decode`; `stop()` sets `stopped`, wakes the backoff sleeps and awaits `close()` of both transports, so it returns `Promise<void>`, which the process shutdown sequence awaits. `decode` (BUS-STREAM-006, BUS-SUB-007) stays in the facade and works on `RawEntry`.

Test fakes implement `BusTransport` directly: a resilience test scripts what `readGroup` resolves or rejects with, at the level the facade decides on.

### Frames path

The frames path is TypeScript end to end: the facade's `publishFrame`, `tailAudio`, `publishAvatarFrame` and `tailAvatarFrames`, the frame codec, tag grammar and protocol constants of `connector.ts`, and the ioredis `FrameTransport` and audio stream naming of `packages/bus/src/frames.ts`. It implements the connector protocol's audio streams (connections CONN-AUD-*, CONN-BP-*) and the avatar-frame stream ([Avatar frames](#avatar-frames)), and never calls the addon.

```ts
type AudioDirection = "in" | "out";
interface FrameEntry { id: string; decoded: DecodedFrame }

interface FrameTransport {
  /** XADD <prefix>:audio.<dir>.<tag> MAXLEN ~ AUDIO_MAXLEN[dir] * <encodeFrame(frame)> and PEXPIRE <stream> 60000,
   *  in one pipeline on the frames publish connection (CONN-AUD-001). Resolves to the id. */
  appendFrame(dir: AudioDirection, tag: string, frame: Frame): Promise<string>;
  /** A frame reader with its own connection, opened at its first readFrames, for one tailAudio loop. */
  openReader(): FrameReader;
  /** Disconnect the publish connection, if one was opened, and every reader; a blocked read rejects. */
  close(): Promise<void>;
}

interface FrameReader {
  /** XREAD COUNT n BLOCK ms STREAMS <prefix>:audio.<dir>.<tag> <fromId>, each entry decoded by decodeFrame (never throws,
   *  CONN-BP-006). null on timeout. */
  readFrames(dir: AudioDirection, tag: string, fromId: string, count: number, blockMs: number): Promise<FrameEntry[] | null>;
  /** Disconnect this reader; a blocked read rejects. */
  close(): void;
}

type FrameTransportFactory = (url: string, opts: { prefix: string; failFast: boolean }) => FrameTransport;
```

- **Validation before the transport.** `publishFrame` checks the frame with the TypeScript codec first: a `pcm` longer than `MAX_FRAME_BYTES` or with an odd byte count rejects with an `Error` whose `code` is `BUS_INVALID`, and nothing is written (BUS-NAT-FRM-001, BUS-NAT-FRM-002; CONN-AUD-002). Otherwise it calls `appendFrame`.
- **Connections.** The factory is called once, when the `Bus` is constructed, and opens nothing. The publish connection opens at the first `appendFrame` or `appendAvatarFrame`, so a `Bus` that never publishes a frame (every service except mouth, the connectors and avatar with the browser driver) holds no frames connection. Each `tailAudio` opens a reader with its own connection, because a blocking `XREAD` occupies it; `openReader` opens nothing, and the reader connects at its first `readFrames`, so a loop stopped before its first read never opens a socket, matching the publish connection's connect-on-first-use. Frames from one `Bus` go out on one connection in call order, so a producer's `seq` stays in order in the stream (BUS-NAT-FRM-005).
- **Outage.** The publish connection follows the shared connection's rule ([Errors, reconnect and backoff](#errors-reconnect-and-backoff)): the first `appendFrame` waits for the connection's first connect attempt (at most the 10 s connect timeout) and then writes or rejects; after that, while the connection is down, `appendFrame` rejects at once and nothing is queued (ioredis's offline queue is off), while ioredis reconnects in the background with the same capped delay, 250 ms doubling to 30 s (BUS-NAT-FRM-006). A frame that cannot go out now is stale by the time Redis returns, and a queue would hold audio outside the stream's cap (CONN-BP-001). A reader keeps ioredis's reconnect with `maxRetriesPerRequest: null`: a blocked read waits for the reconnect instead of failing, and resumes from the last id it read. A read that does reject goes through the facade's backoff and `onRead` like every read loop (BUS-NAT-CONN-002). With `failFast` neither connection reconnects and neither prints anything.
- **Errors.** The frame transport rejects with the codes of the events path, in the same meanings: `BUS_REDIS` when Redis answered with an error (the message is Redis's text), `BUS_CONNECTION` for a connection that could not be opened, failed or was closed by the peer (the message names the cause; ioredis reports a lost connection only as closed, so the last connect error it emitted is used), and `BUS_CLOSED` after `close()` (BUS-NAT-FRM-008, BUS-NAT-ERR-005).
- **Loop.** `tailAudio` is a loop of `readFrames` from `$` with `COUNT 100 BLOCK 5000`, advancing from the last id read, handing each `DecodedFrame` to the handler under the facade's guard (CONN-BP-002, BUS-NAT-FRM-004). `stop()` closes the frame transport with the events transport; a read that rejects after `stop()` ends its loop quietly (BUS-NAT-ERR-004), and a frame published after it rejects with `BUS_CLOSED` (BUS-NAT-ERR-005).
- **Buffers.** `pcm` is a Node `Buffer` both ways. ioredis keeps a reference to the caller's `Buffer` until the command is written to the socket, so a producer must not change a frame's `pcm` after passing it to `publishFrame`; every producer builds a fresh `Buffer` per frame (mouth slices a newly converted line, the Discord connector a newly decoded packet). A `Buffer` a read returns belongs to the caller.

### Avatar frames

The browser avatar driver writes the avatar Engine's frames to one more stream on the frames path, `<prefix>:avatar.frames` (the prefix of BUS-STREAM-008), so the dashboard can relay them to the renderer page without the avatar service opening a port ([avatar](../avatar/avatar-design.md) browser; [dashboard](../dashboard/dashboard-design.md) The relay). The stream is outside `cohost:events`: at the frame rate of `avatar.fps` (30 by default) it would turn over the 20 000-entry event stream in minutes, and nothing that replays or audits events wants it.

```ts
/** One entry of <prefix>:avatar.frames (decoded). Numbers are finite and within the ranges of avatar.state. */
interface AvatarFrame {
  mouthOpen: number; mouthSmile: number;   // 0..1
  headX: number; headY: number; headZ: number;  // degrees, -90..90
  eyeX: number; eyeY: number;       // -1..1
  blink: number;                    // 0 open .. 1 closed
  emotion: Emotion; intensity: number;     // intensity 0..1
  expression: string;               // a VRM expression name, or "" for none; at most 64 characters
}
interface AvatarFrameEntry { id: string; frame: AvatarFrame }

// On FrameTransport:
//   appendAvatarFrame(frame: AvatarFrame): Promise<string>;
//     XADD <prefix>:avatar.frames MAXLEN ~ 120 * ts <ms> data <json> and PEXPIRE <stream> 10000, in one pipeline on the
//     frames publish connection. Resolves to the id.
// On FrameReader:
//   readAvatarFrames(fromId: string, blockMs: number): Promise<AvatarFrameEntry[] | null>;
//     XREAD COUNT 100 BLOCK ms STREAMS <prefix>:avatar.frames <fromId>, each entry decoded by decodeAvatarFrame
//     (never throws; an entry that does not decode is dropped). null on timeout.
```

- **Encoding.** Each entry has two fields: `ts`, the producer's `Date.now()` as a string (for logs; nothing computes from it), and `data`, the JSON of the frame. The frame is text and about 230 bytes with its numbers rounded to three decimals, so the HLD's rule that binary payloads stay off the event stream does not apply and no codec is needed beyond `JSON`. `AvatarFrameSchema` (zod, in `avatar-frame.ts`, exported from `@cohost/bus`) validates a frame: `publishAvatarFrame` parses before the transport and rejects a frame outside the ranges with `BUS_INVALID`, writing nothing, and `decodeAvatarFrame` parses on read, so a malformed entry is dropped, as `decode` drops a malformed event. The ranges are those of `avatar.state` (BUS-EVT-018), so the two cannot disagree about what a parameter may be.
- **Name, cap and expiry.** `avatarFramesStream()` returns `<prefix>:avatar.frames`. The producer trims on every write, `MAXLEN ~ 120`, about four seconds at 30 fps and two at 60, and renews a 10 s expiry (`PEXPIRE`) in the same pipeline, so a stream whose producer has stopped disappears from Redis within 10 s. Nothing else trims, expires or deletes it: a reader never writes. The cap is a memory bound, not a replay window: a frame is a whole snapshot, so no reader needs history.
- **Reading.** `tailAvatarFrames(handler)` is a loop of `readAvatarFrames` from `$` with `COUNT 100 BLOCK 5000`, advancing from the last id read, and hands the handler the entries of each read in order, returning a function that ends the loop and closes its reader connection. `readAvatarFrames` drops undecodable entries inside the call and keeps reading until it has a frame or the block time ends; a call that only skipped entries and timed out returns null, and the caller's cursor does not advance. `decodeAvatarFrame` takes the entry's field list, as `decodeFrame` does. `tailAvatarFrames` calls its handler once per decoded frame, and it returns its stop function synchronously (so a consumer that needs frames only while someone watches can stop reading); the relay uses only the last of a batch, because a newer frame replaces an older one entirely. A reader never replays: a consumer that starts, and a loop that read again after a failure, reads from the next entry (`$`), because an entry written during a failure is stale by the time Redis returns. A failed read is logged once and retried with the backoff of the other loops (250 ms doubling to 30 s). Each loop opens a reader connection of its own, at its first read, and `stop()` closes it (BUS-NAT-FRM-004, BUS-NAT-ERR-004 apply as for `tailAudio`).
- **Connections, outage and errors.** As the audio frames: the publish connection opens at the first `publishAvatarFrame`, so only a `Bus` that writes avatar frames (the avatar service with the browser driver) holds one; during an outage `appendAvatarFrame` rejects at once and nothing is queued, because a frame is stale by the time Redis returns; the codes are `BUS_REDIS`, `BUS_CONNECTION`, `BUS_CLOSED` and, for a frame the schema refuses, `BUS_INVALID`. Frames from one `Bus` go out on one connection in call order. The producer may not change a frame object after passing it; it builds a fresh one per frame.
- **Not on the native path.** Like the audio frames, the avatar frames never cross into the addon: one napi crossing per frame costs more than native Redis I/O saves at these sizes, and tenet 12 allows no per-frame crossing of project-written native code without a passing gate ([Measurement gate](#measurement-gate)). The stream name is TypeScript (`frames.ts`); `crates/cohost-bus` carries no copy.

### Crossing the napi boundary

- **Async methods.** Every I/O method of the binding returns a Promise, resolved from a Rust future on the addon's tokio runtime. One runtime per process, created when the addon is first loaded, with a small fixed worker count (one worker unless the measurement gate shows that more helps); the bus is I/O-bound (constraint N3). The binding's only other exports, the `connectorKey` naming helper and the events-path constants, are synchronous; it exports no frame codec, tag grammar or audio stream naming, which are TypeScript ([Wire conventions](#wire-conventions)).
- **TypeScript owns every read loop.** Rust never calls into JavaScript: there are no threadsafe functions and no callbacks from the runtime (constraint N1). A loop iteration is one awaited `readGroup` / `read` call that returns a whole batch, so the boundary is crossed once per batch, not once per entry.
- **Handlers run serially.** The facade awaits each `subscribe` handler before the next entry and before the next read (BUS-SUB-006); tail handlers run under the facade's guard (BUS-TAIL-004). The next read is not issued until the batch is done, so backpressure is natural: a slow handler leaves the backlog in Redis, bounded by the stream cap, and never in process memory.
- **Acks are pipelined, delivery stays at most once.** After a handler finishes (or fails, or the entry is filtered or undecodable), the facade calls `ack`, which only queues the id. The queued XACKs travel in the same pipeline as the next `XREADGROUP`, so a batch of 50 costs one round-trip instead of 51. Order and outcome: an entry is acked only after its handler returned (BUS-SUB-005), a handler failure is still acked, and an entry never acked is not redelivered to another process (BUS-SUB-008). A refused XACK comes back in `ackErrors` of that `readGroup` and the facade logs it at warn as `ack failed` with the ids, then carries on without retrying it; the entry stays pending and a later drain delivers it once more, and a second refusal of the same id drops it (`ack failed, entry dropped`, BUS-SUB-008, BUS-SUB-009, BUS-NAT-ACK-003, BUS-NAT-ACK-008). During the pending drain the cursor still follows the last id handled (BUS-SUB-003), so within one drain an entry whose ack is queued or refused is never read twice. If the pipeline fails on the connection, the queued acks stay queued and are sent with the next pipeline that reaches Redis (XACK is idempotent).
- **Stop during a handler** keeps BUS-SUB-013: the facade does not queue an ack for that entry or any later entry of the batch.
- **Acks queued at `stop()`** are sent before the connections close: `close()` flushes every reader's queue on the shared connection, which no blocking read occupies, in one pipeline, and only then closes. With no queued acks it sends nothing. Every entry handled before `stop()` is therefore acked when Redis answers, and a shutdown leaves no handled entry pending under a consumer name that is never used again. A flush that fails (the shared connection is down, or Redis refuses an ack) is not retried and is not logged by the transport; `stop()` still resolves. A flush that has not completed 2000 ms after `close()` was called is abandoned the same way (BUS-NAT-ACK-007), so `stop()` resolves within about 2 s even when Redis hangs or the first connect attempt is still in flight; the shutdown budget of shared-runtime counts on that bound (SHARED-BOOT-006).
- **Buffers.** An upload's bytes cross as a Node `Buffer`. Inbound (`putUpload`), the binding copies the bytes into the outgoing command synchronously, inside the call, so the caller may reuse or change its `Buffer` as soon as the call returns, before the Promise settles (BUS-NAT-TRN-009). Outbound (`takeUpload`), the bytes parsed from the Redis reply are handed to Node as an external `Buffer` that owns the Rust allocation, with no copy into the JS heap; Rust frees it when V8 collects the `Buffer` (constraint N2; BUS-NAT-TRN-010). Event `data` crosses as a JS string (one UTF-8 to UTF-16 conversion by V8), which `decode` then parses. Audio frames never cross ([Frames path](#frames-path)).

### Errors, reconnect and backoff

The binding rejects with a JS `Error` whose `code` is one of `BUS_CONNECTION`, `BUS_REDIS`, `BUS_CLOSED`, `BUS_INVALID` and `BUS_INTERNAL`; the frame transport uses `BUS_CONNECTION`, `BUS_REDIS` and `BUS_CLOSED` in the same meanings (BUS-NAT-FRM-008), and also uses `BUS_INVALID` for a refused frame (BUS-NAT-ERR-001):

| Code | Meaning | Facade response |
|---|---|---|
| `BUS_CONNECTION` | could not connect, connection reset or closed by the peer, connect timeout; the message names the cause (the operating system's error text, or `connect timeout`; BUS-NAT-ERR-009) | read loops: warn and back off (BUS-SUB-009, BUS-TAIL-003); publish and other calls: reject to the caller (BUS-STREAM-007) |
| `BUS_REDIS` | Redis answered with an error; the message is Redis's text (`NOGROUP ...`, `WRONGTYPE ...`) | as `BUS_CONNECTION`; `subscribe` and `resetGroup` rethrow a group-creation error other than BUSYGROUP (BUS-SUB-001, BUS-GROUP-001), which the transport has already turned into `false` |
| `BUS_CLOSED` | the transport or reader was closed, including a blocked read interrupted by `close()` | after `stop()`: end the loop quietly (BUS-STOP-001) |
| `BUS_INVALID` | an argument the binding refuses before any Redis call: an unknown stream name, or a negative or non-finite ttl, lease or block duration. The frames path's `publishFrame` also rejects with it for a frame whose `pcm` exceeds `MAX_FRAME_BYTES` or has an odd byte count, before anything is written ([Frames path](#frames-path)) | reject to the caller |
| `BUS_INTERNAL` | a Rust panic caught at the boundary, or a reply of an unexpected shape | as `BUS_CONNECTION` |

Reconnect semantics:

- **Readers** do not retry. A reader whose connection fails rejects the read at once; the facade logs and sleeps for its capped backoff (base 250 ms doubling to 30 s, reset on a successful read) and calls the reader again, which reconnects on that call. So the facade's backoff is the only retry clock, every failed attempt produces exactly one warn line and one `onRead` report (BUS-TAIL-005), and the subscribe and tail promises never reject on a read failure (BUS-SUB-009, BUS-TAIL-003). Tail loops resume from the last id they delivered.
- **The shared connection** reconnects in the background after a failure (a failed first attempt included; never with `failFast`), with its own capped delay (the same 250 ms base doubling to a 30 s cap). The connection has two phases. **Boot:** from construction until the first connect attempt settles (at most the 10 s connect timeout, BUS-NAT-CONN-007), a command waits for that attempt and then runs, or rejects with `BUS_CONNECTION` if the attempt failed (BUS-NAT-CONN-006), so a service's first heartbeat does not fail merely because it was published before the socket opened. **After boot:** no command ever waits for a connect attempt. Whenever the connection is down (the first attempt failed, or an established connection dropped) every command on it (`publish`, `publishHealth`, `putUpload`, `takeUpload`, the registration calls, `recent`, `recentHealth`, `resetGroup`, `createGroup` for `subscribe`, `serverTime`) rejects with `BUS_CONNECTION` at once, including while a background reconnect attempt is in flight, until a reconnect succeeds; nothing is queued for later (BUS-NAT-CONN-005). Rejecting at once keeps heartbeats from piling up behind a dead connection: a heartbeat that cannot go out now is worthless later, and each failure reaches the caller's warn log (BUS-STREAM-007) at the moment it happens.
- **Drain after a read failure.** After any read failure in `subscribe` (once its backoff sleep ends), the loop goes back to cursor `0` and drains this consumer's pending entries again before returning to `>`, with the same drain rules as at the start (BUS-SUB-003). Entries Redis handed to this consumer in a reply that never arrived are therefore delivered late rather than lost. The acks still queued from before the failure travel in the pipeline of that first cursor-`0` read, ahead of the `XREADGROUP`, so every entry whose handler had already run is acked before the drain reads the pending list and is not delivered again. An entry whose ack Redis refused (reported in `ackErrors`) is still pending, so the drain after a later read failure delivers it once more (BUS-SUB-008); within that drain the cursor has moved past it, so it is not read twice. An entry whose ack was refused on both deliveries is in the dropped set, and every later drain skips it without handling or acking it (BUS-NAT-ACK-008).
- **`failFast`** (BUS-STREAM-009): the shared connection is never re-established. The boot phase is the same as without it: a command issued while the first attempt is in flight waits for it, so a refused connection fails within milliseconds and an unanswered one within the 10 s connect timeout; after a failed attempt, or once an established connection drops, every command rejects with `BUS_CONNECTION` at once. Nothing is printed, because the native layer never writes to stdout or stderr. The rejection's message names the cause (BUS-NAT-ERR-009), which `cohostctl` prints (CTRL-CLI-017).
- The connect timeout is 10 s for every attempt: the shared connection's first attempt, its background reconnects and each reader's connect (BUS-NAT-CONN-007).
- **Silent reader connection** (BUS-NAT-CONN-008). A reader's connection has no response timeout (`response_timeout` is `None`), because a blocking read legitimately waits `block_ms` for Redis to answer. A cached reader connection can therefore stop answering without an error, and an unbounded read would wait forever. The transport bounds each read's reply at `block_ms` plus 2000 ms: on expiry it drops that reader's connection and rejects with `BUS_CONNECTION` (BUS-NAT-CONN-001), and the reader's next call opens a new connection. The drop is tagged with the connection's generation, so a stale timeout never clears a newer connection. A `block_ms` of 0 (Redis: block without limit) is bounded the same way, at 2000 ms. The facade passes the caller's `blockMs` (default 5000) through unchanged. The connect itself is not covered by this bound; it has its own 10 s timeout (BUS-NAT-CONN-007).

### Wire conventions

A convention lives with the code that issues the command it governs. Each convention has one implementation, in the language of the services that use it; the frame codec, tag grammar, protocol constants and audio stream names are TypeScript, because only TypeScript services read and write frames today (tenet 12 keeps a frame from crossing into Rust to share code). The contract fixtures guard the TypeScript codec now and hold any later Rust copy to the same behaviour.

In TypeScript, exported from `@cohost/bus`: in `connector.ts` (BUS-NAT-RS-003 to BUS-NAT-RS-005, BUS-NAT-RS-007), and for the audio stream names in `frames.ts` (BUS-NAT-RS-006):

- The frame codec: `encodeFrame`, `decodeFrame` and their rules (field names, `v` = `FRAME_VERSION`, `MAX_FRAME_BYTES` 64 KiB, even byte count, finite header numbers, flush frames without `pcm`; CONN-AUD-002, CONN-AUD-006, CONN-BP-006).
- The connector protocol constants `FRAME_VERSION`, `MAX_FRAME_BYTES`, `AUDIO_MAXLEN` (`in` 3000, `out` 1500), `AUDIO_STREAM_TTL_MS` (60000), `LEASE_INTERVALS` (3), `REGISTRATION_VERSION` (1) and `DEFAULT_CONNECTOR_INTERVAL_MS` (5000).
- The tag grammar and reserved list (`TAG_PATTERN`, `RESERVED_TAGS`, `tagProblem`; CONN-TAG-001, CONN-TAG-002).
- The audio stream names `<prefix>:audio.<dir>.<tag>`, built by `audioStreamName` in `frames.ts`, which `Bus.audioStream` returns and the frame transport writes and reads.
- `AvatarFrameSchema`, `decodeAvatarFrame` and the constants `AVATAR_FRAMES_MAXLEN` (120) and `AVATAR_FRAMES_TTL_MS` (10000) in `avatar-frame.ts` (the avatar-frame stream's name is built by `avatarFramesStream` in `frames.ts`), `parseRegistration` and its zod schemas, `findOffer`, `findReady`, `capabilityDirection`, `FrameSequencer`, `FrameTracker`, `ConnectorRegistrar`, `watchConnectors`, `ConnectorRegistry`, and the `Frame`, `DecodedFrame`, `Registration`, `CapabilityEntry`, `ConnectorSpec` types.

In `crates/cohost-bus`:

- For the events path, which the addon runs: the names `<prefix>:events`, `<prefix>:health`, `<prefix>:upload:<id>` and `<prefix>:connector:<id>`, and the stream caps `MAXLEN` 20000 and `HEALTH_MAXLEN` 1000. `Bus.connectorKey` returns the name the crate builds, through the binding's synchronous `connectorKey`, and `HEALTH_MAXLEN` is the binding's value (BUS-NAT-RS-004, BUS-NAT-RS-006).
- For Rust services, which link the crate directly: the serde codec of the next section. The crate carries no frame codec, tag grammar, audio stream names or avatar-frame stream name and exports no connector protocol constants (its registration codec keeps the registration version, 1, as a private constant), and the binding exports none of these to Node.

### Rust service codec and contract fixtures

A Rust service does not run zod. `crates/cohost-bus` carries a hand-written, typed serde codec for exactly the event types a Rust service publishes or reads, plus the registration value. The first set is `service.heartbeat` and the registration; a type is added to the codec, with its fixtures, when a Rust service first touches it. The codec mirrors the zod schema's rules for that type: required and optional members, enums, ranges, and the defaults zod applies on parse.

The contract for the codecs is a set of shared JSON fixtures in `packages/bus/fixtures/contract/`:

- `events/<type>/<case>.json`: `{ "payload": ..., "valid": true|false, "parsed": ... }`, where `parsed` (valid cases only) is the payload as zod returns it (defaults applied, unknown keys removed).
- `registration/<case>.json`: the same shape for a registration value.
- `frames/<case>.json`: an entry's field list (binary values base64-encoded) and the expected `DecodedFrame` (`ok` with the frame, or the `reason`). The cases cover both directions (`audio.in` with `spk` and `name`, `audio.out` with `utt` and `last`), a flush frame, the size and byte-count limits, and every malformed header.
- `tags/<case>.json`: `{ "tag": ..., "valid": true|false }`, covering the grammar's edges and every reserved tag.
- `constants.json`: the connector protocol constants by name, and the audio stream and connector key names built for a sample prefix, direction, tag and id.

`packages/bus/test/contract.test.ts` checks each event and registration case against the zod schema (`safeParse` success equals `valid`; the parse result deep-equals `parsed`), each frame case against the TypeScript `decodeFrame`, each tag case against the TypeScript `tagProblem` (`null` exactly when `valid`), and `constants.json` against the TypeScript constants and names. `crates/cohost-bus/tests/contract.rs` reads the event and registration fixtures from the same directory (resolved from `CARGO_MANIFEST_DIR`) and checks that the Rust codec accepts exactly the valid cases and that serialising what it parsed gives JSON equal to `parsed`. The frame, tag and constants fixtures guard the TypeScript codec now and are the contract a future Rust copy is held to ([Deferred](#deferred)). A schema change in `events.ts` for a type in the Rust codec therefore fails a test until fixtures and Rust codec agree. Fixtures for types outside the Rust codec are read by the TS test only.

### Rust example client

The docs site's Rust bus client page shows a Rust program on the bus with `examples/rust-bus/`, the package `cohost-example-bus`, a member of the examples Cargo workspace (`examples/Cargo.toml`), which stays outside the root workspace so the image build never needs it (BUS-NAT-EX-001 to BUS-NAT-EX-005). It does the two things a Rust service does first, using only what the crate provides:

- **Publish.** A `service.heartbeat` for `rust-example`, built as `codec::Heartbeat`, checked with `parse_heartbeat` and appended to the health stream every 5000 ms, so the program appears on the dashboard's Services tab beside the services the manifest lists. It publishes no event on `<prefix>:events`: every type there other than the codec's needs a Rust codec and fixtures first (BUS-NAT-RS-009), and the page says so.
- **Read.** A consumer group `rust-example`, read with `Reader::read_group`, printing each entry's `type` and `source` and acknowledging it, without decoding `data`.
- **Stop.** On Ctrl-C a `stopping` heartbeat, then `close`.

The logic is a library function `run(url, prefix, stop, out)`, so `examples/rust-bus/tests/round_trip.rs` runs it with its own prefix, appends an event, reads the line it prints and parses the heartbeat it published (BUS-NAT-CI-002 applies). It depends on nothing the crate does not already use, at the versions the root lockfile holds (docs-site DOCS-GUIDE-026). `packages/bus/test/example-rust-bus.test.ts` runs that test with `cargo test --manifest-path examples/Cargo.toml` during `mise run test`, with the cargo `mise.toml` provides; CI's root `cargo test --workspace` does not reach it, so `test.yml` runs it in a dedicated step, with its Redis service and `REDIS_URL`, that fails on a `SKIP` line and requires the `RAN round_trip` line.

The example is not a service in the module contract's sense: it has no manifest entry, answers no `control` command and no `inject.request`, and its heartbeat comes from its own loop, because the crate has no shared runtime. Those are what a Rust service writes for itself today; a Rust shared runtime is not designed.

### Build, CI and Docker

- **Local build.** The `build:native` task of `mise.toml` (deployment Toolchains and commands) runs `cargo build --release -p cohost-bus-node` followed by a copy of `target/release/libcohost_bus_node.so` to `packages/bus/native/cohost-bus.linux-x64-gnu.node`, and declares the Cargo manifests, `rust-toolchain.toml` and `crates/` as its sources and the addon as its output, so mise skips it while the addon is current. Every task that runs a program importing `@cohost/bus`, or the tests, depends on it (`build`, `test`, `dev:<service>`, `dashboard`, `cohostctl`, the memory one-shots, `bus:*`, `perf:*`), so the addon exists before any of them runs and no one builds it by hand (BUS-NAT-BLD-002). The `.node` and Cargo's `target` directory are build outputs, ignored by git (BUS-NAT-BLD-003) and excluded from the Docker build context (deployment DEPLOY-IMG-004). The Rust toolchain is the one `rust-toolchain.toml` pins, which mise installs per project (deployment DEPLOY-INST-004, DEPLOY-INST-014); `scripts/install.sh` builds the addon on the host through `mise run build`.
- **One addon, two builders.** `crates/cohost-bus-node` is a `cdylib`, and its plain `cargo build --release` output `target/release/libcohost_bus_node.so`, copied under the name `cohost-bus.linux-x64-gnu.node`, is the whole addon: the napi CLI adds only the copy and the name. `native.ts` declares the binding's TypeScript types itself and uses no file the napi CLI generates, so an addon built without the CLI loads and typechecks the same (BUS-NAT-BLD-009).
- **Target.** linux-x64-gnu only (BUS-NAT-BLD-006): the runtime images are `node:<version>-trixie-slim` (Debian, glibc; the addon is linked against glibc 2.35 through Zig, deployment Linking through Zig), CI is ubuntu, and every Node process that uses the bus runs in one of them or in WSL on the same target. The addon does not load on macOS, arm64 or a Node process on the Windows host; a Node tool there that needs the bus runs inside WSL. A Rust program on the Windows host, such as the desktop capture helper (connections CONN-DESK-001), links `crates/cohost-bus` directly and needs no addon.
- **Locating the addon.** `native.ts` loads `../native/cohost-bus.<platform>-<arch>-gnu.node` relative to its own file with `createRequire(import.meta.url)`, and nothing else: no search path, no environment override, no fallback transport. On any other platform, or when the file is missing or fails to load, importing `@cohost/bus` throws an error naming the platform and arch it looked for, the path, and `mise run build:native`.
- **Docker** (deployment DEPLOY-IMG-001). A `native` stage on Debian trixie (the release the runtime's `node` image is built on, so the addon links against the same glibc) installs only Rust and Zig (the linker) through mise and runs the same `build:native` task, a plain `cargo build --release` and the copy of the cdylib to `cohost-bus.linux-x64-gnu.node`; the stage has neither Node nor the napi CLI. The `build` stage copies that file into `packages/bus/native/` before `tsc -b`. Every service image carries the addon, since every service uses the bus. The runtime stage needs no Rust.
- **CI** (deployment DEPLOY-CI-001). The `test` workflow installs `mise.toml`'s tools and, with the job's Redis service and `REDIS_URL`, runs `mise run test`, whose `test:rust` dependency runs `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings` and `cargo test --workspace` (Rust integration tests use their own stream prefix, as the TS tests do, BUS-NAT-CI-002) before the build and the TypeScript suite. Cargo's registry and target directory are cached between runs, and the job's timeout is 20 minutes, room for a Rust build with a cold cache.
- **Release profile.** `panic = "unwind"` (BUS-NAT-BLD-007), so a panic inside a Rust future is caught at the boundary and becomes a `BUS_INTERNAL` rejection rather than aborting the process (BUS-NAT-ERR-006). A test reaches that path through the test-only cargo feature `test-panic`, which adds a binding call that panics inside its future; no release build enables it (BUS-NAT-ERR-011).

### Measurement gate

The native transport merges only if, on `scripts/dev/bus-bench.ts --sources 8 --runs 3` (default 20 s per phase) against the same Redis and machine, run on the native transport and, back to back, on the TypeScript events path it replaced, both of these hold when the medians over the three runs of the `events x8` row are compared between the two transports (BUS-NAT-GATE-001):

- the **events path** (`publish` / `subscribe`) median process CPU (the `cpu%` column, from `process.cpuUsage`, which counts the addon's runtime threads too) is no greater than the TypeScript transport's (BUS-NAT-GATE-004); and
- the events path's median **p99 hop latency is not worse**: at most 1.1 times the TypeScript transport's median p99 (BUS-NAT-GATE-005).

Three runs and their medians keep one noisy run from deciding the merge; the 10% bound on p99 allows for the run-to-run noise of a tail percentile measured over a 20 s phase, so "not worse" means not worse beyond that noise. The bench has `--runs N`, which repeats every phase N times and prints the per-row medians, and `--json`, which writes every run's rows and the medians as one JSON document, so the two transports' results can be compared by a script rather than by reading tables (BUS-NAT-GATE-007). The bench's `p99ms` column is the hop latency and its final PASS/FAIL line (p99 under 5 ms) is a separate sanity bound, not the gate. The bench measures both paths in one process with publisher and consumer on one clock; its events path is a `chat.message` carrying base64 PCM at audio rate, a worst case for that path rather than real traffic. Its `frames x8` row runs the TypeScript frames path on both sides and is not part of the gate. Its scratch-stream cleanup uses ioredis, as the frames path does. If the gate is missed, the native transport is not merged: the TypeScript transport stays, the branch is closed with its numbers recorded, and the HLD's Native layer section is revised to match (BUS-NAT-GATE-006).

**Gate result.** The events-path gate passed: `scripts/dev/bus-bench.ts --sources 8 --runs 3` (20 s per phase) on a quiet machine, the native transport and the TypeScript baseline built from commit `6adc350` (the merge base plus the benchmark script; `packages/bus/src` unchanged from the merge base), run back to back against the same Redis, gave these medians over three runs:

| Row | TypeScript cpu% / p99 ms | Native cpu% / p99 ms | Native / TypeScript |
|---|---|---|---|
| events x8 (the gate) | 11.26 / 4.53 | 9.86 / 2.29 | 0.88x CPU, 0.51x p99 |
| frames x8 (context only) | 8.15 / 1.90 | 9.43 / 2.19 | TypeScript frames path on both sides |

Native CPU is below the TypeScript median (BUS-NAT-GATE-004) and native p99 is about half of it, well inside the 1.1x bound (BUS-NAT-GATE-005). Absolute numbers vary from run to run with machine load: a second run measured the same events x8 row at 7.41% / 2.87 ms (TypeScript) and 6.41% / 1.40 ms (native). Only ratios taken within one back-to-back run are comparable, and both runs give the native events path about 0.87x to 0.88x the CPU and half the p99. The gate is a one-time acceptance procedure that no test re-runs, so BUS-NAT-GATE-001, BUS-NAT-GATE-004, BUS-NAT-GATE-005 and BUS-NAT-GATE-006 are `[D]`; this result is the recorded evidence for them. The frames x8 row runs the same TypeScript frames code in both builds, so its difference (1.16x CPU, 1.15x p99) is run-to-run noise, not a property of either transport.

**The measurement that set the split.** With frames also on the addon, the same bench (8 sources, medians of 3 runs) gave:

| Path | TypeScript cpu% / p99 ms | Native cpu% / p99 ms | Native / TypeScript |
|---|---|---|---|
| frames x8 | 6.23 / 1.31 | 8.19 / 1.46 | 1.31x CPU, 1.11x p99 |
| events x8 | 7.41 / 2.87 | 6.41 / 1.40 | 0.87x CPU, 0.49x p99 |

The events path carries one batch per crossing and gains on both counts. The frames path crosses once per frame of 20 ms audio and spends more on the crossing than native Redis I/O saves, so frames stay TypeScript (HLD tenet 12). These numbers record why the paths are split; they are not a requirement on later runs. Frames stay TypeScript for this reason: the per-frame crossing cost measured here (1.31x CPU, 1.11x p99 with frames on the addon), not the noise of the gate run's frames row.

### Native design constraints

Properties of the native layer that shape its code but that no test observes from outside; review checks them.

- **N1. Rust never calls into JavaScript.** No threadsafe functions and no callbacks from the runtime; each read-loop iteration is one awaited `readGroup` or `read` call that returns a whole batch ([Crossing the napi boundary](#crossing-the-napi-boundary)).
- **N2. Outbound bytes are not copied into the JS heap.** `takeUpload` hands Node an external `Buffer` that owns the Rust allocation, freed when V8 collects it. The observable half, that such a `Buffer` keeps its content while referenced, is BUS-NAT-TRN-010.
- **N3. One tokio runtime per process.** Created when the addon is first loaded, with one worker thread unless the measurement gate shows that more helps; every I/O method is a Promise resolved from a future on it.

- **connector-discord on songbird**: a Rust Discord connector on `cohost-bus`, after a live Discord run of the TypeScript connector.

The tests' and the bench's direct ioredis use stays TypeScript until their tool moves.
- **Schema generation for every event**: one source generating zod and Rust types for the whole catalogue, replacing the hand-written codec and its per-type fixtures.

### Edge-case probe

What the native transport does in situations the sections above do not make obvious.

| # | Situation | Expected behaviour |
|---|---|---|
| 1 | Connection drops while `XREADGROUP` is blocked | The read rejects `BUS_CONNECTION`; the facade logs warn and backs off; the next `readGroup` reconnects. Entries Redis delivered to this consumer whose reply never arrived stay in its pending list; after the backoff the loop returns to cursor `0` and drains them, so they are delivered late, not lost. Queued acks are kept and sent ahead of that first drain read, in its pipeline. |
| 2 | Pending-entry drain on process restart | The new process has a new consumer name, so its cursor-`0` read returns nothing and the loop moves to `>` at once; the predecessor's pending entries are not claimed (BUS-SUB-003, BUS-SUB-008). |
| 3 | A pending entry was trimmed from the stream before the drain read it | Redis returns the id with no fields; the transport returns a `RawEntry` without fields; `decode` treats it as undecodable, the facade acks it without logging, and the drain moves on (BUS-SUB-007). |
| 4 | An entry with unknown `type`, non-JSON `data` or a failed schema | Not delivered, acked in `subscribe`, skipped in tails and `recent`, no log line (BUS-SUB-007, BUS-TAIL-002). |
| 5 | An envelope field (`type`, `ts`, `source`, `data`) that is not valid UTF-8 | The entry is poison: the transport returns it with no fields, `decode` treats it as undecodable, and it is dropped (acked in `subscribe`, skipped in tails and `recent`) without a log line, as BUS-SUB-007. No lossy decode: an entry is never delivered with text the publisher did not write. |
| 6 | A frame read with `pcm` over `MAX_FRAME_BYTES`, odd length, wrong version, or no `pcm` | The frame reader's `readFrames` returns `{ ok: false, reason }` for it from the TypeScript `decodeFrame`; the consumer drops and counts it (CONN-BP-006, CONN-AUD-002, BUS-NAT-FRM-004). |
| 7 | `publishFrame` called with `pcm` over `MAX_FRAME_BYTES` or with an odd byte count | The facade rejects with `BUS_INVALID` before calling the frame transport, so nothing is written; the producer learns of the bad frame at its source instead of every consumer dropping it. Consumers still drop such a frame if one reaches the stream by another writer (row 6). |
| 8 | A `subscribe` handler throws or rejects | The facade catches it, logs `handler failed` at error, queues the ack, continues (BUS-SUB-005). Rust is not involved: it never calls a handler. |
| 9 | A handler is slower than the producer | The next read waits for the batch; the backlog stays in Redis. If the group falls more than the stream cap behind, `MAXLEN ~` trims entries it never read and `>` resumes at the oldest entry left; those entries are lost, consistent with at-most-once. Process memory holds at most one batch (50 entries; on the frames path 100 entries of at most 64 KiB). |
| 10 | Tail handler returns a slow Promise | Tail handlers are guarded, not awaited, so the read loop does not wait for them (BUS-TAIL-004); bounding their concurrency is the handler owner's concern. |
| 11 | `stop()` with acks queued but not yet sent | `close()` sends them on the shared connection before closing; `stop()` resolves after that flush whether or not it succeeded, and at the latest 2000 ms after `close()` was called, abandoning a flush that has not completed (BUS-NAT-ACK-007). A refused or abandoned ack leaves its entry pending under a consumer name never used again; with at-most-once delivery across restarts that costs only pending-list space. |
| 12 | `stop()` while a read is blocked, or while `createGroup` is in flight | `close()` interrupts the read, which rejects `BUS_CLOSED`; the facade sees `stopped` and resolves the promise without logging (BUS-STOP-001). A `createGroup` that rejects after `stop()` also resolves `subscribe` quietly instead of rethrowing. |
| 13 | Redis down at boot | Constructing the `Bus` does not throw. A command issued while the first connect attempt is in flight waits for that attempt (at most 10 s; a refused connection settles it at once), and once it has failed every command rejects with `BUS_CONNECTION` at once until a background reconnect succeeds; `subscribe` rejects from `createGroup` (BUS-SUB-001), which a service's bootstrap reports as `fatal` and exits (SHARED-BOOT-003). With `failFast` the same first wait applies, there is no background reconnect, and nothing is printed (BUS-STREAM-009). The container healthcheck's own 4 s limit (CTRL-CHECK-002) ends a check that waits on a connect attempt Redis never answers. |
| 14 | Redis goes away while services publish | `append` rejects with `BUS_CONNECTION` at once while the shared connection is down; the facade logs it at warn and rethrows (BUS-STREAM-007). Publishing works again as soon as the background reconnect succeeds. |
| 15 | Two `Bus` instances with the same consumer name | The name is `HOSTNAME-<8 hex>` built in the facade (BUS-STREAM-005); a collision would make two instances share one pending list. Accepted as negligible (32 random bits); no detection. |
| 16 | Several subscribers and tails in one process | Each loop has its own reader and connection; blocking reads never share a connection. Non-blocking commands of every loop and every publish share the one multiplexed connection. Connections per process: 1 + events loops on the addon, plus, on the frames path, one publish connection once a frame has been published and one per `tailAudio` loop. |
| 17 | Many concurrent `publish` or `publishFrame` calls without awaiting | `publish` commands enter the shared connection in call order, and frames enter the one frames publish connection in call order; Redis applies each connection's commands in that order, so stream order equals call order per stream for one `Bus` (frames' `seq` stays monotonic, BUS-NAT-TRN-008, BUS-NAT-FRM-005). A `publish` and a `publishFrame` go to different streams on different connections and have no order between them. |
| 18 | The `.node` is missing, built for another platform, or the host is not linux-x64-gnu (Windows, macOS, arm64) | Importing `@cohost/bus` throws the load error described in Build; there is no fallback. linux-x64-gnu is the only supported platform. |
| 19 | A large JSON payload or a large `recent(count)` | Parsing and zod validation stay on the Node event loop; the native layer neither adds nor removes that cost. Batch sizes (50 group, 100 tail) bound the work per loop turn. |
| 20 | Clocks: envelope `ts`, `timing` stamps, `serverTime` | `ts` is stamped by the facade with `Date.now()` before `append`, so `timing` stamps that copy an envelope `ts` (`heardAt`, `focusedAt`) carry the envelope `ts` they were copied from. A Rust service stamps `ts` from its system clock in epoch ms. `serverTime` is Redis `TIME` on the shared connection (CTRL-CHECK-004); the transport never substitutes it for `ts`. |
| 21 | The caller reuses or mutates a `Buffer` it passed to `putUpload` or `publishFrame` | `putUpload`: safe once the call has returned, the bytes were copied synchronously. `publishFrame`: not safe until its Promise settles, because ioredis holds the `Buffer` until it is written; producers build a fresh `Buffer` per frame ([Frames path](#frames-path)). |
| 22 | A `Buffer` returned by `takeUpload` or a frame read is kept long after the read | Safe: an upload's `Buffer` owns its Rust allocation until V8 collects it; a frame's `pcm` is an ordinary Node `Buffer` from ioredis's reply. |
| 23 | A Rust panic inside a transport call | Caught at the boundary; the call rejects `BUS_INTERNAL` and the loop backs off like any read failure. The process does not abort. |
| 24 | A call after `stop()` | Rejects `BUS_CLOSED`, on either path (BUS-NAT-ERR-005); `publish` logs it at warn and rethrows as any failed write (BUS-STREAM-007). A second `stop()` resolves once the first close has completed (BUS-NAT-ERR-008). |
| 25 | An ack refused by Redis (for example `NOGROUP` after the group was destroyed) | Reported in the next `readGroup`'s `ackErrors`, logged at warn `ack failed`, not retried; the entry stays pending. The same read most likely fails with `NOGROUP` too: its rejection carries the refused acks as `ackErrors` (BUS-NAT-ACK-009), so the facade logs them before it backs off; the drain after that failure delivers the entry once more (BUS-SUB-008). If the ack of that redelivery is refused too, the facade logs `ack failed, entry dropped` and no later drain delivers it again (BUS-NAT-ACK-008). |
| 27 | `stop()` while the first connect attempt is still in flight | `close()` abandons the attempt and the commands waiting on it reject `BUS_CLOSED` (BUS-NAT-ERR-010); `close()` has nothing to flush or abandons the flush at 2000 ms, so `stop()` resolves without waiting out the 10 s connect timeout. |
| 26 | Events path latency or CPU worse than TypeScript | The gate is missed and the native transport is not merged (Measurement gate). |
| 28 | Redis goes away while a producer publishes frames | After the publish connection's first connect, `publishFrame` rejects at once while it is down and nothing is queued; ioredis reconnects in the background. The producer logs the failure as any failed write; the frames lost are counted by consumers as `seq` gaps (CONN-BP-003, BUS-NAT-FRM-006). A `tailAudio` read waits for its reader's reconnect and resumes from the last id it read. |
| 29 | A service imports `@cohost/bus` but never touches frames | It opens no frames connection: the frame transport connects only at the first `publishFrame` or `tailAudio` (BUS-NAT-FRM-005). |

The event is a report and not an order to moderate: it says what the platform did, and the name follows the event types that report (`voice.done`, `voice.failed`). It carries no `injected` or `remember` flag and no text.

`voice.stop` orders the body to stop speaking now: `reason` is a free string naming why (salience publishes `barge-in`, or `yield` when an interjected line gives way to the speaker's final; cortex publishes `muted` or `paused` when it stops its own line on a mute or pause), `ids` narrows the order to the named lines, by `brain.say` id, and covers every clause of each, queued or playing; when absent it means every line voice holds and every line a mouth output holds or plays. It is an order and not a report: it carries no sink, and the events that report its effect are the ordinary `voice.done` (flagged `interrupted`) from each sink that was playing. It is not a mute: a `brain.say` published after it is spoken as usual.

`voice.failed` reports that a sink gave up on an utterance; `fallback` is present when the sink plays a pre-generated fallback clip in the line's place. `voice.playing` and `voice.done` keep their shape: a fallback clip is reported through them as ordinary playback under the given-up id and clause.

`Emotion` is imported from `@cohost/config` (`packages/config/src/schema.ts`): `neutral`, `happy`, `laugh`, `surprised`, `smug`, `sad`, `angry`, `confused`, `think`.

- **Request and result.** The pair follows the other request and reply pairs (`memory.recall.*`, `inject.*`): the result carries the request's `id`, a consumer matches by `id` and ignores an unknown or late one, and the producer answers each request it reads exactly once. `tool` is repeated on the result so the feed row reads without the request. `status` `refused` is a decision of the service before the call, `error` is a call that ran and failed, `timeout` is a call that did not return in time; `reason` is present with `refused` and `error` and absent with `ok` and `timeout`. `content` is bounded by `tools.max_result_chars` and `truncated` says it was cut. The `origin` values are cortex's reading of the focus it answers; the table of which origin may call which tool is tools' (Who can cause a call).
- **Catalog.** A snapshot, not a request or a reply: the latest one describes the running service, a consumer treats it as current for three `intervalMs` and as absent after that. `offered` is true for an enabled tool whose effect is `read` or whose `acts` mark is set. `parameters` is a JSON Schema object of at most 4000 serialized characters and `description` at most 400 characters; the service enforces both before it publishes.
- **Timer.** Published once when a timer runs out; `dueAt` is when it was due and the envelope `ts` is when it fired. `note` is at most 200 characters. Salience publishes the same event again with `missed` when it drops a reminder it could not speak in time, and ignores an event that carries `missed`.
- **Confirm and answer.** `tool.confirm` is the pending acting call, shown by the dashboard until `expiresAt` or its `tool.result`; `tool.answer` is the owner's click, published by the dashboard, accepted by `tools` only for a pending `id` and only once ([tools](../tools/tools-design.md) Confirming an acting call).
- **`attention.focus` of kind `reminder`.** The focus a due timer becomes (salience Reminders): `reason` `reminder`, `score` 1, and `focus` `{kind: "reminder", text: <note>}`, with no `who`, `platform` or `userId`, and no `mention`.

### Injection flags

`injected` marks an event that came from the dashboard test-injection panel; `remember` says whether an injected event may be persisted to long-term memory (`remember` is meaningful only when `injected` is true; `skipInjected` in `services/memory/src/region.ts`). The five flagged types are `chat.message`, `vision.summary`, `speech.heard` (the perception inputs) and `brain.say`, `attention.focus` (derived outputs that carry the flags of the input that caused them). Real traffic never carries the keys: zod `.optional()` with no default leaves them absent (asserted in `bus.test.ts`). Copying flags from an input onto a derived output is done by `propagatedFlags` in [working-memory](../working-memory/working-memory-design.md), not here.

### Streamed lines

A reply the co-host speaks clause by clause is one line with one id: the id of its `brain.say`. The shapes and terms below are the only place the clause fields and words are defined; [cortex](../cortex/cortex-design.md) says when each event is published, [voice](../voice/voice-design.md) how a clause is carried to a sink.

- **`brain.say.more`.** The literal `true` on the `brain.say` of a line whose later clauses follow as `brain.clause` events; `false` is rejected. It is absent on a line that is not streamed and on a reply that fits in one clause. The `brain.say` carries the first clause as its `text`, the line's `emotion` and `gesture`, its `route`, its flags and `timing`; those fields describe the line, and `brain.clause` repeats none of them.
- **Streamed line.** A line whose `brain.say` carried `more`. A line without `more` is one clause and is released, played and stopped as one.
- **`brain.clause`.** One later clause of a streamed line. `id` is the line's id, `seq` counts the clauses from 1 (the `brain.say` text is clause 0) with no gap, `text` is the clause. `last` is the literal `true` on the closing event, which cortex publishes exactly once for every streamed line, whatever ended the reply, so no consumer waits for the bound except after a cortex crash; the closing event may carry empty `text`. It carries `through`, an integer from 0 up to its own `seq`: the `seq` of the last clause sinks should expect audio for. On a normal close and on a cut by a check, `through` is the last clause with text; on a synthesis failure of clause k it is k minus 1 (0 when k is 0, when no sink holds audio for the line at all). `cut` names why the reply ended before the model finished: `repeat` (the repetition check), `muted` (mute or pause), `busy` (another line began), `failed` (the stream failed, voice could not synthesize a clause, or nobody was hearing the line), `length` (the clause limit was reached), `stopped` (a `voice.stop` covered the line, or cortex shut down), `timeout` (the no-progress valve ended the line), `vetoed` (the critic vetoed the rest of a reply after a first clause the critic never saw had been spoken) or `tools` (the tool loop's hard stop, [cortex](../cortex/cortex-design.md) The tool loop). `cut` and `through` appear only with `last`, and `through` is required with it. Empty `text` appears only on a closing event, and the event carries no flags and no timing. A consumer that appends clause text accepts a clause only when its `seq` is exactly one more than the last it accepted for that line, and drops any other with a warning; cortex publishes a line's clauses in order, one publish at a time, so a duplicate or a gap does not arise from it. An empty closing event appends nothing.
- **Clause identity downstream.** `seq` is a required member of `voice.utterance`, `voice.playing`, `voice.done` and `voice.failed`: the clause the event is about, 0 for a line that is not streamed. voice copies `seq` onto the utterance, and a sink copies it onto its own reports. `(id, seq)` names one audio file, one envelope and one playback. The `voice.utterance` of clause 0 of a streamed line carries `more: true`, copied from the `brain.say`, so a sink knows the line has more clauses; no other utterance carries it.
- **Closed.** A streamed line is closed once its closing `brain.clause` has been published. A **finished clause** on a sink is one for which the sink has published `voice.done`.
- **Open and ended on a sink.** A streamed line is **open on a sink** from the sink's `voice.playing` for clause 0 until it **ends** on that sink, at the first of: the line is closed and the clause `through` has finished on that sink (at once when it already has, or when the sink has played past `through`; the clauses above `through` that the sink holds are dropped unplayed); a `voice.stop` covers the line; the sink publishes its own `final` for it; or 300 seconds pass with no clause activity for the line (a clause read, played or finished), the one bound every sink uses so that a crashed cortex cannot leave a line open. If voice fails to synthesize a clause at or below `through` after the line closed, the line stays open on the sink until that bound. An ended line is skipped by the sink, and a clause of it that arrives afterwards is dropped. A sink that did not play clause 0 of a line (it was not ready, joined mid-line, read clause 0 only in a connect replay, or had its audio off) never opens it and skips all its later clauses, publishing nothing. A line that is not streamed is open on a sink while its one clause is current. The dashboard page follows the same rules as a mouth output.
- **`voice.done.final`.** The literal `true` (`false` is rejected) on a `voice.done` by which a sink says it will play no more of the line: it dropped the clauses that remain, because one failed or it could not take them. It is per sink: it says nothing about any other sink. A `final` `voice.done` from voice's own sink `error` says that clause `seq` failed to synthesize, so no audio exists for it and the line's last produced clause is `seq` minus 1 (nothing was produced when `seq` is 0); sinks learn it from `through` on the closing clause.
- **Interrupted `voice.done`.** A `voice.stop` makes a sink publish a `voice.done` flagged `interrupted` for each line open on it, and for no other: a line that has ended on the sink gets nothing. For a line with a current clause the `seq` is that clause; for a line open between two clauses it is the last clause played.
- **Order.** `brain.say` and its `brain.clause` events travel on the one stream in order, and voice publishes the utterances of a line in clause order, so a consumer that reads in stream order sees a line's clauses in order.

### Other schema notes

- `control.target` is optional: a command without it is addressed to every service.
- `voice.utterance.audioUrl` is a path on the voice service (`/audio/<id>-<seq>.wav`, with `seq` 0 for a clause-less line); its comment names no host or port.
- `route` (BUS-EVT-023) is one optional string-array schema shared by `control` (meaningful for `say`), `brain.say` and `voice.utterance`: the list of mouth output ids a line is for. The producers copy it down the chain unchanged (cortex, voice); only mouth reads it. Absent means every enabled output, so old publishers stay valid.
- `voice.playing` is the schema `PlaybackReport` (`id`, `seq`, `sink`); `voice.done` extends it with `interrupted?` (the literal `true`), `final?` (the literal `true`), `spokenText?` and `unsaidText?` (BUS-EVT-017, BUS-EVT-031). `interrupted` marks a line that `voice.stop` ended before its audio finished; `spokenText` is the part of the line's text that had been spoken and `unsaidText` the rest, both covering every clause of the line the publishing sink holds, and present only when that sink could compute them from the line's timing (mouth, [mouth](../mouth/mouth-design.md) Stopping a line) and absent otherwise. No consumer reads the two texts in this release: the transcript keeps the line as it was meant to be said.
- `avatar.state` carries ranges, as `affect.state` does (BUS-EVT-018): `intensity`, `mouthOpen`, `mouthSmile` and `blink` 0..1, `eyeX` and `eyeY` -1..1, and the head angles `headX`, `headY`, `headZ` in degrees -90..90 (the avatar's own yaw range is -30..30; the bound here rejects only a corrupt value).
- `speech.partial` (BUS-EVT-026) is an interim, unstable transcript of an utterance that is still open: `text` is the words ears has committed so far (the stable prefix of its latest transcriptions, [ears](../ears/ears-design.md) Partial transcripts), `seq` counts the partials of one utterance from 0 and `utteranceId` names the utterance, the same id the final `speech.heard` carries (BUS-EVT-027). A consumer holds only the latest partial of an utterance (a later one replaces the earlier) and treats it as stale after `PARTIAL_STALE_MS` or when the utterance's final or the speaker's next utterance appears (BUS-EVT-028), so a partial whose utterance ended without a final does not linger. It is never a final transcript and has no injection flags: injection delivers whole clips. `speech.heard` stays the one final event.
- `speech.early` is a transcript of an utterance that is still open, made after a pause: `text` is the transcript of the audio up to the last speech frame, `seq` counts the early transcripts of one utterance from 0, `utteranceId` names the utterance (the id the final `speech.heard` and any `speech.partial` of it carry) and `sttMs` is how long its transcription took. It is neither a partial nor a final: a consumer may act on it provisionally, only until the same utterance's `speech.retracted` or final arrives, and must not treat it as speech that happened, with one exception: a spoken interjection records its text as an unfinished line in a working-memory window ([working-memory](../working-memory/working-memory-design.md) An unfinished line). `speech.retracted` says the speaker resumed and names the early transcript (`utteranceId` and `seq`); ears publishes it once, before any later event of the utterance. A final `speech.heard` that reuses an early transcript carries `earlySeq` and `earlySttMs`, so a consumer that acted on the early transcript knows the final text is the same; one whose early transcription was still running at the close carries `earlyLate` instead. Neither early event has injection flags: injection delivers whole clips. Only salience subscribes ([ears](../ears/ears-design.md) Early transcripts).
- `attention.focus` with `provisional` is a decision that holds until `attention.resolve` names its `utteranceId`: `outcome` `confirm` releases it and carries everything a focus carries, so a reader that holds nothing for that utterance can treat it as an ordinary focus (except an `interjected` confirm, which a reader that holds nothing for it treats as a withdrawal); `withdraw` drops it. A resolve and a provisional focus are matched by `utteranceId` and `seq`. A provisional focus is a focus on an early transcript, so its `focus.kind` is `speech`. A `speech` focus carries the `utteranceId` of its utterance when the event has one, so that a reader holding a provisional think for it can tell the ordinary focus on its final from another focus ([salience](../salience/salience-design.md) Early transcripts, [cortex](../cortex/cortex-design.md) Provisional think).
- `timing` (BUS-EVT-024) is one optional schema, `Timing`, shared by `speech.heard`, `speech.partial`, `speech.early`, `vision.summary`, `attention.focus`, `attention.resolve` and `brain.say`: up to thirteen optional integers, each an epoch-millisecond stamp from the publishing service's clock: `audioEndedAt` (ears: the last frame classified as speech arrived under `silero`, the last frame received under `gap`, or the clip arrived), `closedAt` (ears: the utterance was closed by the silence rule, the frame-gap rule, the length cap or the Kyutai end of turn, present on the `speech.heard` of an utterance ears cut itself, and copied by salience onto the `attention.focus` of a speech focus and so onto the `brain.say`), `confirmedAt` (cortex: the confirmation of a provisional focus reached cortex, present only on the `brain.say` of a reply released by a non-interjected confirm, where it is also the marker that the reply was prepared), `heldAt` (cortex: a provisional think stopped working, its first clause held or parked at a tool call, present only on the `brain.say` of a reply released from such a think), `heardAt` (the `speech.heard` envelope `ts`), `capturedAt` and `describedAt` (eyes: the frame's screenshot returned, and the vision model's reply returned), `focusedAt` (the `attention.focus` envelope `ts`), `llmStartedAt` and `llmEndedAt` (cortex: the first LLM request of the think, and the return of its reply call, the critic excluded) `criticEndedAt` (cortex: the return of the critic hook's call, present only when the critic ran), `toolStartedAt` (cortex: the publication of the reply's first `tool.request`, present only when a request preceded the first clause) and `toolEndedAt` (cortex: the arrival of the last result of the tool wait that held the first clause back, present only when the results had arrived by then). Every member is optional and a non-negative integer; the schema bounds the numbers and nothing else, so a reader tolerates any member being absent. Each stage copies the object it received, adds only its own stamps, and never changes or removes a stamp it received (BUS-EVT-025), so the `brain.say` that answers a spoken line or a screen change carries the whole chain; a line with no such trigger (chat, an operator `say`, a reflex) carries only the stamps its own stage adds, or none. The bus validates the shape only; which stamps appear is each producer's spec ([ears](../ears/ears-design.md), [salience](../salience/salience-design.md), [cortex](../cortex/cortex-design.md)), and the report that reads them is [control-plane](../control-plane/control-plane-design.md) (Latency report).
- `EVENT_TYPES` is exported and used by the dev scripts `scripts/dev/bus-pub.ts` and `scripts/dev/bus-tail.ts` and by tests; `decode` checks `Object.hasOwn(EventPayloads, type)` instead.

## Test double: `packages/testing/src/index.ts`

`@cohost/testing` is the shared helper package for region and service tests (30 import sites across service/package tests). Its test double has tests in `packages/testing/test/fake-bus.test.ts`. Exports:

- `testConfig(over?)`: deep-merges `over` onto a minimal base (`cohost` Coco/Chris/UTC, `llm` model `m` / embed `e`, `vision` model `v`, twitch channel `chan`, `brain.salience.cooldown_ms: 0` and `idle_chatter_ms: 0`, placeholder avatar hosts, empty `voice`, `ears`, `dashboard`) and returns `ConfigSchema.parse(...)`, so a test config is always schema-valid with timing knobs zeroed. The local `merge` / `isObj` helpers duplicate a lambda in `packages/config/src/index.ts`.
- `silentLog` and `recordingLog()`: pino-shaped loggers cast `as never`. `recordingLog` returns `{ log, lines, msgs(level) }` and records `warn`, `info`, `error`, `debug` and `fatal` (no `trace`, unlike `silentLog`).
- `FakeBus implements Publisher`:
  - `published: { type, data }[]` holds the zod-parsed payload of each accepted publish; `of(type)` returns the payloads of one type, `types()` the type sequence, `clear()` empties both `published` and `health`.
  - `publish(type, data)` mirrors the real bus ordering: throws for `service.heartbeat`, then zod-parses (so invalid payloads throw and defaults are applied), then throws `publish <type> failed` when the optional `fail(type)` predicate returns true, then records. Returns a time-ordered id of the form `<ms>-<seq>` (BUS-TEST-011), strictly increasing within the process, as Redis stream ids are.
  - Health: `publishHealth` validates, throws `publishHealth failed` when `failHealth` is true, otherwise records into `health`. `recentHealth(count=100)` returns the last `count` heartbeats wrapped as `BusEvent`s (`id` is the one `publishHealth` returned, `source` is `data.service`). `consumer` is the constant `fake-instance`.
  - Uploads: `putUpload` and `takeUpload` keep bytes and the `ttlMs` in an in-memory `uploads` map (`takeUpload` returns them once, then `null`); `putUpload` rejects with `putUpload failed` while `failUpload` is true (BUS-TEST-012).
  - Timers: `putTimer`, `deleteTimer` and `listTimers` keep the tools service's pending timers in an in-memory map (BUS-TEST-004).
  - It does **not** implement `subscribe`, `tail`, `tailHealth`, `recent`, `resetGroup` or `stop`; services that depend on those (dashboard feed, controller) take narrower `Pick<Bus, ...>` types and use their own fakes.
- `event(type, data, source="test")`: builds a `BusEvent` as a subscriber would receive it, with `EventPayloads[type].parse(data)` (defaults applied), `ts: Date.now()`, and a time-ordered id from the same generator as the fake bus (BUS-TEST-011).
- `runHeartbeat(spec, drive?)`: runs `startHeartbeat` against a `FakeBus` at `intervalMs: 60_000`, calls `drive(hb)` (default `hb.ready()`), waits 10 ms, calls `hb.stop()`, returns `bus.health`. Each call registers another `beforeShutdown` hook in the module-global list (never removed); harmless in tests, a small leak.
- `waitFor(cond, what="condition", ms=2000)`: polls every 2 ms and throws `timed out waiting for <what>`.

## Tests

Tests run from the repo root with `mise run test` (`node:test`; the root script builds first and globs `packages/*/test/*.test.ts`, so fixtures are not picked up directly). Redis integration tests auto-skip when no Redis answers at `REDIS_URL`.

- `packages/bus/test/bus.test.ts`: pure schema tests (catalogue and shape checks for the region events, `service.heartbeat`, `service.lifecycle`, `control`, the injection flags, `inject.request`, `inject.result`, `avatar.state`, the playback events, `voice.stop`) and Redis integration tests (round trip, validate-before-write, handler-throw-is-acked, `recent` ordering and undecodable-skip, `tail`, `stop()` interrupting blocked reads, heartbeat routing, `recentHealth` / `tailHealth`, `resetGroup`).
- Each integration test runs inside `scratch()`, which gives it its own stream pair through `streamPrefix` (BUS-STREAM-008): the test never reads or writes `cohost:events` or `cohost:health`, and the `finally` stops every bus and deletes the streams and their groups whether the body passed, failed or timed out. Waits are on `onReady`, on tails started from id `0`, or on `within`, which fails the test after a timeout, so a failure cannot hang the run.
- `packages/bus/test/resilience.test.ts`, `native-api.test.ts` and `native-loops.test.ts` run `Bus` against scripted fake `BusTransport`s injected through `BusOptions.transport` (start modes, drain, read retry and backoff, `XACK` failure, tail handlers, publish failure, stop during a handler, consumer name format, decode drops); `frames.test.ts` runs the frame transport. None needs a Redis server except where a test says so. `native-binding.test.ts` checks the addon's exports, and `native-integration.test.ts` runs the addon against a real Redis, with `native-failfast.fixture.ts` in a subprocess.
- `contract.test.ts` and `crates/cohost-bus/tests/contract.rs` check the contract fixtures; `crates/cohost-bus/tests/` holds the Rust transport, connection and workspace tests.
- Tests carry `@spec` annotations naming the specs they exercise. Specs with no annotated test: BUS-STREAM-002 (`MAXLEN` trimming), BUS-SUB-006 (sequential delivery), the field-level schema specs BUS-EVT-002, BUS-EVT-012, BUS-EVT-014 to BUS-EVT-016 and BUS-EVT-019 (other tests parse some of those types only to check something else), and the test helpers BUS-TEST-001, BUS-TEST-002, BUS-TEST-004, BUS-TEST-005 and BUS-TEST-007 to BUS-TEST-010, which service tests exercise indirectly.

## Decisions & Alternatives

| Decision | Chosen | Alternatives Considered | Rationale |
|----------|--------|------------------------|-----------|
| Rust example client | `examples/rust-bus/`, a package of the examples Cargo workspace that publishes a codec-checked heartbeat and reads events by envelope, tested against Redis | No example (the crate's tests only); an example that publishes a domain event; a Rust shared runtime first | The crate's tests exercise the transport, not what a service author writes. Publishing a domain event would need that type's Rust codec and fixtures (BUS-NAT-RS-009), a bus change for an example. A shared runtime for Rust is design work no Rust service has asked for yet; the example shows what the crate gives today and the docs page lists what it does not. |
| Reader read timeout | Each reader read's reply is bounded at its `block_ms` plus 2000 ms, measured from the send; on expiry the reader drops its own connection and rejects `BUS_CONNECTION` (BUS-NAT-CONN-008) | A fixed `response_timeout` on each reader connection; TCP keepalive on the reader socket | A fixed per-connection `response_timeout` must exceed the longest `blockMs` any caller passes and so detects a dead connection late for short reads; it also applies to every command on that connection. TCP keepalive detects a vanished peer only after the kernel's probes fail, and a Redis that is alive but not answering keeps the socket healthy, so neither bounds a reply that never comes. Deriving the bound from each read's own `block_ms` matches the wait Redis was asked for. |
| Upload bytes | A plain Redis string `cohost:upload:<id>` with a TTL, written by `putUpload` and read-and-deleted by `takeUpload` (`GETDEL`), on the native shared connection; the event carries only the id | Base64 in the event; an HTTP fetch from the dashboard | The stream is capped at 20000 entries and replayed to every group and `/ws` backfill, so megabytes do not belong on it; containers cannot always reach the host, but all of them reach Redis. A TTL means a key nobody reads (service down) expires by itself. |
| Pending drain | Read this consumer's pending entries batch by batch, the cursor following the last id seen, until a read returns none; on the native transport a drain runs at the start of `subscribe` and again after every read failure | One batch only; always re-read from `0` | A cursor that follows the ids ends even when an entry cannot be acked and so stays pending; re-reading from `0` within a drain would loop on it (BUS-SUB-003). |
| Stop during a handler | The running handler finishes; its entry is not acked and the rest of the batch is neither handled nor acked | Ack on the closed connection; cut the handler short | `stop()` closes the connections, so an ack would fail on a dead socket; an unacked entry is at most once in effect because the next process has a new consumer name (BUS-SUB-013, BUS-SUB-008). |
| A `Bus` is single-use | `stop()` is instance-wide and final; one instance is never restarted | Reset `stopped` on a new `subscribe` | Every service builds one bus for its life and stops it once at shutdown; restart support would add states nothing uses. |

| The closed-at and confirmed-at stamps | `closedAt` (ears, on the `speech.heard` of an utterance it cut) and `confirmedAt` (cortex, on a prepared reply) are `Timing` members | A new event at the close; a field on `speech.heard` outside `timing`; derive the close from the envelope `ts` | The stamp is read by the latency report with the others and travels with them (BUS-EVT-025); the envelope `ts` of `speech.heard` is after transcription and cannot split the wait from the transcription. |

## Cross-segment impacts

Work the native transport requires in other segments, specified there:

- [deployment](../deployment/deployment-design.md): the Dockerfile's `native` stage runs the `build:native` task (plain `cargo build --release` and a rename of the cdylib to the addon), and the `.node` file and Cargo `target` directory leave the build context (DEPLOY-IMG-001, DEPLOY-IMG-004); the `test` workflow runs `mise run test`, whose `test:rust` dependency runs `cargo fmt`, `clippy` and `test` before the TypeScript suite, caches Cargo and has a 20 minute timeout, with every action pinned (DEPLOY-CI-001, DEPLOY-CI-009); the installer installs the pinned toolchain through mise and builds the addon on the host (DEPLOY-INST-007, DEPLOY-INST-014); compose-smoke builds the Rust stage and its `test:launch` task builds the addon through `build` (DEPLOY-CI-002, DEPLOY-CI-007); `lid-check` reads `@spec` annotations in Rust sources (DEPLOY-CI-006).
- [control-plane](../control-plane/control-plane-design.md): the `serverTime` test uses a `BusTransport` fake (CTRL-CHECK-004); `cohostctl` recognises an unreachable Redis by the code `BUS_CONNECTION` and prints the error's message as the reason (CTRL-CLI-017, BUS-NAT-ERR-009).
- [connections](../connections/connections-design.md): the connector client library lives in `@cohost/bus`, with the frame codec, tag grammar, protocol constants and audio stream naming in TypeScript on the frames path, guarded by the contract fixtures (BUS-NAT-RS-003 to BUS-NAT-RS-007, BUS-NAT-FIX-001); the crate carries no Rust copy until a Rust connector needs one; `publishFrame` rejects a frame whose `pcm` exceeds `MAX_FRAME_BYTES` or has an odd byte count with `BUS_INVALID`, writing nothing (CONN-AUD-002).
- [shared-runtime](../shared-runtime/shared-runtime-design.md): `Bus.stop()` returns `Promise<void>` (it flushes queued acks for at most 2 s), and the shutdown sequence awaits it (SHARED-BOOT-005, SHARED-BOOT-006, SHARED-LIFE-001, SHARED-LIFE-004).
- [ears](../ears/ears-design.md) and the [dashboard](../dashboard/dashboard-design.md) feed: a read during a Redis outage rejects at once instead of waiting inside the client, so `onRead` reports a failure each backoff interval and a dependency or the bus reachability turns `down` or `unreachable` sooner; neither design states a timing the native transport changes.
- [mouth](../mouth/mouth-design.md): its frame producer handles a `BUS_INVALID` rejection from `publishFrame`, and the at-once rejection while Redis is down, like any failed write; it does not change a frame's `pcm` after passing it to `publishFrame` (it slices each line's newly converted audio).
- [avatar](../avatar/avatar-design.md) and [dashboard](../dashboard/dashboard-design.md): the browser driver writes frames with `publishAvatarFrame`, handling an at-once rejection like any failed write and never awaiting it inside the Engine's tick; the dashboard's relay reads them with `tailAvatarFrames` while a renderer page is connected and takes the newest entry of each read.
- [voice](../voice/voice-design.md) and [avatar](../avatar/avatar-design.md): a publish rejects at once while Redis is down after boot, the first connect is waited for at most 10 s, and a subscription read fails and backs off without rejecting, so only group creation at subscribe time can reject the subscription (BUS-NAT-CONN-005, BUS-NAT-CONN-006, BUS-SUB-009; AVATAR-BUS-008, AVATAR-STATE-002).
- [connections](../connections/connections-design.md): the Windows desktop capture helper is a Rust program on `crates/cohost-bus`, its build deferred (CONN-DESK-001).
- [tools](../tools/tools-design.md), [cortex](../cortex/cortex-design.md), [salience](../salience/salience-design.md), [memory](../memory/memory-design.md), [dashboard](../dashboard/dashboard-design.md): the tool events, the `reminder` focus and the `source` of a `speech` focus, the `tools` inject target and `memory.recall.request` from a second requester are specified by each; the registry holds one schema per tool event, a `focus.kind` and a `focus.source`, an `inject.request.target`, a `cut` value and two `Timing` members; `tools` keeps its pending timers in one Redis hash through key calls the bus client adds beside `putUpload` (set, delete and list a timer).
- [ears](../ears/ears-design.md), [salience](../salience/salience-design.md), [cortex](../cortex/cortex-design.md), [control-plane](../control-plane/control-plane-design.md): early reply adds `speech.early`, `speech.retracted` and `attention.resolve`, the optional `earlySeq`, `earlySttMs`, `earlyLate`, `provisional`, `seq` and `utteranceId` fields, the `closedAt` and `confirmedAt` members of `Timing`, the `interjected` marker of `brain.say` and the `yield` reason of `voice.stop`; each is specified by the segment that publishes or reads it, the registry holds the schemas, and the report that reads the stamps and counts the early events is control-plane's. `brain.status` gains no state.
