# config

Parent: [high-level-design](../../high-level-design.md). Specs: [config-specs.md](config-specs.md).

## Context and Design Philosophy

`@cohost/config` (`packages/config`) is the dependency root of the workspace: it has no workspace dependencies and every other package and service imports it (`packages/config/package.json` lists only pino, yaml, zod). It owns four things:

1. The **shape** of `config/config.yaml` and `config/expressions.yaml` (zod schemas in `packages/config/src/schema.ts`), including the nine-value `Emotion` enum that the bus event schemas also import (`schema.ts`).
2. The **loader**: locate the config directory, seed user-owned files from committed `*.example.*` templates, load `.env`, reject `${VAR}` placeholders, merge `secrets.yaml`, apply the isolation overrides by key path, validate, warn about unknown keys, and cache (`packages/config/src/index.ts`, `secrets.ts`).
3. **Small runtime helpers** every service uses: `env`/`envOr`, the `urls.*` service-address functions, `createLogger`, the personality read/write pair, and `ollamaModels`, the list of local models a config needs (`models.ts`).
4. The **presentation table** (`packages/config/src/presentation.ts`): the plain-language title, group and one-sentence description of every section, and the help text, label, unit and widget hint of every key, which the settings editor serves with the schema so the Settings screen names every setting without hard-coding any (module-contract MOD-CFG-*).

Design philosophy, as the example files' header comments state it (`config/config.example.yaml`, `config/secrets.example.yaml`, `.env.example`): every operator setting is a literal key of `config/config.yaml` (git-ignored, seeded from an example) with a schema default, so the dashboard's settings editor shows and edits all of it; credentials live in `secrets/secrets.yaml` (git-ignored, mode 0600, merged by the loader at the secret paths and returned by no read API); `.env` holds only bootstrap values and the dashboard's own access controls (HLD tenet 7; [config in one place](../../decisions/config-in-one-place.md)). No environment variable reaches a setting except through the isolation override: the control plane passes one variable, `COHOST_ISOLATION`, to a container it starts isolated, and the loader applies its entries by key path to fourteen keys (CFG-ISO-006, CFG-ISO-007); `config.yaml` holds literals only, and a `${VAR}` placeholder anywhere in it fails the load (CFG-ENV-011). Each backend that can be swapped for a mock or off variant is selected by an enum key of that kind; the mock variants are never the default (comment `schema.ts`). The schema is lenient about unknown keys (warn, do not fail) and strict about enums and ranges. The shipped example config loads with no `.env` and no `secrets.yaml` at all: every key it holds is a literal (CFG-ISO-005), while a value that is set but invalid, such as an unknown `avatar.driver`, still fails the load.

## Files, directory resolution and seeding

| File | Where | Role | Seeded from |
| --- | --- | --- | --- |
| `config.yaml` | `<configDir>/config.yaml` | all behaviour; read by `loadConfig` | `config.example.yaml` |
| `personality.md` | `<configDir>/personality.md` | co-host persona prompt; read/written by `loadPersonality` / `savePersonality` | `personality.example.md` |
| `expressions.yaml` | `<configDir>/expressions.yaml` | emotion to avatar-app name map; read by `loadExpressions` | `expressions.example.yaml` |
| `secrets.yaml` | `COHOST_SECRETS_FILE`, else `<workspace root>/secrets/secrets.yaml`, else `secrets/secrets.yaml` beside the config directory when there is no workspace root (`secretsPath()`; not moved by `CONFIG_DIR`, CFG-SEC-001) | credentials, nested at the secret paths; merged by `loadConfig` (CFG-SEC-*); written only by the dashboard's write-only secret route and by hand; on the host the operator's whole file, in a container its unit's projection ([deployment](../deployment/deployment-design.md) Secret scoping) | `config/secrets.example.yaml` (copied by `install.sh` with mode 0600 into `secrets/`, mode 0700, never by the loader) |
| `.env` | `COHOST_ENV_FILE`, else `.env` at the workspace root, else the parent of `configDir()` (CFG-ENV-010) | bootstrap values and the dashboard's access controls; loaded by `loadDotEnv` | `.env.example` (copied by `install.sh`, not by code) |
| per-service data | `dataDir()`: `COHOST_DATA_DIR`, else `data` under the workspace root (CFG-DIR-006, CFG-DIR-007); each service writes only under `<dataDir()>/<service>/`, its log file apart (next row), such as voice's fallback clip store, mouth's clip cache and the dashboard's uploaded avatar models | generated files a service keeps across restarts; not edited by hand and ignored by version control (`data/` in `.gitignore`) | none: services create what they need |
| log files | `<dataDir()>/logs/<program>.log` and its rotated `<program>.<n>.log` (CFG-LOG-012, CFG-LOG-015) | every entry a program logs, as pino JSON lines; written by the logger of every program except `tools` (CFG-LOG-022), from containers through the `./data/logs` bind mount (deployment DEPLOY-COMPOSE-029); read by people and their tools, never by cohost | none (created by the first program that logs) |

Resolution (`index.ts`):

- `findWorkspaceRoot(start = cwd)` walks parent directories until one contains `pnpm-workspace.yaml`, returning `undefined` at the filesystem root (`index.ts`). It exists because `mise run dev` runs each service with its package directory as cwd (comment `index.ts`).
- `configDir()` = `resolve(CONFIG_DIR ?? join(findWorkspaceRoot() ?? cwd, "config"))` (`index.ts`). Compose sets `CONFIG_DIR=/app/config` (`docker-compose.yml`) and bind-mounts `./config` there (`docker-compose.yml`).
- `dataDir()` = `resolve(COHOST_DATA_DIR ?? join(findWorkspaceRoot() ?? cwd, "data"))`, the same resolution as `configDir()` (CFG-DIR-006, CFG-DIR-007). Each service keeps its own files under `<dataDir()>/<service>/` and never reads another service's subdirectory: voice's fallback clip store is `voice/fallback-clips`, mouth's clip cache `mouth/fallback-clips`, the dashboard's uploaded VRM models `dashboard/avatar-models` (the dashboard is a host process, so its `dataDir()` is the checkout's `data/` or `COHOST_DATA_DIR`; no container reads or mounts it). Services exchange those files over HTTP (HLD tenet 1). In a container the workspace root is `/app`, so the default is the container's own `/app/data`, with no volume. The path is a per-machine value, so it is an environment variable with no YAML key (HLD tenet 7).
- `ensureFromExample(name, example)` returns the real path if it exists; otherwise copies the example, reports `[config] created <file> from <example>` through the config logger (CFG-LOG-001), and returns the path; if the example is also missing it throws `No <file> and no <example> to seed it from` (`index.ts`). It is called for all three user files (`index.ts`), so any service that starts first seeds them (README.md says the same).
- `dotEnvPath()` is `COHOST_ENV_FILE` when set, else `.env` at the workspace root (`findWorkspaceRoot()`), else the parent of `configDir()` when there is no workspace root (CFG-ENV-010). A `CONFIG_DIR` elsewhere does not move where `.env` is looked for. In a container the workspace root is `/app`, so the path is `/app/.env`, which does not exist (it is `.dockerignore`d, `.dockerignore`) and does not matter because Compose injects `.env` through `env_file`. A missing `.env` is not an error: every variable has a default or an owner that reports its absence (the dashboard names `CONTROL_TOKEN`).

Personality and expressions: `loadPersonality()` and `loadExpressions()` read their file on every call (uncached by design: a service that wants a fresh copy asks again, as cortex does on `control reload_personality`) and `savePersonality(text)` overwrites `personality.md` through `writeFileAtomic`, a temporary file in the same directory renamed over the target, which the settings editor's section writer shares (CFG-USR-013). `loadExpressions()` parses `expressions.yaml` with `ExpressionMapSchema`, treats an empty file as `{}`, and reports a schema failure as `Invalid <file>:` followed by `  path: message` lines, the shape `loadConfig` produces (CFG-USR-002). A value in the `browser` block longer than 64 characters fails the load of the file, because the browser driver's frames carry it and a longer one would make every frame invalid ([event-bus](../event-bus/event-bus-design.md) Avatar frames).  The consumers are cortex (loads at start, reloads on `control reload_personality`, `services/cortex/src/cortex.ts`), dashboard (GET/PUT personality, `services/dashboard/src/routes.ts`), memory reflection (`services/memory/src/reflect.ts`) and avatar (expressions, and `configDir()` as the VTube Studio token directory, `services/avatar/src/boot.ts`).

## Loading pipeline

`loadConfig(force = false)` (`index.ts`):

1. Return the module-level cached `Config` unless `force` (`index.ts`). There is no file watching: config is read once per process; only personality has a reload path.
2. `loadDotEnv()` (`index.ts`), from `dotEnvPath()`. Parses `KEY=value` lines (it never sets `COHOST_ISOLATION`, CFG-ISO-008): trims each line, skips blank and `#` whole-line comments, requires `=` at index 1 or later, trims key and value, strips one layer of matching single or double quotes, and sets `process.env[key]` only when it is `undefined` (`index.ts`). Comments follow Compose's `env_file` rules (CFG-ENV-006): an unquoted value loses a whitespace-then-`#` suffix (`KEY= # note` is empty), a quoted value may be followed by a comment and keeps any `#` inside the quotes, and a `#` with no preceding whitespace (`a#b`) is part of the value.
3. `ensureFromExample("config.yaml", "config.example.yaml")` (`index.ts`).
4. Parse and placeholder check (`pipeline.ts`): the raw file text is parsed as YAML (a syntax error is reported as an issue like a schema failure, giving only the line, column and the parser's reason code, because the library's own message quotes the offending source line, which may hold a credential; CFG-LOAD-007), and every string value holding a `${NAME}` or `${NAME:-default}` placeholder, `NAME` matching `[A-Z0-9_]+`, becomes an issue at that key's dotted path (an array entry as `path[index]`). A placeholder inside a comment is not a value and is not checked. No placeholder is ever substituted; the issues end the load as `Invalid <file>:` (CFG-ENV-011), so a `config.yaml` that still holds one fails loudly at the key instead of reading it as empty. The message says that `${...}` is not supported in `config.yaml`; the loader has no escape for a literal dollar-brace before an upper-case name, so prose that needs one is reworded or the name written in lower case, which is literal text.
5. `coerceEmptyNumbers` drops every `null`-valued key at any depth (`index.ts`; the name says numbers but the filter is type-blind; `null` array elements are kept) so schema defaults apply: a key written with no value (`port:`) is the same as a key left out (CFG-LOAD-002).
6. Secrets (`secrets.ts`): `loadSecrets()` reads `secrets.yaml` as described under Secrets file and `mergeSecrets` sets each secret path's value into the parsed object, discarding any value `config.yaml` holds at a secret path (CFG-SEC-004, CFG-SEC-011).
7. Isolation overrides (`pipeline.ts`): when `COHOST_ISOLATION` is set and non-empty, the loader parses it as a JSON object from override name to string and sets each entry at the key path `ISOLATION_OVERRIDES` gives that name, after the file's own values, so the override wins; a value is parsed as a YAML flow value for the boolean keys, `chat.sources` and `ears.sources` and kept as a string for the rest (CFG-ISO-007). A malformed object or an unknown name fails the load naming `COHOST_ISOLATION` (CFG-ISO-010). No other environment variable is consulted.
8. `ConfigSchema.safeParse`. Steps 4 to 8 are one function, `parseConfigText(text, secrets, overrides)`, which `loadConfig` and the settings editor both call, so they accept exactly the same files; the editor passes the secrets it read and no overrides, so it validates the file as it reads once started without isolation. On failure `loadConfig` throws `Invalid <file>:` followed by one `  path: message` line per issue.
9. `unknownKeys(raw, parsed)` recursively lists dotted paths present in the raw object but missing from the parsed one; non-empty results are reported by one warning through the config logger that names only the ignored keys, and loading continues. The walk descends into array entries and reports them as `path[index].key`, so a typo inside a reflex shows up as `brain.salience.reflexes[0].cooldwn_ms` (CFG-LOAD-006).
10. Cache and return.

All diagnostics (the seeding notice, the unknown-key warning and the secrets warnings) go through a pino logger named `config`, created on first use; `setConfigLogger` swaps it so tests and hosts can capture or redirect them (CFG-LOG-001). Nothing in the package writes to `console`. No diagnostic and no error message carries a secret's value or any text of `secrets.yaml`.

## Secrets file

`secrets/secrets.yaml` holds the credentials, so that `config.yaml` can be shown, shared for support and edited by the dashboard whole, and so that no container, all of which mount `./config`, can read them.

- **Location and creation.** `secretsPath()` is `COHOST_SECRETS_FILE` when set, else `<workspace root>/secrets/secrets.yaml`, else `secrets/secrets.yaml` in the parent of `configDir()` when there is no workspace root (the `.env` rule, CFG-ENV-010); it is outside `./config` and unaffected by `CONFIG_DIR` (CFG-SEC-001). `COHOST_SECRETS_FILE` is a bootstrap path like `CONFIG_DIR` and `COHOST_ENV_FILE`, read from the process environment: the tests point it at a file in their temporary directory, and `.env.example`, Compose and the control plane set none. On the host that is the operator's whole file. Inside a container the workspace root is `/app`, where each application service mounts its unit's read-only projection at `/app/secrets` ([deployment](../deployment/deployment-design.md) Secret scoping), so the same path gives the container only the credentials its manifest entry declares and the loader needs no setting to tell the two apart. The control plane rewrites the projections before every start or restart it issues, so a restart applies an edit. The loader never seeds or creates it: a missing file means every secret is unset (`""`, the schema default) and is not a warning (CFG-SEC-001). `install.sh` copies `secrets.example.yaml` (every secret path present and empty, each with a comment) with mode 0600; the dashboard's write-only secret route creates the file with mode 0600 when it does not exist (CFG-SEC-012).
- **Format.** A YAML mapping nested exactly like `config.yaml` but holding only the secret paths of `SECRET_PATHS`: `llm.openai.api_key`, `llm.claude.api_key`, `llm.bedrock.access_key_id`, `llm.bedrock.secret_access_key`, `vision.obs.password`, `ears.http.token`, `ears.openai.api_key`, `ears.nemotron.api_key`, `ears.kyutai.api_key`, `voice.openai.api_key`, `voice.pocket.hf_token`, `chat.twitch.client_id`, `chat.twitch.client_secret`, `chat.twitch.access_token`, `chat.twitch.refresh_token`, `chat.youtube.api_key`, `connections.discord.token` and `tools.servers.*.token` (CFG-SEC-003), where `*` stands for the name of one server of `tools.servers`: a path of the list may hold one such segment, which matches exactly one key of a map the file holds, so the secret of a server the owner adds from the dashboard is a secret path with no change to the list. A secret path whose entry the file does not hold can be cleared (set to `null`) through the secret route, so a removed server's token can be removed too, and is never set. An engine's key lives here like every other credential, and the engine's URL does not (it is a `sensitive` key of `config.yaml`, below). Every value is a string, used exactly as written (no placeholder substitution applies to this file); a non-string at a secret path fails the load naming the path (an unquoted all-digit token needs quotes).
- **Merge.** `loadConfig` trims every value it reads and treats a blank one as not set (a hand-edited block scalar such as `token: |` carries a trailing newline; a value that still holds a line break after trimming fails the load naming the path, CFG-SEC-014), then sets each non-empty string found at a secret path into the config after `config.yaml` has validated, not before: merging first would let a credential create a parent object (a whole `llm.bedrock` section, say) that `config.yaml` is required to hold, and validation of the file would then pass for the wrong reason (CFG-SEC-002). A token for a server that `config.yaml` does not hold is not merged and gets one warning naming the path, because a credential never creates the entry it belongs to. A value in `secrets.yaml` is the one used (CFG-SEC-004). A value `config.yaml` holds at a secret path is never used, whether or not `secrets.yaml` holds one, and produces one warning naming the path, never the value, so a credential pasted into the shareable file is neither used nor returned (CFG-SEC-011). A key of `secrets.yaml` outside `SECRET_PATHS` is ignored with one warning naming the path (CFG-SEC-005); nothing but the secret paths can enter the config this way, so the file cannot override a behaviour setting.
- **Errors.** A file that exists but cannot be read, is not YAML, or whose root is not a mapping ends the load with an error naming the file and, for a syntax error, only the line and column, never the text (CFG-SEC-006, CFG-SEC-007); the loader does not fall back to "no secrets", because a silently empty credential reports as a missing account far from the cause. A file whose mode gives group or other any permission is loaded with one warning naming the file and `chmod 600` (CFG-SEC-008). The check runs only where the platform is not Windows and the reported mode is not `0777`, the mode that drvfs and similar mounts report for every file, so it cannot fire on every load there.
- **Projection.** `projectSecrets(root, units)` (`secrets.ts`) writes each unit's `secrets/units/<composeName>/secrets.yaml` from the operator's file and the units' declared paths (CFG-SEC-019); what it writes and when it fails is deployment's Secret scoping, and the control plane calls it with the manifest's lists.
- **Read side.** The dashboard, `cohostctl` and services run on the host with `mise run dev` load the whole file. A container loads its unit's projection, which holds only the paths its manifest entry's `secrets` list declares ([module-contract](../module-contract/module-contract-design.md)), so a service process holds only its own credentials (HLD Trust boundary). No Compose `environment:` entry carries an operator credential; the fixed credential of the local-only Postgres service is the one exception (DEPLOY-COMPOSE-025). Nothing exported by this package returns a secret's value other than the loaded `Config`; the settings editor reports a secret only as set or not set, read from the file at request time (MOD-CFG-005).
- **Write side.** `updateSecrets(file, changes)` sets or clears secret paths in the file: it refuses a path outside `SECRET_PATHS`, follows a symbolic link to the file it resolves to and writes there so the link stays valid, failing on a dangling link rather than replacing it (CFG-SEC-015), trims leading and trailing whitespace from a value and refuses one that is empty after trimming (clearing is a separate operation, CFG-SEC-013), preserves every other key and comment, writes through `writeFileAtomic`, and never returns or logs a value (CFG-SEC-009). Every write creates its temporary file with mode 0600 before any byte is written, so the file is 0600 after the rename that follows a create and after an update, whatever mode the previous file had (CFG-SEC-012); `writeFileAtomic` takes the mode as an option that it passes when it creates the temporary file, and the personality and `config.yaml` writes pass none. The HTTP route (`PUT /secrets/:path`, a `{ value }` body, `null` clearing, always behind the control token) and the page control that call it are the [dashboard](../dashboard/dashboard-design.md) segment's: secrets are written only through that gated, write-only path, never through `PUT /config/:section`.
- **Not in the file.** The refreshed Twitch token chat persists under `<dataDir()>/chat/` stays a runtime artifact of the chat service, not a `secrets.yaml` key (chat CHAT-TW-011); the VTube Studio token avatar saves as `<configDir>/.vts-token` is likewise runtime state.

## Presentation table

`packages/config/src/presentation.ts` carries, beside the zod schema, everything the Settings screen needs to name and explain a setting, so the page holds no section names and no help text of its own. It is data, not behaviour: it holds no value and no default.

| Level | Field | Meaning |
| --- | --- | --- |
| section | `title` (required) | Plain name, such as "Salience" for `brain.salience` |
| section | `group` (required) | One of `GROUPS`, in order: Identity, Brain, Senses, Voice and body, System |
| section | `about` (required) | One sentence saying what the section affects |
| section | `page` (optional) | Another section whose screen shows this one (`brain.working_memory_events` is shown on `brain.memory`, `renderer` on `avatar`) |
| section | `live` (optional, `true`) | The dashboard applies a saved change to this section at once, with no restart, so the page header says so instead of naming a restart (`renderer`) |
| key | `help` (required, every key) | One sentence of help |
| key | `label` (optional) | Display name when the key name is not plain |
| key | `unit` (optional) | `ms`, `bytes`, `days`, `hours`, `dB`, `chars`, `words`, `fps` and the like |
| key | `sensitive` (optional, `true`) | The key decides where a secret-bearing or private request goes, or who may reach the dashboard's network listeners, so changing it needs the control token (CFG-PRES-010) |
| key | `widget` (optional) | A hint from a closed set: `timezone`; `model` with a kind `chat`, `small`, `vision`, `embed` or `stt`; `voice`; `sources`; `textarea` (a multi-line string); `options` with labelled `value`/`label` pairs; `slider` (a numeric key rendered as a slider whatever the span of its range, `renderer.turn`, and moved by the `step` the hint carries when it has one: `renderer.zoom` 0.05, `renderer.offset_y` 0.01, `renderer.turn` 1); `mcp-servers` (the map `tools.servers`) and `tool-list` (the map `tools.allow`), the two purpose-built controls of the Tools settings ([dashboard](../dashboard/dashboard-design.md) The Tools settings); `avatar-model` (the key `renderer.model`), the model list with its upload and live preview ([dashboard](../dashboard/dashboard-design.md) Avatar settings) |

A section is a declared section path: every top-level key of `ConfigSchema` except `brain`, plus `brain.working_memory_events`, `brain.working_memory_own_lines`, `brain.input_limits`, `brain.salience`, `brain.affect`, `brain.memory` and `brain.cortex` (the sections the manifest's `config` lists cover, MOD-MAN-008, plus the two the dashboard alone reads and no unit declares, `dashboard` and `renderer`). A key is a leaf of a section: a scalar or an array, named by its dotted path from the config root (`brain.salience.reflexes`, `voice.fallback.lines`); an array is one key.

The table is checked at build time (CFG-PRES-007): a key or section without its required fields, an entry for a key or section the schema does not have, a `page` that names no section, a widget outside the closed set or a `model` widget on a key that is not a string fails a test, so a new setting cannot ship unexplained. The widget assignments are fixed by CFG-PRES-006: `cohost.timezone` is a `timezone`; every model-name key is a `model` (`llm.model` and the consolidator's model `chat`, `llm.embed_model` `embed`, `vision.model` `vision`, `ears.stt_model` `stt`, the other hooks' models `small`); `voice.voice` is a `voice`; `vision.prompt` is a `textarea`; `chat.sources`, `ears.sources`, `ears.echo_suppress_sources` and `brain.salience.barge_in_sources` are `sources`; `voice.lang_code` is `options` with a plain language name for each of its nine codes. A key's `help` is also its JSON Schema `description`, generated from the table, so the schema has one source for help (CFG-PRES-008). The `sensitive` keys are exactly the keys that decide where a request carrying a credential or the co-host's private context goes, or who may reach the dashboard's network listeners (CFG-PRES-011): `dashboard.allowed_hosts` and `network.lan` (what the egress marks treat as the LAN); `llm.provider` and `llm.openai.base_url` (where the conversation and the OpenAI-compatible API key go), `vision.obs.host` and `vision.obs.port` (the OBS password), `avatar.vtube_studio.host` and `avatar.vtube_studio.port` (the saved VTube Studio token), `mouth.outputs.http.url` (the co-host's voice audio); `tools.servers` (where the co-host's tool requests and each server's token go) and `tools.allow` (which tools may be called and which may act); the `url` of each of the five hooks (`brain.salience.module`, `brain.affect.module`, `brain.cortex.critic`, `brain.memory.notes.capture`, `brain.memory.notes.consolidator`), which receive the conversation and viewer notes; and the speech and vision engines' destinations: `vision.provider` (which provider receives the screen frames, with a credential it may already hold), `voice.engine`, `voice.openai.base_url` and `voice.pocket.url` (where the text of every spoken line goes), `ears.stt_engine`, `ears.stt_fallback_engine`, `ears.openai.base_url`, `ears.nemotron.url` and `ears.kyutai.url` (where the audio of every utterance goes). `voice.pocket.hf_token` is a secret, so it is written through the secret route and never appears here. An engine selector is sensitive as well as its URL, because choosing an engine whose URL is already stored redirects what that URL receives. Keys that choose a vendor's own endpoint (`llm.bedrock.region`, the Twitch and Discord ids, `chat.youtube.video`, which names a broadcast and not a host) or a local listening address (`ears.http.host`) are not sensitive: nothing a secret travels to changes with them.

## Egress destinations

`egressDestinations(config)` (`packages/config/src/egress.ts`) is a pure function from a loaded config to the places private data is configured to go, one entry per destination: `{ service, data, engine, host, hosted, offLan }`. `data` is `text` (voice: the text of each spoken line and fallback phrase; cortex: the conversation sent to the chat model; tools: the arguments of a tool call, which the model wrote from the conversation), `audio` (ears: each utterance) or `frames` (eyes: each screenshot, from the look loop and from an injected image). `host` is the host name or address of the server the entry names, without a port, or absent; `hosted` names a provider that is hosted by nature, or is absent.

| Entry | Host | Notes |
| --- | --- | --- |
| voice, engine `kokoro` | the `urls.tts()` host | |
| voice, `openai`, `pocket` | the host of `voice.openai.base_url`, `voice.pocket.url` | no entry while the value is blank |
| ears, selected engine and, where the selected engine is `nemotron` or `kyutai`, `ears.stt_fallback_engine` | `speaches`: the `urls.stt()` host; `openai`, `nemotron`, `kyutai`: the host of their URL key | one entry per engine that can receive audio; the fallback only where it is used and is not `none` |
| eyes, provider `ollama` | the `urls.ollama()` host | present whenever the provider is not `stub`, whether or not `vision.enabled` (the describer also serves injected images) |
| eyes, provider `openai` | the host of `llm.openai.base_url`, which defaults to `https://api.openai.com/v1`, so choosing `openai` with the default is the explicit hosted choice and is flagged | |
| eyes, providers `anthropic`, `bedrock` | none; `hosted` is the provider name and `offLan` is true | a provider name is never read as a host name |
| tools, one per `tools.servers` entry while `tools.mode` is `live` | the host of the entry's `url` (`engine` `mcp:<name>`); `offLan` is also true when the entry's `external` is `true`, because a server on the LAN can forward requests on and the rule cannot see that | listed whether or not any of the server's tools is enabled, because the credential goes to the host regardless; no entry in mock mode; stream info has none, because it is a platform connection sending an id and a credential to the platform's own hosts (HLD tenet 8) |
| cortex, `llm.provider` | as the eyes rows, for the chat model | the chat model's calls; a hook that names its own provider or an `http` hook URL, and `mouth.outputs.http.url`, are egress too (HLD tenet 8) and are not in this list |

A `stub` engine, the `mock` chat provider and a blank value have no entry. The voice, ears, eyes and tools services log one warning at start for each of their entries with `offLan` true and name engine and host (or `hosted` provider) in their heartbeat detail; the dashboard shows the whole list ([dashboard](../dashboard/dashboard-design.md) Egress note). The list is computed from the saved file, so after an edit it describes what the services will do at their next restart. A change to `network.lan` is applied by restarting voice, ears, eyes and tools, which log the warnings.

**The off-LAN rule.** `offLan` is true for a `hosted` provider and otherwise comes from one rule, shared by every consumer, which judges a host by its form and never resolves a name, so the services and the dashboard, which read the same configuration, agree:

- On the LAN: an IPv4 loopback, private or link-local address (127/8, 10/8, 172.16/12, 192.168/16, 169.254/16); the IPv6 loopback `::1`, unique-local addresses (fc00::/7) and link-local addresses (fe80::/10); an IPv4-mapped IPv6 address (`::ffff:a.b.c.d`), judged as the IPv4 address it carries; `localhost`; `host.docker.internal`; a host name (not an IP literal) with no dot (a Compose service name such as `tts`, `tts-pocket` or `stt-kyutai`); a name ending `.local`. The brackets of an IPv6 literal in a URL are removed before the host is judged.
- Also on the LAN: any host, suffix or address range the owner lists in `network.lan`, for a tunnel or overlay network (a Tailscale address range, a name inside a VPN). A host entry matches the name exactly, a suffix entry (one starting with a dot) matches names ending in it, a range entry matches addresses inside it.
- Off the LAN: every other host, including a public name that resolves to a LAN address, which the rule cannot see. The owner who runs such a name lists it in `network.lan`.

## Models to pull

`ollamaModels(config)` (`models.ts`) answers "which local models does this config need?" for the `models` container, so the model names live only in `config.yaml` (CFG-MODEL-001). `required` holds `llm.model` while `llm.provider` is `ollama`, `llm.embed_model` while `brain.memory.embedder` is `ollama`, and `vision.model` while it is non-empty and `vision.provider` is `ollama`; `optional` holds the model of every hook (`brain.salience.module`, `brain.affect.module`, `brain.cortex.critic`, `brain.memory.notes.capture`, `brain.memory.notes.consolidator`) whose `kind` is `llm` and whose provider, its own or the inherited `llm.provider`, is `ollama`, an unset hook model meaning `llm.model`; each list is duplicate-free and `optional` leaves out names already required. A failed pull of a required model fails the container; a failed pull of an optional one is a warning (deployment DEPLOY-COMPOSE-008, DEPLOY-COMPOSE-011). `pull-models.ts` is the container's entry point: it calls `loadConfig`, so an invalid config fails with the loader's own message naming the keys.

The `tools` section ([tools](../tools/tools-design.md)) is optional and every key is defaulted, so a config with no `tools` section runs with no tool enabled. The shipped example carries it with nothing configured and the starter filler lines for the owner to edit:

```yaml
tools:
  mode: live                   # live, or mock to answer every enabled tool without reaching any server
  timeout_ms: 10000            # the hard limit of one call, counted from when it is sent; past it the call comes back as a timeout
  confirm_timeout_ms: 20000    # how long you have to answer an Allow or Deny; past it the call is refused
  max_result_chars: 1500       # the longest tool result a prompt carries
  servers: {}                  # MCP servers, added from the dashboard: name -> {url}; each token is in secrets.yaml
  allow: {}                    # per tool: enabled, acts (may change something), chat (usable for a reply to viewer chat), confirm (an acting call waits for your click; default true; turning it off applies only to the dashboard and to speech from a source you list in owner_sources), hash (set when you approve it)
  owner_sources: all           # all, or a list of audio sources whose speech counts as yours for who may use a tool
  reply:
    max_rounds: 3              # the most times the model may ask for tools in one reply
    max_calls: 3               # the most tool calls in one round
    budget_ms: 30000           # after this long since the first call, the model must answer without tools
    filler_after_ms: 1500      # a slow tool and nothing said yet: say one filler line
    max_tokens: 512            # the reply limit for a round that offers tools, so a call's JSON has room
    filler_lines:
      - "Let me check."
      - "Hold on, let me look."
      - "One sec, checking."
      - "Hang on, looking that up."
      - "Give me a moment."
      - "Let me see."
```

A `tools.servers` entry is written by the dashboard or by hand (`weather: {url: "http://host.docker.internal:8931/mcp"}`), and its token only through the secret route as `tools.servers.weather.token`; a credential does not belong in the URL. The `url` of a server is an `http(s)` URL; a name outside the grammar, a missing `url` or an `allow` entry that sets `acts` and `chat` together fails the load naming the key. A `tools.allow` entry whose tool no server lists is kept and ignored; the dashboard shows it as unknown.

`ModuleSchema` (`schema.ts`) is the shared hook config for the three region hooks and the two memory notes hooks: `kind` (blank to `rules`; `rules|llm|http`), `url` (default `""`), `timeout_ms` 8000, and `llm{provider?, model?}` where both blank values mean "inherit" and a provider without a model is rejected via `superRefine` (`schema.ts`). The override provider enum is `ollama|openai|anthropic|bedrock`: `mock` cannot be named on a hook, though a hook that inherits reaches the mock provider when `llm.provider` is `mock` (CFG-SCH-009). The whole object `.default({})`s. Hook behaviour itself belongs to region-hooks.

Required-ness is uneven: `brain.*` regions and `llm.openai/claude/bedrock` default to `{}`, but the nine top-level sections themselves, plus `vision.obs`, `avatar.vtube_studio` and `avatar.vmc` are required objects with no default (`chat.twitch` and `chat.youtube` are optional objects whose every key is defaulted), and the avatar hosts default to `host.docker.internal` and the two avatar ports to 8001 and 39539 (CFG-SCH-001, CFG-SCH-010, CFG-SCH-037, CFG-ISO-005). A blank `vision.model` while `vision.enabled` is true is a configuration gap eyes reports, not a refinement that fails the load (CFG-SCH-025); the same holds for every blank URL, model, voice or key of a selected engine or provider, which its service reports as a down dependency. A usable config therefore needs every section present (an empty `{}` suffices for `brain`, `voice`, `dashboard`), which the example provides.

Blank handling is uniform. An enum key wraps `z.enum` in `z.preprocess((v) => v || default, ...)` (`avatar.driver` blank means `null`; a non-empty unknown value still fails, CFG-ISO-005; `llm.claude.effort` blank means `low`), and a plain string key that has a default wraps `z.string().default(d)` in a preprocess that maps `""` to `undefined` (`cohost.timezone`, `llm.openai.base_url`, `vision.obs.host`, `vision.obs.source`, the two `plugin_*` keys and `ears.stt_model`, CFG-SCH-024), so a key written as an empty string, or an override whose value is empty, lands on the default instead of an empty string. `voice.pocket.url`, `ears.nemotron.url` and `ears.kyutai.url` are the exception: a blank value stays blank and is a configuration gap, only an absent key taking the Compose-service default. `voice.voice` is blank-to-the-engine's-default in the same way, the default depending on `voice.engine`, and an error for the `openai` engine, which has none. Keys with no default and a non-empty requirement (`cohost.name`, `cohost.streamer`, `llm.model`, `llm.embed_model`) still fail validation when blank, and secrets keep `""` as their default.

The dashboard's settings editor ([module-contract](../module-contract/module-contract-design.md), MOD-CFG-*) reads and writes `config.yaml` through `packages/config/src/editor.ts`, which this package exports: `sectionJsonSchema(path)` generates JSON Schema from the zod schema (objects, strings, numbers with their int and range checks, booleans, enums, arrays, defaults, descriptions; a small walker over zod 4's schema classes that reads each wrapper's inner type and each check's definition, so no JSON-Schema dependency is added); `SECRET_PATHS` marks the secret keys (CFG-SEC-003), which the schema output carries as `"x-secret": true` and `sectionSecrets` lists per section; `presentation.ts` supplies each section's and key's name and help to the schema route (MOD-CFG-019 to MOD-CFG-021); `readSection(text, section, secrets, running)` returns each key's source (`literal`, or `default` when absent from the file), editability, effective value and raw text (a secret as set or not set in `secrets.yaml`), the override name and the running units that override a key of `ISOLATION_OVERRIDES` (`isolation.overriddenBy`), and the section's unknown keys (found by walking the file against the schema, so a file that fails validation still reports them); `applySection(text, section, values)` writes edited values into the file text by splicing the edited scalar's or array's byte range (and inserting an absent key after its siblings, or an absent section at the end of the file), so every other byte, comment and alignment stays as the owner wrote it, then runs the result through `parseConfigText` and reads each edited key back to prove the text means what was asked; every key is a literal or absent, so an edit never depends on the form the key has in the file; `writeFileAtomic` overwrites the file. Configuration is read once per process (HLD tenet 10), with the one exception the renderer section states.

## Environment variables

Three tiers, none of which is validated by `ConfigSchema`. An environment variable is never an operator setting (CFG-ENV-012), and the one that carries overrides is written only by the control plane.

**Isolation overrides** (`COHOST_ISOLATION`, CFG-ISO-006, CFG-ISO-007). The control plane sets this one variable, a JSON object from override name to value, on the `docker compose` process for an isolated start of one unit (and sets it empty for every other start); Compose passes the one name to the container (deployment DEPLOY-COMPOSE-017), and the loader applies each entry by key path after reading `config.yaml` and `secrets.yaml`. The override names below are labels in that object, not environment variables: a variable named `AVATAR_DRIVER` or `LLM_PROVIDER` in `.env` or the shell is read by nothing, and `loadDotEnv` never sets `COHOST_ISOLATION` (CFG-ISO-008), so only the control plane's channel can carry an override. The overrides are start-time, per-container, not settings: `.env.example` lists none, no guide tells the operator to set one, and the settings editor reports a key a running unit has overridden (MOD-CFG-018) instead of presenting a permanent shadow. A variable that `config.yaml` owns (for example `TWITCH_CHANNEL`) is not read from `.env`, and nothing warns when `.env` defines one; a `${VAR}` placeholder inside `config.yaml` fails the load (CFG-ENV-011).

## Logging

Every cohost TypeScript program logs through `createLogger(service)`: the services through `runService` (shared-runtime SHARED-BOOT), the dashboard (a `runService` program run on the host), and the one-shots `consolidate`, `reembed` and `reflect`, which create their logger before they load the configuration (memory MEM-START-007). Each entry goes to two outputs: a terminal line a person reads, and a JSON line in a file that keeps every field. `cohostctl` and `pull-models` print plain text of their own and are not loggers. Outside the scheme altogether are the Rust programs and native code: the desktop audio helper prints its own lines, and the bus addon, like Node itself, writes to standard error directly. Raw standard error (Node's own warnings, a native addon's panic, the desktop helper's `eprintln!`) reaches the terminal or `docker compose logs` as written and never the log file.

**Settings and the bootstrap read.** The `logging` section of `config.yaml` (CFG-SCH-113, CFG-SCH-114) holds the level, the terminal format and the file's on switch and rotation limits. The logger exists before `loadConfig` runs, because `runService` creates it first so that a failed load can be logged, and the loader's own diagnostics go through it (CFG-LOG-001). So the first `createLogger` call of a process reads the `logging` section itself (CFG-LOG-002). The read runs once per process, at the first `createLogger` call or the first config-logger write, whichever comes first, and its result is reused. It first calls `loadDotEnv()`, the loader's own idempotent `.env` step that never overrides a variable the process already has, so `CONFIG_DIR` and `COHOST_DATA_DIR` set in `.env` locate the files exactly as `loadConfig` will (with `COHOST_DATA_DIR` set in `.env`, the host-run programs log to `$COHOST_DATA_DIR/logs` while the containers still log to the workspace's `data/logs/`, because the Compose bind mount is relative to the project directory); then it parses `config.yaml` in the config directory and validates that one section with the section's own schema. It seeds no file, merges no secrets and applies no isolation override: the section holds no secret path and no override, and every value in it is a literal. When the file is missing or not YAML, or the section is invalid, the read takes the schema defaults and reports nothing (CFG-LOG-003), because `loadConfig` runs moments later over the same file and reports the same fault with its full message. No environment variable decides a logging setting (CFG-LOG-004).

**One sink per process.** The first `createLogger(service)` call builds the process's sink, which owns standard output and the file `<dataDir()>/logs/<service>.log`; later `createLogger` calls share it and keep their own `name` in every entry (CFG-LOG-017). The file is therefore per program: `dashboard.log`, `chat.log`, `consolidate.log`. The config logger (CFG-LOG-001) is not a `createLogger(service)` call and never names the sink: it looks up the process's sink at each write, so a warning the loader emits after the program's logger exists lands in the program's file, and one emitted before any sink exists (a program that calls `loadConfig` without logging of its own, such as `pull-models`) prints to standard output only, under the bootstrap read's settings, and opens no file (CFG-LOG-018, CFG-LOG-019). `createLogger(service, { file: false })` builds a sink with no file (CFG-LOG-022); `tools` uses it (tools TOOL-SVC-012), because its container mounts no part of `./data` (deployment DEPLOY-COMPOSE-026).

**Crashes.** The sink installs a `process.on("uncaughtExceptionMonitor")` listener that logs the error at `fatal` with `err` before Node's default handling prints it and ends the process with status 1 (CFG-LOG-023). Since Node turns an unhandled rejection into an uncaught exception by default, the same listener covers both. The write is synchronous, so the crash is in the file. A program's own `fatal` paths (`runService` and the one-shots) are unchanged.

**Terminal, `pretty`** (the default; CFG-LOG-005 to CFG-LOG-010). One line per entry:

```
14:03:22.517 ERROR dashboard: Invalid config.yaml:
      llm.model: String must contain at least 1 character(s)
      dashboard.lan_port: must differ from dashboard.port
14:03:22.519 INFO  chat: joined channel channel=cocostream attempt=2
14:03:23.004 WARN  cortex: model call failed
    err:
      Error: connect ECONNREFUSED 127.0.0.1:11434
          at TCPConnectWrap.afterConnect (node:net:1611:16)
      {"code":"ECONNREFUSED"}
```

Time is the process's local time to the millisecond, with no date: the file keeps the full epoch timestamp, and a container's local zone is UTC unless its image sets another. The level name is padded to five characters so messages line up. The name is the logger's: the program's name, or `config` for the loader's diagnostics. A multi-line message prints as real lines, each indented by four spaces on top of whatever indentation the line already has (CFG-LOG-006): the loader's issue list (CFG-LOAD-003) indents each issue by two, so its issues sit six spaces in. A blank line of a message prints as an empty line, with no trailing spaces. Scalar fields follow the message on the first line as `key=value`, quoted as JSON only when the bare form would be ambiguous; objects, arrays and errors print below as indented JSON or as the stack. `time`, `level`, `name`, `msg`, `pid` and `hostname` are left out of the terminal line, since the layout already shows the first four and the last two are noise on one machine; the file keeps them.

Colour marks the level name only, and only when standard output is a TTY and `NO_COLOR` is unset or empty (CFG-LOG-009). Under Compose and under `mise run dev` the output is a pipe, so it carries no escape sequence, and `docker compose logs`, a redirected file and mise's per-task prefix stay plain text. Under `mise run dev` a line reads `[dev:chat] 14:03:22.519 INFO  chat: ...`, and the continuation lines carry the same prefix followed by their indentation, so the prefix does not break the layout. `docker compose logs` adds its own `chat-1  | ` prefix the same way.

Logged text can come from outside: a viewer's chat message, a tool result, a model's reply. The pretty form escapes every C0 and C1 control character and `DEL`, except the line feeds it lays out and the tab, and the bidirectional overrides and isolates U+202A to U+202E and U+2066 to U+2069 (CFG-LOG-010), so no logged text can drive the terminal or reorder what a line shows. The JSON forms are pino's: it escapes C0 controls, but `DEL`, the C1 controls and the bidirectional characters pass through as raw characters, so a JSON line shown raw in a terminal (`cat data/logs/chat.log`) is not neutralised; a JSON tool reading the file is the intended reader.

**Terminal, `json`** (CFG-LOG-011) prints pino's own line, for an owner who pipes the output into a JSON tool or a log shipper.

**File** (CFG-LOG-012 to CFG-LOG-016, CFG-LOG-020, CFG-LOG-021). The file receives pino's own JSON line for every entry at or above the level, whatever the terminal format, so it holds every field: the epoch time, the numeric level, `pid`, `hostname` and any field a caller attached. The logger creates the `logs` directory with mode 0755 and the files with mode 0644, never 0600: they are the owner's to read with any tool, and a file created by a root container stays readable from the host. Writes are synchronous and happen before the logging call returns (CFG-LOG-013), so the line a program logs just before `process.exit(1)` is in the file.

Before each entry the logger stats the file's path (CFG-LOG-014): the stat's size decides rotation, and a path that is gone or names another file than the open descriptor (deleted or replaced by hand) makes the logger open `<program>.log` afresh. One stat per entry costs nothing at cohost's log volume, and it handles a hand-deleted, truncated or replaced file at the very next entry, where tracking the size from the bytes written would keep writing into a deleted file until the tracked size reached the limit. Rotation is by size: when the file is non-empty and the next entry would push it past `max_size_mb`, the files shift up one number (`.log` to `.1.log`, `.1.log` to `.2.log`), the one past `max_files` is deleted, and a new `<program>.log` starts (CFG-LOG-015, CFG-LOG-016); an empty file never rotates, so an entry larger than the limit is written whole into the fresh file. A program's logs therefore never take more than `(max_files + 1) × max_size_mb` MiB plus one entry, 40 MiB with the defaults. A restart appends to the existing file. One writer per file is assumed: running the same program on the host and in a container at once is not a supported setup (the two would also share a consumer group), and two writers would race on rotation.

Failures never stop a program (CFG-LOG-020, CFG-LOG-021). When the directory cannot be created or a write fails (a full disk, a directory belonging to another user), the entry still prints on the terminal, the logger warns once on the terminal with the path and the error code, and it tries the file again with the next entry; the warning repeats only after a write has succeeded and a new failure begins. A failed rename or delete during rotation warns once the same way and the logger keeps appending to the current file, trying the rotation again at the next entry. The usual cause of a failing directory is ownership: application containers run as root, so a `./data/logs` that Compose creates is root's. The control plane and the installer create the directory as the owner before Compose can (control-plane CTRL-RUNTIME-016, deployment DEPLOY-INST-017), so in practice only a hand-run `docker compose up` on a checkout with no `data/logs` produces a root-owned one; the files containers write are root's in any case, readable by the owner and removable only as root. The troubleshooting page names both.

**Secrets and privacy.** No service logs a secret value (CFG-SEC-010 for the loader, and the same rule everywhere else); as a second line, the sink walks every entry (a pino `formatters.log` hook) and replaces with `[Redacted]` the value of every field, at any depth, whose key is `token`, `authorization`, `password`, `api_key`, `apikey`, `secret` and `cookie`, compared case-insensitively (CFG-LOG-024), so `Authorization` in a request's headers, an `apiKey` option or a whole `cfg.llm.openai` object logged by mistake does not carry its credential into either output. Only those key names are covered: a credential under another name, or inside a string message, is the rule's to keep out. The logs do hold conversation: chat messages, transcripts and the co-host's lines appear in them at `info` and `debug`. Rotation bounds how long they stay (the oldest file is deleted when the count is reached), and a viewer's forget request (memory) removes stored notes and memories, not log lines; an owner who must purge a viewer's text deletes the files under `data/logs/`.

**No transport, no new dependency** (CFG-LOG-025). The pretty formatter and the size rotator are small in-repo modules in `@cohost/config`, used as a pino destination stream in the logging thread: pino serialises the entry, and the sink writes that line to the file and, for `pretty`, parses it and lays it out for the terminal. Neither pino transports nor `pino-pretty` or `pino-roll` are used (Decisions & Alternatives).

**No log view in the dashboard.** The dashboard has no screen that shows service logs; an owner reads them with `docker compose logs <service>` or in `data/logs/`. A Logs screen that reads the files is a separate feature (Open Questions).

The JSON Schema `description` is generated from the table's `help` so help has one source. |
| Widgets | A closed set (`timezone`, `model` with a kind, `voice`, `sources`, `options`) | Free-form widget names; derive widgets from key names | A closed set can be checked at build time and implemented once by the page; a page that guessed a widget from a key name would drift from the schema. |
| Per-field help for structured list items | `brain.salience.reflexes` items carry `items`, a `help` for each property (CFG-PRES-009) | One help line for the whole list; no help | A reflex has five properties with different meanings and units; the operator edits them as separate fields, so each needs its own sentence. |

The listen address stays in `.env` because it decides exposure. CFG-SCH-038 |
| The two dashboard ports differ | A refinement on `dashboard`: `port` and `lan_port` must differ, reported on `dashboard.lan_port` (CFG-SCH-038) | Let the dashboard fail at bind time | A save that sets both ports equal makes the dashboard unstartable (the second bind fails, DASH-HOST-003) and it is the one place the dashboard cannot report the problem itself, so the loader rejects it where the owner is editing. A port another program holds cannot be known at save time and stays a bind-time failure. |

| Secrets file creation | `install.sh` copies `secrets.example.yaml` into `secrets/` with mode 0600; every write by the dashboard's route creates its temp file with 0600 (so the file is 0600 after a create and an update); the loader never creates it | The loader seeds it like the other user files | The other seeded files are safe to create with default permissions; a credential file must be created with the right mode, which a loader running in many containers over a bind mount cannot guarantee. |

## Open Questions & Future Decisions

- **Hook provider overrides are not `sensitive`.** `llm.provider` and `llm.openai.base_url` are gated, but a hook can name its own `llm.provider` (`brain.salience.module.llm.provider` and the other four), which can send the conversation to a hosted provider without the control token. Reading A (kept): only the chat model's keys are gated. Reading B: gate the five hook provider keys too.
- **Consolidator model follows `llm.model`?** The example writes the consolidator's `llm.model` as the same literal as `llm.model`; editing `llm.model` leaves the consolidator on the old name. A blank hook model would inherit `llm.model`, but the hook also names `provider: ollama` explicitly, and a blank model with a provider is rejected (CFG-SCH-003). Decision wanted: let a hook with a provider and no model inherit `llm.model` when providers match, or keep two literals.
- **Two writers of `secrets.yaml`.** The file has no etag, so two browser tabs saving different credentials are last-write-wins (each write is atomic and changes only its own paths). Decision wanted: whether an etag is worth it for the write-only route.
- **`vision.model` pulled while vision is off.** `ollamaModels` pulls a non-empty `vision.model` whatever `vision.enabled` says, so enabling vision later needs no second pull and a fresh install downloads the model it may never use. Decision wanted: gate on `vision.enabled`.
- **A Logs screen.** The dashboard shows no service log; the owner reads `docker compose logs` or `data/logs/`. A screen that tails the files under `data/logs/` would serve the host-run programs and the containers alike, but it is a dashboard feature with its own access question (logs carry chat text and tool arguments, which the open reads of the trust boundary already expose on `/ws`). Decision wanted: whether to add one.
- **The two upload caps.** `dashboard.inject.max_image_bytes` and `vision.upload_max_bytes` are separate keys that must agree for an injected image to pass both; nothing ties them.
