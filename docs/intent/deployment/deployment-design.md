# deployment

Parent: [high-level-design](../../high-level-design.md). Specs: [deployment-specs.md](deployment-specs.md).

## Context and Design Philosophy

The segment is everything that turns the repository into a running stack or a published artifact: the Compose topology (every service except the dashboard), the host start script for the dashboard, the one Dockerfile, the project's toolchains and command surface (`mise.toml`), the Linux installer, the CI workflows (including the ones that build and publish the docs site, whose content and checks are the [docs-site](../docs-site/docs-site-design.md) segment's), the workspace and TypeScript build setup, and the licensing and contribution rules. It owns no runtime behaviour of cohost itself; it wires the other segments together and checks that they start.

The installer, the docs site and the examples serve the owner's own stream; packaging cohost for other streamers is not a goal. A defect in the installer or the docs is still a bug and is fixed with the same weight as a runtime defect, and the installer fails loudly rather than leaving a half-working stack: it aborts on a lockfile mismatch, on a failed smoke probe, and after a fresh Docker install that needs a re-login.

Describes the intended design and the files that realize it; where the files lag, the text says so and names the gap spec.

Philosophy, with the evidence for each:

- **Toolchains belong to the project.** Node, pnpm, Rust and Python come from the root `mise.toml` and are installed per project by mise; setup installs nothing system-wide except the prerequisites that cannot be scoped to a project, a global system dependency being a last resort (HLD Tenet 14, [Toolchains and commands](#toolchains-and-commands)).
- **One command surface.** Every command a person or CI runs is a task in `mise.toml`; no `package.json` carries a `scripts` block, and a task's dependencies run the Rust and TypeScript steps it needs, so no command has a manual prerequisite.
- **One image, many services.** Every TypeScript service is built from the same Dockerfile and differs only by a build argument; the whole workspace is compiled once per image (the `Dockerfile` header).
- **Compose publishes on loopback only; the host-run dashboard is the only LAN door.** Redis, Postgres, Ollama, TTS and STT are published on `127.0.0.1` "for host-run services outside docker" (`docker-compose.yml`), and voice on `127.0.0.1:8700` for the host-run dashboard. The dashboard is not a Compose service: the owner starts it on the host (`mise run dashboard`), it launches the stack, and its LAN listener is what OBS on another machine loads the sink page and the avatar renderer page from (dashboard LLD, Host process and stack control, Avatar renderer).
- **The dashboard is started first.** Nothing has to be running for it to start; its Launch button runs `docker compose up -d --build --remove-orphans` through the control plane, so a plain `docker compose up -d` is the same stack the button brings up.
- **CPU by default, GPU as an overlay.** The base file is CPU-only and the GPU is layered on by a second file that `install.sh` selects through `COMPOSE_FILE` (`docker-compose.yml`, `docker-compose.gpu.yml` headers).
- **chat keeps its refreshed Twitch token on the host.** `./data/chat` is mounted at `/app/data/chat` on `chat` only (DEPLOY-COMPOSE-022): Twitch rotates refresh tokens, so a token persisted in the container's own filesystem would be lost when the container is recreated (Rebuild, `docker compose down`) and the stale token in `secrets.yaml` would no longer refresh. Every other service's generated files (clip caches) are cheap to regenerate and stay in the container.
- **Log files land on the host.** Every application service but `tools` mounts `./data/logs` at `/app/data/logs` (DEPLOY-COMPOSE-029), so each program's JSON log file (config CFG-LOG-012) sits in `data/logs/` beside those of the host-run dashboard and dev-loop services, and survives the container. `tools` keeps its least-privilege mounts and logs to its container output only (config CFG-LOG-022).
- **Config is bind-mounted, not baked.** `./config` is mounted at `/app/config` and `CONFIG_DIR` points at it (`docker-compose.yml`, `Dockerfile`), so the config segment's seeding writes real files on the host.
- **Each service holds only its own credentials.** The operator's one `secrets/secrets.yaml` sits outside `./config` in a directory no container mounts; each application service mounts a read-only projection holding only the secret paths its manifest entry declares ([Secret scoping](#secret-scoping)).
- **The tool service is fenced to the bus.** `tools`, the one service that talks to servers the owner adds by URL, is on a Compose network of its own that holds only `redis`, so no other container is reachable from it by name ([The tools network](#the-tools-network)).
- **Optional pieces behind profiles.** `eyes`, `ears`, `mouth` and `discord` are Compose profiles, and so is each optional speech engine server: `pocket`, `nemotron` and `kyutai` (`docker-compose.yml`).
- **Process rules checked where a machine can check them.** The Contributor License Agreement (`CLA.md`, required by `CONTRIBUTING.md`) is enforced in CI on every pull request (DEPLOY-CI-005) and the docs site builds on every pull request (DEPLOY-CI-004); linked-intent development (`CLAUDE.md`, `docs/project/spec-driven.md`) stays a convention.

Shared settings come from two anchors. `x-ts-service-base` carries `restart: unless-stopped`, `host.docker.internal:host-gateway` (reach OBS or VTube Studio on the host), `depends_on: redis: service_healthy` and the container healthcheck. `x-ts-service` extends it with `env_file: .env`, the `environment:` block (in-network service URLs `REDIS_URL`, `DATABASE_URL`, `OLLAMA_URL`, `TTS_URL`, `STT_URL`, `VOICE_URL`, `CONFIG_DIR=/app/config`, `COHOST_SECRETS_FILE` pinned to the empty string so a value in `.env` cannot move a container off its projection, `COHOST_DATA_DIR` pinned to `/app/data` so each log file lands in the `./data/logs` mount, and the one `COHOST_ISOLATION` pass-through, which wins over `.env`, so the in-network URLs, `CONFIG_DIR` and `COHOST_DATA_DIR` cannot be changed from `.env`) and the `./config:/app/config` and `./data/logs:/app/data/logs` volumes. Every application service but `tools` takes `x-ts-service`; `tools` takes only the base and states its own environment (DEPLOY-COMPOSE-026). The secrets mount differs per service, and a service's own `volumes:` replaces the anchor's list, so a service that declares secrets restates the `./config` and `./data/logs` mounts beside its secrets mount ([Secret scoping](#secret-scoping)). Injected test uploads reach `eyes` and `ears` through Redis (dashboard DASH-INJ-005), so the services take no dashboard address and nothing on the host has to be reachable from a container (DEPLOY-COMPOSE-002). A service that declares its own `depends_on` (memory, cortex, voice, ears) replaces the anchor's map and therefore re-lists `redis`. Every `services/*` directory except `dashboard` has a Compose service; `services/dashboard` has none (DEPLOY-COMPOSE-001). Every `packages/*` and `services/*` directory has a project reference in the root `tsconfig.json` (DEPLOY-REPO-001).

Because `env_file: .env` applies to every application service, any variable an operator puts in `.env` reaches every container unless the `environment:` block names it. `CONTROL_ENABLED=1` and `CONTROL_TOKEN` in `.env` therefore reach every container too; nothing in a container reads them (only the dashboard and `loadControlConfig` do), so they need no pin. `.env` holds bootstrap and access values only, never an operator setting or a credential (HLD tenet 7). Credentials reach a service only as its own projection of `secrets/secrets.yaml`, mounted read-only at `/app/secrets` (DEPLOY-COMPOSE-025, [Secret scoping](#secret-scoping)); a restart through the control plane re-projects them, so a restart still applies an edit.

The reverse direction matters for the control plane's isolated starts: `ComposeRuntime` sets the isolation preset on the `docker compose` process (`packages/control/src/runtime.ts`) as one variable, `COHOST_ISOLATION`, a JSON object of override names and values, and it reaches a container only if the `environment:` block names it. The `x-ts-service` block passes that one name through as `${COHOST_ISOLATION:-}`, and the loader applies each entry by key path (DEPLOY-COMPOSE-017, control-plane CTRL-RUNTIME-009, config CFG-ISO-007). It is a start-time override of one container, not an operator setting: `.env.example` lists none. The control plane sets the variable on every `docker compose` process it spawns, `ComposeRuntime` and `StackController` alike (the preset for an isolated start, the empty string otherwise; CTRL-RUNTIME-013, CTRL-STACK-017), and Compose interpolates `${COHOST_ISOLATION:-}` from the process environment first and `.env` second, so the explicit value wins over a line in `.env` and over a variable exported in the shell that started the dashboard or `cohostctl`; for a Windows `docker.exe` the name is listed in `WSLENV` even when empty. `COHOST_ISOLATION` is reserved for the control plane and must not be set in `.env` or the shell. A hand-run `docker compose up` is outside the control plane and nothing checks it: a value there is passed to every container it starts and applied by each as an isolation preset, so every service runs with those overrides, and a malformed value stops each service with an error naming `COHOST_ISOLATION`; a variable named like an override (`AVATAR_DRIVER`) in `.env` reaches a container through `env_file` but no process reads it.

**Container healthcheck**: `node packages/control/dist/healthcheck.js $$SERVICE`, interval 10 s, timeout 5 s, 3 retries, 30 s start period. `SERVICE` is baked into the image (the `Dockerfile` `ENV`). The script is in `@cohost/control` (`packages/control/src/healthcheck.ts`): it reads the last 200 entries of `cohost:health`, takes the newest heartbeat for the named service, and is healthy iff it is not `stopping` and younger than `STALE_FACTOR` (3) times that heartbeat's own `intervalMs`; it self-terminates with exit 1 after 4 s. The healthcheck only reports; no `depends_on` waits for an application service to be healthy, so health gates nothing at startup. Heartbeat semantics belong to control-plane.

**`models`**: built from the shared image with `SERVICE: memory` (the `consolidate` and `reembed` precedent), `./config` mounted, `OLLAMA_URL` from the shared environment, no Redis. It runs `node packages/config/dist/pull-models.js`, which loads the config (so an invalid `config.yaml` fails with the loader's message naming the keys and pulls nothing), polls `ollama` for `/api/tags` until it answers, then POSTs `/api/pull` for each name of `ollamaModels` (config CFG-MODEL-001): the required names first (`llm.model` while the provider is `ollama`, `llm.embed_model` while the embedder is `ollama`, `vision.model` while non-empty and the provider is `ollama`), then the optional hook models, printing the last 200 bytes of each response. A pull fails when the request errors, the server answers an HTTP error, or the response holds an `"error"` line (Ollama reports a pull error that begins after the response started as a 200 with an `{"error":...}` line); the entry still tries the remaining models, then exits non-zero when a required pull failed (DEPLOY-COMPOSE-011). A failed optional pull, such as the viewer-note capture model, is only a `WARNING` line on stderr and does not change the exit status, because the hook it serves degrades to its rules fallback. It has no restart policy, so the failure stays visible in `docker compose ps`. `memory` and `cortex` stay on `service_started` for `ollama`: both wait for the model backend themselves. It is not profile-gated: it runs on every plain `docker compose up -d`, as do `tts` and `stt`; the only way to start without them is to name services explicitly, as the comment at the top of `docker-compose.yml` shows. The model names are config keys, so a name the owner edits in the Settings screen is pulled by the next run of `docker compose up models`; it does not pull `ears.stt_model`.

**`consolidate`**: the memory service's one-shot (memory LLD § Viewer notes, `MEM-CONSOL-012`) as a Compose service, so the owner can run a pass after shutting the AI down by any route: `docker compose run --rm consolidate` or `cohostctl consolidate` (control-plane CTRL-CLI-008). It builds the same image as `memory` (`SERVICE: memory`; the layers are shared) and replaces the image's default command with `node services/memory/dist/consolidate.js`. It inherits `x-ts-service` for the env file, `environment` and `extra_hosts`; it sets `depends_on`, `command`, `restart`, `profiles`, `healthcheck` and `volumes`, the last restating the `./config` mount beside the `memory` unit's secrets projection, since the pass calls the consolidator model with `memory`'s credentials (DEPLOY-SECRET-002). `depends_on` is `postgres` healthy and `ollama` started, restated in full because a service's own `depends_on` replaces the anchor's map; `redis` is left out on purpose, because the entry point reads config, opens the store and calls the consolidator model, and never connects to the bus (`services/memory/src/consolidate.ts`). `docker compose run` starts the listed dependencies if they are down, so a pass works after `docker compose down`; `postgres` and `ollama` then keep running until the next `down`. The anchor's healthcheck asks for a fresh bus heartbeat, which a process that never joins the bus cannot produce, so it is disabled. The service is in the `maintenance` profile (the one-shots `consolidate` and `reembed`; the tool service `tools` has no profile, so this profile never starts it) so a plain `docker compose up -d` never starts it (a one-shot started at boot would find nothing dirty and exit, or compete with the memory service's startup); naming it in `docker compose run` runs it without `--profile`. Nothing waits on it: a stack stopped by `down`, Ctrl-C or a dashboard button is caught up by the memory service at its next start (`MEM-CONSOL-013`, `MEM-CONSOL-015`), so a skipped or failed run loses nothing. Like `models` it runs on the stack's Compose project and its network, so it reaches `postgres` and `ollama` by service name.

**Image pins** (DEPLOY-COMPOSE-014): every image carries an exact version tag, looked up in its registry when it was pinned. Redis runs on major 8 and Postgres on 18 (pgvector 0.8.7). The Postgres 18 image keeps its cluster under `/var/lib/postgresql/18/docker` and declares `/var/lib/postgresql` as its volume, so `pg18-data` mounts there, not at `/var/lib/postgresql/data`. The Postgres volume is named for its major: the 18 image's entrypoint refuses to start on a cluster of an older major found at the volume root, so a volume named `pg-data` that holds a Postgres 16 cluster would leave `postgres` restarting and every service that waits for it unstarted. A stack therefore starts with an empty `pg18-data` (there is no data migration), and an older `pg-data` volume is untouched and unused; the owner can remove it with `docker volume rm <project>_pg-data`. Redis keeps `redis-data`: Redis 8 loads a Redis 7 RDB snapshot, so existing stream data carries over. Changing a pin is an edit to the Compose files that CI then exercises.

**GPU overlay**: the `x-gpu` anchor adds an NVIDIA `deploy.resources.reservations.devices` entry (`count: all`) to `ollama`, `tts`, `stt` and swaps the `tts`/`stt` images to the GPU variants (`docker-compose.gpu.yml`). `KOKORO_IMAGE` / `SPEACHES_IMAGE` override the image in both files, so setting one for a GPU host also changes the base (CPU) file's default image. The GPU overlay's Kokoro image is the CUDA 12.8 build, the one with kernels for RTX 50-series (Blackwell) cards; a host whose card or driver it does not run on selects the CUDA 12.6 build with `KOKORO_IMAGE` ([Speech engine servers](#speech-engine-servers)).

**Fallback clips**: voice keeps its generated fallback clips under `/app/data/voice/fallback-clips` and serves them over its HTTP server; mouth fetches them into `/app/data/mouth/fallback-clips` ([voice](../voice/voice-design.md) Fallback Clips, [mouth](../mouth/mouth-design.md) Fallback Line, [config](../config/config-design.md) `dataDir()`). No volume is added and no directory is shared: both live in their container's filesystem. A container restart keeps them; after a recreate voice regenerates in the background (one TTS call per phrase), and mouth re-fetches from voice.

**The tool service**: `tools` is built from the shared image like every TypeScript service (`SERVICE: tools`) and holds no MCP server: an MCP server is reached by an HTTP(S) URL the owner writes in `tools.servers`, so the image gains no runtime and no package manager for server commands. It publishes no port. Its environment is the bus address, the config directory and the isolation pass-through, and it gets no `env_file`, no `DATABASE_URL` and no engine URL (DEPLOY-COMPOSE-026). Its volumes are the shared `./config` mount, read-only (`:ro`), which holds no credential, and its own secrets projection, `./secrets/units/tools` at `/app/secrets`, read-only, which holds only the MCP server tokens and the stream-info platform credentials (DEPLOY-COMPOSE-025, DEPLOY-SECRET-002; [tools](../tools/tools-design.md) Health and lifecycle). A `config.yaml` absent at start is not seeded inside `tools`: it fails with a read-only error and restarts until another service has seeded the file (a full-stack start recovers; `tools` alone stays down). The installer seeds the directory first. It is on the `tools-redis` network alone, so it reaches `redis` by name and no other Compose service; it reaches a server on the host by `host.docker.internal`, and a server on the LAN or the internet by its address, which is configured egress ([config](../config/config-design.md) Egress destinations; [The tools network](#the-tools-network)). It has no profile: with no tool enabled it is idle and costs almost nothing, and a profile would leave a tool the owner just enabled in the dashboard silently without a service to run it. The dashboard's apply after a tool setting restarts `tools` and `cortex` (module contract); Compose starts nothing else for it. Its startup order beyond Redis is not constrained: it waits for nothing and reports a server that is not up as a down dependency.

**The browser renderer needs nothing from Compose**: the `avatar` service, whichever driver it runs, mounts only `./config` and publishes no port. The `browser` driver writes its frames to Redis, which the container already reaches, and the dashboard on the host reads them there; the owner's VRM model files live under `data/dashboard/avatar-models/` on the host, read only by the dashboard, so the renderer needs no volume, no `.dockerignore` entry beyond `data`, which it already lists, and no published port ([dashboard](../dashboard/dashboard-design.md) Avatar renderer).

**Voice reachability**: `voice` listens on `VOICE_PORT` (default 8700, `services/voice/src/boot.ts`) and advertises `urls.voice()` = `http://voice:8700` inside Compose. Compose publishes it on `127.0.0.1:8700` only, because the dashboard runs on the host and proxies `/audio/*` to `urls.voice()`, whose default is `http://127.0.0.1:8700` (DEPLOY-COMPOSE-007). Browsers, OBS and any other player still go through the dashboard proxy, the only supported path for them; in-network sinks such as `ears` fetch `http://voice:8700` directly. A loopback publish also lets host-run services (`mise run dev`) reach a containerised voice.

## Log files

Each cohost TypeScript program writes its full structured log to `<dataDir()>/logs/<program>.log`, rotated by size (config [Logging](../config/config-design.md#logging)). The `x-ts-service` environment pins `COHOST_DATA_DIR` to `/app/data` (DEPLOY-COMPOSE-003), so a container's data directory does not depend on how the workspace root resolves inside the image or on a value in `.env`, and the anchor's `./data/logs:/app/data/logs` bind mount puts every container's file in the host's `data/logs/`, beside the host-run dashboard's and dev-loop services' files (DEPLOY-COMPOSE-029). The directory is shared: every such container can write it, as every one already writes `./config`. A per-service subdirectory mount (`./data/logs/<service>`) would keep each container to its own file, but would give the host-run and the containerised copies of a program different paths; no service logs a secret value, and the sink censors fields named like a credential (`token`, `authorization`, `password`, `api_key`, `apikey`, `secret`, `cookie`, any case, any depth; config CFG-LOG-024), so one shared directory is kept. The mount is relative to the project directory, so with `COHOST_DATA_DIR` set in `.env` the host-run programs log to `$COHOST_DATA_DIR/logs` while the containers log to the workspace's `data/logs/`.

The mount lets Compose create `./data/logs` when it is missing (DEPLOY-COMPOSE-030), so a fresh checkout starts. Containers run as root, so a directory Compose creates belongs to root, and host-run programs could then not add their files to it. The control plane therefore creates `data/logs` under the workspace root, as the user running it, before every Compose command that can create a container (control-plane CTRL-RUNTIME-016), and the installer creates it when it seeds the user files (DEPLOY-INST-017); only a hand-run `docker compose up` on a checkout with no `data/logs` leaves a root-owned one, and then host programs log to the terminal alone and warn (config CFG-LOG-020). The files a container writes are root's, mode 0644 (config CFG-LOG-012): readable by the owner, removable only as root. `.gitignore` (`data/`, DEPLOY-REPO-003) and `.dockerignore` (`data`, DEPLOY-IMG-004) already keep the files out of the repository and the build context.

`tools` mounts no part of `./data` (DEPLOY-COMPOSE-026) and writes no log file (config CFG-LOG-022, tools TOOL-SVC-012); `models` and the one-shot `pull-models` print plain text and mount none either. The containers' stdout is the readable terminal form by default (config CFG-LOG-005), so `docker compose logs <service>` reads like the host-run programs' output.

Docker keeps its own copy of every container's output. The `x-ts-service-base` anchor, which `tools` shares, sets the `local` log driver with `max-size: 10m` and `max-file: 3` (DEPLOY-COMPOSE-031), so `docker compose logs` keeps working while the daemon's copy stays bounded like the files; the infrastructure and engine services keep the daemon's default driver.

The test tasks never touch the owner's files: `test`, `test:only`, `test:file` and `test:launch` run with `COHOST_DATA_DIR` set to a new temporary directory, `CONFIG_DIR` set to a new temporary directory holding copies of `config/*.example.*`, and `COHOST_ENV_FILE` and `COHOST_SECRETS_FILE` set to paths in that temporary directory (DEPLOY-TOOL-022), so a test that logs writes no file under the checkout's `data/logs/` and no test reads the owner's `config.yaml`, `.env` or `secrets/secrets.yaml`. A test that needs its own directories still sets them, as the config tests do.

## Secret scoping

The operator keeps every credential in one file, and each service can read only the credentials it uses. The rule is about what a container can read, not what it chooses to use: a credential a service has no use for is not in its filesystem at all.

- **The operator's file.** `secrets/secrets.yaml` under the workspace root holds every secret path of `SECRET_PATHS` ([config](../config/config-design.md) Secrets file). The directory has mode 0700 and the file 0600; both are git-ignored and excluded from the build context (DEPLOY-REPO-003, DEPLOY-IMG-005). It is the one source of truth: the dashboard's write-only secret route and a hand edit both write it, and nothing else does. The dashboard and `cohostctl` run on the host and read it there. No Compose service mounts `./secrets`, `./secrets/units`, the workspace root or any other directory that holds the file (DEPLOY-SECRET-001), and `./config`, which every application service mounts, holds no credential.
- **What a unit may read.** Each unit's manifest entry declares `secrets`, the secret paths it reads: paths of `SECRET_PATHS`, the wildcard `tools.servers.*.token` included, each inside a section the unit's `config` list names ([module-contract](../module-contract/module-contract-design.md)). The list is explicit, not derived from the `config` sections, because a unit can read a section's settings without needing its credentials: `cortex` and `salience` read the `tools` section and never connect to an MCP server, and `tools` reads `chat` for the stream-info credentials and never uses the chat user tokens. A unit that declares no secret path gets no secrets mount. The lists are the manifest's declarations ([module-contract](../module-contract/module-contract-design.md) Initial `secrets` declarations); the `tools` list is `tools.servers.*.token`, `chat.twitch.client_id`, `chat.twitch.client_secret` and `chat.youtube.api_key` ([tools](../tools/tools-design.md) Health and lifecycle).
- **The projection.** For every unit that declares a secret path, the projection writes `secrets/units/<composeName>/secrets.yaml`: a YAML mapping nested as `secrets.yaml` is, holding exactly the declared paths for which the operator's file holds a value that is a non-blank string, each value trimmed, and nothing else (no comment, no other key). A declared path the operator has not set is absent, and a unit with nothing set gets an empty mapping, so a credential the owner cleared leaves the projection at the next run. The wildcard copies the `token` of every server entry the operator's file holds; the loader in the container ignores a token whose server `config.yaml` does not hold (config Secrets file). The unit directory is created with mode 0700 and the file is written through a temporary file in the same directory, created with mode 0600 before any byte is written, then renamed over the old file, so a reader never sees a partial file and no temporary copy is visible to another unit (DEPLOY-SECRET-003). A directory under `secrets/units/` that names no unit with declared secrets is removed, so a unit dropped from the manifest leaves no credential behind.
- **The mount.** A unit's Compose service mounts `./secrets/units/<composeName>` read-only at `/app/secrets`, and no other secrets path. The loader reads `<workspace root>/secrets/secrets.yaml`, which inside a container is `/app/secrets/secrets.yaml`, so the container sees its projection where the host sees the operator's file and the loader needs no setting to tell them apart. The mount uses the long syntax with `create_host_path: false`: a missing unit directory fails `docker compose up` naming the path instead of being created empty and root-owned, which would leave the service without credentials and stop the next projection from writing there (DEPLOY-SECRET-002). The one-shots `consolidate` and `reembed`, built as the `memory` unit, mount `memory`'s projection; `models` loads only model names and mounts none. The directory is mounted, not the file, so a projection replaced by rename is what a restarted container reads.
- **When it runs.** The control plane runs the projection on the host before every `docker compose` command it issues that creates, starts or restarts an application container: Launch, Rebuild, Restart all, a unit's start or restart, an isolated start and the `consolidate` and `reembed` runs. Every unit is projected each time. When the projection fails, the command is not run and the action fails with a message naming the file or directory and the reason, never a value (DEPLOY-SECRET-004). The dashboard's apply after a secret write is a restart through the control plane, so the edit reaches the units that read it. The installer seeds `secrets/secrets.yaml` at step 6 and runs the projection once the workspace is built at step 8 (DEPLOY-SECRET-006), as `mise run secrets:project`, so a hand-run `docker compose up -d` right after install finds every directory. A hand-run `docker compose up` outside the control plane uses the projection last written: a hand edit of `secrets/secrets.yaml` reaches the containers at the next action through the dashboard or `cohostctl`.
- **Reading the operator's file.** The projection reads `secrets/secrets.yaml` with the loader's rules for that file (config CFG-SEC-001, CFG-SEC-005 to CFG-SEC-007, CFG-SEC-014): an absent file makes every projection an empty mapping; a file that cannot be read, is not YAML or whose root is not a mapping fails the projection naming the file and, for a syntax error, only the line and column; a non-string at a secret path, or a value that holds a line break after trimming, fails it naming the path; a key outside `SECRET_PATHS` is never projected (DEPLOY-SECRET-005). The file may be a symbolic link (CFG-SEC-015); a file, link or not, that resolves into a directory a Compose service mounts (`./config`, `./data`, `./secrets/units`, each resolved first because it may itself be a link) would put the whole file inside a container, so the projection fails naming the file (DEPLOY-SECRET-007).
- **Where it lives.** `projectSecrets(root, units)` in `@cohost/config` reads the operator's file with the loader's rules and writes the unit files; `@cohost/control` calls it with the manifest's `secrets` lists, from the runtime and from the entry `packages/control/dist/project-secrets.js`, which the `secrets:project` task runs and the installer runs through that task. The projection is built code, so nothing runs it before the first `mise run install` and build.
- **Directories and links.** `secrets/units/` is created with mode 0700, like each unit directory under it. When `secrets/`, `secrets/units/` or a unit directory is a symbolic link, the projection fails naming it and writes nothing, because a link could send the unit files into a directory a container mounts whole. A unit name outside lower-case letters, digits and hyphens fails the projection too, because the name is a path segment under `secrets/units/` (DEPLOY-SECRET-009).
- **Who can read a projection.** The files are owned by the host user who ran the projection, with mode 0600; the containers run as root and read them. Under Docker's user-namespace remapping or rootless Docker, container root is an unprivileged host user and cannot read them, so the service's load fails naming the file (config CFG-SEC-006). Those daemon modes are not supported (DEPLOY-SECRET-010).
- **The check.** A test builds the projection from an operator file that sets every path of `SECRET_PATHS`, with two MCP servers, and fails when any unit's projection holds a path its manifest entry does not declare or lacks a declared one; a Compose test fails when a service mounts a secrets directory other than its own unit's, or any service mounts a path that holds `secrets/secrets.yaml` (DEPLOY-SECRET-008).

What the scoping does not cover: `.env` reaches every application service but `tools` through `env_file` and holds the dashboard's access token (`CONTROL_TOKEN`), which no container reads; the VTube Studio token avatar writes to `<configDir>/.vts-token` is runtime state in `./config`, which every application service mounts; Redis, which every service reaches, carries the bus. The fixed `cohost` Postgres credential is not an operator credential (DEPLOY-COMPOSE-025). Open Questions lists the first two.

## The tools network

`tools` sends conversation text to servers the owner adds by URL, and their answers come back into it: it is the one service an outside party talks to directly. It gets the least network reach that still lets it work: the bus, the host, and the addresses the owner configured.

- **Two networks.** The Compose file declares a second bridge network, `tools-redis`, beside the project's `default` network. `redis` joins both; `tools` joins `tools-redis` only; every other service declares no `networks:` and so joins `default` only (DEPLOY-NET-001, DEPLOY-NET-002). Compose resolves service names per network, so inside `tools` the name `redis` resolves and `postgres`, `ollama`, `tts`, `stt`, `voice` and every application service do not; Docker isolates one user-defined bridge from another, so their container addresses are not reachable from `tools` either (DEPLOY-NET-004 checks the name half on a real daemon; Manual verification covers the address half).
- **Egress.** `tools-redis` is not `internal`: a container on it reaches the host's networks through Docker's NAT, as a container on `default` does (DEPLOY-NET-003). That is the path to an MCP server on the LAN or the internet, which the owner configured by URL and which is configured egress ([config](../config/config-design.md) Egress destinations; [tools](../tools/tools-design.md) Egress). `tools` keeps the anchor's `host.docker.internal:host-gateway` extra host, the path to an MCP server the owner runs on the host (DEPLOY-COMPOSE-026). cohost runs no MCP server in Compose. An owner who runs one as a container publishes its port on the host's loopback and writes `http://host.docker.internal:<port>/...` in `tools.servers`, so that server joins neither network; joining it to `tools-redis` would also give it the bus (DEPLOY-NET-005).
- **What the fence does not stop.** The host gateway reaches what listens on the host. On Docker Desktop (the single-PC setup, DEPLOY-HOST-004) that is expected to include the ports Compose publishes on `127.0.0.1` (Redis, Postgres, Ollama, TTS, STT, voice, the engine servers) and the dashboard's listeners, whose reads are open (HLD Trust boundary): the owner's check from the `tools` network printed `REACHABLE 403` for the loopback dashboard (the `403` being the Host check, which a non-browser client passes by sending `Host: 127.0.0.1`), so every dashboard mutation needs the control token or an unlocked browser's session cookie whenever a token is set (dashboard DASH-CTRL-011), and a loopback bind is never a credential; on a native Linux Docker Engine a port published on `127.0.0.1` is expected not to be reachable through the gateway address, and a port bound to all interfaces is. Neither is verified on the owner's machines (Manual verification). The fence removes the service-name and Docker-network reach to the other containers; it does not filter egress by destination. The host-gateway reach is accepted and stays a manual check (DEPLOY-NET-006); owner decision.
- **Every start alike.** The network is part of the Compose file, so Launch, an isolated start of `tools` and a hand-run `docker compose up tools` place it the same way. A mock-mode `tools` opens no connection to any server and needs only `redis`.

### Edge cases

| What happens when | Behaviour |
| --- | --- |
| The operator's file is absent | Every projection is an empty mapping; each service starts with every secret unset, as a missing `secrets.yaml` does (DEPLOY-SECRET-005) |
| The operator's file is malformed | The projection fails, naming the file and the line and column only; Launch or the start does not run and the running containers keep their last projection (DEPLOY-SECRET-004, -005) |
| A secret is cleared in the dashboard | The next projection drops the path; the restart that applies the save starts the unit without it (DEPLOY-SECRET-003) |
| A unit directory cannot be written (owned by root, a full disk) | The projection fails naming the directory, and the action does not run (DEPLOY-SECRET-004) |
| A hand-run `docker compose up` before any projection, or for a unit added since the last one | `up` fails naming the missing directory, because the mount does not create its source (DEPLOY-SECRET-002) |
| `secrets/secrets.yaml` is a link into `./config`, `./data` or `./secrets/units` | The projection fails naming the link (DEPLOY-SECRET-007) |
| The operator's file holds a token for a server `config.yaml` does not list | It is projected into the units that declare the wildcard; the loader there ignores it with its usual warning (config Secrets file) |
| A unit is restarted while another unit's projection is rewritten | Each unit's file is replaced by rename in its own directory; a running service read its credentials at start and is unaffected |
| `tools` resolves a Compose service name other than `redis` | The lookup fails; Compose registers names per network (DEPLOY-NET-002, DEPLOY-NET-004) |
| An MCP server URL names a Compose service (`http://postgres:5432/`) | The name does not resolve and the server is `down` with the service's own unreachable sentence (tools MCP servers) |
| An MCP server URL is `http://host.docker.internal:<port>/` | Reached through the host gateway, whatever listens there (The tools network) |
| `redis` restarts | It rejoins both networks; `tools` reconnects through the shared retry like every service |
| `secrets/`, `secrets/units/` or a unit directory is a symbolic link | The projection fails naming it and writes nothing (DEPLOY-SECRET-009) |
| Docker runs with user-namespace remapping or rootless | Container root cannot read the 0600 projection; the service's load fails naming the file; not supported (DEPLOY-SECRET-010) |
| `COHOST_SECRETS_FILE` is set in `.env` | The `environment:` block pins it to the empty string, which wins over `env_file`, so every container reads its projection; `tools` takes no `env_file`. It is a test seam that `.env.example` does not list (DEPLOY-COMPOSE-003, config Secrets file) |
| The compose-smoke run on a fresh runner | The script writes an empty projection for every unit directory the Compose file mounts before `up` (DEPLOY-SECRET-011) |

## Speech engine servers

cohost's Compose file runs the default engines, `tts` (Kokoro-FastAPI) and `stt` (speaches), and three optional engine servers, each behind its own profile: `pocket` (`tts-pocket`, Kyutai Pocket TTS), `nemotron` (`stt-nemotron`, NeMo-Speech.cpp serving NVIDIA Nemotron Speech Streaming) and `kyutai` (`stt-kyutai`, `moshi-server` serving Kyutai STT). The owner enables a profile in `COMPOSE_PROFILES` in `.env`, as for `ears`, and selects the engine in `config.yaml` (`voice.engine`, `ears.stt_engine`); Launch then builds and starts it with the rest of the stack. Each engine's URL key defaults to its Compose service ([config](../config/config-design.md) Engine sections), so no address needs writing, and a server the owner runs elsewhere is reached by writing its URL instead. A profile that is enabled while its engine is not selected runs an idle container; an engine that is selected while its profile is not enabled has no server, so its dependency is `down` and its detail says the server is unreachable.

None of the three has a published image, so each is built. The three are not application services: they have no `SERVICE` build argument, do not use the `x-ts-service` anchor, mount no `./config`, and read no `.env` (DEPLOY-COMPOSE-002, DEPLOY-COMPOSE-025).

| Service | Built from | Pin | Port, GPU | Health | Weights |
| --- | --- | --- | --- | --- | --- |
| `tts-pocket` | the Dockerfile in the Pocket TTS repository, as a Git build context | the commit of tag `v4.0.1`, as a full commit SHA | container 8000, host `127.0.0.1:8881`; CPU only (about two cores) | `GET /health`, up once the model has loaded | downloaded at first start into the `tts-pocket-cache` volume |
| `stt-nemotron` | `docker/stt-nemotron/Dockerfile`, which fetches the NeMo-Speech.cpp repository at the pinned commit and builds it as the project's build documentation says | the commit of tag `v0.3.0`, as a full commit SHA | container 8080, host `127.0.0.1:8081`; GPU through the overlay | `GET /ready` | downloaded at first start into `stt-nemotron-cache` |
| `stt-kyutai` | `docker/stt-kyutai/Dockerfile`, which installs the `moshi-server` crate with `cargo install` on an NVIDIA CUDA 12.8 development base, with a configuration file committed beside it | the crate at exactly `0.6.4`, installed with `--locked` and the `cuda` feature; the base image `nvidia/cuda:12.8.2-devel-ubuntu24.04`, Rust `1.100.0` | container 8080, host `127.0.0.1:8082`; GPU through the overlay | none verified: a TCP connection to the port | downloaded at first start into `stt-kyutai-cache` |

**Pinning.** Every image in the Compose files carries an exact version tag (DEPLOY-COMPOSE-014). An image cohost builds is named `cohost-<service>:<upstream version>` (`cohost-tts-pocket:4.0.1`, `cohost-stt-nemotron:0.3.0`, `cohost-stt-kyutai:0.6.4`), so the tag says which version it holds; the versions were verified on 2026-11-23 and a change is made by looking the newer version up in its registry or repository first. The tag is not enough for repeatability, because a Git tag can move: the source of a build is pinned the way a workflow `uses:` ref is (DEPLOY-CI-009), by a full commit SHA for a Git build context and for any `git clone` or `ADD <git url>` in a Dockerfile under `docker/` (so `docker/stt-nemotron/Dockerfile` fetches NeMo-Speech.cpp at the pinned SHA), an exact crate version with `--locked` for the crate, and an exact tag for each base image, and a build that names a branch, a tag or `latest` as its source is refused by `scripts/lid-check.mjs`. The check covers the Dockerfiles cohost owns under `docker/` (their `FROM`, `cargo install`, `git clone` and `ADD <git url>` lines) and every Git build context; the base image of a Dockerfile that lives in an upstream repository (Pocket TTS's) is that repository's pin, not cohost's. The upstream tag stays in a comment beside the SHA.

**GPU and VRAM.** `stt-nemotron` and `stt-kyutai` need the GPU; `docker-compose.gpu.yml` reserves it for them as for `ollama`, `tts` and `stt`, and without the overlay they start without it. One RTX 5080 with 16 GB serves the chat model, the vision model, speaches and Kokoro on their GPU images, and a streaming STT server joins them; the cards are not partitioned, so an out-of-memory in one container degrades the others. The VRAM of `moshi-server` at one stream and of NeMo-Speech.cpp is unverified, and so is whether `moshi-server` runs on RTX 50-series cards. `tts-pocket` runs on the CPU and leaves the GPU alone. speaches stays in the stack as the batch engine for whole clips and the fallback ([ears](../ears/ears-design.md) STT engines), so its GPU use is added to the streaming server's.

**Weights.** A server downloads its weights at its first start, from Hugging Face, into its own named volume, so a container recreate keeps them. Each container mounts its own volume at `/root/.cache`, the cache root its server writes under: the Hugging Face hub and `pocket_tts` for Pocket TTS, `nemo-speech/models` for NeMo-Speech.cpp (its `XDG_CACHE_HOME` default), the Hugging Face hub for `moshi-server`. Pocket TTS's weights sit in a gated Hugging Face repository with a prohibited-use section, and cohost uses catalogue voices only: without accepting the gate the catalogue voices work and cloning does not, and cohost never clones. An owner who has accepted the gate and has a token sets `voice.pocket.hf_token` in `secrets.yaml` (the Settings screen's write-only field). The `tts-pocket` container never mounts `./config`, so no other secret reaches a third-party image. Launch writes the token to a file holding only that one value, `data/tts-pocket-secret/hf_token` under the workspace root (the directory Compose's `./data` paths name), rewrites it on every launch with mode 0600, and leaves the file absent when the token is blank, whitespace-only or unreadable; when `voice.engine` is `pocket` (the engine whose profile the owner enables) and the token file cannot be written, Launch fails before `up`; a token that cannot be read, or a write failure under another engine, is reported as a warning and Launch proceeds. The directory itself is always created, and is mounted read-only at `/run/cohost-secret` in that one container (a missing single file would be created as a directory by a bind mount). The container's entrypoint is a cohost script, `docker/tts-pocket/entrypoint.sh`, mounted read-only and run through the shell as the service's Compose `entrypoint: ["/bin/sh", "/cohost/entrypoint.sh"]`; it exports the file's content as `HF_TOKEN` for the server process alone when the file exists, then replaces itself with the command the service's `command:` names, which is `uv run pocket-tts serve --host 0.0.0.0 --port 8000` (the upstream image's own entrypoint, `uv run pocket-tts`, is replaced by the cohost one). The token is never in a Compose `environment:` entry, a build argument or an image layer (DEPLOY-COMPOSE-025). A stack started by a plain `docker compose up -d` without Launch leaves the file as it was. Whether the model download itself needs the token is unverified.

**Reaching them.** Each server is published on the host's loopback only, like `tts` and `stt`, for host-run services outside Compose; the containers reach one another by service name. cohost publishes no port to the LAN for any of them.

**Health checks and readiness.** Each service has a Compose healthcheck of the probe in the table, with a start period long enough for the first weights download (10 minutes) so the container is not marked unhealthy while it downloads. `voice` and `ears` list the servers in `depends_on` with the condition `service_started` and `required: false`: Compose orders them after the server's container has started when its profile is enabled and ignores them when it is not, and an unhealthy engine never stops `voice` or `ears` from starting. They start regardless and report `deps.tts` or `deps.stt` `down` while the engine is not serving (HLD tenet 5), and Launch does not fail because an engine is unhealthy. Launch's readiness wait is 180 s ([control-plane](../control-plane/control-plane-design.md)): a first start that is still downloading weights ends the wait with Launch reporting `ok: false` and naming the service as not ready on the stack card; nothing is stopped or restarted, and the service comes up when its download ends.

**The first build.** Enabling a profile makes the next Launch build the image, and Launch always passes `--build`. The `moshi-server` build compiles Rust for several minutes; the Pocket TTS and NeMo-Speech.cpp build times are unverified. Launch allows 30 minutes for `up` (control-plane Stack actions), and the stack card shows the build phase; a build that is already cached takes seconds. This is the one first-run cost an owner meets after adding an engine, so the installer's optional-profiles step names it.

**What the dashboard knows.** The three services are compose-only manifest units, like `tts` and `stt`: the Services screen shows a row for each, with start, stop and restart, and the tests that tie the Compose file to the manifest cover them ([module-contract](../module-contract/module-contract-design.md), [control-plane](../control-plane/control-plane-design.md)). They have no heartbeat and no `uses` entry anywhere: `voice` and `ears` do not list them, because a service that is not started would read as `unknown` and falsely annotate the unit that uses it; the engine's own dependency (`deps.tts`, `deps.stt`) is the signal.

**Kokoro and Blackwell.** Kokoro-FastAPI's GPU image publishes each release in two CUDA builds: `vX.Y.Z-cu126` (CUDA 12.6, also the plain `vX.Y.Z` tag) and `vX.Y.Z-cu128` (CUDA 12.8). Only the CUDA 12.8 build has kernels for RTX 50-series (Blackwell, `sm_120`) cards; on one, the CUDA 12.6 build fails with "no kernel image is available" and the container crash-loops. The GPU overlay therefore defaults `tts` to `v0.10.0-cu128`, an exact version tag (DEPLOY-COMPOSE-014), never the floating `latest-cu128` (DEPLOY-ENG-017); the tag was looked up in the registry on 2026-11-26, when `v0.10.0` was the newest release and `v0.10.0-cu128` resolved to the same image index as `latest-cu128`. The CUDA 12.8 build needs a host driver that supports CUDA 12.8 (the R570 series or newer); the NVIDIA container toolkit refuses to start it on an older driver. The two builds also differ in which cards they keep: upstream's GPU Dockerfile (`docker/gpu/Dockerfile.optimized` at the `v0.10.0` image's revision `f2a5270`) builds the CUDA 12.6 wheel set to keep Maxwell and Pascal cards (GTX 9xx and 10xx) working and the CUDA 12.8 set to add Blackwell, so the CUDA 12.8 build drops those older cards. The CUDA 12.8 tag is also amd64 only, while the CUDA 12.6 tag is published for amd64 and arm64. A Maxwell or Pascal card, a driver older than R570 or an arm64 host therefore sets `KOKORO_IMAGE` to the `v0.10.0-cu126` tag in `.env`. That the CUDA 12.8 build stays up and synthesises on the GPU of an RTX 5080, and that it runs on Turing, Ampere and Ada cards (RTX 20xx to 40xx), are unverified (Manual verification).

**Licences.** The code of Pocket TTS is MIT and its weights CC-BY-4.0 behind the gate above; the weights of Kyutai STT are CC-BY-4.0; NeMo-Speech.cpp is Apache-2.0. The built images stay on the owner's machine.

## Host-run dashboard

The dashboard is not a Compose service (owner decision; dashboard LLD, Host process and stack control). This segment owns how the owner starts it and what a fresh install needs for it:

- **Start task.** The owner starts the dashboard with `mise run dashboard` (DEPLOY-HOST-001). The task depends on `build:native` and `build:ui` ([Toolchains and commands](#toolchains-and-commands)), so the bus addon and the UI bundle are current before it runs, then it runs `mise run docs:build` as a step whose failure does not stop it, `tsc -b services/dashboard`, and `node services/dashboard/dist/index.js` from the repository root (mise runs a root task with the directory of `mise.toml` as its working directory, so the dashboard's working directory, and the `docker compose` commands it issues, are the root). The docs build comes first because the dashboard serves the built site at `/cohost/` (dashboard DASH-DOCS-001), and `docs:build` declares its sources and outputs, so a start with no docs change skips it in well under a second while a start after a pull that changed the docs rebuilds them. A failed docs build is printed with the reason the docs check or VitePress gives, followed by the line `mise run dashboard: the docs build failed (see above); starting the dashboard anyway` on stderr, and the dashboard still builds and starts: the dashboard is the program that launches everything else, and a broken page or a docs check failure must not keep the owner from going live (DEPLOY-HOST-006). The docs route then serves whatever build is in place, or its not-built page naming `mise run docs:build`. A failure of `build:native`, `build:ui` (which writes the git-ignored `services/dashboard/dist-ui/`) or `tsc -b services/dashboard` stops the task, so the dashboard never starts with a missing addon or a missing or stale UI. `tsc -b` builds the dashboard and the workspace packages it references, incrementally.
- **`.env.example`.** Lists only bootstrap and access values: the Compose settings (`COMPOSE_FILE`, `COMPOSE_PROFILES`, the image overrides), `DASHBOARD_HOST`, `CONTROL_ENABLED=1`, an empty `CONTROL_TOKEN=` with a comment saying the installer fills it and how to generate one by hand, `CONTROL_ADVANCED`, `COHOST_DOCKER_BIN`, `HEARTBEAT_INTERVAL_MS` and `COHOST_DATA_DIR` (DEPLOY-HOST-002, config CFG-USR-012). The dashboard's ports are `dashboard.port` and `dashboard.lan_port` in `config.yaml`. With control enabled and no token the dashboard refuses to start and names `CONTROL_TOKEN` (dashboard DASH-CTRL-002).
- **Installer.** Seeds `secrets/secrets.yaml` from `config/secrets.example.yaml` with mode 0600 in a directory of mode 0700 (never overwriting) and projects it for the units ([Secret scoping](#secret-scoping)), fills an empty `CONTROL_TOKEN` in `.env` with a generated 48-hex-character secret and never prints it (DEPLOY-INST-013), and its closing instructions say to run `mise run dashboard`, open the URL and press Launch, instead of `docker compose up -d` (DEPLOY-INST-008).
- **Docs site.** The install, OBS, operate and environment pages describe the host-run dashboard: first run, where the token is, the same-PC sink URL `http://localhost:<dashboard.port>/?sink=1`, the second-PC sink URL `http://<ai-pc-ip>:<dashboard.lan_port>/?sink=1` (by IP address, or by a name listed in `dashboard.allowed_hosts`, DASH-HOST-009) (defaults 3000 and 3001), the stop and consolidation controls (DEPLOY-HOST-003). The Commands page lists the `mise.toml` tasks and says that `mise run dashboard` rebuilds the docs when they changed and starts the dashboard even when that build fails (DEPLOY-HOST-005). The install pages name mise and the system prerequisites of HLD Tenet 14 as what a host needs; no page tells the reader to build the bus addon by hand, because every task that imports `@cohost/bus` depends on `build:native` (DEPLOY-README-006).

- **`.env` additions.** `DASHBOARD_HOST=127.0.0.1` (the full surface's address; `0.0.0.0` opens it to other machines and then requires control mode; it stays in `.env` because it decides how far the dashboard is exposed, which the page it serves must not be able to change) and a commented-out `COHOST_DOCKER_BIN=` for a WSL2 distro without Docker Desktop's WSL integration, where only `docker.exe` is on the path (DEPLOY-HOST-002, control-plane CTRL-STACK-012).

## Toolchains and commands

### Toolchains

The root `mise.toml` is the one place a checkout's toolchains are declared, and mise installs them per project, into the invoking user's mise data directory (`~/.local/share/mise`), on `mise install --locked`. Nothing a checkout needs is installed system-wide except the prerequisites listed under [System prerequisites](#system-prerequisites). A global system dependency is a last resort: a tool is an exception only when it cannot be scoped to the project.

| Tool | Where its version is written (the one source) | How mise gets it |
| --- | --- | --- |
| Node | `mise.toml` `[tools] node`, an exact `x.y.z` | the `node` tool |
| pnpm | the root `package.json` `packageManager` field, an exact `pnpm@x.y.z` | `idiomatic_version_file_enable_tools` lists `pnpm`, so mise reads `packageManager` (it reads `devEngines.packageManager` first; the repository declares only `packageManager`); no corepack |
| Rust | `rust-toolchain.toml` (`channel`, an exact `x.y.z`, with its `components` and `targets`) | `idiomatic_version_file_enable_tools` lists `rust`, so mise reads the file's `channel`, `profile`, `components` and `targets` and installs the toolchain through a rustup that lives under mise's data directory |
| Zig | `mise.toml` `[tools] zig`, an exact `x.y.z` | the `zig` tool (mise's core backend); the C compiler and linker for every Rust build (see [Linking through Zig](#linking-through-zig)) |
| Python | `mise.toml` `[tools] python`, an exact `x.y.z` | the `python` tool (a prebuilt standalone CPython) |
| watchexec | `mise.toml` `[tools] watchexec`, an exact `x.y.z` | the `watchexec` tool (aqua backend, checksum-verified); `mise watch` runs it |
| mise | `mise.toml` `min_version`, an exact release | the installer and the `Dockerfile` download that release's tarball and its clearsigned `SHASUMS256.asc` and verify them as [Verifying mise](#verifying-mise) describes; CI passes the version to `jdx/mise-action`, which verifies the download itself |

`mise.toml` sets `[settings] lockfile = true`, and the committed `mise.lock` records each tool's resolved version, download URL and checksum, so `mise install --locked` installs exactly those artifacts on every machine, in CI and in the image build.

`mise.toml` names no pnpm or Rust version itself: the file each ecosystem already reads is the source, and mise reads it. `rust-toolchain.toml` stays because cargo and rustup read it directly, and because its `components` (`rustfmt`, `clippy`) and `targets` (`x86_64-pc-windows-msvc`, for the desktop audio helper's Windows check, ears EARS-SRC-023) have no other home. `packageManager` stays because pnpm itself checks it. Python is pinned because the example hook server `examples/modules/server.py`, the example model stub and audio client and their tests (region-hooks HOOK-EX-*, model-backends, ears EARS-EX-*) run on it; with Python, Rust and Node all from `mise.toml`, those tests always run.

`[settings.rust]` sets `rustup_home = "~/.local/share/mise/rustup"` and `cargo_home = "~/.local/share/mise/cargo"`, so the project's toolchain never installs into or changes an operator's own `~/.rustup` and `~/.cargo`, and a user-wide rustup default is neither needed nor touched. Cargo's registry is therefore `~/.local/share/mise/cargo/registry` on the host, in CI (the path `test.yml` caches) and in the image (`/root/.local/share/mise/cargo/registry`, the path the `native` stage's BuildKit cache mount covers).

A version is also named where an ecosystem demands a literal: the `Dockerfile`'s `ARG MISE_VERSION`, its `FROM debian:<13.x>-slim` and `FROM node:<x.y.z>-trixie-slim`, and the workflows' `jdx/mise-action` `version` input. A test holds each to its source (DEPLOY-TOOL-002): `MISE_VERSION` and the action's `version` equal `min_version`, the `node:` tag equals `mise.toml`'s Node, and the `node:` tag's Debian codename is the release of the `debian:` tag (13 is trixie). The same test fails when any build file names a Node, pnpm, Rust or mise version of its own (a `node-version:` input, `engines.node`, an `.nvmrc`, `.node-version` or `.tool-versions` file, a `rust:` base image, `corepack`, `pnpm/action-setup`, `actions/setup-node`, `rustup toolchain install`).

### Linking through Zig

Rust links its `x86_64-unknown-linux-gnu` artifacts through a C compiler driver, and the bus addon, the desktop helper and every build script and proc-macro are linked that way. The project's driver is Zig from `mise.toml`, not a system `cc`: `mise.toml` `[env]` sets, each to an absolute path under `{{config_root}}/scripts/`, `CARGO_TARGET_X86_64_UNKNOWN_LINUX_GNU_LINKER` and `CC_x86_64_unknown_linux_gnu` to `zig-cc`, `CXX_x86_64_unknown_linux_gnu` to `zig-cxx` and `AR_x86_64_unknown_linux_gnu` to `zig-ar`; it sets `CARGO_TARGET_X86_64_UNKNOWN_LINUX_GNU_RUSTFLAGS` to `-Clinker-features=-lld`, so rustc never passes its self-contained `lld` flags to the wrapper; and it sets `ZIG_GLOBAL_CACHE_DIR` and `ZIG_LOCAL_CACHE_DIR` under `~/.local/share/mise/zig-cache`. `zig-cc` and `zig-cxx` run `zig cc` and `zig c++`: they remove any `--target=…` or `-target <triple>` the caller passed and any `-fuse-ld=…` and `-B<path>` (rustc's self-contained-linker arguments; the `RUSTFLAGS` setting already turns them off, but `RUSTFLAGS` set by hand overrides it and host build scripts under `--target` get no target rustflags, so the wrapper does not rely on it), replace `-lgcc_s` with `-lunwind` (Zig ships libunwind, not libgcc_s; dropping it would break unwinding, which the bus addon's panic catching relies on, event-bus BUS-NAT-ERR-006 and -011), remove `-Wl,-znostart-stop-gc`, which Zig's linker rejects, and add `-target x86_64-linux-gnu.$ZIG_GLIBC`, passing every other argument unchanged. When `ZIG_GLIBC` is empty, as for a cargo run from an IDE outside the mise environment, the wrapper stops with a message saying to run the command through mise, rather than linking against an unpinned glibc. `zig-ar` runs `zig ar` with its arguments (DEPLOY-TOOL-019). Because the setting is per target triple and the host is that triple, every cargo command run in the mise environment (`cargo build`, `check`, `clippy`, `test`, the examples' builds, and the host build scripts of the Windows `cargo check`) links through Zig, with no special subcommand and the usual `target/release/` output paths.

`<glibc>` is `mise.toml` `[env] ZIG_GLIBC`, the glibc version the addon is linked against. It is `2.35`: no newer than the runtime image's glibc (Debian 13, 2.41), so the addon built in the `native` stage loads in `node:<x.y.z>-trixie-slim`, and equal to the glibc of the oldest supported host. The supported host floor is Ubuntu 22.04 (glibc 2.35); `doctor:glibc` warns on a host below it. The toolchain test fails when `ZIG_GLIBC` is newer than the runtime image's glibc or than the host floor (DEPLOY-TOOL-003). Owner decision.

### Verifying mise

The installer and the `Dockerfile`'s `toolchain` stage fetch mise the same way, and each step's exit status is checked explicitly (a step inside an `if` or after `||` is not caught by `set -e`), so any failure stops with a message naming the step (DEPLOY-TOOL-020):

1. `curl -fsSL` downloads `mise-v<V>-linux-x64.tar.gz` and `SHASUMS256.asc` from the GitHub release `v<V>`, `<V>` being `min_version`, into a new temporary directory. `SHASUMS256.txt` is not downloaded: the clearsigned `SHASUMS256.asc` carries the checksums inside its signature, and a separately downloaded `.txt` would be covered by nothing.
2. `gpg --batch --homedir "$tmp" --import scripts/mise-release-key.asc` into a keyring in a fresh temporary home, so the operator's own keyring is never read or changed.
3. `gpg --batch --homedir "$tmp" --status-fd 1 --output sums --decrypt SHASUMS256.asc` must exit 0 and print a `[GNUPG:] VALIDSIG` status line whose last field, the primary-key fingerprint, is `24853EC9F655CE80B48E6C3A8B81C9D17413A06D`. That pins the key: a valid signature from any other key fails.
4. From `sums`, exactly one line may end in ` ./mise-v<V>-linux-x64.tar.gz`; a count other than one fails. That line is piped to `sha256sum -c -` run in the download directory.
5. Only then is the tarball unpacked with `tar`, and the binary moved into place (`~/.local/bin/mise` for the installer, `/usr/local/bin/mise` in the image).

**The release key.** `scripts/mise-release-key.asc` is mise's release signing key, fingerprint `24853EC9F655CE80B48E6C3A8B81C9D17413A06D`, which expires on 2028-01-02. The toolchain test fails when the committed key's fingerprint is not that one, or when it expires within 90 days (DEPLOY-TOOL-021). On a mise bump that changes or extends the key, the key file is refreshed from mise's documentation or `keys.openpgp.org`, and the fingerprint and expiry here and in the test move with it. A verification that fails because the key changed is the intended loud stop: nobody installs a mise signed by a key the repository has not reviewed.

### System prerequisites

These cannot be scoped to one project, so they are the only things setup installs or expects system-wide (HLD Tenet 14). Each row says why it cannot be scoped:

| Prerequisite | Why it cannot be scoped to the project | Who installs it |
| --- | --- | --- |
| Docker Engine (or Docker Desktop on WSL2) with the Compose plugin | a system daemon with a root-owned socket and a `docker` group | the installer, from Docker's apt repository, when `docker` is missing (DEPLOY-INST-002) |
| NVIDIA driver and NVIDIA container toolkit | the driver is kernel-level (on WSL2, the Windows driver); the toolkit configures Docker's runtime | the operator installs the driver; the installer installs the toolkit when a GPU is present (DEPLOY-INST-003) |
| mise | the bootstrap: it cannot install itself through itself | the installer, as one per-user binary in `~/.local/bin` (DEPLOY-INST-004) |
| `libatomic1` | a system shared library the official Node binary that mise installs links dynamically; mise installs Node's own files per project but cannot provide a library the system's dynamic loader resolves | the installer when missing (`doctor:libatomic` checks it); the `Dockerfile`'s `toolchain` stage installs it with `ca-certificates`, `curl` and `gnupg` |
| `git`, `curl`, `ca-certificates` and `gnupg` | needed before any project toolchain exists: `git` fetches the repository, `curl` with `ca-certificates` fetches mise and Docker's repository key, and `gnupg` verifies mise's signed checksums and converts Docker's key for apt | the operator (`git` to clone); the installer installs the other three when missing |

There is no C toolchain, `build-essential`, `pkg-config` or system audio library among them: Zig from `mise.toml` compiles and links every native artifact, and the desktop audio helper speaks the PulseAudio protocol through a pure-Rust client, so neither its build nor its tests need a system library (ears EARS-SRC-023).

The `doctor` task checks every row: `docker` and `docker compose version` work and the daemon answers, the NVIDIA runtime is configured in Docker when `nvidia-smi` sees a GPU, `git` and `curl` are on the path, and the dynamic loader finds `libatomic.so.1` (fix: `sudo apt install libatomic1`); it also checks that the host's glibc is at least the supported host floor (2.35), the one check that warns rather than offering an install command. It prints one line per check, `✓` or `✗`, and for each `✗` the exact command that installs or fixes it (the installer, or the apt command, or the Docker Desktop setting on WSL2), installs nothing, and exits non-zero when any check fails (DEPLOY-TOOL-017). The checks are also tasks of their own (`doctor:docker`, `doctor:gpu`, `doctor:fetch`, `doctor:libatomic`, `doctor:glibc`), and a task that needs a prerequisite depends on its check, so it fails at once with the fix instead of part-way: `infra:up`, `infra:down`, `smoke` and `test:launch` depend on `doctor:docker`.

### Commands (`[tasks]`)

Every command a person or CI runs is a task in `mise.toml`, run as `mise run <task>`. No `package.json` in the workspace has a `scripts` key (DEPLOY-REPO-002): pnpm is the package installer that the `install` task runs, and nobody types `pnpm <script>` or `cargo build` by hand. Dependency edits are the one exception and go through each ecosystem's own tool, run directly: `pnpm add` and `pnpm remove` for a workspace package, `cargo add` and `cargo remove` for a crate (owner decision); everything else is `mise run`. Tasks call the tools directly (`cargo`, `pnpm install`, `tsc`, `tsx`, `vite`, `vitepress`, `oxlint`, `node`, `python3`, `docker compose`, a script under `scripts/`), with the root `node_modules/.bin` on the path through `mise.toml`'s `[env]` `_.path`; a task whose tool is a devDependency of one package (`vite`, in `services/dashboard`) sets `dir` to that package and runs the tool from that package's `node_modules/.bin` (`node_modules/.bin/vite`), since mise puts only the root's on the path. A root task runs in the repository root.

The task graph is the reason for the design. `depends` makes each task run what it needs first, so no command has a manual prerequisite, and `sources`/`outputs` make an up-to-date step free: a task with both is skipped while its outputs are newer than its sources and nothing changed since its last successful run, and when it does run, every task that depends on it runs too. A change to `mise.toml` itself changes every task's definition, so each task with sources runs again on its next run. `mise run --force <task>` reruns a task and its dependencies regardless.

`test` depends on `test:rust` rather than running the cargo steps inline, so one `mise run test` runs the Rust and the TypeScript suites, the same command locally and in CI, while `mise run test:rust` stays available for a Rust-only change. Formatting and Clippy are `lint:rust`, not tests; `mise run lint` and `mise run test` together are what CI runs. mise runs independent dependencies in parallel; cargo serialises on its own lock of `target/`.

**Watching.** `mise watch` re-runs a task when the task's `sources` change, through `watchexec` from `mise.toml`. `mise watch --restart dev:<service>` stops the service, re-runs its dependencies (so `build:ts` recompiles the changed packages incrementally and `build:native` rebuilds the addon when a crate changed) and starts it again. `mise run dev` is one `mise watch --restart` over every `dev:<service>` task, the tasks separated by `:::` and `MISE_JOBS` set to the number of services so every long-running service gets a slot; within that one run the shared `build:ts` and `build:native` run once per change, not once per service. Because every `dev:<service>` lists `packages/*/src/**` among its sources, a change to a package restarts every service in that one watch, and a change under `services/<service>/src` restarts the watch as well; the dev loop trades a few seconds of restart for never running a service against a stale package. `infra:up` is not a `dev:` task, so no `dev:*` pattern reaches it.

**Auto-install.** `mise run` installs a missing tool before it runs a task. Where only some tools are present on purpose (the `native` image stage, which installs only Rust and Zig; the CI jobs that install only Node or Node and pnpm), the task runs with `MISE_TASK_RUN_AUTO_INSTALL=false`, so a task that needs a tool that is not there fails instead of installing every tool in `mise.toml`.

Commands outside this surface: `scripts/install.sh` (it installs mise, so it cannot be a mise task), and the commands an Extend page gives for code the reader keeps outside the checkout (their own copy of an example, their own project), which run with that code's own tools (`node`, `python3`, `cargo`) and whose rule the docs-site segment owns (DOCS-GUIDE-005). Every program inside the checkout, the examples included, runs through a task.


### Linting

`mise run lint` is `lint:ts` and `lint:rust`; CI runs it on every pull request and push to `main` (`test.yml`, DEPLOY-CI-001), and any finding fails it.

**TypeScript.** `lint:ts` runs `typecheck` first, then `oxlint --type-aware --deny-warnings` over the repository. oxlint is the linter, and `oxlint-tsgolint` gives it the rules that need type information; tsgolint is built on TypeScript 7, the compiler the workspace uses, so the type-aware rules see the same types the build does. `--deny-warnings` makes a warning fail the run like an error, so no finding is advisory; every rule the configuration turns on is set to `error` anyway.

The rule set lives in `.oxlintrc.json` at the repository root, the only oxlint configuration:

- **Plugins**: `eslint`, `typescript`, `unicorn`, `oxc` (oxlint's default set, named explicitly).
- **Categories**: `correctness` (code that is wrong or does nothing) and `suspicious` (code that is most likely wrong) at `error`. `pedantic`, `style`, `perf`, `restriction` and `nursery` stay off: they are taste, or have false positives the project would spend its time silencing.
- **Promise rules outside those categories**, at `error`: `no-misused-promises`, `only-throw-error` and `prefer-promise-reject-errors`. A dropped promise or an async callback where a void one is expected is the commonest real bug in a bus of async services, and `no-floating-promises` (`correctness`) treats node:test's `test`, `describe`, `it`, `suite` and hooks as known-safe calls, since the runner awaits them.
- **Rule options narrowed** to the project's patterns: `no-unused-vars` ignores a name that starts with `_` and a key destructured out of a rest; `no-base-to-string` leaves `unknown` unchecked (as typescript-eslint does) and ignores `ArrayBuffer`, which reaches it only through ws's `RawData`; `no-misused-spread` allows a string, because `[...text]` is how the project counts code points; `only-throw-error` and `prefer-promise-reject-errors` accept rethrowing a caught `unknown`; in test files `no-misused-promises` allows an async request handler passed to a stub HTTP server, and `require-array-sort-compare` is off, since a test sorts both sides of a comparison the same way.
- **React, for the dashboard UI**: an override for `services/dashboard/ui/**` and `services/dashboard/test/ui/**` adds the `react` plugin (its `correctness` and `suspicious` rules then apply there) and sets `react-hooks/rules-of-hooks` and `react-hooks/exhaustive-deps` to `error`. A hook called conditionally, or an effect that reads a value its dependency list leaves out, is reported. Where the dependency list is deliberately narrower (an effect keyed on one draft value that must not run again when the others change), the line carries an inline disable whose reason says so; a value that is only unstable because it is rebuilt each render (a derived array, an object of callbacks) is given a stable key or reference instead.
- **Copying sort and reverse**, at `error`: `unicorn/no-array-sort` and `unicorn/no-array-reverse` report a `sort()` or `reverse()` whose result is used, whose fix is `toSorted()` or `toReversed()` (in the ES2024 `lib`), so an expression never reorders an array a caller or another reference still holds. A statement that sorts an array in place (`list.sort(cmp);`) is not reported: there the mutation is the point.
- **Rules turned off**, each with its reason in a comment beside it in `.oxlintrc.json`:

| Rule | Why it is off |
| --- | --- |
| `typescript/no-unsafe-type-assertion` | Asserting a parsed or boundary value to its known shape is the project's pattern (JSON bodies, test fakes cast `as never`); the rule reports every one. |
| `typescript/no-unnecessary-type-assertion` | About 690 hits under the project's own compiler options, many of them assertions tsc needs (`x as never` passed to a typed parameter, `object as T`); its autofix removes those and breaks the build. |
| `typescript/consistent-return` | `noImplicitReturns` in `tsconfig.base.json` is the check: tsc reports a code path that ends without the return value the function's type promises, and it sees exhaustiveness and calls that never return. What the rule reports beyond that is correct code: a `switch` that returns in every case of a union, a test helper ending in `assert.fail`, a React effect that returns a cleanup on one path only, a VitePress hook that returns nothing to leave the page unchanged. |
| `unicorn/no-useless-spread` | Reports deliberate copies: a snapshot of a set the loop body changes, and `[...text].length` as a code-point count; its fix changes behaviour. |
| `unicorn/no-new-array` | `new Array(n).fill(x)` is unambiguous, and TypeScript types the one-argument form. |
| `unicorn/prefer-add-event-listener` | Each `on*` handler is set once on a socket or audio element just created, and the dashboard's test fakes model those properties. |
| `unicorn/consistent-function-scoping`, `eslint/no-underscore-dangle` | Style. |
| `eslint/no-shadow` | Block scoping and strict mode make a shadowed name a local choice; `no-unused-vars` catches a shadowed binding never read. |
| `eslint/no-control-regex` | The text sanitizers match control characters on purpose. |

An inline `oxlint-disable-next-line` names one rule and says after `--` why that line is the exception (a test saving `process.kill` to put it back, a rethrown caught failure, a loop whose condition changes while it awaits); a rule that is wrong for the project is turned off in the configuration instead, with its reason. oxlint honours `eslint-disable` comments too, so the same rule holds for them, and `reportUnusedDisableDirectives` makes a disable comment that suppresses nothing an error.

**Type information for tests.** tsgolint reads each file's nearest `tsconfig.json`. A package's own `tsconfig.json` covers `src/` only (it is a `tsc -b` project that emits `dist/`), so each `packages/*/test` and `services/*/test` directory holds a `tsconfig.json` that extends `tsconfig.base.json` with `noEmit` and includes the directory, and `services/dashboard/test/ui/tsconfig.json` extends the UI's options. Without them a test file would be linted under TypeScript's defaults (no `strict`, no `noUncheckedIndexedAccess`), and the type-aware rules would report what the real options make correct. The same files are what `typecheck` checks the tests with: they are not `tsc -b` projects (a `tsc -b` project must list every file it compiles, and a test imports its package's `src/` and sometimes `packages/testing/src/`), so `scripts/typecheck-tests.sh` runs `tsc -p` over each one that sets `noEmit`, after `tsc -b` (DEPLOY-TOOL-023). Editors, the linter and `typecheck` therefore see a test file under one set of options, and a type error in a test fails `typecheck` and so CI's `mise run lint`. `services/avatar/test/tsconfig.json` and `services/voice/tsconfig.test.json` are `tsc -b` projects that type-check those two services' tests in the build itself. tsgolint also needs the root `tsconfig.json` to be a solution file (`"files": []` and references only) and no `baseUrl` in any tsconfig; the workspace meets both.

**Rust.** `lint:rust` is `cargo fmt --check`, then `cargo clippy --workspace --all-targets -- -D warnings`: rustfmt's defaults and Clippy's default lint groups, with every warning an error. No Clippy lint is allowed project-wide.

## Image build

`Dockerfile`, four stages. The build stages run the same `mise.toml` tasks a developer runs, so a command is defined once; the `Dockerfile` runs no `cargo`, `pnpm`, `npm`, `corepack` or `tsc` command of its own:

0. `toolchain`: `FROM debian:<13.x>-slim` (an exact point release of Debian 13, trixie, the release the runtime's `node` image is built on, so the addon links against a glibc that image has), installs `ca-certificates`, `curl`, `gnupg` and `libatomic1` (which the official Node binary links dynamically), then mise at `ARG MISE_VERSION`, fetched and verified as [Verifying mise](#verifying-mise) describes and unpacked into `/usr/local/bin` (DEPLOY-IMG-006, DEPLOY-TOOL-020). No C toolchain: Zig from `mise.toml` is the compiler and linker.
1. `native`: from `toolchain`; copies `rust-toolchain.toml`, `mise.toml` and `mise.lock` and installs Rust and Zig through mise (`mise install --locked rust zig`: Rust's version comes from `rust-toolchain.toml`, Zig's from `mise.toml`, and both downloads from `mise.lock`), then copies `Cargo.toml`, `Cargo.lock`, `crates/`, `scripts/zig-cc`, `scripts/zig-cxx` and `scripts/zig-ar`, and runs `MISE_TASK_RUN_AUTO_INSTALL=false mise run build:native` with BuildKit cache mounts at `/root/.local/share/mise/cargo/registry`, `/root/.local/share/mise/zig-cache` and `/app/target`, which writes `cohost-bus.linux-x64-gnu.node` (event-bus Build, CI and Docker; BUS-NAT-BLD-009; DEPLOY-IMG-001). The toolchain layer is rebuilt when `mise.toml` or `mise.lock` changes, since Zig's version and the locked downloads live there; a change to the crates alone reuses it. The stage copies no `package.json` and has neither Node nor the napi CLI: the CLI only copies and names the library. It does not depend on the `SERVICE` build argument, so BuildKit builds it once for every service image.
2. `build`: from `toolchain`; `CI=true`, copies `mise.toml`, `mise.lock` and `package.json`, `mise install --locked node pnpm`, copies `pnpm-workspace.yaml pnpm-lock.yaml tsconfig.base.json tsconfig.json`, then `packages/` and `services/`, a copy of the addon from `native` into `packages/bus/native/`, then `MISE_TASK_RUN_AUTO_INSTALL=false mise run build:ts` (which runs `install`, so `pnpm install --frozen-lockfile`, then `tsc -b`). Every service image carries the addon, since every service uses the bus. The root `tsconfig.json` references every package and service project, so every service directory must exist in the build context and every image compiles the whole workspace.
3. `runtime`: `FROM node:<x.y.z>-trixie-slim`, where `<x.y.z>` is exactly the Node version `mise.toml` pins (DEPLOY-TOOL-002), `ARG SERVICE`, `ENV NODE_ENV=production SERVICE=${SERVICE}`, `COPY --from=build /app /app` (the full tree including sources and dev dependencies), `CMD ["sh","-c","exec node services/${SERVICE}/dist/index.js"]`. It carries neither mise, pnpm, Zig nor a Rust toolchain.

The Dockerfile does not prune: under pnpm 10, `pnpm prune --prod` empties `services/*/node_modules` and drops the `@cohost/*` workspace links (issue #6), and `pnpm deploy --prod` on pnpm 10.0.0 needs `inject-workspace-packages=true`, which fails `--frozen-lockfile` unless enabled workspace-wide (commit 18ea80a). The consequence is a larger image that ships dev dependencies. No `USER` is set (containers run as root, so files the config loader seeds into the bind mount are root-owned on Linux hosts) and the Dockerfile declares no `HEALTHCHECK` (Compose supplies it).

`.dockerignore`: `node_modules`, `**/node_modules`, `**/dist`, `.git`, `data`, `secrets`, `.env`, `**/*.tsbuildinfo`, `**/*.log`, `**/*.node`, `target`, `config/.vts-token`, `config/config.yaml`, `config/personality.md`, `config/expressions.yaml`. Excluding `**/*.node` keeps an addon built on the host out of the `build` stage's `COPY packages`, so the image always runs the one the `native` stage built; excluding `target` keeps Cargo's build directory (gigabytes on a developer machine) out of the context (DEPLOY-IMG-004). Excluding `.tsbuildinfo` stops stale host incremental state from making `tsc -b` in the image skip emitting while `**/dist` is ignored (issue #7, commit 7e89e4e). It does not exclude `worktrees/`, `docs/` or `graphify-out/`, which only inflate the context. `config/` can hold the VTube Studio credential (`<config>/.vts-token`, `services/avatar/src/drivers/vtube-studio.ts`) and the operator's own `config.yaml`, `personality.md` and `expressions.yaml`, and `secrets/` holds the credentials file and its per-unit projections; `.dockerignore` excludes those four files and the `secrets` directory so no credential or operator file reaches the daemon (DEPLOY-IMG-005). The `config/*.example.*` files stay in the context; the Dockerfile copies only `packages/` and `services/`, and config arrives by bind mount.

## Installer: `scripts/install.sh`

`set -euo pipefail`, runs from the repo root, flag `--no-pull`. Steps in order:

1. Detect WSL (`grep -qi microsoft /proc/version`), source `/etc/os-release`, warn if the distro is not Ubuntu or Debian.
2. Detect NVIDIA via `nvidia-smi`.
3. If `docker` is missing, install docker-ce from the Docker apt repo, `usermod -aG docker`, start the daemon (`service` on WSL, `systemctl` otherwise), then stop and exit non-zero with a "log out and back in, then re-run" message, because the current shell lacks the new group and the docker commands below would fail part-way (DEPLOY-INST-010); on every run, die if `docker compose version` fails.
4. If a GPU exists and `docker info` shows no NVIDIA runtime, install `nvidia-container-toolkit` if needed, `nvidia-ctk runtime configure`, restart Docker.
5. Ensure `curl`, `ca-certificates`, `gnupg` and `libatomic1` (system prerequisites). Unless `~/.local/bin/mise` is the release `mise.toml`'s `min_version` names, fetch and verify that release as [Verifying mise](#verifying-mise) describes and unpack it to `~/.local/bin/mise` for the invoking user, without `sudo`; an older mise elsewhere on the path is left alone and not used, because the installer runs `~/.local/bin/mise` by its full path (DEPLOY-INST-004). Then `mise trust` the repository's `mise.toml`, `mise install --locked` (Node, pnpm, Rust, Zig, Python and watchexec at the versions of [Toolchains](#toolchains)), and put mise's shims first on the path for the rest of the run (`mise activate bash --shims`), so every later step uses the project's tools whatever Node, pnpm or cargo the host has (DEPLOY-INST-009). Then add the `mise activate` line to the rc file of the operator's login shell when it is not there: `~/.zshrc` for zsh, `~/.bashrc` for bash; for any other shell, print the line to add (DEPLOY-INST-016).
6. Create `data/logs` as the invoking user (DEPLOY-INST-017). Seed `.env`, the three `config/` files (`config.yaml`, `personality.md`, `expressions.yaml`) and `secrets/secrets.yaml` (from `config/secrets.example.yaml`, mode 0600, in a `secrets/` directory of mode 0700) from their examples if absent; rewrite the `COMPOSE_FILE=` line in `.env` on every run from the GPU detected on that run (GPU: `docker-compose.yml:docker-compose.gpu.yml`), replacing a hand-set value by design; fill an empty `CONTROL_TOKEN=` line with a generated secret (DEPLOY-INST-013); `mkdir -p data` (the services that keep files there create their own folders beneath it, such as `data/dashboard/avatar-models/`).
7. Nothing further for Rust: mise installed the toolchain `rust-toolchain.toml` pins, with its components and targets, and Zig, which links it, in step 5; the installer installs no C toolchain (DEPLOY-INST-014). The host needs the bus addon because the dashboard, `cohostctl` and the Docker-free dev loop run there and import `@cohost/bus`.
8. `mise run build` (whose `install` dependency runs `pnpm install --frozen-lockfile`, aborting with its error on a lockfile mismatch as CI and the `Dockerfile` do, never falling back to a non-frozen install, DEPLOY-INST-012; then the bus addon, `tsc -b` and the UI bundle) (DEPLOY-INST-007), then `mise run secrets:project`, the projection of [Secret scoping](#secret-scoping) (DEPLOY-SECRET-006), then `mise run docs:build`, whose failure prints a warning and does not stop the installer, so the first dashboard start has docs to serve (DEPLOY-INST-015).
9. Unless `--no-pull`: `docker compose pull --ignore-buildable`, `up -d ollama models`, follow `models` logs, `docker compose wait models`.
10. Smoke test: `up -d redis postgres`, then `probe <name> 60 <fn>` polls `redis-cli ping`, `pg_isready` and, when pulling, Ollama `/api/tags` once a second until each passes (printing `  <name> ok`) or 60 s elapse, when it prints one failure line naming the probe and exits non-zero (DEPLOY-INST-007). The probes compare command substitutions rather than piping into `grep -q`, so `pipefail` cannot turn an early-closing reader into a false failure.
11. Next steps: open a new shell (so the `mise activate` line applies), run `mise run dashboard`, open the dashboard URL and press Launch, instead of `docker compose up -d` (DEPLOY-INST-008), then a step starting the optional `eyes`, `ears`, `mouth` and `discord` profiles that names `connections.discord.token` in `secrets.yaml` as the one Discord bot; the dashboard URL uses `dashboard.port` as the built `@cohost/config` loader returns it, and when the load fails the installer prints the loader's first error line and a URL without a port, since the dashboard's own start output shows the address (DEPLOY-INST-008); the Docker-free dev loop is `mise run infra:up` (which starts `redis postgres ollama tts stt`) and then `mise run dev`, or `mise watch --restart dev:<service>` for one service (DEPLOY-INST-011); and `mise run doctor` checks the host's system prerequisites.

What it stops is a closed fork that serves users or is shipped: a business that wants to keep its changes private while offering them over a network, or ship cohost inside a proprietary product, needs the commercial licence. `COMMERCIAL.md` and the README state this plainly rather than implying the AGPL forbids commercial use.

The owner can only grant that exemption for code they hold the rights to relicense. Every outside contribution is therefore accepted under an individual Contributor License Agreement, `CLA.md`, adapted from the Apache Individual CLA: the contributor keeps copyright and grants CoderCoco a perpetual, worldwide, royalty-free copyright licence that includes the right to sublicense and to relicense the contribution under other terms (commercial terms included), plus a patent licence, and represents that the contribution is their own original work or is identified as third-party work (DEPLOY-LIC-003). The text is a template adaptation, not legal advice. `CONTRIBUTING.md` requires that a contribution is offered to the public under AGPL-3.0-only and that its author has signed the CLA, and explains how to sign (DEPLOY-LIC-002).

Enforcement is the `cla` workflow (DEPLOY-CI-005):

- **Who must sign.** Each commit in the pull request resolves to one contributor: the commit author's GitHub account, else the committer's GitHub account, else the raw author name. Every such contributor must have signed, not only the pull request's opener.
- **No allow-list.** The action matches allow-list entries against the commit author's raw name, and a commit whose author email is not linked to a GitHub account resolves to that raw name, so an entry such as `CoderCoco` or `*[bot]` could be claimed by anyone who sets that author name. The workflow therefore sets none: the owner signs once like any contributor, and the repository uses no bot accounts that commit to pull requests. The action itself skips `github-actions[bot]` by account id. A bot that later commits to pull requests is added by its exact account name.
- **Signing once.** A signature is recorded once per contributor, with the pull request it was given on; later pull requests from the same contributor pass without a new comment.
- **Where signatures live.** `.github/cla/signatures.json` on the dedicated `cla-signatures` branch. The branch carries a seed file, `{"signedContributors": []}`, because v2.6.1 fails with a 404 comparison bug on the first pull request when the file is missing; after the seed only the action writes it. `main` is protected by a repository ruleset that requires pull requests, which would reject the action's direct commits, so the record lives on an unprotected branch that only the action writes. That branch must exist before the workflow first runs.
- **What it does not check.** `Co-authored-by:` trailers are not read, so a co-author named only in a trailer is not asked to sign; a pull request with human trailer co-authors needs their signatures collected by hand before it merges. Corporate contributions are out of scope: the CLA is individual only, and someone contributing on an employer's behalf opens an issue first.
- **History.** Commits already on `main` before the `cla` workflow existed are not re-checked.

### Third-party notices

The AGPL and the commercial licence cover cohost's own code. The code the UI build bundles into the pages the dashboard serves (React, and the avatar renderer's `three` and `@pixiv/three-vrm`, both MIT-licensed) is third-party code under its own licences, which for the MIT, ISC and BSD families ask that the copyright and permission notices accompany every copy, and a page served to an OBS Browser Source is a copy. The rule, which the dashboard's UI build carries out ([dashboard](../dashboard/dashboard-design.md) Libraries and notices):

- **Every bundled third-party package has a notice.** "Third-party" is a package outside the pnpm workspace that ends up in a built UI bundle (the workspace's own `@cohost/shared/head-rotation` is cohost's code under the AGPL, not a third party's). The build writes one file, `assets/third-party-notices-<hash>.txt`, `<hash>` being the first 8 hexadecimal characters of the SHA-256 of its content so that a changed file has a new name, with each package's name, version, licence expression and the full text of its licence files (a file in the package's root named `LICENSE`, `LICENCE`, `COPYING` or `NOTICE`), and each entry script's first line is a comment naming the file. Being under `assets/`, it is served wherever the bundle is, the LAN listener included.
- **Only permissive licences ship without a decision.** The build fails when a bundled third-party package has no licence file, or its SPDX licence expression is not satisfied by MIT, ISC, BSD-2-Clause, BSD-3-Clause, Apache-2.0, 0BSD, CC0-1.0, Unlicense, Zlib or BlueOak-1.0.0 (an `OR` is satisfied by any allowed alternative, an `AND` only by all), until the owner has decided and the list names it. A copyleft or unknown licence inside a served bundle may not combine with the AGPL and the commercial licence, so adding one is a decision, not an install. A licence file is one in the package root named `LICENSE`, `LICENCE`, `COPYING` or `NOTICE` in any case, optionally with a `-SUFFIX` and a `.md`, `.markdown` or `.txt` extension: `LICENSE-MIT.txt` matches, and `LICENSES` and `license-checker.json` do not. A manifest whose legacy `licenses` array lists several licences is read as an AND of them, so it is allowed only when every one is.
- **Dev-only packages are not shipped.** A package used only by the build or the tests (the bundler, the test DOM) is not in any served file and needs no notice.
- **The owner's own models are not covered.** A VRM model is the owner's asset under its author's terms; cohost stores and serves it for the owner and takes no licence in it.

## Open Questions & Future Decisions

- **The desktop helper's PulseAudio client.** The prerequisites list holds no audio library because the helper's Linux back end uses the pure-Rust `pulseaudio` client (ears EARS-SRC-023); if that client cannot capture a monitor source as the design needs, the fallback is loading `libpulse` at run time, never a system `-dev` package at build time.
- **Profiles for `tts` and `stt`.** With another engine selected, the Kokoro and speaches containers still start and `voice` and `ears` still depend on them (speaches is also the fallback batch engine). Putting them behind profiles would let an install skip them, at the price of a default `docker compose up -d` that does not start the default engines. Decision wanted.
- **Profile and engine are two settings.** The profile is in `.env`, the engine in `config.yaml`, and they must agree; a mismatch shows as a down dependency. Whether the Settings screen should offer the profile is open.
- **`.env` in every container.** `env_file: .env` gives every application service but `tools` the dashboard's `CONTROL_TOKEN`, which no container reads. Dropping `env_file` from every application service and naming the few `.env` values a container does read (`HEARTBEAT_INTERVAL_MS`, `COHOST_DATA_DIR`) in `environment:` would remove them; decision wanted.
- **The VTube Studio token in `./config`.** `avatar` writes `<configDir>/.vts-token`, which every application service can read through the `./config` mount. Moving it to a directory only `avatar` mounts is the same kind of change as the projection; decision wanted.
- **The Pocket token.** `tts-pocket`'s one-value file (`data/tts-pocket-secret/hf_token`) is separate from the per-unit projections; folding it into `secrets/units/tts-pocket/` would put every credential file under `secrets/`. Its file format differs (one raw value, read by a shell entrypoint), so it stays separate until decided.
- **One Kokoro GPU tag for every card.** Maxwell and Pascal cards (GTX 9xx and 10xx) need the CUDA 12.6 tag, which upstream builds to keep them working. Whether the CUDA 12.8 build runs on Turing, Ampere and Ada cards (RTX 20xx to 40xx) is unverified; if it does not on some of them, the GPU overlay keeps the CUDA 12.8 default and the CUDA 12.6 tag is the documented `KOKORO_IMAGE` value for those cards too.

## Manual verification

Needs a Docker daemon, a real account or a real run; the docs site's Single-PC checklist page (`docs/advanced/testing/single-pc.md`) is where each is checked and ticked off.

1. **Compose behaviours.** DEPLOY-COMPOSE-003, -006, -010, -015 and -017 and the smoke script's health polling (DEPLOY-CI-002) are read from the files, not executed against a daemon here; the launch end-to-end test (CTRL-STACK-015, DEPLOY-CI-007) skips without a daemon and has passed against Docker Desktop and runs on the CI runner's Docker.
2. **Installer.** The Docker-install stop (DEPLOY-INST-010) runs only on a machine that lacks Docker; `probe` and the port lookup were run in isolation; the mise bootstrap on a machine without mise, and a host build of the addon through Zig loading on Ubuntu 22.04, are checked on a fresh WSL2 distro.
3. **CLA workflow.** The `cla` workflow runs from the base branch on `pull_request_target`, so it cannot run on the pull request that adds it and has no local harness; its behaviour (DEPLOY-CI-005) is read from the action's source at the pinned tag until a pull request exercises it. `contributor-assistant/github-action@v2.6.1` runs on the `node20` action runtime.
4. **First real run.** `cohostctl launch` against the real stack (images, model pulls, healthchecks) is the first step of the single-PC checklist (DEPLOY-HOST-004).
5. **The tools network's reach.** From inside `tools`, on Docker Desktop and on a native Linux Docker Engine: that a container address on `default` (Postgres's, say) is not reachable, and which of the loopback-published ports and the dashboard's listeners are reachable through `host.docker.internal` (DEPLOY-NET-006).
6. **Kokoro on the GPU.** With the GPU overlay on an RTX 50-series card, the `tts` container on `v0.10.0-cu128` stays up for ten minutes without restarting, a line synthesised through it shows the Kokoro process in `nvidia-smi`, and on a Turing, Ampere or Ada card (RTX 20xx to 40xx) either the same tag works or the card is recorded as needing `v0.10.0-cu126`; Maxwell and Pascal cards (GTX 9xx and 10xx) need `v0.10.0-cu126` by upstream's build (DEPLOY-ENG-017).
