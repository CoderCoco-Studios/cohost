# model-backends

Status: the `chat()` path, the pings, the embedders, the mock's text replies and the example stubs are built and audited (the `[x]` lines of [model-backends-specs.md](model-backends-specs.md)); on Ollama and OpenAI-compatible the result contract (the `ChatMessage` union, `ChatResult`, `ChatRequest`, `ToolSpec`, `ToolCall`), `ChatError` with kind `http`, and `complete()` are built, and `chat()` is `complete()` reduced to text. Not yet built: `complete()` on the Claude, Bedrock and mock providers, `stream()`, tool calls, image input on every provider, the `connect`, `stream` and `not_configured` kinds of `ChatError`, and the mock's tool and failure markers (the `[ ]` lines of the specs file). Describes the intended design. See [high-level-design](../../high-level-design.md).

## Context and Design Philosophy

`@cohost/llm` (`packages/llm`) hides the chat-model backend behind one small interface, `ChatProvider`, so that "use a stronger model" is a config change (`llm.provider`, `llm.model`) rather than a code change (`packages/llm/src/index.ts`; HLD tenet 2: a model provider is config plus one adapter file, never a brain region). The callers are cortex (a streamed reply, with the chat model's tool loop), the memory reflect job and the `llm`-kind hooks built by `region-hooks` (plain text or JSON), and the eyes describer (a text reply to a frame). None of them learns which vendor is behind the provider. One contract serves all of them: a caller that wants only text calls `chat()`, and the streamed reply, the model's tool calls and image input are separate, opt-in parts of the same contract that a simple caller never touches.

Observed principles:

- **One interface, five implementations.** `ollama` (local GPU, the config default), `openai` (any server that speaks `POST /chat/completions`), `anthropic` (Claude API), `bedrock` (Claude on Amazon Bedrock) and `mock` (offline, opt-in only). `index.ts`, `index.ts`.
- **Embeddings are decoupled from the chat model.** Switching the chat model never changes the vector size of the memory table, because embedders never follow the chat provider. The package exports the `Ollama` and `HashEmbedder` classes and no factory that maps the chat provider to an embedder; memory chooses between them with `brain.memory.embedder` (LLM-EMBED-004).
- **No retries of its own.** Each call is a single request, streamed only when the caller asks for a stream; the Ollama and OpenAI-compatible providers never retry, and the Claude and Bedrock SDK clients retry a failed request at most twice, before any reply has begun (LLM-CLAUDE-014). Failures are thrown as `ChatError`, a timeout as `TimeoutError` and a caller's abort as the caller's abort reason (see Errors); callers decide what to do (hooks fall back to rules, the cortex waits and retries at the call site, and a streamed reply that fails is never retried once any of it has been delivered).
- **Tool calls cross the boundary; tools are never run here.** The provider carries tool definitions to the model, the model's requests for tool calls back to the caller, and the results forward again as messages. It never calls a tool and knows no MCP server: cortex runs the loop and the `tools` service runs the tools over the bus (HLD Tool use, tenet 1).
- **The package sends what it is asked to send.** It never silently drops tools or images from a request and never guesses what a model can do. Which capabilities a model has is declared by the owner through configuration; a backend that rejects a request fails the call as an ordinary `http` error. Streaming degrades (the reply arrives late but whole) (see Capabilities and what the contract promises).
- **Every request is bounded (HLD tenet 3).** A caller's `AbortSignal` cancels a request; without one, the default timeout `llm.timeout_ms` (default 60000 ms, CFG-SCH-013) applies to chat, embed and ping, so a black-holed backend fails a call rather than hanging it. `requestSignal` returns the caller's signal when there is one and `AbortSignal.timeout(llm.timeout_ms)` otherwise; the Claude path passes the SDK request option `timeout` instead of a signal (LLM-CHAT-008). A streamed reply is bounded differently, because it legitimately lasts longer than one timeout: see Streamed replies. The package reads `llm.timeout_ms` directly from the config object it is given; the config schema always supplies it.
- **The package is a pure library.** It owns no bus subscriptions, publishes no events, runs no timers, and emits no heartbeat. Its only health surface is `ping()` plus `lastError`, which cortex consumes (`services/cortex/src/startup.ts`).

Dependencies: `@cohost/config` (types, `urls.ollama()`), `@cohost/working-memory` (`TRANSCRIPT_TAGS`), `@anthropic-ai/sdk`, `@anthropic-ai/bedrock-sdk` (`packages/llm/package.json`). The mock backend lives in `packages/llm/src/mock.ts` and is re-exported from the index (`index.ts`).

## Provider contract and factory

```ts
type ChatMessage =
  | { role: "system"; content: string }
  | { role: "user"; content: string; images?: string[] }   // base64 images for a model that takes them (LLM-VIS-001)
  | { role: "assistant"; content: string; toolCalls?: ToolCall[]; continuation?: unknown }
  | { role: "tool"; callId: string; name: string; content: string; isError?: boolean };  // one tool's result
interface ToolSpec { name: string; description: string; parameters: object /* JSON Schema, type "object" */ }
interface ToolCall { id: string; name: string; arguments: Record<string, unknown>; invalid?: string }

interface ChatOptions { maxTokens?: number; temperature?: number; json?: boolean; signal?: AbortSignal }
interface ChatRequest extends ChatOptions { tools?: ToolSpec[] }

interface ChatResult {
  text: string;                       // trimmed; "" when the model said nothing or only asked for tools
  toolCalls: ToolCall[];              // in the order the model asked
  finish: "stop" | "length" | "tool_calls" | "refusal";
  message: ChatMessage;               // the assistant message to append to the history, role "assistant"
}
type ChatEvent =
  | { type: "text"; delta: string }
  | { type: "tool_call"; call: ToolCall }                  // a whole call, emitted once its arguments are complete
  | { type: "done"; result: ChatResult };                  // exactly once, last, on success only

interface ChatProvider { readonly name: string; readonly model: string;
  chat(messages, opts?: ChatOptions): Promise<string>;                  // plain text
  complete(messages, req?: ChatRequest): Promise<ChatResult>;           // text, tool calls, finish reason
  stream(messages, req?: ChatRequest): AsyncIterable<ChatEvent>;        // the same reply, as it is generated
  ping(): Promise<boolean>; lastError?: string;
  readonly pingIsNominal?: boolean }  // true only on bedrock: ping() is not a probe (LLM-PING-006)
class ChatError extends Error { kind: "http" | "connect" | "stream" | "not_configured"; status?: number }
interface Embedder { embed(text: string): Promise<number[]> }
```

(`index.ts`.) The three calls are one request with three ways to read the reply (LLM-IF-020). `complete()` and `stream()` build their request, apply the token budget, defaults, timeouts, retry rule, `json` handling, images and stop sequences as `chat()` does on each provider, except where this document says otherwise (LLM-CHAT-011 to LLM-CHAT-022, LLM-STOP-011 to LLM-STOP-018, LLM-CLAUDE-023 to LLM-CLAUDE-033, LLM-VIS-008 to LLM-VIS-013, LLM-MOCK-020, LLM-MOCK-021).

- **`chat()` is the simple call.** It resolves to the trimmed reply text and is text only: it offers no `tools` and never returns a tool call. A tool call the model emits unasked is ignored and the text is returned. A `chat()` call whose history contains a `tool` message or an assistant message with a non-empty `toolCalls` is a programming error. The region hooks, the memory reflect job and the eyes describer use it and see none of the types around it. It is `complete()` reduced to `text`, so it fails wherever `complete()` fails (LLM-IF-004, LLM-IF-011, LLM-IF-012).
- **`complete()`** sends a non-streamed request and resolves to a `ChatResult` (LLM-IF-005 to LLM-IF-007). `finish` is `length` when the token cap ended the reply, even if the model also asked for tools (completed calls are kept in `toolCalls`); otherwise `tool_calls` when the model asked for tools (whether or not it also wrote text), `refusal` when a Claude provider reports a refusal (and then `text` is `""` and `toolCalls` is empty, as for `chat()`), and `stop` (LLM-IF-013 to LLM-IF-016, LLM-CLAUDE-021). Only a tool call whose arguments the token cap cut off is dropped; calls completed before it are kept; the reply finishes as `length` (LLM-TOOL-022).
- **`stream()`** returns an async iterable that sends the request when it is first read. It yields `text` events as the model generates them, a `tool_call` event for each tool the model asks for, all at the end of the reply (LLM-TOOL-023), then one `done` event whose `result` carries the finish reason, the assistant message and the tool calls, and whose `result.text` always equals the concatenation of the `text` deltas delivered and whose `result.toolCalls` always equals the `tool_call` events delivered, in order (LLM-STREAM-009, LLM-STREAM-032). A failure is thrown by the iterator and no `done` follows, so a truncated reply never looks complete. Ending the loop early (`break`, or `return()` on the iterator) cancels the request and is not an error. The caller keeps the text it has already been given; the error carries no copy of it (LLM-IF-008 to LLM-IF-010).
- **Messages.** `content` is always a string. A user message may carry `images`. An assistant message carries `toolCalls` when the model asked for tools; a `tool` message answers one call by `callId` and `name`, with `isError` set when the tool failed (a provider whose API has no error flag sends the content as given; LLM-TOOL-019). Results for several calls in one turn are separate `tool` messages in the order of the calls. `ChatResult.message` omits `toolCalls` when the model asked for none (LLM-IF-022), and an assistant message with `toolCalls` and empty `content` is sent without a text block (Claude) or in the vendor's form for no text, `null` content for OpenAI-compatible servers and an empty string for Ollama (LLM-TOOL-013, LLM-TOOL-027, LLM-TOOL-028). A caller appends `ChatResult.message` to the history unchanged: it carries whatever the adapter needs to continue the model's turn (`continuation`, opaque to every caller, for example Claude's thinking blocks, which the API requires back with the tool results; a `continuation` carries the `name` of the provider that produced it, and a provider ignores one whose name differs from its own, so `anthropic` and `bedrock` do not read each other's (LLM-TOOL-030); LLM-TOOL-014, LLM-TOOL-015).
- **Tool definitions.** `ToolSpec.name` matches `[A-Za-z0-9_-]{1,64}`, the strictest rule among the backends; a name outside it is a programming error thrown before any request (LLM-TOOL-001). `parameters` is a JSON Schema object. A `ToolCall.arguments` is always a parsed object: the adapter parses a backend that sends a JSON string. When the model's arguments are not a JSON object, `arguments` is `{}` and `invalid` holds the raw text, so the caller can answer the call with an error result instead of losing it (LLM-TOOL-016); an empty or whitespace-only arguments string from a backend gives `arguments` `{}` with no `invalid` (LLM-TOOL-029). An assistant message whose `ToolCall` has `invalid` is sent back to the model with `arguments` `{}`; the raw text reaches the model only through the error result the caller writes for that call (LLM-TOOL-017). Backends that send no call id (Ollama) get one synthesized, unique within the reply (LLM-TOOL-004). A reply's `toolCalls` are in the order the model asked (LLM-TOOL-024).
- **`json: true` and a non-empty `tools` array are exclusive.** "With `tools`" means a non-empty array everywhere in this document: an empty array is the same as no `tools`, so stop sequences are sent as for a call without tools and `json: true` with `tools: []` is not an error (LLM-STOP-019, LLM-TOOL-026). A request with both is a programming error thrown before any request: a JSON reply is a different kind of call from a tool turn (see the Decisions table; LLM-TOOL-002).
- **`signal`** aborts the in-flight request and exists for hook timeouts and for cortex to cancel a streamed reply (`index.ts`).

### Errors

Every failure this package raises from `chat()`, `complete()` and `stream()` is a `ChatError` with a `kind` (LLM-ERR-001):

- `connect`: the backend could not be reached or the connection failed before any reply, on any provider and any of the three calls. It carries no `status` (LLM-ERR-008, LLM-ERR-009).

- `http`: the backend answered non-2xx. It carries `status`, and the message keeps the text `<provider> chat <status>: <body>` (LLM-CHAT-005, LLM-ERR-007). Errors from the Claude and Bedrock SDKs that carry an HTTP status are wrapped the same way (LLM-ERR-002). A backend's rejection of a request is an `http` error whatever its body says (LLM-ERR-004).
- `stream`: a stream whose response had begun and that dropped, ended without a final event, or sent an unparseable chunk (LLM-STREAM-021 to LLM-STREAM-023).
- `not_configured`: a provider whose credentials are not set (LLM-ERR-003, LLM-CLAUDE-017, LLM-CLAUDE-018).

Two failures are not `ChatError`: a timeout is the `TimeoutError` an `AbortSignal.timeout` gives (LLM-ERR-005), and a caller's abort is the caller's abort reason (LLM-ERR-006).

A request the caller built wrongly is a programming error and is a `TypeError` thrown before any request: a tool name outside the pattern (LLM-TOOL-001), `json` together with `tools` (LLM-TOOL-002), image data in no supported format (LLM-VIS-005), and a `tool` message or an assistant message with `toolCalls` passed to `chat()` (LLM-IF-012). `chat()` and `complete()` reject with it and a `stream()` iterator throws it on the first read; `stream()` itself never throws synchronously, whatever the failure, including `not_configured` (LLM-IF-021); none of them sends a request first. Once a streamed response has begun, any failure is kind `stream`, whatever the SDK's error type, for example a Claude `error` event mid-stream (LLM-STREAM-021).

`json: true` means "a JSON reply is wanted": no stop sequences are sent and, where the backend has a schema-free JSON mode, it is requested: Ollama `format: "json"` and OpenAI-compatible `response_format: {type: "json_object"}` (LLM-CHAT-010). Claude has none, so its reply is parsed by the caller; the token cap can still truncate a JSON reply mid-object, which the caller treats as unusable.

`createChatProvider(cfg.llm)` is a `switch` over `cfg.provider` with no default branch; it relies on the config enum for exhaustiveness.

### How each provider maps streaming, tool calls and images

The streaming column is LLM-STREAM-001 to LLM-STREAM-008, LLM-STREAM-030 and LLM-STREAM-031, the tool column is LLM-TOOL-003 to LLM-TOOL-013, LLM-TOOL-018 and LLM-TOOL-020, and the image column is LLM-VIS-001 to LLM-VIS-003 and LLM-VIS-007.

| Provider | Streamed reply | Tool calls | Images on a user message |
| --- | --- | --- | --- |
| `ollama` | `stream:true`; NDJSON lines `{message:{content, tool_calls?}, done, done_reason}`; a `content` piece is a `text` event | `tools:[{type:"function", function:{name, description, parameters}}]`; `message.tool_calls[].function` gives `name` and an `arguments` object; no call id, so one is synthesized; a result goes back as `{role:"tool", tool_name, content}` | the message's `images` array, base64 (LLM-VIS-001) |
| `openai` | `stream:true`; SSE `data:` chunks until `[DONE]`; `delta.content` is a `text` event; `delta.tool_calls` fragments are assembled by `index` and each call is emitted once `finish_reason` has arrived, after the text; the chunk carrying `finish_reason` is the final event, so a stream that ends after it without `[DONE]` completes and one that ends before it fails with kind `stream` (LLM-STREAM-036, LLM-STREAM-037) | `tools:[{type:"function", function}]`; `message.tool_calls[]` with an `id` and `arguments` as a JSON string, which the adapter parses; a result goes back as `{role:"tool", tool_call_id, content}`; an assistant turn sends its calls with `arguments` re-serialized | `content` becomes `[{type:"text"}, {type:"image_url", image_url:{url:"data:<media type>;base64,<data>"}}]` for a message that has images, and stays a string otherwise |
| `anthropic`, `bedrock` | the SDK's streaming request; `text_delta` events are `text` events, `thinking` deltas are dropped, a `tool_use` block's `input_json_delta` fragments are assembled and the call is held until `stop_reason` arrives in the final message delta and is then emitted with the other calls, after the text | `tools:[{name, description, input_schema}]`; `tool_use` blocks give `id`, `name` and `input`; results go back as `tool_result` blocks (`tool_use_id`, `is_error`) in one user turn, consecutive `tool` messages being merged into it; an assistant turn sends its text and `tool_use` blocks, preceded by the thinking blocks kept in `continuation` | `{type:"image", source:{type:"base64", media_type, data}}` blocks before the message's text |
| `mock` | see The mock backend | see The mock backend | accepted and ignored |

Common rules:

- **Finish reason.** OpenAI `finish_reason` `tool_calls`, Claude `stop_reason` `tool_use`, or any `tool_calls` in an Ollama message, gives `finish` `tool_calls`; `length` and `max_tokens` give `length`; Claude `refusal` gives `refusal`; everything else is `stop`. `length` takes precedence over `tool_calls` whenever the token cap ended the reply. A tool call cut off by the cap is dropped, since its arguments are incomplete and the model's intent is unknown; calls completed before it are kept (LLM-IF-017 to LLM-IF-019, LLM-TOOL-022).
- **Image media type.** A message's `images` are base64 strings with no media type, so the adapters that need one (OpenAI-compatible, Claude, Bedrock) read it from the decoded leading bytes (JPEG, PNG, GIF, WebP); data in none of those formats is a programming error thrown before any request (LLM-VIS-004, LLM-VIS-005).
- **No stop sequences with tools.** A request that offers `tools` sends no stop sequences on any provider, because a stop could cut the JSON of a tool call, as it could cut a `json: true` reply. The reply is then bounded by the token cap and by the caller, which already treats the first line as the spoken line (see Stop sequences; LLM-STOP-008 to LLM-STOP-010).
- **Retries and `lastError`.** `complete()` and `stream()` follow the retry rules of `chat()`: none from this package, the Claude SDK's at most two before any reply begins (LLM-CHAT-009, LLM-CLAUDE-020). `lastError` is set only by `ping()`; a failed reply is thrown and leaves it alone (LLM-PING-007).

### Streamed replies

A streamed call has to stay bounded without capping a reply that is long because it is still producing text, and a caller that has already spoken part of it must not be handed a result that looks whole.

- **Ordering.** Tool calls are delivered at the end of a streamed reply, on every provider: the `tool_call` events are yielded only once the backend has reported how the reply ended, after every `text` event, in the order the model asked and immediately before `done`, so a call cut off by the token cap is never delivered. Text from several blocks is joined with no separator (LLM-STREAM-012, LLM-STREAM-013).
- **Trimming.** The concatenation of all `text` deltas equals `done.result.text`, which is the reply's text as a whole trimmed as `chat()` trims it. The adapter drops leading whitespace until the first non-whitespace character and holds trailing whitespace back until more text follows it, so a delta never starts a reply with whitespace and the held-back tail is never emitted. Whitespace held back is released if more text follows it, and is never emitted otherwise. A caller can therefore speak deltas as they arrive and have said exactly the trimmed reply (LLM-STREAM-009 to LLM-STREAM-011). A reply in which the model wrote no text delivers no `text` event and a `done` with `text` `""` (LLM-STREAM-028).
- **Stop sequences** are sent with the request as for a non-streamed call and the backend ends the stream at one; the adapter performs no cut of its own. A `text` event arrives only for text the backend has produced, so the first-line rule that cortex applies to the reply applies to the streamed text the same way (cortex segment; LLM-STREAM-014).
- **Timeouts.** Two bounds, both `llm.timeout_ms`, always apply to a streamed call, whether or not the caller passes a `signal`: the time from sending the request to the first output, measured on content the backend sends and not on events delivered: the first reply text (including whitespace that is held back), the first tool-call fragment, or the end of the reply, whichever comes first (this includes the Claude SDK's retries of the initial request, and thinking does not satisfy it, so a model that thinks longer than `llm.timeout_ms` before any output fails the stream), and then, after the first output, the gap between one backend event and the next (a thinking delta or a keepalive counts as an event here). Both clocks run only while the caller is waiting on the iterator, that is while a `next()` is pending; time the caller spends between reads is not counted. Either one rejects the iterator with a `TimeoutError` (the same error an `AbortSignal.timeout` gives). There is no total-duration bound in this package: how long a reply may run is bounded by `maxTokens` and by the caller's `signal`, which the caller can abort at any point. A caller's `signal` adds a way to cancel; for a streamed call it does not replace the two bounds, unlike for `chat()` (LLM-CHAT-008; LLM-STREAM-015 to LLM-STREAM-019, LLM-STREAM-034, LLM-STREAM-035).
- **Failure and abort after text was delivered.** The iterator throws: a `ChatError` of kind `http` (the backend answered non-2xx, before any event) or `stream` (the connection dropped after the response began, or the stream ended without a final event, or a chunk was not parseable), the `TimeoutError` above, or the caller's abort reason. There is no `done` event and no retry once an event has been delivered, because a retry would repeat what was already said. The caller decides: with nothing delivered it treats the call as a failed reply (cortex ends the think without a line, as for any failed model call; the pre-generated fallback lines belong to mouth and play only when playback fails); with text already delivered it keeps what it has, treats the line as cut short and does not speak a fallback over it (LLM-STREAM-020 to LLM-STREAM-026).
- **Refusal.** On a non-streamed call a refusal beats tool calls: `complete()` returns `finish` `refusal` with empty `text` and `toolCalls` whatever the model asked (LLM-IF-013 does not apply). A Claude `refusal` ends the stream with `done` whose `finish` is `refusal`. The two `done` invariants still hold: `result.text` is whatever text had been delivered and `result.toolCalls` is whatever `tool_call` events had been delivered, in order (normally nothing in both), not blanked, since delivered output cannot be recalled; so for the same refused reply `stream()` and `complete()` may give different `text` (LLM-STREAM-033). `chat()` and `complete()` return `""` for a refusal (LLM-CLAUDE-006, LLM-CLAUDE-021). A caller that streams treats `refusal` as "say nothing more" (LLM-STREAM-027).
- **A backend that does not stream.** A server that ignores `stream:true` and answers one JSON body is read as a single reply: the adapter emits it as one `text` event (and a `tool_call` event for each call) and then `done`. Correctness holds and only the latency benefit is lost (LLM-STREAM-029).
- **`ping()`** is unaffected: it checks reachability and does not stream.

### Capabilities and what the contract promises

A provider's adapter can send tools, images and streaming, but whether the configured model accepts them depends on the model, which the package cannot know (a local model served by Ollama may have no tool support; an OpenAI-compatible server may serve a text-only model). The owner declares what the model can do, through configuration, and the package never infers it from an error.

- **Streaming.** Always available; it degrades to a late whole reply (above).
- **Tools.** Tools reach a model only because the owner configured tools, and none are configured by default; configuring tools is the switch, so choosing a model that can use them is the owner's when they turn tools on. The package sends the tools it is given, drops none and answers none without them. A backend that rejects the request fails the call as an ordinary `http` error and the package does not retry without the tools (LLM-ERR-004, LLM-CHAT-009). A model that accepts `tools` and simply never asks for one returns text, which is a normal result (LLM-TOOL-021). A model that writes a tool call as plain text is returned as text.
- **Images.** Frames reach a hosted provider only because the owner chose that provider for the describer, so choosing a model that takes images is the owner's when they do. The package sends the images it is given and drops none; a backend that rejects the request fails the call as an ordinary `http` error. The package cannot detect a model that accepts images and ignores them (Choose a model page).
- **Egress of frames (HLD tenet 8).** The package sends images to the endpoint the configured provider names and decides nothing about whether that endpoint is hosted. The setting that lets a frame go to a hosted chat provider is explicit and has no hosted default; it belongs to the configuration and to eyes, which builds the describer's provider with `createChatProvider({...llm, provider: <the vision provider>, model: vision.model})`, so the factory takes no new parameter and a hosted provider's credentials are the ones already under `llm.claude.*`, `llm.openai.*` and `llm.bedrock.*`.

Class-level facts: `ClaudeBase` is not exported; tests reach into the protected `client` field by cast (`llm.test.ts`).

## Stop sequences and the transcript coupling

Two constants drive truncation (`index.ts`):

- `TRANSCRIPT_STOPS` = `"\n"` followed by each tag in working-memory's `TRANSCRIPT_TAGS` (`"\n[chat]"`, `"\n[voice]"`, `"\n[screen]"` today), derived rather than copied (LLM-STOP-007): "the model started writing the next transcript entry".
- `REPLY_STOPS = ["\n\n", ...TRANSCRIPT_STOPS]` - a blank line also ends a spoken reply. The comment states "Exactly four entries: OpenAI-style APIs reject more than four stops" (`index.ts`).

Behavior matrix:

| Call | Ollama / OpenAI | Claude (Anthropic and Bedrock) |
| --- | --- | --- |
| reply (`json` not true) | `REPLY_STOPS` (4 entries) | `TRANSCRIPT_STOPS` (3 entries, no `"\n\n"`) |
| `json: true` | Drop stop sequences and request the backend's JSON mode where it has one (Ollama, OpenAI-compatible); a judgement that wants JSON never asks for it through a tool call | Stops dropped only; tool calls or prefill for Claude; keep stops | "a blank line or a transcript tag inside JSON would truncate it" (comment `index.ts`); commit `969f6d7` "JSON calls send no stop sequences". Ollama `format` and OpenAI `response_format` are cheap to request and make a well-formed object likely; Claude has no schema-free equivalent without tools or prefill, so its path stays prompt-and-extract, as does the caller's validation for every backend (`region-hooks` extracts the first balanced value, the region validates it, an unusable reply falls back to rules). `json_object` mode requires an object root and a prompt that mentions JSON; every current hook asks for an object. A server that rejects `response_format` fails the call and the hook falls back. The tool-call rejection is scoped to hook judgements: a hook runs on whatever chat model is configured, including a local model with no tool support, with a budget of 60 to 160 tokens, and the contract has no forced tool choice that would guarantee a call. Tool calls exist for cortex's tool loop only, and a request cannot combine `json` and `tools`. |
| `tools` offered | no stop key at all | no `stop_sequences` key |

The same stops apply to a streamed reply, which the backend cuts where it would cut a non-streamed one. The Claude path deliberately omits `"\n\n"`; the test comment says "thinking-era replies may use it" (`llm.test.ts`).

The coupling to working-memory is string-based. working-memory owns the tag list (WM-TRANS-006); working-memory exports it as `TRANSCRIPT_TAGS` (WM-TRANS-009) and this segment's `TRANSCRIPT_STOPS` is derived from it (LLM-STOP-006, LLM-STOP-007). End to end, the contract has four parts, two of them owned by other segments:

1. **Producer (working-memory).** `Context.transcript(name)` renders one line per event, oldest first, joined with `"\n"`: `[chat] <user>[ (mod)]: <text>`, `[voice] <speaker>: <text>`, `[screen] <text>`, and the co-host's own lines as `<name>: [<emotion>] <text>` (`packages/working-memory/src/index.ts`). Field values are interpolated unescaped.
2. **Framing (cortex).** `buildMessages` puts the transcript in the user turn after `## Recent transcript\n` and ends that turn with a nudge whose last token is `<name>:` (`services/cortex/src/prompt.ts`); the system turn asks for one short line that starts with an emotion tag (`prompt.ts`). The model is therefore primed to continue the transcript as the co-host.
3. **Stops (this segment).** Each `TRANSCRIPT_STOPS` entry is a tag prefix preceded by `"\n"`, so a stop fires only when the generated text contains a newline followed by `[chat]`, `[voice]` or `[screen]`; a reply that itself begins with a tag is not cut. Ollama and OpenAI-compatible calls also stop at the first blank line (`REPLY_STOPS`); Claude calls do not. `json: true` calls send no stops at all.
4. **Consumer (cortex).** `parseReply` trims the reply, keeps only its first line, and strips a leading `Name:` in front of the emotion tag (`services/cortex/src/prompt.ts`), so everything after the first newline is discarded whether or not a provider stop fired.

Rules that follow:

- The stops are a token and latency saver. Correctness of the spoken line rests on `parseReply`'s first-line rule in cortex, which holds whether or not a provider stop fired.
- The self-line form `<name>: [<emotion>] text` is not a stop. A model that runs past its own line into another `<name>:` line is cut by `parseReply` after the extra tokens are generated; the four-stop cap (`index.ts`) leaves no room for a fifth entry, and the first-line rule already guards the output.
- The literals are linked by a cortex-level test that renders a transcript with working-memory and checks every line after the first against the stop list (owned by the cortex segment); `llm.test.ts` pins the stop list and `packages/working-memory/test/context.test.ts` pins the tags.
- A new transcript line kind added to working-memory needs a matching stop here; adding it to `REPLY_STOPS` would exceed the four-stop limit (`index.ts`), so such a change revisits the `"\n\n"` entry or accepts that the new kind is cut only by `parseReply`.

## The Claude path (Anthropic API and Bedrock)

`ClaudeBase.chat` (`index.ts`) is shared; subclasses differ in client, ping, and whether server-side fallbacks are enabled.

1. **Messages.** All `system` messages are joined with `"\n\n"` into the `system` field (omitted when empty); the rest become turns. A user message with `images` becomes image blocks followed by its text block; an assistant message with `toolCalls` becomes its `continuation` blocks, its text and `tool_use` blocks; consecutive `tool` messages become `tool_result` blocks of one user turn. If there are no turns, or the first is not `user`, a `user` turn with content `(begin)` is prepended (`index.ts`).
2. **Token budget.** `max_tokens` is the caller's `maxTokens` when given (raised to 1, the API minimum), else `claude.max_tokens` (default 2048, minimum 256 per schema). Thinking and text share the budget, so a hook that names a very small one can get an empty reply and fall back to its rules (LLM-CLAUDE-003).
3. **Effort and sampling.** `output_config: { effort: claude.effort }` (default `low`); no `temperature` is ever sent, so `opts.temperature` and `llm.temperature` are ignored for Claude (`index.ts`, schema comment `schema.ts`).
4. **Stop sequences.** `TRANSCRIPT_STOPS` unless `json` or `tools` (`index.ts`).
5. **Server-side fallbacks.** When `serverFallbacks` is true a non-streamed request adds `betas: ["server-side-fallback-2026-07-01"]` and `fallbacks: "default"`. `AnthropicProvider` sets this from `claude.fallbacks` (default `true`); `BedrockProvider` hard-codes `false` (`index.ts`). The installed, lockfile-pinned SDKs type all three: `@anthropic-ai/sdk` 1.8.0 lists `server-side-fallback-2026-07-01` in `AnthropicBeta` and types `fallbacks` as `Array<BetaFallbackParam> | 'default'`, and `@anthropic-ai/bedrock-sdk` 1.1.2 exports `AnthropicBedrockMantle` with an optional `awsRegion`; `tsc -b` compiles the request against those types. A streamed request on `anthropic` sends neither field: a fallback re-run that begins after text has been delivered cannot be unsaid, and no recorded response shows how the beta behaves on a stream (Open Questions); a refusal on a stream is `finish: "refusal"` (LLM-CLAUDE-022). An opt-in live smoke test (LLM-CLAUDE-013) pings and completes one chat when `ANTHROPIC_API_KEY` and `COHOST_LIVE_CLAUDE_MODEL` are set.
6. **Refusal.** If `res.stop_reason === "refusal"` `chat()` and `complete()` return `""` ("say nothing"), and `complete()` finishes as `refusal`; a stream ends with `done` and that `finish` (`index.ts`; see Streamed replies; LLM-CLAUDE-006, LLM-CLAUDE-021).
7. **Reply assembly.** `text` blocks are kept, concatenated and trimmed, and `tool_use` blocks become `toolCalls`; `thinking` blocks are dropped from the text and kept, with the tool calls, in the result message's `continuation` so the next request can send them back (`index.ts`, `llm.test.ts`).
8. **Abort.** `opts.signal` is passed as the SDK request option; a streamed request runs under an `AbortController` that combines the caller's signal with the two stream bounds (`index.ts`).
9. **Errors.** An SDK error that carries an HTTP status is wrapped as a `ChatError` of kind `http` with that status; a failure of a streamed read after the request began is a `ChatError` of kind `stream` (see Errors; LLM-ERR-002, LLM-STREAM-021).

**Credentials come from config only.** The environment decides no credential and no endpoint (HLD tenet 7, config CFG-ENV-012), and the SDKs would otherwise fall back to their own lookups (`ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL`, the AWS environment variables, profiles and instance metadata); a key left in `.env` would otherwise keep a provider working while Settings showed Not set. `AnthropicProvider` therefore builds its client from `claude.api_key` and the API's own base URL alone (LLM-CLAUDE-009); with the key empty it builds no client, `ping()` returns false naming `llm.claude.api_key` and `chat()` rejects with the same message (LLM-CLAUDE-017). `BedrockProvider` builds `AnthropicBedrockMantle` from `bedrock.region`, `bedrock.access_key_id` and `bedrock.secret_access_key` explicitly, with no session token, so temporary credentials are not supported (LLM-CLAUDE-015); with exactly one key set it refuses to start and names both (LLM-CLAUDE-016); with both empty or the region empty it builds no client and `chat()` rejects naming each empty key, while `ping()` stays nominal (LLM-CLAUDE-018). The SDKs also read `ANTHROPIC_CUSTOM_HEADERS` (merged after their own auth headers, so an `Authorization:` line there replaces the credential and any other line adds a request header), `ANTHROPIC_LOG`, the `ANTHROPIC_OPEN_TELEMETRY*` family, the Anthropic profile, federation and workspace variables, and the Bedrock endpoint and region variables; all of those reads happen while a client is constructed. Both providers therefore construct the client with every `ANTHROPIC_*` and `AWS_*` variable removed from the process environment for the duration of the synchronous construction (by prefix, so a variable a later SDK version adds is covered), and send through a `fetch` that pins the credential headers at request time: `anthropic` sets `Authorization` from config and drops `x-api-key`; `bedrock` refuses a request not signed with the configured access key (LLM-CLAUDE-019). Variables outside both prefixes that the SDKs read (`HOME`, `XDG_CONFIG_HOME`, `APPDATA`, `USERPROFILE`, `HOSTNAME`, `PATH`) only locate profile files for the default credential chain, which an explicit credential never enters. `backends.test.ts` sets every variable the installed SDK sources read to a hostile value, and scans those sources so an SDK upgrade that reads a new variable fails the test until it is covered; it asserts the requests still use the configured credentials, endpoint, region and headers.

## Health ping semantics

`ping()` answers "is the backend reachable and answering"; on `false`, `lastError` says why. A successful ping clears `lastError`.

- **Ollama:** `GET /api/tags`; non-OK sets `ollama <status> at <base>`; a thrown fetch error sets `cannot reach ollama at <base>: <err>` (`index.ts`).
- **OpenAI-compatible:** `GET <base>/models` with the same headers; non-OK sets `<base>/models answered <status>` plus ` (check llm.openai.api_key)` on 401/403; thrown error sets `cannot reach <base>: <err>` (`index.ts`).
- **Anthropic:** `client.models.retrieve(model)`; on failure the SDK error's `status` selects `Claude API rejected the credentials (<status>): check llm.claude.api_key` (401/403), `Claude API has no model "<model>": check llm.model` (404), or `String(err)` (`index.ts`).
- **Bedrock:** always `true`, and the provider exposes `pingIsNominal = true` so a caller can tell the answer is not a probe (LLM-PING-006); the comment says there is no cheap probe and errors surface on the first chat (`index.ts`).
- **Mock:** always `true`, `lastError` stays undefined (`mock.ts`).

Consumers: cortex blocks startup in a 3-second retry loop until `ping()` is true (`services/cortex/src/startup.ts`, owned by `cortex`), reporting each miss through `heartbeat.degraded` via the `onDown` callback wired at `services/cortex/src/main.ts`; memory pings only an `Ollama` instance for its embeddings (`services/memory/src/startup.ts`, owned by `memory`). Because Bedrock always reports reachable, a bad Bedrock credential or un-enabled model would show as a healthy `llm` dependency and fail only on the first `chat()`; the Bedrock ping stays optimistic, and cortex states that it is unprobed in its heartbeat `detail` (cortex segment).

## Embeddings and the mock backend

`Ollama.embed` POSTs `{model: embed_model, input, keep_alive:"24h"}` to `/api/embed`, returns `embeddings[0]`, and throws `ollama embed <status>: <body>` on non-OK or `ollama embed returned no vector` when the array is empty (`index.ts`).

`HashEmbedder` (`mock.ts`): lowercases, tokenizes with `/[\p{L}\p{N}]+/gu`, hashes each token with 32-bit FNV-1a into one of `HASH_DIMS = 64` buckets with a +1/-1 sign taken from bit 16, then L2-normalises. Empty or token-free text yields the unit vector e0 so downstream cosine math never sees NaN. It is deterministic and dependency-free.

### The mock backend

`MockProvider` (`mock.ts`) is the isolated mode of the chat provider (HLD tenet 6). It performs no I/O, starts no timer and never sleeps, so cortex and the `tools` service can be developed and tested on Redis alone, and every output is a pure function of its input.

- **Text.** `json: true` is decided first: `complete()` with it returns `{}` whatever the last message is (LLM-MOCK-020). `chat()` and `complete()` throw `mock chat aborted` if the signal is already aborted; return `"{}"` for `json: true` (valid JSON that the salience, affect and critic `validate` functions all reject, so mock-backed `llm` hooks always fall back to rules); otherwise return `[happy] mock: <last user message, whitespace-collapsed, first 80 chars, or "hello">`, in the `[emotion] text` format cortex parses (LLM-MOCK-001 to LLM-MOCK-003, LLM-MOCK-006).
- **Streaming.** `stream()` yields that same text as one `text` event per word (the first word bare, each later word with a single leading space), then `done`. The signal is checked before each event, so an abort between words ends the stream with the abort reason, as a real provider does; ending the loop early stops it (LLM-MOCK-007, LLM-MOCK-008).
- **Markers.** Both markers are read from the last user message only, and act on `complete()` and `stream()` only; `chat()` ignores both and returns its ordinary reply (LLM-MOCK-016, LLM-MOCK-018, LLM-MOCK-019).
- **A tool round trip.** When the request offers `tools` and the last paragraph of the last user message (the closing nudge with the focus text, after the blank line that ends the transcript; the transcript, recalled memories and viewer notes are never read) contains `[mock-tool <name> {<json arguments>}]` with `<name>` among the offered tools, the reply is no text and one tool call, id `mock_call_<n>` (`n` one more than the number of tool calls already in the history), `finish` `tool_calls`. When the last message is a `tool` message, the reply is `[happy] mock: <tool name> said <its content, whitespace-collapsed, first 80 chars>` with `finish` `stop`. A tool name that is not offered gives the plain text reply; arguments that are not a JSON object give the call with `arguments` `{}` and `invalid` holding the raw text. The marker is ordinary text, so an injected speech line that is the focus of a reply (a speech reply is owner-prompted under the default `tools.owner_sources`) drives a call through cortex and the `tools` service with no real model; a viewer's marker in chat history does nothing, and one that is the focus of a chat-prompted reply fires only a tool the owner marked for chat, because only such a tool is offered. (LLM-MOCK-009 to LLM-MOCK-013, LLM-MOCK-016.)
- **A failing stream.** A user message containing `[mock-fail-after <n>]` makes `stream()` yield `n` text events and then throw a `ChatError` of kind `stream`, so a caller's handling of a reply cut short after text was delivered can be tested without a network. `complete()` throws the same error at once. When `n` is at or past the number of words in the reply, the call completes normally (LLM-MOCK-014, LLM-MOCK-015, LLM-MOCK-017).
- **Images** on a user message are accepted and ignored; the reply is unchanged (LLM-VIS-006).
- `ping()` is always true and `lastError` stays undefined.

Who builds embedders: memory, not this package. `services/memory/src/backend.ts` switches on its own key `brain.memory.embedder` (`ollama` or `hash`), constructing `HashEmbedder` or `Ollama` directly, so a mock chat provider leaves memory on the Ollama embedder unless `brain.memory.embedder` is `hash` as well (an isolated start of `memory` sets it) (LLM-EMBED-004; the `memory` segment owns that key). The separate switch avoids a silently offline memory: "Memory always uses the real Ollama embedder unless `MEMORY_EMBEDDER=hash`, even with `LLM_PROVIDER=mock` (deliberate, avoids silent offline)" (commit `51d5a9c`).

## Example stub servers

The docs site's Your own model server page explains what cohost asks of an OpenAI-compatible server and lets the reader check the connection before pointing cohost at a real one. `examples/model-stub/` holds the smallest server that satisfies the OpenAI-compatible provider, in Python (`stub.py`, standard library) and in TypeScript (`stub.ts`, Node built-ins only, run with `node` on Node 22.18 or later by type stripping):

- `GET /v1/models` answers a one-model list, so `ping()` succeeds (LLM-PING-002, LLM-EX-003).
- `POST /v1/chat/completions` answers one fixed, non-streamed completion whose content is `[happy] Hello from the stub model server.`, in the `[emotion] text` form cortex parses, so a whole co-host pointed at the stub speaks a line (LLM-EX-004). The body is the same whatever the request asks for, so a streamed request gets one JSON completion, which the provider reads as a whole reply in one `text` event (LLM-EX-007), and an offer of tools gets text and no tool call (LLM-EX-008). A `json: true` call (an `llm`-kind hook) gets the same text, which is not JSON, so the hook falls back to its rules, as on the mock provider.
- Both listen on 8901 by default, a port nothing in the stack uses, take another port as their first argument and print `listening on <port>` (LLM-EX-001), which is how the test starts them.
- `try.sh` sends the two requests cohost sends with `curl`; `try.expected.txt` holds the replies (LLM-EX-006). Against any other server the same script shows whether it answers in the shape cohost reads.

`packages/llm/test/example-stub.test.ts` points the real OpenAI-compatible provider at each stub (LLM-EX-005), so the example is held to the client it stands in for. The stubs are examples for readers, not test infrastructure: `scripts/dev/stub-llm.ts` remains the fake Ollama server of the dev loop.

An iterable lets cortex hand each delta to clause splitting in a loop and leave the loop to cancel, where a callback needs its own completion and error channel. |
| Wire paths | `chat()` and `complete()` send `stream:false` and read one body; only `stream()` sends a streaming request | Always stream and drain for non-streamed callers | A hook's JSON and a describer's line keep a single request and body (and the recorded Claude and Bedrock fixtures), and stream parsing is exercised only by callers that asked for it. The cost is two readers per adapter. |
| Stream events | `text` deltas, whole `tool_call`s, then one `done` carrying a `ChatResult` whose `text` is what was delivered; failures are thrown | Argument fragments as events; emit each call when its block completes; an `error` event or a `done` with `finish: "error"` carrying the partial reply | Cortex acts only on a complete call, so fragments would be reassembled by every caller. Emitting each call when its block completes is rejected: a call cut by the token cap would already be out, and the caller needs the whole assistant message before it can answer any call anyway. A thrown error means a cut-off reply cannot be mistaken for a finished one, and the caller already holds the text it was given. |
| Reply trimming on a stream | The deltas concatenate to the trimmed reply: leading whitespace dropped, trailing whitespace held back | Emit raw deltas and let the caller trim; trim only `done.result.text` | A caller that speaks deltas as they arrive must have said exactly what `chat()` would have returned. Holding back trailing whitespace costs at most one word of delay. |
| Stream timeouts | Two bounds, each `llm.timeout_ms`: to the first `text` or `tool_call` event, and between events; they apply even when the caller passes a signal; no total bound in this package | One total timeout; time to first text only; the caller's signal replaces the bounds as it does for `chat()` | A total bound would cut a reply that is long and healthy, and a bound on the first event alone would leave a stalled stream hanging mid-line. Cortex passes a signal to cancel a reply, so letting a signal replace the bounds would leave the live path unbounded (HLD tenet 3). A thinking delta does not count toward the first bound, since the wait that matters is the wait for the first clause. |
| Failure after output | No retry once an event has been delivered; the iterator throws and the caller keeps its text | Retry from the start; resume with the delivered text as a prefix; end the stream normally with a flag | A retry repeats speech already said, and a resumed generation is not the same sentence. The fallback is the caller's (HLD tenet 3): this package never answers in the model's place. |
| Message shape | A closed union by role: `tool` messages with `callId`, `name`, `isError`; assistant `toolCalls`; `images` on user messages; `content` always a string | `content` as an array of typed parts; tool results as user messages | Callers that build `{role, content}` today compile unchanged and the hook and describer code stays flat. Typed parts are what each vendor wants, but the translation belongs in the adapter, not in every caller. |
| Tool call arguments | A parsed object; text that is not a JSON object becomes `{}` plus `invalid` holding the raw text; a malformed call sent back in the history carries `{}` | The vendor's raw string; throw on bad arguments; send the raw text back as arguments | Ollama and Claude send objects and OpenAI-compatible servers send strings (Bedrock follows Claude), so the contract gives one form. A model's malformed call is something the model can be told about, which a thrown error would hide. Sending the raw text back as arguments would put non-JSON where the backends require an object; the error result the caller writes carries the text instead. |
| Tool names | Must match `[A-Za-z0-9_-]{1,64}`; others fail before a request | Escape names inside the adapter; leave the check to each backend | The pattern is the strictest of the four backends. Escaping would put a name mapping in every adapter and make the model's call name differ from the one the owner allow-listed. The `tools` service owns a name that meets it (cascade). |
| Continuing a turn | The result's `message` is appended to the history unchanged, and carries an opaque `continuation` the adapter reads back; one from another provider is ignored | The caller rebuilds the assistant message from `text` and `toolCalls`; thinking blocks dropped | Claude requires the thinking blocks of a tool-using turn back with the results, and only the adapter knows that. Callers never inspect `continuation`, so a new provider adds no caller code (HLD tenet 2). |
| A feature the model cannot do | Declared by the owner through configuration (tools are configured, none by default; frames go to a hosted provider only when the owner chose it for the describer); a backend's rejection is a plain `http` error; streaming degrades to one late reply | Classify an HTTP 400 by its body text as `unsupported`; drop tools or images and warn once; a `capabilities` flag per provider | A malformed tool schema or an oversized image produces a body that also names tools or images, so a caller bug would be mistaken for a missing capability. A silent drop turns a request for a tool-using or image-reading reply into a different request with a normal-looking answer. A flag per provider is wrong for the same adapter serving different models. |
| Stops with tools | No stop sequences when `tools` is offered | Keep the reply stops; stops only on the final text turn | A stop sequence can cut a tool call's JSON. Cortex's first-line parse remains the correctness guard for the spoken line (owner decision 2026-11-01), so the cost is generation past the line end, which cortex discards: on a round that offers tools it reads to the end of the stream instead of cancelling it at the newline, because the calls arrive after the text (cortex The tool loop), and the token cap bounds that generation. |
| Parallel tool calls | A reply may hold several calls; results go back as separate `tool` messages in call order; no forced tool choice (`tool_choice`) | One call per reply; a `toolChoice` option | The vendors that allow several calls return them in one reply and expect all results in the next request; whether to run them in parallel is cortex's. A forced choice is the only use for `toolChoice` and no caller has one. |
| Image media type | Read from the leading bytes of the base64 data | A media type field on each image; JPEG assumed | The existing callers send bare base64 (the eyes frames are JPEG, a dashboard upload may be PNG), and they stay unchanged. |
| Frame egress | The package sends images to whatever endpoint the configured provider names and enforces nothing; the explicit hosted-describer setting is configuration's and eyes' | A flag on the provider; refusing images on a hosted provider unless a flag is set | Whether an endpoint is hosted is not knowable from a `base_url` or a provider name here, and the vision provider is built through the same factory as the chat provider. The tenet-8 test is applied where the setting is made. |
| Mock isolated mode | Deterministic streaming word by word; a tool round trip driven by a `[mock-tool <name> <json>]` marker in the focus text of the closing nudge; `[mock-fail-after <n>]` for a failing stream | A scripted mock configured per test; a mock that calls the first tool on every turn | A marker travels through an injected line that is the reply's focus, so cortex and the `tools` service run end to end on Redis alone with no test harness, and a marker never changes a run that does not contain it (HLD tenet 6). |
| Claude fallbacks on a stream | A streamed request sends no fallback beta | The same fields as a non-streamed request | A fallback re-run that starts after text was delivered cannot be unsaid, and its behavior on a stream is unverified here. A refusal is `finish: "refusal"`. |
| OpenAI-compatible example server | Two stubs (Python, TypeScript) answering `/v1/models` and `/v1/chat/completions` with fixed replies, tested against the real provider | Extend `scripts/dev/stub-llm.ts` to speak the OpenAI API; launch commands for llama.cpp, vLLM and LM Studio; one stub only | The dev stub is Ollama-shaped and lives with the dev scripts, not with the examples a reader copies. Third-party launch commands change with their releases and no test here runs them, so the docs site links their documentation instead. Two languages match the toolchains every other example uses; a fixed reply keeps the try-it output a file the test compares. |
| HTTP client | Global `fetch`; no retry or backoff in this package's own code (LLM-CHAT-009). The Claude and Bedrock paths go through the SDK, which retries a failed request at most twice; the client states `maxRetries: 2` (LLM-CLAUDE-014, `index.ts`) | HTTP library; retries and backoff on Ollama and OpenAI-compatible calls | Owner decision 2026-11-08: accept no retry. A failed call rejects `chat()` (or `complete()`, or ends a `stream()` with an error) once (LLM-CHAT-005, LLM-CHAT-008) and each caller already has a defined failure path. cortex's `think` catches it, logs `think failed` and returns to `idle`; the next focus starts a fresh think (CTX-GATE-007), and `trackLlm` feeds the failure into the heartbeat, so `deps.llm` reads `down` until a later reply succeeds (CTX-HEALTH-003). Hooks fall back to their `rules` implementation (HOOK-FALLBACK-002). The memory reflect job logs `reflect failed`, exits 1 and leaves the cursor in place for the next run (MEM-REFLECT-009). Retries are deferred because the supported backends are local (Ollama, OpenAI-compatible servers on the LAN or localhost) and fail fast, and a retry would hold the cortex's single think slot and delay a live reply that may already be stale. Revisit if a backend proves flaky in practice. |

## Open Questions & Future Decisions

- **Server-side fallback on a stream.** Whether the `server-side-fallback-2026-07-01` beta can be sent on a streamed request, and what a fallback re-run after delivered text does, is unverified. Until a recorded streamed response settles it, streamed requests send no fallback fields.
- **First-text deadline.** The first bound is `llm.timeout_ms` (60 s by default), far above a useful time to a first clause. Whether cortex needs a tighter first-text deadline of its own, aborting through its signal, is for the `cortex` segment.
- **Text beside a tool call.** The contract carries text and tool calls in one reply. Whether text that precedes a tool call is spoken before the tool's result is `cortex` policy; the mock does not produce both in one reply.
- **Hosted describer setting.** The package carries images wherever the provider points. The name and shape of the explicit setting that permits a hosted vision provider (HLD tenet 8) is for `config` and `eyes`.
