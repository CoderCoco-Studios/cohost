# config

Parent: [high-level-design](../../high-level-design.md). Specs: [config-specs.md](config-specs.md).

## Context and Design Philosophy

`@cohost/config` (`packages/config`) is the dependency root of the workspace: it has no workspace dependencies and every other package and service imports it (`packages/config/package.json` lists only pino, yaml, zod). It owns four things:

1. The **shape** of `config/config.yaml` and `config/expressions.yaml` (zod schemas in `packages/config/src/schema.ts`), including the nine-value `Emotion` enum that the bus event schemas also import (`schema.ts`).
2. The **loader**: locate the config directory, seed user-owned files from committed `*.example.*` templates, load `.env`, reject `${VAR}` placeholders, merge `secrets.yaml`, apply the isolation overrides by key path, validate, warn about unknown keys, and cache (`packages/config/src/index.ts`, `secrets.ts`).
3. **Small runtime helpers** every service uses: `env`/`envOr`, the `urls.*` service-address functions, `createLogger`, the personality read/write pair, and `ollamaModels`, the list of local models a config needs (`models.ts`).
4. The **presentation table** (`packages/config/src/presentation.ts`): the plain-language title, group and one-sentence description of every section, and the help text, label, unit and widget hint of every key, which the settings editor serves with the schema so the Settings screen names every setting without hard-coding any (module-contract MOD-CFG-*).

Design philosophy, as the example files' header comments state it (`config/config.example.yaml`, `config/secrets.example.yaml`, `.env.example`): every operator setting is a literal key of `config/config.yaml` (git-ignored, seeded from an example) with a schema default, so the dashboard's settings editor shows and edits all of it; credentials live in `config/secrets.yaml` (git-ignored, mode 0600, merged by the loader at the secret paths and returned by no read API); `.env` holds only bootstrap values and the dashboard's own access controls (HLD tenet 7; [config in one place](../../decisions/config-in-one-place.md)). No environment variable reaches a setting except through the isolation override: the control plane passes one variable, `COHOST_ISOLATION`, to a container it starts isolated, and the loader applies its entries by key path to thirteen keys (CFG-ISO-006, CFG-ISO-007); `config.yaml` holds literals only, and a `${VAR}` placeholder anywhere in it fails the load (CFG-ENV-011). Each backend that can be swapped for a mock or off variant is selected by an enum key of that kind; the mock variants are never the default (comment `schema.ts`). The schema is lenient about unknown keys (warn, do not fail) and strict about enums and ranges. The shipped example config loads with no `.env` and no `secrets.yaml` at all: every key it holds is a literal (CFG-ISO-005), while a value that is set but invalid, such as an unknown `avatar.driver`, still fails the load.

## Files, directory resolution and seeding

| File | Where | Role | Seeded from |
| --- | --- | --- | --- |
| `config.yaml` | `<configDir>/config.yaml` | all behaviour; read by `loadConfig` | `config.example.yaml` |
| `personality.md` | `<configDir>/personality.md` | co-host persona prompt; read/written by `loadPersonality` / `savePersonality` | `personality.example.md` |
| `expressions.yaml` | `<configDir>/expressions.yaml` | emotion to avatar-app name map; read by `loadExpressions` | `expressions.example.yaml` |
| `secrets.yaml` | `<configDir>/secrets.yaml` | credentials, nested at the secret paths; merged by `loadConfig` (CFG-SEC-*); written only by the dashboard's write-only secret route and by hand | `secrets.example.yaml` (copied by `install.sh` with mode 0600, never by the loader) |
| `.env` | `COHOST_ENV_FILE`, else `.env` at the workspace root, else the parent of `configDir()` (CFG-ENV-010) | bootstrap values and the dashboard's access controls; loaded by `loadDotEnv` | `.env.example` (copied by `install.sh`, not by code) |
| per-service data | `dataDir()`: `COHOST_DATA_DIR`, else `data` under the workspace root (CFG-DIR-006, CFG-DIR-007); each service writes only under `<dataDir()>/<service>/`, such as voice's fallback clip store and mouth's clip cache | generated files a service keeps across restarts; not edited by hand and ignored by version control (`data/` in `.gitignore`) | none: services create what they need |

Resolution (`index.ts`):

- `findWorkspaceRoot(start = cwd)` walks parent directories until one contains `pnpm-workspace.yaml`, returning `undefined` at the filesystem root (`index.ts`). It exists because `pnpm dev` runs each service with its package directory as cwd (comment `index.ts`).
- `configDir()` = `resolve(CONFIG_DIR ?? join(findWorkspaceRoot() ?? cwd, "config"))` (`index.ts`). Compose sets `CONFIG_DIR=/app/config` (`docker-compose.yml`) and bind-mounts `./config` there (`docker-compose.yml`).
- `dataDir()` = `resolve(COHOST_DATA_DIR ?? join(findWorkspaceRoot() ?? cwd, "data"))`, the same resolution as `configDir()` (CFG-DIR-006, CFG-DIR-007). Each service keeps its own files under `<dataDir()>/<service>/` and never reads another service's subdirectory: voice's fallback clip store is `voice/fallback-clips`, mouth's clip cache `mouth/fallback-clips`. Services exchange those files over HTTP (HLD tenet 1). In a container the workspace root is `/app`, so the default is the container's own `/app/data`, with no volume. The path is a per-machine value, so it is an environment variable with no YAML key (HLD tenet 7).
- `ensureFromExample(name, example)` returns the real path if it exists; otherwise copies the example, reports `[config] created <file> from <example>` through the config logger (CFG-LOG-001), and returns the path; if the example is also missing it throws `No <file> and no <example> to seed it from` (`index.ts`). It is called for all three user files (`index.ts`), so any service that starts first seeds them (README.md says the same).
- `dotEnvPath()` is `COHOST_ENV_FILE` when set, else `.env` at the workspace root (`findWorkspaceRoot()`), else the parent of `configDir()` when there is no workspace root (CFG-ENV-010). A `CONFIG_DIR` elsewhere does not move where `.env` is looked for. In a container the workspace root is `/app`, so the path is `/app/.env`, which does not exist (it is `.dockerignore`d, `.dockerignore`) and does not matter because Compose injects `.env` through `env_file`. A missing `.env` is not an error: every variable has a default or an owner that reports its absence (the dashboard names `CONTROL_TOKEN`).

Personality and expressions: `loadPersonality()` and `loadExpressions()` read their file on every call (uncached by design: a service that wants a fresh copy asks again, as cortex does on `control reload_personality`) and `savePersonality(text)` replaces `personality.md` through `writeFileAtomic`, a temporary file in the same directory renamed over the target, which the settings editor's section writer shares (CFG-USR-013). `loadExpressions()` parses `expressions.yaml` with `ExpressionMapSchema`, treats an empty file as `{}`, and reports a schema failure as `Invalid <file>:` followed by `  path: message` lines, the shape `loadConfig` produces (CFG-USR-002). The consumers are cortex (loads at start, reloads on `control reload_personality`, `services/cortex/src/cortex.ts`), dashboard (GET/PUT personality, `services/dashboard/src/routes.ts`), memory reflection (`services/memory/src/reflect.ts`) and avatar (expressions, and `configDir()` as the VTube Studio token directory, `services/avatar/src/boot.ts`).

## Loading pipeline

`loadConfig(force = false)` (`index.ts`):

1. Return the module-level cached `Config` unless `force` (`index.ts`). There is no file watching: config is read once per process; only personality has a reload path.
2. `loadDotEnv()` (`index.ts`), from `dotEnvPath()`. Parses `KEY=value` lines (it never sets `COHOST_ISOLATION`, CFG-ISO-008): trims each line, skips blank and `#` whole-line comments, requires `=` at index 1 or later, trims key and value, strips one layer of matching single or double quotes, and sets `process.env[key]` only when it is `undefined` (`index.ts`). Comments follow Compose's `env_file` rules (CFG-ENV-006): an unquoted value loses a whitespace-then-`#` suffix (`KEY= # note` is empty), a quoted value may be followed by a comment and keeps any `#` inside the quotes, and a `#` with no preceding whitespace (`a#b`) is part of the value.
3. `ensureFromExample("config.yaml", "config.example.yaml")` (`index.ts`).
4. Parse and placeholder check (`pipeline.ts`): the raw file text is parsed as YAML (a syntax error is reported as an issue like a schema failure), and every string value holding a `${NAME}` or `${NAME:-default}` placeholder, `NAME` matching `[A-Z0-9_]+`, becomes an issue at that key's dotted path (an array entry as `path[index]`). A placeholder inside a comment is not a value and is not checked. No placeholder is ever substituted; the issues end the load as `Invalid <file>:` (CFG-ENV-011), so a `config.yaml` that still holds one fails loudly at the key instead of reading it as empty.
5. `coerceEmptyNumbers` drops every `null`-valued key at any depth (`index.ts`; the name says numbers but the filter is type-blind; `null` array elements are kept) so schema defaults apply: a key written with no value (`port:`) is the same as a key left out (CFG-LOAD-002).
6. Secrets (`secrets.ts`): `loadSecrets()` reads `secrets.yaml` as described under Secrets file and `mergeSecrets` sets each secret path's value into the parsed object, discarding any value `config.yaml` holds at a secret path (CFG-SEC-004, CFG-SEC-011).
7. Isolation overrides (`pipeline.ts`): when `COHOST_ISOLATION` is set and non-empty, the loader parses it as a JSON object from override name to string and sets each entry at the key path `ISOLATION_OVERRIDES` gives that name, after the file's own values, so the override wins; a value is parsed as a YAML flow value for the boolean keys and `ears.sources` and kept as a string for the rest (CFG-ISO-007). A malformed object or an unknown name fails the load naming `COHOST_ISOLATION` (CFG-ISO-010). No other environment variable is consulted.
8. `ConfigSchema.safeParse`. Steps 4 to 8 are one function, `parseConfigText(text, secrets, overrides)`, which `loadConfig` and the settings editor both call, so they accept exactly the same files; the editor passes the secrets it read and no overrides, so it validates the file as it reads once started without isolation. On failure `loadConfig` throws `Invalid <file>:` followed by one `  path: message` line per issue.
9. `unknownKeys(raw, parsed)` recursively lists dotted paths present in the raw object but missing from the parsed one; non-empty results are reported by one warning through the config logger that names only the ignored keys, and loading continues. The walk descends into array entries and reports them as `path[index].key`, so a typo inside a reflex shows up as `brain.salience.reflexes[0].cooldwn_ms` (CFG-LOAD-006).
10. Cache and return.

All diagnostics (the seeding notice, the unknown-key warning and the secrets warnings) go through a pino logger named `config`, created on first use; `setConfigLogger` replaces it so tests and hosts can capture or redirect them (CFG-LOG-001). Nothing in the package writes to `console`. No diagnostic and no error message carries a secret's value or any text of `secrets.yaml`.

## Secrets file

`config/secrets.yaml` holds the credentials, so that `config.yaml` can be shown, shared for support and edited by the dashboard whole.

- **Location and creation.** `secretsPath()` is `<configDir()>/secrets.yaml`, beside `config.yaml` in the bind-mounted `./config`, so a container restart applies it like any other edit. The loader never seeds or creates it: a missing file means every secret is unset (`""`, the schema default) and is not a warning (CFG-SEC-001). `install.sh` copies `secrets.example.yaml` (every secret path present and empty, each with a comment) with mode 0600; the dashboard's write-only secret route creates the file with mode 0600 when it does not exist (CFG-SEC-012).
- **Format.** A YAML mapping nested exactly like `config.yaml` but holding only the secret paths of `SECRET_PATHS`: `llm.openai.api_key`, `llm.claude.api_key`, `llm.bedrock.access_key_id`, `llm.bedrock.secret_access_key`, `vision.obs.password`, `ears.http.token`, `chat.twitch.client_id`, `chat.twitch.client_secret`, `chat.twitch.access_token`, `chat.twitch.refresh_token` and `connections.discord.token` (CFG-SEC-003). Every value is a string, used exactly as written (no placeholder substitution applies to this file); a non-string at a secret path fails the load naming the path (an unquoted all-digit token needs quotes).
- **Merge.** `loadConfig` sets each non-empty string found at a secret path into the parsed config before validation; a value in `secrets.yaml` is the one used (CFG-SEC-004). A value `config.yaml` holds at a secret path is never used, whether or not `secrets.yaml` holds one, and produces one warning naming the path, never the value, so a credential pasted into the shareable file is neither used nor returned (CFG-SEC-011). A key of `secrets.yaml` outside `SECRET_PATHS` is ignored with one warning naming the path (CFG-SEC-005); nothing but the eleven paths can enter the config this way, so the file cannot override a behaviour setting.
- **Errors.** A file that exists but cannot be read, is not YAML, or whose root is not a mapping ends the load with an error naming the file and, for a syntax error, only the line and column, never the text (CFG-SEC-006, CFG-SEC-007); the loader does not fall back to "no secrets", because a silently empty credential reports as a missing account far from the cause. A file whose mode gives group or other any permission is loaded with one warning naming the file and `chmod 600` (CFG-SEC-008). The check runs only where the platform is not Windows and the reported mode is not `0777`, the mode that drvfs and similar mounts report for every file, so it cannot fire on every load there.
- **Read side.** Every container and the dashboard load the merged config, so every service process can hold every credential; this is the trust boundary (HLD Trust boundary), as `.env` reaching every container was. No Compose `environment:` entry carries a credential (DEPLOY-COMPOSE-025). Nothing exported by this package returns a secret's value other than the loaded `Config`; the settings editor reports a secret only as set or not set, read from the file at request time (MOD-CFG-005).
- **Write side.** `updateSecrets(file, changes)` sets or clears secret paths in the file: it refuses a path outside `SECRET_PATHS`, trims leading and trailing whitespace from a value and refuses one that is empty after trimming (clearing is a separate operation, CFG-SEC-013), preserves every other key and comment, writes through `writeFileAtomic`, and never returns or logs a value (CFG-SEC-009). Every write creates its temporary file with mode 0600 before any byte is written, so the renamed file is 0600 after a create and after an update, whatever mode the previous file had (CFG-SEC-012); `writeFileAtomic` takes the mode as an option that it passes when it creates the temporary file, and the personality and `config.yaml` writes pass none. The HTTP route (`PUT /secrets/:path`, a `{ value }` body, `null` clearing, always behind the control token) and the page control that call it are the [dashboard](../dashboard/dashboard-design.md) segment's: secrets are written only through that gated, write-only path, never through `PUT /config/:section`.
- **Not in the file.** The refreshed Twitch token chat persists under `<dataDir()>/chat/` stays a runtime artifact of the chat service, not a `secrets.yaml` key (chat CHAT-TW-011); the VTube Studio token avatar saves as `<configDir>/.vts-token` is likewise runtime state.

## Presentation table

`packages/config/src/presentation.ts` carries, beside the zod schema, everything the Settings screen needs to name and explain a setting, so the page holds no section names and no help text of its own. It is data, not behaviour: it holds no value and no default.

| Level | Field | Meaning |
| --- | --- | --- |
| section | `title` (required) | Plain name, such as "Salience" for `brain.salience` |
| section | `group` (required) | One of `GROUPS`, in order: Identity, Brain, Senses, Voice and body, System |
| section | `about` (required) | One sentence saying what the section affects |
| section | `page` (optional) | Another section whose screen shows this one (`brain.working_memory_events` is shown on `brain.memory`) |
| key | `help` (required, every key) | One sentence of help |
| key | `label` (optional) | Display name when the key name is not plain |
| key | `unit` (optional) | `ms`, `bytes`, `days`, `hours`, `dB`, `chars`, `words`, `fps` and the like |
| key | `sensitive` (optional, `true`) | The key decides where a secret-bearing or private request goes, so changing it needs the control token (CFG-PRES-010) |
| key | `widget` (optional) | A hint from a closed set: `timezone`; `model` with a kind `chat`, `small`, `vision`, `embed` or `stt`; `voice`; `sources`; `textarea` (a multi-line string); `options` with labelled `value`/`label` pairs |

A section is a declared section path: every top-level key of `ConfigSchema` except `brain`, plus `brain.working_memory_events`, `brain.salience`, `brain.affect`, `brain.memory` and `brain.cortex` (the same set the manifest's `config` lists cover, MOD-MAN-008). A key is a leaf of a section: a scalar or an array, named by its dotted path from the config root (`brain.salience.reflexes`, `voice.fallback.lines`); an array is one key.

The sections, as the table assigns them:

| Section | Title | Group | About |
| --- | --- | --- | --- |
| `cohost` | Identity | Identity | The co-host's name, your name and the time zone prompts use |
| `llm` | Language model | Brain | Which model answers for the co-host, its limits and the accounts it needs |
| `brain.salience` | Salience | Brain | When the co-host decides to speak, and its canned reflexes |
| `brain.working_memory_events` | Working memory | Brain | How many recent events each part of the brain keeps (shown on `brain.memory`) |
| `brain.affect` | Mood | Brain | How the co-host's mood moves and settles |
| `brain.memory` | Memory | Brain | What the co-host remembers about viewers and how it fades |
| `brain.cortex` | Replies | Brain | How the co-host waits for memory and voice, and checks a reply before speaking |
| `chat` | Twitch chat | Senses | Which chat the co-host reads and which messages it ignores |
| `vision` | Vision | Senses | Whether and how the co-host looks at the game through OBS |
| `ears` | Hearing | Senses | Where the co-host's audio comes from and how speech is detected and transcribed |
| `voice` | Voice | Voice and body | The co-host's speaking voice and the lines it says when speech fails |
| `mouth` | Speech output | Voice and body | Where the co-host's voice is played and how loud |
| `avatar` | Avatar | Voice and body | Which avatar app the co-host drives and how it moves |
| `connections` | Discord | System | The Discord bot's server and voice channel, shared by hearing and speaking |
| `dashboard` | Dashboard | System | The dashboard's ports and its test-upload limits |

The table is checked at build time (CFG-PRES-007): a key or section without its required fields, an entry for a key or section the schema does not have, a `page` that names no section, a widget outside the closed set or a `model` widget on a key that is not a string fails a test, so a new setting cannot ship unexplained. The widget assignments are fixed by CFG-PRES-006: `cohost.timezone` is a `timezone`; every model-name key is a `model` (`llm.model` and the consolidator's model `chat`, `llm.embed_model` `embed`, `vision.model` `vision`, `ears.stt_model` `stt`, the other hooks' models `small`); `voice.voice` is a `voice`; `vision.prompt` is a `textarea`; `ears.sources`, `ears.echo_suppress_sources` and `brain.salience.barge_in_sources` are `sources`; `voice.lang_code` is `options` with a plain language name for each of its nine codes. A key's `help` is also its JSON Schema `description`, generated from the table, so the schema has one source for help (CFG-PRES-008). The `sensitive` keys are exactly the eleven keys that decide where a request carrying a credential or the co-host's private context goes (CFG-PRES-011): `llm.openai.base_url` (the OpenAI-compatible API key), `vision.obs.host` and `vision.obs.port` (the OBS password), `avatar.vtube_studio.host` and `avatar.vtube_studio.port` (the saved VTube Studio token), `mouth.outputs.http.url` (the co-host's voice audio) and the `url` of each of the five hooks (`brain.salience.module`, `brain.affect.module`, `brain.cortex.critic`, `brain.memory.notes.capture`, `brain.memory.notes.consolidator`), which receive the conversation and viewer notes. Keys that choose a vendor's own endpoint (`llm.bedrock.region`, the Twitch and Discord ids) or a local listening address (`ears.http.host`) are not sensitive: nothing a secret travels to changes with them.

## Models to pull

`ollamaModels(config)` (`models.ts`) answers "which local models does this config need?" for the `models` container, so the model names live only in `config.yaml` (CFG-MODEL-001). `required` holds `llm.model` while `llm.provider` is `ollama`, `llm.embed_model` while `brain.memory.embedder` is `ollama`, and `vision.model` while it is non-empty and `vision.engine` is `ollama`; `optional` holds the model of every hook (`brain.salience.module`, `brain.affect.module`, `brain.cortex.critic`, `brain.memory.notes.capture`, `brain.memory.notes.consolidator`) whose `kind` is `llm` and whose provider, its own or the inherited `llm.provider`, is `ollama`, an unset hook model meaning `llm.model`; each list is duplicate-free and `optional` leaves out names already required. A failed pull of a required model fails the container; a failed pull of an optional one is a warning (deployment DEPLOY-COMPOSE-008, DEPLOY-COMPOSE-011). `pull-models.ts` is the container's entry point: it calls `loadConfig`, so an invalid config fails with the loader's own message naming the keys.

`ModuleSchema` (`schema.ts`) is the shared hook config for the three region hooks and the two memory notes hooks: `kind` (blank to `rules`; `rules|llm|http`), `url` (default `""`), `timeout_ms` 8000, and `llm{provider?, model?}` where both blank values mean "inherit" and a provider without a model is rejected via `superRefine` (`schema.ts`). The override provider enum is `ollama|openai|anthropic|bedrock`: `mock` cannot be named on a hook, though a hook that inherits reaches the mock provider when `llm.provider` is `mock` (CFG-SCH-009). The whole object `.default({})`s. Hook behaviour itself belongs to region-hooks.

Required-ness is uneven: `brain.*` regions and `llm.openai/claude/bedrock` default to `{}`, but the nine top-level sections themselves, plus `vision.obs`, `chat.twitch`, `avatar.vtube_studio` and `avatar.vmc` are required objects with no default, and the avatar hosts default to `host.docker.internal` and the two avatar ports to 8001 and 39539 (CFG-SCH-001, CFG-SCH-010, CFG-SCH-037, CFG-ISO-005). `vision.model` is required only while `vision.enabled` is true (a refinement on the `vision` object naming `vision.model`, CFG-SCH-025). A usable config therefore needs every section present (an empty `{}` suffices for `brain`, `voice`, `dashboard`), which the example provides.

Blank handling is uniform. An enum key wraps `z.enum` in `z.preprocess((v) => v || default, ...)` (`avatar.driver` blank means `null`; a non-empty unknown value still fails, CFG-ISO-005; `llm.claude.effort` blank means `low`), and a plain string key that has a default wraps `z.string().default(d)` in a preprocess that maps `""` to `undefined` (`cohost.timezone`, `llm.openai.base_url`, `vision.obs.host`, `vision.obs.source`, `voice.voice`, the two `plugin_*` keys and `ears.stt_model`, CFG-SCH-024), so a key written as an empty string, or an override whose value is empty, lands on the default instead of an empty string. Keys with no default and a non-empty requirement (`cohost.name`, `cohost.streamer`, `llm.model`, `llm.embed_model`) still fail validation when blank, and secrets keep `""` as their default.

The dashboard's settings editor ([module-contract](../module-contract/module-contract-design.md), MOD-CFG-*) reads and writes `config.yaml` through `packages/config/src/editor.ts`, which this package exports: `sectionJsonSchema(path)` generates JSON Schema from the zod schema (objects, strings, numbers with their int and range checks, booleans, enums, arrays, defaults, descriptions; a small walker over zod 4's schema classes that reads each wrapper's inner type and each check's definition, so no JSON-Schema dependency is added); `SECRET_PATHS` marks the eleven secret keys (CFG-SEC-003), which the schema output carries as `"x-secret": true` and `sectionSecrets` lists per section; `presentation.ts` supplies each section's and key's name and help to the schema route (MOD-CFG-019 to MOD-CFG-021); `readSection(text, section, secrets, running)` returns each key's source (`literal`, or `default` when absent from the file), editability, effective value and raw text (a secret as set or not set in `secrets.yaml`), the override name and the running units that override a key of `ISOLATION_OVERRIDES` (`isolation.overriddenBy`), and the section's unknown keys (found by walking the file against the schema, so a file that no longer validates still reports them); `applySection(text, section, values)` writes edited values into the file text by splicing the edited scalar's or array's byte range (and inserting an absent key after its siblings, or an absent section at the end of the file), so every other byte, comment and alignment stays as the owner wrote it, then runs the result through `parseConfigText` and reads each edited key back to prove the text means what was asked; every key is a literal or absent, so an edit never depends on the form the key has in the file; `writeFileAtomic` replaces the file. Configuration is still read once per process (HLD tenet 10).

## Environment variables

Three tiers, none of which is validated by `ConfigSchema`. An environment variable is never an operator setting (CFG-ENV-012), and the one that carries overrides is written only by the control plane.

**Isolation overrides** (`COHOST_ISOLATION`, CFG-ISO-006, CFG-ISO-007). The control plane sets this one variable, a JSON object from override name to value, on the `docker compose` process for an isolated start of one unit (and sets it empty for every other start); Compose passes the one name to the container (deployment DEPLOY-COMPOSE-017), and the loader applies each entry by key path after reading `config.yaml` and `secrets.yaml`. The override names below are labels in that object, not environment variables: a variable named `AVATAR_DRIVER` or `LLM_PROVIDER` in `.env` or the shell is read by nothing, and `loadDotEnv` never sets `COHOST_ISOLATION` (CFG-ISO-008), so only the control plane's channel can carry an override. The overrides are start-time, per-container, not settings: `.env.example` lists none, no guide tells the operator to set one, and the settings editor reports a key a running unit has overridden (MOD-CFG-018) instead of presenting a permanent shadow. A variable that `config.yaml` owns (for example `TWITCH_CHANNEL`) is not read from `.env`, and nothing warns when `.env` defines one; a `${VAR}` placeholder inside `config.yaml` fails the load (CFG-ENV-011).

The complete placement of every setting is the table in [config in one place](../../decisions/config-in-one-place.md).

## Service URLs and logger

`urls` is an object of functions, each calling `envOr` at call time so tests and late-loaded `.env` values take effect (`index.ts`). `urls.voice()` defaults to loopback built from `VOICE_PORT` so host-run (`pnpm dev`) services work outside Compose, where `docker-compose.yml` sets `VOICE_URL` to an in-network hostname. `createLogger(service)` returns `pino({ name, level: LOG_LEVEL || "info" })` and `Logger` is its type (`index.ts`); packages' tests cast fake loggers to `never`.

## Tests

`packages/config/test/config.test.ts` carries an `@spec` annotation on every test and restores `CONFIG_DIR`, `COHOST_ENV_FILE` and the environment after each one; it points `.env` at its sandbox through `COHOST_ENV_FILE` and captures loader warnings through `setConfigLogger`. `config-c3.test.ts` covers blank-to-default strings, `vision.model`, `ModuleConfig`, `.env` resolution, logger routing, `loadExpressions` errors, atomic writes and `.env.example`; `editor.test.ts` covers the schema export, secrets, section reads and in-place writes. Like the example-file specs, the shipped-example tests read `config/config.example.yaml`, `.env.example` and `config/expressions.example.yaml` from the repository root on purpose: they are the files the specs describe.

Not covered by any test: `urls.database/ollama/tts/stt`.

## Open Questions & Future Decisions

- **Consolidator model follows `llm.model`?** The example writes the consolidator's `llm.model` as the same literal as `llm.model`; editing `llm.model` leaves the consolidator on the old name. A blank hook model would inherit `llm.model`, but the hook also names `provider: ollama` explicitly, and a blank model with a provider is rejected (CFG-SCH-003). Decision wanted: let a hook with a provider and no model inherit `llm.model` when providers match, or keep two literals.
- **Two writers of `secrets.yaml`.** The file has no etag, so two browser tabs saving different credentials are last-write-wins (each write is atomic and changes only its own paths). Decision wanted: whether an etag is worth it for the write-only route.
- **`vision.model` pulled while vision is off.** `ollamaModels` pulls a non-empty `vision.model` whatever `vision.enabled` says, so enabling vision later needs no second pull and a fresh install downloads the model it may never use. Decision wanted: gate on `vision.enabled`.
- **The two upload caps.** `dashboard.inject.max_image_bytes` and `vision.upload_max_bytes` are separate keys that must agree for an injected image to pass both; nothing ties them.
