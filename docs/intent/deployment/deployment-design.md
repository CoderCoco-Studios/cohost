# deployment

Parent: [high-level-design](../../high-level-design.md). Specs: [deployment-specs.md](deployment-specs.md).

## Context and Design Philosophy

The segment is everything that turns the repository into a running stack or a published artifact: the Compose topology (every service except the dashboard), the host start script for the dashboard, the one Dockerfile, the Linux installer, the CI workflows (including the ones that build and publish the docs site, whose content and checks are the [docs-site](../docs-site/docs-site-design.md) segment's), the workspace and TypeScript build setup, and the licensing and contribution rules. It owns no runtime behaviour of cohost itself; it wires the other segments together and checks that they start.

The installer, the docs site and the examples serve the owner's own stream; packaging cohost for other streamers is not a goal. A defect in the installer or the docs is still a bug and is fixed with the same weight as a runtime defect, and the installer fails loudly rather than leaving a half-working stack: it aborts on a lockfile mismatch, on a failed smoke probe, and after a fresh Docker install that needs a re-login.

Describes the intended design and the files that realize it; where the files lag, the text says so and names the gap spec.

Philosophy, with the evidence for each:

- **One image, many services.** Every TypeScript service is built from the same Dockerfile and differs only by a build argument; the whole workspace is compiled once per image (the `Dockerfile` header).
- **Compose publishes on loopback only; the host-run dashboard is the only LAN door.** Redis, Postgres, Ollama, TTS and STT are published on `127.0.0.1` "for `pnpm dev` outside docker" (`docker-compose.yml`), and voice on `127.0.0.1:8700` for the host-run dashboard. The dashboard is not a Compose service: the owner starts it on the host (`pnpm dashboard`), it launches the stack, and its LAN listener is what OBS on another machine loads the sink page and the avatar renderer page from (dashboard LLD, Host process and stack control, Avatar renderer).
- **The dashboard is started first.** Nothing has to be running for it to start; its Launch button runs `docker compose up -d --build --remove-orphans` through the control plane, so a plain `docker compose up -d` is the same stack the button brings up.
- **CPU by default, GPU as an overlay.** The base file is CPU-only and the GPU is layered on by a second file that `install.sh` selects through `COMPOSE_FILE` (`docker-compose.yml`, `docker-compose.gpu.yml` headers).
- **chat keeps its refreshed Twitch token on the host.** `./data/chat` is mounted at `/app/data/chat` on `chat` only (DEPLOY-COMPOSE-022): Twitch rotates refresh tokens, so a token persisted in the container's own filesystem would be lost when the container is recreated (Rebuild, `docker compose down`) and the stale token in `secrets.yaml` would no longer refresh. Every other service's generated files (clip caches) are cheap to regenerate and stay in the container.
- **Config is bind-mounted, not baked.** `./config` is mounted at `/app/config` and `CONFIG_DIR` points at it (`docker-compose.yml`, `Dockerfile`), so the config segment's seeding writes real files on the host.
- **Optional pieces behind profiles.** `eyes`, `ears`, `mouth` and `discord` are Compose profiles, and so is each optional speech engine server: `pocket`, `nemotron` and `kyutai` (`docker-compose.yml`).
- **Process rules checked where a machine can check them.** The Contributor License Agreement (`CLA.md`, required by `CONTRIBUTING.md`) is enforced in CI on every pull request (DEPLOY-CI-005) and the docs site builds on every pull request (DEPLOY-CI-004); linked-intent development (`CLAUDE.md`, `docs/project/spec-driven.md`) stays a convention.

Shared settings come from two anchors. `x-ts-service-base` carries `restart: unless-stopped`, `host.docker.internal:host-gateway` (reach OBS or VTube Studio on the host), `depends_on: redis: service_healthy` and the container healthcheck. `x-ts-service` extends it with `env_file: .env`, the `environment:` block (in-network service URLs `REDIS_URL`, `DATABASE_URL`, `OLLAMA_URL`, `TTS_URL`, `STT_URL`, `VOICE_URL`, `CONFIG_DIR=/app/config`, and the one `COHOST_ISOLATION` pass-through, which wins over `.env`, so the in-network URLs and `CONFIG_DIR` cannot be changed from `.env`) and the `./config:/app/config` volume. Every application service but `tools` takes `x-ts-service`; `tools` takes only the base and states its own environment (DEPLOY-COMPOSE-026). Injected test uploads reach `eyes` and `ears` through Redis (dashboard DASH-INJ-005), so the services take no dashboard address and nothing on the host has to be reachable from a container (DEPLOY-COMPOSE-002). A service that declares its own `depends_on` (memory, cortex, voice, ears) replaces the anchor's map and therefore re-lists `redis`. Every `services/*` directory except `dashboard` has a Compose service; `services/dashboard` has none (DEPLOY-COMPOSE-001). Every `packages/*` and `services/*` directory has a project reference in the root `tsconfig.json` (DEPLOY-REPO-001).

Because `env_file: .env` applies to every application service, any variable an operator puts in `.env` reaches every container unless the `environment:` block names it. `CONTROL_ENABLED=1` and `CONTROL_TOKEN` in `.env` therefore reach every container too; nothing in a container reads them (only the dashboard and `loadControlConfig` do), so they need no pin. `.env` holds bootstrap and access values only, never an operator setting or a credential (HLD tenet 7). Credentials reach every service through the same `./config` bind mount as `config.yaml`, as `secrets.yaml` (DEPLOY-COMPOSE-025): they are inside the trust boundary, and a restart applies an edit to them.

The reverse direction matters for the control plane's isolated starts: `ComposeRuntime` sets the isolation preset on the `docker compose` process (`packages/control/src/runtime.ts`) as one variable, `COHOST_ISOLATION`, a JSON object of override names and values, and it reaches a container only if the `environment:` block names it. The `x-ts-service` block passes that one name through as `${COHOST_ISOLATION:-}`, and the loader applies each entry by key path (DEPLOY-COMPOSE-017, control-plane CTRL-RUNTIME-009, config CFG-ISO-007). It is a start-time override of one container, not an operator setting: `.env.example` lists none. The control plane sets the variable on every `docker compose` process it spawns, `ComposeRuntime` and `StackController` alike (the preset for an isolated start, the empty string otherwise; CTRL-RUNTIME-013, CTRL-STACK-017), and Compose interpolates `${COHOST_ISOLATION:-}` from the process environment first and `.env` second, so the explicit value wins over a line in `.env` and over a variable exported in the shell that started the dashboard or `cohostctl`; for a Windows `docker.exe` the name is listed in `WSLENV` even when empty. `COHOST_ISOLATION` is reserved for the control plane and must not be set in `.env` or the shell. A hand-run `docker compose up` is outside the control plane and nothing checks it: a value there is passed to every container it starts and applied by each as an isolation preset, so every service runs with those overrides, and a malformed value stops each service with an error naming `COHOST_ISOLATION`; a variable named like an override (`AVATAR_DRIVER`) in `.env` reaches a container through `env_file` but no process reads it.

**Container healthcheck**: `node packages/control/dist/healthcheck.js $$SERVICE`, interval 10 s, timeout 5 s, 3 retries, 30 s start period. `SERVICE` is baked into the image (the `Dockerfile` `ENV`). The script is in `@cohost/control` (`packages/control/src/healthcheck.ts`): it reads the last 200 entries of `cohost:health`, takes the newest heartbeat for the named service, and is healthy iff it is not `stopping` and younger than `STALE_FACTOR` (3) times that heartbeat's own `intervalMs`; it self-terminates with exit 1 after 4 s. The healthcheck only reports; no `depends_on` waits for an application service to be healthy, so health gates nothing at startup. Heartbeat semantics belong to control-plane.

**`models`**: built from the shared image with `SERVICE: memory` (the `consolidate` and `reembed` precedent), `./config` mounted, `OLLAMA_URL` from the shared environment, no Redis. It runs `node packages/config/dist/pull-models.js`, which loads the config (so an invalid `config.yaml` fails with the loader's message naming the keys and pulls nothing), polls `ollama` for `/api/tags` until it answers, then POSTs `/api/pull` for each name of `ollamaModels` (config CFG-MODEL-001): the required names first (`llm.model` while the provider is `ollama`, `llm.embed_model` while the embedder is `ollama`, `vision.model` while non-empty and the provider is `ollama`), then the optional hook models, printing the last 200 bytes of each response. A pull fails when the request errors, the server answers an HTTP error, or the response holds an `"error"` line (Ollama reports a pull error that begins after the response started as a 200 with an `{"error":...}` line); the entry still tries the remaining models, then exits non-zero when a required pull failed (DEPLOY-COMPOSE-011). A failed optional pull, such as the viewer-note capture model, is only a `WARNING` line on stderr and does not change the exit status, because the hook it serves degrades to its rules fallback. It has no restart policy, so the failure stays visible in `docker compose ps`. `memory` and `cortex` stay on `service_started` for `ollama`: both wait for the model backend themselves. It is not profile-gated: it runs on every plain `docker compose up -d`, as do `tts` and `stt`; the only way to start without them is to name services explicitly, as the comment at the top of `docker-compose.yml` shows. The model names are config keys, so a name the owner edits in the Settings screen is pulled by the next run of `docker compose up models`; it does not pull `ears.stt_model`.

**`consolidate`**: the memory service's one-shot (memory LLD § Viewer notes, `MEM-CONSOL-012`) as a Compose service, so the owner can run a pass after shutting the AI down by any route: `docker compose run --rm consolidate` or `cohostctl consolidate` (control-plane CTRL-CLI-008). It builds the same image as `memory` (`SERVICE: memory`; the layers are shared) and replaces the image's default command with `node services/memory/dist/consolidate.js`. It inherits `x-ts-service` for the env file, `environment`, the `./config` mount and `extra_hosts`; it sets only `depends_on`, `command`, `restart`, `profiles` and `healthcheck`, and none of those hides the anchor's `volumes`. `depends_on` is `postgres` healthy and `ollama` started, restated in full because a service's own `depends_on` replaces the anchor's map; `redis` is left out on purpose, because the entry point reads config, opens the store and calls the consolidator model, and never connects to the bus (`services/memory/src/consolidate.ts`). `docker compose run` starts the listed dependencies if they are down, so a pass works after `docker compose down`; `postgres` and `ollama` then keep running until the next `down`. The anchor's healthcheck asks for a fresh bus heartbeat, which a process that never joins the bus cannot produce, so it is disabled. The service is in the `maintenance` profile (the one-shots `consolidate` and `reembed`; the tool service `tools` has no profile, so this profile never starts it) so a plain `docker compose up -d` never starts it (a one-shot started at boot would find nothing dirty and exit, or compete with the memory service's startup); naming it in `docker compose run` runs it without `--profile`. Nothing waits on it: a stack stopped by `down`, Ctrl-C or a dashboard button is caught up by the memory service at its next start (`MEM-CONSOL-013`, `MEM-CONSOL-015`), so a skipped or failed run loses nothing. Like `models` it runs on the stack's Compose project and its network, so it reaches `postgres` and `ollama` by service name.

**Image pins** (DEPLOY-COMPOSE-014): every image carries an exact version tag, looked up in its registry when it was pinned. Redis runs on major 8 and Postgres on 18 (pgvector 0.8.7). The Postgres 18 image keeps its cluster under `/var/lib/postgresql/18/docker` and declares `/var/lib/postgresql` as its volume, so `pg18-data` mounts there, not at `/var/lib/postgresql/data`. The Postgres volume is named for its major: the 18 image's entrypoint refuses to start on a cluster of an older major found at the volume root, so a volume named `pg-data` that holds a Postgres 16 cluster would leave `postgres` restarting and every service that waits for it unstarted. A stack therefore starts with an empty `pg18-data` (there is no data migration), and an older `pg-data` volume is untouched and unused; the owner can remove it with `docker volume rm <project>_pg-data`. Redis keeps `redis-data`: Redis 8 loads a Redis 7 RDB snapshot, so existing stream data carries over. Changing a pin is an edit to the Compose files that CI then exercises.

**GPU overlay**: the `x-gpu` anchor adds an NVIDIA `deploy.resources.reservations.devices` entry (`count: all`) to `ollama`, `tts`, `stt` and swaps the `tts`/`stt` images to the GPU variants (`docker-compose.gpu.yml`). `KOKORO_IMAGE` / `SPEACHES_IMAGE` override the image in both files, so setting one for a GPU host also changes the base (CPU) file's default image. The GPU overlay's Kokoro image has no kernels for RTX 50-series (Blackwell) cards: on one, the container's TTS runs on the CPU. The Blackwell build is the tag `latest-cu128` of Kokoro-FastAPI's GPU image, selected with `KOKORO_IMAGE` ([Speech engine servers](#speech-engine-servers)).

**Fallback clips**: voice keeps its generated fallback clips under `/app/data/voice/fallback-clips` and serves them over its HTTP server; mouth fetches them into `/app/data/mouth/fallback-clips` ([voice](../voice/voice-design.md) Fallback Clips, [mouth](../mouth/mouth-design.md) Fallback Line, [config](../config/config-design.md) `dataDir()`). No volume is added and no directory is shared: both live in their container's filesystem. A container restart keeps them; after a recreate voice regenerates in the background (one TTS call per phrase), and mouth re-fetches from voice.

**The tool service**: `tools` is built from the shared image like every TypeScript service (`SERVICE: tools`) and holds no MCP server: an MCP server is reached by an HTTP(S) URL the owner writes in `tools.servers`, so the image gains no runtime and no package manager for server commands. It publishes no port. Its environment is the bus address, the config directory and the isolation pass-through, and it gets no `env_file`, no `DATABASE_URL` and no engine URL (DEPLOY-COMPOSE-026). Its only volume is the shared `./config` mount, which also holds `secrets.yaml` (DEPLOY-COMPOSE-025). Inside Compose it reaches a server on the Compose network by service name, a server on the host by `host.docker.internal`, and a server elsewhere by its address, which is configured egress ([config](../config/config-design.md) Egress destinations). It has no profile: with no tool enabled it is idle and costs almost nothing, and a profile would leave a tool the owner just enabled in the dashboard silently without a service to run it. The dashboard's apply after a tool setting restarts `tools` and `cortex` (module contract); Compose starts nothing else for it. Its startup order beyond Redis is not constrained: it waits for nothing and reports a server that is not up as a down dependency.

**The browser renderer needs nothing from Compose**: the `avatar` service, whichever driver it runs, mounts only `./config` and publishes no port. The `browser` driver writes its frames to Redis, which the container already reaches, and the dashboard on the host reads them there; the owner's VRM model files live under `data/dashboard/avatar-models/` on the host, read only by the dashboard, so the renderer needs no volume, no `.dockerignore` entry beyond `data`, which it already lists, and no published port ([dashboard](../dashboard/dashboard-design.md) Avatar renderer).

**Voice reachability**: `voice` listens on `VOICE_PORT` (default 8700, `services/voice/src/boot.ts`) and advertises `urls.voice()` = `http://voice:8700` inside Compose. Compose publishes it on `127.0.0.1:8700` only, because the dashboard runs on the host and proxies `/audio/*` to `urls.voice()`, whose default is `http://127.0.0.1:8700` (DEPLOY-COMPOSE-007). Browsers, OBS and any other player still go through the dashboard proxy, the only supported path for them; in-network sinks such as `ears` fetch `http://voice:8700` directly. A loopback publish also lets `pnpm dev` services on the host reach a containerised voice.

## Speech engine servers

cohost's Compose file runs the default engines, `tts` (Kokoro-FastAPI) and `stt` (speaches), and three optional engine servers, each behind its own profile: `pocket` (`tts-pocket`, Kyutai Pocket TTS), `nemotron` (`stt-nemotron`, NeMo-Speech.cpp serving NVIDIA Nemotron Speech Streaming) and `kyutai` (`stt-kyutai`, `moshi-server` serving Kyutai STT). The owner enables a profile in `COMPOSE_PROFILES` in `.env`, as for `ears`, and selects the engine in `config.yaml` (`voice.engine`, `ears.stt_engine`); Launch then builds and starts it with the rest of the stack. Each engine's URL key defaults to its Compose service ([config](../config/config-design.md) Engine sections), so no address needs writing, and a server the owner runs elsewhere is reached by writing its URL instead. A profile that is enabled while its engine is not selected runs an idle container; an engine that is selected while its profile is not enabled has no server, so its dependency is `down` and its detail says the server is unreachable.

None of the three has a published image, so each is built. The three are not application services: they have no `SERVICE` build argument, do not use the `x-ts-service` anchor, mount no `./config`, and read no `.env` (DEPLOY-COMPOSE-002, DEPLOY-COMPOSE-025).

**Pinning.** Every image in the Compose files carries an exact version tag (DEPLOY-COMPOSE-014). An image cohost builds is named `cohost-<service>:<upstream version>` (`cohost-tts-pocket:4.0.1`, `cohost-stt-nemotron:0.3.0`, `cohost-stt-kyutai:0.6.4`), so the tag says which version it holds; the versions were verified on 2026-11-23 and a change is made by looking the newer version up in its registry or repository first. The tag is not enough for repeatability, because a Git tag can move: the source of a build is pinned the way a workflow `uses:` ref is (DEPLOY-CI-009), by a full commit SHA for a Git build context and for any `git clone` or `ADD <git url>` in a Dockerfile under `docker/` (so `docker/stt-nemotron/Dockerfile` fetches NeMo-Speech.cpp at the pinned SHA), an exact crate version with `--locked` for the crate, and an exact tag for each base image, and a build that names a branch, a tag or `latest` as its source is refused by `scripts/lid-check.mjs`. The check covers the Dockerfiles cohost owns under `docker/` (their `FROM`, `cargo install`, `git clone` and `ADD <git url>` lines) and every Git build context; the base image of a Dockerfile that lives in an upstream repository (Pocket TTS's) is that repository's pin, not cohost's. The upstream tag stays in a comment beside the SHA.

**GPU and VRAM.** `stt-nemotron` and `stt-kyutai` need the GPU; `docker-compose.gpu.yml` reserves it for them as for `ollama`, `tts` and `stt`, and without the overlay they start without it. One RTX 5080 with 16 GB serves the chat model, the vision model, speaches and Kokoro on their GPU images, and a streaming STT server joins them; the cards are not partitioned, so an out-of-memory in one container degrades the others. The VRAM of `moshi-server` at one stream and of NeMo-Speech.cpp is unverified, and so is whether `moshi-server` runs on RTX 50-series cards. `tts-pocket` runs on the CPU and leaves the GPU alone. speaches stays in the stack as the batch engine for whole clips and the fallback ([ears](../ears/ears-design.md) STT engines), so its GPU use is added to the streaming server's.

**Weights.** A server downloads its weights at its first start, from Hugging Face, into its own named volume, so a container recreate keeps them. Each container mounts its own volume at `/root/.cache`, the cache root its server writes under: the Hugging Face hub and `pocket_tts` for Pocket TTS, `nemo-speech/models` for NeMo-Speech.cpp (its `XDG_CACHE_HOME` default), the Hugging Face hub for `moshi-server`. Pocket TTS's weights sit in a gated Hugging Face repository with a prohibited-use section, and cohost uses catalogue voices only: without accepting the gate the catalogue voices work and cloning does not, and cohost never clones. An owner who has accepted the gate and has a token sets `voice.pocket.hf_token` in `secrets.yaml` (the Settings screen's write-only field). The `tts-pocket` container never mounts `./config`, so no other secret reaches a third-party image. Launch writes the token to a file holding only that one value, `data/tts-pocket-secret/hf_token` under the workspace root (the directory Compose's `./data` paths name), rewrites it on every launch with mode 0600, and leaves the file absent when the token is blank, whitespace-only or unreadable; when `voice.engine` is `pocket` (the engine whose profile the owner enables) and the token file cannot be written, Launch fails before `up`; a token that cannot be read, or a write failure under another engine, is reported as a warning and Launch proceeds. The directory itself is always created, and is mounted read-only at `/run/cohost-secret` in that one container (a missing single file would be created as a directory by a bind mount). The container's entrypoint is a cohost script, `docker/tts-pocket/entrypoint.sh`, mounted read-only and run through the shell as the service's Compose `entrypoint: ["/bin/sh", "/cohost/entrypoint.sh"]`; it exports the file's content as `HF_TOKEN` for the server process alone when the file exists, then replaces itself with the command the service's `command:` names, which is `uv run pocket-tts serve --host 0.0.0.0 --port 8000` (the upstream image's own entrypoint, `uv run pocket-tts`, is replaced by the cohost one). The token is never in a Compose `environment:` entry, a build argument or an image layer (DEPLOY-COMPOSE-025). A stack started by a plain `docker compose up -d` without Launch leaves the file as it was. Whether the model download itself needs the token is unverified.

**Reaching them.** Each server is published on the host's loopback only, like `tts` and `stt`, for `pnpm dev` outside Compose; the containers reach one another by service name. cohost publishes no port to the LAN for any of them.

**Health checks and readiness.** Each service has a Compose healthcheck of the probe in the table, with a start period long enough for the first weights download (10 minutes) so the container is not marked unhealthy while it downloads. `voice` and `ears` list the servers in `depends_on` with the condition `service_started` and `required: false`: Compose orders them after the server's container has started when its profile is enabled and ignores them when it is not, and an unhealthy engine never stops `voice` or `ears` from starting. They start regardless and report `deps.tts` or `deps.stt` `down` while the engine is not serving (HLD tenet 5), and Launch does not fail because an engine is unhealthy. Launch's readiness wait is 180 s ([control-plane](../control-plane/control-plane-design.md)): a first start that is still downloading weights ends the wait with Launch reporting `ok: false` and naming the service as not ready on the stack card; nothing is stopped or restarted, and the service comes up when its download ends.

**The first build.** Enabling a profile makes the next Launch build the image, and Launch always passes `--build`. The `moshi-server` build compiles Rust for several minutes; the Pocket TTS and NeMo-Speech.cpp build times are unverified. Launch allows 30 minutes for `up` (control-plane Stack actions), and the stack card shows the build phase; a build that is already cached takes seconds. This is the one first-run cost an owner meets after adding an engine, so the installer's optional-profiles step names it.

**What the dashboard knows.** The three services are compose-only manifest units, like `tts` and `stt`: the Services screen shows a row for each, with start, stop and restart, and the tests that tie the Compose file to the manifest cover them ([module-contract](../module-contract/module-contract-design.md), [control-plane](../control-plane/control-plane-design.md)). They have no heartbeat and no `uses` entry anywhere: `voice` and `ears` do not list them, because a service that is not started would read as `unknown` and falsely annotate the unit that uses it; the engine's own dependency (`deps.tts`, `deps.stt`) is the signal.

**Kokoro and Blackwell.** The image behind `tts` for an RTX 50-series (Blackwell, CUDA 12.8) card is the tag `latest-cu128` of Kokoro-FastAPI's GPU image, which publishes a Blackwell build; the plain GPU tag is an older CUDA build with no kernels for those cards, so TTS would run on the CPU there. It is a floating tag and every image in the Compose files carries an exact version tag (DEPLOY-COMPOSE-014, DEPLOY-CI-009), so it is not written into either Compose file: an owner on such a card sets `KOKORO_IMAGE` in `.env` after checking that it runs on their card. That the image runs on an RTX 5080 is unverified.

**Licences.** The code of Pocket TTS is MIT and its weights CC-BY-4.0 behind the gate above; the weights of Kyutai STT are CC-BY-4.0; NeMo-Speech.cpp is Apache-2.0. The built images stay on the owner's machine.

## Image build

`Dockerfile`, a Rust stage and three stages on `node:26-slim`:

0. `native`: `FROM rust:<version>-slim-trixie`, where `<version>` is the exact toolchain `rust-toolchain.toml` pins and trixie is the Debian release `node:26-slim` is built on, so the addon links against the same glibc. It copies `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml` and `crates/`, runs `cargo build --release -p cohost-bus-node` (BuildKit cache mounts for Cargo's registry and `target`) and copies the cdylib `target/release/libcohost_bus_node.so` to `cohost-bus.linux-x64-gnu.node` (event-bus Build, CI and Docker; BUS-NAT-BLD-009; DEPLOY-IMG-001). The stage has neither Node nor the napi CLI: the CLI only copies and names the library. It does not depend on the `SERVICE` build argument, so BuildKit builds it once for every service image.

1. `base`: `WORKDIR /app`, copy `package.json`, then `npm install -g corepack@0.36.0 && corepack enable && corepack prepare "$(node -p "require('./package.json').packageManager")" --activate` (Node 26 does not bundle corepack, so it is installed first), so the pnpm version is the `packageManager` field and nothing else (DEPLOY-IMG-006).
2. `build`: `CI=true`, copy `pnpm-workspace.yaml package.json pnpm-lock.yaml tsconfig.base.json tsconfig.json`, then `packages/` and `services/`, `pnpm install --frozen-lockfile`, a copy of the addon from `native` into `packages/bus/native/`, then `pnpm exec tsc -b`. Every service image carries the addon, since every service uses the bus. The root `tsconfig.json` references every package and service project, so every service directory must exist in the build context and every image compiles the whole workspace.
3. `runtime`: `ARG SERVICE`, `ENV NODE_ENV=production SERVICE=${SERVICE}`, `COPY --from=build /app /app` (the full tree including sources and dev dependencies), `CMD ["sh","-c","exec node services/${SERVICE}/dist/index.js"]`.

The Dockerfile does not prune: under pnpm 10, `pnpm prune --prod` empties `services/*/node_modules` and drops the `@cohost/*` workspace links (issue #6), and `pnpm deploy --prod` on pnpm 10.0.0 needs `inject-workspace-packages=true`, which fails `--frozen-lockfile` unless enabled workspace-wide (commit 18ea80a). The consequence is a larger image that ships dev dependencies. No `USER` is set (containers run as root, so files the config loader seeds into the bind mount are root-owned on Linux hosts) and the Dockerfile declares no `HEALTHCHECK` (Compose supplies it).

`.dockerignore`: `node_modules`, `**/node_modules`, `**/dist`, `.git`, `data`, `.env`, `**/*.tsbuildinfo`, `**/*.log`, `**/*.node`, `target`, `config/.vts-token`, `config/config.yaml`, `config/secrets.yaml`, `config/personality.md`, `config/expressions.yaml`. Excluding `**/*.node` keeps an addon built on the host out of the `build` stage's `COPY packages`, so the image always runs the one the `native` stage built; excluding `target` keeps Cargo's build directory (gigabytes on a developer machine) out of the context (DEPLOY-IMG-004). Excluding `.tsbuildinfo` stops stale host incremental state from making `tsc -b` in the image skip emitting while `**/dist` is ignored (issue #7, commit 7e89e4e). It does not exclude `worktrees/`, `docs/` or `graphify-out/`, which only inflate the context. `config/` can hold the VTube Studio credential (`<config>/.vts-token`, `services/avatar/src/drivers/vtube-studio.ts`) the operator's own `config.yaml`, `personality.md` and `expressions.yaml` and the credentials file `secrets.yaml`; `.dockerignore` excludes those five files so no credential or operator file reaches the daemon (DEPLOY-IMG-005). The `config/*.example.*` files stay in the context; the Dockerfile copies only `packages/` and `services/`, and config arrives by bind mount.

## Installer: `scripts/install.sh`

`set -euo pipefail`, runs from the repo root, flag `--no-pull`. Steps in order:

1. Detect WSL (`grep -qi microsoft /proc/version`), source `/etc/os-release`, warn if the distro is not Ubuntu or Debian.
2. Detect NVIDIA via `nvidia-smi`.
3. If `docker` is missing, install docker-ce from the Docker apt repo, `usermod -aG docker`, start the daemon (`service` on WSL, `systemctl` otherwise), then stop and exit non-zero with a "log out and back in, then re-run" message, because the current shell lacks the new group and the docker commands below would fail part-way (DEPLOY-INST-010); on every run, die if `docker compose version` fails.
4. If a GPU exists and `docker info` shows no NVIDIA runtime, install `nvidia-container-toolkit` if needed, `nvidia-ctk runtime configure`, restart Docker.
5. If Node is missing or its full version (from `node -p process.versions.node`) is below the minimum in the root `package.json` `engines.node` (major, then minor, then patch), install the NodeSource setup for that minimum's major (piped to `sudo -E bash`) (DEPLOY-INST-009); if `pnpm` is missing, `npm install -g corepack@0.36.0`, `corepack enable` and prepare the `packageManager` version of `package.json`, read by `pnpm_spec` (DEPLOY-IMG-006).
6. Seed `.env` and the four `config/` files (`config.yaml`, `secrets.yaml` with mode 0600, `personality.md`, `expressions.yaml`) from their examples if absent; rewrite the `COMPOSE_FILE=` line in `.env` on every run from the GPU detected on that run (GPU: `docker-compose.yml:docker-compose.gpu.yml`), replacing a hand-set value by design; fill an empty `CONTROL_TOKEN=` line with a generated secret (DEPLOY-INST-013); `mkdir -p data` (the services that keep files there create their own folders beneath it, such as `data/dashboard/avatar-models/`).
7. If `rustup` is missing, install it from rustup.rs as the invoking user with no default toolchain (`sh -s -- -y --default-toolchain none`); then, on every run, install the toolchain `rust-toolchain.toml` pins with its components (rustup reads the file from the repo root, so the script names no Rust version), source `$HOME/.cargo/env` so `cargo` is on the path for the rest of the run, and install `build-essential` if `cc` is missing, since Rust links through the C toolchain (DEPLOY-INST-014). The host needs the addon because the dashboard, `cohostctl` and the Docker-free dev loop run there and import `@cohost/bus`.
8. `pnpm install --frozen-lockfile`, aborting with its error on a lockfile mismatch as CI and the `Dockerfile` do, never falling back to a plain `pnpm install` (DEPLOY-INST-012), then `pnpm build:native` to build the bus addon on the host, then `pnpm typecheck` (DEPLOY-INST-007).
9. Unless `--no-pull`: `docker compose pull --ignore-buildable`, `up -d ollama models`, follow `models` logs, `docker compose wait models`.
10. Smoke test: `up -d redis postgres`, then `probe <name> 60 <fn>` polls `redis-cli ping`, `pg_isready` and, when pulling, Ollama `/api/tags` once a second until each passes (printing `  <name> ok`) or 60 s elapse, when it prints one failure line naming the probe and exits non-zero (DEPLOY-INST-007). The probes compare command substitutions rather than piping into `grep -q`, so `pipefail` cannot turn an early-closing reader into a false failure.
11. Next steps: run `pnpm dashboard`, open the dashboard URL and press Launch, instead of `docker compose up -d` (DEPLOY-INST-008), then a step starting the optional `eyes`, `ears`, `mouth` and `discord` profiles that names `connections.discord.token` in `secrets.yaml` as the one Discord bot; the dashboard URL uses `dashboard.port` as the built `@cohost/config` loader returns it, and when the load fails the installer prints the loader's first error line and a URL without a port, since the dashboard's own start output shows the address (DEPLOY-INST-008); the Docker-free dev loop lists `redis postgres ollama tts stt` (DEPLOY-INST-011).

Enforcement is the `cla` workflow (DEPLOY-CI-005):

- **Who must sign.** Each commit in the pull request resolves to one contributor: the commit author's GitHub account, else the committer's GitHub account, else the raw author name. Every such contributor must have signed, not only the pull request's opener.
- **No allow-list.** The action matches allow-list entries against the commit author's raw name, and a commit whose author email is not linked to a GitHub account resolves to that raw name, so an entry such as `CoderCoco` or `*[bot]` could be claimed by anyone who sets that author name. The workflow therefore sets none: the owner signs once like any contributor, and the repository uses no bot accounts that commit to pull requests. The action itself skips `github-actions[bot]` by account id. A bot that later commits to pull requests is added by its exact account name.
- **Signing once.** A signature is recorded once per contributor, with the pull request it was given on; later pull requests from the same contributor pass without a new comment.
- **Where signatures live.** `.github/cla/signatures.json` on the dedicated `cla-signatures` branch. The branch carries a seed file, `{"signedContributors": []}`, because v2.6.1 fails with a 404 comparison bug on the first pull request when the file is missing; after the seed only the action writes it. `main` is protected by a repository ruleset that requires pull requests, which would reject the action's direct commits, so the record lives on an unprotected branch that only the action writes. That branch must exist before the workflow first runs.
- **What it does not check.** `Co-authored-by:` trailers are not read, so a co-author named only in a trailer is not asked to sign; a pull request with human trailer co-authors needs their signatures collected by hand before it merges. Corporate contributions are out of scope: the CLA is individual only, and someone contributing on an employer's behalf opens an issue first.
- **History.** Commits already on `main` before the `cla` workflow existed are not re-checked.

The rule, which the dashboard's UI build carries out ([dashboard](../dashboard/dashboard-design.md) Libraries and notices):

- **Every bundled third-party package has a notice.** "Third-party" is a package outside the pnpm workspace that ends up in a built UI bundle (the workspace's own `@cohost/shared/head-rotation` is cohost's code under the AGPL, not a third party's). The build writes one file, `assets/third-party-notices-<hash>.txt`, `<hash>` being the first 8 hexadecimal characters of the SHA-256 of its content so that a changed file has a new name, with each package's name, version, licence expression and the full text of its licence files (a file in the package's root named `LICENSE`, `LICENCE`, `COPYING` or `NOTICE`), and each entry script's first line is a comment naming the file. Being under `assets/`, it is served wherever the bundle is, the LAN listener included.
- **Only permissive licences ship without a decision.** The build fails when a bundled third-party package has no licence file, or its SPDX licence expression is not satisfied by MIT, ISC, BSD-2-Clause, BSD-3-Clause, Apache-2.0, 0BSD, CC0-1.0, Unlicense, Zlib or BlueOak-1.0.0 (an `OR` is satisfied by any allowed alternative, an `AND` only by all), until the owner has decided and the list names it. A copyleft or unknown licence inside a served bundle may not combine with the AGPL and the commercial licence, so adding one is a decision, not an install.
- **Dev-only packages are not shipped.** A package used only by the build or the tests (the bundler, the test DOM) is not in any served file and needs no notice.
- **The owner's own models are not covered.** A VRM model is the owner's asset under its author's terms; cohost stores and serves it for the owner and takes no licence in it.

## Developer scripts (`scripts/dev/`)

`bus-pub.ts` validates a payload with the bus zod schemas then publishes (`exit 1` on rejection, `2` on unknown type, bad JSON or no arguments); `bus-tail.ts` does a non-group `XREAD` tail with `--replay N`, `--json` and type filters; `stub-llm.ts` fakes Ollama `/api/tags` and `/api/chat` (not `/api/embed`) on `STUB_LLM_PORT` (11434); `stub-tts.ts` fakes `/v1/audio/speech` and returns a pulsing 24 kHz WAV on `STUB_TTS_PORT` (8880). All import the bus from `../../packages/bus/src` (source, not `dist`). For service-level runs the config segment's `llm.provider: mock` and `voice.engine: stub` need no extra process; the stubs serve a run that wants a real HTTP server in place of Ollama or Kokoro.

## Open Questions & Future Decisions

- **Profiles for `tts` and `stt`.** With another engine selected, the Kokoro and speaches containers still start and `voice` and `ears` still depend on them (speaches is also the fallback batch engine). Putting them behind profiles would let an install skip them, at the price of a default `docker compose up -d` that does not start the default engines. Decision wanted.
- **Profile and engine are two settings.** The profile is in `.env`, the engine in `config.yaml`, and they must agree; a mismatch shows as a down dependency. Whether the Settings screen should offer the profile is open.
- **The Blackwell tag as the GPU overlay's default.** Reading A (kept): the owner sets `KOKORO_IMAGE` after trying it. Reading B: the overlay names an exact versioned cu128 tag, once one is known to exist and run on an RTX 5080. Whether a versioned cu128 tag exists is unverified.

## Manual verification

Needs a Docker daemon, a real account or a real run; the docs site's Single-PC checklist page (`docs/advanced/testing/single-pc.md`) is where each is checked and ticked off.

1. **Compose behaviours.** DEPLOY-COMPOSE-003, -006, -010, -015 and -017 and the smoke script's health polling (DEPLOY-CI-002) are read from the files, not executed against a daemon here; the launch end-to-end test (CTRL-STACK-015, DEPLOY-CI-007) skips without a daemon and has passed against Docker Desktop and runs on the CI runner's Docker.
2. **Installer.** The Docker-install stop (DEPLOY-INST-010) runs only on a machine that lacks Docker; `probe`, the port lookup and the Node version check were run in isolation.
3. **CLA workflow.** The `cla` workflow runs from the base branch on `pull_request_target`, so it cannot run on the pull request that adds it and has no local harness; its behaviour (DEPLOY-CI-005) is read from the action's source at the pinned tag until a pull request exercises it. `contributor-assistant/github-action@v2.6.1` runs on the `node20` action runtime.
4. **First real run.** `cohostctl launch` against the real stack (images, model pulls, healthchecks) is the first step of the single-PC checklist (DEPLOY-HOST-004).

- Deployment depends on every service segment (builds and runs them) and on `config` (`.env.example`, `config/*.example.*`, `CONFIG_DIR`, seeding), `control-plane` (the healthcheck binary `packages/control/dist/healthcheck.js` and heartbeats), `event-bus` (`scripts/dev` imports `packages/bus/src`; Redis is the only service every container waits for), `memory`/`cortex`/`voice`/`ears`/`eyes` (dependency ordering), and `dashboard` (the host-run program the start script launches; it reaches Redis and voice on loopback, proxies `/audio/`, and stores injected uploads in Redis, from which the containers read them, so nothing in a container needs to reach the host). The control plane's stack controller runs `docker compose up -d --remove-orphans` and `docker compose stop` against this Compose file.
- Nothing depends on deployment at runtime.
