# control-plane

Status: AUDITED. The document describes intended behaviour; where the code does not match, the text names the `[ ]` spec line. Parent: [high-level-design](../../high-level-design.md). Specs: [control-plane-specs.md](control-plane-specs.md).

## Context and Design Philosophy

The control plane is the operator-facing half of "know what is running and change it". It has three parts that share one vocabulary (the service manifest):

1. A **heartbeat contract**: every app service publishes `service.heartbeat` on a separate Redis stream, `cohost:health`. The publisher half lives in `packages/shared/src/lifecycle.ts` (`startHeartbeat`, called from `packages/shared/src/boot.ts`), the consumer half in `packages/control/src/health.ts` (`HealthTracker`).
2. A **controller**: `ServiceController` (`packages/control/src/controller.ts`) turns "start/stop/restart service X, resume or fresh, optionally isolated" into runtime calls, behind a small set of guards, and emits an audit event. The one runtime is `ComposeRuntime` (`runtime.ts`): compose is the only runtime, and the control plane never spawns or supervises host processes, so no service handles another service outside the container runtime.
3. A **stack controller** (`packages/control/src/stack.ts`, CTRL-STACK-*): whole-stack actions (launch, rebuild, stop-all, restart-all, and the consolidate one-shot), a Compose status probe, and the derivation of one stack state from it. The host-run dashboard's Launch button and `cohostctl launch` run the same code (Stack controller, below).
4. Two clients of that core: the dashboard (HTTP routes, `services/dashboard/src/control.ts`, `routes.ts`, `feed.ts`; owned by the dashboard segment), which runs on the host outside Compose, and the `cohostctl` CLI (`packages/control/src/cli.ts`). A third consumer, `healthcheck.ts`, is the docker-compose container healthcheck.

Guiding ideas:

- **Allow-list, not command passing.** `manifest.ts` states that nothing from a request reaches an argv except by picking a manifest entry; the runtime re-checks the id against the manifest even though the controller already did.
- **UI-agnostic core.** The controller and tracker know nothing about HTTP or WebSocket; the dashboard and CLI inject the audit callback and the group resetter (`controller.ts`, `cli.ts`, the dashboard's `control.ts`).
- **Monitoring is cheap and safe, control is gated.** The tracker runs unconditionally in the dashboard (`services/dashboard/src/index.ts`); control is off unless `CONTROL_ENABLED=1` (`config.ts`).
- **Derived states are local.** Tracker states are computed from receive time and never published (`health.ts`).

The package is `@cohost/control` (`packages/control/package.json`): ESM, AGPL-3.0-only, `bin.cohostctl` is `dist/cli.js`, depends on `@cohost/bus` and `@cohost/config`. `@cohost/config` supplies `findWorkspaceRoot` (to `stack.ts`, `lock.ts` and `cli.ts`) and `urls` (to `cli.ts`). `index.ts` re-exports health, manifest, runtime, docker, stack, lock, controller, config and cli but not healthcheck or latency, because healthcheck is a script and latency is reached through `cli.ts`.

## Service manifest

`SERVICE_MANIFEST` (`manifest.ts`) lists 20 units: every Compose service the controller may act on. The dashboard is not one: it runs on the host, outside Compose, so there is no container to start, stop or restart, and the manifest carries no `self` flag.

Two small builders (`svc`, `compose`, in `manifest.ts`) fill defaults: `composeName` equals `id`, `pnpmFilter` is `@cohost/<id>` for `svc` and removed for `compose`.

**Unit ids are service names.** A unit id is the name of a process: the `service` its heartbeat publishes, its Compose service name, the `SERVICE` build argument its container healthcheck checks and the name `HealthTracker` and `withContainerRestarts` key entries by (MOD-MAN-012). It is not the name of a platform: the Discord connector's unit is `connector-discord`, while `discord` is the connector id it registers under, the tag of its source and sink and the name of its config section (connections LLD, Process naming). Anything that names a process uses the unit id; anything that names the platform keeps `discord`. The preset variable names are the env spellings introduced by `add-isolated-backends` (`config/config.example.yaml:19,38,49,109,110,128,134,148` interpolate them).

**One list of services.** `appServiceIds()` (`manifest.ts`) returns the ids of the units that have a `pnpmFilter`, the twelve application services (CTRL-MANIFEST-005). It is the `HealthTracker`'s default known list, so the dashboard's tracker and `cohostctl status` show the same rows; the dashboard's own heartbeat still shows in every snapshot as a service that has sent one. No other list of services exists in `packages/control`; the dashboard page takes its unit list from `GET /services/manifest` (dashboard DASH-HTTP-014, DASH-UI-021), which is `unitDescriptors()`.

**Start modes and the bus.** Where a restarted service starts reading is decided by the service itself: every subscription names a bus start mode, `latest` (reset the group to `$` on every start) or `resume` (keep the stored position); memory subscribes with `resume`, every other service with `latest` (event-bus BUS-SUB-010, BUS-SUB-011). The controller's `fresh` / `resume` mode is an operator override on top of that: `fresh` resets the unit's manifest groups before the start, which matters for `resume` subscribers (memory) and is redundant for `latest` ones; `resume` leaves the groups alone, so a `latest` service still skips its backlog. The manifest defaults agree with the bus modes for every unit: `fresh` for each service that owns groups except memory (the `latest` subscribers), `resume` for memory and the compose-only units. Each pnpm service that subscribes owns a group of its own name (memory also `memory-recall` and `memory-notes`), so a `fresh` start resets exactly the groups the service reads under.

**Isolated starts and requirements.** The manifest `requires` field lists the units a unit needs on the bus (cortex requires salience and affect). An isolated start of a unit first starts its `requires` closure, followed transitively, depth-first in list order, each unit once, then the named unit. Each required unit starts with its own isolation preset and its own default mode, and is audited as its own start. A required unit that fails to start ends the start: the named unit is not started and the result is `ok: false`, naming the failed unit. A non-isolated start, and every restart and stop, act on the named unit only (CTRL-GUARD-008).

The isolation preset is a start-time override of one container, injected by the control plane and never an operator setting: `isolatedEnv` maps override names (the keys of `ISOLATION_OVERRIDES`, config CFG-ISO-006) to values, the names are labels and not environment variables, and the control plane delivers the whole preset in one variable, `COHOST_ISOLATION`, a JSON object of those names and values (CTRL-RUNTIME-009). The names appear in no `.env.example`, the loader applies each entry by key path (config CFG-ISO-007), and the settings editor reports a key a running unit has overridden (module-contract MOD-CFG-018) instead of presenting a permanent shadow. The container keeps the override across `docker compose restart`, which keeps its environment, until it is started again without one.

**Module-contract fields.** Each application unit also carries the descriptor fields the [module contract](../module-contract/module-contract-design.md) defines (`config`, `uses`, `pause`, `test`; MOD-MAN-*), and the tracker's known services and `cohostctl status`'s list derive from the manifest (MOD-MAN-006). The tracker adds a `needs` annotation from `uses` (MOD-LIFE-001) without changing any derived state.

## Runtimes and controller

### Runtime interface

`Runtime` has `name` (always `compose`), `start(id, opts)`, `stop(id)`, `restart(id, opts)` returning `{ ok, detail? }`. `StartOptions` carries `env` (the isolation preset, which the runtime serialises into `COHOST_ISOLATION`). `ServiceController` and both clients construct `ComposeRuntime` unconditionally (CTRL-CLI-004, DASH-CTRL-001); there is no runtime selection, and the `Runtime` interface remains so tests can inject a fake.

### ComposeRuntime (`runtime.ts`)

- start: `docker compose up -d <composeName>`; stop: `docker compose stop <composeName>`; restart: `docker compose restart <composeName>`.
- With a non-empty env override, restart becomes `up -d --force-recreate` because a native `restart` keeps the container's environment.
- Executed via `execFile` (argv array, no shell), 120 s timeout, `cwd` defaults to the process cwd, so `docker-compose.yml` must be found there (`runtime.ts`). Both clients construct it with `cwd` set to the workspace root (`findWorkspaceRoot()` from `@cohost/config`, else the process cwd), so Compose finds the file, `.env` and the project name however the client was started (CTRL-STACK-001). The runtime sets `COHOST_ISOLATION` on the `docker` CLI process: the preset's JSON for an isolated start or recreate and the empty string for every other action, which also replaces a value inherited from the shell or read from Compose's own `.env` interpolation (CTRL-RUNTIME-009, CTRL-RUNTIME-013); it sets no per-name variable.
- The isolation preset reaches the container through one pass-through entry in the compose `x-ts-service` environment (and in the `tools` service's own environment, DEPLOY-COMPOSE-026), `COHOST_ISOLATION: ${COHOST_ISOLATION:-}` (CTRL-RUNTIME-009), so an empty value leaves the literal values of `config.yaml` in charge. The entry belongs to `docker-compose.yml` (deployment segment); without it an isolated compose start would set the preset only in the `docker compose` CLI's own environment and nothing would reach the container.
- The compose runtime is driven from the host: by the dashboard, which always runs on the host outside Compose, and by `cohostctl`. Both use the host's own `docker` CLI and the owner's access to it; no container receives the Docker socket.
- Failure returns `ok: false` with stderr (else message) truncated to 500 chars.
- **Log directory** (CTRL-RUNTIME-016). Before the same commands, the control plane creates `data/logs` under the workspace root as the user running it, so the `./data/logs` bind mount of the application containers (deployment DEPLOY-COMPOSE-029) finds an owner-owned directory instead of one Compose would create as root; host-run programs write their log files there too (config Logging). A failure is a warning: the containers' logs still reach `docker compose logs`.
- **Secret projection** (CTRL-RUNTIME-014, deployment DEPLOY-SECRET-004). `packages/control/src/project-secrets.ts` turns the manifest into the unit list (each unit with a Compose service and a non-empty `secrets` list, by `composeName`; `consolidate` and `reembed` use `memory`'s) and calls `projectSecrets` from `@cohost/config` (CFG-SEC-019); its built entry `packages/control/dist/project-secrets.js` runs the same call from the command line for the installer and a hand-run stack, exiting 0 on success and 1 with the error on stderr (CTRL-RUNTIME-015). Before `start`, `restart` (either form), `consolidate` and `reembed`, the runtime runs the secrets projection (`@cohost/config`, deployment Secret scoping): it writes each unit's `secrets/units/<composeName>/secrets.yaml` from `secrets/secrets.yaml` and the manifest's `secrets` lists. When it fails, the `docker compose` command is not run and the action returns `ok: false` with a detail naming the file or directory and the reason, never a value. Every unit is projected each time, so a restart of one unit also refreshes the others' files, which they read at their next start.

### ServiceController (`controller.ts`)

Guard order:

1. Unknown id: `refused: "unknown"` (HTTP 404 in the dashboard). `dashboard` is an unknown id.
2. `infra` and not `advanced`: `refused: "forbidden"` (403); detail names `CONTROL_ADVANCED=1`.

There is no third refusal: the manifest has no `self` flag, so nothing is refused as a conflict.

Refusals are returned before anything runs and are not audited, by design (commit `1d316ff`).

Mode and orchestration: effective mode is `resume` for infra, otherwise the caller's `mode`, otherwise the manifest default. `fresh` only takes effect when the unit owns groups.

| Action | Condition | Calls |
|---|---|---|
| stop | always | `runtime.stop` (never resets groups) |
| start | fresh | reset each group, then `runtime.start` |
| start | resume | `runtime.start` |
| start | isolated, unit has `requires` | the closure first (each required unit as an isolated start in its own default mode, audited separately), then the named unit's start as above |
| restart | resume, no isolation env | `runtime.restart` (native) |
| restart | fresh or isolation env | `runtime.stop`, then (only if it resolved ok) reset groups if fresh, then `runtime.start` |

Isolation env is `{ ...def.isolatedEnv }` when `isolated` is set and the unit is not infra, else `undefined`. Because an empty object is truthy, isolated restarts of salience or affect (empty presets) also take the stop-then-start path.

The consumer-group reset is `Bus.resetGroup` (`packages/bus/src/index.ts`, event-bus segment): `XGROUP SETID cohost:events <group> $`, creating the group with `MKSTREAM` at `$` when missing and ignoring `BUSYGROUP`. `resetConsumerGroups` runs groups in manifest order and stops at the first failure with detail `consumer group reset failed: ...`. A failed reset aborts the start (tested in `controller.test.ts`).

Audit: after any executed attempt the controller calls `audit({ service, action, by, ok, detail? })`, with `detail` present whenever the runtime returned one (on success too, which is useful audit data), inside a try/catch that swallows errors ("the audit is best effort, e.g. bus down while stopping redis"). Both clients wire it to `bus.publish("service.lifecycle", rec)` (`cli.ts`, and the dashboard's `control.ts`, which also swallows and logs). The `service.lifecycle` schema is in `packages/bus/src/events.ts` (event-bus segment); the event is published on `cohost:events`, not on the health stream.

## Stack controller

The owner's decisions are settled: the host-run dashboard has a Launch button that brings up the whole application through the compose runtime, it can stop the stack and restart its services, and the stack actions live in this package so the dashboard and `cohostctl` share one implementation. The mechanics below are owner-confirmed (CTRL-STACK-001 to 012, CTRL-CLI-010 to 012).

`StackController` wraps the same injected exec as `ComposeRuntime` (argv array, no shell, the workspace root as `cwd`, the caller's environment) and takes no caller input that reaches an argv: every command is fixed (CTRL-STACK-001, CTRL-STACK-009). It reports progress through an optional `onPhase(kind, phase)` callback and returns a result `{ ok, detail?, services? }`, where `services` is the last status the action saw.

| Action | Commands | Phases | Timeout |
|---|---|---|---|
| `status()` | `docker compose ps --all --format json` | none | 10 s |
| `statusWithRestarts()` | `status()`, then `docker compose ps --all -q` and one `docker inspect` over the ids (restart counts and preset overrides) | none | 10 s each |
| `launch()` | `docker compose up -d --build --remove-orphans`, then `status()` every 2 s until ready | `compose-build`, `waiting` | 30 min for `up` (a build can be long); 180 s for readiness |
| `rebuild()` | the same as `launch()`, reported under kind `rebuild` | `compose-build`, `waiting` | as `launch()` |
| `stopAll()` | `docker compose stop` | `stopping` | 300 s |
| `restartAll(controller)` | `status()`, then `ServiceController.restart` per running application unit | `restarting <id>` | per restart, 120 s (CTRL-RUNTIME-001) |
| `consolidate()` | `ComposeRuntime.consolidate` (CTRL-RUNTIME-010) | `running` | 30 min |

- **Status** (CTRL-STACK-008). Parses the JSON Compose prints (a JSON array, or one object per line, depending on the Compose version) into `{service, status, health?, exitCode?}` per container of the project. It never throws: a missing `docker` binary, a daemon that does not answer, or unparsable output yields `docker: {ok: false, detail}` with the stderr or message cut to 500 characters. A project with no containers is a successful status with an empty list.
- **Restart counts** (CTRL-STACK-014, CTRL-HEALTH-010). `docker compose ps` does not report restarts, so `statusWithRestarts()` lists the project's container ids (`ps --all -q`, each id checked against a hex pattern before it can reach an argv) and reads `RestartCount`, the Compose service label and the environment entries with one `docker inspect --format`. From the environment it keeps only the `COHOST_ISOLATION` entry, parses its JSON, and keeps, as the container's `overrides`, the entries whose name is an override name of the manifest and whose value is non-empty, discarding every other environment entry without logging or returning it (the environment also holds `CONTROL_TOKEN` and any other `.env` value, so the inspect output is never placed in an error detail or a log line either); the dashboard's stack status passes `overrides` on so the settings editor can say which units run isolated (CTRL-STACK-016). A failure of either extra command leaves the plain status. `withContainerRestarts` overlays the counts on the heartbeat snapshot: a service the heartbeats cannot vouch for (`unknown`, `stale`, `down`) whose container is `restarting`, or is stopped after three or more restarts, shows `crash-looping`, which is how a service that dies before its first heartbeat becomes visible. The dashboard probe and `cohostctl status` use it; the launch readiness poll does not.
- **Rebuild** (CTRL-STACK-013). The same command as Launch, kept as its own action name for the callers that already use it (the dashboard's Rebuild button, `cohostctl rebuild`).
- **Launch** (CTRL-STACK-002 to 005). `up -d` with no service names starts every service Compose would start for a plain `up`: profile-gated services (`eyes`, `ears`, `mouth`, `connector-discord`, `consolidate`, `reembed`, and the engine servers `tts-pocket`, `stt-nemotron`, `stt-kyutai`) join only when `COMPOSE_PROFILES` in `.env` names them, and `COMPOSE_FILE` in `.env` keeps the GPU overlay. `--remove-orphans` removes containers of services the Compose file no longer defines. `--build` is always passed, so an image never lags the code (an unchanged build context is a cache hit and costs a few seconds). Before `up`, Launch (and Rebuild) runs the secrets projection as the runtime does, and fails without running `up` when it fails (deployment DEPLOY-SECRET-004); it then writes the Pocket TTS Hugging Face token (`voice.pocket.hf_token`, read through the config loader) to the file `data/tts-pocket-secret/hf_token` under the workspace root, creating the directory and omitting the file when the token is blank ([deployment](../deployment/deployment-design.md) Speech engine servers). After `up` succeeds, the controller polls until every long-running container (every container except the one-shots `models`, `consolidate` and `reembed`) is `running` and either `healthy` or without a healthcheck (ollama, tts, stt), and then resolves `ok: true`. If that does not happen within the readiness timeout, it resolves `ok: false` naming each container that is not ready with its status and health; it stops nothing (no rollback), so a partial stack stays up for the owner to inspect. A one-shot that exited non-zero (a failed model pull) is appended to `detail` as a warning without making the launch fail, matching DEPLOY-COMPOSE-011. Launching an already-running stack is the same command: Compose leaves services that match the file alone, starts stopped ones and recreates any whose configuration differs (for example one that an isolated start recreated with a preset).
- **Lifecycle lock** (CTRL-LOCK-001 to 004). The dashboard and `cohostctl` are separate processes and Compose does not serialise two `up`, `stop` or `restart` runs against one project, so every lifecycle action (stack or service) holds a lock file, `data/control.lock` under the workspace root, for its duration. The file carries the holder's pid, entry point (`dashboard` or `cohostctl`), action and start time. A second action finds the file, sees a live pid and is refused with `busy: <action> held by <by> (pid <pid>)`: a 409 from the dashboard (DASH-STACK-009), exit 1 from `cohostctl`. A file whose pid is gone (a crash) is removed and the lock taken. The lock is taken at the entry point, not inside `StackController` or `ServiceController`, because `restartAll` calls the controller's restart and the whole action is the unit that must not overlap. It is a file, not a Redis lock, because Redis is down before a launch and during a stop-all, which are exactly the actions that need it. Both processes run on the same host (the dashboard is a host process and `cohostctl` a shell command), so a pid check is sound.
- **Stop-all** (CTRL-STACK-006). `docker compose stop` stops every container of the project, infrastructure included, in reverse dependency order with Compose's grace period, so every service shuts down through `onShutdown` (memory records `notes.shutdown_run_owed`, MEM-CONSOL-013). It never runs `down` and never removes volumes, containers or networks.
- **Restart-all** (CTRL-STACK-007). Restarts, in manifest order, every manifest unit that is an application service (a unit with a `pnpmFilter`) whose container the status shows `running`, each through `ServiceController.restart` in its default mode and not isolated, so each is guarded and audited like a single restart. Infrastructure and the compose-only units (`ollama`, `tts`, `stt`) are left alone. A failed restart does not stop the rest; the result is `ok` only when every restart succeeded, and `detail` names each failure.
- **Windows interop env** (CTRL-RUNTIME-012). A Windows process started from WSL2 receives only the variables named in `WSLENV`. When the Docker executable ends in `.exe`, the runtime appends `COHOST_ISOLATION` to `WSLENV` (colon-separated, existing entries kept, once), so an isolated start's preset reaches `docker compose` and then the container through CTRL-RUNTIME-009.
- **Docker binary** (CTRL-STACK-012). Every command, the per-unit runtime's included, runs `COHOST_DOCKER_BIN` when set, else `docker`, else `docker.exe`. On WSL2 with Docker Desktop and no WSL integration only the Windows `docker.exe` is on the path; it is started from the distro with the workspace root as its working directory, which Windows sees as a `\\wsl.localhost\...` path, so the `./config` bind mount and `.env` resolve through that path. The single-PC test checklist (deployment DEPLOY-HOST-004) exercises Launch this way.
- **Guards** (CTRL-STACK-010). Stack actions do not go through the per-unit guards: they need no `CONTROL_ADVANCED`, because Launch must start Redis and Postgres and stop-all is a deliberate whole-stack act. Restart-all goes through the controller and so never touches infrastructure.
- **Stack state** (CTRL-STACK-011). A pure function maps a status and the running action (if any) to one of `docker-unavailable`, `stopping`, `starting`, `down`, `up`, `degraded`, in that precedence: Docker not answering; a stop running; a launch running; no long-running container `running`; every long-running container ready; some long-running container still `starting` its healthcheck with none exited, restarting or unhealthy; otherwise `degraded`. The dashboard shows it; `cohostctl launch` uses the same readiness test.

The stack state is computed from Compose, not from the heartbeat tracker, because only Compose can say whether Docker answers and which containers exist, infrastructure included, and because it works while Redis is down. The tracker keeps the per-service detail; the Compose healthcheck of each application container is itself heartbeat freshness (CTRL-CHECK-001), so the two views agree.

## Heartbeat contract and health derivation

### Publisher (`@cohost/shared`)

The publisher's mechanics are specified by shared-runtime (SHARED-LIFE-006 to 014); its code is `startHeartbeat` in `packages/shared/src/lifecycle.ts`, called from `packages/shared/src/boot.ts`. This segment keeps what the published states mean (Health derivation). The description below is of that publisher.

`startHeartbeat(bus, { service, version?, mode, deps, detail?, intervalMs?, log? })` returns `{ ready(), degraded(detail?), stop() }`.

- Payload fields: `service`, `instance` (the bus consumer name, `hostname-uuid8`), `pid`, `version` (option, else `COHOST_VERSION`, else `dev`), `startedAt` (`processStartedAt`, the module-load time), `state` (`starting`, `ready`, `degraded`, `stopping`), `deps` (`ok`, `down`, `n/a` per name), `mode` (`live`, `mock`, `off` by convention, a free string in the schema), optional `detail`, `intervalMs`.
- Cadence: one `starting` publish at call time, a steady `setInterval` of `intervalMs`, an immediate publish on `ready()` or `degraded()`, and a watcher at `min(1000, intervalMs)` that republishes if `[state, deps, mode, detail]` changed. Both timers are `unref`ed.
- A standing `detail` option is published in every state, including `starting` and after `ready()`. Precedence: explicit `degraded(detail)`, then `dependency down: ...`, then the standing detail (SHARED-LIFE-013).
- `intervalMs` is `HEARTBEAT_INTERVAL_MS` floored when positive and finite, else 5000 (`.env.example`).
- Dependency-derived degradation: if the base is `ready` and any dep is `down`, the published state is `degraded` with detail `dependency down: a, b`, unless an explicit detail was given. An explicit `degraded(detail)` keeps its own detail. A service that is still `starting` stays `starting` even with a dep down.
- Shutdown: `stop()` is registered with `beforeShutdown` (SHARED-LIFE-010). The shutdown sequence itself is event-bus's: `onShutdown` (`packages/shared`) awaits all registered hooks, capped at 2 s, and then runs the service's own callback and `process.exit(0)` (SHARED-LIFE-001). So the `stopping` heartbeat is only sent if the service calls `onShutdown`; there is no handling of other exit paths (crash, `process.exit`, SIGKILL).
- Failure: a rejected `publishHealth` is logged at warn and swallowed.
- `tracked(fn, set)` wraps an async call to feed dep status.
- Transport (owned and specified by event-bus, BUS-STREAM-004 and BUS-HEALTH-001 to 004): `Bus.publishHealth` validates against the zod schema and `XADD`s to `cohost:health` with `MAXLEN ~ 1000`; `Bus.publish("service.heartbeat")` throws (`packages/bus/src/index.ts`). `Bus.tailHealth` is a non-group `XREAD` tail; `Bus.recentHealth(n)` is `XREVRANGE` reversed to oldest-first.

Every app service owns a `src/health.ts` exporting a `HeartbeatSpec` (service, mode, deps) and calls `startHeartbeat` itself; those files belong to each service's segment. The dashboard's own heartbeat is in `services/dashboard/src/index.ts`.

### HealthTracker (`packages/control/src/health.ts`)

State precedence in `derive` (`health.ts`), evaluated with the tracker's own clock (`Date.now` by default):

1. `unknown` if no heartbeat has ever been seen for a known name.
2. `crash-looping` if at least 3 distinct `startedAt` values were first seen within the last 60 s (`CRASH_LOOP_RESTARTS = 3`, `CRASH_LOOP_WINDOW_MS = 60000`); this beats everything else, including silence.
3. `down` if the last heartbeat is `stopping` or its age exceeds `10 x intervalMs` (`DOWN_FACTOR`).
4. `stale` if age exceeds `3 x intervalMs` (`STALE_FACTOR`).
5. `degraded` if the last heartbeat state is `degraded` or `starting`, or any dep is `down`.
6. `up` otherwise.

Details worth knowing:

- Age is `now - receivedAt` on a monotonic clock (`performance.now()` by default), so a wall-clock step (sleep, NTP, a VM clock correction) cannot revive or kill a service (CTRL-HEALTH-008). Live heartbeats are stamped on arrival. `seed(history)` converts each record's wall-clock `ts` into a monotonic receive time `now - max(0, wallNow - ts)`; a record stamped in the future counts as received now, so a publisher clock ahead of the observer's cannot make a silent service look fresh (CTRL-HEALTH-009). The monotonic axis has no meaningful origin: a freshly started process (the `cohostctl status` case) reads a small `performance.now()`, so seeded receive times are routinely negative and are kept as such, never floored at zero (CTRL-HEALTH-011); flooring them would give every seeded record age zero and let an old `starting` heartbeat tie with, and beat, the newest `ready` one.
- A replayed older heartbeat does not overwrite a newer one; start history is trimmed to the 60 s window except for the current process's start. Consequently a long-running service reports `restarts: 0`, and a service with exactly one start inside the window reports `restarts: 1`.
- `snapshot()` returns the known list (default `appServiceIds()`) plus any other name that has sent a heartbeat. `onChange` listeners are called only when the per-service key (derived state, restarts, heartbeat state, mode, detail, deps, instance) changes; `tick()` re-derives time-based transitions. `lastSeenAgeMs` is deliberately not in the key.
- The dashboard feeds it with `recentHealth(500)` then `tailHealth` and runs `tick()` every second (`services/dashboard/src/feed.ts`); `GET /services` returns the snapshot (`routes.ts`) and WebSocket clients get a `services` message on change.

### Container healthcheck (`healthcheck.ts`)

`isHealthy(service, recent, now)` takes the newest heartbeat for the service from the list and is true iff it exists, is not `stopping`, and `now - latest.ts < 3 x intervalMs`. `checkHealth` reads `recentHealth(200)` and the server time and maps them to the exit code; the script exits 0 or 1, exits 2 without an argument, and hard-exits 1 after 4 s. It is wired as `node packages/control/dist/healthcheck.js $$SERVICE` in the `x-ts-service` anchor (`docker-compose.yml`, interval 10 s, timeout 5 s, retries 3, start period 30 s); `SERVICE` is baked in by the `Dockerfile` (`ENV`).

The healthcheck compares the heartbeat's bus-side `ts` (publisher time) with the Redis server's own clock (`Bus.serverTime`, Redis `TIME`), not the container's, so a container whose clock is off cannot flap its own health (CTRL-CHECK-004); a server time that cannot be read is unhealthy. The healthcheck's bus waits for its first connect attempt like any `Bus` (at most 10 s, event-bus BUS-NAT-CONN-006); the script's own 4 s limit ends a check whose Redis never answers, inside Compose's 5 s timeout. The test of `Bus.serverTime` runs the real facade on a fake `BusTransport` (`BusOptions.transport`), since the bus has no connection-level seam. With roughly eleven services beating every 5 s, 200 records covers about 100 s, comfortably more than the 15 s freshness bound; a much shorter `HEARTBEAT_INTERVAL_MS` would shrink that window.

## cohostctl and configuration

CLI (`cli.ts`): `cohostctl status [service]`, `cohostctl start|restart <service> [--mode resume|fresh] [--isolated]`, `cohostctl stop <service>` (no options), `cohostctl consolidate`, `cohostctl reembed`, `cohostctl latency [--count N]` (the speech-path and vision-path report, Latency report below), and the stack commands `cohostctl launch`, `cohostctl rebuild`, `cohostctl stop-all` and `cohostctl restart-all` (CTRL-CLI-001, CTRL-CLI-010 to 012, CTRL-CLI-014). The stack commands take no arguments or options; `launch`, `rebuild` and `stop-all` never open the bus (the bus is not up before a launch and goes down during a stop), print the phases and the final per-container status, and exit 0 or 1; `stop-all` ends with a hint that `cohostctl consolidate` can tidy viewer notes; `restart-all` opens the bus to audit each restart with `by: "cohostctl"`. Parsing uses `node:util.parseArgs`; any parse problem raises `UsageError` and exit code 2 with the usage text, before a runtime is built, the bus is opened or any Docker command runs (CTRL-CLI-013). Every command except `status` first takes the lifecycle lock (CTRL-LOCK-004); a held lock is a refusal, exit 1. Exit codes: 0 success, 1 refusal or failure, 2 usage.

- `status` builds a throwaway `HealthTracker` with known = `appServiceIds()`, seeds it from `bus.recentHealth(200)`, overlays the Compose restart counts when Docker answers (CTRL-CLI-015) and prints `service  state  mode  Ns ago` per row. Because the known list excludes infra and compose-only units, `cohostctl status redis` reports `unknown service` and exits 1.
- `executeCli` is the whole of `cohostctl` (the entry guard only calls it): it parses first, then builds a `ComposeRuntime` (no runtime selection and no `CONTROL_RUNTIME` or `CONTROL_PROCESS_MODE` setting exists), constructs `new Bus("cohostctl")` lazily, on first use by `status`, `start`, `stop`, `restart`, `restart-all` or `latency` (never for `consolidate`, `reembed`, `launch`, `rebuild` or `stop-all`), passes `by: "cohostctl"` and `advanced` from `CONTROL_ADVANCED === "1"`, and stops the bus in `finally` when it was opened. Its factories (bus, runtime, stack) are injectable, which is how the wiring is tested.
- `consolidate` runs the Compose `consolidate` one-shot (deployment DEPLOY-COMPOSE-018; the memory service's viewer-note pass, `MEM-CONSOL-012`) through `ComposeRuntime.consolidate`, which executes `docker compose run --rm -T consolidate` and waits for it (CTRL-RUNTIME-010, CTRL-CLI-008). It is a job, not a service: it is not in the manifest, takes no service name or options, and bypasses `ServiceController`, so it has no guards, no consolidator-group reset and no `service.lifecycle` audit record. It also never opens the bus, so it works after the owner has stopped the whole stack (`docker compose down`, `cohostctl stop-all`, the dashboard's Stop button), which is when it is useful (CTRL-CLI-009). Because it can take minutes (one model call per consolidated batch), its exec timeout is 30 minutes instead of the 120 s the lifecycle verbs use. The pass is best-effort: the memory service catches up at its next start (`MEM-CONSOL-013`), so a failure is reported (exit 1) and nothing else changes. `docker compose run` starts `postgres` and `ollama` if they are down and leaves them running.
- The bus `cohostctl` opens is fail-fast (BUS-STREAM-009): no background reconnect and no output from the native layer. A command waits for the first connect attempt (immediate for a refused connection, at most the 10 s connect timeout for one nobody answers); when it fails with code `BUS_CONNECTION`, `cohostctl` prints `cannot reach Redis at <url>: <reason> (is the stack up? run cohostctl launch)`, the reason being the error's message, and exits 1 (CTRL-CLI-017).
- It runs as the invoking user and does not read `CONTROL_ENABLED` or `CONTROL_TOKEN` (those only gate the dashboard's HTTP surface).
- `executeCli` runs from the entry guard only when `process.argv[1]` ends with `cli.js`. Since `index.ts` re-exports `cli.js`, importing the package from another entry script runs nothing, but the check is a suffix match, so any other entry script named `cli.js` that imports `@cohost/control` would also start the CLI. Running the TypeScript source under tsx does not trigger it either (the suffix would be `cli.ts`), so `cohostctl` only works from the built `dist`; the README invokes it as `mise run cohostctl`, which builds the addon and `packages/control` and runs `dist/cli.js`.

Config gate (`config-gate.ts`): `configRefusal(check = checkConfig)` turns the config segment's problem list (config CFG-RCV-002) into one refusal: `undefined` when nothing fails, otherwise `the config is invalid (<n> problem(s); first: <path>): fix it on the dashboard's config recovery screen (mise run dashboard), then try again` (CTRL-GATE-001). `cohostctl launch`, `rebuild`, `start`, `restart` and `restart-all` print it and exit 1 before they take the lifecycle lock, build anything or open the bus (CTRL-CLI-018): every service would fail its own load moments later, and a launch would rebuild images for nothing. `stop`, `stop-all`, `status`, `consolidate`, `reembed` and `latency` are not gated, since none starts a service from the configuration. The dashboard in config recovery mode answers its stack and lifecycle routes with the same text (dashboard DASH-RCV-010). The check never caches: it reads the files as they are now.

Configuration (`config.ts`): `loadControlConfig(env)` is used by the dashboard. `CONTROL_ENABLED` must be exactly `1`; otherwise `{ enabled: false }`. Enabled requires a non-blank `CONTROL_TOKEN`. `CONTROL_ADVANCED` defaults to off. The config carries no listen address: the dashboard's address is its own `DASHBOARD_HOST`, with `LOOPBACK_BIND` (`127.0.0.1`) as the default it applies. The config carries no runtime choice. `bearerOk(header, token)` compares SHA-256 digests with `timingSafeEqual`. `isLoopback` accepts `localhost`, `::1`, and anything starting with `127.`.

| Env var | Read by | Meaning |
|---|---|---|
| `CONTROL_ENABLED` | `loadControlConfig` (dashboard) | `1` turns the lifecycle routes and token gate on |
| `CONTROL_TOKEN` | `loadControlConfig` | required bearer secret when enabled |
| `CONTROL_ADVANCED` | both | `1` allows redis and postgres mutations |
| `REDIS_URL` | `Bus` (via `@cohost/config` `urls.redis()`), CLI, healthcheck | bus address |
| `HEARTBEAT_INTERVAL_MS`, `COHOST_VERSION` | `startHeartbeat` (`packages/shared/src/lifecycle.ts`) | beat interval (default 5000) and reported version (default `dev`) |

Consumers of this segment: dashboard `control.ts` (`setupControl`, warns on non-loopback bind and on `CONTROL_ADVANCED`), `routes.ts` (404 when disabled, 401 without a bearer, body parsing of `mode` and `isolated`, refusal-to-status map unknown 404 / forbidden 403, and the stack routes), `feed.ts`, `index.ts`; and the compose healthcheck. Those files are specified in the dashboard segment; this segment owns the semantics they delegate to. The bearer gate guards mutations only: the LAN is the trust boundary, so health reads (`GET /services`, the WebSocket feed) stay open.

## Latency report

`cohostctl latency [--count N]` prints how long each stage of the speech path and of the vision path takes, from bus history (CTRL-LAT-001 to 014), as two titled sections (`speech path`, then `vision path`, CTRL-LAT-013). It reads the last `N` events (default 5000; the stream keeps about 20000, BUS-STREAM-002) with `Bus.recent`, so it needs Redis up and no running service. It is read-only, so unlike the lifecycle commands it takes no lifecycle lock and publishes no `service.lifecycle` (CTRL-LAT-002); `status` and `latency` are the commands that take no lock.

A sample is the first `brain.say` of an `id` whose `timing.audioEndedAt` is present (an injected or interjected `brain.say` is never a sample, CTRL-LAT-029), joined by `id` to the `voice.utterance` and to a `voice.playing` of the line's first clause (`seq` 0; a streamed line has one `brain.say` and so one sample, and its later clauses are not read): the earliest from a real output sink (a `sink` other than `virtual`, voice's own stand-in sink, VOICE-SINK-001), else the earliest `voice.playing`. A `brain.say` marked `injected` (a dashboard test injection) is not a sample, so injected lines never skew the figures (the id is the line's id all the way down: cortex mints it, voice copies it, sinks report it). The stamps are the [event-bus](../event-bus/event-bus-design.md) `timing` object plus the envelope `ts` of the joined events:

| Stage | From | To |
| --- | --- | --- |
| `endpoint` (only when `closedAt` is present) | `audioEndedAt` | `closedAt` |
| `stt` | `closedAt` when present, else `audioEndedAt` | `heardAt` |
| `salience` | `heardAt` | `focusedAt` |
| `prep` | `focusedAt` | `llmStartedAt` |
| `llm` | `llmStartedAt` | `llmEndedAt` (the first clause cut from the stream; the whole reply with an `llm` or `http` critic), less the `tool` stage when that row is present |
| `tool` (only when `toolStartedAt` and `toolEndedAt` are both present) | `toolStartedAt` | `toolEndedAt` |
| `critic` | `llmEndedAt` (when the critic ran) | `criticEndedAt` |
| `say` | `criticEndedAt` when present, else `llmEndedAt` | `brain.say` envelope `ts` |
| `tts` | `brain.say` envelope `ts` | `voice.utterance` envelope `ts` (first clause) |
| `sink` | `voice.utterance` envelope `ts` (first clause) | joined `voice.playing` envelope `ts` (first clause) |
| `total` | `audioEndedAt` | joined `voice.playing` envelope `ts` |
| `think` (speech path, when `heldAt` is present; not in the sum) | `focusedAt` | `heldAt` (the end of the think's own work, not the confirm) |

`endpoint` is the end-of-speech wait: the time from the last speech frame to the utterance being closed, which `ears.silence_ms` sets. Early reply never shortens it. It exists for an utterance ears cut itself from a connector source's frames, because only ears stamps `closedAt`; a clip posted to the `http` source, a file in `dir` and an injected line carry no `closedAt`, so for them there is no `endpoint` sample and `stt` runs from `audioEndedAt`. A `brain.say` marked `interjected` is not a sample, as one marked `injected` is not: it answers a pause, not the end of speech, and its stamps, which are never removed once set, would otherwise read as a response time.

**A prepared reply.** A sample whose `brain.say` carries `confirmedAt` was released from a provisional think by a confirm (HLD Early reply). cortex kept its real stamps, which may precede the final, so the report cuts the stages after `stt` from `confirmedAt`, the time the confirmation reached cortex, and the stages still add up to `total`:

- `salience` runs from `heardAt` to `confirmedAt`, the wait from the final to the confirmation reaching cortex (`focusedAt`, the provisional focus's time, is not used);
- `prep` starts at `confirmedAt`, the end of `salience`, and not at `focusedAt`;
- every boundary from the start of `prep` through the start of `say` is raised to at least `confirmedAt`: `prep`, `llm`, `tool` and `critic` are computed from their stamps so raised, so a stage that finished before the confirmation is zero and one still running at it counts only its remainder, and `say` starts at the later of its ordinary start and `confirmedAt`;
- `tts`, `sink` and `total` are as for any sample.

The real think time is its own row, `think`, printed after `total` and left out of the sum: `focusedAt` to `heldAt`, the stamp cortex sets when the provisional think stops working (its first clause held, or parked at a tool call). A reply without `heldAt` (released before the think stopped working, not prepared, or a confirm that cortex treated as an ordinary focus) has no `think` sample. The saving shows as short `prep`, `llm` and `critic` rows, with `endpoint` unchanged.

When any early transcript was read, the report prints, after the speech-path rows (and after the line of omitted durations, when there is one), the line `early transcripts: <p> published, <w> retracted, <r> reused as the final, <b> replies released from a prepared think, <i> interjections spoken, <l> still running at the close`, and an `early stt` row in the stage layout with the p50 and p95 of `sttMs` over the early transcripts read. The counts come from the same history as the samples, each event once: `p` counts the `speech.early` events (each distinct `utteranceId` and `seq`), `w` the `speech.retracted` events, `r` the `speech.heard` events that carry `earlySeq`, `b` the `brain.say` events whose timing carries `confirmedAt`, `i` the `brain.say` events marked `interjected`, and `l` the `speech.heard` events flagged `earlyLate` (an early transcription that was still running at the close and published nothing is counted only in ears' own heartbeat count). A nonzero `l` says the early snapshot came too late: `ears.early.after_ms` is too long for the engine, or the engine too slow. The line is absent when all six counts are zero. A published early transcript that is neither retracted nor reused in the window read is in flight or belongs to an utterance whose final fell outside it. A `brain.say` marked `injected` counts in neither `b` nor `i`; one marked `interjected` counts in `i` only, even when it carries `confirmedAt` (CTRL-LAT-026). `r` and `l` key a `speech.heard` by its `utteranceId`, or by the envelope id when it carries none.

A reply whose first clause waited for a tool reports a `tool` row between `prep` and `critic`, and its `llm` row excludes that wait, so the stage lines still add up to `total`; a reply with only `toolStartedAt` (its first clause was spoken during the wait, as the filler or as text before the call) has no `tool` row, because the co-host did not make anyone wait for it; when that first clause is the filler or the built-in line its `brain.say` carries `llmEndedAt` equal to its own publication and no `criticEndedAt`, so `llm` is the wait before the co-host spoke and `say` is zero. A vision-path sample is a `brain.say` whose `timing.capturedAt` is present and `timing.audioEndedAt` is absent, joined the same way (CTRL-LAT-011; its stages are those of CTRL-LAT-012). Its stages replace `stt` with `describe` (`capturedAt` to `describedAt`, eyes) and start `salience` at `describedAt`; `prep` to `sink` are those of the table above, and `total` runs from `capturedAt` to the joined `voice.playing` (CTRL-LAT-012). The vision path has no `tool` or `think` row (CTRL-LAT-013), so its `llm` keeps any tool wait. The path of a line is decided by its stamps: speech focus carries `audioEndedAt` and vision focus carries `capturedAt`, never both. A section with no samples prints its own no-sample line (CTRL-LAT-008, CTRL-LAT-014).

The stages are contiguous, so for a fully stamped sample they sum to `total`. For a streamed line every stage is the first clause's: the report measures how long the co-host takes to start speaking, and what follows the first clause (later clauses, the end of the line) is not a stage. The report is a header line (`stage`, `n`, `p50`, `p95`) and one row per stage with the sample count, p50 and p95 in whole milliseconds, columns of width 9, 5, 8 and 8 (CTRL-LAT-005), with percentiles by nearest rank over the sorted durations. Each stage is computed on its own: a sample missing any stamp or joined event a stage needs contributes to the other stages and not to that one, so a line still in flight (no `voice.playing` yet), a `brain.say` with no `voice.utterance`, and a think with no critic each still count where they can. Stamps are read defensively: a stamp that is absent, not an integer or negative removes only the stages that use it and never stops the report or drops the line (CTRL-LAT-006). A negative duration (stamps out of order, or a clock that differs between hosts) is left out of that stage's statistics and counted (CTRL-LAT-007). The report assumes one host clock for every service, as the HLD states; it cannot detect a cross-host skew that leaves durations positive. A duplicated or replayed event is counted once (CTRL-LAT-003). The chat path has no report: `attention.focus` carries no id of the `chat.message` it answers, so a chat-triggered line cannot be tied to its message (CTRL-LAT-009, deferred).

An utterance that never closes, or whose transcript is dropped, publishes no `speech.heard` and so yields no sample; there is nothing for the report to repair.

**Measuring the connector path.** The report reads whatever history holds, so the connector path needs no option: a run that feeds frames through a source tag (HLD Latency budget, Measuring the connector path) produces samples with an `endpoint` row, and the same run with `ears.early.enabled` on and off shows the saving in `prep`, `llm` and `critic` against `endpoint` and in the early counts. An `http` run is the baseline of the stages after the close. The report does not label a sample as early or not; the counts give the share, and two runs, each read with its own `--count`, give the comparison.

| Readiness signal | Container state and Compose healthcheck from `docker compose ps` | The heartbeat tracker | Works with Redis still coming up and covers infrastructure, which sends no heartbeat; the application healthcheck is heartbeat freshness, so the signals agree. |

| Heartbeat timers | One steady interval plus a faster change watcher (at most 1 s) | Publish on every dep mutation | Comments in `startHeartbeat` (deps are "re-read every check so changes publish immediately"; one timer for the beat, one at most 1 s for changes). | Stages sum to `total` | `critic` runs from `llmEndedAt` to `criticEndedAt`, so the hand-off between the reply call and the critic belongs to the critic; with no critic there is no gap, `say` starts at `llmEndedAt`, and the stages stay contiguous | A separate `gap` stage; leave the hand-off in no stage | A `gap` stage would be empty whenever the critic is off and would add a line that means nothing to the owner; folding keeps the table contiguous in both cases, so the stage lines add up to the total. |
