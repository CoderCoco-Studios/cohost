# deployment specs

Prefix `DEPLOY`. Design: [deployment-design.md](deployment-design.md). No OpenSpec capability covers this segment (the retired `openspec/specs/` baseline has none for Compose, the Dockerfile, the installer, CI, the docs site or licensing), so no spec below carries an OpenSpec reference.

Verified against the files at git `49ba935` (audit pass 2026-11-01). Owner decisions of 2026-11-01 applied at git `1b57790`.

Markers: `[x]` implemented; `[ ]` intended but not yet implemented (gap); `[D]` deferred. DEPLOY-COMPOSE-016 is retired with the containerised dashboard; the number is not reused.

Annotations: `@spec DEPLOY-…` comments sit in the deployment files themselves. In `docker-compose.yml` and `docker-compose.gpu.yml` they are trailing comments on mapping keys, and in `Dockerfile` and `scripts/install.sh` they are appended to existing comment lines; everywhere else they are full comment lines. `<!-- impl: path:line -->` points at an implementation in a file that carries no annotation (a file owned elsewhere, or plain data such as `.gitignore`). `<!-- test: path:line -->` points at a test that exercises the line.

## Compose topology

- [x] **DEPLOY-COMPOSE-001**: The base `docker-compose.yml` shall define the infrastructure services `redis`, `postgres`, `ollama`, `tts`, `stt`, the one-shot `models`, the one-shot `consolidate`, and one application service per directory under `services/` except `dashboard` (`chat`, `salience`, `affect`, `memory`, `cortex`, `voice`, `avatar`, `eyes`, `ears`, `mouth`), and no `dashboard` service, because the dashboard runs on the host. <!-- test: packages/config/test/compose-consolidate.test.ts:26 --> <!-- test: packages/config/test/compose-chat-data.test.ts -->
- [x] **DEPLOY-COMPOSE-002**: Each application service shall be built from the single root `Dockerfile` with the build argument `SERVICE` set to its directory name, and shall inherit the shared `x-ts-service` settings: `restart: unless-stopped`, `env_file: .env`, the in-network URLs `REDIS_URL`, `DATABASE_URL`, `OLLAMA_URL`, `TTS_URL`, `STT_URL`, `VOICE_URL`, `CONFIG_DIR=/app/config` (no dashboard address: injected uploads reach eyes and ears over Redis), the `./config:/app/config` bind mount, the `host.docker.internal:host-gateway` extra host, a dependency on `redis` being healthy, and the container healthcheck (DEPLOY-HC-001). <!-- test: packages/config/test/compose-standalone.test.ts -->
- [x] **DEPLOY-COMPOSE-003**: While a variable is set in a service's `environment` block (`REDIS_URL`, `DATABASE_URL`, `OLLAMA_URL`, `TTS_URL`, `STT_URL`, `VOICE_URL`, `CONFIG_DIR`), the Compose stack shall use that value over the same name in `.env`, so those addresses cannot be changed through `.env` for containerised services. <!-- test: packages/config/test/compose-standalone.test.ts -->
- [x] **DEPLOY-COMPOSE-004**: The `eyes` service shall belong only to the `eyes` profile, the `ears` service only to the `ears` profile, the `mouth` service only to the `mouth` profile, the `connector-discord` service only to the `discord` profile and the `consolidate` service only to the `tools` profile; every other service, including `models`, `tts` and `stt`, has no profile, so a plain `docker compose up -d` starts everything except `eyes`, `ears`, `mouth`, `connector-discord` and `consolidate`. <!-- test: packages/config/test/compose-consolidate.test.ts:67 --> <!-- test: packages/config/test/compose-chat-data.test.ts -->
- [x] **DEPLOY-COMPOSE-005**: Where a service has dependencies beyond redis, Compose shall order startup as follows: `memory` waits for `redis` and `postgres` healthy and `ollama` started; `cortex` for `redis` healthy and `ollama` started; `voice` for `redis` healthy and `tts` started; `ears` for `redis` healthy and `stt` started.
- [x] **DEPLOY-COMPOSE-006**: The infrastructure ports `redis` 6379, `postgres` 5432, `ollama` 11434, `tts` 8880 and `stt` 8000 and the `voice` port 8700 shall be published on `127.0.0.1` only, and no Compose service shall publish a port on any other interface. <!-- test: packages/config/test/compose-standalone.test.ts -->
- [x] **DEPLOY-COMPOSE-007**: The `voice` service shall publish its HTTP server (`VOICE_PORT`, default 8700) on `127.0.0.1:8700` only, so the host-run dashboard reaches it at its `urls.voice()` default `http://127.0.0.1:8700`, while containers keep using `http://voice:8700` and browsers keep receiving audio only through the dashboard's `/audio/` proxy. <!-- test: packages/config/test/compose-standalone.test.ts -->
- [x] **DEPLOY-COMPOSE-008**: When the `models` service starts, it shall wait for `ollama` to answer `/api/tags`, then request `/api/pull` for `LLM_MODEL`, `VISION_MODEL`, `EMBED_MODEL` and `NOTES_MODEL` from `.env` one after another, printing the last 200 bytes of each response, and exit; `NOTES_MODEL` shall fall back to `gemma3:4b` when it is unset or empty, the value `config.example.yaml` and `.env.example` ship; it shall not pull `STT_MODEL`. <!-- test: packages/config/test/compose-models.test.ts:65 -->
- [x] **DEPLOY-COMPOSE-009**: The stack shall persist data in the named volumes `redis-data`, `pg-data`, `ollama-data` and `stt-cache`; `redis` and `postgres` shall expose healthchecks (`redis-cli ping`, `pg_isready -U cohost`; every 5 s, 3 s timeout, 10 retries) used by `depends_on`.
- [x] **DEPLOY-COMPOSE-010**: Where `docker-compose.gpu.yml` is layered over the base file (via `-f` or `COMPOSE_FILE`), the overlay shall add an NVIDIA device reservation (`count: all`) to `ollama`, `tts` and `stt` and switch `tts` and `stt` to the GPU images `ghcr.io/remsky/kokoro-fastapi-gpu:v0.10.0` and `ghcr.io/speaches-ai/speaches:0.8.3-cuda` unless `KOKORO_IMAGE` / `SPEACHES_IMAGE` are set.
- [x] **DEPLOY-COMPOSE-011**: If a model pull requested by the `models` service fails (curl reports an HTTP error, or the response carries an `"error"` line), then the `models` container shall exit non-zero after attempting every model, except that a failed pull of `NOTES_MODEL` shall be logged as a warning on stderr and shall not change the exit status (viewer-note capture degrades to writing no notes without it); it shall carry no restart policy. <!-- test: packages/config/test/compose-models.test.ts:78 --> <!-- test: packages/config/test/compose-models.test.ts:90 -->
- [x] **DEPLOY-COMPOSE-012**: The `ollama` service shall keep loaded models resident for 24 h (`OLLAMA_KEEP_ALIVE=24h`) and run with flash attention (`OLLAMA_FLASH_ATTENTION=1`) and a `q8_0` KV cache (`OLLAMA_KV_CACHE_TYPE`).
- [x] **DEPLOY-COMPOSE-013**: The `redis` service shall snapshot to the `redis-data` volume when at least one key changed in the last 60 s (`--save 60 1`) and shall keep no append-only file (`--appendonly no`).
- [x] **DEPLOY-COMPOSE-014**: Every image the Compose files name shall carry an exact version tag, never `latest` and never a floating major or minor: the base file runs `redis` from `redis:7.4.12-alpine`, `postgres` from `pgvector/pgvector:0.8.7-pg16`, `ollama` from `ollama/ollama:0.40.16`, `models` from `curlimages/curl:8.23.0`, `tts` from `KOKORO_IMAGE` (default `ghcr.io/remsky/kokoro-fastapi-cpu:v0.10.0`) and `stt` from `SPEACHES_IMAGE` (default `ghcr.io/speaches-ai/speaches:0.8.3-cpu`); the Redis and Postgres majors stay on 7 and 16 because their data volumes are not portable across majors. <!-- test: packages/control/test/compose.test.ts -->
- [x] **DEPLOY-COMPOSE-015**: The application services, `redis`, `postgres`, `ollama`, `tts` and `stt` shall restart unless stopped; the one-shot `models` shall carry no restart policy and the one-shot `consolidate` shall set `restart: "no"` (DEPLOY-COMPOSE-018). <!-- test: packages/config/test/compose-consolidate.test.ts:74 -->
- [x] **DEPLOY-COMPOSE-017**: The `x-ts-service` `environment:` block shall pass through the isolation variables the control plane's isolated start sets (`CHAT_SOURCE`, `MEMORY_STORE`, `MEMORY_EMBEDDER`, `LLM_PROVIDER`, `VOICE_ENGINE`, `AVATAR_DRIVER`, `VISION_ENABLED`, `VISION_ENGINE`, `EARS_SOURCE`, `EARS_STT_ENGINE`, `MOUTH_DISCORD_ENABLED`, `MOUTH_DRYRUN_ENABLED`) as `${VAR:-}` entries, so a value set on the `docker compose` process (`packages/control/src/runtime.ts:61`) reaches the container and an unset one falls through to the `${VAR:-default}` in `config.yaml` (control-plane CTRL-RUNTIME-009). <!-- test: packages/control/test/compose.test.ts --> <!-- test: packages/control/test/runtime.test.ts -->
- [x] **DEPLOY-COMPOSE-018**: The `consolidate` service shall run the memory service's one-shot `consolidate` command, so that `docker compose run --rm consolidate` runs one viewer-note consolidation pass over the stack's Postgres and Ollama and then exits with the command's status. It shall build from the root `Dockerfile` with `SERVICE: memory`, inherit the shared `x-ts-service` settings (env file, `environment`, the `./config` mount, `extra_hosts`), override the image's default command with `node services/memory/dist/consolidate.js`, set `restart: "no"`, disable the container healthcheck (the one-shot publishes no heartbeat, so the inherited check could never pass), and wait for `postgres` healthy and `ollama` started. It shall not depend on `redis`, because the command never opens the bus: a pass can run with the rest of the stack stopped. (Memory MEM-CONSOL-012, MEM-CONSOL-013.) <!-- test: packages/config/test/compose-consolidate.test.ts:32 --> <!-- test: packages/config/test/compose-consolidate.test.ts:41 --> <!-- test: packages/config/test/compose-consolidate.test.ts:53 --> <!-- test: packages/config/test/compose-consolidate.test.ts:61 -->
- [x] **DEPLOY-COMPOSE-019**: Where the `consolidate` service is selected (by name with `docker compose run`, or with `--profile tools`), Compose shall run it; no start, stop or `down` of the stack shall depend on it, because the pass is a best-effort extra and the memory service's catch-up at its next start is the guarantee (memory MEM-CONSOL-013). <!-- test: packages/config/test/compose-consolidate.test.ts:67 -->
- [x] **DEPLOY-COMPOSE-020**: The `mouth` service shall depend only on `redis` being healthy (no dependency on `voice`, `tts`, `ears` or `connector-discord`), publish no port and mount nothing of its own beyond the shared `./config` bind mount every application service gets (no data volume), so its fallback clip cache lives in the container's filesystem like ears' former cache. <!-- test: packages/config/test/compose-chat-data.test.ts -->
- [x] **DEPLOY-COMPOSE-021**: The `reembed` service shall run the memory service's one-shot `reembed` command in the `tools` profile with `restart: "no"`, no healthcheck and no dependency on `redis`, depending on `postgres` being healthy and `ollama` started, so that `docker compose run --rm reembed` migrates the stored vectors to the configured embedder's dimension and exits with the command's status; no start, stop or `down` of the stack shall depend on it. <!-- test: none -->
- [x] **DEPLOY-COMPOSE-022**: The `chat` service shall bind-mount `./data/chat` at `/app/data/chat` in addition to the shared `./config` mount, so the refreshed Twitch token chat persists under its data directory (CHAT-TW-011) survives a container being recreated (Rebuild, `docker compose down`); no other application service mounts `./data`. <!-- test: packages/config/test/compose-chat-data.test.ts -->
- [ ] **DEPLOY-COMPOSE-023**: The `connector-discord` service shall depend only on `redis` being healthy, publish no port, mount nothing of its own beyond the shared `./config` bind mount (no data volume), and receive `DISCORD_TOKEN` from `.env` (the one Discord token of the stack); `ears` and `mouth` shall not receive it.

## Container health

- [x] **DEPLOY-HC-001**: Every application service container shall run the healthcheck `node packages/control/dist/healthcheck.js $SERVICE` every 10 s with a 5 s timeout, 3 retries and a 30 s start period, with `SERVICE` taken from the image environment (`Dockerfile:20`).
- [x] **DEPLOY-HC-002**: When the healthcheck runs, it shall exit 0 only if the newest `service.heartbeat` for that service among the last 200 entries of `cohost:health` is younger than 3 times its declared interval and its state is not `stopping`, and shall exit 1 when no heartbeat is found, the heartbeat is stale, Redis cannot be read, or 4 s elapse. (Semantics owned by control-plane; this spec records the compose wiring.) <!-- impl: packages/control/src/healthcheck.ts:10-31 --> <!-- test: packages/control/test/healthcheck.test.ts:12 --> <!-- test: packages/control/test/healthcheck.test.ts:16 --> <!-- test: packages/control/test/healthcheck.test.ts:22 --> <!-- test: packages/control/test/healthcheck.test.ts:36 -->

## Image build

- [x] **DEPLOY-IMG-001**: The `Dockerfile` shall build in three stages on `node:22-slim` (`base` with corepack-activated pnpm at the version `packageManager` names (DEPLOY-IMG-006), `build`, `runtime`), where `build` copies the workspace manifests, `packages/` and `services/`, runs `pnpm install --frozen-lockfile` and `pnpm exec tsc -b`, and `runtime` copies the entire `/app` from `build`.
- [x] **DEPLOY-IMG-002**: The image shall set `NODE_ENV=production` and `SERVICE` from the build argument and start with `exec node services/${SERVICE}/dist/index.js`; it shall contain every service's built code regardless of `SERVICE`. <!-- test: scripts/compose-smoke.sh:20 -->
- [x] **DEPLOY-IMG-003**: The `Dockerfile` shall not run `pnpm prune --prod` (it removes the `@cohost/*` workspace links under pnpm 10 and crash-loops every service, issue #6); the smoke script shall guard this regression. <!-- test: scripts/compose-smoke.sh:20 -->
- [x] **DEPLOY-IMG-006**: The `Dockerfile` and `scripts/install.sh` shall take the pnpm version from the root `package.json` `packageManager` field and name no pnpm version of their own, so that field is the one place the version is written. <!-- test: packages/config/test/pnpm-version.test.ts -->
- [x] **DEPLOY-IMG-004**: The `.dockerignore` shall exclude `node_modules`, `**/dist`, `.git`, `data`, `.env`, `**/*.tsbuildinfo` and `**/*.log` from the build context, so stale incremental-build state cannot stop `tsc -b` from emitting output in the image and secrets in `.env` are not sent to the daemon.
- [x] **DEPLOY-IMG-005**: The `.dockerignore` shall also exclude the VTube Studio token `config/.vts-token` (written by avatar to `<configDir>/.vts-token`, `services/avatar/src/drivers/vtube-studio.ts:104`) and the user-owned files `config/config.yaml`, `config/personality.md` and `config/expressions.yaml` from the build context, so no credential or operator file is sent to the daemon; the `config/*.example.*` files stay in the context.

## Installer

- [x] **DEPLOY-INST-001**: When `scripts/install.sh` runs, it shall detect WSL2 from `/proc/version`, read `/etc/os-release`, warn but continue on a distribution other than Ubuntu or Debian, and report whether an NVIDIA GPU is visible through `nvidia-smi`.
- [x] **DEPLOY-INST-002**: Where `docker` is not installed, the installer shall install `docker-ce`, the CLI, containerd, buildx and the compose plugin from Docker's apt repository, add the user to the `docker` group and start the daemon (`service docker start` on WSL, `systemctl enable --now docker` otherwise); on every run it shall then abort unless `docker compose version` succeeds.
- [x] **DEPLOY-INST-003**: Where an NVIDIA GPU is detected and `docker info` does not list an NVIDIA runtime, the installer shall install `nvidia-container-toolkit` if absent, run `nvidia-ctk runtime configure --runtime=docker` and restart Docker.
- [x] **DEPLOY-INST-004**: Where Node is missing or older than 22, the installer shall install Node 22 from NodeSource; where `pnpm` is missing it shall enable corepack and prepare the `packageManager` version of `package.json` (DEPLOY-IMG-006).
- [x] **DEPLOY-INST-005**: When `.env`, `config/config.yaml`, `config/personality.md` or `config/expressions.yaml` is missing, the installer shall copy it from `.env.example` or the matching `config/*.example.*` file, and shall never overwrite an existing one.
- [x] **DEPLOY-INST-006**: When the installer runs, it shall re-detect the GPU and rewrite the `COMPOSE_FILE=` line in `.env` to `docker-compose.yml:docker-compose.gpu.yml` if an NVIDIA GPU was detected and to `docker-compose.yml` otherwise, on every run and replacing any value the operator set; a `.env` without a `COMPOSE_FILE=` line is left without one.
- [x] **DEPLOY-INST-007**: When the installer runs, it shall install workspace dependencies and typecheck; unless `--no-pull` is given it shall pull images (`--ignore-buildable`), start `ollama` and `models` and wait for `models` to exit while following its log; it shall then start `redis` and `postgres` and poll each probe (`redis-cli ping`, `pg_isready`, and when pulling Ollama `/api/tags`) once a second until it passes or 60 s elapse, printing `<name> ok` for a passing probe; if a probe does not pass in time, it shall print one failure line naming that probe and exit non-zero.
- [ ] **DEPLOY-INST-008**: When the installer finishes, it shall print as next steps to run `pnpm dashboard`, open the dashboard URL and press Launch (and no `docker compose up -d` step), with the URL built from `DASHBOARD_PORT` from the calling shell if set, otherwise from `.env`, otherwise 3000, reading `.env` as text (never sourcing it) and accepting only a numeric value, and shall add that the dashboard's startup log shows the URL it actually listens on (which differs when `PORT` or `DASHBOARD_HOST` is set); it shall also print a step starting the optional `eyes`, `ears`, `mouth` and `discord` profiles, naming the one Discord bot (`DISCORD_TOKEN`, used by the Discord connector). <!-- test: packages/config/test/installer.test.ts -->
- [x] **DEPLOY-INST-009**: When the installer decides whether Node is recent enough, it shall compare the numeric major version (`process.versions.node.split('.')[0]` as reported by `node`), so Node 9 is replaced and Node 100 is kept.
- [x] **DEPLOY-INST-010**: If `docker` was installed during the same run, then the installer shall stop after the Docker install with a message telling the operator to log out and back in (so the new `docker` group applies) and re-run it, and shall exit non-zero.
- [x] **DEPLOY-INST-011**: When the installer prints the Docker-free dev loop, it shall list the same infrastructure containers the README lists (`redis postgres ollama tts stt`).
- [x] **DEPLOY-INST-012**: If `pnpm install --frozen-lockfile` fails, then the installer shall show the error and exit non-zero, and shall never fall back to a non-frozen install that could rewrite `pnpm-lock.yaml`, matching CI and the `Dockerfile`.
- [x] **DEPLOY-INST-013**: When the installer runs and `.env` has a `CONTROL_TOKEN=` line whose value is empty (nothing, or only whitespace or an inline `#` comment, after the `=`), it shall replace that value with a newly generated 48-hex-character secret (24 random bytes), shall leave a non-empty `CONTROL_TOKEN` untouched, shall add no line when `.env` has none, and shall never print the token. <!-- test: packages/config/test/installer.test.ts -->

## Continuous integration

- [x] **DEPLOY-CI-001**: When a pull request is opened or `main` is pushed, the `test` workflow shall start a `redis:7.4.12-alpine` service, set `REDIS_URL`, run `pnpm install --frozen-lockfile` and `pnpm test` on Node 22 with the pnpm version from `packageManager` and a 10 minute timeout, and cancel an older run of the same ref.
- [x] **DEPLOY-CI-002**: When a pull request is opened or `main` is pushed, the `compose-smoke` workflow shall run `scripts/compose-smoke.sh`, which seeds `.env` from `.env.example` if absent, builds and starts `redis` plus the named services (default `salience affect avatar`) with `docker compose up -d --build`, polls until each named service's container reaches Compose health status `healthy` with `restarts=0` within `SMOKE_WAIT` seconds (default 60, one budget for all services), fails at once for a restart, an exit or an `unhealthy` verdict, prints the last 20 log lines of a failing service, and always runs `docker compose down -v` on exit. Every application service inherits the DEPLOY-HC-001 healthcheck, so each named service has one. <!-- test: packages/config/test/compose-standalone.test.ts -->
- [x] **DEPLOY-CI-003**: When `main` is pushed or the workflow is dispatched manually, the `pages` workflow shall run `pnpm docs:build`, upload `docs/.vitepress/dist` and deploy it to the `github-pages` environment, serialising runs without cancelling an in-flight deploy.
- [x] **DEPLOY-CI-004**: When a pull request is opened, CI shall run `pnpm docs:build` (build only, no upload or deploy) in the `docs-build` workflow, so a broken link or template error is caught before merge.
- [x] **DEPLOY-CI-005**: When a pull request is opened or synchronized, or a comment is created on one, the `cla` workflow shall run `contributor-assistant/github-action` (pinned to the full commit SHA of an exact release) in the base repository's context without checking out pull-request code, resolve each commit in the pull request to a contributor (the commit author's GitHub account, else the committer's, else the author name), and fail its check and post a comment linking `CLA.md` while any contributor has no recorded signature (the workflow sets no allow-list, so the owner signs like any contributor); when a contributor comments exactly `I have read the CLA Document and I hereby sign the CLA`, it shall record that contributor once in `.github/cla/signatures.json` on the `cla-signatures` branch and pass once every contributor is signed; a `recheck` comment shall re-run the check; and when the pull request is merged it shall lock the conversation. `Co-authored-by:` trailers are not checked, and commits already on `main` are not re-checked.
- [x] **DEPLOY-CI-006**: When a pull request is opened or `main` is pushed, the `lid-check` workflow shall run `node scripts/lid-check.mjs`, which exits non-zero, naming each offence, when a `@spec` ID cited in a source, test or deployment file is defined in no `*-specs.md` file, when a `*-specs.md` file defines the same ID twice, or when a spec file mentions an ID that no spec file defines on a line that does not say the ID is retired, moved or superseded (so a deleted ID cannot linger in a cross-reference); and exits 0 otherwise. The check reads files only and needs no install. <!-- test: packages/config/test/lid-check.test.ts -->
- [x] **DEPLOY-CI-007**: When a pull request is opened or `main` is pushed, the `compose-smoke` workflow shall also run the launch end-to-end test (`CTRL-STACK-015`) on the runner's Docker, so `StackController.launch` and `stopAll` run against a real Compose project. The step is in the workflow; CTRL-STACK-015 passed against a Docker daemon on 2026-11-11. <!-- impl: .github/workflows/compose-smoke.yml -->
- [x] **DEPLOY-CI-008**: When the `test` workflow runs, it shall start a `pgvector/pgvector:0.8.7-pg16` service (the tag `docker-compose.yml` pins) with an empty `cohost_test` database and set `COHOST_TEST_DATABASE_URL` to it, so the memory store's real-Postgres tests (`services/memory/test/notes-store.pg.test.ts`) run; with the variable set and the database unreachable in CI those tests shall fail the run instead of skipping. <!-- test: none -->
