# tools

> The tool service: MCP servers reached over HTTP, the co-host's built-in tools, the owner's per-tool settings, per-call timeouts, timers, and a mock mode. Specs: [tools-specs.md](tools-specs.md). HLD: [high-level-design](../../high-level-design.md) (Tool use, Tool runtime).

## Context and Design Philosophy

The co-host can look something up or do a small thing in the middle of a reply: what the stream title is, what was said earlier, what time it is, what a web search finds, "remind me in ten minutes". The model decides to; the `tools` service (`services/tools`) carries it out. cortex runs the model's tool loop and never calls a tool itself ([cortex](../cortex/cortex-design.md) The tool loop); `tools` owns everything outside the model: the connections to MCP servers, the built-in tools, which tool is allowed and for whom, how long a call may take, and the timers that act later. The two talk only through bus events (HLD tenet 1).

Design leanings:

- **The service is the allow-list.** Nothing is enabled by default, built-in tools included. A tool exists for the model only when the owner enabled it, and acts only when the owner marked it as allowed to act.
- **The owner decides who can cause a call.** A tool is offered to the model only when the reply was prompted by the owner, unless the owner marked that tool as usable for replies prompted by viewer chat. A tool that acts can never be marked for chat. The rule is enforced twice, by cortex when it chooses what to offer and by `tools` when it receives a request (Who can cause a call).
- **An acting call needs the owner's click.** Every prompt holds some viewer text (recent chat, recalled memories) even when the owner prompted the reply, so quoting alone would be the only barrier between a crafted chat message and an action. A call to a tool that acts waits for the owner to allow it in the dashboard, unless the owner marked that tool as needing no confirmation; the built-in `timer` never needs it (Confirming an acting call).
- **Scope.** The built-in tools and this design cover no control of the game or of OBS. An MCP server the owner adds and marks as allowed to act can do whatever it does: cohost cannot know what such a tool does beyond the server's label, which is why acting calls are confirmed. The design neither provides nor tests OBS or game control (HLD Non-Goal 4, Future / ideal state).
- **A result is information, not an instruction.** `tools` bounds a result; cortex quotes it before it reaches a prompt ([shared-runtime](../shared-runtime/shared-runtime-design.md) Untrusted text guard). A tool result never reaches `brain.say` except as input to cortex's reply (HLD tenet 4).
- **Every wait ends.** A call has a hard time limit and comes back as a result that says what happened, whatever the server does; cortex answers without a tool when the service is absent (HLD tenet 3).
- **HTTP only, nothing started locally.** An MCP server is a backend of `tools` the way the TTS server is a backend of `voice`: a URL. The service starts no process and the image is unchanged.
- **The dashboard manages it.** The owner adds a server by URL, sees the tools it offers and sets each tool's three marks from the dashboard; the settings live in `config.yaml` like every other setting ([dashboard](../dashboard/dashboard-design.md) The Tools settings).
- **Same posture as every service.** A server that is down degrades its own tools and nothing else; the service stays up and reports it in its heartbeat; with `tools.mode` `mock` it runs on Redis alone (HLD tenets 5 and 6).

This segment owns: the service, its subscriptions and heartbeat; the catalog and what a tool is; the call pipeline (checks, timeouts, result shaping); the MCP client; the four built-in tools; the timer and the way a fired timer reaches speech; which replies may use which tools; mock mode. It does not own the loop that talks to the model (cortex), the event schemas (event-bus), the `tools` config schema (config), the settings screen (dashboard), the quoting of results (shared-runtime), or the speaking gates (salience, cortex).

Code layout (`services/tools/src/`): `main.ts` wires `runService`; `catalog.ts` builds the tool list; `calls.ts` is the call pipeline; `mcp.ts` is the MCP client; `builtin/` holds `clock`, `stream-info`, `memory-lookup` and `timer`; `mock.ts` is mock mode; `health.ts` builds the heartbeat.

## Event wiring

Subscription: group `tools`, start mode `latest` (BUS-SUB-010): types `tool.request`, `tool.answer` (the owner's answer to a confirmation), `memory.recall.reply` (the answers to its own lookups, matched by `id`; any other id is ignored), `inject.request` (test injection, target `tools`) and nothing else. The service publishes `tool.result`, `tool.catalog`, `tool.confirm`, `tool.timer`, `memory.recall.request` and `inject.result`. It never reads `control`: it has no mute or pause, because it speaks nothing.

`ready` is reported once the `tools` group exists, whatever the state of the MCP servers. A server that cannot be reached when the service starts is a down dependency, not a reason to wait.

| Event | Direction | Meaning |
|---|---|---|
| `tool.request` | cortex to `tools` | One call the model asked for: the model-facing tool name, its arguments and the origin of the reply |
| `tool.result` | `tools` to cortex and the dashboard | The answer to one request, matched by `id` |
| `tool.catalog` | `tools` to cortex and the dashboard | The tools that exist, their marks and the state of each server; a snapshot, republished |
| `tool.confirm` | `tools` to the dashboard | An acting call is waiting for the owner's answer |
| `tool.answer` | dashboard to `tools` | The owner's Allow or Deny for one pending call |
| `tool.timer` | `tools` to salience; salience to the dashboard | A timer the co-host set has run out; salience marks one it dropped as missed |

The schemas are [event-bus](../event-bus/event-bus-design.md) Tool events; this document says what the fields mean and when each event is published.

**Correlation.** A request carries a fresh `id` (a uuid); the result has the same `id`, and so does the `tool.confirm` and `tool.answer` of the same call. This is the shape of the other request and reply pairs on the bus (`memory.recall.request` and `.reply`, `inject.request` and `.result`). cortex ignores a result whose `id` it is not waiting for, so a late result is harmless. The service answers every request that passes the bus's validation with exactly one result, including a request it refuses, and a call still in flight when the service stops with a `refused` result of reason `shutdown`; a request it never reads (the service is down) or the bus drops as malformed gets no result, and cortex's own wait bounds that case. `tool.answer` is trusted as published by the dashboard, because the bus is inside the operator's LAN trust boundary (HLD Trust boundary) and the dashboard is the program that gates the owner's click; the service checks the call's `id`, not the publisher. A `tool.request` whose `id` is already admitted (in flight or waiting for its confirmation) publishes nothing: it is logged at `warn` and the admitted request is untouched (TOOL-CALL-022).

## Tools and the catalog

A **tool** has a model-facing **name** (`[A-Za-z0-9_-]{1,64}`, the strictest rule among the model backends; [model-backends](../model-backends/model-backends-design.md) Provider contract), a description, a JSON Schema for its arguments, an **effect** and the owner's **marks**.

- **Names.** A built-in tool has a fixed bare name: `clock`, `stream_info`, `memory_lookup`, `timer`. A tool of an MCP server is named `<server>__<tool>`: the server's name from `tools.servers` (which contains no underscore, so the first `__` is the separator) and the tool's own name. A tool whose server or own name has a character outside the pattern, whose qualified name is longer than 64, or whose argument schema serializes to more than 4000 characters is not listed.
- **Third-party text.** A tool's description and schema are written by the MCP server, which is third-party text that reaches the model as part of its tool definition and cannot be quoted there. Three things bound it: the description is cut to 400 characters and the schema is refused above 4000 (fixed limits, not settings); the owner reads the description in the dashboard when approving the tool, which is the trust step; and the approval pins the definition, so a definition the server changes later is not offered until the owner approves it again (Pinned definitions). The model sees only tools the owner enabled and approved.
- **Label and effect.** A tool's **label** is `read`, `acts` or `unlabelled`. Each built-in tool declares its own: `timer` acts, the others read. An MCP tool's label comes from the server's own tool annotation: `readOnlyHint: true` is `read`, `readOnlyHint: false` is `acts`, no annotation is `unlabelled`; in mock mode the label is the entry's `effect` key. The label is the server's claim, and the dashboard shows it to the owner as one. A tool's **effect**, the value every rule below uses, is `acts` when its label is not `read` or the owner set its `acts` mark, and `read` otherwise: a tool the owner marked `acts` is treated as acting everywhere (confirmation, origin limits, ordering), whatever its server says.
- **Marks**, from `tools.allow` by tool name (Settings): `enabled`, `acts`, `chat` and `confirm`. `enabled` puts the tool in the model's offer. `acts` is the owner's allowance for a tool whose label is not `read`, and also marks any tool as acting. `chat` makes the tool usable for a reply prompted by viewer chat or by speech from a source the owner did not name (Who can cause a call). `confirm` (default true) makes a call to a tool that acts wait for the owner's answer. `acts` and `chat` on one tool is a configuration error (the load fails), so a tool that acts is never usable from chat.
- **Offered.** A tool is `offered` when it is enabled, its server is `ok` (or it is built in), its label is `read` or its `acts` mark is set, and, for an MCP tool, its pinned definition matches the server's. Otherwise it is not offered and carries a `reason` in the catalog, the first that applies in this order: `not_enabled`, `acts_not_allowed`, `not_approved`, `changed`, `server_down`. A server is `ok` or, in mock mode, `mock`.

### Pinned definitions

Each MCP tool's `allow` entry records `hash`, the SHA-256, as lower-case hexadecimal, of the tool's definition as the owner approved it in the dashboard: the JSON object of the qualified name, the title (cut to 100 characters, absent when the server gives none), the description as cut, the argument schema and the label, with every object's keys in sorted order at every depth and no whitespace outside strings, encoded as UTF-8. The label is covered, so a server that flips `readOnlyHint` makes the tool `changed`. The catalog carries the hash of the definition the server lists now. An enabled MCP tool with no recorded hash is `not_approved`; one whose recorded hash differs is `changed`. Neither is offered, a request for either is refused (`not_approved`, `definition_changed`), and the dashboard shows it as needing approval again. Approving writes the current hash with the `enabled` mark. Built-in tools are code of this project and are not pinned. In mock mode a tool's definition is fixed by the mock, and no pin is checked.

### The catalog

The catalog is the service's list of every tool it knows, with the effect, the marks, `hash`, `offered` and its `reason`, and a `servers` list giving each server's state (`ok`, `down`, `auth` or `mock`), whether it is marked external, and a `detail` sentence. Every listed tool counts toward the limits below, whether or not it is enabled. The service publishes it as `tool.catalog`:

- when it becomes ready, whenever the list or any server's state changes, and otherwise every `tools.catalog_ms` (default 30000), so a consumer that started later learns the state within one interval;
- it describes the process as it runs. Settings apply by restart (HLD tenet 10), so the marks are those of the saved file at the service's last start, and the dashboard compares them with the file.

**Size.** A server lists at most `tools.max_tools_per_server` tools (default 32) and the catalog at most `tools.max_tools` (default 64) in all, built-ins first and then servers in the order of `tools.servers`. The tools past a limit are not listed and cannot be enabled; the server's `detail` says how many were left out, and the dashboard shows it on the server's row so the owner sees why a tool is missing.

A consumer treats the latest catalog as current for three intervals (`intervalMs` is in the event) and as absent after that. cortex offers no tools while the catalog is absent. If `tools` stops, cortex keeps offering its tools until the catalog goes stale, about 90 s with the default interval; a call made in that time is answered by cortex's own wait as a timeout. There is no request for the catalog: neither cortex nor the dashboard blocks on the service.

An entry the owner enabled that no server lists (a removed server, a renamed tool) is not in the catalog and is never offered; the dashboard shows it as unknown.

## Who can cause a call

Every request carries the **origin** of the reply that asked for it, which cortex derives from the focus the reply answers ([cortex](../cortex/cortex-design.md) The tool loop), the **round** it was asked in (1 for the first round of the reply) and `listed`, whether the reply's speech source is named in a `tools.owner_sources` list. This table is the one definition of which origin may call which tool; cortex and `tools` both apply it.

| Origin | The reply was prompted by | Tools allowed |
|---|---|---|
| `speech` | a final transcript whose `source` the owner counts as theirs (`tools.owner_sources`: every source by default); an injected speech line is judged by the source the injection names, none when it names none | any offered tool |
| `dashboard` | the dashboard's own tool test (`as: tool`), never a focus | any offered tool |
| `reminder` | a timer the co-host set (`attention.focus` of kind `reminder`) | only an offered tool whose effect is `read`: never `timer`, never a tool that acts |
| `guest` | a final transcript from a source `tools.owner_sources` does not list | only a tool marked `chat` and whose effect is `read` |
| `chat` | a viewer's chat line (kind `chat`) | only a tool marked `chat` and whose effect is `read` |
| `vision` | a screen description (kind `vision`) | none |
| `idle` | no focus object (idle chatter) | none |

A focus's origin comes from its kind whether or not the focus was injected: an injected chat line is `chat` and an injected speech line is `speech` or `guest` by the rule above, so injecting can never reach more tools than the real input. **Owner-prompted** means `speech`, `dashboard` or `reminder`. `tools.owner_sources` is the word `all` (the default) or a list of source names valid for `ears.sources` (`http`, `dir`, a connector tag). With `all`, every `speech` focus is origin `speech`. With a list, speech from a source not listed is origin `guest` and is treated like viewer chat. cohost knows the source of a line and not who spoke. A reminder counts because only an owner-prompted reply can set a timer, so it is the owner's request coming due, and it gets read-only tools because the note it carries was written by the model from text that may have come from viewers or from a tool result.

**Enforced twice.** cortex offers the model only the tools that are offered and that the origin allows; `tools` checks each request against its own catalog with the same table and refuses it with reason `origin_not_allowed` otherwise. A model can name a tool it was not offered, and cortex's check is on what it chose to publish. The facts that narrow a confirmation (`listed`, `round`) are carried by the request and applied by `tools`, so cortex can ask for confirmation to be skipped only by telling the truth about them, and a wrong value can only cost a confirmation, never remove one (Confirming an acting call).

**What the table does not decide.** A reply the owner prompted still carries viewer text in its prompt (the transcript, recalled chat), and a tool result of round 1 is in the prompt of round 2. The table decides who prompted the reply, not what the prompt contains. The barrier between that text and an action is the owner's confirmation of acting calls (Confirming an acting call); the alternatives are in Decisions & Alternatives.

**Mock markers.** The mock chat provider calls a tool when its marker `[mock-tool <name> {json}]` appears and the named tool is among those offered. It reads the marker only from the last paragraph of the reply's last user message (the closing nudge with the focus text), never from the transcript, a recalled memory, a viewer note or a tool result ([model-backends](../model-backends/model-backends-design.md) Mock provider). A viewer's marker in chat history does nothing; a viewer's marker as the focus of a chat-prompted reply fires only a tool marked `chat`. An injected speech line is the isolated stack's way to drive a call through cortex.

## The call pipeline

For each `tool.request` that passes the bus's validation the service runs these steps in order and publishes one `tool.result`.

1. **Look up.** The first refusal that applies, in this order, ends the request: the tool is not in the catalog (`unknown_tool`), is not enabled (`not_enabled`), is enabled and acting without its `acts` mark (`acts_not_allowed`), has no recorded hash (`not_approved`), has a hash that differs (`definition_changed`), is of a server that is `down` or `auth` (`server_down`), is not allowed for the origin (`origin_not_allowed`), or has arguments a built-in tool rejects or arguments that serialize to more than 64 KiB (`invalid_arguments`, TOOL-CALL-021). The arguments of an MCP tool are not validated against the server's schema by `tools`: the server owns that, and its error comes back as an `error` result.
2. **Admit.** At most `tools.max_concurrent` calls (default 4) hold a slot at once, a call waiting for confirmation included; a request beyond that is refused with reason `busy` at once, so nothing queues without a bound and at most `max_concurrent` confirmations are ever pending.
3. **Confirm.** A call that needs the owner's answer waits for it, for at most `tools.confirm_timeout_ms` (default 20000); `denied` and `unconfirmed` are refusals (Confirming an acting call).
4. **Call.** A built-in tool runs in-process; an MCP tool is a `tools/call` request to its server. The call is bounded by `tools.timeout_ms` (default 10000), counted from the moment the call is sent, which for a confirmed call is after the owner allowed it. When the time passes the call is abandoned (an MCP request is aborted and a cancellation is sent on a best-effort basis) and the result is `timeout`; an acting call that timed out after it was sent may have taken effect. A failure of the request or the session during the call is an `error` result of reason `unavailable` with a sentence the service wrote.
5. **Shape.** The result text is the tool's text: an MCP result's text parts joined by newlines, then one bracket pair per part that is not text, joined by a space and set after the text with a space, in order; when it has no text part and has structured content, the serialized structured content comes before the notes. The notes name each non-text part by its type when the type is `image`, `audio` or `resource`, and `other` for any other type the server gives, never the server's own string. The text is cut to `tools.max_result_chars` (default 1500) with a trailing `…` and `truncated` is set. A result the server flagged as an error is `error` with reason `tool_error`, its text kept. A tool failure that is the service's own (no credential for stream info, the memory service not answering) is `error` with reason `unavailable`. A refusal, a timeout and an unavailable tool carry a sentence the service wrote, never text from a server.
6. **Publish.** `tool.result` carries the status, the reason when there is one, the text, `truncated` when set, the duration in milliseconds from the moment the request was read, and `mock` in mock mode. The same event is the dashboard feed's row for the call.

The service never retries a call: a retry could repeat an effect, and a read the model still wants it can ask for again. It keeps no history of calls beyond the bus stream and its own log, which records the tool name, the origin, the status and the duration at `info` and never an argument, a result, a secret, or a server's URL userinfo or query string.

## Confirming an acting call

A call to a tool whose effect is `acts` waits for the owner's answer in the dashboard. The built-in `timer` never does: its only effect is the co-host speaking a reminder. A call skips the confirmation only when all of these hold: the tool's `confirm` mark is false; the request's origin is `dashboard`, or is `speech` with `listed` true (the owner named the source in a `tools.owner_sources` list; the value `all` never qualifies); its `round` is 1, so no tool result is yet in the prompt; and it is not `injected`, so a call driven by test injection always asks. In every other case, including a `confirm` mark that is absent, the confirmation is asked. The dashboard says so beside the mark, and says that a listed source covers everyone who speaks through it: a listed Discord source includes guests in that channel.

- **The pending call.** When a request has passed the look-up and admission and needs an answer, `tools` publishes `tool.confirm` with the request's `id`, the tool, its arguments, the origin and `expiresAt`, the moment the confirmation window ends (the moment the request was read plus `tools.confirm_timeout_ms`, in epoch milliseconds). The answer is a bus event too, `tool.answer` with the same `id` and `allow`, as the other request and reply pairs are. At most one bar is shown per pending call, and the pending calls are at most `max_concurrent`.
- **The dashboard.** It shows every pending confirmation wherever the owner is, not only in Settings: the tool's name, its arguments bounded and as plain text, the origin in words, a countdown, and Allow and Deny ([dashboard](../dashboard/dashboard-design.md) Confirming a tool call). The dashboard publishes `tool.answer` from a gated operator route.
- **One call only.** An answer is accepted only while its call is pending and only once. An answer for an unknown, finished or already answered `id`, or one that arrives after `expiresAt`, is ignored. The `id` is a fresh uuid per request, so an answer cannot be replayed against another call.
- **Outcomes.** Allow starts the call, whose own limit begins then. Deny is `refused` with reason `denied`. No answer by `expiresAt` is `refused` with reason `unconfirmed`, never `timeout`. cortex's wait covers the window and the call (cortex The tool loop), and its filler rule and status republishing cover the silence. A confirmation is asked whenever the reply's focus was injected: an injected focus carries no `listed` and no skip, so injecting never removes a confirmation.
- **Where it cannot arise.** Acting tools are not offered to a `reminder`, `chat`, `guest`, `vision` or `idle` reply, so those never reach a confirmation.
- **Mock mode** confirms by itself: an isolated stack has no dashboard click, so a mock call to a tool that acts runs at once. The result carries `mock`.

## MCP servers

A server is an entry of `tools.servers`: a name, an HTTP(S) URL, an optional header name and secret value (Settings) and an `external` mark. The service speaks the MCP protocol's Streamable HTTP transport only; there is no stdio server and no process is started.

- **Connection.** The service connects to every configured server when it starts, initializes a session, lists the server's tools and keeps the session. A server whose connection drops or whose request fails is reconnected with the shared retry-with-backoff ([shared-runtime](../shared-runtime/shared-runtime-design.md) Retry with backoff); until it answers, its tools stay in the catalog with their last known definitions, are not offered, and a call for a listed tool that arrives meanwhile is refused `server_down`. The service re-lists a server's tools when the server announces a change and at every `tools.catalog_ms`, so the catalog follows the server.
- **Why every server is connected.** The owner needs to see a server's tools before enabling any, so a server with no enabled tool is still connected and listed; no tool request reaches it.
- **Auth.** A server may carry one secret header: the header name is `tools.servers.<name>.header` (default `Authorization`) and the value is the secret `token`. The header is `Authorization` when the name is blank or absent; when the name is `Authorization` (compared without regard to case) the value is sent as `Bearer <token>`, and with any other header name the token is sent as written. A server that answers `401` or `403` is `auth`, which the heartbeat maps to a `down` dependency and which ends when a later reconnect succeeds. Nothing outside the connection itself carries a server's secret, the userinfo of its URL or its URL's query string: no event, catalog entry, log line, heartbeat detail, error text or config route (HLD tenet 7).
- **Credentials stay out of the URL.** A URL with userinfo (`user:pass@host`) fails the load naming `tools.servers.<name>.url`. A query parameter whose name looks like a credential (`key`, `token`, `api_key`, `apikey`, `secret`, `auth`, `password`, `access_token`) produces one load warning naming the server and the parameter, never its value, and a dashboard advisory, because `config.yaml` is returned by the open settings reads and a secret belongs in the header.
- **External.** A server is external when its host is off the LAN by the LAN rule or when the owner set `external: true`; a server on the LAN can itself forward requests to the internet (a web-search server is the usual case), which cohost cannot see, so the owner can force the mark. The mark decides the egress entry ([config](../config/config-design.md) Egress destinations).
- **Transport security.** The service sends the secret to the URL the owner wrote. A secret over a plain `http` URL to a host outside the LAN is reported in the server's `detail` ("credential sent without TLS"); it is not refused, because the owner decides what leaves their network (Egress).
- **Health.** A server with at least one enabled `tools.allow` entry naming it, listed or not, is a dependency of the heartbeat, `mcp.<name>`: `ok` while connected, `down` when not (an `auth` server included), `n/a` in mock mode; the other servers and the built-in tools keep working (HLD tenet 5). A server with no such entry has no dependency entry: its state is in the catalog and its row in the dashboard, and it does not degrade the service. The entry is the owner's enablement, so a server that has not yet listed its tools (for example one refused at initialize) still degrades the service. The heartbeat rule is in Health and lifecycle.
- **Client.** `services/tools/src/mcp.ts` is a small client written over `fetch` (no MCP SDK, no process): initialize, the initialized notification, `tools/list` with paging, `tools/call`, the cancellation notification and the optional GET stream for `notifications/tools/list_changed`. It declares an empty set of client capabilities (TOOL-MCP-021), so a server cannot ask it to sample a model, read roots or elicit input, and it answers no request a server sends it. Every request goes to the configured URL with `redirect: "manual"` (TOOL-MCP-013) and the secret header; a 3xx is an error for that request. A request that gets no answer within the setup timeout of 10 seconds (initialize and list only) is aborted (TOOL-MCP-014).
- **Answers and size.** A response body is read to 1 MiB and no further: past that the service stops reading and hangs up (TOOL-MCP-012). A tool call whose response is so cut ends `error` with reason `unavailable` and a sentence saying the server's response was too large; a `tools/list` that is cut fails the list, so none of its tools is listed, before `tools.max_tools_per_server` applies (TOOL-MCP-016). Nothing of a partial body is parsed or shown. A JSON or event-stream answer is taken only when its JSON-RPC id is the id of its request (TOOL-MCP-024); concurrent calls on one session each take their own answer (TOOL-MCP-025). A legacy `endpoint` event is never used to pick an address (TOOL-MCP-022). A resource link in a result is never fetched; it is reported by its type (TOOL-MCP-023).
- **Paging and list rules.** `tools/list` follows `nextCursor` for at most 50 pages and 10 000 entries; a repeated, non-string or over-limit cursor fails the list (TOOL-MCP-015). Within one list a name is taken once, the first definition (TOOL-MCP-017); a tool whose `inputSchema` is not an object is left out (TOOL-MCP-018); a non-boolean `readOnlyHint` gives the label `unlabelled` (TOOL-MCP-019); a non-string `title` is dropped (TOOL-MCP-020).
- **Calls and sessions.** A call is `tools/call` on the current session. When the call limit passes, the request is aborted and a cancellation naming the request id is sent best-effort; the server is not reconnected for it (TOOL-CALL-011, TOOL-MCP-028). A JSON-RPC error answer ends the call `error` with reason `tool_error` and keeps the session (TOOL-MCP-027). A failed request, a `404` for a session the server forgot, or an over-long body fails the call `unavailable`, marks the server `down` and reconnects it on a new session; the call is not retried (TOOL-CALL-012, TOOL-MCP-026). A `401` or `403` marks the server `auth`; the first reconnect after it waits one base delay, so `auth` shows until a later reconnect succeeds (TOOL-MCP-006).
- **Untrusted answers.** A server is untrusted. No text from a server reaches an event, a log line, a detail or a catalog entry except as a tool's description, title, schema and content, which the catalog cuts and the model reads as tool results. The sentences the service writes for failures are its own (TOOL-CALL-012).
- **Response size and redirects.** The transport follows no redirect (TOOL-MCP-013), and the secret header goes only to the configured URL.
- **Trust.** The tool descriptions and annotations come from a server the owner added; the owner approves each tool from its description and effect, and the approval is pinned (Pinned definitions).

**Web search** is not built in. It is an MCP server the owner adds, and it is the reference MCP tool: the dashboard flow, the marks and the tests exercise it. A search server normally labels its tool read-only, so enabling it needs the `enabled` mark only.

## Built-in tools

Four tools are built in. Each is disabled until the owner enables it.

**`clock`** (read). Any arguments are ignored. Returns the current time, the date, the weekday and the zone in `cohost.timezone`, as one sentence. The prompt's `## Now` block already carries the time at the start of the think; the tool answers a question asked after a long reply or a long wait.

**`stream_info`** (read). Optional argument `platform` (`twitch` or `youtube`). With it, the tool answers for that platform; without it, for every platform that has a channel or video configured. A platform's answer states whether the stream is live and, when it is, the title, the viewer count and how long it has been live, and for Twitch the category. The tool returns one result: `ok` when at least one platform answered, with a sentence in the text naming each platform that could not (the credentials or the channel or video missing, or its call failed), and `error` with reason `unavailable` only when no platform answered, including when none is configured. It uses the platform credentials the chat sense already holds: Twitch's Get Streams call for `chat.twitch.channel` with `chat.twitch.client_id` and an app access token the service obtains and refreshes with `chat.twitch.client_secret` (it holds no user token), and the YouTube Data API's video lookup for `chat.youtube.video`, read by the parser `@cohost/shared` shares with chat ([chat](../chat/chat-design.md) The video value), with `chat.youtube.api_key`. A platform's answer is cached for `tools.stream_info.cache_ms` (default 30000); a failed call is not cached. The dependencies `stream.twitch` and `stream.youtube` exist only while `stream_info` is enabled: `ok` after an answer, `down` after a failed call, `n/a` for a platform whose channel or video or credentials are missing. This is a platform connection, an intentional external integration and not egress (HLD tenet 8): what leaves is the channel or video id and the credential, to the platform's own hosts, and no chat text.

**`memory_lookup`** (read). Arguments `query` (text) and optional `k` (1 to 8, default 4). The service publishes `memory.recall.request` with a fresh `id`, the query and `k`, and waits for the `memory.recall.reply` with that `id` within the call's time limit; it never touches the database ([memory](../memory/memory-design.md); HLD tenet 1). It renders each memory as one line, `- (YYYY-MM-DD) <who>: <text>`, the date in `cohost.timezone`, with `who` through `speakerLabel` and the text through `boundText` at the limits of `viewer_text`. A reply that does not come is `error` with reason `unavailable`. The dependency `memory` exists only while `memory_lookup` is enabled. cortex already recalls for the focus on every reply; this tool is the model's own question, asked when the recalled memories were not the ones it needed.

**`timer`** (acts, needing no confirmation). Arguments `minutes` (an integer from 1 up to `tools.timer.max_minutes`, default 120) and `note` (required text, cut to 200 characters). A `minutes` that is not such an integer, or a `note` that is missing, not text or empty after trimming, is refused as `invalid_arguments`. It starts a timer and answers with a sentence saying when it will fire. At most `tools.timer.max_active` timers (default 5) run at once; a request beyond that is `error` with reason `limit`. Pending timers are kept in the Redis hash `<prefix>:tools:timers` (field the timer's `id`, value the JSON `{id, note, setAt, dueAt}` and nothing else), which only `tools` reads and writes, through the bus client's key calls; it holds at most `tools.timer.max_active` fields. A restart of the service loses no timer: on start it reads the hash, publishes `tool.timer` at once for each timer already due, oldest `dueAt` first, whatever its lateness, and keeps each other timer until its `dueAt`. A timer has no cancel and no list.

### How a fired timer reaches speech

When a timer runs out the service publishes `tool.timer` with the timer's `id`, `note`, when it was set and when it was due, and then deletes the timer from the hash. It is consumed only by salience ([salience](../salience/salience-design.md) Reminders), which keeps it as a **due reminder**. Lateness is measured from `dueAt`: salience marks a reminder more than `brain.salience.reminder_expiry_ms` (default 1800000, 30 minutes) past its `dueAt` as missed instead of speaking it, whether it arrives that late (a timer that came due while `tools` was down) or reaches that age while it waits. Within that time the next decision pass, after the mute flag, the busy gate and the cooldown and before it looks for anything new, publishes an `attention.focus` of kind `reminder` carrying the note, with reason `reminder` and a score of 1, so it clears the threshold; cortex replies to it as to any focus, and the reply is spoken through the same checks as every other reply. Salience keeps a reminder until its focus is published, so a failed publish retries at the next pass. Reminders salience holds are lost when salience restarts, with no trace; that loss is accepted, because a restart of salience is the owner's own act and the timer's promise is one reply long.

This is the whole path: `tools` has no way to publish `brain.say` or `brain.clause` and no way to reach cortex's think directly, so a timer cannot bypass the speaking gates (HLD tenet 4). It does not make `tools` a sense: a sense reports something about the world and the brain decides what to do with it; a timer reports a promise the co-host made in an earlier reply, which comes due now. The service publishes no other input to the brain.

The note is text the model wrote from a prompt that may hold viewer text or a tool result, so cortex quotes it as untrusted text when it renders the prompt, like a result.

## Mock mode

`tools.mode` is `live` or `mock`. The isolated start of the unit (`TOOLS_MODE=mock`, [config](../config/config-design.md) Environment variables) sets `mock`; the heartbeat then reports `mode: mock` (HLD tenet 6). In mock mode the service opens no connection to any MCP server or platform, publishes no `memory.recall.request` and touches no Redis key:

- every configured server is `mock` in the catalog, and every `tools.allow` entry named `<server>__<tool>` for a configured server is a tool with the description `a mock tool`, an arguments schema that accepts any object, and the label its entry's `effect` key gives (`read`, `acts` or `unlabelled`; default `read`), offered under the same rules as a live tool except that a mock server counts as `ok` and no pin is checked, so the refusal of an acting tool without its mark, the order of acting calls and the confirmation rule are exercised in isolation;
- `clock` runs as in live mode; `timer` runs as in live mode except that its timers live in the service's memory and fire `tool.timer` when due, so an isolated stack observes the whole path; `stream_info` answers a fixed live stream (title `Mock stream`, 42 viewers, one hour); `memory_lookup` answers one fixed memory line;
- every `tool.result` carries `mock: true`, a call that would wait for a confirmation runs at once, and the same marks, origin rules, timeouts and result limit apply, so an isolated stack exercises the whole call path.

The service reads `tools.allow` in mock mode too: a mock tool exists only when the owner enabled it, so mock mode answers every allowed tool and invents none that was not allowed.

## Test injection

The unit's test input is `inject.request` with `target` `tools`, kind `text`, whose `text` is a JSON object `{"tool": "<name>", "arguments": {...}}` ([dashboard](../dashboard/dashboard-design.md) Test-input injection; [module-contract](../module-contract/module-contract-design.md) Test inputs). The service runs the call through the pipeline above as an injected request with origin `dashboard`, round 1, `listed` false and `injected` true, publishes the `tool.result`, and answers `inject.result` with `ok` true and the status and duration as `detail`. `ok` means the call ran through the pipeline and a result was published, whatever its status: a refusal is a correct answer, so a default configuration, with no tool enabled, still answers its test input. Text that is not that JSON is `ok` false with a detail naming the problem. The dashboard route that publishes it always needs the control token, because an injected call can run an acting tool.

## Health and lifecycle

`services/tools/src/main.ts` runs on `runService`. The heartbeat has service `tools` and mode `mock` while `tools.mode` is `mock` and `live` otherwise. Its **state** is `ready` once the consumer group exists, whatever the state of the servers; afterwards it is `degraded` while any dependency is `down`, and `ready` otherwise. Its `deps` hold `mcp.<name>`, `memory`, `stream.twitch` and `stream.youtube` only for what an enabled tool uses. Its **detail** is one sentence built from these parts joined by `; `, in this order: the number of tools offered (`<n> tools offered`), `no tools enabled` when none is enabled, the name of each server whose dependency is `down` with `refused its credential` for an `auth` one, and `off LAN: <names>` for each external server. With no tool enabled the service is idle and not degraded, because nothing is missing that the owner asked for (HLD tenet 5).

The manifest entry (control-plane owns the manifest; the declaration is part of this segment's contract): a pnpm unit with group `tools`, default mode `fresh`, isolation preset `TOOLS_MODE=mock`, `config` listing `tools`, `cohost`, `chat`, `viewer_text` and `network`, `uses` listing `memory`, no pause, and the test input above. cortex and salience list `tools` among the sections they read, and cortex lists `tools` in its own `uses`, so the dashboard marks cortex as needing `tools` when `tools` is stopped. The Compose service has no profile and depends on Redis only: a service with nothing enabled costs a few megabytes and no account, and a profile would mean a tool the owner enabled silently never ran.

Shutdown, on the shared sequence, publishes a `refused` result of reason `shutdown` for each call in flight and each pending confirmation, then closes the MCP sessions and then the bus; pending timers stay in Redis.

## Egress

An MCP server is a configured destination: the arguments of a call are text the model wrote from the conversation. `egressDestinations` gives `tools` one entry per configured server in live mode, with data `text` and the host of the server's URL, and `offLan` true when the server is external (off the LAN by the rule, or marked `external`), so an owner who adds a server outside the LAN, or a LAN server that forwards on, is told so; the dashboard also says that cohost cannot see what a LAN server itself sends on ([config](../config/config-design.md) Egress destinations). `tools` logs one warning at start for each entry that is off the LAN and names the server and host in its heartbeat detail. Stream info has no entry: it is a platform connection (above). No tool or server is configured by default, so nothing leaves the LAN until the owner adds one (HLD tenet 8).

## Decisions & Alternatives

| Decision | Chosen | Alternatives Considered | Rationale |
|----------|--------|------------------------|-----------|
| Catalog delivery | `tools` publishes a `tool.catalog` snapshot when it changes and every `catalog_ms`; consumers hold the latest and treat it as stale after three intervals | A catalog request and reply per think; cortex reading the `tools` section and the servers itself; the dashboard asking per page load | A per-think request would add a wait to every reply, and a full wait whenever `tools` is down; a snapshot costs the live path nothing and the staleness rule is also the "tools down, answer without tools" test. cortex reading the servers would make it hold connections (tenet 1). |
| Discovery before saving | The owner saves the server first; the service then lists its tools and the dashboard shows them | Probe a URL from the dashboard before it is saved | A probe needs the token, which would travel on the bus or through a route that is not the write-only secret route (HLD tenet 7). Saving first costs one restart of `tools`. |
| Tool settings | One flat map `tools.allow` keyed by model-facing tool name, three booleans each | Settings nested under each server; a list of enabled names plus separate lists for the marks; per-server defaults | Built-in and MCP tools share one shape and one place; a tool the owner enabled that no server lists stays visible as unknown; no tool is enabled by absence. |
| Effect and the acts mark | A tool is read-only unless the owner marked it; a tool that its server does not label read-only is refused without the mark; the mark and the chat mark exclude each other | Trust the server's label alone; one mark `trusted`; refuse unlabelled tools outright | Most MCP servers label little; refusing them outright would exclude servers the owner chose, while trusting a missing label would let an unknown tool act. The owner's explicit mark is the only thing that lets a tool change something, and it is never combined with chat. |
| Who can cause a call | Origin classes derived from the focus, injected or not: `speech`, `dashboard` and `reminder` are the owner's; `chat` needs the tool's `chat` mark; `vision` and `idle` allow none | Owner identified by speaker name or id; every origin allowed; chat-marked tools usable from any origin | The focus is what cortex has, and a vision or idle reply has no person to authorize it. Identifying the owner's voice needs a speaker identity ears does not have. |
| Enforcement | cortex offers only the eligible tools and `tools` refuses an ineligible request | Cortex only; `tools` only | A model can name a tool it was not offered, and an offer rule alone would trust cortex's filter; refusing alone would offer the model tools it can never use. |
| Name format | `<server>__<tool>`, with server names that hold no underscore; built-ins bare | A prefix with a dot; a server-unique hash; bare names with clash detection | The model backends accept only `[A-Za-z0-9_-]{1,64}`; the double underscore is unambiguous and readable in the feed. |
| Timer path to speech | `tool.timer` goes to salience, which publishes an `attention.focus` of kind `reminder`; cortex replies as to any focus | `tools` publishes `brain.say` with the note; `tools` publishes `attention.focus`; cortex holds the timer and thinks when it fires; a canned reflex line | `brain.say` from `tools` and a self-started think in cortex would each be a new path to speech that bypasses the gates (HLD tenet 4). `tools` publishing `attention.focus` would make it a second decider of when to speak. Through salience the gates apply unchanged and the co-host says it in its own words. A canned reflex would lose the note and the voice. |
| Reminder priority | Score 1, so the threshold is cleared; mute, busy and cooldown still apply; dropped after `reminder_expiry_ms` | Wait for the threshold like chat; bypass cooldown and busy; keep until spoken | A promise to speak should not depend on a chat score, and cooling down after a line is brief; but a reminder never talks over a line or past a mute, and a bound keeps a muted co-host from announcing a stale timer minutes later. |
| Timer control | No tool to cancel or list timers | A cancel tool; a list tool | A cancel tool needs a second acting tool and a timer id the model must keep (TOOL-TIMER-008). Persistence is the Redis-hash row below. |
| Where results are quoted | `tools` bounds and shapes; cortex quotes when it renders the prompt, under a notice for tool results | Quote in `tools`; neither | The prompt builder quotes each text exactly once (cortex Prompt and reply). The result text is bounded at the source so the bus and the stream stay small, whoever reads it, the dashboard included. |
| Retry | None | One retry on a transport failure | A retry can repeat an effect; the model can ask again within the reply's bounds. |
| MCP client library | A hand-written Streamable HTTP client over `fetch`: the four requests, the cancellation, the GET stream, with the caps and checks above | The official MCP TypeScript SDK; a stdio or process transport | The owner ruled no SDK: the protocol surface this service uses is small, and an SDK would bring a transport and client capabilities (sampling, roots, elicitation) the service must not offer to an untrusted server. Keeping the client here makes every cap, redirect rule and id check auditable in one file. |
| Stream info and egress | A platform integration with no egress entry; the MCP servers get entries | An egress entry for each platform; a new `data` kind | Stream info sends an id and a credential to the platform the chat sense already talks to and no conversation text, which is what tenet 8 excludes from egress; MCP arguments are conversation text. |
| Transport | Streamable HTTP only | stdio servers started in the container; both | A local process needs a runtime inside the image and the process lifecycle in the service (tenet 12 and the single Dockerfile). A server the owner wants local can run on the host and be reached by URL. |
| Confirming acting calls | A call to a tool that acts waits for the owner's Allow in the dashboard, in a window of its own (`tools.confirm_timeout_ms`, 20 s) before the call's 10 s; `confirm: false` skips it only for the owner's listed speech source or the dashboard, in round 1; the timer exempt | Trust the quoting; offer acting tools only for requests typed in the dashboard; an `acts` mark alone | Every prompt holds some viewer text, so quoting alone is the only barrier between a crafted chat message and an action; offering acting tools only to dashboard requests would make them useless for speech. A click is a barrier the model cannot cross. |
| Confirmation transport | `tool.confirm` and `tool.answer` bus events, the answer published by the dashboard from a gated operator route | A new HTTP route from the dashboard to `tools`; the answer on `tool.request` | The pair follows the other request and reply pairs and keeps `tools` off HTTP (tenet 1); HTTP between the dashboard and the browser is an operator API. |
| Pinned definitions | A hash of the approved definition in each `allow` entry; a changed definition is not offered | Re-list freely; compare only the effect label | A server can change a description or a schema, or flip `acts` to `read`, after the owner approved it, and the description reaches the model unquoted; the approval has to cover what the model will see. |
| Timers persist | In a Redis hash owned by `tools`; due timers fire at start | In memory only; a database | The settings apply by restart and a save of several sections restarts `tools`, so a promise must survive it; Redis is already there and the hash holds id, note and two times. |
| Reminder replies | Read-only tools only; held 30 minutes then marked missed | Any tool; 120 s | The note is model-written from possibly viewer-influenced text, and a reminder reply that could set a timer could re-arm itself. A longer hold keeps a timer that came due during a muted or busy stretch. |
| Final round | After `max_rounds` or the budget the round still carries the tools and any call in it is answered locally with an error; one more such round, then the reply ends | A round with no tool definitions | A request with tool history and no definitions can be rejected by a provider; the tool results stay valid in every request. |
| Tool catalog bounds | 32 tools per server, 64 in all, the rest left out and counted | Unbounded | The catalog travels the bus and the feed every interval and the model's context is finite. |
| Owner speech | `tools.owner_sources` is `all` by default; a list narrows it, and speech from an unlisted source is `guest`, treated like chat | No source counts by default; per-speaker identity from the connector | cohost knows the source of a line, not the speaker; guests in the owner's voice channel are people the owner invited; an acting call still needs the owner's confirmation, so a guest can at most cause a read-only lookup. Speaker identity needs ears to carry who spoke, which is not designed. |
| Acting tools and viewer text | The owner's confirmation of every acting call is the barrier | Trust the quoting; offer acting tools only for dashboard-typed requests; stop offering them after a tool result or when the transcript holds chat | See Confirming acting calls. |
| Game and OBS control | None in the built-in tools or this design; HLD Non-Goal 4 stands and game control is a deferred idea; an acting MCP server the owner adds is confirmed like any acting tool | Ship an OBS or game tool; forbid acting servers | cohost cannot know what an owner-added tool does beyond its label, which is why acting calls are confirmed; a prohibition it could not enforce would be false. |
| Round token cap | `tools.reply.max_tokens` (default 512) applies to a round that offers tools on every provider alike; a provider whose own default is larger is still sent this value | Keep `llm.max_tokens`; a per-provider value | One number the owner can reason about; the spoken length is bounded by the clause rules. |
| Tool arguments and results in the feed | Shown in full, bounded by `max_result_chars`, on the loopback dashboard; a connection from a LAN listener gets only the tool, the status and the duration | Full everywhere; an excerpt only; status only | The owner must see what a tool was asked and what it answered on their own screen; the LAN listener serves other machines and carries no tool text, as DASH-FEED-007 keeps viewer notes off `/ws`. |
| Compose profile | None: `tools` starts with the stack | A `tools` profile like the optional senses | A tool enabled in the dashboard should work after the restart the dashboard performs; the service needs no account or hardware. |
| Test input | `inject.request` to `tools`; `ok` means a result was published | A new event type for tool tests; a bus event JSON sample | The dashboard already injects through `inject.request`, and the pipeline's refusals are answers worth seeing. |
| Mock content | Deterministic fixed answers; enabled tools only; `read` effect | Scripted per test; every tool name answers | Matches the mock model provider's determinism; inventing tools the owner did not allow would defeat the allow-list in the mode that exists to test it. |

## Open Questions & Future Decisions

- **More tools.** Cancelling or listing timers, a calendar, and tools that need the owner's confirmation before they read are not designed. Controlling the game is not part of this design (HLD Future / ideal state).
