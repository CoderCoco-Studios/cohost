# control-plane specs

Specs for `packages/control`, `packages/bus/src/heartbeat.ts`, and the semantics the dashboard and compose consumers delegate to. Verified against the code at git `49ba935` (audit pass 2026-11-01); owner decisions of 2026-11-01 applied at git `1b57790`. `[x]` = implemented and observed in code, `[ ]` = intended but not yet implemented (gap), `[D]` = deferred (deliberately not provided). CTRL-HEARTBEAT-007 is retired (its statements are event-bus BUS-STREAM-004 and BUS-HEALTH-001); the number is not reused. Each `<!-- test: -->` pointer names the `test(` line that carries the matching `@spec` annotation; a line with no pointer has no direct test. Design context: [control-plane-design.md](control-plane-design.md).

## Service manifest (CTRL-MANIFEST)

- [x] **CTRL-MANIFEST-001**: The system shall define `SERVICE_MANIFEST` as the allow-list of exactly 15 controllable units: ten pnpm app services (`chat`, `salience`, `affect`, `memory`, `cortex`, `voice`, `avatar`, `eyes`, `ears`, `dashboard`), each with `composeName` equal to its id and `pnpmFilter` equal to `@cohost/<id>`, and five compose-only units (`redis`, `postgres`, `ollama`, `tts`, `stt`) that have no `pnpmFilter`. <!-- openspec: service-control § Manifest-only service ids --> <!-- test: packages/control/test/manifest.test.ts:6 -->
- [x] **CTRL-MANIFEST-002**: The manifest shall declare, per unit, the Redis consumer groups on `cohost:events` that a fresh start resets (`chat`, `salience`, `affect`, `cortex`, `voice`, `avatar`, `eyes` and `ears` each own a group of their own name; `memory` owns `memory` and `memory-recall`; `dashboard` and the compose-only units own none) and a default start mode of `fresh` for every pnpm service that owns groups except `memory` (`chat`, `salience`, `affect`, `cortex`, `voice`, `avatar`, `eyes`, `ears`) and `resume` for `memory`, `dashboard` and the compose-only units, so the control-plane default matches each service's bus subscribe start mode (`latest` for all but `memory`, which resumes). <!-- openspec: service-control § Start modes (resume vs fresh) --> <!-- test: packages/control/test/manifest.test.ts:28 -->
- [x] **CTRL-MANIFEST-003**: The manifest shall flag `redis` and `postgres` as `infra`, flag `dashboard` as `self`, and carry these isolation env presets applied by an isolated start: `chat` `CHAT_SOURCE=fake`; `memory` `MEMORY_STORE=memory` and `MEMORY_EMBEDDER=hash`; `cortex` `LLM_PROVIDER=mock`; `voice` `VOICE_ENGINE=stub`; `avatar` `AVATAR_DRIVER=null`; `eyes` `VISION_ENABLED=false`; `ears` `EARS_SOURCE=off`; every other unit an empty preset. <!-- openspec: service-control § Protected services --> <!-- test: packages/control/test/manifest.test.ts:28 -->
- [x] **CTRL-MANIFEST-004**: When `findService` is given an id that is not a manifest entry (including a crafted string such as `cortex; rm -rf /`), the system shall return `undefined`, so no request text can reach a runtime argv except by selecting a manifest entry. <!-- openspec: service-control § Manifest-only service ids --> <!-- test: packages/control/test/manifest.test.ts:39 -->
- [x] **CTRL-MANIFEST-005**: Every name in `KNOWN_SERVICES` (the health tracker's default known list) shall be the id of a `SERVICE_MANIFEST` entry. <!-- test: packages/control/test/manifest.test.ts:23 -->

## Runtime adapters (CTRL-RUNTIME)

- [x] **CTRL-RUNTIME-001**: When `ComposeRuntime` is asked to start, stop or restart a manifest unit, the system shall run `docker compose up -d <composeName>`, `docker compose stop <composeName>` or `docker compose restart <composeName>` through `execFile` with an argv array (no shell), a 120 s timeout and the configured `cwd`. <!-- openspec: service-control § Runtime interface and adapters --> <!-- test: packages/control/test/runtime.test.ts:19 -->
- [x] **CTRL-RUNTIME-002**: When `ComposeRuntime.restart` receives a non-empty env override, the system shall run `docker compose up -d --force-recreate <composeName>` instead of `restart`, and shall merge the override over the base environment of the spawned `docker` process. <!-- openspec: service-control § Runtime interface and adapters --> <!-- test: packages/control/test/runtime.test.ts:44 -->
- [x] **CTRL-RUNTIME-003**: If a `docker compose` command fails, then `ComposeRuntime` shall resolve `ok: false` with `detail` set to the trimmed stderr (else the error message), truncated to 500 characters, rather than throwing. <!-- test: packages/control/test/runtime.test.ts:54 -->
- [x] **CTRL-RUNTIME-004**: If `ComposeRuntime` or `ProcessRuntime` is asked to act on an id that is not in its manifest, then it shall resolve `ok: false` with an `unknown service` detail without executing or spawning anything. <!-- openspec: service-control § Manifest-only service ids --> <!-- test: packages/control/test/runtime.test.ts:33 --> <!-- test: packages/control/test/runtime.test.ts:111 -->
- [x] **CTRL-RUNTIME-005**: When `ProcessRuntime.start` is asked to start a pnpm service, the system shall spawn `pnpm --filter <pnpmFilter> dev` (or `start`; the script is the per-call `processMode`, else the constructor `mode`, else `dev`) with no shell, `detached: true`, `stdio: "ignore"` and the base env merged with the override env, resolve after the child's `spawn` event with `detail` `pid <n>`, track the child by id, and `unref` it. <!-- openspec: service-control § Runtime interface and adapters --> <!-- test: packages/control/test/runtime.test.ts:87 -->
- [x] **CTRL-RUNTIME-006**: If `ProcessRuntime.start` is asked for a compose-only unit, then it shall resolve `ok: false` and spawn nothing; if the id is already tracked it shall resolve `ok: true` with `already running` and spawn nothing; if the spawn emits an error it shall resolve `ok: false` and track nothing. <!-- test: packages/control/test/runtime.test.ts:101 --> <!-- test: packages/control/test/runtime.test.ts:111 --> <!-- test: packages/control/test/runtime.test.ts:119 -->
- [x] **CTRL-RUNTIME-007**: When `ProcessRuntime.stop` is called for a tracked service, the system shall send SIGTERM to the child's process group (falling back to the pid), escalate to SIGKILL if the child has not exited within `killTimeoutMs` (default 10 s) and wait up to 2 s more, drop the tracked entry when the child exits, and resolve `ok: true` with `stopped` or `killed (SIGKILL after timeout)`; a tracked child that has already exited shall resolve `ok: true` with `already exited` without signalling, and stopping an id with no tracked child shall resolve `ok: false`. <!-- openspec: service-control § Runtime interface and adapters --> <!-- test: packages/control/test/runtime.test.ts:129 --> <!-- test: packages/control/test/runtime.test.ts:140 --> <!-- test: packages/control/test/runtime.test.ts:150 -->
- [ ] **CTRL-RUNTIME-008**: When `ProcessRuntime.restart` is called, the system shall stop the service and then start it again; if no child is tracked for the id (the service is stopped or was started elsewhere), it shall start the service instead of failing. Gap: a restart with no tracked child returns the stop failure `not running under this process runtime (no tracked pid)` without starting (`packages/control/src/runtime.ts:154`, `runtime.ts:171-175`). <!-- test: packages/control/test/runtime.test.ts:160 -->
- [ ] **CTRL-RUNTIME-009**: Where `ComposeRuntime` starts or recreates a service with an isolation env preset, the system shall make that env visible inside the started container, through pass-through entries for every preset variable (`CHAT_SOURCE`, `MEMORY_STORE`, `MEMORY_EMBEDDER`, `LLM_PROVIDER`, `VOICE_ENGINE`, `AVATAR_DRIVER`, `VISION_ENABLED`, `EARS_SOURCE`) in the compose `x-ts-service` environment, written as `VAR: ${VAR:-}` so an unset variable still falls to the `${VAR:-default}` in `config.yaml`. Gap: the preset is only placed in the environment of the `docker compose` CLI process (`runtime.ts:61`), and `docker-compose.yml:11-20` (deployment segment) neither interpolates nor passes the preset variables through, so under the compose runtime an isolated start has no effect on the container. <!-- openspec: service-control § Runtime interface and adapters -->

## Controller guards and orchestration (CTRL-GUARD)

- [x] **CTRL-GUARD-001**: If `ServiceController` is asked to act on an id that is not in its manifest, then it shall return `refused: "unknown"` without calling the runtime, resetting any group or publishing an audit record. <!-- openspec: service-control § Manifest-only service ids --> <!-- test: packages/control/test/controller.test.ts:75 -->
- [x] **CTRL-GUARD-002**: If stop or restart is requested for a unit flagged `self` (the dashboard), then `ServiceController` shall return `refused: "conflict"` with detail `<id> cannot <action> itself` without acting, while a start of that unit shall be allowed. <!-- openspec: service-control § Protected services --> <!-- test: packages/control/test/controller.test.ts:86 -->
- [x] **CTRL-GUARD-003**: If an action targets a unit flagged `infra` (`redis`, `postgres`) and `advanced` is not set, then `ServiceController` shall return `refused: "forbidden"` naming `CONTROL_ADVANCED=1`; where `advanced` is set it shall execute the action and shall always use `resume` mode for infra, so no consumer group is reset. <!-- openspec: service-control § Protected services --> <!-- test: packages/control/test/controller.test.ts:94 -->
- [x] **CTRL-GUARD-004**: When a start is requested in `fresh` mode (the caller's `mode`, else the manifest `defaultMode`) for a unit that owns consumer groups, the system shall reset each group to `$` in manifest order and then start the service, and if a reset fails shall not start it and shall return `ok: false` with detail `consumer group reset failed: <reason>`. <!-- openspec: service-control § Start modes (resume vs fresh) --> <!-- test: packages/control/test/controller.test.ts:45 --> <!-- test: packages/control/test/controller.test.ts:125 -->
- [x] **CTRL-GUARD-005**: When a restart is requested in `fresh` mode (for a unit with groups) or with isolation env, the system shall stop the service, reset its groups only after the stop resolved `ok`, and then start it, returning the reset failure without starting if a reset fails; when a restart is requested in `resume` mode without isolation env it shall issue one native runtime restart and leave all groups untouched; a stop shall never reset groups. <!-- openspec: service-control § Start modes (resume vs fresh) --> <!-- test: packages/control/test/controller.test.ts:21 --> <!-- test: packages/control/test/controller.test.ts:28 --> <!-- test: packages/control/test/controller.test.ts:35 --> <!-- test: packages/control/test/controller.test.ts:45 --> <!-- test: packages/control/test/controller.test.ts:53 -->
- [x] **CTRL-GUARD-006**: Where an action carries `isolated: true` and the unit is not infra, the system shall pass a copy of the unit's manifest `isolatedEnv` to the runtime start, and shall replace a native restart with stop-then-start even when that preset is empty. <!-- test: packages/control/test/controller.test.ts:63 -->
- [x] **CTRL-GUARD-007**: When an action has been executed (not refused), the system shall call the controller's `audit` callback with `service`, `action`, `by`, `ok` and, whenever the runtime returned one (on success as well as failure), `detail`; it shall swallow any error the callback throws, and shall return only `ok` and `detail` to the caller. <!-- openspec: service-control § Lifecycle audit event --> <!-- test: packages/control/test/controller.test.ts:106 --> <!-- test: packages/control/test/controller.test.ts:116 -->
- [ ] **CTRL-GUARD-008**: Where an isolated start of a unit is requested, the system shall also start the units named in that unit's manifest `requires` list, transitively (for cortex: salience and affect), and nothing else; a start that is not isolated shall start only the named unit. Gap: the manifest has no `requires` field and the controller starts only the named unit (`packages/control/src/manifest.ts:39-55`, `controller.ts:73-99`); the OpenSpec cortex requirement "Isolation preset and closure" (from `add-isolated-backends`) and `docs/plans/control-plane.md` §7.2 both assume the supervisor computes this closure. <!-- openspec: cortex § Isolation preset and closure -->
- [ ] **CTRL-GUARD-009**: When a restart in `fresh` mode or with isolation env is requested and the runtime's stop step reports that the service is not running, the system shall continue as for a start: reset the unit's groups (when fresh) and start it. Gap: the controller returns the stop failure without resetting or starting (`packages/control/src/controller.ts:91-93`), so under `ProcessRuntime` a fresh or isolated restart of a stopped service fails.

## Control configuration (CTRL-CONFIG)

- [x] **CTRL-CONFIG-001**: The system shall treat control as disabled unless `CONTROL_ENABLED` is exactly `1`, and if control is enabled with `CONTROL_TOKEN` unset or blank then `loadControlConfig` shall throw an error naming `CONTROL_TOKEN`. <!-- openspec: service-control § Enablement gating --> <!-- test: packages/control/test/config.test.ts:6 --> <!-- test: packages/control/test/config.test.ts:12 -->
- [x] **CTRL-CONFIG-002**: Where control is enabled, `loadControlConfig` shall default `bind` to `127.0.0.1` (with `bindExplicit` false unless `CONTROL_BIND` is non-blank), `runtime` to `compose` and `processMode` to `dev`, shall set `advanced` only when `CONTROL_ADVANCED` is exactly `1`, and shall throw if `CONTROL_RUNTIME` is not `compose` or `process` or `CONTROL_PROCESS_MODE` is not `dev` or `start`; `isLoopback` shall accept `localhost`, `::1` and any host starting with `127.`. <!-- openspec: service-control § Enablement gating --> <!-- test: packages/control/test/config.test.ts:18 --> <!-- test: packages/control/test/config.test.ts:24 -->
- [x] **CTRL-CONFIG-003**: When `bearerOk` is given an `Authorization` header, the system shall accept it only if it has the form `Bearer <token>` and the token equals the configured secret under a constant-time comparison of SHA-256 digests, and shall reject a missing header, another scheme, an empty bearer value or an empty configured token. <!-- openspec: dashboard (add-service-control) § Bearer token on mutating routes --> <!-- test: packages/control/test/config.test.ts:32 -->

## Heartbeat contract (CTRL-HEARTBEAT)

- [x] **CTRL-HEARTBEAT-001**: When `startHeartbeat` builds a heartbeat, the system shall set `service` from the options, `instance` to the bus consumer name, `pid` to the process pid, `version` to the option, else `COHOST_VERSION`, else `dev`, `startedAt` to the module-load time of `heartbeat.ts` (constant for the process), `state` from the `starting`/`ready`/`degraded` base, `deps`, `mode`, optional `detail` and `intervalMs`. <!-- openspec: service-health § Heartbeat contract -->
- [x] **CTRL-HEARTBEAT-002**: When `startHeartbeat` is called, the system shall publish a `starting` heartbeat immediately, publish immediately on every `ready()` or `degraded(detail?)` call, and republish every `intervalMs`, where `intervalMs` is `HEARTBEAT_INTERVAL_MS` floored when it is a positive finite number and otherwise 5000. <!-- openspec: service-health § Heartbeat contract --> <!-- test: packages/bus/test/bus.test.ts:200 -->
- [x] **CTRL-HEARTBEAT-003**: While a heartbeat is running, the system shall re-read `deps` and `mode` (each may be a getter) at least once per second (every `min(1000, intervalMs)` ms) and republish at once when the state, deps, mode or detail differs from the last publication; when the base state is `ready` and any dep is `down` it shall publish `degraded` with detail `dependency down: <names>`. <!-- openspec: bus (add-service-health) § Heartbeat helper --> <!-- test: packages/bus/test/bus.test.ts:214 -->
- [x] **CTRL-HEARTBEAT-004**: When `stop()` is called, the system shall publish exactly one heartbeat with `state: "stopping"`, cancel both timers, ignore later `ready()`/`degraded()` publications, and make repeated `stop()` calls no-ops. <!-- openspec: bus (add-service-health) § Heartbeat helper --> <!-- test: packages/bus/test/bus.test.ts:231 -->
- [x] **CTRL-HEARTBEAT-005**: When `startHeartbeat` is called, the system shall register the heartbeat's `stop()` as a `beforeShutdown` hook, so that a SIGINT or SIGTERM handled through `onShutdown` publishes the `stopping` heartbeat before the service's own shutdown callback runs; the hook time limit, callback order and exit code are event-bus BUS-STOP-002. <!-- openspec: bus (add-service-health) § Heartbeat helper --> <!-- test: packages/bus/test/bus.test.ts:257 -->
- [x] **CTRL-HEARTBEAT-006**: If publishing a heartbeat fails, then the system shall log a warning (when a logger was supplied) and keep running without throwing into the service. <!-- openspec: bus (add-service-health) § Heartbeat helper --> <!-- test: packages/bus/test/bus.test.ts:244 -->
- [x] **CTRL-HEARTBEAT-008**: The system shall provide `tracked(fn, set)` which wraps an async call so `set(true)` follows a success and `set(false)` follows a failure while the error still propagates, so a service can feed a dependency status from real call outcomes. <!-- test: packages/bus/test/bus.test.ts:265 -->

## Health derivation (CTRL-HEALTH)

- [x] **CTRL-HEALTH-001**: When `HealthTracker` derives the state of a service that has never sent a heartbeat, the system shall report `unknown` (not `down`) with no heartbeat and zero restarts. <!-- openspec: service-health § Derived health states --> <!-- test: packages/control/test/health.test.ts:42 -->
- [x] **CTRL-HEALTH-002**: When a service's latest heartbeat is `stopping` or older than 10 times its `intervalMs`, `HealthTracker` shall report `down` (a `stopping` heartbeat immediately regardless of age), and when it is older than 3 times its `intervalMs` it shall report `stale`, using the latest heartbeat's own `intervalMs` and the tracker's receive-time clock. <!-- openspec: service-health § Derived health states --> <!-- test: packages/control/test/health.test.ts:25 --> <!-- test: packages/control/test/health.test.ts:35 --> <!-- test: packages/control/test/health.test.ts:69 -->
- [x] **CTRL-HEALTH-003**: When a service's latest heartbeat is fresh, `HealthTracker` shall report `degraded` if its `state` is `degraded` or `starting` or any dep is `down`, and `up` otherwise (`n/a` deps do not degrade). <!-- openspec: service-health § Derived health states --> <!-- test: packages/control/test/health.test.ts:17 --> <!-- test: packages/control/test/health.test.ts:49 --> <!-- test: packages/control/test/health.test.ts:62 -->
- [x] **CTRL-HEALTH-004**: While a service has at least 3 distinct `startedAt` values first seen within the last 60 s, `HealthTracker` shall report `crash-looping` in preference to every other state (including silence), and shall clear it once fewer than 3 such starts remain in the window; repeated heartbeats with the same `startedAt` shall not count as restarts. <!-- openspec: service-health § Crash-loop detection --> <!-- test: packages/control/test/health.test.ts:77 --> <!-- test: packages/control/test/health.test.ts:92 --> <!-- test: packages/control/test/health.test.ts:104 -->
- [x] **CTRL-HEALTH-005**: When `HealthTracker.snapshot` is called, the system shall return one `ServiceHealth` (state, latest heartbeat, `lastSeenAgeMs`, `restarts`) for each name in the known list (default `KNOWN_SERVICES`, the ten app services) plus any other service that has sent a heartbeat. <!-- openspec: service-health § Tracker snapshot --> <!-- test: packages/control/test/health.test.ts:112 -->
- [x] **CTRL-HEALTH-006**: When a heartbeat is ingested or `tick()` is called, `HealthTracker` shall notify its `onChange` listeners only if a service's derived state, restart count or heartbeat state/mode/detail/deps/instance differs from what was last notified, and shall never publish derived states to the bus. <!-- openspec: service-health § Derived health states --> <!-- test: packages/control/test/health.test.ts:126 -->
- [x] **CTRL-HEALTH-007**: When `HealthTracker.seed` is given history oldest-first, the system shall use each record's `ts` as its receive time, and shall not let a replayed older heartbeat overwrite a newer one already held for the same service. <!-- test: packages/control/test/health.test.ts:139 -->

## Container healthcheck (CTRL-CHECK)

- [x] **CTRL-CHECK-001**: When `isHealthy` is evaluated for a service, the system shall report healthy only if the newest heartbeat for that service among the supplied records exists, is not `stopping`, and its bus timestamp `ts` is less than 3 times its `intervalMs` before the local clock. <!-- openspec: service-health § Compose healthcheck --> <!-- test: packages/control/test/healthcheck.test.ts:13 --> <!-- test: packages/control/test/healthcheck.test.ts:18 --> <!-- test: packages/control/test/healthcheck.test.ts:25 -->
- [x] **CTRL-CHECK-002**: When `healthcheck.js <service>` runs, the system shall read `recentHealth(200)` and exit 0 if healthy and 1 otherwise, shall exit 2 with a usage message when no service argument is given, and shall exit 1 if the run takes longer than 4 s or throws. <!-- openspec: service-health § Compose healthcheck --> <!-- test: packages/control/test/healthcheck.test.ts:40 -->
- [x] **CTRL-CHECK-003**: Where a service is declared through the `x-ts-service` anchor in `docker-compose.yml`, the system shall run `node packages/control/dist/healthcheck.js $$SERVICE` as its container healthcheck every 10 s with a 5 s timeout, 3 retries and a 30 s start period. <!-- openspec: service-health § Compose healthcheck -->

## cohostctl command line (CTRL-CLI)

- [x] **CTRL-CLI-001**: When `cohostctl` parses its arguments, the system shall accept `status [service]` and `start|stop|restart <service> [--mode resume|fresh] [--isolated]`, and if the command is missing or unknown, a service name is missing for start/stop/restart, an extra positional is given, `--mode` is not `resume` or `fresh`, an unknown flag is used, or options are given to `status` or `stop`, then it shall print the usage text and exit 2. <!-- openspec: service-control § Optional cohostctl CLI --> <!-- test: packages/control/test/cli.test.ts:6 --> <!-- test: packages/control/test/cli.test.ts:15 --> <!-- test: packages/control/test/cli.test.ts:63 -->
- [x] **CTRL-CLI-002**: When `cohostctl status` runs, the system shall build a throwaway `HealthTracker` whose known list is the manifest's non-infra pnpm services, seed it from `recentHealth(200)`, print one row per service (name, state, heartbeat mode or `-`, last-seen age in whole seconds or `never`) and exit 0, and if a named service is not in the snapshot (that list plus any other service that has sent a heartbeat) it shall print `unknown service: <id>` and exit 1. <!-- openspec: service-control § Optional cohostctl CLI --> <!-- test: packages/control/test/cli.test.ts:63 -->
- [x] **CTRL-CLI-003**: When `cohostctl start|stop|restart` runs, the system shall delegate to `ServiceController` and exit 0 printing `<cmd> <id>: ok` (followed by ` (<detail>)` when the controller returned a detail) on success, and shall exit 1 printing `refused (<reason>): <detail>` for a refusal (unknown, conflict, forbidden) or `<cmd> <id> failed: <detail>` for a runtime failure. <!-- openspec: service-control § Optional cohostctl CLI --> <!-- test: packages/control/test/cli.test.ts:37 --> <!-- test: packages/control/test/cli.test.ts:45 --> <!-- test: packages/control/test/cli.test.ts:52 -->
- [x] **CTRL-CLI-004**: When `cohostctl` executes an action, the system shall record it by publishing `service.lifecycle` with `by: "cohostctl"` through the bus, shall select the runtime from `CONTROL_RUNTIME` (default `compose`; any other value than `compose`/`process` exits 2), and shall honour `CONTROL_PROCESS_MODE`, `CONTROL_ADVANCED=1` and `REDIS_URL`, without reading `CONTROL_ENABLED` or `CONTROL_TOKEN`. <!-- openspec: service-control § Lifecycle audit event -->
- [x] **CTRL-CLI-005**: When the module `cli.js` is the process entry script (its `argv[1]` ends with `cli.js`), the system shall run `main()`, always stop the bus connection in a `finally` block, and exit the process with the returned code; importing the package index from any other entry script shall run nothing.
- [D] **CTRL-CLI-006**: Where `cohostctl` uses the process runtime, the system shall be able to stop a service that a different invocation or the dashboard started. Deliberately not provided: tracked pids live only in the memory of the controlling process, and `README.md` (lines 331-332) documents this limitation and says to use the compose runtime instead. <!-- openspec: service-control § Runtime interface and adapters -->
- [ ] **CTRL-CLI-007**: If `CONTROL_PROCESS_MODE` is set to a non-empty value other than `dev` or `start`, then `cohostctl` shall print the same message `loadControlConfig` uses (`CONTROL_PROCESS_MODE must be "dev" or "start", got <value>`) and exit 2 without acting. Gap: the CLI maps every value other than `start` to `dev` silently (`packages/control/src/cli.ts:92,106`), while the dashboard's `loadControlConfig` throws (`config.ts:33`).
