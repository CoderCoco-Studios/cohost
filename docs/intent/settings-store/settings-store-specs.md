# settings-store specs

Prefix `STORE`. `[x]` = implemented and observed in code; `[ ]` = intended but not yet implemented (gap); `[D]` = deferred. A retired line keeps its number, says `Retired.`, and the number is not reused. Design context: [settings-store-design.md](settings-store-design.md). The `@cohost/store` package and its `config:*` tasks are built; a line stays `[ ]` while a clause of it depends on a consumer (the dashboard, the control plane, a service) that does not use the store yet.

## Package boundary (PKG)

- [x] **STORE-PKG-001**: `@cohost/store` shall be imported only by `services/dashboard`, `packages/control` and its own task entry points, and a test shall fail when any other package or service imports it, or when source under `services/` other than `services/dashboard` names a path under `<dataDir()>/store/` or the master key file. <!-- test: packages/store/test/store-boundary.test.ts -->
- [x] **STORE-PKG-002**: `@cohost/store` shall depend on `@cohost/config` and on no package outside the workspace and Node's standard library. <!-- test: packages/store/test/store-boundary.test.ts -->
- [x] **STORE-PKG-003**: A program that opens the store (the dashboard, `cohostctl`, the unit runner, the `config:*` tasks) shall register the store's `logging` section with `setLoggingSource` (config CFG-LOG-002) before its first log line, the dashboard before it calls `runService`; a message the store emits before that (the recovery-key notice excepted, which goes to standard output only) shall use the logging defaults.

## The database (DB)

- [x] **STORE-DB-001**: The store shall open its database with Node's built-in `node:sqlite` `Database` class, through one module (`packages/store/src/db.ts`) that no other module of the package bypasses, and a test shall fail when another file of the package imports `node:sqlite`. <!-- test: packages/store/test/store-boundary.test.ts -->
- [x] **STORE-DB-002**: When a program opens the store, it shall use `<dataDir()>/store/cohost.db`, create a missing `store` directory with mode 0700 and create the database with its WAL and shared-memory files under a umask of `0o077`, and where any of them grants a permission to group or other it shall log one warning naming the files and `chmod 600`, and where an existing `store` directory does it shall log one warning naming it and `chmod 700`, except on Windows and where the reported mode is `0777`. <!-- test: packages/store/test/store-db.test.ts -->
- [x] **STORE-DB-003**: When the store opens the database, it shall set `journal_mode=WAL`, `synchronous=NORMAL`, `foreign_keys=ON` and `secure_delete=ON`, and a busy timeout of 5000 ms in the control plane, the unit runner and the tasks and of 250 ms in the dashboard (STORE-SET-004).
- [x] **STORE-DB-004**: When the store opens an existing database, it shall run `PRAGMA integrity_check` and refuse the database as damaged, naming the file and the first reported problem, when the answer is not `ok` or `meta.schema_version` or `meta.store_id` is missing, and shall refuse it as newer, saying `the settings store is newer than this build: update cohost` and changing nothing, when `meta.schema_version` is greater than the newest version the build knows. <!-- test: packages/store/test/store-db.test.ts -->
- [x] **STORE-DB-005**: The store shall hold the tables `meta`, `sections`, `documents`, `secrets` and `keys` of the LLD § Tables, with one `sections` row per declared section path holding the keys the owner set as a JSON object, and the configuration assembled from all rows (a key a row does not hold taking its schema default) shall be what every reader of settings sees.
- [x] **STORE-DB-006**: Every committed write to any table shall increment `meta.revision` by one in the same transaction. <!-- test: packages/store/test/store-db.test.ts -->
- [ ] **STORE-DB-007**: When the store opens a database whose `meta.schema_version` is older than the build's, it shall take a backup (STORE-DB-008) and run every migration from that version in one transaction, setting `meta.schema_version`; if a migration fails, it shall roll back, leave the file as it was and refuse the store as damaged.
- [x] **STORE-DB-008**: When a backup is taken (at the dashboard's first start of a UTC day, before a migration, an import or a restore, and through `mise run config:backup`), the store shall write it with SQLite's online backup to `<dataDir()>/store/backups/cohost-<yyyymmddThhmmssZ>.db` with mode 0600 and then delete all but the ten newest files of that directory matching that name. <!-- test: packages/store/test/store-peek.test.ts --> <!-- test: services/dashboard/test/recovery-start.test.ts -->
- [x] **STORE-DB-009**: When a new store is created, the store shall write `meta.schema_version` 1, `meta.store_id` 16 random bytes in lowercase hex, `meta.revision` 0 and `meta.created_at`, and then seed it (STORE-IO-005). <!-- test: packages/store/test/store-db.test.ts -->
- [x] **STORE-DB-010**: The store shall give a program that opens it the configuration as `store.config()`: every stored section assembled and validated with `ConfigSchema` (null values dropped, no isolation override, no credential), the same typed `Config` a service's loader returns for its declared sections; the dashboard reads its `dashboard`, `renderer` and `logging` sections from it.
- [x] **STORE-DB-011**: When an import (STORE-IO-003) or a restore (STORE-TASK-005, STORE-TASK-006) completes, `meta.revision` shall be the live store's revision before it, plus one (one when the live store could not be read), whatever revision the imported or restored content carried, so no etag a client holds can match the new content. <!-- test: packages/store/test/store-db.test.ts --> <!-- test: packages/store/test/store-io.test.ts --> <!-- test: packages/store/test/store-cli.test.ts -->

## Keys and encryption (KEY)

- [ ] **STORE-KEY-001**: The master key file shall be `COHOST_KEY_FILE` when it is set and non-empty, else `$XDG_CONFIG_HOME/cohost/master.key` when `XDG_CONFIG_HOME` is set and non-empty, else `.config/cohost/master.key` under the user's home directory, and shall hold one line, `cohost-key-1:` followed by 32 bytes in base64url without padding; if `COHOST_TEST_ENV` is set and non-empty (the test environment, deployment DEPLOY-TOOL-022) while `COHOST_KEY_FILE` is unset or empty, resolving the key file shall fail with a message naming `COHOST_KEY_FILE` and the default path it refused, so no program run by a test reads or creates the owner's key file. <!-- test: packages/store/test/store-keys.test.ts -->
- [ ] **STORE-KEY-002**: When a program opens the store and the key file does not exist, and the store does not exist or holds no row in `secrets` or `keys`, the program shall create the key file's directory with mode 0700 when missing, write a new random key to a temporary file with mode 0600 in that directory and `link()` it to the key file's name, removing the temporary file either way; when the link fails with `EEXIST` it shall read the existing file, retrying for up to 2 s until it holds a well-formed key; when standard output is a terminal it shall write to standard output only, never through a logger or the bus, the key file's text as the recovery key with a sentence saying it is the only way to recover the stored credentials if the file is lost and should be kept in a password manager, and otherwise write only `a recovery key was created; run mise run config:key -- --show`, to standard error so that a redirected standard output never receives it, and set `meta.recovery_key_unconfirmed`. The tasks that open the store run with mise's `raw` mode (deployment DEPLOY-TOOL-024), so under `mise run` their standard input, output and error are the terminal mise was started from and the terminal rule above sees it. <!-- test: packages/store/test/store-keys.test.ts --> <!-- test: packages/store/test/store-cli.test.ts -->
- [x] **STORE-KEY-003**: If a program opens the store, the key file does not exist and the store holds at least one row in `secrets` or `keys`, then it shall create no key and refuse with a message that names the key file and the store, gives the number of stored credentials, lists the kept key files beside the key file (`master.key.rotated-…`, `.replaced-…`, `.discarded-…`) or says there are none, and names `mise run config:key -- --restore`, `mise run config:restore` and `mise run config:reset-credentials`; a restore (STORE-TASK-005) creates no key when the key file is missing. <!-- test: packages/store/test/store-keys.test.ts -->
- [x] **STORE-KEY-004**: The key id shall be the first 16 lowercase hex digits of HMAC-SHA256 keyed with the master key of the text `cohost/key-id/v1`; the store shall record it in `meta.key_id` when it first encrypts a value, and if the key file's id differs from `meta.key_id`, it shall refuse the key as STORE-KEY-003 does, naming both ids and never the key. <!-- test: packages/store/test/store-keys.test.ts -->
- [x] **STORE-KEY-005**: If the key file grants any permission to group or other, then the store shall refuse it naming the file and `chmod 600`, and if the key file's directory can be written by group or other, it shall refuse it naming the directory and `chmod 700`, except on Windows and where the reported mode is `0777`; a key file kept beside it (rotated, replaced or discarded) shall get mode 0600 and never overwrite another kept file. <!-- test: packages/store/test/store-keys.test.ts -->
- [x] **STORE-KEY-006**: The store shall encrypt every value of `secrets` and `keys` with AES-256-GCM under the master key with a new 12-byte random nonce per write and the associated data `cohost/v1|<store_id>|<table>|<path or name>`, storing the nonce, the 16-byte tag, the ciphertext and the key id, and if a value fails to decrypt it shall refuse the store as damaged naming the table and path, never a value. <!-- test: packages/store/test/store-keys.test.ts -->
- [x] **STORE-KEY-007**: When `mise run config:key -- --rotate` runs, it shall write a new key to a temporary file with mode 0600 beside the key file, re-encrypt every row of `secrets` and `keys` under it and set `meta.key_id` in one transaction, then keep the old key file as `master.key.rotated-<yyyymmddThhmmssZ>` with mode 0600, rename the temporary file over the key file, and show the new recovery key as STORE-KEY-002 does (to a terminal only, otherwise the pointer on standard error and `meta.recovery_key_unconfirmed`); if the transaction fails, the key file shall be unchanged and the temporary file removed, and if the rename fails after the commit, the error shall name the temporary file that holds the new key. <!-- test: packages/store/test/store-keys.test.ts --> <!-- test: packages/store/test/store-db.test.ts --> <!-- test: packages/store/test/store-cli.test.ts -->
- [x] **STORE-KEY-008**: When `mise run config:key -- --restore` runs, it shall read a recovery key from the terminal without echo, refuse it when it is not of the form of STORE-KEY-001 or its id differs from `meta.key_id`, and otherwise write the key file as STORE-KEY-002 creates it; `--show` shall print the key file's text. <!-- test: packages/store/test/store-keys.test.ts --> <!-- test: packages/store/test/store-cli.test.ts -->
- [x] **STORE-KEY-009**: When `mise run config:reset-credentials` runs and the owner types `delete credentials` at its prompt, it shall take a backup, delete every row of `secrets` and `keys` and remove `meta.key_id` in one transaction, create a new key as STORE-KEY-002 does and write a new random `keys.session` under it, and print that ears has no listener key until the next bearer check that succeeds (STORE-TOK-003) or the next `mise run config:token`; any other answer shall change nothing. <!-- test: packages/store/test/store-keys.test.ts --> <!-- test: packages/store/test/store-cli.test.ts -->
- [x] **STORE-KEY-010**: While `meta.recovery_key_unconfirmed` is set (STORE-KEY-002), the dashboard shall show a banner that a recovery key was created and has not been saved, naming `mise run config:key -- --show`, until the owner confirms it with `mise run config:key -- --confirm` (which clears the flag after printing the key once more) or the banner's "I have saved it" button, a gated request that clears the flag (dashboard DASH-RCV-029). <!-- test: services/dashboard/test/routes.test.ts -->

## The control token (TOK)

- [x] **STORE-TOK-001**: When `mise run config:token` runs, it shall generate a token of 32 random bytes in base64url, set it (STORE-TOK-002) and print it once to standard output with a sentence saying it is shown once and belongs in a password manager; with `--stdin` it shall read the token from standard input (asking for it without echo when standard input is a terminal, and otherwise reading it to its end), trim it and refuse, changing nothing, one shorter than 32 characters with a message that never includes it; with `--if-unset` it shall change nothing and say so when the store already holds a verifier. <!-- test: packages/store/test/store-token.test.ts --> <!-- test: packages/store/test/store-cli.test.ts -->
- [x] **STORE-TOK-002**: When the token is set, the store shall in one transaction write `meta.token_verifier` as JSON `{alg: "scrypt", N: 32768, r: 8, p: 1, maxmem: 67108864, salt, hash}` (a new 16-byte random salt and the 32-byte scrypt output of the token computed with `maxmem` 64 MiB, both base64url), replace `keys.session` with 32 new random bytes, and write `keys.ears-listener` as the listener key derived from the token as control-plane CTRL-RUNTIME-017 defines it; it shall store the token itself nowhere. <!-- test: packages/store/test/store-token.test.ts -->
- [x] **STORE-TOK-003**: When the store checks a presented bearer value, it shall compute its scrypt output with the stored salt and parameters and `maxmem` 64 MiB and compare it with the stored hash in constant time, running at most one such computation at a time with at most four checks waiting, a fifth failing at once as busy (the dashboard answers it 429 `{ok: false, detail}` with `retry-after: 1`); it shall remember in memory only the SHA-256 of at most four values that verified against the current verifier, accepting a remembered value without scrypt, and forget them all when `meta.token_verifier` changes; and when a value verifies while the store holds no `keys.ears-listener` (after STORE-KEY-009), it shall derive and store the listener key from that value. <!-- test: services/dashboard/test/service.test.ts --> <!-- test: services/dashboard/test/unlock.test.ts -->
- [x] **STORE-TOK-004**: The store shall give the dashboard the session key from `keys.session`, re-reading it when `meta.revision` has changed since it was read, so a token set while the dashboard runs ends every session at the dashboard's next check (dashboard DASH-UNL-005).
- [x] **STORE-TOK-005**: If `.env` (config CFG-ENV-010) or the process environment defines `CONTROL_TOKEN` with a value that is not empty after trimming, then the dashboard at start and the control plane before any `docker compose` command that starts a container shall refuse, naming `.env` or the environment and saying that the token belongs in the owner's password manager and is set with `mise run config:token -- --stdin`, never including the value; `mise run dashboard:unlock` is exempt and may read it from its own environment (dashboard DASH-UNL-007). <!-- test: services/dashboard/test/recovery-start.test.ts -->

## Settings writes (SET)

- [x] **STORE-SET-001**: The store shall export one write operation for settings, documents and credentials that every writer uses (the dashboard's routes, recovery, the `config:*` tasks, the import), and no writer shall issue SQL that changes those tables outside it.
- [x] **STORE-SET-002**: When a write runs, the store shall run it in one `BEGIN IMMEDIATE` transaction that applies the change, assembles the whole configuration, validates it with `ConfigSchema` after dropping null values (and the documents with their own schemas), and commits only when validation passes; otherwise it shall roll back and return every issue as `{path, message}` with no secret value. <!-- test: packages/store/test/store-write.test.ts -->
- [x] **STORE-SET-003**: Where a write carries an expected revision, the store shall compare it with `meta.revision` inside the write's transaction and, when they differ, roll back and return the current revision without applying anything. <!-- test: packages/store/test/store-write.test.ts -->
- [x] **STORE-SET-004**: When a write is blocked past the busy timeout, the store shall fail it with a message naming the store and that another program is writing, and apply nothing; in the dashboard, a write blocked past its 250 ms timeout shall be retried asynchronously (yielding the event loop between tries) after 50, 100, 200, 400 and 800 ms before it fails, so no request holds the event loop for more than 250 ms waiting on a lock.
- [x] **STORE-SET-005**: When a credential is written, the store shall trim it, refuse one that is empty after trimming or holds a control character (C0 or DEL), refuse a path outside `SECRET_PATHS` (config CFG-SEC-003) and a `tools.servers.<name>.token` whose server the stored `tools` section does not hold (a clear excepted), and encrypt it as STORE-KEY-006 states; clearing shall delete the row. <!-- test: packages/store/test/store-write.test.ts -->
- [x] **STORE-SET-006**: When a write removes a `tools.servers` entry, the store shall delete the token row of that server in the same transaction. <!-- test: packages/store/test/store-write.test.ts -->
- [x] **STORE-SET-007**: No result, error, issue message or log line of the store shall contain a credential, a key, the token or the scrypt hash. <!-- test: packages/store/test/store-write.test.ts --> <!-- test: packages/store/test/store-io.test.ts -->

## Projections (PROJ)

- [x] **STORE-PROJ-001**: A unit's projection shall hold exactly the stored sections the unit's manifest `config` lists and the documents its `documents` lists (module-contract MOD-MAN-016), and no credential, key or verifier.
- [x] **STORE-PROJ-002**: When a projection is written, the store shall write `data/projections/<composeName>/settings.json` under the workspace root (the directory Compose mounts, whatever `COHOST_DATA_DIR` says), as JSON `{format: 1, unit, revision, sections, documents}`, creating a missing directory with mode 0700 and writing through a temporary file in the same directory created with mode 0600 and renamed over the file, and shall remove each directory under `data/projections/` that names no unit; a `composeName` outside lower-case letters, digits and hyphens, or a projection directory that is a symbolic link, shall fail the write naming it.
- [x] **STORE-PROJ-003**: Before the control plane issues a `docker compose` command that creates, starts or restarts an application container (Launch, Rebuild, Restart all, a unit's start or restart, an isolated start, a `consolidate` or `reembed` run), it shall write every unit's projection from one read transaction, and if that fails it shall issue no command and fail the action with a message naming the file and the reason (control-plane CTRL-RUNTIME-014).
- [x] **STORE-PROJ-004**: When `mise run config:project` runs, it shall write every unit's projection and the `models` projection (STORE-PROJ-005), and exit 1 with the reason when that fails.
- [x] **STORE-PROJ-005**: The `models` projection shall hold the sections `ollamaModels` reads (config CFG-MODEL-001), from a list kept beside that function, and a test shall fail when `ollamaModels` reads a section the list lacks.
- [x] **STORE-PROJ-006**: When the dashboard saves the personality, it shall rewrite the projection of every unit that declares the `personality` document before it publishes `control reload_personality`. <!-- test: services/dashboard/test/routes.test.ts -->

## Credential delivery (DLV)

- [x] **STORE-DLV-001**: The control plane shall hand a unit its credentials only through the message of STORE-DLV-002, carried as STORE-DLV-003 (a container) or STORE-DLV-007 (a host-run program) states, and shall never put a credential, a key or the token in a command argument, an environment variable, a Compose file, a projection or any other file.
- [x] **STORE-DLV-002**: A unit's message shall be JSON of at most 64 KiB `{format: 1, unit, revision, credentials, state_key?}`, where `credentials` maps each secret path the unit declares and the store holds (the wildcard expanded to the servers of the stored `tools` section) to its value, plus `ears.http.verifier` from `keys.ears-listener` for the `ears` unit alone, and `state_key` is present exactly for a unit whose manifest entry sets `stateKey` (STORE-STATE-001); a unit that declares no secret path and no state key shall get no message.
- [x] **STORE-DLV-003**: When the control plane has run a `docker compose` command that may start containers, it shall deliver to every container of a unit that gets a message whose `State.StartedAt` (from `docker inspect`) differs from the value it read before the command (a container that did not exist counts as changed) or, for a unit with a recorded delivery, whose `StartedAt` or container id differs from that record (Docker restarted it since), and to a one-shot the container named by its `--name`, by running `docker exec -i <container> sh -c 'umask 077 && cat > /run/cohost/.credentials.json.tmp && mv /run/cohost/.credentials.json.tmp /run/cohost/credentials.json'` with the message on standard input; if the project's containers or their `StartedAt` cannot be read before the command (`docker compose ps` or `docker inspect` fails), it shall fail the action before running the command, naming the failure, and deliver nothing; it shall record each delivery's unit, container id and `StartedAt` in `data/control/deliveries.json` under the workspace root (mode 0600, no credential), rewriting the whole file through a temporary file in the same directory and a rename, since the dashboard and `cohostctl deliver` both write it, and if the exec exits non-zero it shall fail the action naming the unit and the exit status, never the message. <!-- test: packages/control/test/provision.test.ts -->
- [x] **STORE-DLV-004**: Where a service's unit gets a message, the shared runtime shall, before it loads the configuration, read the message from file descriptor `COHOST_CREDENTIALS_FD` to its end when that variable is set, and otherwise wait for `/run/cohost/credentials.json`, read it and delete it (shared-runtime SHARED-BOOT-009, SHARED-BOOT-010); it shall refuse a message whose `format` is not 1, whose `unit` is not its own, that holds a path its unit does not declare (`ears.http.verifier` for `ears` excepted) or a credential that is not a non-empty string, or that carries a `state_key` its unit's manifest entry does not set (or one that is not 32 bytes) and keep the credentials in memory only; while it waits, a service that publishes heartbeats shall publish them with state `starting` and reason `waiting for credentials`, and a one-shot that never opens the bus (`consolidate`, `reembed`) shall log that reason once.
- [x] **STORE-DLV-005**: When the dashboard starts, and afterwards while it runs and no lifecycle action holds the lock, it shall deliver as STORE-DLV-003 writes to every running unit that gets a message and either reports the heartbeat reason `waiting for credentials` or whose container's `StartedAt` differs from the one recorded for its last delivery, except that a unit with no recorded delivery whose latest heartbeat is `ready` is skipped (it already holds its credentials); `tts-pocket`, which publishes no heartbeat, is judged by `StartedAt` alone through the stack probe. It delivers at most once per container start, counting a waiting heartbeat as a new wait only when it arrives more than one heartbeat interval after its last delivery to that unit (so a heartbeat sent before the unit took the message leaves no second message unclaimed), and logs `delivered credentials to <unit>`. A unit that still waits past its Compose healthcheck's start period is unhealthy (control-plane CTRL-CHECK-001), so a Launch does not report it ready. <!-- test: services/dashboard/test/deliver.test.ts --> <!-- test: services/dashboard/test/service.test.ts --> <!-- test: packages/control/test/healthcheck.test.ts -->
- [x] **STORE-DLV-006**: The control plane shall deliver to `tts-pocket`, as STORE-DLV-003 writes the message and on the same triggers (STORE-DLV-003, STORE-DLV-005, control-plane CTRL-CLI-019), the file `/run/cohost/hf_token` holding the value of `voice.pocket.hf_token`, or empty when the store holds none, so the file is always written once the container is delivered to.
- [x] **STORE-DLV-007**: When `node packages/control/dist/run-unit.js <unit> [entry]` runs, it shall write the unit's projection, start `node <entry>` (default `services/<unit>/dist/index.js`) with the service directory as working directory, `CONFIG_DIR` set to the projection directory, `COHOST_CREDENTIALS_FD=3` and a pipe on file descriptor 3 when the unit gets a message, write the message to the pipe and close it, forward `SIGINT` and `SIGTERM` to the child, and exit with the child's exit status.
- [x] **STORE-DLV-008**: A test shall fail when a unit's message holds a path its manifest entry does not declare or lacks a declared path the store holds, when any message but `ears`' holds `ears.http.verifier`, or when any message holds the token or the master key.

## Unit state keys (STATE)

- [x] **STORE-STATE-001**: When the control plane builds the message of a unit whose manifest entry sets `stateKey: true`, it shall take `keys.state:<unit>`, creating it as 32 random bytes in the store when absent, and carry it as `state_key`.
- [x] **STORE-STATE-002**: When a service writes a credential it obtained at run time to a file under its data directory (chat CHAT-TW-011, avatar AVATAR-VTS-003), it shall encrypt the file's content with AES-256-GCM under its state key with a new random nonce and the associated data `cohost/state/v1|<unit>|<file name>`, write it with mode 0600 through a rename, and treat a file it cannot decrypt as absent, logging one warning naming the file.

## The reflection outbox (OUT)

- [x] **STORE-OUT-001**: When `reflect` would save the personality (memory MEM-REFLECT-007), it shall write to `<dataDir()>/memory/personality-outbox.json`, with mode 0600 through a rename, `{base, text}`, `base` the SHA-256 in hex of the personality text it read from its projection and `text` the whole new text, instead of writing any store.
- [x] **STORE-OUT-002**: When the unit runner's `reflect` child exits 0, or the dashboard starts, and the outbox exists, the program shall write its `text` as the `personality` document when the SHA-256 of the current document equals the outbox's `base`, then delete the outbox and rewrite the personality projections (STORE-PROJ-006); otherwise it shall keep the outbox and log a warning that the reflection's block was not applied because the personality changed. <!-- test: services/dashboard/test/recovery-start.test.ts -->

## Export and import (IO)

- [x] **STORE-IO-001**: The export format shall be one YAML document with `cohost_export: 1`, `settings` (the stored sections nested as the schema nests them), `personality`, `expressions` and, only when credentials are exported, `secrets` with `kdf` and `values`. <!-- test: packages/store/test/store-io.test.ts -->
- [x] **STORE-IO-002**: When `mise run config:export -- [file] [--secrets]` runs, it shall write the format to the file with mode 0600, or to standard output, with a comment listing the secret paths that are set and no value; with `--secrets` it shall read a passphrase of at least 12 characters twice from the terminal without echo, derive a key with scrypt (`N` 131072, `r` 8, `p` 1, `maxmem` 256 MiB, a new 16-byte salt) and write each value as `enc1:<nonce>.<ciphertext and tag>` in base64url, encrypted with AES-256-GCM with the path as associated data; it shall never export `meta.token_verifier` or a row of `keys`. <!-- test: packages/store/test/store-io.test.ts --> <!-- test: packages/store/test/store-cli.test.ts -->
- [x] **STORE-IO-003**: When `mise run config:import -- <file> [--dry-run]` runs, it shall parse the format, validate the result as STORE-SET-002 does, ask for the passphrase when the file holds `secrets`, and with `--dry-run` print what it would change (sections and documents added, changed or removed, and the secret paths it would set, never a value) and write nothing, comparing with a new seeded store in a temporary directory, and creating neither the store nor the key file, when no store exists yet; otherwise it shall take a backup and in one write replace every section, document and, when the file holds `secrets`, every credential with the file's, removing any the file does not hold; on any problem it shall write nothing and print each as `path: message`. <!-- test: packages/store/test/store-io.test.ts --> <!-- test: packages/store/test/store-cli.test.ts -->
- [x] **STORE-IO-004**: Where `config:import` is given `--settings`, `--personality`, `--expressions` or `--secrets` files instead of an export, it shall read the settings part as a mapping shaped like `settings`, the personality as text, the expressions as YAML and the secrets part as a plain mapping nested by secret path, import them as STORE-IO-003 does, replacing only the parts given, and after importing a secrets part print a reminder to delete that file. <!-- test: packages/store/test/store-io.test.ts --> <!-- test: packages/store/test/store-cli.test.ts -->
- [x] **STORE-IO-005**: When a new store is created, it shall be seeded by importing as parts `config/config.example.yaml`, `config/personality.example.md` and `config/expressions.example.yaml`, and the store shall be refused if the seed does not validate. <!-- test: packages/store/test/store-db.test.ts -->
